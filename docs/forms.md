# Управляемые формы OneBase — спецификация `.form.yaml`

OneBase описывает форму объекта декларативно: дерево элементов и обработчики
событий лежат в `<projectDir>/forms/<entity>/<name>.form.yaml`. Авто-генерация
по полям сущности по-прежнему доступна для тех объектов, у которых
управляемой формы нет — выбор за пользователем (см. раздел «Опциональность»).

## Файлы и каталоги

```
<projectDir>/
  forms/
    <entityLower>/
      <formLower>.form.yaml           # описание элементов
      <formLower>.form.os             # обработчики событий (опционально)
      <formLower>/
        _resources/
          <ElementName>/
            Picture.png               # бинарные ресурсы PictureField
            ValuesPicture.png
```

- Имена каталогов и файлов — в нижнем регистре, для совместимости с
  case-insensitive ФС.
- **Каталог обязателен и должен точно совпадать с именем сущности в нижнем
  регистре.** Это ИМЯ сущности из YAML (поле `name`), а не имя файла: если
  справочник лежит в `catalogs/counterparty.yaml`, но называется `Контрагент`,
  каталог формы — `forms/контрагент/`. Файл, положенный прямо в `forms/` или в
  каталог с другим именем, **молча не загружается**: сущность откроется
  авто-генерируемой формой, а файл не повлияет ни на что. `onebase check`
  предупреждает об этом кодом `form.not-loaded`.
- `.form.os` хранит DSL-процедуры, привязанные к события дерева
  (`ПриОткрытии`, `ПриИзменении`, и т. д.). Связь задаётся в YAML через
  поле `events`.
- `_resources/` нужны только если в форме есть `ПолеКартинки` со ссылкой
  на файл (для `stdpic:X` копии не нужны).

В режиме «конфигурация в БД» (см. `onebase migrate`) те же пути
адресуют записи в таблице `_onebase_config(path, content)`.

## Опциональность

Каждая сущность независимо выбирает режим формы:

| Состояние `forms/<entity>/` | Поведение в пользовательском режиме |
|---|---|
| **Каталог отсутствует**          | Старая авто-форма по полям сущности — без изменений. |
| **Есть `.form.yaml` объектной формы** | Карточка рендерится по YAML (маркер `◇ managed`). Авто-форма становится fallback. |
| **Есть `.form.yaml` с `kind: list`** | Список сущности показывает колонки по элементам этой формы, в их порядке. Без такой формы состав колонок берётся из `list_form` сущности, затем из `tile_view.fields`, затем — все поля. |
| **Несколько форм одного `kind`** | Берётся первая найденная. |

Это позволяет постепенно мигрировать большой проект: сначала навешиваем
managed-форму на один справочник, остальное продолжает работать.

Роль формы задаёт **`kind`**, а не её имя: `ФормаСписка` с `kind: object`
останется карточкой, и список сущности продолжит показывать все поля. В
конфигураторе вид выбирается при создании («Управляемые формы» → «Создать
форму» → «Вид формы») и меняется в конструкторе на вкладке «Форма».

Приоритет загрузчика реализован в `internal/project/loader.go:loadFormModules`.

## Структура `.form.yaml`

```yaml
schema: onebase.form/v1       # ОБЯЗАТЕЛЬНО. Других схем пока нет.

form:                         # Общие свойства формы.
  name: ФормаОбъекта          # ObjectForm | ListForm | ChoiceForm | произвольное имя.
  kind: object                # object | list | choice | folder | custom.
  entity: Контрагент          # имя сущности, к которой привязана форма.
  title:                      # локализованный заголовок (lang → текст).
    ru: "Карточка контрагента"
  original_id: "0"            # id корневого узла из 1С (опционально, для round-trip).
  auto_save_settings: true    # сохранять данные в настройки пользователя.
  vertical_scroll: auto       # auto | never | always.
  ref_card_button: false      # убрать 🔍 «Открыть карточку» у ссылочных полей формы
                              # (по умолчанию кнопка есть). Нужно плотным формам,
                              # повторяющим раскладку 1С: кнопка у каждой заполненной
                              # ссылки заметно расширяет строку. Ячейки табличных
                              # частей ключ не затрагивает — их рисует SlickGrid.

attributes:                   # реквизиты формы (живут отдельно от полей сущности).
  - name: Объект
    type: CatalogRef.Контрагент
    save: true
    main: true                # эквивалент <MainAttribute>true</MainAttribute>.
  - name: Товары
    type: ValueTable
    columns:
      - { name: Номенклатура, type: CatalogRef.Номенклатура }
      - { name: Цена,         type: "decimal(15,2)" }

commands:                     # команды формы.
  - name: Провести
    title: { ru: "Провести" }
    action: ПровестиКоманду   # имя процедуры в .form.os
    picture: stdpic:Post

command_bar:                  # авто-командная панель (необязательно).
  name: ФормаКоманднаяПанель
  visible: true
  buttons:
    - { name: КнПровести, command: Провести, representation: PictureAndText }

elements:                     # дерево UI. Порядок значим.
  - kind: ГруппаФормы
    name: Реквизиты
    title: { ru: "Реквизиты" }
    children:
      - kind: ПолеВвода
        name: ПолеНаименование
        title: { ru: "Наименование" }
        data_path: Объект.Наименование
        required: true
        hint: "Полное юридическое наименование"
        readonly_when: 'СтадияОформления = "Принята"'  # см. «Условная доступность»
        hidden_when: 'Тип <> "Обзвон"'
        events:
          ПриИзменении: НаименованиеПриИзменении

events:                       # form-level handlers (имя события → имя процедуры).
  ПриОткрытии: ПриОткрытииФормы
  ПередЗаписью: ПередЗаписьюФормы

resources:                    # ресурсы (заполняется автоматически при импорте).
  - { path: _resources/Логотип/Picture.png, element: Логотип, original_name: Picture.png }

conditional_formatting:       # условное оформление строк/ячеек табличных частей.
  - target: Товары            # имя ТЧ, ValueTable или элемента формы.
    when: Количество < 0      # DSL-выражение в контексте строки.
    field: Сумма              # опционально; пусто = вся строка.
    then:
      background: "#fee2e2"
      color: "#991b1b"
      bold: true

oneC_meta:                    # служебный блок, рантайм игнорирует.
  version: "2.20"
  unknown_xml: []             # base64-узлы XML без аналога в IR (для round-trip).
```

## Состав и доступность: пять точечных ключей

**`choice_folders`.** Подбор ссылочного поля всегда прячет группы иерархического
справочника. Там, где значение по смыслу и есть группа — населённый пункт в
адресном классификаторе, у которого есть улицы, — поле становится невыбираемым:
список пуст, а записанное значение платформа считает недопустимым. Ключ
возвращает группы в выдачу и в проверку записанного значения; на соседние поля
того же справочника он не влияет. Полю нужен уникальный стабильный `id` для
контекста подбора; без него `onebase check` отклоняет форму.

**`choice_dropdown: false`.** Выпадающий список ссылочного поля по умолчанию
несёт предзагруженную страницу вариантов. У большого справочника это вводит в
заблуждение: показаны произвольные первые N записей, и оператор выбирает из них,
не подозревая, что видит не весь список. С ключом в списке остаётся только
текущее значение, а выбор уходит в форму подбора.

**`editable_admin_only`.** Запрет по тому, кто смотрит, а не по данным записи
(этим он отличается от `readonly_when`). Вычисляется на сервере: поле приезжает
нередактируемым, ответ события формы держит запрет даже когда `readonly_when`
ложно, а присланное значение сервер отбрасывает до обработчика и при записи — у существующей
записи остаётся прежнее, у новой применяется объявленное `default:`. Это верно и
для событийного пути: обработчик, вызвавший `Объект.Записать()` у новой записи,
видит умолчание, а не пустое значение. Значения, которые считает
`ПриСозданииНового`, событие формы не пересчитывает — как и для любого другого
неприсланного реквизита. Поэтому ключ
допустим только у поля с `data_path` вида `Объект.<Реквизит>`: для
`Форма.<Реквизит>` и колонки табличной части серверный запрет не обеспечен,
поэтому `onebase check` отклоняет такое сочетание.

**`primary`** красит кнопку акцентным стилем — он нужен формам, где штатный ряд
«Записать / ОК / Закрыть» скрыт и единственное действие объявлено своей кнопкой.
**`scroll_x`** у горизонтальной группы заменяет перенос прокруткой: ряд кнопок,
разорванный пополам, читается как два разных блока. Оба ключа в неподходящем
месте `onebase check --lint` называет предупреждением — молча игнорировать
объявленный ключ он не должен.

## Зависимый подбор ссылочного поля

`choice_filter` ограничивает варианты одного ссылочного поля значениями другого.
Типичный пример: после выбора склада поле «Место хранения» показывает только места
этого склада. Условия задаются на `ПолеВвода`, которое ссылается на справочник:

```yaml
- kind: ПолеВвода
  name: ПолеСклад
  data_path: Объект.Склад
  choice: true

- id: inventory-storage-choice       # обязателен и уникален в пределах формы
  kind: ПолеВвода
  name: ПолеМестоХранения
  data_path: Форма.МестоХранения
  choice: true
  choice_filter:
    - field: Склад                    # реквизит справочника МестоХранения
      op: eq
      from: Объект.Склад              # текущее значение поля-источника формы
```

Условия идут в указанном порядке и соединяются через **И**. Допустимо от одного
до восьми условий:

- `op: eq` сравнивает ссылочный реквизит целевого справочника с `from`;
- `op: eq_or_empty` — то же сравнение, но оставляет и записи с **пустым**
  реквизитом: общие записи видны вместе со своими (запись без филиала — в
  документе любого филиала). Пустой `from` оставляет только общие записи, а не
  пустой список, как у `eq`. С глубоким источником `Объект.<Поле>.<Реквизит>`
  так работает только пустое ведущее поле; если запись в нём закрыта правами
  или не найдена либо её реквизит скрыт полевой политикой или пуст — выдача
  пустая, как у `eq`: иначе пустой список и список общих записей различали бы
  «реквизита нет» и «реквизит закрыт»;
- `op: in_hierarchy` включает элементы выбранной группы и всех её потомков;
- `op: not_in_hierarchy` — точное дополнение `in_hierarchy` для того же поля и
  источника: запись проходит, если её реквизит **не** лежит в поддереве группы
  (сама группа включена в поддерево). Запись с **пустым** реквизитом проходит:
  она ни в каком поддереве не лежит. Исключаемую группу пользователь обязан
  видеть: если её нет в базе или она закрыта правами (как и при пустом `from`),
  выдача пустая, а не весь справочник;
- `field: is_folder`, `op: eq`, `value: true|false` оставляет только группы или
  только элементы и работает лишь для иерархического справочника;
- `field: is_root`, `op: eq`, `value: true|false` выбирает записи верхнего
  уровня (без родителя) или вложенные записи иерархического справочника.
  Служебный признак действует, только если в справочнике **нет** реквизита
  `is_root` (без учёта регистра). Объявленный реквизит имеет приоритет:
  условие фильтрует его значение по обычным правилам его типа, в том числе
  в плоском справочнике. Для служебного признака `from` и `ref` недопустимы.
  В SQLite пустая строка родителя, оставленная импортом, тоже считается
  отсутствием родителя. Редактор формы проверяет синтаксис условия;
  `onebase check` проверяет его смысл по метаданным выбираемого справочника;
- `field: parent_id` — место самой записи в дереве **иерархического** справочника:
  служебная ссылка записи на её родителя в том же справочнике. К ней применимы
  операторы ссылочного реквизита: `op: eq` — непосредственные дети группы из
  `from`, `op: in_hierarchy` — записи, родитель которых лежит в поддереве этой
  группы, то есть записи строго внутри неё (саму группу условие не пропускает).
  У корневых записей родителя нет, они не проходят ни `eq`, ни `in_hierarchy`.
  `op: not_in_hierarchy` — всё, что не строго внутри группы: корневые записи и
  сама группа проходят. `from` обязан ссылаться на тот же справочник, в том
  числе через одну ссылку;
- `op: eq` с `value: true|false` у **булева реквизита** справочника — постоянное
  ограничение без источника на форме: «только немуниципальные адреса». Литералы
  других типов в контракт не входят: строка или число рядом с колонкой — это уже
  отбор, который пишется запросом, а не грамматикой подбора.
- `op: eq` у **строкового реквизита** справочника сравнивает его со строковым
  реквизитом записи за ссылкой, `from: Объект.<Поле>.<Реквизит>` (см.
  «Строковый конец пути» ниже).
- `field: <ТЧ>.<Колонка>`, `op: eq` — отбор по **табличной части** выбираемого
  справочника (см. «Отбор по табличной части» ниже).

### Отбор по табличной части

Связь «многие ко многим» лежит не в реквизите записи, а в её табличной части:
бренд обслуживает несколько направлений, и список этот — строки ТЧ
«Направления». `field` в виде `<ТЧ>.<Колонка>` отбирает записи, у которых в
табличной части есть **хотя бы одна** строка с нужной ссылкой:

```yaml
- id: brand
  kind: ПолеВвода
  data_path: Объект.Бренд
  choice_filter:
    - field: Направления.Направление   # ТЧ.Колонка справочника Бренд
      op: eq
      from: Объект.Направление
```

- Только `op: eq` и только **ссылочная** колонка; источник — `from` (в том
  числе за одной ссылкой) или `ref` той же сущности, на которую ссылается
  колонка. `value`, другие операторы, строковые колонки и несуществующие ТЧ или
  колонки `onebase check` отклоняет.
- Запись с двумя подходящими строками приходит один раз — и в выдаче, и в
  `total` (условие компилируется в `EXISTS`, а не в соединение).
- Пустой `from` — пустой подбор. Запись источника (`from` или `ref`), которой
  нет в базе или которую пользователь не видит (нет права чтения справочника
  колонки, строковый доступ), тоже даёт пустой подбор: иначе по UUID закрытой
  записи можно было бы узнать, у каких записей она стоит в табличной части.
  Строковый доступ (RLS) выбираемого справочника действует как всегда.
- Колонка под полевой политикой (`field_access` на `<ТЧ>.<Колонка>` или на ТЧ
  целиком) или с признаком `pii: true` закрывает условие: подбор пуст, иначе
  выдача рассказывала бы, есть ли у записи строка с этим значением. Как и у
  реквизитов шапки, явный `read: full` роли открывает, администратору маска не
  применяется.
- Условие соединяется с остальными через **И**, как любое другое.

Иерархический сценарий из #1303 задаёт оба ограничения явно:

```yaml
choice_filter:
  - field: Направление
    op: in_hierarchy
    from: Объект.Направление
  - field: is_folder
    op: eq
    value: false
```

Например, корневые группы адресного классификатора без вложенных городов:

```yaml
choice_filter:
  - field: is_root
    op: eq
    value: true
  - field: is_folder
    op: eq
    value: true
```

Всё, кроме архивной ветки «Неиспользуемые», — `not_in_hierarchy` с постоянной
ссылкой (см. «Постоянная ссылка `ref`» ниже):

```yaml
choice_filter:
  - field: parent_id
    op: not_in_hierarchy
    ref: "c976331e-6119-41c6-9e9e-a4e26fefd169"   # папка «Неиспользуемые»
  - field: is_folder
    op: eq
    value: false
```

Товарная группа из поддерева папки, указанной у направления, — `parent_id` с
источником за одной ссылкой (см. ниже):

```yaml
choice_filter:
  - field: parent_id
    op: in_hierarchy
    from: Объект.Направление.ТоварнаяГруппа   # папка того же справочника
  - field: is_folder
    op: eq
    value: false
```

### Постоянная ссылка `ref`

Третий вид источника — `ref: "<UUID>"`: постоянная ссылка на конкретную запись
справочника, на который ссылается `field` (для `parent_id` — самого
справочника). Нужна, когда условие от выбора пользователя не зависит: «причина
обращения — только из папки „Рабочие“».

```yaml
- id: ПолеПричинаОбращения
  kind: ПолеВвода
  data_path: Объект.ПричинаОбращения
  choice_filter:
    - field: parent_id
      op: in_hierarchy
      ref: "d4ba641c-70ae-4632-bf99-035f4caaa0af"   # папка «Рабочие»
    - field: is_folder
      op: eq
      value: false
```

- В условии ровно одно из `from`, `value` и `ref`. `ref` применим к ссылочному
  реквизиту и к `parent_id` с операторами `eq`, `eq_or_empty`, `in_hierarchy` и
  `not_in_hierarchy` (два последних требуют иерархический справочник ссылки); к
  `is_folder`, `is_root`, булеву и строковому реквизиту — нет.
- `onebase check` отклоняет пустой `ref: ""`, нулевой и неразбираемый UUID.
  Существование записи статически не проверить: UUID — данные базы, а не
  метаданные. У справочников, загруженных из одной 1С с исходными GUID, он
  совпадает во всех базах.
- **Записи с таким UUID нет или пользователь её не видит** (нет права чтения
  справочника ссылки, строковый доступ, запись удалена) — подбор пуст при
  **любом** операторе. Иначе пропавшая папка раскрыла бы весь справочник.
  Причины снаружи неразличимы: пустой подбор не рассказывает, существует ли
  запись.
- Значение берётся из метаданных формы. Браузер его не присылает и подменить
  не может, в контексте подбора `ref` не передаётся.

### Источник за одной ссылкой

`from` — явный путь из двух или трёх сегментов: `Объект.<Поле>` / `Форма.<Поле>`
(значение самого элемента формы) либо `Объект.<Поле>.<Реквизит>` /
`Форма.<Поле>.<Реквизит>` — **ровно один переход по ссылке**. Трёхсегментная
форма нужна там, где ведущее поле и отбираемый реквизит разного вида: у
выбранного Направления есть реквизит `ГруппаНеисправностей`, а фильтровать надо
неисправности по их собственной `Группе`.

```yaml
- id: Неисправность
  kind: ПолеВвода
  data_path: Объект.Неисправность
  choice_filter:
    - field: Группа
      op: eq
      from: Объект.Направление.ГруппаНеисправностей
```

Значение за ссылкой читает сервер, под правами пользователя: строковый доступ к
записи-посреднику и полевая политика её реквизита проверяются до отбора. Если
посредник не виден, реквизит закрыт маской, запись отсутствует или реквизит
пуст — выдача пустая, и все четыре причины выглядят снаружи одинаково. Значения
посредника в браузер не возвращаются: из формы приходит только ссылка ведущего
поля.

**Строковый конец пути.** Конец пути может быть и строковым реквизитом
посредника — тогда `field` тоже обязан быть строковым, а оператор — `eq`. Так
устроено подчинение в адресном классификаторе: дом ссылается на улицу не
ссылкой, а её строковым ИД в реквизите `ВладелецКод`.

```yaml
- id: ДомКлассификатор
  kind: ПолеВвода
  data_path: Объект.Дом
  choice_filter:
    - field: ВладелецКод
      op: eq
      from: Объект.Улица.ИД
```

Строку читает сервер с теми же проверками прав, что и ссылку; из формы
по-прежнему приходит только ссылка ведущего поля. Сравнение точное: регистр и
пробелы значимы, одинаково на SQLite и PostgreSQL. Пустое значение (или из
одних пробелов) у посредника даёт пустую выдачу, а не элементы с пустым
реквизитом. Двухсегментный источник для строкового `field` не
поддерживается: сравнивать строку со ссылкой нечего.

Пути глубже одного перехода и источники из строк табличной части не
поддерживаются: это срезы B2/B3 плана 183. Тип ссылки источника должен совпадать
с типом `field`, строковый конец пути — со строковым `field`; `onebase check`
проверяет весь контракт, включая уникальность `id`, длину пути, существование
реквизита посредника и совместимость видов.

Список обновляется сразу после изменения источника и после серверного события
формы. Если быстрые изменения отправили несколько запросов, применяется только
ответ для последнего состояния. Текущее значение сохраняется, когда сервер
подтвердил, что оно подходит, даже если его нет на первой странице результата;
если значение больше не подходит, поле очищается и отправляет обычное
`ПриИзменении`. При сетевой ошибке прежние варианты и значение остаются на месте,
поле помечается ошибкой — полный нефильтрованный справочник не подставляется.

### В форме обработки

`choice_filter` работает и в управляемой форме обработки (#1840). Владелец формы —
обработка: `Объект.<Поле>` — её **параметр** (`params` в YAML обработки),
`Форма.<Поле>` — реквизит формы, переход по ссылке — от параметра-ссылки.
Операторы и виды источников те же, что у формы документа:

```yaml
# processors/СозданиеЗадачи.yaml
params:
  - {name: Филиал, type: "reference:Филиалы"}
  - {name: Реклама, type: "reference:Реклама"}
# forms/созданиезадачи/объекта.form.yaml — kind: processor
- id: ПолеРеклама
  kind: ПолеВвода
  data_path: Объект.Реклама
  choice_filter:
    - {field: Филиал, op: eq_or_empty, from: Объект.Филиал}
```

Подбор такого поля принимается только от пользователя с правом запуска
обработки (`processor/<имя>/run`; недоверенной внешней — только администратору), в
остальном — тот же серверный путь: права чтения цели, RLS, маски, пустая выдача
без источника. `onebase check` проверяет `choice_filter` форм обработок тем же
контрактом, что форм документов и справочников.

Фильтр действует на интерфейс подбора, а не является правилом записи или
заменой прав доступа. REST, импорт и код могут записать другое значение; для
бизнес-инварианта добавьте серверную проверку. Сам endpoint подбора повторно
восстанавливает `field` и `op` из метаданных формы и применяет обычные права,
RLS, маскирование и строку поиска.

В визуальном конструкторе выберите ссылочное поле, задайте **«Устойчивый id
элемента»**, затем добавьте и расставьте условия в секции **«Зависимый подбор»**.
Пример есть в форме инвентаризации проекта `examples/trade`.

## Условная доступность элементов

`readonly_when` и `hidden_when` — условия по полям **записи**: пока условие
истинно, элемент нередактируем либо не показывается вовсе.

`readonly_when` **каскадирует на потомков** — так же, как статический
`readonly: true`. Условие на `ГруппаФормы`, `СтраницыФормы` или `Страница`
запирает всё, что лежит внутри, поэтому «после проведения вся группа реквизитов
замерзает» пишется одним условием на группе, а не копией на каждом реквизите.
Добавленное в группу поле подхватывает запрет само. `hidden_when` у контейнеров
работает по-прежнему и скрывает контейнер вместе со всем содержимым.

Итоговое состояние элемента — «постоянный запрет (свой или предка) ИЛИ истинное
условие (своё или предка)». Отсюда следует главное про сочетание: **ложное
условие предка не отпирает потомка со своим `readonly: true`** — постоянный
запрет конфигурации не снимается условием ни при каких обстоятельствах. Свой
`readonly_when` у потомка складывается с условием предка по «ИЛИ»: истинного
любого из них достаточно.

Если один элемент явно задаёт и `readonly: true`, и непустой
`readonly_when`, обычный `onebase check` выводит предупреждение
`form.readonly-conflict` с файлом формы и именем элемента. Выберите постоянный
или условный запрет; намеренно избыточную пару можно оставить — предупреждение
не блокирует проверку и не меняет поведение формы. Унаследованный запрет
предка вместе с условием потомка сам по себе эту диагностику не вызывает.

```yaml
- kind: ПолеВвода
  name: ПолеУлица
  data_path: Объект.Улица
  readonly_when: 'СтадияОформления = "Принята"'

- kind: Кнопка
  name: КнопкаПринять
  hidden_when: 'СтадияОформления = "Принята"'
  events: { Нажатие: КомандаПринятьНажатие }
```

Зачем: запрет, который живёт в бизнес-логике (хук `ПриЗаписи`, проверка в
модуле), без этого не виден на форме — поле выглядит редактируемым, а отказ
прилетает исключением уже при записи. Кнопка, недоступная в текущем состоянии,
точно так же должна не показываться, а не отвечать ошибкой на нажатие.

- Язык выражений — тот же, что у `when` условного оформления; в контексте
  доступны поля шапки записи.
- Условия пересчитываются при отрисовке **и после каждого события формы**.
  Что из пересчёта видно без перезагрузки:
  - `readonly_when` — в обе стороны: команда, изменившая состояние объекта,
    сразу замораживает поля, а переставшее выполняться условие сразу снимает
    запрет;
  - `hidden_when` — только в сторону скрытия. Элемент, скрытый **на момент
    отрисовки**, в разметку не попал, поэтому показать его обратно до
    перезагрузки страницы нечем.
  - Применяется это к элементам, которые несут якорь для пересчёта: поля ввода
    и кода, поля списка, даты, флажки, переключатели, кнопки, надписи, поля
    картинки и `КоманднаяПанель`. Для `hidden_when` якорь также есть у группы и
    отдельно стоящей страницы. У табличной части и набора `СтраницыФормы`
    (включая страницы внутри него) якоря нет — новое состояние видно после
    перезагрузки.
  - Каскада это ограничение не отменяет: состояние потомков целиком считает
    сервер, поэтому при **отрисовке** страницы табличная часть внутри
    замороженной группы уже нередактируема. Без якоря не работает только
    пересчёт на лету — если условие группы изменилось событием формы, новое
    состояние табличной части появится после перезагрузки.
- `hidden_when` не отрисовывает элемент вообще (вместе с детьми, если это
  группа или страница) — в том числе страницу внутри `СтраницыФормы`: скрытая
  вкладка не даёт ни кнопки, ни содержимого. Это управление интерфейсом, а не
  право доступа: ограничение доступа задаётся ролями (`permissions`,
  `row_access`, `field_access`).
- То же и про `readonly_when`, включая каскад. Отправку события формы сервер
  отклоняет по постоянному `readonly` (своему или контейнера-предка), а условие
  на эту проверку не влияет: кнопка под истинным `readonly_when` рисуется
  неактивной, но её обработчик достижим прямым запросом. Если действие должно
  быть недоступно, а не просто скрыто, проверяйте состояние в самом обработчике
  либо закрывайте его ролью.
- Условия `КоманднаяПанель` применяются к фактической автоматической панели,
  которую рисует обвязка формы: `readonly_when` отключает её кнопки, а
  `hidden_when` скрывает панель целиком. Служебная
  `СтраницаКоманднаяПанель` отдельного DOM-элемента по-прежнему не создаёт.
- Скрытую табличную часть браузер не отправляет, и запись формы это учитывает:
  прежние строки сохраняются, а не стираются пустым срезом. Так же ведут себя
  реквизиты шапки в скрытой группе и флажок: у флажка «ключа нет» само по себе
  значит «галка снята», поэтому запись отличает снятую галку от неотрисованного
  флажка по маркеру, который форма рисует рядом с каждым доступным на ввод
  флажком. Без этого скрытый (и точно так же нередактируемый по
  `readonly_when`) флажок сбрасывал бы реквизит в ложь при каждой записи.
- Ошибка вычисления условия не запирает элемент: условие игнорируется, а
  конфигуратор получает предупреждение на форме. Опечатка в **имени поля**
  ошибкой не считается (неизвестный идентификатор — пустое значение), поэтому
  условие с опечаткой просто никогда не срабатывает — как и в условном
  оформлении.

## Условное оформление

Форма принимает ключи `conditional` и `conditional_formatting`. Правило
применяется к строкам табличной части сущности или к формовому реквизиту
`ValueTable`; `target` можно указать как имя таблицы или как имя элемента формы.
В `when` доступны поля строки, значения шапки формы и служебные
`НомерСтроки`/`ИндексСтроки`. Если `field` не задан, стиль применяется ко всей
строке; если задан — только к этой колонке.

Поддерживаются свойства `color`, `background`, `bold`, `italic`. Цвета проходят
через CSS-фильтр безопасности; небезопасные значения отбрасываются.

Правила проверяются в порядке объявления, и действует **первое совпавшее**:
для каждой строки — первое правило без `field`, для каждой ячейки — первое
правило с её `field` (стиль строки и стиль ячейки независимы и могут
сочетаться). Позднее правило не перекрывает раннее.

В обработчиках `.form.os` можно менять оформление программно для текущего
round-trip события:

```bsl
Процедура Подсветить()
    ОчиститьОформление();
    ДобавитьПравилоОформления("Товары", "Сумма < 0", "Сумма", "#fee2e2", "#991b1b", Истина);
    ДобавитьПравилоОформления("Товары", "Количество < 0", "#fef3c7");
КонецПроцедуры
```

Сокращённая форма с тремя аргументами — `ДобавитьПравилоОформления(Цель,
Условие, Фон)` — оформляет всю строку; вместо цвета фона третьим/четвёртым
аргументом можно передать структуру стиля (`Фон`/`ЦветФона`, `Цвет`/`ЦветТекста`,
`Жирный`, `Курсив`, `Поле`).

`ОчиститьОформление()` сбрасывает правила на время ответа события, а
`ОчиститьОформление("Товары")` очищает только указанную табличную часть,
`ValueTable` или элемент формы. Изменения не записываются в YAML.

Runtime-правила действуют только на ответ текущего события: следующее событие
формы строит оформление заново из YAML. Чтобы подсветка не пропадала, вынесите
вызовы `ДобавитьПравилоОформления` в отдельную процедуру и вызывайте её из
каждого обработчика, который должен её сохранять.

## Типы элементов

| `kind`             | 1С эквивалент      | Описание                                                  |
|--------------------|--------------------|-----------------------------------------------------------|
| `ПолеВвода`        | `InputField`       | Поле ввода значения. Тип ввода зависит от `metadata.Field` |
| `ПолеСписка`       | `InputField` + `choices` | Выбор из декларативного списка значений (аналог `СписокВыбора`); рендерится `<select>` |
| `Надпись`          | `LabelField`       | Декоративная подпись                                       |
| `Кнопка`           | `Button`           | Кнопка действия                                            |
| `Флажок`           | `CheckBoxField`    | Чекбокс                                                    |
| `Переключатель`    | `RadioButtonField` | Radio-группа                                               |
| `ПолеКартинки`     | `PictureField`     | Поле с изображением (`picture: stdpic:X` или путь)        |
| `ТабличнаяЧасть`   | `Table`            | Табличная часть с колонками                                |
| `Колонка`          | `ColumnGroup`      | Колонка табличной части: задаёт состав/порядок показа и своё событие `ПриИзменении` |
| `ГруппаФормы`      | `UsualGroup`       | Группа (`<fieldset>`)                                      |
| `СтраницыФормы`    | `Pages`            | Закладки                                                   |
| `Страница`         | `Page`             | Одна закладка внутри `СтраницыФормы`                       |
| `КоманднаяПанель`  | `AutoCommandBar`   | Командная панель                                           |
| `КнопкаКП`         | `Button (CommandBarButton)` | Кнопка в командной панели                         |
| `ПолеКода`         | `TextDocumentField` | Многострочный редактор с подсветкой синтаксиса    |

Равные колонки: у горизонтальной `ГруппаФормы` ключ `equal_columns: true`
делит ширину строки поровну между непосредственными детьми — полями, кнопками,
флажками и вложенными группами. В конструкторе это флажок «Равные колонки».
Холст, предпросмотр и форма в «Предприятии» используют один режим раскладки.

```yaml
- kind: ГруппаФормы
  name: Реквизиты
  orientation: horizontal
  equal_columns: true
  children:
    - kind: ПолеВвода
      name: Артикул
      data_path: Объект.Артикул
    - kind: ПолеВвода
      name: Наименование
      data_path: Объект.Наименование
```

Минимальная ширина колонки — 180 px, промежуток — 12 px. При недостатке места
дети переносятся; каждая строка делит доступную ширину поровну, в том числе
последняя неполная строка. При ширине контейнера меньше 180 px колонка сжимается
до его ширины. Режим группы управляет шириной детей: их `width` и `halign`
уступают равным колонкам; `height` и `valign` сохраняются. Настройка не наследуется
вложенными группами. `scroll_x` несовместим с равными колонками: при его наличии,
вертикальной ориентации или другом виде элемента режим не включается, а `check`
выдаёт предупреждение `form.equal-columns`.

Без `equal_columns` (или с `false`) действует прежняя раскладка: обычные поля
горизонтальной группы имеют `flex: 0 1 260px` и `min-width: 180px`.

Фон контейнера: у `ГруппаФормы` необязательный ключ `background` задаёт цвет
фона группы (значение проходит проверку csssafe.Color — hex, `rgb(...)` или
именованный CSS-цвет; недопустимое значение `onebase check` назовёт
предупреждением `form.background-color`). У остальных видов элементов ключ
игнорируется, и check тоже об этом предупреждает (`form.background-kind`).

В YAML можно указывать и канонические 1С-имена — обе формы понимаются
загрузчиком; mapping_out при экспорте обратно нормализует в 1С-канон.

### Поле кода (`ПолеКода`)

Для полей, где правят не текст, а код или структурированные данные — правила
обмена, шаблоны, запросы, JSON/XML-настройки:

```yaml
- kind: ПолеКода
  name: КодПравила
  data_path: Объект.КодПравила
  language: bsl        # bsl | sql | json | xml | yaml | markdown | javascript | plaintext
```

Отличие от `ПолеВвода` с `multiline: true` — подсветка, номера строк и
моноширинный ввод. Редактор встроен в платформу (тот же, что в конфигураторе),
внешних загрузок нет: важно для офлайн-инсталляций и строгих CSP.

Поле остаётся рабочим без JavaScript: под редактором лежит обычная `textarea`,
и если скрипт не загрузился, пользователь правит значение в ней. У
`read_only: true` редактор не монтируется вовсе — `textarea` показывается
только для чтения.

⚠️ Ассеты редактора грузятся только на формах, где такое поле есть.

### Состав колонок табличной части (`Колонка`)

По умолчанию табличная часть показывает **все свои реквизиты** в порядке
объявления. Чтобы выбрать состав и порядок, вложите в неё элементы
`kind: Колонка`:

```yaml
- kind: ТабличнаяЧасть
  name: ТабТовары
  data_path: Объект.Товары
  auto_sum: true
  children:
    - kind: Колонка
      name: КолНоменклатура
      data_path: Объект.Товары.Номенклатура
    - kind: Колонка
      name: КолКоличество
      data_path: Объект.Товары.Количество
      events:
        ПриИзменении: КоличествоПриИзменении   # событие ЭТОЙ колонки
    - kind: Колонка
      name: КолЦена
      data_path: Объект.Товары.Цена
```

Правила:

- **Ни одной колонки-ребёнка = показать все реквизиты.** Так выглядят все формы,
  написанные до появления выбора состава; «ничего не выбрано» не значит
  «показать пусто».
- Реквизит сопоставляется по `data_path` (последний сегмент), затем по `field`,
  затем по имени элемента. Несопоставленную колонку `onebase check` отклоняет:
  молча она просто не появилась бы.
- **Невыбранный реквизит не исчезает из документа — он перестаёт
  показываться.** Значение по-прежнему уезжает на сервер при записи и остаётся
  в базе; убрать колонку с формы и продолжать заполнять реквизит проведением
  или обработчиком совершенно законно.
- Один реквизит нельзя разместить двумя колонками: в строке появились бы две
  ячейки с одинаковым именем, и какая победит — зависело бы от разбора.
- Виртуальные колонки (`virtual_columns`) идут после выбранных, их состав
  задаётся отдельно.

### Область просмотра в форме выбора

Диалог подбора показывает список представлений — этого мало там, где элемент
нужно ПРОЧИТАТЬ, а не узнать по названию: памятка по направлению обслуживания,
условия по тарифу, ограничения по складу.

Сущность объявляет, что показывать:

```yaml
# catalogs/НаправлениеОбслуживания.yaml
choice_preview: Информация          # реквизит, текст которого видно в подборе
```

Диалог становится шире и показывает справа от списка текст строки, на которой
стоит курсор (мышью и стрелками). У элемента без текста — прочерк: колонка не
исчезает, чтобы окно не прыгало. Справочник без `choice_preview` получает
прежний диалог без изменений.

Если реквизит объявлен как `richtext`, текст показывается **с оформлением**
(жирный, списки, абзацы); разметка чистится тем же санитайзером, что и остальной
richtext платформы.

### Текст, зависящий от контекста

Памятка бывает разной для разных филиалов, а диалог подбора сам по себе не знает,
для чего идёт выбор. Вызывающая форма передаёт это параметрами:

```yaml
# forms/обращение/ФормаОбъекта.form.yaml
- kind: ПолеВвода
  name: ПолеНаправлениеВыбор
  data_path: НаправлениеВыбор
  choice_context:
    Филиал: Объект.Филиал
```

Сущность указывает процедуру, которая собирает тексты страницы подбора:

```yaml
choice_preview_proc: ПриёмОбращения.ПамяткиДляПодбора
```

```bsl
// Один вызов на страницу подбора, а не на строку: полсотни строк — полсотни
// запросов на каждое нажатие в поиске.
Функция ПамяткиДляПодбора(Ссылки, Контекст) Экспорт
    Результат = Новый Соответствие;
    Филиал = Строка(Контекст.Получить("Филиал"));
    Для Каждого Ид Из Ссылки Цикл
        Результат.Вставить(Строка(Ид), ПамяткаПоПаре(Филиал, Ид));
    КонецЦикла;
    Возврат Результат;
КонецФункции
```

Процедура задана вместе с `choice_preview` — значения берутся у процедуры: она
знает про контекст, а реквизит нет. Формат при этом наследуется от объявленного
`choice_preview`: если он `richtext`, текст процедуры тоже показывается с
оформлением и чистится санитайзером. Без объявленного `choice_preview` текст
процедуры показывается как обычный. Ошибка в процедуре не ломает подбор: выбирать элемент
всё равно нужно, поэтому диалог остаётся с прежним текстом, а причина уходит в
лог сервера.

## События на колонке

`events` на элементе `kind: Колонка` срабатывает на правку **ячейки именно этой
колонки**. Поддерживается одно событие — `ПриИзменении`: строка добавляется и
удаляется не «в колонке», эти события объявляются на самой табличной части.

Обработчик колонки **не отменяет** обработчик табличной части. Если объявлены
оба, они выполняются последовательно: сначала колонка, затем `ПриИзменении`
таблицы, затем `ПриИзмененииСтроки`. Иначе событие, добавленное на колонку,
молча гасило бы уже работающий обработчик таблицы.

Контекст тот же, что у события ячейки таблицы: `ИмяТабличнойЧасти`,
`НомерСтроки`, `ТекущаяКолонка`, `ТекущаяСтрока`.

```
// @directive=&НаСервере
Процедура КоличествоПриИзменении()
    ТекущаяСтрока.Сумма = ТекущаяСтрока.Количество * ТекущаяСтрока.Цена;
КонецПроцедуры
```

> **События ячейки работают только в гриде.** При `no_grid: true` (простая
> таблица) их нет ни у колонки, ни у самой табличной части — `onebase check`
> сообщит об этом, чтобы обработчик не выглядел настроенным.

Живой пример — `examples/trade/forms/заказпокупателя/`.

### Списки значений (`ПолеСписка`)

`ПолеСписка` показывает `<select>` с произвольным списком значений, заданным
декларативно прямо в форме (аналог 1С `СписокВыбора`) — без перечисления и без
справочника. Значение хранится строкой в реквизите; выбор дёргает событие
`ПриИзменении`, поэтому обработчик в `.form.os` может подгрузить/показать связанные
данные:

```yaml
- kind: ПолеСписка
  name: ПолеВалюта
  data_path: Объект.Валюта      # реквизит сущности типа string
  choices:
    - value: RUB
      title: { ru: "Российский рубль", en: "Russian ruble" }
    - value: USD
      title: { ru: "Доллар США", en: "US dollar" }
  events:
    ПриИзменении: ВалютаПриИзменении
```

`value` — что записывается в реквизит, `title` локализует подпись (откат
`en→ru→value`). Рабочий пример — `examples/crm`, форма «Сделка», поле «Валюта».

**Динамический список (`НачалоВыбора`).** Если список зависит от данных и должен
строиться кодом, объявите обработчик `НачалоВыбора` — он наполняет список билтином
`ДобавитьЗначениеСписка(значение[, представление])`; пункты приходят на клиент и
заполняют `<select>` при получении фокуса. `choices` и `НачалоВыбора` можно
сочетать: статический список виден сразу, динамический обновляет его при фокусе.

```yaml
- kind: ПолеСписка
  name: ПолеВалюта
  data_path: Объект.Валюта
  events:
    НачалоВыбора: ВалютаНачалоВыбора
```

```bsl
Процедура ВалютаНачалоВыбора()
    ДобавитьЗначениеСписка("USD", "Доллар США");
    ДобавитьЗначениеСписка("EUR", "Евро");
КонецПроцедуры
```

### Отбор в подборе (связи параметров выбора)

Ссылочное поле показывает не весь справочник, а только подходящие элементы — как
«Связи параметров выбора» в 1С и так же без кода.

**Подчинённый справочник.** Если справочник объявил владельца (`owner: Контрагент`
в его YAML) и у объекта ровно один реквизит ссылается на справочник-владелец,
отбор ставится автоматически и берёт значение из этого реквизита. Если таких
реквизитов несколько, автоматический источник неоднозначен: задайте нужную
связь явно через `choice_filter` на ссылочном поле. Без источника владельца
автоматический отбор не ставится.

### Размер и выравнивание

`width`, `height`, `halign`, `valign` задают геометрию **внешнего блока**
элемента. Размер — в пикселях, а не в условных единицах 1С; ширина всегда
ограничена контейнером (`max-width: 100%`), поэтому на узком экране элемент не
уезжает за край.

```yaml
- kind: ПолеВвода
  name: ПолеИндекс
  data_path: Объект.Индекс
  width: 120                 # узкое поле под шесть цифр
- kind: ПолеВвода
  name: ПолеКомментарий
  data_path: Объект.Комментарий
  multiline: true
  height: 180                # textarea растянется на всю высоту блока
- kind: Кнопка
  name: КнопкаПечать
  halign: right              # прижать к правому краю
```

Что важно знать:

- **Ключа нет — раскладка прежняя.** Ноль и пустая строка ничего не меняют, форма
  без этих ключей рисуется ровно как раньше.
- **`height` растягивает сам ввод**, а не пустое место под ним: подпись сверху
  сохраняет свою высоту, остаток достаётся полю.
- **`valign` виден только там, где есть вертикаль** — то есть в группе с
  `orientation: horizontal`. В обычной (вертикальной) группе выравнивать элемент
  по вертикали не относительно чего.
- **`halign: stretch` старше `width`**: растянуть на контейнер и «ровно 200 px» —
  взаимоисключающие требования, побеждает растяжение, а `onebase check` о такой
  паре предупреждает.
- **Колонки формы делят ширину строки.** Вложенные группы горизонтальной
  группы — это колонки; по умолчанию они растягиваются на всю строку и
  сжимаются вместе с окном, а карточка управляемой формы занимает всю рабочую
  область, а не 1400 px. Так на широком мониторе справа от формы не остаётся
  пустого места в половину экрана. Заданный колонке `width` действует по
  общему контракту выше — это ширина её внешнего блока, и растягивание в
  свободное место она отменяет.
- **`ПолеКартинки` — исключение**: там `width`/`height` ограничивают саму
  картинку (как и до появления общего контракта), а `halign`/`valign` работают
  как у всех.
- **`ТабличнаяЧасть`**: `height` задаёт высоту таблицы вместо автоматической (она
  считается по числу строк), `width` — её ширину.
- **Своего блока нет у `Колонка`, `КоманднаяПанель`, `КнопкаКП`** — колонка
  описывает колонку таблицы, командная панель разворачивается в тулбар формы.
  Раскладку к ним приложить некуда, и `onebase check` об этих ключах
  предупреждает.

`onebase check` предупреждает о значении не из словаря (`halign: centre`),
отрицательном размере и размере больше 4000 px: рантайм такие значения
игнорирует, и без предупреждения это выглядело бы как «ключ не работает».

Конструктор форм показывает эти свойства в панели «Раскладка» и рисует их на
холсте и в предпросмотре так же, как нарисует рантайм.
### Обязательность: форма и метаданные

У `required` на элементе управляемой формы и у `required` на реквизите сущности
разный охват:

- `required: true` у элемента формы проверяет ввод именно через эту форму. Для
  редактируемого контрола, где нативная HTML-проверка соответствует типу данных,
  рендерится атрибут `required`; сервер в любом случае повторяет проверку при
  создании и изменении объекта — подмена POST-запроса или отключение браузерной
  проверки не позволяют сохранить пустое значение;
- `required: true` у реквизита в `catalogs/*.yaml` или `documents/*.yaml` —
  глобальный инвариант данных. Он действует для формы, REST, DSL и остальных
  путей записи и проверяется по финальному состоянию после автонумерации и
  обработчиков записи. Если такой реквизит шапки размещён отдельным элементом
  ввода в управляемой форме, форма автоматически показывает звёздочку, но не
  ставит нативный HTML-атрибут `required`: значение ещё может заполнить обработчик
  записи. Чтобы дополнительно запретить пустой submit до обработчика, укажите
  `required: true` на самом элементе формы. Для автоматически нумеруемого
  `Код`/`Номер` звёздочка также сохраняется, а браузер не требует ручного ввода.

Обратного переноса нет: галочка «Обязательное» в конструкторе формы не изменяет
метаданные сущности и не защищает импорт, REST или запись из DSL. Для
бизнес-критичных данных задавайте `required: true` именно у реквизита сущности;
отдельный ключ `not_null` в метаданных полей не поддерживается. Ноль и `Ложь`
считаются заполненными значениями. Элемент, доступный только для чтения, form-level
проверку не блокирует: пользователь всё равно не может его заполнить; глобальный
инвариант `Field.required`, если он задан, продолжает действовать.

Поле `Наименование` у справочника не становится обязательным неявно. Если оно
должно быть обязательным во всех путях записи, укажите `required: true` в
метаданных справочника.

### Маска: проверка и шаблон — разные ключи

`mask` и `input_mask` решают разные задачи и не заменяют друг друга:

```yaml
- kind: ПолеВвода
  name: ПолеШифр
  data_path: Объект.Шифр
  input_mask: "00.00.00"                  # что подставляется при наборе
  mask: '\d{2}\.\d{2}\.\d{2}'           # что считается верным при отправке
  hint: "6 цифр в формате 12.34.56"
```

`input_mask` форматирует ввод: набрали `123456` — в поле `12.34.56`. Точки
ставятся сами, лишние символы отбрасываются, вставка из буфера с чужими
разделителями раскладывается по шаблону. Висячий разделитель не дописывается:
после `12` в поле остаётся `12`, а точка появится вместе со следующей цифрой —
иначе ушедший с половины заполненного поля сохранил бы `12.`.

`mask` ничего не подставляет, это регулярное выражение в атрибуте `pattern`:
браузер по нему не даёт отправить форму. Два ключа можно задавать вместе, и
обычно так и нужно — шаблон помогает набрать, выражение не пускает неверное.

Оба ключа проверяются `onebase check`: шаблон в `mask` («00.00.00» как regexp
отвергает `12.34.56` и принимает `00X00Y00`) и регулярное выражение в
`input_mask` (символы `\`, `{`, `}` уехали бы в поле литералами).

### Accesskey

`accesskey` пробрасывается в HTML-атрибут одноимённого control-элемента
managed-формы: `Кнопка`, `ПолеВвода`, `ПолеСписка`, `ПолеДаты`, `Флажок`,
`Переключатель`.

```yaml
- kind: Кнопка
  name: КнопкаКопировать
  title: { ru: "Создать копию" }
  accesskey: "7"
  events:
    Нажатие: Копировать
```

Это именно стандартный браузерный `accesskey`: пользователь нажимает сочетание
с системным модификатором браузера/ОС (например, Alt/Option + клавиша).

### Hotkey

`hotkey` задаёт runtime-сочетание для кнопок managed-формы (`kind: Кнопка`).
Первый срез поддерживает bare F-клавиши `F2`, `F4`, `F7`, `F8`, `F9`, `F10`.
При нажатии клавиши браузер активирует кнопку тем же путём, что обычный клик:
вызывается обработчик события `Нажатие`.

```yaml
- kind: Кнопка
  name: КнопкаКопировать
  title: { ru: "Создать копию" }
  hotkey: F7
  events:
    Нажатие: Копировать
```

Если одна форма объявляет одну F-клавишу на нескольких кнопках, `onebase check --lint`
выдаёт предупреждение. `hotkey` на полях ввода не используется: для них нужен
`accesskey`. Платформенная `command_bar` остаётся отдельной runtime-задачей.

**Что реально вызывается управляемой формой** (остальные имена — задел и/или
маппинг импорта 1С):

- `ПриОткрытии` — на клиенте после рендера. То, что обработчик заполняет
  (умолчания нового объекта, поля рабочего места), — исходное состояние формы:
  изменённой её это не делает, как и в 1С. Изменённой форму делают правки
  пользователя и изменения данных другими событиями (кнопки, `ПриИзменении`);
- `ПриЧтенииНаСервере` — на сервере до рендера (RLS на чтение, может отказать);
- `ПриИзменении` — изменение поля (вкл. `ПолеСписка`), ячейки ТЧ и отдельной
  колонки (`kind: Колонка`, см. «События на колонке»);
- `ПриИзмененииСтроки` — правка ячейки с контекстом строки: «пересчитать эту
  строку» против «пересчитать форму» у `ПриИзменении`;
- `ПриАктивизацииСтроки` — переход на другую строку ТЧ;
- `ПослеДобавленияСтроки` — следом за `ПриДобавленииСтроки`; удобно разделять
  «заполнить значения по умолчанию» и «пересчитать итоги»;
- `Нажатие` — кнопки формы, командной панели и ТЧ;
- `ПередЗаписью` / `ПриЗаписи` / `ПослеЗаписи` — на сервере при сохранении: первые
  два до записи и могут отменить её через `ВызватьИсключение`, `ПослеЗаписи` —
  после (Объект уже с номером); серверные;
- `ПередЗакрытием` — перед закрытием управляемой формы крестиком, кнопкой
  «Закрыть», по Esc или программно. Обработчик может принять параметр `Отказ`
  (английский вариант — `Cancel`) и присвоить ему `Истина`, чтобы оставить
  форму открытой. Исключение и таймаут тоже оставляют форму открытой; сообщения
  и изменённые значения возвращаются в неё до решения. В обработчике доступны
  `ПричинаЗакрытия` / `CloseReason`: `cross`, `escape`, `close`,
  `programmatic` или `popup_cancel`. Закрытие самой вкладки браузера нельзя
  надёжно задержать асинхронным серверным вызовом, поэтому этот путь ограничен
  стандартным предупреждением браузера о несохранённых данных. Если пользователь
  меняет форму, пока сервер проверяет закрытие, старый ответ не применяется и
  форма остаётся открытой. После сети/таймаута неизменившийся запрос безопасно
  повторяет тот же intent; после штатного `Отказ` следующий клик выполняет новую
  проверку. «Записать» сохраняет и оставляет форму открытой; «ОК» и
  «Провести и закрыть» сначала проходят полный обычный save/post pipeline и лишь
  после успешной записи вызывают `ПередЗакрытием`. При изменённой форме обычное
  закрытие предлагает «Да / Нет / Отмена»: сохранить и проверить закрытие,
  проверить без сохранения либо остаться без HTTP-запроса соответственно.
  Диалоги в `ПередЗакрытием` недоступны: закрытие ждёт один ответ сервера, и
  второго хода (событий `Ответ`, `Выбор`) у него нет. `ПоказатьВопрос`,
  `ПоказатьПодбор` и `ОткрытьФорму` здесь — ошибка обработчика с объяснением,
  форма остаётся открытой; причину называйте через `Сообщить` и `Отказ`, а
  вопрос задавайте командой формы;
- `ПриДобавленииСтроки` / `ПриУдаленииСтроки` — строки ТЧ в гриде;
- `НачалоВыбора` — динамический список значений `ПолеСписка`
  (билтин `ДобавитьЗначениеСписка`);
- `Выбор` — диалог подбора (`ПоказатьПодбор`); имя `ОбработкаВыбора` из таблицы
  выше движок не вызывает, оно только принимает импорт из 1С;
- `Поиск` — строка поиска ОТКРЫТОГО диалога подбора, когда он объявлен
  `Конфиг.ПоискНаСервере` (см. ниже).
- `Ответ` — ответ на вопрос (`ПоказатьВопрос`): переменная `ВопросОтвет` несёт
  подпись нажатой кнопки (план 158 срез A, #1528).

### Диалог подбора ищет на сервере

По умолчанию строка поиска диалога `ПоказатьПодбор` фильтрует то, что УЖЕ приехало
на клиент: обработчик отдал строки одним куском, браузер их и перебирает. Этого
не хватает в двух случаях, и оба встречаются на первой же рабочей конфигурации:

- выдача ограничена пределом (`ВЫБРАТЬ ПЕРВЫЕ N`), а искомое осталось за ним —
  фильтр честно ищет среди показанных и не находит того, что не привезли;
- колонка показана **маской ПДн** (план 88): в тексте строки стоит `••••2233`,
  и искать по нему бессмысленно — значения в браузере просто нет.

`Конфиг.ПоискНаСервере = Истина` переводит строку поиска на сервер: набранное
уходит событием `Поиск` той же кнопке, обработчик получает текст в переменной
`ПодборЗапрос`, отбирает по нему и снова зовёт `ПоказатьПодбор` — клиент заменяет
строки в открытом окне, не открывая второго. Закрывать и открывать диалог заново,
чтобы поменять критерий, не нужно.

```bsl
// Фаза 1 — открыть диалог (событие Нажатие)
Процедура НайтиНажатие()
    Показать(ПодборЗаявок.Свежие());
КонецПроцедуры

// Повторная фаза 1 — оператор набрал в строке поиска (событие Поиск)
Процедура НайтиПоиск()
    Показать(ПодборЗаявок.НайтиПо(ПодборЗапрос));
КонецПроцедуры

Процедура Показать(Строки)
    Колонки = Новый Массив;
    Колонки.Добавить(Новый Структура("Имя,Заголовок,Тип", "Номер", "Заявка №", "string"));
    Конфиг = Новый Структура;
    Конфиг.Вставить("Заголовок", "Выберите заявку");
    Конфиг.Вставить("ПоискНаСервере", Истина);
    ПоказатьПодбор(Строки, Колонки, Конфиг);
КонецПроцедуры
```

Правила, о которых стоит знать:

- обработчик `Поиск` может читать данные, но запись из него запрещена: поиск
  отправляется отдельно от очереди событий записи формы, поэтому попытка
  `Объект.Записать()` или записи через менеджер завершится ошибкой;
- обработчик `Поиск` **обязан звать `ПоказатьПодбор`** и на пустой выдаче — тогда
  окно покажет пустой список. Если он ограничится `Сообщить` и вернётся, диалог
  очистит строки сам и напишет «Ничего не найдено»: оставить прежнюю выдачу нельзя,
  её прочитают как ответ на новый запрос;
- пустая строка поиска — такой же запрос («покажи всё»), `ПодборЗапрос` придёт
  пустым. Отличить его от первого открытия можно по самому событию: при `Нажатие`
  переменной нет вовсе;
- запрос уходит с задержкой 250 мс после последней буквы, а не на каждую, и
  в пределах одного открытия диалога в пути не больше одного поиска: набранное
  позже ждёт ответа на предыдущий. Ошибка отправки освобождает очередь, поэтому
  после временного сбоя можно искать снова;
- **выбор переживает смену выдачи**: отметили строки в одной выдаче, нашли по
  другому запросу, отметили ещё — «Перенести» отдаст всё вместе, а не только
  последнюю выдачу. Строки узнаются по идентификатору, правленые количества
  тоже сохраняются;
- при `ОдинВыбор` выбранная строка заменяет предыдущую и после нового поиска;
  клик по строке и клик по радиокнопке отправляют одну выбранную строку;
- закрытие диалога — «Отмена», «Перенести» или Esc — отменяет ожидание результата
  поиска: поздний ответ не откроет закрытое окно и не изменит новый подбор,
  даже если он вызван той же кнопкой;
- диалог, открытый **командой автопанели**, ищет ровно так же, как открытый
  кнопкой: событие `Поиск` уходит той же цели;
- отбор считает сервер, поэтому ПДн остаются на сервере: маска в колонке не мешает
  искать по полному значению.

### Диалог подбора: выбор двойным щелчком и отборы по колонкам

При `ОдинВыбор` строку можно выбрать, не дотягиваясь до кнопки «Выбрать»:

- **двойной щелчок** по строке выбирает её и закрывает окно;
- в строке поиска **↑/↓** переносят отметку по видимым строкам, **Enter**
  выбирает отмеченную, а если отметки нет — первую видимую. Набрал фамилию,
  нажал Enter — готово.

Мультивыбор так не делает: там двойной щелчок не отличить от двух щелчков по
флажку, а Enter оставлен строке поиска.

`Конфиг.Отборы` ставит над списком выпадающие отборы по колонкам — имена
колонок строкой через запятую или `Массивом`:

```bsl
Конфиг = Новый Структура("Заголовок,ОдинВыбор", "Выбор мастера", Истина);
Конфиг.Вставить("Отборы", "Направление,Филиал");
ПоказатьПодбор(Данные, Колонки, Конфиг);
```

- Строка поиска ищет **подстроку во всех колонках** и не отличает направление
  «СМ» от мастера «Смирнов». Отбор сравнивает значение колонки **целиком**.
- Значения отбора — то, что есть в приехавших строках, по алфавиту, первым идёт
  «Все». Отборы сужают друг друга: выбрали филиал — в списке направлений остались
  только направления этого филиала. Значение, которого больше нет среди
  подходящих строк, сбрасывается на «Все».
- Отборы и строка поиска действуют вместе: видна строка, подходящая под всё
  сразу.
- При `ПоискНаСервере` отборы применяются к выдаче сервера и переживают её смену;
  новое открытие окна начинает без отборов. Сервер значений отборов не получает:
  если выдача обрезана пределом, отбор выбирает только из привезённого.
- Имя колонки сверяется без учёта регистра. Колонки, которой нет в `Колонках`,
  или редактируемой колонки (количество) — ошибка обработчика, а не молча
  пропущенный отбор.

**Остальные имена из таблицы платформа принимает, но не вызывает** — их знает
конвертер 1С, их пропускает `onebase check`, а вызывающей стороны в движке нет:

<!-- ob:uncalled-form-events:begin -->
`ПриЗакрытии`, `ПриАктивации`, `ПриСоздании`,
`ОбработкаВыбора`, `ПередУдалением`, `ПриУдалении`, `ПослеУдаления`,
`ПередДобавлениемСтроки`, `ПередУдалениемСтроки`, `НачалоВыбораИзСписка`,
`АвтоПодбор`, `ВыполнитьКоманду`.
<!-- ob:uncalled-form-events:end -->

Список между маркерами сверяется с `metadata.UncalledFormEvents()` тестом
`TestUncalledFormEventsDocMatchesPlatform`: в день, когда событие реализуют, оно
исчезнет из перечня платформы, и тест напомнит вычеркнуть его отсюда.

Обработчик на такое событие пишется, проходит
проверку и не выполняется ни разу — «не работает, и ошибки нет». С версии,
закрывшей [#1153](https://github.com/ivanarama/onebase/issues/1153), об этом
предупреждает `onebase check` (код `form.event-not-dispatched`); ошибкой это не
сделано намеренно — конфигурации с такими обработчиками уже существуют и
работают ровно так же, как работали.

Событие после закрытия (`ПриЗакрытии`) и активацию формы платформа пока не
отслеживает. Заполнение
нового объекта — хук `ПриСозданииНового` **модуля объекта** (не формы) и ключ
`default` у поля. Удаление — хуки `ПередУдалением`/`ПослеУдаления` тоже в модуле
объекта: там они работают на всех пяти путях удаления, а не только из формы.

> **Особенности хуков записи формы.** `ПередЗаписью`/`ПриЗаписи`/`ПослеЗаписи` —
> это валидация и мутация шапки/ТЧ объекта при сохранении из формы, а не проводка.
> Движения регистров (`Движения.X.Добавить(...)`) в этих хуках **не
> записываются** в БД (коллектор движений не сохраняется) — проводки формирует
> `ОбработкаПроведения` документа, как и в 1С.
>
> Поддерживаемая сигнатура обработчика — без выходного параметра, например
> `Процедура ПередЗаписьюФормы()`. Параметр `Отказ` и присваивание
> `Отказ = Истина` сейчас не отменяют запись. Для отказа вызовите
> `ВызватьИсключение("Укажите наименование")` в самом обработчике или в вызванном
> им общем модуле: необработанное исключение распространяется до формы и запись
> не выполняется.
>
> Сообщения `Сообщить` всегда попадают в глобальный колокольчик «Сообщения»
> (он опрашивается на каждой странице). Дополнительно: при ошибке валидации
> (`ВызватьИсключение` в `ПередЗаписью`/`ПриЗаписи`) форма перерисовывается и
> показывает сообщения прямо в теле; после успешной записи (`ПослеЗаписи`)
> происходит редирект, поэтому в самом теле формы сообщения не видны, но в
> колокольчике они появятся. Чтобы показать сообщение именно в теле формы,
> используйте `ПередЗаписью`/`ПриЗаписи` с `ВызватьИсключение`.

### Что происходит с реквизитами, которых нет на форме

Управляемая форма показывает столько реквизитов, сколько вы разместили, — она
частична по построению. Поэтому запись из неё трактуется как **частичное**
состояние записи:

- реквизит, элемент которого есть на форме, записывается тем, что прислал
  браузер; пустое значение — это **очистка** (ссылка сбрасывается в «не
  выбрано», строка становится пустой);
- реквизит, которого на форме **нет** (или он показан только для чтения и потому
  не отправляется браузером), **сохраняет прежнее значение** — оно перечитывается
  из базы.

Раньше такой реквизит затирался в `NULL` при каждой записи, даже если
пользователь ничего не менял.

Практическое следствие: **из формы нельзя записать реквизит, который на ней не
размещён**. Если значение нужно вычислять — либо разместите элемент (можно
`read_only: true`), либо считайте его в `ПередЗаписью`: хук выполняется после
восстановления и его присваивание всегда побеждает.

Исключение одно — `kind: Флажок` без `read_only`. Неотмеченный флажок браузер не
отправляет, поэтому для него отсутствие значения по-прежнему означает «снят».

Авто-генерируемая форма рисует все реквизиты сущности и всегда присылает полный
набор, поэтому её поведение не изменилось.

### Реквизиты формы в обработчиках

Реквизиты формы (`attributes` с `save: false`) не хранятся в базе, но доступны
обработчикам события как `Объект.<ИмяРеквизита>`: значение приходит с формы,
типизируется по объявленному `type`, а ссылочные (`CatalogRef.X`,
`DocumentRef.X`) разворачиваются в ссылку — работает и `Объект.Склад.Наименование`.

Присваивание в обработчике возвращается на форму, как и у полей сущности:

```
Процедура СкладПриИзменении()
    Если ЗначениеЗаполнено(Объект.Склад) Тогда
        Объект.Комментарий = "Отгрузка со склада " + Объект.Склад.Наименование;
    КонецЕсли;
КонецПроцедуры
```

Если имя реквизита формы совпадает с именем реквизита сущности, побеждает
реквизит сущности — реквизит формы в этом случае недоступен. Не называйте их
одинаково.

## Типы реквизитов

| OneBase                    | 1С `<v8:Type>`              | Качества                          |
|----------------------------|-----------------------------|-----------------------------------|
| `string`, `string(N)`      | `xs:string`                 | `<StringQualifiers><Length>N</Length></StringQualifiers>` |
| `number`, `decimal(P,S)`   | `xs:decimal`                | `<NumberQualifiers><Digits>P</Digits><FractionDigits>S</FractionDigits></NumberQualifiers>` |
| `date`, `dateTime`         | `xs:date` / `xs:dateTime`   | —                                 |
| `bool`                     | `xs:boolean`                | —                                 |
| `CatalogRef.X`             | `cfg:CatalogRef.X`          | —                                 |
| `DocumentRef.X`            | `cfg:DocumentRef.X`         | —                                 |
| `EnumRef.X`                | `cfg:EnumRef.X`             | —                                 |
| `ChartOfAccountsRef.X`     | `cfg:ChartOfAccountsRef.X`  | —                                 |
| `AnyRef`                   | `cfg:AnyRef`                | импорт даёт `W021`                |
| `ValueTable` + `columns:`  | `v8:ValueTable` + `<Columns>` | —                               |

При экспорте составные типы (`composite`) сворачиваются до строки + `W020`.

## Связка с `.form.os`

`.form.os` — это файл DSL OneBase с процедурами-обработчиками. Перед каждой
процедурой может стоять аннотация `// @directive=&НаКлиенте` (или
`&НаСервере`); конвертер использует её при экспорте обратно в `Module.bsl`.

Связь YAML ↔ `.form.os` по именам процедур:

```yaml
events:
  ПриОткрытии: ПриОткрытииФормы   # ← имя процедуры в .form.os
```

```bsl
// @directive=&НаСервере
Процедура ПриОткрытииФормы()
  ...
КонецПроцедуры
```

## Конструктор и редактор

В UI конфигуратора (узел дерева **◇ Управляемые формы**) есть split-pane
Monaco-редактор со следующими кнопками:

- **Сохранить** — пишет YAML и `.form.os` (в файлы или БД, по режиму базы).
- **Просмотр** — показывает упрощённую HTML-форму в iframe (без обращения к БД).
- **Проверить** — вызывает `Validate` и подсвечивает предупреждения.
- **Удалить** — удаляет YAML/OS/ресурсы.

Клик по элементу на холсте открывает панель свойств. Для табличной части там:
галочка **«Считать Сумма = Количество × Цена»** (`auto_sum`), список
**«Колонки (показывать)»** — состав, и секция **«События»** со всеми шестью
событиями, которые табличная часть отправляет. У выбранной колонки — своё
`ПриИзменении`. Пункт «Создать обработчик…» дописывает заготовку процедуры в
`.form.os` вместе с комментарием о доступном контексте.

Импорт из 1С (`onebase forms convert-from-1c`) автоматически создаёт
правильную структуру каталогов; результат сразу видно в редакторе.
