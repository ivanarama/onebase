# Обновление платформы: источник, каналы, политика

Обновление OneBase — это замена бинарей платформы из выпуска (release). Источник
выпусков — **GitHub Releases**: своего сервера обновлений у платформы нет, и
«настроить свой сервер» здесь означает «указать другой репозиторий GitHub», а не
поднять веб-сервер. Эта страница описывает, как всё устроено, что можно менять
и где границы.

## Как это устроено

Проверка обновления — это два запроса к GitHub API репозитория (по умолчанию
`ivanarama/onebase`):

- канал **stable** — `GET /repos/<repo>/releases/latest`, то есть последний
  обычный релиз с тегом `vX.Y.Z` (GitHub сам исключает черновики и pre-release);
- канал **build** (по умолчанию) — `GET /repos/<repo>/releases`, берётся первый
  подходящий pre-release с тегом `build-<номер>`; это сборки из `main`,
  выходящие по нескольку раз в день.

Отдельного манифеста или реестра версий нет: клиент читает стандартный ответ
GitHub Releases API (тег, заметки, список файлов) и скачивает файлы выпуска по
адресам из него. Выпуск обязан содержать для каждой платформы:

| Файл | Обязателен | Назначение |
|---|---|---|
| `onebase-<платформа>.zip` / `.tar.gz` | да | сама сборка |
| `<архив>.sha256` | да | контрольная сумма; без неё обновление отвергается |
| `<архив>.sha256.sig` | нет* | Ed25519-подпись файла контрольной суммы |

\* Пока действует мягкий режим: релиз без подписи проходит с предупреждением,
релиз с **неверной** подписью отвергается всегда. Подробнее — в
[`release-signing.md`](release-signing.md): там же про ротацию ключа и ловушку,
которая стоит целого парка установленных копий.

Обновление проверяет и применяет **лаунчер** (кнопка в шапке, страница
`/updates`) или команда `onebase update`. Рабочие процессы баз в сеть за
обновлениями не ходят — «О программе» лишь показывает результат проверки,
сделанной лаунчером.

## «Свой источник» — это репозиторий GitHub, а не сервер

Адрес API (`https://api.github.com`) зашит в платформе и настройкой не меняется:
ни флагом, ни переменной окружения, ни политикой. Настраивается только репозиторий
в формате `владелец/имя`, и оба способа указать его эквивалентны:

```bash
onebase update --repo myorg/onebase-dist        # на одну команду
```

```yaml
# onebase.policy.yaml рядом с бинарём — на всё установка
updates:
  repo: myorg/onebase-dist
```

Политика при этом перекрывает флаг: если `repo` задан в политике, `--repo`
игнорируется без предупреждения. Страница обновлений в лаунчере показывает
источник, но поменять его из интерфейса нельзя — только политикой или флагом.

### Зеркало предприятия

Для закрытого контура, где обновления должны приходить из-под контроля
администратора, подойдёт репозиторий-зеркало на GitHub. Два рабочих сценария:

1. **Перенос официальных выпусков как есть.** Репозиторий-источник меняется, а
   файлы — нет: те же архивы, `.sha256` и `.sig`, что в официальном выпуске.
   Подпись продолжает сходиться, потому что подписаны именно эти файлы, —
   переиздавать подпись не нужно.

2. **Свои сборки.** Платформа собирается из своего форка, и тогда пара ключей
   нужна своя: приватный подписывает выпуски, открытый вшивается в бинарь при
   сборке. Порядок — в [`release-signing.md`](release-signing.md), раздел
   «Сборка из исходников и форки».

В обоих случаях зеркалу нужно сохранять **схему тегов** канала (`build-NNN` или
`vX.Y.Z`): клиент отказывается ставить выпуск с тегом другого канала и не даёт
откатиться на выпуск старше последнего им увиденного. Нумерация при этом
доверяется источнику: если зеркало ведёт свою, клиент поверит ей.

Побочный эффект стоит знать заранее: `updates.repo` перенаправляет не только
обновления, но и ссылку «сообщить об ошибке» — баг-отчёты поведут в issues
зеркала, а не upstream.

### Офлайн-контур

Там, где сети нет вовсе, источником становится флешка:

```bash
onebase update --from D:\flash\onebase-windows-amd64.zip --sha256 <64-hex>
```

Сумма обязательна и передаётся рукой — подпись на этом пути не проверяется.
В отличие от сетевого пути, офлайн может заменить и dev-сборку, и бинарь с
нестандартным ярлыком версии. Сетевые проверки при этом стоит запретить
политикой (`check: off`), чтобы лаунчер не оставлял следов исходящих соединений.
Подробнее — в [`DEPLOYMENT.md`](DEPLOYMENT.md), §7.

## Файл политики `onebase.policy.yaml`

Лежит **рядом с бинарём**, а не в профиле пользователя — на общей установке это
зона администратора. Секция `updates`:

```yaml
updates:
  ui: false                    # спрятать кнопку и страницу обновлений
  check: off                   # запретить обращения к сети (офлайн-контур)
  channel: stable              # зафиксировать канал: переключатель откажет
  repo: myorg/onebase-dist     # источник сборок (перекрывает --repo)
```

Булевы значения понимаются широко (`true/false`, `yes/no`, `on/off`, `1/0`).
Битый YAML трактуется как полный запрет обновлений — безопасная сторона.

Аварийный выключатель на одну машину — переменная окружения
`ONEBASE_UPDATES=off`: запрещает и проверки, и кнопку, поверх файла политики.
Обратного «включающего» действия у неё нет.

Выбор канала (`--channel` или переключатель на странице обновлений)
запоминается в `~/.onebase/updates/state.json` и переживает рестарты.

## Команды

```bash
onebase update                      # проверить, скачать и применить
onebase update --check              # только проверить
onebase update --check --json       # для мониторинга и планировщика
onebase update --download           # скачать, не применяя
onebase update --rollback           # вернуть предыдущую версию
onebase update --channel stable     # сменить канал (запомнится)
```

Офлайн-путь и оркестрация службы: `--from` + `--sha256`, `--service` / `--id`
(имя службы и порт из реестра баз), `--target`, `--healthz-url`, `--port`,
`--timeout`. После подмены бинаря службой платформа опрашивает `/healthz` и,
не увидев новую версию за таймаут, откатывает старый бинарь сама.

Применение останавливает запущенные базы (с опциональным бэкапом), меняет бинари
и поднимает базы обратно; лаунчер перезапускает сам себя. `onebase update` без
службы меняет только файлы — запущенные процессы доиграют на старой версии и
обновятся при перезапуске.

## Ограничения, о которых стоит знать

- **Произвольный сервер обновлений не поддерживается**: источник — только
  публичный репозиторий GitHub. GitHub Enterprise и самописные HTTP-эндпоинты
  не настраиваются.
- **Приватный репозиторий не работает**: клиент не отправляет токен, GitHub
  отвечает «нет доступа», и ошибка прямо советует проверить, что источник
  публичный.
- **Лимит GitHub API** — 60 анонимных запросов в час с IP. При проверке раз в
  4 часа он недостижим, но за корпоративным NAT нескольких десятков машин может
  хватить; это «проверить не удалось», а не поломка. Прокси `HTTP_PROXY` /
  `HTTPS_PROXY` / `NO_PROXY` уважаются стандартным транспортом.
- **Обновляться кнопкой может только личная установка** (каталог внутри профиля
  пользователя). `C:\Program Files`, терминальный сервер и каталоги у корня
  диска обновляются вручную распаковкой архива; права администратора правила не
  меняют.
- **Смена ключа подписи** обрывает автообновление парка — старый бинарь всегда
  отвергает чужую подпись. Порядок ротации описан в
  [`release-signing.md`](release-signing.md).
