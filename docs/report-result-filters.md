# Типизированные отборы результата отчёта

Разработка platform2, Draft #2640. Реализация для обычного query-отчёта подготовлена в source; это не поставка SDK и не закрытие всего ENG04. Интеграция в накопленный B30+ и DSL result_proc — отдельные незавершённые этапы.

## Поведение обычного отчёта

В «Настройке отчёта» выбираются разрешённая колонка результата, подходящий её типу оператор и значение. Несколько условий соединяются AND. Настройка сохраняется в пользовательском варианте; повреждённый, удалённый, чужой или более не разрешённый вариант даёт явную ошибку. API использует те же __settings/__preset и серверную проверку. Отбор действует в HTML, Excel/PDF, фоновой выгрузке и API до лимита принятых строк, разрешения UUID в подписи, пользовательских группировок/итогов и пагинации.

Пример __settings:

```json
{"filters":[{"field":"amount","op":"ge","value":"100.25"},{"field":"active","op":"eq","value":"true"}]}
```

Строка: eq/ne/contains; contains без учёта регистра, как в прежнем отборе платформы. Число и дата: eq/ne/gt/ge/lt/le. Bool, enum и UUID ссылки: eq/ne. Дополнительно is_null/not_null с пустым value, отдельно от пустой строки/false/0/нулевой UUID. Обычные сравнения с SQL NULL не совпадают, включая ne. Для чисел применяется decimal без преобразования в float64; дата принимает ISO дату/время и ДД.ММ.ГГГГ, часовой пояс без явного смещения — time.Local платформы. Ссылка вводится UUID, enum ограничен метаданными.

Сервер восстанавливает тип и происхождение по ProjectionColumn.Path, SourceOccurrences и метаданным источника; алиас лишь именует уже доказанное поле. Метаданные/операторы от браузера не являются полномочиями. Поддержаны однозначные прямые поля и доказанные UUID ссылок. Объектное чтение и row access сохраняются. Повтор выходного ключа, неизвестное выражение, wildcard без proof, UNION/подзапрос, виртуальный источник и неоднозначная неквалифицированная колонка не попадают в доступные поля; подделанный запрос отклоняется. Отчёт с авторским FIRST/LIMIT также не получает отбор по уже обрезанному набору. Это ограничение доказательства, а не полное покрытие СКД.

## Порядок, ограничения и ПДн

Общий модуль internal/report/resultfilter проверяет все условия до чтения данных. Исходный параметризованный SQL и его args не меняются, значения условий в SQL не вставляются. storage.VisitQuery читает поток; в памяти остаются только принятые строки страницы/лимита. Непринятые строки не расходуют report_max_rows/export_max_rows. В API total и page считаются по совпадениям.

Независимые пределы: 64 условия, 64 КиБ JSON, 4096 байт значения; числовой литерал до128 символов с ограниченным exponent. Сканирование до100000 исходных строк и до30 секунд с учётом отмены внешнего контекста. Исчерпание сканирования или времени возвращает ошибку без частичного результата: неполный общий итог не выдаётся за полный. Лимит принятых строк сохраняет существующий признак truncated/предупреждение, экспорт не выдаёт усечённый файл за полный.

Допустимость исходного поля задаёт общий gate platform3 internal/access/report_output.go: обязательный hide metadata.Field.PII и исходных LabelFields защищённой сущности независимо от admin/full. Дополнительно проверяются обычные объектные/полевые права. UUID ссылки не обходит pii самого поля. Защищённая подпись не предлагается для отбора, маска готового результата не считается разрешением фильтровать сырой секрет. Отчётные границы используют ReportOutputQueryMaskPlan; resolver получает только доказанные RefColumns, сохраняет UUID/переходы и не разыскивает произвольные UUID строки по всем справочникам. Карточки неизменны. Код policy перенесён из опубликованных b3e0e9f24 и c6849a276, не написан повторно по именам Телефон/Адрес.

## Граница source и остаток ENG04

Узкие подключения: handlers_reports.go перед RunLimit, report_settings.go сохранение/загрузка, API v2 перед пагинацией. Background использует тот же reportExportRowsWithContext. Отдельный report-result-filter.js получает только разрешённые дескрипторы и ограничивает оператор/ввод; сервер повторяет проверку.

В B29 уже есть result_proc и отборы источника; они не объявляются отсутствующими. Несколько SQL внутри result_proc ещё не получают общий проверенный контекст эффективных отборов из этого source-коммита. Для этого нужны runtime-адаптер, provenance каждого набора и явное выполнение/отказ условия до соответствующего лимита; произвольная DSL-ready строка без lineage остаётся закрытой для такого отбора. При интеграции нельзя оставлять обход через queryless result_proc, старый ParseSourceSettings либо поздние ApplyFilters/ApplySourceFilters. Нативные варианты B29+ требуют фактического compileReportVariantQuery, а не схемы базового rep.Query.

Независимое review и накопленный SDK ещё не получены. Native в открытом координатором окне, owned PostgreSQL, full build после разрешённых .go конфликтов и интеграционные HTTP/API/result_proc — в общей пачке ~раз в3ч. Новая сборка не приписывает себе прежние source127/native16 меню. Выкладка только её словом пакетом в ЛПЦ8448;8444/8443 не затрагиваются.
