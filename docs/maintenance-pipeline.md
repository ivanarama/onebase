# Конвейер сопровождения: какие метки ставить и когда

Заявки и pull request'ы движутся по репозиторию полуавтоматически. Четыре
этапа — **триаж**, **фикс**, **ревью**, **мерж** — выполняет Claude Code по
расписанию, а переключают этапы **метки GitHub**.

Устройство держится на одном разделении: **починка — не решение, а новая
возможность — решение**. Очевидный дефект едет до готового PR сам: продукт уже
обещал это поведение, и возврат к обещанному никем не санкционируется заново.
Всё остальное — enhancement, спорная семантика, архитектурный выбор — уходит
человеку с оценкой целесообразности. И ничто не вливается в `main` без метки
`ship`, которую ставит только человек.

Эта страница — памятка для человека: что и где нажимать. Точная процедура
каждого этапа лежит в `.claude/skills/<этап>/SKILL.md`, правки процесса вносятся
туда.

## Коротко

| Метка | Ставится на | Кто ставит | Что означает |
|---|---|---|---|
| `ready-fix` | ишью | триаж | очевидный дефект, критерии сошлись — ушёл в автофикс |
| `in-work` | ишью | фиксер | PR открыт, заявка едет; снимает пастух после мержа |
| `reviewed` | **PR** | ревью | блокирующего нет — **ждёт вашего `ship`** |
| `changes-requested` | **PR** | ревью | есть замечания, фиксер дорабатывает |
| `needs-decision` | ишью или PR | автоматика | **ход человека**: решение или ответ |
| `approved` | ишью | **только человек** | «делаем» по заявке, которая не дефект; при развилке — **рекомендованный** триажем вариант |
| `decision:1` … `decision:3` | ишью | **только человек** | «делаем вариант N» — ставится вместе с `approved`, когда рекомендация не подходит |
| `ship` | **PR** | **только человек** | ревью прочитано, можно вливать; заодно — согласие с разбором хвоста |
| `no-tail` | **PR** | **только человек** | хвост ревью не заводить заявками вообще |
| `manual` | ишью | триаж или человек | правка вне репозитория: делает человек руками, конвейеру не предлагать |
| `hold` | ишью или PR | человек | стоп-кран: автоматика не трогает вообще |

Список читается так: **`needs-decision` и `reviewed` — ваш ход**;
`ready-fix`, `in-work`, `changes-requested` — везёт машина, трогать не нужно.

На PR `needs-decision` всегда перекрывает новую машинную работу. Разрешены только
завершение уже начатого handoff и явная обратная передача: `pp:review-again`
возвращает REVIEW, `pp:fix-decision <SHA>` — FIX. Без этих маркеров ревью,
фиксер и пастух PR не трогают.
`reviewed` относится к
конкретному HEAD: новый SHA автоматически требует нового ревью. Для повтора того
же SHA человек пишет отдельной строкой `pp:review-again`; этот запрос
поглощается только новым заключением, опубликованным после запроса.

Где нажимать: на странице ишью или PR правая колонка → **Labels** → шестерёнка.
Или из консоли:

```bash
gh issue edit 1130 --remove-label needs-decision --add-label approved

# на PR метка ставится через REST: gh pr edit в этом окружении не работает
echo '{"labels":["ship"]}' | gh api -X POST repos/ivanarama/onebase/issues/1131/labels --input -
```

> **Почему так.** В рабочей копии `gh` 2.4.0, а GitHub отключил Projects
> (classic). Команды, которые тянут объект целиком, падают с
> `GraphQL: Projects (classic) is being deprecated … (projectCards)`:
> `gh pr edit` (любой), `gh pr view` и `gh issue view` без `--json`. Работают
> те же команды с явным `--json`, весь `gh api`, а также `gh issue edit`,
> `gh pr list`, `gh issue list`, `gh pr diff`, `gh pr comment`.
> Настоящая починка — обновить `gh`; до тех пор скилы этапов ходят по REST.
> У REST номера PR и ишью — одно пространство, поэтому метка PR ставится
> через `/issues/<N>/labels`; это не опечатка.

## Как заявка проходит конвейер

```
новая заявка
   │   триаж (авто, раз в 4 ч)
   ▼
разбор: воспроизведение, корень, план фикса
   │
   ├─ очевидный дефект ──────────────► ready-fix        (человек не нужен)
   │
   ├─ чинится не коммитом ───────────► manual + needs-decision
   │        │   ← ЧЕЛОВЕК: применить правку руками и ЗАКРЫТЬ заявку
   │        │              (approved здесь ничего не запускает)
   │
   └─ всё остальное: + оценка целесообразности (+ варианты с рекомендацией,
          │            если есть развилка) + needs-decision
          │   ← ЧЕЛОВЕК: approved (делаем; при развилке — рекомендованный вариант)
          │              approved + decision:N (делаем вариант N) / закрыть / hold
          ▼
      фикс (авто, раз в 4 ч) → ветка, тесты, PR с «Fixes #N», на заявке in-work
          ▼
      ревью (авто) → заключение в PR
          │
          ├─ есть замечания ──► changes-requested ──► фиксер дорабатывает ──┐
          │        (до двух кругов; третий — needs-decision человеку)       │
          │                                                                 │
          └─ годится ──────────► reviewed  ◄─────────────────────────────────┘
                  │   ← ЧЕЛОВЕК: прочитать заключение, поставить ship
                  │              (не нужен хвост — заодно no-tail)
                  ▼
             мерж (авто, раз в 2 ч) → влито в main, заявка закрылась по «Fixes #N»
                  ▼
             хвост (пока вручную) → находки [заявка] из заключения ревью
                                    становятся новыми заявками → триаж
```

### 1. Триаж — `/triage-issues`

Берёт до пяти неразобранных заявок (старые вперёд), читает целиком, ищет корень
по коду, пробует воспроизвести и оставляет комментарий «**Триаж.**
Воспроизводится / Корень / План фикса / Сложность / Риски» с маркером
`<!-- pp:triage -->` — по нему этап понимает, что заявка уже разобрана.

Дальше он решает маршрут.

**`ready-fix` (автоход)** — только для дефектов и только если сошлись все четыре
условия:

- воспроизвёл сам либо доказал корень по коду с указанием `файл:строка`;
- корень локализован в конкретном месте, а не «где-то в подсистеме»;
- сложность мелкая или средняя;
- поведение существующих конфигураций не меняется.

Крупное — миграция схемы, смена семантики DSL/SQL, архитектурный сдвиг — уходит
человеку всегда, даже если это стопроцентный дефект. Не сошёлся хоть один пункт —
`needs-decision` и строка о том, какой именно.

**`manual` — правка не коммитом.** Настройки GitHub (описание, topics, защита
ветки), внешний сервис, инфраструктура: конвейер двигает код, и у фиксера нет
способа положить такую правку в дифф. Без метки заявка с `approved` молча ждала
бы прогона, который никогда её не возьмёт — так вышло с #1142 (пустой блок
About: заявка одобрена, а чинить в репозитории нечего). Триаж ставит `manual`
вместе с `needs-decision` и пишет в плане конкретную команду; вы применяете её и
**закрываете заявку сами** — `Fixes #N` тут неоткуда взяться.

**Оценка целесообразности** — для всего, что не дефект. Триаж дописывает блок и
ставит `needs-decision`:

> **Целесообразность.**
> Зачем: какая работа пользователя сейчас не делается.
> Обходной путь без кода: есть / нет — какой.
> Цена: сложность, какие подсистемы затрагивает.
> Риск: что может сломаться и что придётся поддерживать дальше.
> **Рекомендация: делать / не делать / потом** — с причиной.

Причина обязательна и у «не делать»: без неё заявка вернётся через месяц и будет
разобрана заново с нуля.

**Развилка — пронумерованные варианты с рекомендацией.** Если решение упирается
в выбор (архитектура, спорная семантика, «а надо ли вообще»), триаж обязан не
просто выложить варианты, а назвать свой:

> **Развилка.** В чём выбор.
> 1. Что делаем — цена.
> 2. Что делаем — цена.
> **Рекомендую 2**: что оптимизируем и во что обойдётся откат, если ошиблись.

Вариантов не больше трёх. «Выбор за человеком» без рекомендации — не ответ:
выбираете вы в любом случае, а от разбора нужна позиция, с которой можно
согласиться одним движением. Когда варианты близки, критерий по умолчанию —
**что дешевле откатить**: правка кода отменяется коммитом, изменённые данные в
базе у пользователя — нет.

Ваш ход дальше стоит одной метки: `approved` — «делаем рекомендованный»,
`approved` + `decision:2` — «делаем второй». Читать разбор заново, чтобы
переписать выбор словами, не нужно; словами имеет смысл писать то, чего в
вариантах нет.

**Заявке со стороны триаж отвечает сам — но только при `ready-fix`.** Внешний
автор из технического разбора не узнаёт ни что ему поверили, ни что делать
сегодня. Поэтому, отправляя чужую заявку в автоход, триаж пишет автору отдельный
короткий комментарий: воспроизвели или разобрали по коду, что не так
человеческим языком, обходной путь на сейчас, что делать с уже испорченным
состоянием, если фикс его не лечит. Без сроков — очередь фикса и ваш `ship` от
триажа не зависят.

Заявка, ушедшая к вам с `needs-decision`, автоответа не получает: сообщать там
пока нечего, кроме «решение за мейнтейнером», и говорит это человек, который
решение принимает. Ответ автору такой заявки — ваш ход.

**Напоминание об этом ходе — еженедельная сверка.** Корзину «внешняя заявка без
ответа» в `backlogsweep` больше не гасит машинная запись: разбор триажа и
заключение ревью помечены маркером `<!-- pp:` и за разговор с автором не
считаются (#1166). Разобранная заявка, на которую автору никто не ответил, в
отчёт теперь попадает. Отчёт не гейт и читается раз в неделю, поэтому первая
страховка по-прежнему автоответ триажа при `ready-fix` — но он покрывает только
автоход. Корзина «needs-decision без движения» при этом гаснет от вашего же
`approved` или `hold`: про заявку, решённую меткой и не отвеченную словами,
напомнит только первая корзина.

Триаж не ставит `approved`, `decision:*`, `ship`, `reviewed`, не начинает фикс,
не закрывает и не редактирует заявки.

### 2. Фикс — `/fix-approved`

Порядок работ жёсткий: **сначала доработать свой PR по замечаниям ревью**
(метка `changes-requested`, но без `ship`/`hold`/`needs-decision`), и только если
таких нет — брать новую заявку. `ship` передаёт ветку MERGE: увидев его на
контрольной проверке, FIX больше ветку не меняет, даже если человек оставил
старую `changes-requested`. HEAD, все comments, labels и вычисленный из единого
потока владелец перечитываются непосредственно перед каждым push, комментарием
и изменением меток. До CAS-push нужен прежний HEAD и владелец FIX. После
успешного собственного push разрешена только узкая финализация, привязанная к
отправленному SHA; перед её комментарием и снятием метки снова проверяются новый
HEAD и отсутствие новых переходов. `pp:review-again` или новая completion останавливают FIX даже
при оставшейся `changes-requested`; если `ship` появился в узком окне сразу
после push, MERGE снимет его как относящийся к неотревьюенному HEAD.
Открытые PR для обычной доработки и восстановления handoff FIX получает одним
пагинированным REST-списком, а не двумя `gh pr list` с лимитом по умолчанию:
31-й припаркованный PR также обязан дойти до восстановления.

FIX также просматривает сочетание `changes-requested` + `needs-decision`, но не
работает по коду: он только завершает handoff с точным SHA-маркером. Машинный
`pp:fix-handoff` гарантирует финал «остаётся needs-decision», человеческий
`pp:fix-decision <SHA>` — «остаётся changes-requested», а более поздний
`pp:review-again` передаёт мяч REVIEW и отменяет старое восстановление FIX.
Новый каноничный `pp:head-reviewed` после override поглощает его и снова задаёт
владельца по Outcome-Label. Перед каждым шагом recovery FIX перечитывает HEAD,
все комментарии и labels; действует только последний валидный переход текущего SHA. Если процесс
оборвался между двумя изменениями меток, следующий прогон продолжает актуальный,
а не просто старый недостающий шаг.

Новая заявка = `ready-fix` **или** `approved`, без `hold`, без уже открытого PR.
Её remote-ветка строго детерминирована как `fix/<N>` и атомарно создаётся через
GitHub `POST /git/refs`: только ответ `201` даёт branch-claim, а любой другой
статус останавливает запуск (`409`/`422` включены) даже при том же SHA. Обычный
`git push --force-with-lease=...:` здесь непригоден: второй worker получил бы
ложный успех `Everything up-to-date`. Три
полных пагинированных поиска связанного PR — в начале, перед push и перед
`gh pr create` — остаются диагностикой, но не подменяют атомарный branch-claim;
поэтому два worker, одновременно увидевшие пустой список, не создают два PR.
`bug` раньше `enhancement`, при равенстве — меньший номер. За прогон берётся одна.
`approved` перебивает `needs-decision`: это ваш последний ход, снимать вторую
метку руками не нужно.

Если в триаже была развилка, вариант выбирается по старшинству: ваш комментарий
с решением → метка `decision:N` → рекомендация триажа. Реализованный вариант
фиксер обязан назвать в теле PR строкой `Вариант: 2 (метка decision:2)` или
`Вариант: 2 (рекомендация триажа)` — иначе через месяц не отличить его выбор от
вашего решения.

Чинит в отдельном worktree, гоняет `go build ./...` и тесты затронутых пакетов,
пушит ветку, открывает PR с обязательным английским `Fixes #N`, вешает на заявку
`in-work` и пишет туда комментарий со ссылкой на PR — с маркером
`<!-- pp:in-work -->`, потому что адресован он конвейеру, а не автору заявки.

Не получилось (не воспроизводится, нужен выбор, фикс выходит за рамки) —
комментарий с конкретным вопросом, `needs-decision` и **снятие
`approved`/`ready-fix`**: очередь ведётся по ним, и заявка с вопросом к вам не
должна вернуться к фиксеру следующим прогоном. Недоделанное не пушится.

Можно вызвать точечно: `/fix-approved 1125`.

### 3. Ревью — `/review-queue`

Отдельный агент со свежим контекстом — не автор изменений. Самопроверка фиксера
бесполезна: он подтвердит сам себя.

Берёт до двух обычных аудитов открытых PR без `ship`/`hold` и не черновики;
`changes-requested`/`needs-decision` обычно передают мяч дальше, но REVIEW сначала
проверяет, не осталась ли под ними его незавершённая транзакция. Полный список
открытых PR и все комментарии читает
пагинированным REST: первые 50/100 объектов не являются границей очереди.
Метка `reviewed` сама по себе PR не исключает: ревью
сравнивает текущий SHA с доверенным маркером `pp:head-reviewed`, поэтому новый
push не наследует старый вердикт. Перед любым итоговым комментарием и меткой
перепроверяются HEAD и стоп-метки. Затем ревью читает дифф и связанную
заявку, **прогоняет сборку и тесты в отдельном worktree** и пишет заключение:

> **Ревью.** (круг K)
> Reviewed-SHA: полный проверенный SHA.
> Outcome-Label: reviewed / changes-requested / needs-decision (одно значение).
> Что меняется: 2–4 строки по существу.
> Проверено: что запускал и с каким результатом.
> Блокирующее: нумерованный список (или «нет»).
> Хвост: пункты `[заявка]` / `[выброс]` — см. ниже.
> **Вердикт: годится к мержу / есть замечания.**
> `<!-- pp:review pp:tail=N -->`

После заключения ревью сначала публикует claim
`<!-- pp:review-claim <SHA> review-comment=<id заключения> -->` и перечитывает
события. Только самый ранний валидный claim текущей override-эпохи вправе
ставить outcome-метку; остальные параллельные попытки заканчиваются до мутации.
Победитель ставит и подтверждает `Outcome-Label`, затем публикует
отдельный committed-комментарий
`<!-- pp:head-reviewed <SHA> review-comment=<id заключения> -->`. Он явно
связывает SHA с конкретным более ранним review-комментарием. Валидна только
первая completion-ссылка на этот id; между заключением и completion не должно
быть `pp:review-again`, а `Reviewed-SHA` обязан совпадать. Маркер долговечно
доказывает, что соответствующая `Outcome-Label` была подтверждена; её
последующее снятие FIX не стирает круг. Для одного
SHA без разделяющего override канонична только первая валидная пара, поэтому
параллельный дубль аудита круг не увеличивает. Если сбой случился до committed-
маркера, сорванная попытка круг не увеличивает.

REVIEW на следующем прогоне узнаёт незавершённую транзакцию по `Reviewed-SHA`,
`Outcome-Label` и событиям, подтверждает/добавляет ожидаемую метку и дописывает
маркер. Если валидный claim уже есть, recovery восстанавливает orphan, на который
ссылается **самый ранний claim**, независимо от порядка orphan. Самый ранний
orphan выбирается и получает новый claim только когда claims вообще нет. Если в той
же эпохе после последнего override уже есть каноничная
committed-пара текущего SHA, параллельный orphan остаётся только диагностикой и
не может поставить другую метку. При нескольких orphan без пары восстанавливается
только владелец самого раннего claim. Stale `reviewed` прошлой эпохи — безопасная
UI-подсказка, не конфликт; stale `changes-requested` при каноничном другом
outcome убирает FIX. Если же от legacy/внешней гонки остался необъяснимый
`needs-decision` или одновременно активны две блокирующие route-метки, автоматика
ставит `hold` и передаёт человеку. Общую метку после гонки REVIEW
никогда не удаляет вслепую: у метки GitHub нет владельца. Для старого
`changes-requested` без доказуемой пары FIX ничего не исправляет: снимает
осиротевшую метку и возвращает PR на полноценный аудит. Поэтому частичный сбой
не оставляет PR навсегда между очередями.

Блокирующим считается: PR не решает заявку целиком или молча разошёлся с планом;
дефекты корректности; тест дёргает приватную функцию вместо публичной точки
входа; тронута семантика SQL без матричного теста; строки UI без ключа в
`en.json`; `feat:` без секции в `docs/features.md`; отсутствие `Fixes #N`;
необъявленное изменение поведения существующих конфигураций; **неверное по факту
утверждение в тексте, который поставляет сам PR** — документация, руководство
`ai-guide`, сообщение пользователю, текст скила. Последнее — не придирка к стилю:
влитый текст становится источником правды, а читают его в том числе агенты,
которые спорить не станут.

Стиль и упрощения не блокируют, но и не пропадают — они уходят в хвост.

**Хвост — то, что переживёт мерж.** Ревью находит больше, чем обязан починить
один PR, и раньше это оседало в комментарии, а с `ship` пропадало. Теперь каждая
неблокирующая находка получает класс:

> Хвост:
> 1. [заявка] Сторож событий копирует словарь платформы вместо ссылки на него →
>    заголовок: «ai-guide: сторож событий копирует словарь вместо ссылки»
> 2. [выброс] Формулировка «даёт режим no_grid» чуть шире, чем есть.

`[заявка]` требует готового заголовка будущей заявки: не формулируется одной
строкой — значит `[выброс]`. При сомнении ревью обязано выбрать `[выброс]`,
и больше трёх `[заявка]` с одного PR не бывает — иначе хвост станет генератором
мусора для триажа. `[выброс]` не молчание: вы видите, что находку заметили и
решили не заводить.

Дальше — метка: `reviewed` (ждёт вас) или `changes-requested` (обратно фиксеру).
**Два круга машина закрывает сама; на третьем** ревью ставит `needs-decision` —
это уже спор, а не недоделка.

Повторить аудит без нового push можно доверенным комментарием, отдельная строка
которого равна `pp:review-again`. Override потребляется только новым заключением,
опубликованным после него: запоздалый completion старого аудита его не гасит.
Если PR припаркован на `needs-decision`, достаточно сначала опубликовать
override: REVIEW распознает явный handoff, снимет парковочную метку и продолжит.
Тот же override после `changes-requested` передаёт мяч от FIX обратно в REVIEW:
более поздний непоглощённый override сильнее старой маршрутной метки, а FIX в
это время доработку не начинает. Crash после комментария восстанавливается
следующим прогоном. Прежнюю
`reviewed` REVIEW не удаляет из-за гонок общей метки;
источником истины служит новый каноничный committed-маркер.

Ревью не ставит `ship` никогда и заявки по хвосту не заводит — это делает этап 6,
после мержа.

### 4. Решение человека: `ship`

Метка вешается **на PR, не на заявку**, и означает: заключение прочитано, вливаем.

`ship` — это заодно и согласие с разбором хвоста: пункты `[заявка]` станут
заявками после мержа. Не согласны — тем же движением:

| Что хотите | Что сделать |
|---|---|
| Заводим всё, что предложило ревью | просто `ship` |
| Не заводить ничего | `ship` + метка `no-tail` |
| Не заводить конкретные пункты | `ship` + комментарий строкой `pp:tail-drop 1,3` — номера пунктов хвоста **как они напечатаны** в заключении, сквозные по всему списку вперемешку с `[выброс]` |

Это та же грамматика, что у `approved` / `approved + decision:N` на заявках:
согласие — одна метка, несогласие — метка плюс уточнение.

**`ship` не запускает ревью, а разрешает мерж текущего проверенного SHA.**
Мерж-этап код не читает. Если ему пришлось обновить ветку до свежего `main` или
разрешить механический конфликт, HEAD изменился: пастух снимает старый `ship` и
возвращает PR на повторное ревью. Только неизменившийся проверенный SHA ждёт
зелёного CI и вливается. Если хотите посмотреть сами — `gh pr diff <N>`,
`/review <N>` в Claude Code.

`ship` — разрешение человека на мерж, но не обход стоп-кранов. Поставленный на PR
с `changes-requested`, он всё равно сработает: человек так решил. `hold` и
`needs-decision` всегда блокируют мерж до снятия.

### 5. Мерж — `/merge-shepherd`

Вливает только PR с `ship` и без `hold`/`needs-decision`, по возрастанию номера,
не больше трёх за прогон. Метки перечитываются через REST перед любым внешним
изменением PR (включая update-branch, push разрешённого конфликта, комментарий и
метку), на каждом опросе CI и непосредственно перед merge: решение человека во
время ожидания останавливает текущую попытку. Ветка `main` защищена с
`strict: true`, поэтому очередь строго последовательна.
Начальный список MERGE также читается целиком пагинированным REST: 30 первых
припаркованных `ship`-PR не скрывают следующий допустимый PR.
Метка `ship` должна быть поставлена после каноничного completion текущего SHA;
порядок доказывается полной timeline PR. Последний переход `ship` среди событий
всех actors обязан быть `labeled` от `ivanarama` и позже creation/edit обоих
комментариев. Старый trusted label, затем trusted unlabel и чужой re-label не
возвращают разрешение. Поэтому старый `ship`, оставшийся до нового заключения,
не считается согласием человека с этим заключением.

На каждой такой проверке MERGE также сравнивает текущий SHA с доверенной парой
`pp:head-reviewed … review-comment=<id>` → существующий review-комментарий и
убеждается, что это первая completion-ссылка на id, `Reviewed-SHA` совпадает,
между парой и после completion нет непоглощённого `pp:review-again`, а связанное
заключение содержит точную `Outcome-Label`. Если
`ship` относится к старому HEAD или аудит не завершён, пастух снимает устаревший
`ship`, сверяет удаление, пишет причину в рамках той же атомарной передачи и
возвращает PR в REVIEW; новый код без ревью не вливается. Этот завершающий
комментарий — явное исключение из обычного re-gate после снятия `ship`.
Перед финальным PUT MERGE сохраняет `node_id` review и completion и watermark
последнего комментария. Один raw GraphQL snapshot адресует оба комментария по
node ID, возвращает их `fullDatabaseId`/body/`lastEditedAt` вместе с HEAD, labels
и `labels.pageInfo.hasNextPage`, последними 100 comments и label-events.
`hasNextPage` обязан быть false, иначе стоп-метка могла остаться за пределом
снимка. Последний ship-transition должен быть trusted labeled позже создания и
последнего edit обоих адресованных комментариев. Watermark обязан оставаться в окне: если появилось
100+ новых комментариев, нужен новый аудит/completion; перестановка `ship` лечит
только отсутствие свежего ship-event, а не потерю доказательства комментариев.
Именно `fullDatabaseId: BigInt`, а не старый `databaseId: Int`, сравнивается как
строка с REST comment id: реальные идентификаторы уже не помещаются в 32 бита.

FIX использует замечания только для SHA из committed-пары. Он сравнивает этот
SHA с удалённым HEAD до создания worktree и ещё раз непосредственно перед push.
После fetch `FETCH_HEAD` обязан равняться этому SHA, а worktree создаётся из
самого сохранённого SHA, не из плавающей ветки. Тот же контракт действует для
конфликтного worktree MERGE.
Оба этапа отправляют изменения атомарным CAS-push:
`--force-with-lease=refs/heads/<ветка-PR>:<проверенный SHA>` и точным refspec
`HEAD:refs/heads/<ветка-PR>`. Поэтому чужой push в окне после REST-сверки
отклоняет операцию, а не перезаписывается локальным результатом.
Если HEAD уже другой, устаревший `changes-requested` снимается и PR возвращается
в REVIEW без применения замечаний к новому коду.

- `BEHIND` → `update-branch` вызывается с `expected_head_sha` проверенного HEAD.
  После `422` HEAD перечитывается: только фактическое несовпадение означает гонку;
  validation/rate-limit отказ при прежнем SHA не снимает `ship`. Успешное
  обновление меняет HEAD, поэтому снять `ship` и вернуть в REVIEW.
- `DIRTY` → результат `git merge origin/main` разбирается по exit code и наличию
  unmerged-файлов (`git diff --name-only --diff-filter=U`). Ненулевой код с
  unmerged-файлами — настоящий конфликт; неизменившийся HEAD сам по себе не
  означает no-op, потому что при конфликте он остаётся прежним до commit.
  Механические конфликты (`docs/features.md`, `internal/i18n/locales/*.json`,
  `Plans/README.md`) разрешает сам, но пушит точным refspec и CAS-lease
  `git push --force-with-lease=refs/heads/<ветка-PR>:<проверенный SHA> origin HEAD:refs/heads/<ветка-PR>`,
  сверяет новый PR HEAD через REST и лишь
  после подтверждённого push снимает `ship`, возвращая новый HEAD в REVIEW;
  содержательный конфликт не трогает — комментарий и эскалация.
- Ждёт обязательные проверки: `build`, `lint`, `postgres-integration`, `vuln`,
  `smoke`, `e2e`, `test-windows`, `launcher-webview-build` — до 35 минут на PR.
  Не блокирует мёрж только `bench`.
- Флейк (таймаут, обрыв раннера, сеть; `test-windows` мигает примерно раз на
  тридцать прогонов) → полный label+SHA-гейт непосредственно перед единственным
  перезапуском. Настоящий провал → комментарий с выдержкой лога и эскалация.

Финальный merge выполняется REST-запросом compare-and-merge с полем
`sha=<проверенный HEAD>`. Непосредственно перед ним один raw GraphQL snapshot
содержит одновременно HEAD, текущие labels и последние timeline events; это
последняя проверка `ship`/`hold`/`needs-decision`, completion и override.
Успешный snapshot — точка невозврата: GitHub не умеет сделать merge условным по
labels, поэтому стоп-метка, поставленная уже после отправки PUT, не отменяет
запрос в полёте. До этой точки она останавливает MERGE. Push нового HEAD в
последнем окне безопасно даёт `409`, после чего пастух снимает устаревший `ship`
и возвращает новый HEAD в REVIEW.

После мержа остальные PR очереди становятся `BEHIND` — это норма. Их `MERGEABLE`
до первого мержа ничего не значит.

Там же снимается `in-work` с заявок, закрытых этим PR: вешает метку фиксер при
открытии PR, а снять её больше некому — он к заявке не возвращается. Без этого
шага каждая проехавшая заявка уносит `in-work` в закрытые, и метка перестаёт
означать «едет прямо сейчас».

### 6. Хвост — `/tail-issues`

Проходит по PR, влитым за две недели, находит заключение, на которое ссылается
последняя каноничная committed-пара merged HEAD после последнего поглощённого
override, и заводит его пункты `[заявка]` — без меток, то есть ровно в том виде,
в каком их берёт триаж. На PR остаётся комментарий «**Хвост разобран**» с
маркером `<!-- pp:tail-done -->`, чтобы прогон не повторился.
Если после этой пары остался непоглощённый `pp:review-again`, старый аудит
считается отменённым и TAIL такой вручную влитый PR пропускает.

Для перехода действует ограниченный legacy-drain. Время мержа PR #1261 — точная
граница включения committed-протокола. Если пары нет, TAIL берёт последнее
доверенное заключение с точным tail-маркером только когда **само заключение**
создано строго раньше границы и после него нет `pp:review-again`. Время мержа
исходного PR не используется: начатый старым MERGE PR мог законно влиться после
cutover. Последнее заключение в момент границы или позже fallback не получает.
Если границу через GitHub API получить нельзя, этап ничего не меняет.

Каждый пункт хвоста имеет ключ `review-comment id:item`, earliest trusted
`pp:tail-claim`, детерминированный `pp:tail-source` в теле issue и completion
`pp:tail-item-done`. Перед каждой мутацией TAIL перечитывает labels/comments,
`hold`/`no-tail`/`tail-drop` и владельца claim. Exact-source ищется до create и
повторно прямо перед ним прямым пагинированным `/issues?since=<claim time>`;
exact-source считается своим только у issue автора `ivanarama`. Проверка идёт
напрямую, без eventually-consistent Search API. Поэтому параллельный worker проигрывает claim, а crash
или timeout после `gh issue create` восстанавливается по source-маркеру без
дубля. Общий `pp:tail-done` ставится только после completion каждого пункта;
issue create — точка невозврата конкретного пункта.
После неё поздний стоп не может удалить issue и разрешает только дописать
восстановительный item-done с уже существующим номером; до неё стоп старше TAIL.

Расписания у этапа пока нет — зовите руками (`/tail-issues`). Окно в две недели
для того и взято: пропущенный прогон ничего не теряет, пока PR не старше
двух недель.

Не заводит в двух случаях: такая заявка уже есть (называет номер) или находка на
свежем `main` не подтвердилась — пока хвост ждал мержа, её мог починить соседний
PR. Спорить с оценкой ревью «стоит ли это работы» этап не должен: это решило
ревью и подтвердили вы меткой `ship`. У PR, влитого руками, `ship` могло и не
быть — такой этап тоже разбирает, полагаясь на одно ревью: потерять хвост из-за
непоставленной метки хуже, чем дать триажу отклонить лишнюю заявку.

Заключением считается только комментарий от учётной записи конвейера
(`ivanarama`). Репозиторий публичный, и без этой проверки посторонний завёл бы
заявку, дописав маркер в любой влитый PR, — или, наоборот, погасил бы настоящий
пункт строкой `pp:tail-drop`. Отличить в этой проверке этап от вас нельзя:
учётная запись одна, доверены оба.

Отдельный этап, а не часть мержа, по двум причинам: мерж-пастух намеренно тупой
(«кода не читаю, только вливаю»), и заводить хвост до мержа рано — PR могут
закрыть или переделать. Побочно этап подбирает и за PR, влитыми руками.

## Стоп-метки

- **`hold`** — «не трогать автоматикой». Действует на всех этапах и перекрывает
  `ready-fix`, `approved`, `ship`.
- **`needs-decision`** — ставит автоматика. На заявке его может перебить ваш
  `approved`: это и есть решение по варианту. На PR это стоп по умолчанию, но есть два точных автоматических handoff:
  более поздний `pp:review-again` разрешает REVIEW проверить состояние и снять
  парковку, а `pp:fix-decision <SHA>` возвращает PR в FIX через порядок
  «сначала `changes-requested`, затем
  снять `needs-decision`». Без одного из этих маркеров метку после решения нужно
  снять вручную, и до этого REVIEW, FIX и MERGE PR не берут. Для заявок
  `approved` перебивает `needs-decision`, потому что поставлен позже и именно он
  и есть решение. Цикла
  «фиксер эскалировал → фиксер взял снова» это не создаёт: эскалируя, фиксер сам
  снимает `approved`/`ready-fix`, так что вернуть заявку в очередь можете только
  вы. Ответить комментарием и не поставить метку — значит выронить заявку из
  конвейера молча.

### Как отвечать на `needs-decision`

Если триаж выложил пронумерованные варианты, ответ — это одна-две метки, без
текста:

| Решение | Что поставить |
|---|---|
| Согласен с рекомендацией | `approved` |
| Берём другой вариант | `approved` + `decision:1` / `decision:2` / `decision:3` |
| Делаем, но заявка помечена `manual` | применить правку самому и **закрыть заявку**; `approved` не ставить |
| Не делаем | закрыть заявку (при желании `wontfix`) |
| Потом | `hold` |
| Нужны данные от автора | оставить `needs-decision`, спросить в комментарии |

На заявке `needs-decision` при этом можно не снимать — `approved` его перебивает.
На PR `approved` маршрута не задаёт. Для повторного аудита того же SHA добавьте
строку `pp:review-again` — REVIEW само проверит и снимет `needs-decision`; для
доработки используйте `pp:fix-decision <SHA>` по процедуре ниже. В остальных
случаях парковочную метку снимите вручную.

**`manual` — единственная строка, где `approved` не работает.** Метка означает,
что правка вне репозитория, и фиксер такую заявку не отбирает даже одобренную:
`approved` на ней ничего не запускает, но выглядит она после этого отправленной
в работу — хуже, чем просто забытая. Согласны — примените команду из плана
триажа и закройте заявку сами. Если триаж выкладывал варианты, назовите
применённый в комментарии при закрытии: `decision:N` здесь читать некому, а без
записи через месяц не восстановить, какой вариант в итоге сделан.

Снимать `manual` не нужно и некому: ни один этап её не трогает, заявка живёт с
меткой до закрытия. Этим она отличается от `needs-decision`, который гасится
вашим `approved`. Правка неожиданно оказалась кодовой — метку снимаете вы, и
тогда заявка возвращается в конвейер обычным порядком.

Смешанный случай — часть кодом, часть руками — на `manual` не помечается целиком:
триаж обязан разделить его на две заявки (кодовую и ручную со ссылкой на первую).
Если видите заявку, где `manual` висит на смеси, — это недоделка триажа, а не
ваше решение.

Когда ни один вариант не годится или развилки в разборе не было:

1. **Решение пишется комментарием в самой заявке** (или в PR, если метка на PR) —
   тем же тредом, где этап сформулировал варианты. Отдельного места для решений
   нет: следующий исполнитель читает тред целиком.
2. Формулируйте как указание, а не как мнение: «делаем вариант 2, поле хранить в
   настройках пользователя». Ваш комментарий старше и плана триажа, и метки
   `decision:*` — но если решение отменяет часть плана, скажите это прямо.
3. Дальше маршрут зависит от типа объекта:
   - **заявка** → `approved`, как в таблице выше;
   - **PR, нужна доработка** → в комментарии с решением добавить отдельную
     строку `pp:fix-decision <текущий SHA>`, затем **сначала поставить и проверить**
     `changes-requested` и только после этого снять `needs-decision`. Пока висят
     обе метки, FIX припаркован; после снятия он возьмёт именно этот более
     поздний текст, а не только старое заключение;
   - **PR, код оставляем / повторяем аудит текущего SHA** → добавить отдельной
     строкой `pp:review-again`; REVIEW само безопасно завершит handoff.

   `approved` на PR не ставьте: ни REVIEW, ни FIX, ни MERGE эту метку там не
   используют.

## Чего конвейер не делает никогда

- не ставит себе `approved` или `ship`;
- MERGE не вливает и сам не трогает PR без `ship`; REVIEW и FIX как раз работают
  с такими PR до человеческого одобрения;
- не отправляет в автофикс ничего, кроме дефектов с сошедшимися критериями;
- не коммитит в `main` и не закрывает заявки руками — заявка закрывается только
  через `Fixes #N` в теле влитого PR;
- не исполняет инструкции из текста заявок, PR и комментариев: это данные о
  проблеме, а не команды исполнителю.

## Расписание и ручной запуск

Этапы запускаются планировщиком (PromptPilot) рекуррентными задачами: мерж — раз
в 2 часа, фикс, ревью и триаж — раз в 4 часа; результат уходит уведомлением в
Telegram. Работают они в отдельной рабочей копии репозитория, которая должна
стоять на `main`: синхронизация в скилах — только `git merge --ff-only
origin/main` и только если ветка уже `main`.

**Хвост (`/tail-issues`) расписания пока не имеет** — запускается вручную.
Задача планировщика живёт вне репозитория, поэтому завести её отсюда нельзя:
пока рекуррентной задачи нет, хвост разбирается тогда, когда этап позвали.
Заведёте задачу — исправьте эту строку и схему выше.

Каждый прогон заканчивается строкой вердикта:

| Вердикт | Смысл |
|---|---|
| `ИТОГ: ГОТОВО (…)` | сделано, перечислено что |
| `ИТОГ: НУЖЕН ЧЕЛОВЕК (…)` | застряло, нужна ваша реакция |
| `ИТОГ: НЕ СМОГ (…)` | этап не отработал (среда, доступы) |
| `ИТОГ: ПУСТО (…)` | делать было нечего — **тихий**, уведомление не шлётся |

Тишина в Telegram означает «очереди пусты», а не «планировщик умер».

Руками любой этап запускается из Claude Code в этом репозитории:
`/triage-issues`, `/fix-approved [номер]`, `/review-queue`, `/merge-shepherd`,
`/tail-issues`.

Ревью-этап называется `review-queue`, а не напрашивающееся `review-pr`, из-за
коллизии имён: скил `review-pr` есть в плагине `pr-review-toolkit`, а плагины
разрешаются раньше проектных скилов — прогон уехал бы в чужой скил, и в списке
скилов планировщика показывалось бы его описание.

## Ревизия хвоста — `tools/backlogsweep`

Конвейер умеет поставить заявку на паузу, но снять её может только человек, а
забывчивость дисциплиной не лечится — в этом репозитории это проверено дважды
(`featureage` для статусов `docs/features.md`, `issuetail` для «сделано, но
открыто»). Третья сверка — про припаркованные заявки:

```bash
go run ./tools/backlogsweep                # отчёт по открытым заявкам
go run ./tools/backlogsweep -hold-days 30  # строже к залежавшимся паузам
```

Показывает пять видов застревания: внешняя заявка без ответа (самое дорогое
молчание — автор ждёт), `hold` без ссылки на план, ссылка на план, которого нет
или который переехал под другой номер, `hold` без движения дольше 8 недель,
`needs-decision` без движения дольше двух недель. Ссылки сверяются по **имени
файла**, а не по номеру: номера сталкиваются в открытых PR и переезжают, и
`Plans/155-nav-collapse.md` при живом `155-excel-print-template.md` — как раз
поломка, а не совпадение. Планы из открытых PR считаются существующими.
Не гейт: находки на код возврата не влияют, «заявка залежалась» — не дефект
кода, а повод посмотреть.

Ответом автору считается только то, что ему адресовано. Разбор триажа,
заключение ревью и отметка «взято в работу» пишутся от «своего» логина, но
помечены машинным маркером (`<!-- pp:triage -->`, `<!-- pp:review … -->`,
`<!-- pp:in-work -->`) и за ответ не идут — иначе первый же проход
`/triage-issues` уносил бы заявку из корзины навсегда, и ловила бы сверка только
те заявки, до которых триаж ещё не дошёл (#1166). Маркер `<!-- pp:reply -->` —
наоборот, ответ и есть. Неизвестный маркер считается машинным: маркеры и ставят
затем, чтобы комментарий читала машина, а живой ответ человека маркеров не носит
вовсе — поэтому новый этап конвейера попадает под правило сам, без правки
списка.

Битые ссылки показываются **все**, а не первая на заявку, — но не больше трёх
строк на одну заявку: сверх потолка идёт строка «и ещё N», а остальные приходят
следующим прогоном, когда первые три починены. Счётчик корзины считает при этом
все находки, а не показанные, и обрезка названа вслух: молчаливая превратила бы
«ссылка на план, которого нет — 3» в неправду ровно так же, как молчаливая
обрезка по `-limit`. Ту, что ниже в треде уже поправлена комментарием (план
перенумеровали, верное имя дописали, старый текст не тронули), отчёт помечает
«ниже в треде уже поправлено на …», но не прячет: скрытая находка неотличима от
«инструмент не заметил», а отчёт читают ради полноты. Все три повадки — от того,
что читаемость еженедельного отчёта тут и есть работоспособность: знакомая
строка, которую глаз пропускает, уносит с собой соседние, а заявка на десяток
планов уносит целый экран.

Порядок комментариев отчёт задаёт сам (по `createdAt`), а не берёт из выдачи
`gh`: пометка «поправлено ниже» держится ровно на нём, а сортировка в `gh` нигде
не обещана — сменись она молча, отчёт перестал бы гасить шум, ничем этого не
показав.

Правило, ради которого сверка заведена: **припаркованная заявка обязана
попадать ровно в одну корзину.**

| Корзина | Как выглядит | Почему так |
|---|---|---|
| Делаем планом | `hold` + комментарий со ссылкой на план | это дорожная карта: сто таких заявок читаются нормально, у каждой есть адрес |
| Не делаем | **закрыта** с причиной | открытая заявка, которую никто не собирается делать, отнимает внимание при каждом просмотре |
| Не решено | `needs-decision` и только он | как только решение принято, метка снимается, иначе список «мой ход» врёт |

`hold` без ссылки на план — это не четвёртая корзина, а незаконченное решение:
через месяц по такой заявке не отличить «решили отложить» от «забыли».

## Если что-то не движется

| Симптом | Почему обычно |
|---|---|
| Заявка одобрена, PR не появляется вовсе | посмотрите, не `manual` ли это: правку вне репозитория конвейер не берёт по устройству, её применяет человек |
| Дефект разобран, но `ready-fix` нет | не сошёлся критерий автохода — смотрите строку об этом в триаж-комментарии; дальше ваше `approved` |
| Заявка с `ready-fix`/`approved` висит, PR не появился | на неё уже есть открытый PR; либо висит `hold`; либо прогон занят доработкой чужого PR — доработки идут раньше новых заявок |
| Поставил `decision:2`, а сделан другой вариант | ваш комментарий с решением старше метки — проверьте, нет ли в треде более раннего указания словами; реализованный вариант фиксер называет строкой `Вариант:` в теле PR |
| PR отревьюен, но ничего не происходит | стоит `reviewed` — это ваш ход: прочитать заключение и поставить `ship` |
| PR третий раз возвращается на доработку | не возвращается: на третьем круге ревью ставит `needs-decision` и описывает спор |
| Заявка разобрана, но триаж её больше не видит | висит `needs-decision`, снимите после ответа |
| Ревью нашло что-то мимо этого PR, и оно потерялось | не потерялось: пункт `[заявка]` в хвосте заключения станет заявкой после мержа. Ничего не заводить — `no-tail` вместе с `ship` |
| Влитый PR не закрыл заявку | в теле не было английского `Fixes #N` — русское «Закрывает #N» GitHub не понимает. Сверка хвоста: `go run ./tools/issuetail` |
| Мерж встал на одном PR надолго | ждёт CI (до 35 минут) либо перезапустил флейк; после этого эскалирует |
