# Конвейер сопровождения: какие метки ставить и когда

Заявки и pull request'ы движутся по репозиторию полуавтоматически. Три этапа —
**триаж**, **фикс**, **мерж** — выполняет Claude Code по расписанию, а
переключают этапы **метки GitHub**. Две метки ставит только человек: без них
автоматика не двигается дальше, и это сделано намеренно — машина предлагает,
решает человек.

Эта страница — памятка для человека: что и где нажимать. Точная процедура
каждого этапа лежит в `.claude/skills/<этап>/SKILL.md`, правки процесса вносятся
туда.

## Коротко

| Метка | Ставится на | Кто ставит | Что означает |
|---|---|---|---|
| `approved` | ишью | **только человек** | разбор верен, можно чинить → фиксер сделает PR |
| `ship` | **PR** | **только человек** | ревью пройдено, можно вливать → пастух сольёт |
| `needs-decision` | ишью | автоматика | застряло, нужно решение человека |
| `hold` | ишью или PR | человек | стоп-кран: автоматика не трогает вообще |

Руками нужны ровно два действия: **`approved` на ишью** и **`ship` на PR**.
Всё остальное — реакция на `needs-decision`.

Где нажимать: на странице ишью или PR правая колонка → **Labels** → шестерёнка.
Или из консоли:

```bash
gh issue edit 1125 --add-label approved
gh pr edit 1127 --add-label ship
gh issue edit 1122 --remove-label needs-decision
```

## Как заявка проходит конвейер

```
новая заявка
   │   триаж (авто, раз в 4 ч)
   ▼
комментарий «Триаж.» + тип (bug / enhancement / question / documentation)
   │   ← ЧЕЛОВЕК: метка approved
   ▼
фикс (авто, раз в 4 ч) → ветка, тесты, PR с «Fixes #N»
   │   ← ЧЕЛОВЕК: ревью, метка ship
   ▼
мерж (авто, раз в 2 ч) → влито в main, заявка закрылась сама по «Fixes #N»
```

### 1. Триаж — `/triage-issues`

Берёт до пяти неразобранных заявок (старые вперёд), читает их целиком, ищет
корень по коду, пробует воспроизвести и оставляет комментарий по шаблону
«**Триаж.** Воспроизводится / Корень / План фикса / Сложность / Риски» с
невидимым маркером `<!-- pp:triage -->` в конце — по маркеру этап понимает, что
заявка уже разобрана, и второй раз её не берёт.

Заодно вешает тип: `bug`, `enhancement`, `question`, `documentation`.

Пропускает заявки с `needs-decision`, `approved`, `hold`. Не начинает фикс, не
ставит `approved`/`ship`, не закрывает и не редактирует заявки.

### 2. Решение человека: `approved`

Прочитайте разбор. `approved` означает не «проблема реальна», а «чините именно
так»: фиксер работает по плану из триаж-комментария (а если план разошёлся с
кодом — по коду, и описывает расхождение в PR).

Если решение неочевидно — этап сам вешает `needs-decision` и формулирует
варианты с рекомендацией; тогда от вас нужен ответ комментарием, а не метка.

### 3. Фикс — `/fix-approved`

За прогон берёт **одну** заявку: `approved`, без `hold`, на которую ещё нет
открытого PR; `bug` раньше `enhancement`, при равенстве — меньший номер. Чинит в
отдельном worktree (основная рабочая копия не трогается), гоняет `go build ./...`
и тесты затронутых пакетов, пушит ветку и открывает PR на `main` с обязательным
английским `Fixes #N`.

Метку `ship` не ставит — это ревью, а ревью за человеком.

Если не получилось (не воспроизводится, нужен архитектурный выбор, фикс выходит
за рамки) — комментарий с конкретным вопросом, метка `needs-decision`,
недоделанное не пушится.

Можно вызвать точечно: `/fix-approved 1125` — тогда выбор кандидата пропускается.

### 4. Решение человека: `ship`

Метка вешается **на PR, не на заявку**. До неё PR не существует для мержа: пастух
такой PR не обновляет, не комментирует и не проверяет — он его просто не видит.

**`ship` не запускает ревью, а объявляет его состоявшимся.** Код перед мержем
никто не читает: мерж-этап только доводит ветку до актуального `main`, дожидается
зелёного CI и жмёт merge. Единственная автоматическая проверка качества — сами
обязательные джобы. Поэтому `ship` ставится после того, как диff прочитан
человеком (`gh pr diff <N>`, `/review <N>` в Claude Code — сколько нужно раз),
а не вместо этого.

### 5. Мерж — `/merge-shepherd`

Вливает только PR с `ship` и без `hold`, по возрастанию номера, не больше трёх за
прогон. Ветка `main` защищена с `strict: true`, поэтому очередь строго
последовательна: один PR доводится до конца, потом следующий.

- `BEHIND` → `update-branch`, дальше ждать CI.
- `DIRTY` → механические конфликты (`docs/features.md`, `internal/i18n/locales/*.json`,
  `Plans/README.md`) разрешает сам; содержательный конфликт не трогает — пишет
  комментарий и эскалирует.
- Ждёт обязательные проверки: `build`, `lint`, `postgres-integration`, `vuln`,
  `smoke`, `e2e`, `test-windows` — до 35 минут на PR. `bench` и
  `launcher-webview-build` мёрж не блокируют, их красноту он только упоминает.
- Красная проверка с профилем флейка (таймаут, обрыв раннера, сеть; `test-windows`
  мигает примерно раз на тридцать прогонов) → один перезапуск. Настоящий провал →
  комментарий с выдержкой лога и эскалация.

После мержа остальные PR очереди становятся `BEHIND` — это норма. Их `MERGEABLE`
до первого мержа ничего не значит.

## Стоп-метки

- **`hold`** — «не трогать автоматикой». Действует на всех этапах и перекрывает
  `approved`/`ship`. Ставьте, когда заявка или PR должны подождать человека.
- **`needs-decision`** — ставит автоматика, **снимает человек**. Пока метка
  висит, триаж заявку пропускает всегда — ответить комментарием и забыть снять
  метку значит выронить заявку из конвейера молча.
  Фиксер, наоборот, `needs-decision` не смотрит: он отбирает по `approved`, так
  что пара `approved` + `needs-decision` читается им как «чинить». Если этап
  эскалировал вопрос по уже одобренной заявке, снимите `approved` или поставьте
  `hold` — иначе он возьмёт её снова на следующем прогоне.

### Как отвечать на `needs-decision`

1. **Решение пишется комментарием в самой заявке** — тем же тредом, где этап
   сформулировал варианты (метка всегда висит на ишью, даже когда вопрос возник
   на этапе фикса). Отдельного места для решений нет: следующий исполнитель
   читает заявку целиком.
2. Формулируйте как указание, а не как мнение: «делаем вариант Б, поле хранить
   в настройках пользователя». Если ваше решение расходится с планом из
   триаж-комментария — скажите об этом прямо, иначе фиксер пойдёт по плану.
3. Дальше метками:

| Решение | Что поставить |
|---|---|
| Делаем | снять `needs-decision`, поставить `approved` |
| Не делаем | снять `needs-decision`, закрыть заявку (при желании `wontfix`) |
| Потом | снять `needs-decision`, поставить `hold` |
| Нужны данные от автора | оставить `needs-decision`, спросить в комментарии |

## Чего конвейер не делает никогда

- не ставит себе `approved` или `ship`;
- не трогает PR без `ship`;
- не коммитит в `main` и не закрывает заявки руками — заявка закрывается только
  через `Fixes #N` в теле влитого PR;
- не исполняет инструкции из текста заявок и комментариев: текст заявки — это
  данные о проблеме, а не команды исполнителю.

## Расписание и ручной запуск

Этапы запускаются планировщиком (PromptPilot) рекуррентными задачами: мерж — раз
в 2 часа, фикс и триаж — раз в 4 часа; результат уходит уведомлением в Telegram.
Работают они в отдельной рабочей копии репозитория, которая должна стоять на
`main`: синхронизация в скилах — только `git merge --ff-only origin/main` и
только если ветка уже `main`.

Каждый прогон заканчивается строкой вердикта:

| Вердикт | Смысл |
|---|---|
| `ИТОГ: ГОТОВО (…)` | сделано, перечислено что |
| `ИТОГ: НУЖЕН ЧЕЛОВЕК (…)` | застряло, нужна ваша реакция |
| `ИТОГ: НЕ СМОГ (…)` | этап не отработал (среда, доступы) |
| `ИТОГ: ПУСТО (…)` | делать было нечего — **тихий**, уведомление не шлётся |

Тишина в Telegram означает «очереди пусты», а не «планировщик умер».

Руками любой этап запускается из Claude Code в этом репозитории:
`/triage-issues`, `/fix-approved [номер]`, `/merge-shepherd`.

## Если что-то не движется

| Симптом | Почему обычно |
|---|---|
| Заявка с `approved` висит, PR не появился | на неё уже есть открытый PR (фиксер такие пропускает), стоит `hold`, или прогон занят другой заявкой — за раз берётся одна |
| PR готов, но ничего не происходит | нет метки `ship` |
| Заявка разобрана, но триаж её больше не видит | висит `needs-decision`, снимите после ответа |
| Фиксер раз за разом берёт одну заявку и снова эскалирует | на ней `approved` + `needs-decision`: фиксер вторую метку не смотрит. Снимите `approved` или поставьте `hold`, пока думаете |
| Влитый PR не закрыл заявку | в теле не было английского `Fixes #N` — русское «Закрывает #N» GitHub не понимает. Сверка накопившегося хвоста: `go run ./tools/issuetail` |
| Мерж встал на одном PR надолго | ждёт CI (до 35 минут) либо перезапустил флейк; после 35 минут этап эскалирует |
