# Длинные имена таблиц и колонок (#1946, #1949)

PostgreSQL обрезает идентификатор до 63 байт. Кириллическая буква занимает 2
байта, поэтому в предел помещается около 31 буквы. До #1949 платформа отдавала
в базу имя как есть: SQLite хранила его целиком, PostgreSQL — обрезанным. Две
колонки или таблица и её табличная часть с общими первыми 31 буквами на
PostgreSQL сливались в одно имя, и схема не создавалась.

С #1949 правило одно для обеих СУБД (`metadata.SQLIdent`):

- имя не длиннее 63 байт не меняется — все конфигурации с короткими именами не
  затронуты;
- длиннее — `<начало по границе символа>_<8 hex sha256(полного имени)>`, не
  больше 63 байт, детерминированно.

Логическое (полное) имя по-прежнему видно в метаданных, запросах и выгрузках;
меняется только физическое имя в базе.

## Матрица: какая база или архив что получает

| Что есть | Что делает новая платформа |
|---|---|
| Свежая база SQLite или PostgreSQL | Создаёт сразу короткие имена. Ничего переносить не нужно. |
| База без длинных имён (любая СУБД) | Ничего не меняет. |
| Старая база SQLite с длинными именами (хранятся целиком) | `migrate` переименовывает таблицы и колонки `ALTER … RENAME` в короткие. Данные не копируются, индексы и внешние ключи следуют за таблицей, карта полей `_schema_fields` обновляется вместе с ними. |
| Старая база PostgreSQL с обрезанными именами, обрезка однозначна | То же: обрезанное имя → короткое. |
| Старая база PostgreSQL, где на одно обрезанное имя претендуют два поля или таблица и её табличная часть | **Отказ.** Чьи данные лежат под общим именем, не установить. Миграция останавливается до переименования в этой таблице. На практике такая база не могла быть создана: PostgreSQL отказывал на `specified more than once`. |
| Действующее короткое имя совпадает с прежней обрезкой другого длинного имени | **Отказ до переименования.** Короткая таблица или колонка сохраняет свои данные; они не присваиваются новому объекту. |
| В базе есть и новая (короткая) таблица или колонка, и прежняя с данными | **Отказ.** Какие данные верные, не установить. Прежняя без данных не мешает: переносить нечего. |
| Архив `.obz` новой платформы | Загружается как есть, включая сохранённые колонки удалённых реквизитов. Длина короткого имени сама по себе не означает старую обрезку. |
| Архив `.obz` старой базы SQLite (полные имена) | Импорт переводит полное имя в короткое по тому же правилу. Так переносится база SQLite → PostgreSQL. |
| Архив `.obz` старой базы PostgreSQL (имена обрезаны до 62–63 байт) | **Отказ импорта при точном совпадении с прежней обрезкой длинного имени из конфигурации архива.** Полного имени в данных нет, привести колонку к реквизиту нельзя. Раньше импорт заводил под обрезанным именем новую текстовую колонку, и данные уходили мимо реквизита. Решение — обновить эту базу новой платформой (`migrate`) и снять архив заново. |

Платформа нигде не угадывает: неоднозначное имя — отказ с текстом, что именно
и почему.

## План миграции рабочей базы

1. **Инвентаризация.** Новым бинарём, базу не трогая:

   ```bash
   onebase migrate --project <dir> --db <строка> --dry-run   # или --sqlite <файл>
   ```

   Раздел «Длинные имена (#1946)» перечисляет каждое переименование
   `таблица|колонка <прежнее> → <новое>` и каждый конфликт с причиной. Нет раздела
   — переименований и конфликтов для текущей конфигурации нет. Проверяются
   сущности, табличные части, регистры накопления, сведений, бухгалтерии и
   включённые таблицы итогов с их колонками.
2. **Конфликты.** Если они есть, миграция на них откажет. Разберите вручную:
   какие данные верные, перенесите их и удалите лишнюю таблицу или колонку.
   Платформа этого не делает за вас.
3. **Резервная копия** — обязательно, см. ниже.
4. **Миграция.** Остановить сервер, `onebase migrate` новым бинарём, запустить
   сервер. Каждое переименование пишется в лог («длинное имя таблицы
   сокращено», «длинное имя колонки сокращено»).
5. **Проверка.** Повторный `migrate --dry-run` не показывает раздела «Длинные
   имена»; объекты с длинными именами открываются со своими данными.

Переименование — несколько `ALTER … RENAME`, оно быстрое и не зависит от
объёма данных.

## Резервная копия и откат

Старая платформа не читает переименованную базу: она ищет прежние имена.
Поэтому откат — только восстановление копии, снятой **до** миграции, вместе со
старым бинарём.

| СУБД | Копия до миграции | Откат |
|---|---|---|
| SQLite | копия файла базы при остановленном сервере | вернуть файл и старый бинарь |
| PostgreSQL | `pg_dump -Fc` (или `onebase backup`) | `pg_restore` в чистую базу и старый бинарь |

Архив `.obz` старой PostgreSQL-базы как копию для отката не годится: новая
платформа его не загрузит (см. матрицу), а старая загрузит только в старую
схему.

Внешним потребителям базы (BI, ручной SQL, выгрузки по имени таблицы)
нужно сообщить новые физические имена: их перечисляет шаг инвентаризации.
