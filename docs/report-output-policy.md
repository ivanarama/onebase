# Обязательная политика вывода ПДн в отчётах

Встроенные отчёты и REST v2 отчётов скрывают поля с `pii: true` или
`report_pii: true` для всех
пользователей, включая администратора, `disclose` и `read: full`. Это отдельная
политика отчёта; права обычной карточки, исходные данные и обмен не меняются.
Полный адрес скрывается целиком: выделение города из произвольной строки не
считается безопасным. `report_pii` — отдельный признак поля для данных,
которые разрешены на карточке, но запрещены в отчётах, например дома/корпуса.
Он не меняет обычный `pii`, его условные исключения и ролевой `field_access`.
Безопасные Город/Улица остаются отдельными полями без отчётного запрета.

Строки представления объекта с ПДн также считаются защищёнными: произвольный
текст может содержать телефон/дом/квартиру. Его нельзя восстановить через
разрешение UUID. Отчётная ссылка получает техническую подпись UUID; сам UUID
и переход сохраняются. Разрешаются только ссылки с типом, доказанным
компилятором (`Result.RefColumns`); произвольная строка, похожая на UUID, не
разрешается поиском совпадения во всех справочниках.

Защищённое поле в SQL-отборе, сортировке, группировке или агрегате отклоняет
отчёт до чтения строк. Простая проекция маскируется перед компоновкой и
выгрузкой. Для UNION/подзапросов с защищённым источником пока применяется
отказ, поскольку поколоночное происхождение не доказано. Если у объекта нет
явного `presentation`, все строковые кандидаты стандартного представления
считаются защищёнными; это консервативное ограничение, а не догадка о том,
какая строка содержит ПДн.

Виртуальная таблица может использовать защищённые измерения/период внутри
PARTITION/выбора записи, даже если запрос содержит только SUM публичного ресурса.
До отдельного доказательства и authorization этих control dependencies отчётный
gate отклоняет VT с защищёнными metadata. Это консервативный STOP, не готовность
совместимого ENG16. Обычные Query и физические таблицы с неиспользованным ПДн
этой проверкой не меняются; проекции ТЧ не считаются срезом регистра.

Общий источник решений для универсальных отборов:

Первичная форма параметров нативного отчёта применяет обязательную маску до
вычисления подписей ссылок, включая выбранный UUID за пределами первой страницы.
Защищённый объект получает техническую подпись UUID и порядок по UUID до лимита:
изменение скрытой подписи не меняет состав страницы. Общие справочники без ПДн
сохраняют свой порядок; права чтения, RLS и обычные подборы карточек не меняются.
Это не закрывает отдельную границу интерактивного поиска/preview ссылок отчёта.

```go
access.ReportOutputDecisions(meta *metadata.Entity) map[string]access.FieldDecision
access.ReportOutputFilterAllowed(meta *metadata.Entity, field string) bool
access.ReportOutputQueryMaskPlan(user *auth.User, result query.Result,
    lookup func(kind, name string) *metadata.Entity) access.QueryMaskPlan
```

`ReportOutputFilterAllowed` проверяет исходное поле. Вызывающий код обязан
доказать lineage/тип выходной колонки и применить обычные object/row/field
права. Alias/preset не заменяет доказательство. UUID не разрешает обход маски
самого ссылочного реквизита с `pii: true`. Проверка пресета повторяется на
каждом запуске. Значения масок не дают права фильтровать исходные данные.

HTML, синхронный и фоновый Excel/PDF используют один путь маскирования
нативного отчёта; REST применяет тот же план до JSON/компоновки.

Обработка, исполняющая отчёт/KPI, объявляет `kind: report`. Её обычный HTTP
запуск, managed form-event и offline запуск получают серверный контекст
`access.WithReportOutput`: SQL и чтение реквизитов/представлений через DSL
используют обязательную маску ещё до формирования результата. Нативный
`chart_proc` и фоновые экспорты также получают этот контекст. Обычные
обработки без `kind: report` продолжают применять прежние ролевые правила.

Необходимо явно разметить отчётные обработки и исходные поля. Произвольные
готовые строки из файлов, внешних источников и прикладных констант не имеют
доказанного происхождения; контекст не является универсальным анализатором
ПДн в любом тексте. Такие источники должны возвращать безопасную схему
результата до передачи в отчёт.
