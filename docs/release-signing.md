# Подпись релизов и проверка при обновлении

Что защищает: подмену обновления. До подписи доверие к обновлению равнялось
доверию к аккаунту GitHub — контрольная сумма лежит там же, где архив, и тот,
кто получил доступ к репозиторию, подменял обе.

Цепочка теперь такая: **подпись подтверждает файл контрольной суммы, сумма
подтверждает архив**. Подписывается `.sha256`, а не архив: подпись маленькая, её
тянут до многомегабайтной закачки, и отказ происходит раньше.

Границу стоит понимать точно, чтобы не рассчитывать на большее. Подпись
закрывает подмену файлов уже опубликованного релиза и публикацию в обход
конвейера. Она **не** закрывает того, кто владеет самим конвейером: приватный
ключ лежит секретом сборки, и всё, что проведено в `main`, подписывается
автоматически. Это защита артефактов, а не замена контролю над веткой.

## Чего эта подпись не делает: «Неизвестный издатель»

Есть вторая граница, важная для пользователя, а не для конвейера. Ed25519-подпись
отвечает на вопрос **«тот ли это файл»**. Windows и macOS при первом запуске
спрашивают другое — **«кто его выпустил»**, — и нашего ключа они не знают.
Поэтому непрограммист, скачавший архив браузером, видит «Неизвестный издатель»
(SmartScreen) или «не удалось проверить разработчика» (Gatekeeper).

Разница по существу: `relsign` защищает **обновление**, и проверку делает наш же
установленный бинарь. Первую установку он защитить не может по построению —
нашего кода на машине ещё нет, проверяет ОС, а ей нужен сертификат от
удостоверяющего центра, которому она доверяет.

Это закрывается подписью издателя (Authenticode + нотаризация macOS) — отдельная
статья расходов, разобранная с ценами и порядком действий в
[`Plans/132-code-signing.md`](../Plans/132-code-signing.md) (#988, А2). Там же
бесплатные меры, которые стоит применить до покупки сертификата.

## Разовая настройка (владелец)

```bash
go run ./tools/relsign keygen
```

Выводит два значения:

| Что | Куда положить | Секретность |
|---|---|---|
| приватный ключ | секрет репозитория `RELEASE_SIGNING_KEY` | **никогда** не в git, не в журналы CI, не в issue |
| открытый ключ | переменная репозитория `RELEASE_PUBLIC_KEY` | публичен, вшивается в каждую сборку |

Настройки → Secrets and variables → Actions: приватный на вкладке **Secrets**,
открытый на вкладке **Variables**. Разные вкладки не случайно: переменная видна
в логах сборки, секрет — нет.

Больше ничего делать не нужно: релизный workflow подписывает суммы сам, а
сборка вшивает открытый ключ через `-ldflags -X`.

## Что происходит при обновлении

| Состояние | Поведение |
|---|---|
| ключ вшит, подпись верна | обновление применяется |
| ключ вшит, подпись **неверна** | отказ, архив не скачивается вовсе |
| ключ вшит, подписи в релизе нет | мягкий режим: обновление применяется, в журнал уходит предупреждение |
| ключ не вшит | проверки нет, поведение как до подписи |

Мягкий режим — сознательное решение на время перехода. Если бы проверка стала
обязательной сразу, у всех, кто стоит на версиях без подписи, автообновление
оборвалось бы, и чинить пришлось бы руками на каждой машине. Через несколько
версий режим переключается на жёсткий сборкой с

```
-X github.com/ivantit66/onebase/internal/selfupdate.RequireSignature=1
```

Мягкость касается **отсутствия** подписи, а не её несовпадения: неверная подпись
отвергается всегда, в любом режиме.

## Сборка из исходников и форки

```bash
go build ./cmd/onebase
```

Ключ не вшит → проверка выключена → всё работает как раньше. Контрибьютору не
нужно знать про ключи вовсе.

Форк, который публикует **свои** сборки, генерирует **свою** пару и подставляет
свой открытый ключ при сборке. Тогда его обновление проверяет его же подпись.
Открытый ключ не константа в исходниках именно поэтому: иначе форк собрал бы
платформу с чужим ключом и его собственные релизы отвергались бы его же
бинарём.

Источник обновлений тоже переопределяется — файлом политики рядом с бинарём
(`Policy.Repo`), так что зеркало предприятия работает вместе со своей подписью.

## Смена ключа

Здесь есть ловушка, и она стоит целого парка установленных копий. Уже
установленный бинарь несёт **старый** открытый ключ. Увидев релиз, подписанный
**новым** приватным, он получит несовпадение подписи — а несовпадение
отвергается всегда, в любом режиме (см. таблицу выше). Мягкий режим тут не
спасает: он прощает отсутствие подписи, а не чужую подпись. Поэтому «просто
заменить обе половины и выпустить релиз» обрывает автообновление у всех разом,
и чинить это придётся руками на каждой машине.

Рабочий порядок, пока действует мягкий режим, — провести парк через один
**переходный релиз без подписи**:

1. `go run ./tools/relsign keygen` — новая пара;
2. заменить переменную `RELEASE_PUBLIC_KEY` на новый открытый ключ, а секрет
   `RELEASE_SIGNING_KEY` пока **удалить** (не заменить — именно удалить);
3. выпустить релиз. Шаг подписи пропускается с предупреждением, `.sig` в релизе
   нет; установленные копии проходят по мягкой ветке и обновляются, получая
   бинарь с новым открытым ключом;
4. когда парк перешёл на этот релиз — завести `RELEASE_SIGNING_KEY` с новым
   приватным ключом. Следующие релизы подписаны новым ключом, и обновлённые
   копии их принимают.

Плата за переход честная: релиз шага 3 не подписан, и на время его раскатки
защита не работает. Это осознанное окно, а не побочный эффект, — выпускать его
стоит тогда, когда за релизом есть кому проследить.

После включения жёсткого режима (`RequireSignature=1`) этот путь закрывается:
неподписанный релиз будет отвергнут, и смена ключа потребует ручной
переустановки парка. Значит, ротацию либо проводят **до** переключения на
жёсткий режим, либо закладывают переустановку в план. Это же соображение — ещё
один довод переключать режим не раньше, чем парк установленных версий научится
проверять подпись.

## Проверить подпись вручную

```bash
go run ./tools/relsign keygen            # если нужна тестовая пара
RELEASE_SIGNING_KEY=<приватный> RELEASE_PUBLIC_KEY=<открытый> \
  go run ./tools/relsign sign dist/*.sha256
```

Открытый ключ здесь не для подписи, а для сверки половин пары: без него
рассинхрон при ротации даёт зелёный релиз, который не примет ни один
установленный бинарь. Если переменной нет, утилита предупредит и подпишет —
форку, у которого своя пара, сверять не с чем.

Файл `<архив>.sha256.sig` — это base64 от 64 байт Ed25519 над содержимым
`.sha256`. Проверяется любым инструментом, умеющим Ed25519, — формат
намеренно простой и не завязан на утилиту.
