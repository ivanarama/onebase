# Типизированные расшифровки штатного отчёта (П4)

`drilldowns` объявляется в доверенном YAML отчёта, действует в плоской таблице и
детальных строках обычной компоновки. Это отдельный контракт от payload/snapshot
П1: ТабличныйДокумент и обработчики формы не меняются.

```yaml
name: Платежи
query: |
  ВЫБРАТЬ Подпись КАК Документ, СсылкаРегистратора КАК DocID,
    ВидРегистратора КАК DocType, Задача КАК TaskID,
    ПодписьФото КАК Фото, Картинка КАК ImageID,
    ПодписьЗаписи КАК Запись, ВложениеЗаписи КАК RecordingID
  ИЗ Справочник.ИсточникОтчета
drilldowns:
  - field: Документ
    id_field: DocID
    type_field: DocType
    targets:
      Начисление: {kind: entity, entity: А_Начисление}
      Списание: {kind: entity, entity: А_Списание}
  - title: Открыть задачу
    id_field: TaskID
    target: {kind: entity, entity: А_Задача}
  - field: Фото
    id_field: ImageID
    target: {kind: image}
  - field: Запись
    id_field: RecordingID
    target: {kind: attachment}
```

`field` — колонка отображаемой ячейки. Без `field` обязательна `title`, и действие
появляется в отдельной колонке «Действия» строки. Несколько действий могут вести
к разным документам, справочнику записи, изображению и вложению из одной строки.
Ячейка имеет одно действие. `id_field` содержит UUID; для подписи и UUID лучше
использовать разные алиасы. Алиасы колонок сопоставляются без учёта регистра.

`target` — фиксированная цель, либо `type_field` + `targets` — явная карта
разрешённых типов. Значение источника выбирает **ключ этой карты**, а не имя
сущности или произвольный URL. Неизвестный тип, пустой/невалидный UUID дают
обычный текст вместо ссылки. `kind: entity` разрешает известную метаданную
сущность `catalog` или `document`; реальный kind берётся из реестра. Для записи
разговора, представленной сущностью, используйте entity; для файла — attachment.
Навигация по отдельной строке регистра с составным ключом этим контрактом не
объявляется реализованной.

Ссылка ведёт в `/ui/report/{name}/drilldown`, а не исполняет URL из данных.
Сервер заново проверяет run отчёта, индекс определения, whitelist типа, UUID и
актуальные права цели. Для entity — read + RLS; для image — сохранённый владелец
блоба и существующий blobAllowed, без возможности заменить владельца; для
attachment — существующие права строки-владельца/узкое native uploader-preview.
Изображения без владельца не дают новую ссылку через П4. Затем выполняется
редирект в штатный защищённый маршрут объекта/изображения/скачивания, который
повторяет свои проверки. Отзыв прав действует и для уже сформированной ссылки.

ID/селектор в URL не являются правом доступа или правом записи. Изменённый
клиентом ID может открыть только доступную ему цель того типа, который разрешён
доверенной конфигурацией. Режимы просмотра/редактирования формы не обходят
native серверные права записи. GET расшифровки ничего не записывает, не
исполняет callback и не сохраняет менеджеры/DSL payload.

Служебные `id_field`/`type_field` сохраняются до рендера, чтобы подстановка
представлений UUID не испортила переход. Чтобы не показывать UUID отдельными
колонками, выбирайте видимые detail_fields компоновки в общей runtime-линии.
Показатели групп/итогов и агрегированные pivot-ячейки без однозначной исходной
строки не превращаются в ссылки. Excel/PDF остаются снимками данных, не вызывают
действий; web-переходы не внедряются в выгрузку автоматически.

Доступность на базе определяется точным engine/runtime commit и пройденными
гейтами интеграции. Отсутствие ключа сохраняет прежнюю разметку и legacy detail_link/detail_entity.
При интеграции поверх B20 сохранить П3 DetailFields/rowWithDetail и отсутствие
служебной колонки в плоских 12 деталях; новые ссылки применяются к detail_cells.
