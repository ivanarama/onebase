# Приложение к ТЗ `compsem`: схема обмена с фабрикой знания

Источник: поставка `compsem-vneshnie-2026-11-10.tar.gz` (1854 файла, архив
`compsem/` — данные, инструменты, документы фабрики). Разбор сделан по фактическим
файлам поставки; числа подписаны командами измерения. Файл — приложение к
`examples/compsem/tz.md` (§11 формат обмена, §4 объекты, §13 объёмы).

## 0. Транспорт

1. Все файлы знания — **TSV** (разделитель — табуляция), UTF-8, LF. Строки
   `#` — комментарии; строки-заголовки колонок в поставке **отсутствуют**.
   Импорт читает колонки по позициям; порядок колонок фиксирует манифест.
2. Обязателен **манифест поставки**: номер версии, дата, список файлов
   (имя, контрольная сумма, число строк). Без манифеста приёмка 1.1.1
   отказана (аудит §10).
3. Дельта — файл с полным содержимым объекта (классы, правила, лексикон
   поставляются целиком: файл `rules.txt` перекрывается целиком, номер версии
   обязателен).
4. Импортируемый комплект (12 файлов): `classes.txt`, `rules.txt`,
   `recipes.txt`, `knowledge.txt`, `refusals.txt`, `words.txt`,
   `paradigms.txt`, `verb_classes.tsv`, `verb_bridge.tsv`, `class_map.tsv`,
   `book/lexicon.tsv`, `puzzles.txt` (+ `exam.txt`, `corpus.txt` —
   тестовые тексты).
5. В продукт **не входят**: `taiga.conllu` (157 MB), `opcorpora.dat`
   (413 MB индекс), `dict.opcorpora.txt` (284 MB), `slots.tsv` (99 206),
   `skeletons.tsv`, `patterns.tsv` (входы генератора), `context.txt`
   (производная запись модели), очереди человеку (`verb_classes.queue.tsv`,
   `dict/queue.tsv`, `decisions.tsv`, `class_map.decisions.tsv`),
   `dict/ozhegov.tsv` (словарные материалы), `baranov/`, `koziev/`,
   `abrial/`, `semarkup/`, `shmelev/`, `dialog/`.
6. Русские заголовки колонок, как требовал §11 ТЗ, в поставке нет: колонки
   позиционные. Русские имена колонок задаёт манифест и таблица §1 ниже.

## 2. Форматы файлов

### `classes.txt`

```
КЛ_Локация : КЛ_Предмет {
    СВ_Содержимое : Связь(КЛ_Предмет)*
}
КЛ_Действие : отношение {
    СВ_Исполнитель : Связь(КЛ_Человек, КЛ_Группа) : субъект, агент
    СВ_Объект : Связь(КЛ_Предмет, КЛ_Локация, КЛ_Человек) : объект
    СВ_Время : Граммема(КЛ_Время)
}
```

- объявление: `КЛ_Имя [ : Родитель[, Родитель] ] [ : отношение ] { … }`;
- свойство: `СВ_Имя : Тип[(КЛ_…)[, КЛ_…]][*] [ : роль[, роль] ]`;
- типы: `Текст`, `Граммема(КЛ_…)`, `Связь(КЛ_…)*` (`*` — множественное),
  `Класс`;
- список в скобках `Связь(...)` = domain свойства; имя после `:` = роль
  (псевдоним свойства);
- класс-отношение (`: отношение`) несёт `СВ_Название`, `СВ_Время`,
  `СВ_Отрицание`, `СВ_Действует` и участников; класс-сущность связей не несёт
  (исключения решения человека: `СВ_Состав` на `КЛ_Группа`, `СВ_Содержимое`
  на `КЛ_Локация`);
- падеж, предлог и порядок слов живут в правиле и рецепте, не в классе.

### `rules.txt` — 9 колонок (табуляция)

| # | колонка | содержание |
|---|---|---|
| 1 | вид | `frame` (разбор) или `вопрос` |
| 2 | ключ | лемма в ВЕРХнем регистре (`КУПИТЬ`) или `КЛ_…` (`КТО`, `КЛ_Владение`) |
| 3 | часть речи главного слова | `Глаг`, `Сущ`, `Мест`, `Прил`, `Нареч`, `Союз`, `Числ`, `Предл`, `Частица` |
| 4 | класс главного слова | `КЛ_…` (класс-владелец правила) |
| 5 | позиции | список через `,` (у `вопрос` — варианты через `|`), item: `[предлог+]Разряд[.Падеж][.Род][.КЛ_…]:роль`, напр. `у+Сущ.Род:владелец`, `Сущ.Вин.КЛ_Товар:объект` |
| 6 | заполнение | список через `;`: `купить_1.СВ_Объект=<объект>`, `<объект>.=Предмет_1`, `Владение_1.СВ_Название=принадлежать`, `Человек_1.субъект=#` (`#` — неизвестное) |
| 7 | рецепт печати правила | `субъект{Им,,1};глагол{,,2};объект{Вин,,3}` = `роль{Падеж,Предлог,Порядок}` |
| 8 | профиль | пустой (= `-`) или `один_предмет` |
| 9 | вид ответа | `один` (597+3) или `список` (8+5) |

Вопросительные правила (18 строк: `КТО`, `ЧТО`, `ГДЕ`, `КОГДА`, `СКОЛЬКО`)
связывают вопросительное слово с ролью и порождают экземпляр вопроса с
неизвестным значением (`Человек_1.субъект=#`).

### `recipes.txt`

Строка: `КЛ_ИМЯ[.отр|.глагол|.<лексема>]` + элементы через пробел. Элемент:

- literalное слово (`у`, `нет`, `в`);
- свойство главного слова `Обладатель.Род` (с предлогом — `у.Владелец.Род`);
- участник отношения `@Владение.Обладатель.Род.у` (предлог — 4-й член);
- `<Название>` — глагол;
- суффикс `.отр` читается при `СВ_Отрицание = Да`, `.глагол` — образец печати
  конкретного глагола класса главного слова.

### `knowledge.txt`

```
ограничение 1 профиль: один_предмет {
    условие: Владение_1.СВ_Обладатель == Человек_1 && … && Предмет_1.СВ_Название == Предмет_2.СВ_Название
    следствие: Предмет_1 == Предмет_2
}
```

- вид: `вывод` (дописывает неизвестное `#`), `ограничение` (отбрасывает мир),
  `пересмотр` (перезаписывает записанное); порядковый номер после вида;
  `профиль: X` — привязка к профилю; без профиля — применяется всегда;
- условие — конъюнкция сравнений `==`, `!=`, `<`, `<=`, `>=`, `>` над
  `Экземпляр.СВ_Свойство` и литералами; следствие — одно равенство;
- **`knowledge.txt` фабрикой не валидируется** (`check` его не читает);
  продукт обязан валидировать его при приёмке (аудит §10).

### `refusals.txt` — 3 колонки

`код отказа`, `аргументы (через запятую)`, `шаблон сообщения` (`{аргумент}`).
19 кодов: `форма не распознана`, `нет в лексиконе`, `класс позиции не
покрывает`, `правил нет`, `рецептов печати нет`, `глагол не согласуется с
подлежащим`, `две координации в одном фрейме`, `роли нет свойства`,
`экземпляр без числа`, `парадигмы нет`, `покрытие печати неполное`,
`значение вне класса`, `анафора не разрешена`, `экземпляр знания без класса`,
`свойства знания нет в классе`, … Полный список — справочник `Коды_отказов`.

### `words.txt` — 4 колонки

`ЛЕММА`, `ЧастьРечи`, `КЛ_…`, `Код_парадигмы` (`И Союз КЛ_Союз союз1`,
`ОН Мест КЛ_Человек м10`).

### `paradigms.txt` — колонка 1 код, 2 часть речи, 3 лемма, далее `Граммема=Форма`

```
гл1 Глаг БЕЛИТЬ Наст.3.Един=белит Наст.1.Един=белю Прош.Един.Муж=белил Инф=белить
жместприт Мест ЕЁ Им.Един=её Дат.Един=ней Тв.Един=ней
```

Морфология фабрики — **словарь точных форм**: форма, которой нет в парадигме,
не размечается (отказ `форма не распознана`). Разбор не выводит признаки из
окончания: признаки берутся из записи словаря.

### `verb_bridge.tsv` — 2 колонки

`Форма_корпуса`, `Лемма_UD` (`пошёл → пойти`): мост форм opcorpora к леммам
парадигм.

### `verb_classes.tsv` — 3 колонки

`лемма`, `КЛ_…`, `способ` (`llm`, `check`, `спор: …`). Строка без класса =
спорный глагол; в поставке 47 + 5 спорных, они не импортируются (очередь
человеку — `verb_classes.queue.tsv`, в продукт не входит).

### `class_groups.tsv` / `class_map.tsv` — золотые классы UDC → `КЛ_`

`ANIMAL  КЛ_Животное` (543 группы), `ANIMAL  животное  КЛ_Животное`. Дают код
`UDC` класса и имя класса; продукт хранит как реквизит `Классы.UDC`.

### `book/lexicon.tsv` — 7 колонок

`ЛЕММА`, `ЧастьРечи`, `КЛ_…`, `Код_парадигмы` (пусто = нет парадигмы), `код
UDC`, `частота`, `статус` (`золото` / `парадигмы нет`). Строки со статусом
`парадигмы нет` импортируются с признаком «без парадигмы» (аудит
«лексикограмма без парадигмы» — О).

### `puzzles.txt` — 5 колонок

`id`, `текст-отрывок`, `вопрос`, `ожидаемый ответ`, `профиль`. Ожидаемый
ответ — в формате системы: `ответ: …`, `неопределённо (3): Маша купила
кошку, Петя не купил попугая, Соня не купила кошку`. 19 кейсов;
`exam.txt` — `id`, `вопрос`, `предложение-ответ (дословно)`, `ожидаемый
ответ` (20 кейсов по Чехову; покрытие меряется предложениями-ответами).

## 3. Отображение на объекты OneBase

1. `classes.txt` → `Классы` (Код = `КЛ_…`, Родитель = список родителей,
   ТипКласса = сущность/отношение/значение) + ТЧ `Свойства_класса`
   (Свойство → `Свойства`, Порядок); `Свойства` (Код = `СВ_…`,
   ТипЗначения = Текст/Граммема/Связь/Класс, Множественное = `*`,
   Роль = псевдоним, ТЧ `Domain`).
2. `rules.txt` → `Правила` (Вид = frame/вопрос, Основа правила (Лемма или Класс), ЧастьРечи,
   Класс-владелец, Профиль, ВидОтвета, Версия); колонка 5 → ТЧ `Позиции`
   (Разряд, Падеж, Род, Предлог, Класс_требуемый, Роль, Порядок из колонки
   7); колонка 6 → ТЧ `Действия` (Тип: создание — `<роль>.=Класс_1`, запись —
   `экземпляр.СВ_Свойство=<роль>|литерал|#`, снятие — снятие значения);
   вопросительные правила → `Вопросительные_правила` (Вопросительное слово,
   Роль, Класс вопроса, Варианты позиций, ВидОтвета).
3. `paradigms.txt` → `Парадигмы` (Код, ЧастьРечи, Лемма) + ТЧ `Формы`
   (Граммема, Форма, Порядок); за тем же проведением → регистр
   `Формы_лексикона` (Форма → Лексикограмма, Граммема, Парадигма) — словарь
   точных форм, горячий путь морфологии.
4. `words.txt` + `book/lexicon.tsv` + `verb_classes.tsv` + `class_map.tsv`
   → `Лексикон` (Лемма, ЧастьРечи, Класс, Парадигма, UDC, Частота, Статус,
   СпособНазначения).
5. `verb_bridge.tsv` → `Мосты_форм` (Форма, Лемма, Частота) — чтение в 2.1
   при разборе форм корпуса.
6. `recipes.txt` → `Рецепты` (Класс, Вариант = базовый/отрицание/глагол) +
   ТЧ `Элементы` (Тип: слово/свойство/участник/глагол, Слово, Свойство,
   Падеж, Предлог, Порядок).
7. `knowledge.txt` → `Знания_вывода` (Вид, Номер, Условие, Следствие,
   Профиль → `Профили_вывода`) и `Профили_вывода` (`один_предмет`, `-`);
   константа `Профиль_по_умолчанию` = `-`, значение выбирается в форме
   вопроса.
8. `refusals.txt` → `Коды_отказов` (Наименование, Аргументы, Шаблон);
   записи регистра `Отказы.Причина` обязаны ссылаться на справочник.
9. `puzzles.txt` + `exam.txt` → `Золотые_кейсы` (Вид = кейс/экзамен, Текст,
   Вопрос, Ожидаемый_результат, Профиль, Функция →, Сценарий →). Функция
   назначается при наполнении кейса владельцем (аудит: кейс без функции — П).
10. `corpus.txt` и тексты книги (`book/text.txt`) → документы `Тексты`.

## 4. Проверки приёмки (продукт обязан, фабрика не делает)

1. Файл без манифеста / без номера версии → отказ приёмки (О).
2. `classes.txt`: наследование ацикличное; домены — объявленные классы;
   свойства — только объявления класса-владельца; роль свойству назначена.
3. `rules.txt`: 9 колонок; класс позиции — объявленный класс; роль — роль
   свойства класса-владельца; `<роль>` заполнения — роль колонки 5;
   `экземпляр.СВ_Свойство` — свойство класса, порождаемого этим правилом;
   порядок печати (колонка 7) покрывает все позиции; `#` встречается только в
   вопросительных правилах.
4. `knowledge.txt` (фабрика не валидирует): экземпляр знания — класс
   объявлен; свойство знания есть в классе; сравнения — только над парами
   одного типа; следствием обязан быть один `==`. Отказ приёмки — О.
5. `paradigms.txt`: форма в парадигме уникальна по граммеме; две формы одной
   парадигмы с одинаковой граммемой → О.
6. `book/lexicon.tsv`: лексикограмма без кода парадигмы → О (поставка
   содержит такие строки — они импортируются как «парадигмы нет» и разбор
   таких форм обязан давать отказ, не молчание).
7. Зеркальные регистры (`Формы_лексикона`, `Позиции_правил`) заполняются тем
   же проведением; запись регистра без пары в справочнике → О.
8. `Коды_отказов` — полный набор кодов; код отказа, которого нет в
   справочнике, при приёмке — О.
9. Смена формата поставки (манифест, номер версии, колонки, наборы) обязана
   сопровождаться обновлением `exam.txt`, `puzzles.txt` и сценариев §8 ТЗ;
   приёмка нового формата без обновлённых кейсов и сценариев — О (правило §7
   ТЗ).

## 5. Пробелы поставки, которые закрывает продукт (не фабрика)

1. **Идентичность экземпляра.** Фабрика переиспользует экземпляр по базе
   леммы: `Иван купил книгу. Маша купила книгу.` даёт одну книгу и
   `неизвестно`. Продукт обязан хранить экземпляр с идентификатором
   (`Экземпляр` = лемма + номер в тексте), одноимённые предметы — разные
   экземпляры.
2. **Время, вид, модальность.** `СВ_Время` — литерал правила; модальный
   глагол (`хочет`, `должен`, `будет`) не размечен и порождает совершившийся
   факт. Продукт обязан: клауза с немаркированной модальностью даёт отказ, а
   не факт прошедшего времени; вид и время входят в состояние.
3. **Ответ по глаголу вопроса.** Печатаемая клауза выбирается по роли, глагол
   вопроса проверяется только на наличие: `Маша купила кошку` + вопрос
   `Что купила Маша?` печатает пересказ владения. Продукт обязан печатать
   клаузу того глагола, о котором вопрос.
4. **Передача.** `КЛ_Передача` назначен 10 глаголам, правил датива получателя
   нет; `подарила`, `продала`, `отдала` не размечены. Знание смены владельца
   (пересмотр) отсутствует. Продукт требует knowledge-строк передачи от фабрики; до
   поставки — отказ с кодом.
5. **Канон значений.** `СВ_Признак` пишется то леммой, то поверхностной
   формой (`красный` vs `синяя`); фильтр по признаку ненадёжен. Продукт
   хранит значение свойства канонизованным (лемма) и сравнивает по канону.
6. **Количество и группа.** Числительное не попадает в мир (`Иван купил три
   книги` → мир без `три`), кванторов в лексиконе нет, `СВ_Состав` правилами
   не читается.
7. **Фразеологизмов в поставке нет** (идиомы — не-цель фабрики, §1.4
   спецификации фабрики). Справочник `Фразеологизмы` в продукте остаётся
   пустым; наполняется тестовым набором владельца; тест покрытия цепочки
   фразеологизма выполняется на тестовом наборе владельца, не на фабричных
   файлах.
8. **Не-цели модели (фиксируются как границы продукта):** придаточные
   (`который`, `чтобы`, `когда`), деепричастные и причастные обороты,
   сравнительная степень, модальность, вид, события передачи, адвербиальные
   группы (`быстро`, `за сто рублей`), полисемия предлогов, эллипсис связки,
   идиомы, дискурс и контраст (`а`), отрицание вне действия, кванторы
   (`все`, `каждый`, `несколько`), время как слова (`теперь`, `раньше`).
9. **Качество разбора по экзамену:** прогон экзамена — 11 из 20
   предложений-ответов разобрано, 1 из 20 верных; отказов 261, уникальных
   нераспознанных форм 140. Целевые значения — открытое решение ТЗ (§12),
   прогон фиксируется в `Журнал_разбора`, покрытие меряется
   предложениями-ответами. Состав экзамена и ожидаемые результаты — открытая
   часть: они дорабатываются по ходу разработки и при каждой смене формата
   входных данных (правило §7 ТЗ, проверка приёмки §4.9).

## 6. Требования к доработке формата правил (фабрика)

Измеренное раздувание формата (615 правил, 1701 позиций):

| Позиция (без роли) | Повторов |
|---|---|
| `в+Сущ.Пред` (локация) | 541 |
| `Частица.не` (отрицание) | 265 |
| `Сущ.Вин` (объект) | 254 |
| `Мест.Им` | 208 |
| `Сущ.Им` (субъект) | 156 |
| `Сущ.Тв` | 56 |
| `Прил.Им` (признак) | 33 |
| `у+Мест.Род` (владелец) | 28 |

Уникальных комбинаций (разряд/падеж/предлог + роль) — **38**, позиций в
файле — **1701**: одна и та же позиция повторяется в каждом правиле, где она
нужна (`в+Сущ.Пред:локация` — 541, `Им:субъект` — 349, `Сущ.Вин:объект` —
287, `не:отрицание` — 265). Правил на лемму — **550**, на класс — **47**;
наборов падежей/предлогов в формате **нет** (0 вхождений); правил, которые
наследуются по иерархии, в поставке нет (иерархия 56 классов объявлена, к
ней правила не привязаны).

Требования к формату (продукт обязан читать, фабрика обязана поставлять):

1. **Позиция ссылается на набор**, а не перечисляет падежи/предлоги по
   одному. Вариант записи колонки 5: `Сущ.ВсеПадежи:роль`,
   `Сущ.Места:локация`, `Места+Сущ.Род:владелец`, где `ВсеПадежи`, `Места`,
   `Переход`, `Обладание` — именованные наборы; при разборе учитываются все
   варианты набора. Продукт принимает и поставку с явными падежами (обратная
   совместимость). Раздувание правила перечислением падежей в каждом
   правиле — Предупреждение аудита (П).
2. **Правила пишутся на класс, а не на каждое слово**; класс наследует
   правила родителей; класс может иметь несколько родителей, и родители тоже
   (множественное наследование; порядок родителей задаёт порядок
   наследования). Наследование правил по иерархии обязано быть в формате.
3. **Собственный приоритет**: своё правило класса имеет больший приоритет,
   чем наследуемое; собственное с наследуемым конфликтом не считается
   конфликтом.
4. Приёмка сворачивает позиции с наборами в `Позиции_правил` с индексом по
   набору; свёртка обязана сократить число записей (цель — меньше 1701).
5. **Морфология — словарь точных форм** (колонок `Граммема=Форма`):
   признаки берутся из записи, из окончания не выводятся; для форм корпуса
   обязана поставляться таблица моста (`verb_bridge.tsv`).
6. Обязателен **манифест поставки** (номер версии, дата, список файлов,
   контрольные суммы, число строк) и дельта с номером версии.
7. Манифест несёт **номер версии формата**; при смене формата фабрика обязана
   поставлять обновлённые `exam.txt` и `puzzles.txt`, иначе продукт формат не
   принимает (проверка §4.9, правило §7 ТЗ).
