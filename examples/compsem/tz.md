# ТЗ: compsem — конфигурация OneBase (понимание текста и ответы на вопросы)

Писано по методологии СППР (этапы 1–8). ТЗ описывает, **что** обязано делать
система и в каком формате; механизмы (порядок разбора, разрешение конфликтов)
— решение исполнителя.

Платформа: **OneBase** (аналог 1С:Предприятие 8.3, Go, метаданные YAML + DSL
`.os`, SQLite/PostgreSQL, управляемые формы, регламентные задания, обмен, роли).
Конфигурация **самостоятельная**. СППР используется для управления процессом
разработки (задачи, идеи, ошибки, техпроекты, сценарии, аудит), в продукт не
входит.

## Три уровня задач продукта

1. **Основная** — разбор текста и **сопоставление слов с классами** (иерархия
   классов, наследование, выбор класса по роли и приоритету).
2. **Вспомогательная** — корпусная фабрика (внешний проект: Taiga, opcorpora,
   словари, LLM; производит классы, правила, лексикон, знание; в объём нашего
   проекта не входит, зависимости перечислены в §0.3).
3. **Задача максимум** — шаблоны мышления: правила вывода новых знаний из
   имеющихся и поиск ответов на вопросы.

**Приоритет**: основа продукта — **внутренняя структура представления данных**,
правильное и непротиворечивое представление мира, поддающееся машинному
мышлению по правилам и шаблонам (§4 объекты, §11 правила). Разбор текста и
восстановление текста — **вспомогательные функции**; они обслуживают модель
мира, а не являются целью. Требования к структуре данных и правилам имеют
приоритет над удобством ввода/вывода.

Граница продукта: текст + вопрос → ответ из модели мира.

## 0. Проект

1. Наименование проекта: `compsem` (решение принято). Имя конфигурации
   `compsem`, краткое имя `compsem`, наименование «Семантический разбор текста
   и ответы на вопросы». Требование к будущему имени: слово из двух корней со
   смыслом прошлого и будущего и «запись/чтение ленты событий» — кандидат
   `Бытопись`, решение отложено (§12).
2. Самостоятельная конфигурация (не библиотека, не надстройка). UI даёт
   платформа.
3. Зависимости: **внешний фабричный проект** (классы, правила, лексикон,
   знание, тексты книг) — заготовленные артефакты, передаёт файлами (§11);
   источники фабрики: Taiga (UD-tagger), opcorpora, Ожегов, Баранов,
   УД-концепты, LLM. Продукт читает и исполняет, чужие файлы не правит.
   Поставка: `compsem-vneshnie-2026-11-10.tar.gz` (1854 файла); фактический
   формат описан приложением [`exchange-schema.md`](exchange-schema.md).
   **Формат правил ещё не отвечает требованиям §11** (наборы падежей и
   предлогов, наследование по иерархии) — формат подлежит доработке
   фабрикой, продукт обязан читать расширенный формат (§12).
4. Ответственный: **владелец (заказчик)** — по всем функциям, подсистемам,
   объектам метаданных и целевым задачам.
5. Участники: человек = заказчик/владелец; агент (pi) = исполнитель работ.
   Агент не является профилем пользователя; его работы идут в СППР-задачи
   (§7).
6. Режим разработки: git-репозиторий, ветки `feature/*`, `experiment/*` от
   `main`; приёмка каждой правки `onebase check --project compsem`.
7. Версия платформы: актуальная OneBase; база SQLite (эталонная — тестовая,
   фиксированное знание).
8. Обработчики обновления: нужны (согласование изменений справочников знаний
   с загрузкой из фабрики).
9. Проектные разделы (подсистемы): `Знание`, `Вход`, `Морфология`, `Разбор`,
   `Мир`, `Вывод_и_ответы`, `Журнал_и_аудит`.
10. Тестирование включено, Gherkin-сценарии в конфигурации, справочник
    золотых кейсов публикуется вместе с конфигурацией.

## 1. Автоматизируемые процессы

Автоматизируемый процесс — **понимание текста**. Не автоматизируются нашим
проектом: производство классов/правил/лексикона, разметка корпуса, подбор
LEM-кандидатов (внешний фабричный проект).

### `Разбор_текста`

- **Начало**: текст загружен. **Завершение**: весь текст разобран; каждый
  текст имеет результат — мир или отказ с причиной.
- Шаги (по порядку), тип шага — шаг процесса; каждая строка указывает функцию
  (§2.2) и форму (§5):
  1. **1.2.1 Регистрация_текста** — fb2/txt, разметка клаузы (Taiga-формат)
     или собственный делитель; статус текста `Загружен`. Форма:
     `Тексты (загрузка)`. Исполнитель: `Владелец знания`.
  2. **1.2.2 Разбиение_текста_на_клаузы** — граница клаузы = граница
     предложения.
  3. **1.2.3 Сверка_клауз_с_предложениями** — расхождение = отказ.
  4. **2.1→2.2→2.3→2.4→2.5** — **первый слой, морфология**: морфология
     **готовит входные данные для семантики** — по форме токена (словарь
     точных форм `Формы_лексикона`, при необходимости мост `Мосты_форм`) находит
     кандидатов: лемма, часть речи, класс, парадигма, граммема, признаки
     (разряд, падеж, число, род, предлог); особые формы; фразеологизм
 покрывается цепочкой токенов; **проверка покрытия
     каждого токена**. Морфология вариантов не выбирает и не противоречит —
     она готовит набор вариантов.
  5. **3.1→3.2→3.3→3.4→3.5→3.6** — **второй слой, семантика**: связи клаузы,
     роли (позиция сопоставляется по разряду, предлогу, **набору падежей и
     набору предлогов**), domain-проверка, выбор класса по иерархии
     (множественные родители, наследование правил), разрешение приоритетов
     (собственное правило выше наследуемого), сборка фрейма; семантика берёт
     подготовленные варианты отношений и подставляет в классы, **выбирая
     наиболее подходящие**.
  6. **4.1→4.2→4.3→4.4** — мир: лента событий (создание экземпляра, запись
     свойства, снятие) на моменте = порядковый номер события в тексте;
     состояние на моменте.
- Статусы текста: `Загружен → Разбирается → Разобран | Отказ`; `Разбирается`
  снимается проведениям `Разбор_текста` или отказом; переходы только по
  проведениям/отчётам.
- Параллельность: разбор идёт **по предложениям**; предложения одного текста
  обрабатываются параллельно.
- **Альтернативная группа** (условие: отказ на любом шаге) —
  **6.3 Формирование_отчёта_по_отказам**: процесс завершается результатом
  `Отказ`, текст остаётся в очереди решений для фабрики.
- **Требования к системе по шагам**: каждый токен текста покрыт позицией
  правила; непокрытый токен — отказ с указанием предложения, формы, роли,
  domain; молча потерянный токен запрещён; отказ фиксируется в `Отказы` и
  `Журнал_разбора`; ответ существует только при распознанном тексте и
  распознанном вопросе; система отвечает только тем, что представлено в модели
  мира; ложный ответ хуже отсутствия ответа; **противоречия не мешают**: если
  по одному токену есть несколько вариантов, а по остальным клауза складывается,
  предложение разобрано; неразрешимое противоречие — отказ с причиной.
- **Измерение**: длительность каждого этапа (морфология, связи, классы, мир,
  ответ) пишется в `Журнал_разбора` и показывается отчётом `Скорость_разбора`
  (по предложениям и по тексту).
- **Исполнители**: шаги 2–6 — системный профиль `Ядро`; шаг 1 —
  `Владелец знания`.
- Исходные данные: тексты (fb2/txt, корпусные отрывки) — от владельца;
  классы/правила/лексикон/парадигмы — из фабричного проекта загрузкой.
- Потребители: ответ, лента событий, трасса разбора, очередь отказов (для
  фабричного проекта).
- Узкое место сегодня: знание ручное, разбор не воспроизводится. После
  автоматизации: разбор и ответ воспроизводимы из файлов знаний, отказами
  управление принимает владелец.

### `Ответ_на_вопрос`

- **Начало**: вопрос зарегистрирован (`Владелец знания`). **Завершение**:
  результат записан в `Ответы`, статус вопроса `Отвечен` или `Не_распознан`.
- Шаги: **1.3.1 Регистрация_вопроса** (форма `Форма_вопроса`; вопрос
  регистрируется документом `Текст` с видом `Вопрос`, запись `Вопросы` ссылается
  на него, статус `Зарегистрирован`) → **1.3.2 Постановка_структуры_вопроса** (вопрос
  проходит тот же конвейер: 2.1→…→2.5, 3.1→…→3.6; в структуре выделена роль
  с пустым наполнителем) → **5.3 Сопоставление_вопроса_со_структурой** →
  **4.4 Расчёт_состояния_на_моменте_вопроса** → **5.4 Формирование_ответа**
  (область результата `Форма_вопроса`).
- Статусы вопроса: `Зарегистрирован → Разобран → Отвечен | Не_распознан`;
  переходы только по проведениям/отчётам.
- Требования: `ответ:` существует только при распознанном вопросе; ответ
  только из мира; `неизвестно` — законный ответ; ложный ответ хуже отсутствия.
- Исполнители: 1.3.1 — `Владелец знания`, остальные — `Ядро`.

### `Восстановление_текста` (обратный ход)

- **Начало**: лента событий/состояние заданного текста. **Завершение**:
  восстановленный текст записан в `Восстановленные_тексты`.
- Шаг: **6.4 Восстановление_текста** — лента/состояние → текст с классами и
  фразеологизмами; форма `Восстановление_текста`. Исполнитель:
  `Владелец знания`.
- Восстановленный текст регистрируется как обычный `Текст` и разбирается по
  тем же правилам; расхождение повторного разбора с оригиналом —
  Предупреждение (аудит §10).
- Пустой наполнитель показывается пустым, не «додумывается».

## 2. Логическая модель

### 2.1 Дерево функций

Функция 1-го уровня: **`0 Понимание_текста_и_ответ_на_вопрос`**. Группы 2-го
уровня (6, покрытие полное, без пересечений; в скодках — подсистема):

1. **`1 Приём_данных`** — 1.1 `Приём_знания` (1.1.1–1.1.4),
   1.2 `Приём_текста` (1.2.1–1.2.3), 1.3 `Приём_вопроса` (1.3.1–1.3.2)
   (`Знание`, `Вход`)
2. **`2 Морфологический_разбор`** — 2.1–2.5 (`Морфология`)
3. **`3 Разбор_клаузы_и_классов`** — 3.1–3.6 (`Разбор`)
4. **`4 Построение_мира`** — 4.1–4.4 (`Мир`)
5. **`5 Вывод_и_ответ`** — 5.1–5.4 (`Вывод_и_ответы`)
6. **`6 Отчёты_и_аудит`** — 6.1–6.5 (`Журнал_и_аудит`)

Конечные функции — 33; декомпозиция: уровень 1 → 2 → 3 (у группы 1 — уровень
4), глубина 3. Типы: Ф = Функция, У = Учетный механизм, О = Отчёт.

Проверки модели: у каждой конечной функции есть выход и управляющее
воздействие (правила, domain, приоритет, лексикон, парадигмы); каждая связь —
выход ровно одной функции; функции одной группы равны по объёму; функции
разных групп исполняют разные профили; функций с одинаковой
функциональностью нет.

### 2.3 Профили

1. **`Владелец знания`** — неделимая единица обязанностей (квалификация:
   лингвист): загрузка текста и знания, приёмка классов/правил/лексикона/
   парадигм, запуск разбора, просмотр отказов, формулирование вопросов,
   чтение ответов, лента событий, восстановление текста, отчёты и аудит.
   Совмещение обслуживания допустимо. Профиль = {`Приём_знания`,
   `Приём_текстов`, `Чтение_результатов`, `Обслуживание`}.
2. **`Ядро`** — системный профиль (тип `Система`): проведение `Разбор_текста`,
   движения ленты, состояние, вывод, ответы, журнал — без участия человека.
   Профиль = {`Разбор_и_мир`, `Вывод_и_ответы`}.
3. Компетентности: получение ответа (чтение) отделено от приёмки знания
   (загрузка) — разные роли внутри одного профиля.
4. Внешние участники: фабричный проект — поставщик данных и потребитель
   очереди отказов; профилю пользователей не соответствует. Агент (pi) —
   исполнитель работ, не профиль пользователя.
5. Изменений реального процесса не требуется: владелец формулирует вопрос и
   получает ответ; данные поступают текстами и файлами фабрики.

## 3. Момент и состояние

1. **Момент** = порядковый номер события в тексте (number). Момент не дата;
   события одного текста упорядочиваются номером.
2. **Состояние на моменте** = срез последних: для каждой пары (Экземпляр,
   Свойство) берётся запись ленты с наибольшим Моментом ≤ запрошенного;
   снятые записи в срез не входят.
3. **Пересмотр**: запись того же (Экземпляр, Свойство) с новым значением;
   предыдущее значение снимается, лента хранит оба.
3. Срез последних платформы привязан к дате (период регистра); Момент —
   номер, поэтому срез по Момент выполняется запросом с MAX(Момент) по
   индексу. На объёме §13 ответ за вопрос не должен требовать полного
   сканирования ленты.

## 4. Архитектура

Подсистемы (дерево = функции; ответственный — владелец): `compsem` →
`Знание`, `Вход`, `Морфология`, `Разбор`, `Мир`, `Вывод_и_ответы`,
`Журнал_и_аудит`.

Объекты метаданных (Имя, Синоним, Пояснение, Ответственный — владелец):

- справочник **`Классы`** (иерархический, **множественное наследование**:
  класс может иметь несколько родителей, и родители тоже; порядок родителей
  задаёт порядок наследования правил): Наименование, Код (`КЛ_…`, стабильный,
  присваивает фабрика), Родители → (список), ТипКласса
  (`сущность`/`отношение`/`значение`), UDC (золотой класс фабрики),
  Пояснение; ТЧ `Свойства_класса` (Свойство → `Свойства`, Порядок);
  правила наследуются по иерархии (3.4, 3.5);
- справочник **`Свойства`**: Наименование, Код (`СВ_…`),
  ТипЗначения (`Текст`/`Граммема`/`Связь`/`Класс`), Множественное (`*`),
  Роль (псевдоним свойства — имя после `:` в `classes.txt`), Пояснение; ТЧ
  `Domain` (Класс → `Классы`, Порядок) — домен из `Связь(КЛ_…)`;

- справочник **`Парадигмы`**: Код (`м1`, `ж1`, `гл1`, `им3`, …), ЧастьРечи,
  Лемма, Тип (склонение/спряжение/неизменяемое), Пояснение; ТЧ `Формы`
  (Граммема — `Наст.3.Един`, `Прош.Един.Муж`, `Инф`, Порядок, Форма — точная
  поверхность из поставки); парадигма = **словарь точных форм**, окончание не

  (`один`/`список`), Версия_знания; ТЧ `Позиции` (Порядок — нумерация внутри

  Набор_предлогов → `Наборы_предлогов`, Род, Класс_требуемый → `Классы`,

- регистр сведений **`Трасса`**: измерения Текст, Клауза, Этап; ресурсы
  Результат, Причина, Позиция, Класс;
- регистр сведений **`Упоминания`**: измерения Текст, Клауза, Свойство →;
  ресурсы Форма, Экземпляр →, Порядок — поверхность формы, которой записано
  свойство; используется 6.4 (восстановление печатает форму, а не лемму) и
  5.4 (печать ответа по рецепту);
- регистр сведений **`Кандидаты_ответа`**: измерения Вопрос, Экземпляр,
  Свойство, Момент; ресурсы Значение, Domain_проверка;
- регистр сведений **`Ответы`**: измерения Вопрос; ресурсы Результат,
  Значение, N, Состояние_на_моменте, Ссылка_на_отказ;
- регистр сведений **`Версии_знания`** (периодический по Дате): измерения
  Объект (тип), Код; ресурсы Версия, Признак (принят/отменён), Источник;
- регистр сведений **`Результаты_проверки`**: измерения Правило, Объект;
  ресурсы Информация, ЭлементОбъекта, ДатаПроверки;
- константы: `ПодробныйЛог`, `МоментПоУмолчанию`, `Профиль_по_умолчанию`
  (`-`);
- перечисления: `ЧастьРечи`, `Падеж`, `Разряд`, `Число`, `Род`, `Предлог`,
  `Роль`, `ТипПозиции`, `ТипДействия`, `ТипЗначенияСвойства`, `ТипПарадигмы`,
  `ТипКласса`, `ТипЭлементаРецепта`, `ВидЗнания`, `ВидКейса`, `ВидОтказа`,
  `ВидСобытия`, `РезультатРазбора`, `РезультатОтвет`, `Важность`,
  `СтатусТекста`, `СтатусВопроса`, `ВидТекста`;
- обработки `Задать_вопрос`, `Загрузить_знание`, `Загрузить_текст`,
  `Проверить_целостность`; регламентные задания: разбор очереди текстов,
  аудит знания, удаление устаревших разборов;
- отчёты `Трасса_разбора`, `Лента_текста`, `Отказы_по_тексту`,
  `Восстановление_текста`, `Скорость_разбора`, `Проверка_целостности`,
  `Протокол_приёмки`;
- план обмена с фабричным проектом (файловый поставщик обязателен; план —
  позже) и роли.

**Индексы горячего пути**: реквизиты табличных частей индексов не имеют,
поиск по 3.9M форм и позициям правил (1701 в поставке, после свёртки наборами
и иерархией — существенно меньше) идёт по индексам `Формы_лексикона` и
`Позиции_правил`; зеркальные регистры заполняются тем же проведением
`Загрузка_знания` и обязаны согласоваться со справочниками (аудит §10).

Разделение данных: общие (неразделённые), РИБ/библиотеки не используются.
Синхронизация: загрузка знания из фабрики; согласование новых объектов
требуется (проверка формальных правил §10 перед приёмкой).

## 5. Интерфейс

Формы (управляемые), команды и видимые профили:

- `Тексты` — список + форма элемента (загрузить, статус, ТЧ `Клаузы`,
  команда «Разобрать») — `Владелец знания`;
- `Классы`, `Правила`, `Вопросительные_правила`, `Лексикон`, `Парадигмы`,
  `Свойства`, `Экземпляры`, `Фразеологизмы`, `Рецепты`, `Знания_вывода`,
  `Профили_вывода`, `Коды_отказов`, `Мосты_форм`, `Наборы_падежей`,
  `Наборы_предлогов`, `Золотые_кейсы`, `Восстановленные_тексты`,
  `Правила_целостности` — форма списка + форма элемента, read-only (запись
  только проведением `Загрузка_знания`; `Наборы_падежей`/`Наборы_предлогов`
  заполняет владелец); на форме элемента видны Родители (список), ТЧ
  Позиции/Действия/Формы/Элементы, Приоритет, Код, Версия;
- `Форма_вопроса` — текст вопроса, момент, профиль → `Профили_вывода`,
  команда «Ответить», область результата (`ответ:`, `неопределённо (N):` и
  перечень кандидатов экземпляр · свойство · значение · момент, `неизвестно`,
  `не распознано: <предложение>`) и ссылка на отказ; статус вопроса;
- `Лента_текста` (отчёт) — Момент, Экземпляр, Свойство, Значение, создатели;
- `Трасса_разбора` (отчёт) — по предложениям: этапы морфология → связи →
  классы → фрейм → мир → вывод; результат; причина отказа;
- `Восстановление_текста` (отчёт) — лента/состояние → восстановленный текст
  с классами и фразеологизмами; результат пишется в
  `Восстановленные_тексты`;
- `Отказы_по_тексту` (отчёт) — список отказов; очередь решений передаётся
  фабричному проекту;
- `Скорость_разбора` (отчёт) — длительность этапов по предложениям и тексту,
  сравнение с целевыми рамками §13;
- `Проверить_целостность` (обработка) — формальный аудит данных;
  `Протокол_приёмки` — очередь решений приёмки знания.
Команды «Загрузить знание», «Загрузить текст», «Разобрать», «Ответить»,
«Восстановить», «Проверить целостность» — профиль `Владелец знания`;
регламентный разбор — системный профиль.

### 6.1 Агенты, подключаемые к программе

Агент подключается под ролью пользователя и токеном; матрица операций —
`docs/agent-roles.md`.

| Профиль агента | Роль | Интерфейс | Операции | Ожидаемый отказ при нарушении |
|---|---|---|---|---|
| `$design-base-sync` | Проектировщик | `onebase describe`, REST v2, headless bridge `ИмпортОписания` | функции, ICOM, объекты метаданных, трассировка, задача «Базовая синхронизация» | `403` на запись вне прав; отказ гейта переходов; регистровые строки через REST не пишутся |
| `$acceptance-run` | Тестировщик | `onebase test`, `gherkin compile`, `procrun` аудита, REST v2 | сценарии §8, результаты проверок, документ `Ошибка` | прогон с провалом (код 1), `403` на запись объектов |
| `$lead-desk` | подготовка, роль `Руководитель` — человека | REST v2 (документы публикаций, планы занятости) | проекты правил, планы, очередь | `403` агенту; утверждение и публикация — человек |
| `$knowledge-intake` | `Приём_знания` | REST v2 (каталоги знания, `Загрузка_знания`), headless загрузки на учебной копии | приём дельты по манифесту, проверка форматов, статус приёмки, золотые кейсы | отказ загрузки (манифест, колонки, коды) — код 1; `403` |
| `$night-ops` | `Обслуживание` | headless прогонов, REST read, отчёты | ночной прогон книги и экзамена, отчёт объёмов/скорости, регистрация отказов | прогон с провалом (код 1), `403` на запись знания |
| `$base-observer` | `Наблюдатель` | MCP read-only, REST read, отчёты | аудит срез, функций, результатов, соответствия документации | `403` на запись; запись вне прав — каркасный дефект enforcement |

Правила подключения (проверено 2026-11-10):

1. Пользователь агента заводится офлайн (`onebase user add`, `onebase user role
   assign`); токен выдаёт владелец в UI **Система → API-токены** — CLI-команды
   создания токена нет. Ролевая запись — REST v2 под Bearer-токеном
   (`internal/api/v2.go`), нарушение — `403 forbidden`.
2. Headless `procrun` (и MCP-инструмент `procrun` под флагом `--allow-procrun`)
   работает без контекста роли: роль-scoped запись через него невозможна, права
   роли им не доказываются. Headless разрешён каркасным обработкам (импорт,
   расстановка, аудит, загрузка на учебной копии).
3. MCP-запись открывается флагом, не ролью (`--allow-procrun`, `--allow-write`,
   `--allow-fmt-write`, `--allow-refactor-write`, `--allow-config-rollback`):
   флаги включаются на время операции и снимаются после.
4. YAML роли валидируется `check`: ссылка на несуществующий справочник, регистр
   или отчёт — `metadata.invalid`, код 1. Роль заводится в той же задаче, что
   объекты, на которые ссылается: роль compsem не опережает скелет.
5. `processors_default: allow` ловит lint-warning; права на обработку задаются
   списком `processors: {Имя: [run]}`.
6. Агент не принимает полномочий утверждающего: роль `Руководитель` агенту не
   выдаётся; права агента соответствуют профилю, роль шире профиля — запись вне
   профиля аудится (§10).

## 7. Управление проектом и изменениями

Ведётся в СППР (внешний по отношению к продукту инструмент):

- **Целевые задачи**: основная (разбор — сопоставление с классами);
  вспомогательная (фабрика — внешний проект); максимум (шаблоны мышления:
  вывод новых знаний и ответы на вопросы). Ответственный — владелец.
- **Идеи** (что предложено) и **ошибки** (что воспроизводится: шаги,
  фактический результат, ожидаемый результат; описание реализации/исправления).
- **Технические проекты**: цель, концепция, версия платформы, ветка
  разработки, вид деятельности, плановые сроки, статус, публикация.
- **Проектные решения** техпроекта: затронутые функции (по кодам §2.2),
  профили, сценарии, разделы проекта, объекты метаданных, ключевые операции;
  результаты проверки формальных правил.
- **Задачи**: исполнитель (человек или агент pi), контролирующий (без него
  выполнение не отмечается), плановая дата начала, крайняя дата, вышестоящая
  задача, предшествующие/последующие, дочерние. Работы агента — задачи СППР,
  не профиль пользователя.
- На контроле: справочники знаний, регистры мира, формат обмена с фабрикой,
  справочник золотых кейсов, экзамен, сценарии §8, отчёт скорости.
- **Правило изменений формата входных данных**: изменение формата поставки
  (манифест, номер версии, колонки, наборы падежей/предлогов, наследование,
  knowledge-правила) оформляется задачей, в состав которой входят: приёмка
  нового формата (1.1.1–1.1.3), обновление `Золотые_кейсы` и `exam.txt`,
  обновление сценариев Gherkin и шагов, обновление целевых рамок §13 и
  полный прогон §8 в ночном контуре. Задача без обновления экзамена и
  тестов не закрывается; старый формат остаётся действующей поставкой, пока
  новый не принят.
- **Интерфейс проверенного результата**: каждое закрытие среза подтверждается
  прогоном внутренней логики, который возвращает проверенный результат или
  отказ: статика (`check`, компиляция Gherkin), тестовый прогон (строка на
  проверку, провал — ненулевой код), прогон обработки над базой (вывод
  обработки; нарушение гейта переходов — отказ записи), запись под ролью
  (отказ прав — `forbidden`). Итог прогона пишется строкой результата
  (функция, правило, объект, результат), отказ — документом ошибки. Закрыть
  срез записью без проверенного прогона нельзя; отказ интерфейса — нормальный
  результат, он фиксируется в истории, а не обходится.

## 8. Тестирование

Сценарии Gherkin живут в конфигурации (`features/*.feature` + шаги), группа
сценария привязана к функции (по кодам §2.2), профиль запуска — `Владелец
знания`, эталонная база — тестовая SQLite с фиксированным знанием. Минимум —
по одному ключевому сценарию на каждую группу, плюс сценарии поперечных
требований. **Экзамен и тесты дорабатываются по ходу разработки и смены
формата входных справочных данных**: состав кейсов, ожидаемые результаты, шаги
и целевые значения пересматриваются в той же задаче, что принимает новый
формат (правило §7); тест, который не ловит смену формата, неполон:

1. **1.1.1/1.1.2 Загрузка_знания**: `Дано` дельта TSV с классом, domain
   которого не класс → `Тогда` приёмка отказана с указанием файла, строки,
   колонки и нарушенного правила, версия не применена, `Версии_знания` не
   изменена; `Дано` файл поставки без манифеста версии → `Тогда` приёмка
   отказана; `Дано` `knowledge.txt` (фабрикой не валидируется) со следствием,
   отличным от одного `==` → `Тогда` приёмка отказана (Ошибка).
2. **1.1.3 Версионирование**: `Дано` дельта снимает класс, на который ссылается
   мир → `Тогда` приёмка отказана (Ошибка), предыдущая версия остаётся
   действующей.
3. **1.2.x Приём_текста**: `Дано` fb2-книга (333 предложения, 16 566 токенов
   по мерке §13) → `Тогда` число клауз = числу предложений, границы клауз =
   границы предложений, статус текста `Разобран | Отказ`.
4. **2.x Морфология (первый слой)**: `Дано` форма, отсутствующая в словаре
   точных форм `Формы_лексикона` и не покрытая мостом `Мосты_форм` → `Тогда`
   отказ `не распознано: <предложение>` с указанием формы и причины; молча
   пропущенных форм нет; `Дано` форма корпуса (`пошёл`) → `Тогда` лемма
   найдена по мосту (`пойти`) и парадигма найдена; `Дано` тестовый
   фразеологизм владельца → `Тогда` цепочка токенов покрыта одной позицией,
   остаток цепочки непокрытым не остался; `Дано` форма с несколькими
   лексикограммами → `Тогда` морфология отдаёт **все кандидаты** семантике,
   сама не выбирает.
5. **3.x Сопоставление_с_классами (второй слой)**: `Дано` клауза «В машину
   вошла кошка», наполнитель роли вне domain → `Тогда` отказ с ролью, domain,
   классом наполнителя; `Дано` две позиции, совпадающие по (Разряд, Падеж,
   Предлог, Ключевое, Роль) с разными действиями → `Тогда` конфликт при
   приёмке (Ошибка); `Дано` собственное правило и наследуемое с одинаковым
   приоритетом → `Тогда` применено собственное, конфликтом не считается;
   `Дано` правило класса-родителя (`КЛ_Животное`) и отсутствие собственного
   правила у `КЛ_Кошка` → `Тогда` кошке применено унаследованное правило;
   `Дано` правило с набором «предлоги места» → `Тогда` «в машине», «из
   машины», «под машиной» покрываются одной позицией, правила по каждому
   предлогу не заведены; `Дано` правило с набором «все падежи» → `Тогда`
   все варианты набора проверены, предложение разобрано, если всё
   складывается.
6. **4.x Построение_мира**: `Дано` «Машина в гараже» (момент 1), затем
   «машина выехала» (момент 2) → `Тогда` лента содержит запись и снятие с
   номерами моментов; `Тогда` срез последних на моменте 1 = «в гараже», на
   моменте 2 — пусто по свойству «нахождение»; `Дано` «Иван купил книгу. Маша
   купила книгу.» → `Тогда` два разных экземпляра книги (идентификатор =
   лемма + номер), не один; `Дано` «Иван хочет купить книгу» → `Тогда` отказ
   с кодом, факта прошедшего времени нет; `Дано` «Иван продал книгу Петру»
   (при knowledge-правиле передачи) → `Тогда` пересмотр владельца,
   предыдущее значение снято.
7. **5.x Вывод_и_ответ**: `Дано` вопрос «Где машина?» на моменте 1 → `Тогда`
   `ответ: машина в гараже`; вопрос не распознан → `не распознано: <вопрос>`;
   свойство не представлено → `неизвестно`; два кандидата, прошедших
   domain-проверку → `неопределённо (2):` с перечислением
   экземпляр · свойство · значение · момент каждого; один кандидат →
   `ответ:`; `Дано` «Маша купила кошку» и вопрос «Что купила Маша?» →
   `Тогда` ответ печатает клаузу глагола вопроса (`Маша купила кошку`), а не
   пересказ владения; `Дано` лента и состояние → `Тогда` восстановленный текст
   по рецепту класса (порядок, предлог, падеж, глагол), записанный в
   `Восстановленные_тексты`.
8. **6.x Отчёты_и_аудит**: `Дано` текст с отказом на этапе 3.3 → `Тогда`
   `Трасса_разбора` показывает этап, роль, domain, класс, правило;
   `Дано` аудит знания → `Тогда` `Проверка_целостности` выдаёт нарушения по
   правилу и строке с важностью.
9. **Скорость**: `Дано` книга 333 предложения / 16 566 токенов из
   фиксированного знания → `Тогда` полный прогон ≤ 10 минут, 100 предложений
   ≤ 2 минут; `Тогда` `Скорость_разбора` показывает длительность каждого
   этапа; `Дано` предложения одного текста → `Тогда` разбор идёт параллельно.
Сценарий проверяет прогон на фактических файлах поставки (333 предложения,
16 566 токенов) и на поставке с изменённым форматом; контур включает
интерфейс, который прогоняет логику и возвращает проверенный результат
или отказ (статика, тест, обработка над базой, запись под ролью).
10. **Экзамен (качество разбора)**: `Дано` прогон `exam.txt` (20
    предложений-ответов) → `Тогда` `Журнал_разбора` фиксирует число
    распознанных предложений-ответов и число верных ответов; целевые значения
    (§12) достигаются при закрытых находках §5 приложения; отказы считаются
    законным результатом, молчание — нет; `Дано` формат поставки изменён
    (наборы, наследование, новые колонки) → `Тогда` состав кейсов и
    ожидаемые результаты пересмотрены (правило §7), прогон фиксирует новые
    цели; `Дано` срез закрыт записью, проверенного прогона которого нет, или
    отказ интерфейса (отвергнутый переход статуса, запись под ролью без права)
    проигнорирован → `Тогда` аудит (§10) даёт нарушения; итог прогона
    записан строкой результата (функция, правило, объект, результат),
    отказ — документом ошибки.
11. **Права агентов**: `Дано` пользователь с ролью `Наблюдатель` (только
    чтение) и токен → `Дано` запись справочника через REST v2 → `Тогда`
    `403 forbidden`, запись не появилась; `Дано` запуск обработки без
    контекста роли → `Тогда` запись прошла и зафиксирована аудитом как
    каркасный дефект enforcement (права роли headless не проверяет); `Дано`
    роль со ссылкой на каталог скелета, ещё не созданный → `Тогда` `check`
    даёт `metadata.invalid` и отказ (код 1).

Ночной контур: `onebase check --project compsem` + полный прогон сценариев и
замеров; дневная сборка — сценарии затронутых функций. Золотые кейсы
(`Золотые_кейсы`) приходят поставкой `puzzles.txt` (19) и `exam.txt` (20),
функцию и сценарий назначает владелец по мере разбора; справочник публикуется
вместе с конфигурацией. Целевые показатели экзамена (покрытие классов,
свойств и отношений поставки, доля корректных ответов, доли отказов по видам)
публикуются и пересматриваются при смене формата поставки, при смене
замера книги и при уточнении цели; приёмка проверяет фактические файлы
поставки (333 предложения, 16 566 токенов), результат прогона обязана
принять публикация, которая фиксирует замеры.

## 11. Запреты (директивы заказчика)

- **Механизмы не описываются** — порядок разбора, разрешение конфликтов,
  порядок применения правил решает исполнитель; ТЗ фиксирует требуемое
  поведение, форматы, запреты и процесс.
- **Основа — внутренняя структура представления данных**: продукт строит
  правильное, непротиворечивое представление мира, поддающееся машинному
  мышлению по правилам и шаблонам; разбор и восстановление текста —
  вспомогательные функции. Структура объектов (§4) и правила (§11) важнее
  удобства ввода-вывода.
- **Наборы, не перечисление**: правила не раздуваются по падежам и
  предлогам; позиция ссылкиется на набор («все падежи», «предлоги места»,
  «предлоги перехода»), и разбор обязан учитывать все варианты набора;
  дублирование одной и той же позиции по всем падежам в каждом правиле
  недопустимо.
- **Иерархия классов**: понятия объединяются в иерархию классов, правила
  наследуются от классов-родителей; класс может иметь нескольких родителей,
  и те в свою очередь тоже; правила пишутся на класс, а не на каждое слово.
- **Приоритет собственного правила**: если у класса есть своё правило, оно
  имеет больший приоритет, чем наследуемое.
- **Двухслойный разбор**: разбор морфологии готовит входные данные для
  семантики; семантика берёт подготовленные варианты отношений и подставляет
  в классы, выбирая наиболее подходящие; если всё складывается — слова
  разобраны, противоречия не мешают — предложение разобрано.
- **Морфология — словарь точных форм**: признаки (разряд, падеж, число, род,
  предлог) берутся из записи словаря, окончание не выводится; формы корпуса
  читаются через мост `Мосты_форм`; парадигма — словарь грамем → форм, она
  же даёт поверхность для восстановления.
- **Идентичность**: одноимённые предметы — разные экземпляры; экземпляр
  хранится с идентификатором (лемма + номер в тексте), переиспользование
  экземпляра по базе леммы запрещена.
- **Модальность, вид, время**: немаркированная модальность (хочет, должен,
  будет) не порождает совершившийся факт — она даёт отказ; вид и время входят
  в состояние; факт прошедшего времени создаётся только маркированным
  глаголом.
- **Ответ по глаголу вопроса**: ответ печатает клаузу того глагола, о котором
  вопрос; пересказ чужого отношения вместо ответа — ложный ответ.
- **Канон значений**: значение свойства хранится канонизованным (леммой),
  сравнение идёт по канону; фильтрация по признаку по поверхностной форме
  недопустима.
- **Количество**: числительное обязано попасть в мир (`СВ_Количество`,
  состав группы); кванторы (`все`, `каждый`, `несколько`) — открытая зона,
  молча игнорируются не могут.
- **Передача**: события передачи (купить, продать, подарить, отдать) обязаны
  менять владельца (пересмотр); knowledge-правила передачи требует фабрика.
- **Границы модели (не-цели, фиксируются как отказа, не как додумывание)**:
  придаточные (`который`, `чтобы`, `когда`), деепричастные и причастные
  обороты, сравнительная степень, модальность, вид, адвербиальные группы
  (`быстро`, `за сто рублей`), полисемия предлогов, эллипсис связки, идиомы,
  дискурс и контраст (`а`), отрицание вне действия, кванторы, время как слова
  (`теперь`, `раньше`).
- **Исключений по отдельным точкам (номерам) не допускается.**
- **Ручных правил не требуется** — правило порождается; знание в текстовых
  файлах, генератор/LLM — внешний проект.
- **Полное покрытие**: каждый токен текста покрыт позицией; непокрытый токен
  = отказ; молчание запрещено; цепочка фразеологизма покрывается одной
  позицией и заменяется лексемой класса, остаток цепочки непокрытым не
  остаётся.
- **Ответ только из мира**: система отвечает тем, что представлено в модели
  мира; `неизвестно` — законный ответ; ложный ответ хуже отсутствия ответа;
  N = число кандидатов, прошедших domain-проверку вопроса; каждый кандидат
  перечисляется (экземпляр · свойство · значение · момент); N=1 → `ответ:`.
- **Классы и правила приходят из внешнего проекта заранее подготовленными**;
  продукт их загружает, исполняет и проверяет формально, но не редактирует
  вручную. Коды классов/свойств/правил присваивает фабрика, коды стабильны;
  продукт коды не создаёт.
- **Формат обмена**: TSV (разделитель — табуляция), UTF-8, LF; колоночные
  заголовки в поставке отсутствуют, строки `#` — комментарии, колонки
  позиционные; обязателен **манифест поставки** (номер версии, дата, список
  файлов с контрольными сумками и числом строк). Поимённая схема файлов —
  приложение [`exchange-schema.md`](exchange-schema.md). Поставщик — файл
  (падение файла в каталог загрузки → документ `Загрузка_знания`); HTTP и
  план обмена — позже. Дельта с обязательным номером версии; `Версии_знания`
  вести; класс, снятый на фабрике при ссылках из мира — приёмка отказана
  (Ошибка), версия не применяется. **Формат правил подлежит доработке
  фабрикой**: поставка не содержит наборов падежей/предлогов и правил,
  наследуемых по иерархии; продукт обязан читать расширенный формат (§12).
- **Знание в текстовых файлах**; истина во время разбора — справочники
  конфигурации, куда знание попадает загрузкой.
- **Экзамен и тесты живут вместе со знанием и форматом входных данных**: при
  смене формата дорабатываются `Золотые_кейсы`, `exam.txt`, сценарии и
  целевые значения; прогон §8 обязателен, чтобы принять новый формат; тест,
  не ловящий смену формата, неполон; расхождение ожидаемого результата
  фиксируется как отказ, не молчание.
- **Интерфейс проверенного результата**: закрытие среза подтверждается
  прогоном внутренней логики, который возвращает проверенный результат
  (статика, тест, обработка над базой, запись под ролью) или отказ; итог
  прогона пишется строкой результата (функция, правило, объект, результат),
  отказ — документом ошибки. Срез, закрытый записью без проверенного прогона,
  и отказ интерфейса (отвергнутый переход статуса, запись под ролью без
  права), оставленный без записи причины, — подделка проверки.
- **Агент подключается под своей ролью и токеном**: роль-scoped запись — REST
  v2 под Bearer-токеном, нарушение — `403`; права роли headless-прогон не
  проверяет, и запись, сделанная headless под ролью без права, доказательством
  прав не считается. Права агента соответствуют профилю; роль утверждающего
  (`Руководитель`) агенту не выдаётся; роль заводится в той же задаче, что
  объекты, на которые ссылается (§6.1).
- **Морфология своя, внутри продукта**: лексикон и парадигмы — активные
  данные конфигурации; отсутствие формы в парадигме = отказ; фразеологизмы
  приходят из фабрики. Фразеологизмов в поставке нет (идеомы — не-цель
  фабрики): справочник наполняется тестовым набором владельца.
- **Момент** — порядковый номер события в тексте; не дата, не качественная
  метка.
- **Позиции применяются в порядке нумерации внутри правила**; порядок сборки
  фрейма задают связи клаузы (главное слово → зависимое), общий порядок позиций
  между правилами не задаёт.
- **Статусы** (`Текст`, `Вопрос`) меняются только проведениями/отчётами.
- **Скорость**: разбор измеряется по этапам, полный прогон фиксируется и
  оптимизируется; долгие прогоны не принимаются как норма; предложения
  разбираются параллельно.
- Критерии приемки и дипломная работа в ТЗ не входят.

## 12. Открытые решения

- Наименование: `compsem` оставлено; `Бытопись` — кандидат будущего,
  окончательное решение отложено.
- Схема обмена с фабрикой описана приложением
  [`exchange-schema.md`](exchange-schema.md) по фактической поставке
  `compsem-vneshnie-2026-11-10.tar.gz`. Остаётся открытым **доработанный
  формат правил** (приложение §6): наборы падежей/предлогов, наследование
  правил по иерархии, собственный приоритет; поставка этого не содержит
  (38 уникальных позиций раздуваются до 1701 записей, правил на класс —
  47) — фабрика обязана дополнить формат, продукт обязан читать
  расширенный формат (аудит §10).
- Имена и состав наборов («все падежи», «предлоги места», «предлоги
  перехода», «предлоги обладания») заполняет владелец; фабрика обязана
  ссылаться на них в правилах.
- Требуется поставке: правила передачи (датив получателя), knowledge-правила
  смены владельца, модальность/вид/время, кванторы, количество, идиомы,
  придаточные; до поставки эти случаи — отказ с кодом.
- Фразеологизмы: поставка не содержит; тестовый набор владельца (тест 4).
- Целевые значения качества экзамена (доля распознанных предложений-ответов
  и доля верных ответов) — открытое решение; прогон фиксируется
  `Журнал_разбора`.
- **Экзамен и тесты — открытая часть**: состав кейсов, ожидаемые результаты
  и целевые значения дорабатываются по ходу разработки и смены формата
  входных справочных данных (правило §7, тест 10); формат поставки не
  считается принятым без обновлённого прогона §8; итог прогона обязана
  принять публикация, которая фиксирует замеры.
- HTTP/план обмена с фабрикой — позже, файловый поставщик обязателен.
- Права агентов: каркас обязан применять роль-scoped enforcement в
  headless-прогоне (контекст пользователя) и дать REST-маршрут записи строк
  регистров; до этого роль-scoped запись регистров и доказательство прав агента
  невозможны (план 222 §5, п. 7–8).

## 13. Non-functional (числовые рамки)

1. Объёмы знания (измерено по поставке `compsem-vneshnie-2026-11-10`):
   56 классов, 79 строк свойств; 615 правил (597 `frame` + 18 `вопрос`),
   1701 позиция, из них 38 уникальных (разряд/падеж/предлог + роль) —
   свёртка наборами и иерархией обязана сократить число позиций (аудит «П»
   §10); 3626 лексикограмм (`words.txt`), 3834 парадигмы, 9627 точных форм
   книги, 8871 мост форм корпуса; 12 рецептов, 5 knowledge-правил, 19 кодов
   отказов, 543 золотых класса UDC; полный корпус — 3.9M форм, 237k
   лексикограмм, 5.6M строк слотов (фабрика, в базу не входит).
2. Объём текста: книга — 373 абзаца, 333 предложения, 16 566 токенов
   (измерено по `book/text.txt`); экзамен — 20 предложений-ответов, 19
   золотых кейсов, 11 корпусных фраз. Состав экзамена, состав кейсов и
   целевые значения пересматриваются при каждой смене формата поставки
   (правило §7, тест 10).
3. Целевое время: полная книга ≤ 10 минут; 100 предложений ≤ 2 минут.
4. Параллельность: разбор по предложениям.
5. Размер базы ≤ 1 GB (файлы фабрики: индекс opcorpora 413 MB, Taiga
   157 MB, слоты 99 206 строк, в базу не импортируются).
6. Измерение: отчёт `Скорость_разбора` по этапам (морфология, связи, классы,
   мир, ответ), аналог speed.log; результат прогона фиксируется в
   `Журнал_разбора`.
7. Ответы на вопросы читаются из срезов последних по индексу; полный прогон
   книги не должен сканировать ленту без индекса.
8. Горячие пути (9627 форм книги, 8871 моста, 3.9M форм корпуса, 1701
   позиций) читаются по индексам зеркальных регистров `Формы_лексикона` и
   `Позиции_правил`, а не по табличным частям справочников.
