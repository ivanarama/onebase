# Демонстрация: сайт → заказ → рабочее место менеджера

Этот сценарий дополняет публичный CMS-пример. Все новые контакты, товары,
адреса и названия городов вымышлены. Он использует существующий движок
платформы из снимка `main` от 19.10.2026 (`5022b936`), без изменений движка.
Доработанная конфигурация поставляется в этой ветке вместе со статьёй.

## Подготовка отдельной базы

Команды выполняются из корня репозитория. Нужен собранный `onebase`, доступный
в `PATH`. В PowerShell локальный бинарь вызывается как `./onebase.exe`.
Используйте новую демонстрационную базу: наполнитель сайта предназначен для
демонстрации, а не для наполнения рабочего сайта.

```sh
go build -o onebase ./cmd/onebase
onebase check --project examples/cms
onebase migrate --project examples/cms --sqlite cms-article.db
onebase procrun --project examples/cms --sqlite cms-article.db --proc ЗаполнитьТестовуюБазу
onebase procrun --project examples/cms --sqlite cms-article.db --proc ПодготовитьДемоЗаказов
onebase settings set net.enabled вкл --sqlite cms-article.db
onebase user add admin --name "Администратор демо" --admin --generate --project examples/cms --sqlite cms-article.db
onebase user add manager --name "Менеджер демонстрации" --show-in-list --generate --project examples/cms --sqlite cms-article.db
onebase user role assign manager МенеджерЗаказов --project examples/cms --sqlite cms-article.db
onebase run --project examples/cms --sqlite cms-article.db --host 127.0.0.1 --port 18330
```

Если собранный бинарь не находится в `PATH`, используйте `./onebase` вместо
`onebase` (Windows: `./onebase.exe`, сборка `go build -o onebase.exe ./cmd/onebase`).
Команда `user add` печатает сгенерированный пароль; сохраните пароли обеих
демонстрационных учётных записей. Повторно создавать пользователей не нужно.

Основной наполнитель сайта и `ПодготовитьДемоЗаказов` запускаются отдельно.
Вторая обработка добавляет двух покупателей, три подчинённых адреса, два города,
три пункта выдачи, три товара и предыдущую покупку Анны. Повторный запуск
сохраняет эти записи и не перезаписывает их ручные изменения.

## Сценарий для просмотра

1. Без входа откройте [каталог](http://127.0.0.1:18330/hs/site/catalog).
   Добавьте кружку за 790 рублей в корзину и оформите заказ от имени
   «Анна Примерова», контакт `anna@example.test`.
2. Сохраните личную ссылку на заказ. В отдельном окне войдите как `manager`
   на [рабочее место](http://127.0.0.1:18330/ui). Строка на рабочем столе
   открывает документ; он также доступен в разделе «Заказы и покупатели».
3. Выберите покупателя «Анна Примерова». Появятся её телефон и предыдущая
   покупка в истории. Контакт, пришедший с сайта, сохраняется отдельно.
4. Выберите доставку и адрес Анны. Смените покупателя на Павла: адрес очистится,
   в выборе останется адрес Павла. Верните Анну.
5. Выберите самовывоз и «Учебный город». Через кнопку `…` видны только два его
   пункта. После смены города прежний пункт очищается.
6. Кнопкой «Добавить товары» откройте подбор. У ежедневника укажите количество
   2 и перенесите выбор. Сумма заказа станет 3170 рублей. Старые строки заказа
   сохраняют цены покупки; цена добавляемого товара читается из базы.
7. Укажите пункт выдачи, подтвердите заказ. На личной странице покупателя
   появится «В работе». Откройте «Печать → ЗаказСайта» или PDF.
8. Завершите заказ: посетитель увидит «Выполнен». На другом новом заказе
   проверьте отмену: ответ «Нет» ничего не меняет, ответ «Да» отменяет заказ.

У менеджера есть доступ ко всем заказам примера; фильтрации по ответственному
правами не задано. Роль разрешает вести покупателей и адреса, но товары,
города, пункты и сайты доступны только на чтение. Контент и оформление сайта
не разрешены. Наполнение, изменение товаров и настройка базы остаются администратору.

| Задача | Где смотреть |
|---|---|
| Модель заказа, уведомления и строгий маршрут | [documents/ЗаказПокупателя.yaml](documents/ЗаказПокупателя.yaml) |
| Цветные группы, условные поля, подчинение и зависимости | [forms/заказпокупателя/объекта.form.yaml](forms/заказпокупателя/объекта.form.yaml) |
| Очистка зависимых ссылок, история, подбор и команды | [обработчики формы](forms/заказпокупателя/объекта.form.os) |
| Проверка принадлежности адреса и пункта вне формы | [РаботаСЗаказами.module.os](src/РаботаСЗаказами.module.os), [модуль объекта](src/ЗаказПокупателя.os) |
| Владельцы подчинённых справочников | [АдресаДоставки.yaml](catalogs/АдресаДоставки.yaml), [ПунктыВыдачи.yaml](catalogs/ПунктыВыдачи.yaml) |
| Разрешения менеджера | [МенеджерЗаказов.yaml](roles/МенеджерЗаказов.yaml) |
| Печать из снимков строк заказа | [ЗаказСайта.layout.yaml](printforms/ЗаказСайта.layout.yaml) |
| Дополнительные вымышленные данные | [ПодготовитьДемоЗаказов.proc.os](src/ПодготовитьДемоЗаказов.proc.os) |
| Серверные проверки и права | [ТестРабочегоМестаЗаказов.proc.os](src/ТестРабочегоМестаЗаказов.proc.os) |

Кнопки отражают прикладной процесс, а `stages.enforce: strict` запрещает
переходы вне маршрута при записи. Модуль объекта проверяет получение и
обязательные данные подтверждённого заказа. Условная недоступность формы
дополняет эти проверки; она не означает запрета любого изменения остальных
полей документа из прикладного кода.

Исходная публичная цепочка `Магазин → Корзина → Заказы` сохранена: оформление
закрывает корзину и создаёт документ в одной транзакции; письмо отправляется
после записи и при ошибке оставляет диагностику. Без настройки SMTP письма
не отправляются. Публичная ссылка на заказ открывает его контактные данные:
не публикуйте ссылки на реальные заказы.

## Проверки

Сначала проверка метаданных и тесты **на отдельной базе без демо-наполнения**:

```sh
onebase check --project examples/cms
onebase test --project examples/cms --sqlite cms-check.db --format tap
```

Все шесть тест-обработок выполняются с откатом. Старые тесты маршрутизации
рассчитаны на отсутствие заранее созданного сайта с доменом `*`, поэтому
не запускайте их на наполненной демонстрационной базе.

Полный браузерный сценарий находится в [e2e/cms-orders-demo.cjs](../../e2e/cms-orders-demo.cjs).
Он работает с настоящим отдельно запущенным сервером, создаёт два новых заказа,
проверяет зависимые поля, историю, подбор и сумму, сохранение и публичный статус,
отказ менеджеру в создании товара, HTML/PDF и оба ответа на отмену. API
приложения не подменяется. После сценария тестовые заказы остаются в демо-базе.

```sh
npm --prefix e2e ci --ignore-scripts
npx --prefix e2e playwright install chromium
CMS_DEMO_PASSWORD='<пароль manager>' node e2e/cms-orders-demo.cjs
```

В PowerShell:

```powershell
$env:CMS_DEMO_PASSWORD = Read-Host 'Пароль демонстрационного manager'
node e2e/cms-orders-demo.cjs
Remove-Item Env:CMS_DEMO_PASSWORD
```

На Windows сценарий использует установленный Microsoft Edge, если он найден;
в остальных случаях нужен Chromium Playwright. Путь к другому исполняемому
файлу можно передать через `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.
`CMS_DEMO_URL` меняет адрес сервера, `CMS_DEMO_USER` — логин, а
`CMS_DEMO_SCREENSHOTS` — каталог снимков. По умолчанию снимки попадают в
`e2e/test-results/cms-orders`.

Проверено 20.10.2026: сборка Go, `onebase check` без предупреждений, все шесть
тест-обработок SQLite, повторное наполнение и браузерный сценарий в Edge,
включая настоящий PDF с сигнатурой `%PDF-`. Проверка PostgreSQL локально не
выполнялась. Изменений движка платформы в этой работе нет.

Также прошли существующие проверки CMS платформы:
`go test ./internal/ui ./internal/project -run '^TestCMS' -count=1 -timeout 4m`.
Их фикстуры теперь создают схему авторизации перед миграцией конфигурации:
добавленный ответственный ссылается на системную таблицу `_users`.

## Ограничения примера

Здесь нет оплаты, фискализации, резервирования остатков, расчёта тарифа
доставки и личного кабинета покупателя. Карточка покупателя привязывается
менеджером после проверки контакта. Доставка и самовывоз демонстрируют данные
и интерфейс, а не подключение к внешней службе доставки.

При обновлении существующей CMS-базы выполните `migrate`. Все добавленные поля
допускают пустое значение; старые заказы сохранятся. Перед переводом прежнего
нового заказа в работу заполните покупателя, способ и место получения.
У терминальных статусов нет обратных переходов. Основная статья:
[«Сайт, корзина и заказы в одной базе»](../../docs/articles/onebase-site-orders.md).
