# Пример «cms» — сайт на OneBase

Конфигурация показывает, как вести публичный сайт в той же базе, где идёт учёт:
контент правится обычными формами платформы, а страницы отдаются HTTP-сервисом.

Состояние: **готов к обкатке** (слайсы C1–C12 плана
`Plans/129-cms-site-configuration.md`). Есть роутер, меню, список и карточки
новостей, редиректы, 404, `robots.txt`, `sitemap.xml`, canonical и Open Graph.
Из плана остались только необязательные пункты: параметры блоков (C3.5) и
дополнительные готовые стили.

## Установка

```bash
onebase check --project examples/cms
onebase migrate --project examples/cms --sqlite cms.db
onebase procrun --project examples/cms --sqlite cms.db --proc ЗаполнитьТестовуюБазу
onebase settings set net.enabled вкл --sqlite cms.db   # предохранитель сети (план 62)
onebase run --project examples/cms --sqlite cms.db --port 8080
```

Шаг `procrun ЗаполнитьТестовуюБазу` необязателен. Без него сайт открывается
страницей «Сайт готов к наполнению» с подсказкой, где завести первую страницу:
пустая база — не ошибка, и встречать администратора страницей 404 она не должна.
Как только появится любой материал (даже черновик), приглашение исчезает.
Несуществующие адреса при этом по-прежнему отвечают 404 — там это правильный
ответ и посетителю, и поисковику.

Сайт отвечает на адрес, записанный в поле «Домен» карточки сайта. У демо-сайта
там стоит `*` — «любой адрес»: одну и ту же базу открывают и по `localhost`, и
по `127.0.0.1` (так её открывает лаунчер), и по имени машины с соседнего
ноутбука, и все эти адреса верны одновременно. `localhost`, `127.0.0.1` и `::1`
считаются одним адресом. Для боевого сайта вписывают его домен — тогда сайт
отвечает только на него, а конкретный домен всегда приоритетнее `*`, поэтому
многосайтовая база продолжает различать адреса.

Если ни один сайт базы не отвечает на адрес запроса, посетитель получает `404`
со страницей «Здесь пока нет сайта» и подсказкой про поле «Домен» — это не то
же самое, что пустая база, и путать их нельзя.

Сайт открывается по `http://localhost:8080/hs/site/`. Проверенные адреса:

| Адрес | Ответ |
|---|---|
| `/hs/site/` | главная (страница со слагом `главная`) |
| `/hs/site/about` | страница по слагу |
| `/hs/site/o-kompanii` | `301` на `/hs/site/about` — правило из справочника «Редиректы» |
| `/hs/site/нет-такой` | `404` со страницей ошибки в оформлении сайта |
| `/hs/site/catalog` | витрина каталога: разделы верхнего уровня |
| `/hs/site/catalog/<слаг>` | раздел каталога: подразделы и товары |
| `/hs/site/product/<слаг>` | карточка товара |
| `/hs/site/catalog?group=<код>` | `301` на новый адрес раздела — совместимость со старыми ссылками |
| `/hs/site/news` | список новостей с анонсами и датами |
| `/hs/site/news?категория=<слаг>` | новости одной категории |
| `/hs/site/news/<слаг>` | карточка публикации |
| `/hs/site/sitemap.xml` | карта сайта по опубликованным адресам |
| `/hs/site/robots.txt` | содержимое из реквизита сайта |
| `/hs/site/style.css` | CSS сайта отдельным файлом |

Сайт живёт под префиксом `/hs/site/`. Чтобы отдавать его в корне домена,
поставьте перед OneBase reverse proxy (nginx, Caddy) с правилом
`/ → /hs/site/`: разрешать сервисам занимать корень платформы означало бы
конфликт с `/ui`, `/api` и статикой.

**Поставили прокси — очистите реквизит сайта «Базовый префикс адреса»**
(`ПрефиксПути`). Из него собираются канонические адреса и `sitemap.xml`, и
пустое значение означает «сайт виден в корне домена». В демо-базе там
`/hs/site` — для прямого доступа к платформе без прокси. Если оставить его за
прокси, поисковик получит адреса вида `https://домен/hs/site/about`, которых
снаружи нет: прокси добавит свой префикс ещё раз и ответит 404.

> **За прокси перестаёт работать ограничение по адресу.** `rate_limit` в
> сервисах считается по адресу соединения и намеренно не доверяет заголовку
> `X-Forwarded-For` (подделать его может кто угодно, если фронт не свой). За
> прокси адрес соединения у всех запросов один, поэтому лимит из
> «60 отправок формы с одного посетителя» превращается в «60 со всех разом»:
> один бот исчерпает квоту, и остальные получат 429. Пока в платформе нет
> списка доверенных прокси, ограничивайте частоту на самом прокси —
> `limit_req` в nginx, `rate_limit` в Caddy — по настоящему адресу клиента.

## Устройство

Раздел **«Сайт»** — то, что правит контент-менеджер:

| Объект | Назначение |
|---|---|
| `Страницы` | Статические страницы («О компании», «Контакты»), иерархия |
| `Новости` | Публикации с датой, категорией и анонсом |
| `КатегорииКонтента` | Рубрики новостей и статей |
| `Меню` | Многоуровневые меню, сгруппированные по `КодМеню` |
| `Медиа` | Файлы сайта; наружу отдаются ссылкой `/pub/<токен>` |

Раздел **«Оформление и адреса»** — то, что правит редактор:

| Объект | Назначение |
|---|---|
| `Сайты` | Домен, язык, ссылки на стиль и шаблон, содержимое `robots.txt` |
| `СтилиСайта` | Палитра и дополнительный CSS |
| `ШаблоныСайта` | HTML-макет страницы для объекта `ШаблонHTML` |
| `Блоки` | Переиспользуемые фрагменты разметки (шапка, подвал, баннер) |
| `МаршрутыURL` | Правила адресов: шаблон → тип контента |
| `Редиректы` | Старый адрес → новый (301), чтобы переезд не обнулил поиск |

Роли: `КонтентМенеджер` — только контент, `РедакторСайта` — контент и
оформление. Разделение осознанное: ошибка в макете ломает сайт целиком, а
тексты правятся ежедневно.

### Общий контентный контур

У «Страниц», «Новостей» и будущих товаров одинаковый набор реквизитов: `Слаг`,
`СтатусПубликации`, `ДатаПубликации`, `ЗаголовокSEO`, `ОписаниеSEO`,
`OGКартинка`, `Сайт`. Один набор имён — один код роутера и рендера на все типы
контента (идея инфоблоков Битрикса, но без второго уровня «тип инфоблока»).
Публичные выборки всегда ограничены сайтом, выбранным по `Host`; совпадающие
слаги, маршруты и коды меню на разных сайтах не смешивают контент. Справочник
`КатегорииКонтента` остаётся общей таксономией.
Отложенная публикация работает без регламентного задания: роутер показывает
только `Опубликовано` с `ДатаПубликации <= сейчас`.

## Правила, которых держится конфигурация

1. **HTML собирается только объектом `ШаблонHTML`** (план 125). Никакой склейки
   строк: значения из базы обязаны экранироваться по контексту вставки, иначе
   наименование товара с `<script>` исполнится у посетителя.
2. **Готовая разметка проходит через `БезопасныйHTML(...)`** — санитайзер
   вырезает скрипты и обработчики событий, оставляя форматирование.
3. **Картинки живут в базе** и отдаются публичными ссылками `/pub/<токен>`
   (план 127), а не внешним CDN.
4. **Публичный сервис кэшируется** (план 126, только `auth: none`), а
   инвалидация — обязанность конфигурации: `СброситьКэшСервисов("Сайт")` из
   `ПриЗаписи` контентных справочников.

## Перенос сайта с 1С-Битрикс

Каталог переносится YML-выгрузкой — её умеет отдавать почти любая российская
CMS, включая Битрикс. Доступ к чужой базе и конвертер инфоблоков не нужны:

```bash
onebase procrun --project examples/cms --sqlite cms.db --proc ИмпортИзYML \
  --set Сайт=<UUID сайта> --file Файл=examples/cms/demo/catalog.yml
```

Импорт создаёт группы и товары, восстанавливает иерархию категорий и собирает
слаги транслитерацией («Бельгийское пиво» → `belgiyskoe-pivo`).
Сайт-владелец обязателен: его UUID можно скопировать из адреса карточки сайта
или получить запросом `ВЫБРАТЬ Ссылка, Наименование ИЗ Справочник.Сайты`.
Повторный запуск обновляет позиции по внешнему коду внутри выбранного сайта, а
не плодит дубли и не затрагивает каталог другого сайта.

**Внешний код в адрес не подставляется, пока адрес свободен.** Он приписывается
только при столкновении названий (`.../gruziya`, при повторе — `.../gruziya-gruziya-2`).
Иначе раздел «Грузия» с кодом `gruziya` получал адрес `/catalog/gruziya-gruziya`,
а карточка — хвост из полного наименования, уже переведённого в начале адреса.
Занятость считается в пределах сайта: составной UNIQUE `(Сайт, Слаг)` разрешает
разным сайтам одинаковые адреса. Длинные наименования обрезаются по границе
слова — адрес в 200 символов не читается и рвётся при переносе в письме.

**Картинки выгрузки скачиваются в медиатеку.** Раньше импорт сохранял только
адрес — «перенос картинок отдельным шагом». Шага не было, а публичная страница
отдаётся с политикой `img-src 'self' data:`: чужой адрес браузер не покажет.
Каталог приезжал с нулём картинок, и заметить это можно было только глазами —
в разметке тег есть, ответ 200, на странице пусто. Теперь каждая картинка
кладётся в справочник «Медиа» и отдаётся ссылкой `/pub/<токен>` с адреса самого
сайта: политика её пропускает, а каталог не зависит от чужого сервера.

**Куда идти за картинками, решает оператор, а не файл.** Адреса приходят из
загруженной выгрузки, то есть от того, кто её прислал; сервер, который ходит по
ним без ограничений, — это доступ во внутренний периметр чужими руками (за
ключами облака на `169.254.169.254`, по портам соседних служб). Поэтому у
обработки есть параметр «Домен, с которого качать картинки»: качаем только с
него, остальные адреса пропускаем и считаем. Пусто — картинки не скачиваются
вовсе. Домен без порта означает обычные 80 и 443; если картинки лежат на другом
порту, его указывают явно (`example.com:8443`). У URL должен точно совпасть
разрешённый `authority` — хост и эффективный порт: похожее имя, поддомен, суффикс
после имени или учётные данные перед ним границу не расширяют. Схемы кроме
`http`/`https` запрещены.

Проверка имени не заканчивается сравнением строк. После DNS запрещается весь
ответ, если хотя бы один IPv4- или IPv6-адрес относится к private, loopback,
link-local, CGNAT, multicast, документационному, тестовому или другому
special-use диапазону. Соединение открывается с уже проверенным числовым
адресом, без повторного DNS между проверкой и `dial`, поэтому DNS rebinding не
создаёт окно TOCTOU. Каждый redirect заново проходит ту же проверку URL и
разрешённого источника; переход на другой хост, порт или непубличный адрес
отвергается.

**Формат определяется по байтам, а не по заголовку.** `Content-Type` пишет тот
же сервер, что и тело: «страница не найдена» с кодом 200 и заголовком
`image/png` иначе сохранилась бы в медиатеку как картинка. Принимаются PNG,
JPEG, GIF и WEBP по сигнатуре; SVG отвергается намеренно — это документ со
скриптами, и публичная выдача его картинкой не рисует. Размер ограничен 5 МБ.

Адрес источника всё равно сохраняется в реквизите «Адрес картинки в источнике» —
по нему видно происхождение и можно перезагрузить позже. Неудача одной картинки
не прекращает импорт: отчёт называет число загруженных, число пропущенных
по границе источника, число неудач и первую причину. Повторный импорт картинку
не перекачивает: элемент медиатеки ищется по **адресу источника в пределах
сайта** (реквизиты «Сайт» и «Адрес в источнике»), а не по наименованию —
названия товаров повторяются и внутри каталога, и между сайтами, и поиск по
имени отдавал второму товару картинку первого. Составной `UNIQUE`
`(Сайт, ВнешнийКлюч)` закрепляет это правило в БД, поэтому два параллельных
импорта не создадут две записи после одновременного поиска.

Скачивание и проверка формата завершаются до короткой транзакции записи. В ней
импорт сначала занимает уникальный ключ неактивной записью-claim, затем
сохраняет blob с этой записью как владельцем, активирует её и публикует ссылку.
Claim, метаданные blob и публикация фиксируются вместе; при ошибке или конфликте
транзакция откатывается. В top-level режиме helper работает как create-or-read:
до своего `Begin` возвращает готовую запись, а при проигранном INSERT делает до
200 проверок победителя с паузами 50 мс в пределах execution deadline (DB-вызовы
могут увеличить календарное время). Внутри уже открытой транзакции helper не
делает lookup и работает только на создание: existing/conflict возвращается
наружу. Caller должен искать до `Begin` либо повторить весь внешний workflow с
новым snapshot; SQLite не обновляет snapshot после rollback savepoint.
Второй claim/blob при конфликте не создаётся. Для disk/S3 rollback запускает
best-effort компенсационное удаление внешнего объекта; при crash или недоступном
хранилище окно может потребовать операторской cleanup/reconciliation.

**Отчёт называет то, что оказалось в базе.** Один товар часто лежит в нескольких
разделах выгрузки, а у позиции каталога раздел один — она остаётся в последнем,
и разделы, потерявшие так все позиции, на витрине окажутся пустыми. Поэтому
импорт печатает «позиций N из M предложений» и отдельной строкой — сколько было
повторов по внешнему коду. Прежний отчёт печатал число предложений («товаров
62» при 50 позициях в базе): расхождение объяснимое, но цифра, не сходящаяся с
каталогом, отправляет искать пропажу вместо чтения объяснения.

### Макет и стили правятся полем кода

У «Шаблонов сайта», «Стилей сайта» и «Блоков» есть управляемые формы
(`forms/<справочник>/`): HTML-макет, CSS и разметка блока открываются
редактором кода с подсветкой и номерами строк, а не однострочным полем.
Редактор встроен в платформу — внешних загрузок нет, что важно для офлайн-
инсталляций и строгих CSP.

Демо-база заводит шаблон «Базовый» с тем же макетом, который модуль отдаёт по
умолчанию: вид сайта не меняется, меняется место, где макет правят — карточка
справочника вместо исходника модуля.

**Поставляемый макет обновляется по номеру версии.** Макет живёт в базе, поэтому
базы прежних сборок держали бы прежнюю вёрстку вечно: повторное заполнение их не
трогало. Теперь `ЗаполнитьТестовуюБазу` смотрит на реквизит «Версия» шаблона и
обновляет разметку, если там стоит номер прежней **поставляемой** вёрстки, о чём
пишет в отчёте. Правите макет руками — поднимите версию: номер, которого
платформа не ставила, для неё признак ручной правки, и такой макет она не
трогает.

### Главная — витрина, а не одна строка текста

Корень сайта показывает текст страницы «Главная», под ним восемь разделов
каталога и три свежие новости. Раньше там были заголовок и абзац: посетителю
некуда идти, кроме меню, а на демонстрации это первое, что видит заказчик.
Разделов именно восемь — каталог из полусотни превращает главную в простыню,
за которой не видно ни новостей, ни подвала; полный список открывается из меню.

**У раздела каталога обложка берётся из первой позиции внутри.** Разделы
приходят из выгрузки пустыми, своей картинки у них нет, и витрина встречала
посетителя сеткой серых плашек. Заодно вместо подписи «Раздел каталога»
показывается число позиций («6 позиций», у пустого — «Пока пусто»): это
единственное, что о разделе полезно знать до перехода.

### Витрина выглядит магазином, а не отладочной страницей

Оформление по умолчанию — не «пример вёрстки», а рабочий вид: белая шапка с меню
и поиском, витрина карточками (фото, название, крупная цена), карточка товара в
две колонки, подвал, адаптив под телефон. Цена показывается как `187 ₽`, ровные
копейки не пишутся — `187.00 RUB` выглядит выгрузкой, а не ценником.

Рамки при этом жёсткие и осознанные: политика страницы разрешает стили только со
своего адреса, поэтому ни CDN-фреймворков, ни внешних шрифтов и иконок; JS на
сайте нет вовсе. Всё оформление — один CSS, который отдаётся файлом
`/style.css` и собирается из палитры сайта (`СтилиСайта`) плюс произвольный CSS
редактора. Нейтральные тона (поверхность, граница, приглушённый текст) в палитру
намеренно не вынесены: иначе редактор, поменявший основной цвет, перекрашивал бы
заодно рамки и подписи.

### Адреса задаются таблицей, а не кодом

Куда ведёт адрес, решает справочник «Маршруты URL»: шаблон → тип контента.
Чтобы список новостей открывался по `/stati`, достаточно завести правило —
модули править не нужно.

| шаблон | тип контента | что открывается |
|---|---|---|
| `/` | Страница | главная |
| `news` | Новости | список |
| `news/{слаг}` | Новости | карточка |
| `catalog` | Каталог | витрина |
| `catalog/{слаг}` | Каталог | раздел |
| `product/{слаг}` | Товар | карточка товара |
| `{слаг}` | Страница | страница по слагу |

Шаблон без подстановки проверяется раньше шаблона с ней, поэтому `news`
выигрывает у `{слаг}` независимо от приоритета. Пустой справочник сайт не
ломает: тогда действуют те же правила по умолчанию, а правила справочника
проверяются первыми — умолчания остаются запасными, чтобы одна заведённая
строка не выключила все остальные адреса разом.

Импортированный каталог сразу виден на сайте: `/catalog` показывает верхний
уровень дерева, `/catalog/<группа>` — содержимое раздела, `/product/<товар>` —
карточку с артикулом, ценой, картинкой и описанием. Старые битриксовые адреса
вида `/catalog?group=<код>` отвечают `301` на новый адрес раздела — по коду из
выгрузки или по слагу, так что вес ссылок переезжает вместе с каталогом.

Соответствие остальных понятий: инфоблок → справочник, символьный код → слаг,
типы меню → `КодМеню`, композитный сайт → кэш ответов, агенты → регламентные
задания, веб-формы → «Формы обратной связи».

## Медиатека

Файлы сайта лежат в базе, а не на внешнем CDN. Картинка кладётся в поле карточки
«Медиа», а публичный адрес выдаёт хук `ПриЗаписи`:

```
ЭтотОбъект.ПубличнаяСсылка = ОпубликоватьКартинку(ЭтотОбъект.Файл, Опции);
```

Публикация происходит при записи, а не при рендере: GET-запрос посетителя не
должен писать в базу. Снятие галки «Активен» отзывает ссылку — адрес перестаёт
работать сразу, а не после чистки кэша. Браузер сохраняет тело картинки, но
ревалидирует ETag перед повторным использованием и обычно получает короткий 304.

Адрес содержит случайный токен, подобрать его нельзя. В разметку он попадает
через обычное поле данных, поэтому шаблон экранирует его как URL.

## Кэш и его инвалидация

Публичный сервис кэширует ответы на 60 секунд. Правка контента сбрасывает кэш
сама — в модулях объектов контентных справочников есть `ПриЗаписи` с вызовом
`СброситьКэшСервисов("Сайт")`.

**Важное свойство:** кэш живёт в памяти процесса сервера, поэтому сбрасывает
его только правка, сделанная ЭТИМ процессом — то есть через веб-интерфейс или
REST. Изменения из отдельного процесса (`onebase procrun`, регламентное задание
в другом экземпляре, прямая правка базы) сервер увидит лишь по истечении `ttl`.
Это проверено: правка заголовка через `procrun` не изменила выдачу до
истечения срока. Если сценарий требует мгновенного обновления из внешнего
процесса — уменьшайте `ttl` или дёргайте сайт после записи.

## Запуск обработок: командная строка не нужна

Обе обработки примера — заполнение демо-контентом и импорт каталога — запускаются
**из веб-интерфейса**: раздел «Обработки» в боковом меню. Командная строка нужна
только для развёртывания базы (`migrate`) и запуска сервера; заказчику,
работающему с готовой базой, она не нужна вовсе.

| Обработка | Кто может запустить | Что нужно указать |
|---|---|---|
| Заполнить демо-контент сайта | администратор, «Редактор сайта» | ничего |
| Импорт каталога из YML-выгрузки | администратор, «Редактор сайта», **«Контент-менеджер»** | сайт-владелец + файл |

Заполнение демо-контентом требует прав редактора: оно создаёт сайт, стиль,
шаблон и маршруты адресов — то, что контент-менеджеру закрыто намеренно. Раньше
обработка падала на первой записи сообщением платформы про отказ доступа —
верным, но не объясняющим, чего не хватает; теперь она называет нужную роль и
подсказывает, что каталог контент-менеджер загружает сам.

Проверка прав сделана **обработкой ошибки, а не пробной записью**: «проба пера»
оставляла бы в справочнике мусорный элемент при каждом запуске.

## Рабочий стол

`/ui` открывается страницей «Управление сайтом»: кнопки **«Посмотреть сайт»**
(главная, каталог, новости, `sitemap.xml`, `robots.txt`), быстрое добавление
контента, счётчик необработанных заявок и два списка — свежие заявки и
последние публикации.

Смысл первого виджета в том, что сайт и админка живут в одной базе и на одном
порту: контент-менеджер правит текст и тут же смотрит результат, не набирая
адрес руками. Ссылки записаны с префиксом `/hs/site` — это расположение сервиса
ВНУТРИ платформы. Поставили reverse proxy — поправьте адреса в виджете
`widgets/ОткрытьСайт.yaml` под внешний адрес сайта.

Ссылки помечены `new_tab: true` и открываются в новой вкладке. Это не мелочь
оформления: сайт — не интерфейс базы, ссылок назад в админку там нет и быть не
должно, поэтому переход в текущей вкладке оставляет пользователя без пути
обратно. Признак поддерживает любой виджет `type: actions` — он нужен всякой
ссылке, ведущей за пределы интерфейса.

Кнопки «Добавить» фильтруются правами: контент-менеджер видит «Страницу» и
«Новость», но не увидит того, на что у его роли нет права записи.

Демо-заполнение заводит три заявки, одна из них — со статусом «Спам»:
подозрительное обращение конфигурация не выбрасывает, и это видно на рабочем
столе, а не только в документации. В счётчик необработанных спам не идёт.

## Тесты конфигурации

```bash
onebase test --project examples/cms --sqlite cms.db --format tap
```

`ТестРоутера` проверяет подбор контента — ту часть, где ошибка не видна глазом:
страница открывается, но не та, либо черновик утекает наружу. Тест сразу нашёл
настоящий дефект: `НайтиСтраницу` не нормализовала входной адрес, и слаг в
другом регистре не находился.

`ТестРазметки` проверяет **готовый HTML**, а не промежуточные данные: тело
ответа читается методом `Ответ.ПолучитьТелоКакСтроку()`. Так ловится класс
дефектов, невидимый для проверок подбора: данные находятся правильные, а в
разметку попадает мусор. Первым же таким дефектом был `src="<nil>"` у позиции
без картинки (браузер запрашивал несуществующий адрес и рисовал битую иконку) и
`og:image="<nil>"` в карточке без обложки — то есть в превью для соцсетей.

## Поиск по сайту

Строка поиска в шапке ведёт на `/hs/site/search?q=…`. Под ней — полнотекстовый
индекс платформы: состав задан блоком `fulltext:` в метаданных «Страниц» и
«Новостей», отдельный индекс сайту не нужен.

Выдача фильтруется дважды: по типу объекта (адрес на сайте есть только у
страниц и новостей) и по публикации — индекс знает о черновике, но посетителю
его показывать нельзя.

## Формы обратной связи

Форма привязывается к странице реквизитом «Форма» и отправляется обычным
`<form method="post">` — без JavaScript. Приём вынесен в ОТДЕЛЬНЫЙ сервис
`Формы` (`/hs/forms/submit/<код>`): у «Сайта» анонимное чтение с кэшем, здесь
анонимная запись, и настройки одного не должны молча распространяться на другой.

Проверка полей — регулярными выражениями (план 124). Правила намеренно мягкие:
задача не отсеять почту по букве RFC, а поймать очевидный мусор. Подозрительное
не выбрасывается молча — заявка сохраняется со статусом «Спам», потому что живой
человек с необычным адресом не должен исчезать бесследно.

Защита от ботов — honeypot: поле, скрытое стилями (`position:absolute;
left:-9999px`, а не `type=hidden` — скрытое по типу бот распознаёт и пропускает).
Заполненная ловушка даёт ответ «спасибо» без записи в базу: иначе бот поймёт,
что попался, и подстроится.

Проверено живой отправкой: корректная заявка → 200 и запись в базе; кривой
контакт → 422 с внятным текстом; honeypot → 200 без записи; сообщение со
ссылкой → сохранено со статусом «Спам».

## Три грабли, на которых стоит эта конфигурация

1. **Ссылка из результата запроса не разыменовывает реквизиты** в контексте
   HTTP-сервиса: `ЗначениеРеквизитаОбъекта(Ссылка, "Домен")` молча возвращает
   `Неопределено`, и в `canonical` уезжает `https://<nil>/…`. Поэтому параметры
   сайта берутся ОДНИМ запросом с разыменованием через точку
   (`Стиль.CSS КАК CSS`), а роутер отдаёт структуру, а не ссылку.
2. **CSS нельзя вставлять в `<style>` шаблоном**: `html/template` в
   CSS-контексте заменяет произвольное значение на `ZgotmplZ` — и правильно
   делает. CSS отдаётся отдельным файлом `/style.css`, заодно кэшируется
   браузером и позволяет держать `style-src 'self'` без `unsafe-inline`.
3. **Функции внутри одного `.service.os` не видят друг друга** — вспомогательная
   процедура рядом с обработчиком падает в рантайме с «unknown function».
   Общий код живёт в `*.module.os`; сборка страницы-подтверждения поэтому
   лежит в `Рендер`, а не рядом с обработчиком формы.
4. **Латиница в публичных адресах и именах полей формы.** Кириллический сегмент
   шаблона URL сопоставляется только с процентным кодированием, а имя поля,
   присланное внешним клиентом, легко приходит не в UTF-8. Подписи для
   посетителя при этом остаются русскими — они в разметке.
5. **`Строка(Неопределено)` даёт «<nil>», а не пустую строку.** Непереданное
   поле формы выглядело заполненным, из-за чего honeypot считался сработавшим
   и КАЖДАЯ заявка молча отбрасывалась с видом успеха. Поля читаются через
   функцию `Поле()`, которая возвращает пустую строку.

   То же самое приходит из **незаполненной ссылки** в результате запроса: у
   товара без картинки `Строка(Стр.КартинкаСсылка)` — это «<nil>», строка
   непустая, поэтому её пропускают и `ПустаяСтрока()`, и `{{if}}` в шаблоне.
   В разметку уезжало `src="<nil>"`. Значения для разметки берутся через
   `Рендер.ТекстЗначения()`, а `ТестРазметки` следит, чтобы «<nil>» не
   появился снова — в трёх видах: как есть, экранированным и процентно
   закодированным в адресе (в последнем виде дефект и приехал).
6. **XML не собирается объектом `ШаблонHTML`**: он экранирует XML-декларацию
   как текст, и `sitemap.xml` перестаёт быть XML. Карта сайта собирается
   строкой с явным экранированием — правило простое: `ШаблонHTML` только для
   HTML.
