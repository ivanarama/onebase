# Как работать с проектной базой СППР

Это конфигурация OneBase, описывающая проектируемое решение как данные. Она не
содержит кода конфигурации — код лежит в YAML и `.os` целевого проекта; здесь
живёт модель: функции, связи, объекты метаданных, трассировка, сценарии,
правила, задачи, затраты.

## Порядок работы агента

1. Импорт описания целевого проекта, а не ручное перечисление файлов: выгрузи
   `onebase describe --project <путь> > desc.json` и проведи обработку
   `ИмпортОписания` с параметром `Файл`. Мост заводит справочник «Объекты
   метаданных» с составом полей и именами процедур модулей; импорт идемпотентен,
   повторный прогон добавляет только новые объекты. Записывать объекты руками
   можно только то, чего описания `describe` не видят: пакеты Go, планы
   (`Plans/*.md`), CLI-команды, документацию.
2. Заведи функцию (справочник «Функция») со статусом «Черновик», опиши
   результат для бизнеса и родителя. Переводы статуса: Черновик →
   НаСогласовании → Утверждена. Гейт этапов запрещает перескок.
3. Опиши связи функции в регистре «Связи функций» (Источник, Выход,
   Управление, Ресурс) — это стрелки IDEF0.
4. Привяжи импортированные объекты к функции (реквизит «Функция» объекта
   метаданных) и запиши трассировку в регистр «Трассировка»: функция, объект,
   путь к файлу, коммит. Импорт функцию не назначает — закрепление объекта за
   узлом декомпозиции решение проектировщика, аудит потом найдёт незакреплённые.
   Список закрепления задаётся парами «имя:тип»: объект одного типа может носить
   имя объекта другого (обработка и регламентное задание), модуль проведения
    документа носит имя документа. Порядок наполнения базы: `ЗаполнитьДемоданные`
    → `ИмпортОписания` → `ЗавестиДеревоФункций` (JSON-массив узлов, Черновик) →
    `ЗаписатьСвязи` (список «потребитель;источник;вид;данные~…») →
    `РасставитьФункции` (параметр `Пары` для целевого проекта, зашитый список —
    каркас) → `АудитПравил`.
5. Заведи тестовый сценарий (вид «Сценарий») с шагами; функция без сценария
   попадает в результаты аудита.
6. Заведи задачу по функции; статусы идут по маршруту Новая → Принята →
   ВРаботе → НаПроверке → Выполнена. Проведение пишет историю в регистр
   «История статусов задач». Задачу берешь из регистра «Очередь задач» по
   позиции; очередь заполняется планировщиком, агент не переставляет позиции.
7. Запусти аудит: обработка `АудитПравил` (регламентное задание по расписанию)
   применяет опубликованные правила и пишет результаты; читай их отчётом
   «Результаты аудита».

## Правила записи

* Статусы объектов меняются только по маршруту этапов: запись вне маршрута
  отклоняется слоем хранения.
* Правило аудита — самодостаточный запрос без параметров; его изменения
  публикуются документом «Публикация правила», старые результаты не меняются.
* Тесты каркаса: `onebase test --project examples/sppr --sqlite :memory:`
  (`kind: test`, проверяет гейт этапов, права ролей, трассировку, аудит, мост
  метаданных).
* Проверка конфигурации после каждой правки: `onebase check --project examples/sppr`.
* Мост метаданных не назначает функцию объекту и не перетирает уже записанный
  объект: импорт добавляет новые объекты и помечает их контролем «НеПроверено».
* Покрытие функций считается различными ссылками: функция, соединённая с
  объектами, сценариями и задачами одним запросом, даёт произведение строк.

## Второй агент

Второй агент подключается к той же проектной базе, когда выполнены шесть
условий:

1. Отдельный проект (справочник «Проект») и своя очередь: задачи второго агента
   не пересекаются с задачами первого, очередь заполняет планировщик.
2. Пользователь и роль заведены в интерфейсе (`Система → Пользователи`),
   API-токен выдаёт владелец в `Система → API-токены`; агент работает через
   REST v2 с Bearer-токеном, только там действуют права роли и RLS.
 3. Головой `onebase procrun` и MCP `procrun` пишут привилегиями платформы без
    проверки ролей: запись под ролью идёт через REST v2, headless-прогоном
    разрешены только обработки каркаса (`ЗаполнитьДемоданные`, `ИмпортОписания`,
    `ЗавестиДеревоФункций`, `ЗаписатьСвязи`, `РасставитьФункции`, `АудитПравил`).
4. Статусы идут по гейту этапов; агент не переставляет позиции очереди и не
   перекрашивает статусы напрямую.
5. Целевой проект подключён мостом (`ИмпортОписания`), объекты закреплены
   обработкой расстановки функций; аудит на пустой базе даёт только сознательно
   незакреплённые объекты.
6. Коммиты агента идут по одному коммиту на задачу с трейлером
   `Generated-with: Codex`; общие неотданные правки каркаса запрещены.

## Права ролей

* Проектировщик — функции, объекты метаданных, сценарии, связи, трассировка.
* Разработчик — задачи, объекты метаданных, трассировка, учёт времени,
  проведение ошибок.
* Тестировщик — сценарии, проведение ошибок, чтение результатов аудита.
* Руководитель — утверждение функций, публикация правил, планирование занятости.

## Наполнение базы целевым проектом

Целевой проект — `examples/compsem` (ТЗ: `examples/compsem/tz.md`, формат
поставки: `examples/compsem/exchange-schema.md`, контур синхронизации:
`examples/compsem/AGENTS.md`, `Plans/222-sppr-base-sync-instruction.md`).
Рабочая база — `examples/sppr/sppr.db` (SQLite, в git не попадает).

Порядок наполнения (документирован в `docs/help/bridge.md` и
`docs/help/assign.md`):

1. скелет целевого проекта (справочники, документы, регистры, роли);
2. `onebase describe --project examples/compsem > /tmp/compsem-desc.json`;
3. `ИмпортОписания` с параметром `Файл` (+ `Проект`, `КорневаяФункция`) —
   идемпотентен, назначенную проектировщиком функцию не затирает;
4. дерево функций по кодам ТЗ и ICOM-связи (`СвязиФункций`);
5. закрепление объектов (`РасставитьФункции`), сценарии, правила аудита, задачи
   и роли;
6. `АудитПравил`, отчёты `ПокрытиеФункций`, `ФункцииБезОбъектов`,
   `ТрассировкаФункции`, `РезультатыАудита`.

Функции, сценарии, правила аудита и задачи заводятся и до появления скелета
целевого проекта — `onebase describe` их не видит; объекты метаданных
закрепляются только после появления конфигурации, которую описывает `describe`.

Наполнение ведёт этап `$design-base-sync` (каноническая процедура
`.claude/skills/design-base-sync/SKILL.md`, Codex-адаптер
`.agents/skills/design-base-sync/SKILL.md`): цикл синхронизации
после каждой правки compsem, контроль соответствия каркаса документации,
немедленная правка каркаса при расхождении, границы полномочий (функции
утверждает Руководитель, правила публикует Руководитель, очередь и статусы
агент не перекрашивает).

## Контроль каркаса: документация обязана соответствовать прогону

Каркас — продукт, который описывает свои контракты в `docs/help/*.md` и в этом
файле. Каркас в разработке, документация опережает реализацию. Правило: каждое
утверждение документации проверяется прогоном (`onebase check --project
examples/sppr`, `onebase test --project examples/sppr --sqlite :memory:`,
`onebase procrun`/`onebase query` по базе). Утверждение, которое прогон не
подтверждает, — дефект каркаса: правь каркас в той же задаче (минимальная
правка `YAML`/`.os`, тест в `features/` + шаг в `features/шаги.yaml`,
обновление `docs/help/*`, один коммит по задаче). Обход расхождения — подделка
проверки, запрещён. Ограничение движка оформляется заявкой в конвейер
(`TRIAGE`), а не правкой каркаса; факт ограничения доказывает проба (`check` +
`migrate` + `procrun` + `query` на минимальном проекте).

Известные расхождения (записаны в `Plans/222-sppr-base-sync-instruction.md`,
правятся заявками по `CONTRIBUTING.md`):

1. `docs/help/model.md` описывает поле «Родительская функция», справочник
   `Функция` имеет иерархическое поле `Родитель`.
2. `РасставитьФункции` не принимает список пар назначения — **закрыто 2026-11-11**:
   параметр `Пары` (`кодфункции=имя:тип;…|…`), зашитый список каркаса остался
   значением по умолчанию; тест `features/наполнение_базы.feature`.
3. Мост читает 14 разделов; форм и плана обмена в выводе `onebase describe` нет,
   поэтому управляемые формы и план обмена целевого проекта в базу не попадают.
4. Справочника «Процесс» в базе нет: процессы целевого проекта не имеют места
   для записи.
5. Аудит выполняет запрос правила только по данным базы; правила над
   конфигурацией целевого проекта исполняются на стороне целевого проекта, а
   результат пишет обработка базы (headless `procrun`).
6. Дерева целевого проекта не чем было заводить — **закрыто 2026-11-11**:
   обработка `ЗавестиДеревоФункций` (файл JSON-массива узлов, идемпотентно по
   коду, статус «Черновик»).
7. Списка связей функций целевого проекта не чем было заводить — **закрыто
   2026-11-11**: обработка `ЗаписатьСвязи` (список «потребитель;источник;вид;
   данные~…», идемпотентно по паре измерений).
8. Родителя иерархического справочника нельзя прочесть в запросе и объекте DSL:
   `Ф.Родитель.Код` компилятор запроса не транслирует, `ПолучитьОбъект()`
   родителя не отдаёт (write-маппинг `Родитель`→`parent_id` есть, read — нет).
   Факт доказан пробой 2026-11-11 (`onebase query … Ф.Родитель.Код` — отказ);
   иерархия читается SQL по колонке `parent_id` вне DSL.

Интерфейсы работы с базой (проверено): справочники и документы пишет REST v2
(`POST/PUT/DELETE /api/v2/catalog/{Имя}`, `POST/PUT /api/v2/document/{Имя}`,
`POST …/post`) под Bearer-токеном роли; регистровый write-маршрут в REST v2
отсутствует (`/api/v2/inforeg/{name}` — только `get`), поэтому строки
`СвязиФункций`, `Трассировка`, `РезультатыПроверки`, `КонтрольОбъектов`,
`ОчередьЗадач` пишет только DSL-обработка базы (headless `onebase procrun`).
Чтение: `onebase query`, `GET /api/v2/inforeg/{Имя}`, `GET /api/v2/report/{Имя}`.
GUI (`onebase run --port 8080`) — интерфейс человека.

Агенты подключаются под своими ролями и токенами; матрица операций —
[`docs/agent-roles.md`](../../docs/agent-roles.md): `$design-base-sync`
(Проектировщик), `$acceptance-run` (Тестировщик), `$lead-desk` (подготовка под
ролью руководителя-человека), `$knowledge-intake` (Владелец знания),
`$night-ops` (Оператор), `$base-observer` (Наблюдатель), `$framework-fix`
(каркас). Факты прав (проверено 2026-11-10): роль-scoped запись — только REST
v2 под Bearer-токеном, нарушение — `403 forbidden`; headless `procrun` (и MCP
`procrun` под флагом `--allow-procrun`) работает без контекста роли; токен
выдаёт владелец в UI **Система → API-токены**, CLI-команды создания токена нет;
пользователи и роли заводятся офлайн (`onebase user add`, `onebase user role
assign`); YAML роли валидируется `check` и ссылку на несуществующий справочник,
регистр или отчёт отвергает (`metadata.invalid`, код 1) — роль заводится в той
же задаче, что её объекты; `processors_default: allow` ловит lint-warning, права
на обработку задаются списком.

Интерфейс проверенного результата (план 222 §2.2): `onebase test` — строка на
проверку и код возврата (провал — код 1 и `ОШИБКА — <модуль>:<строка>`);
`onebase procrun` — вывод обработки, код 1 на `ВызватьИсключение`; `onebase
check` и `onebase gherkin compile` — отказ статики; REST v2 под токеном роли —
код 200 или `403 forbidden`. Гейт переходов этапов стоит в слое хранения
(`internal/storage/stage.go`), отказ перехода действует и на headless-прогоне;
права роли headless-прогон не применяет (у `procrun` нет `--user`/`--role`).
Результат каждого прогона записывается в `РезультатыПроверки`, отказ —
документом `Ошибка`; обработки, которая это делает над целевым проектом, в
каркасе нет (план 222 §5, п. 5, 7) — это обязано дорасти, имитировать результат
запрещено.
