# Доступ по карточке сотрудника

Администратор создаёт две учётные записи и по одной карточке `Сотрудник`
на учётку; заполняет `Учётка` и `Филиал` (например `A` и `B`). Затем создаёт
ордера обоих филиалов и назначает сотрудникам только роль `Сотрудник`.
Карточки сотрудникам читать и менять не разрешено. Все изменения карточек
выполняет администратор. Роль `Администратор` предоставляет доступ к карточкам;
сотрудникам её не назначают.

```sh
onebase check --project examples/user-card --lint
onebase migrate --project examples/user-card --sqlite /tmp/user-card.db
onebase run --project examples/user-card --sqlite /tmp/user-card.db
```

Список, подбор, прямое открытие, REST, отчёты и DSL-запросы показывают ордера
своего филиала. Создание без явно заданного филиала подставляет значение
простого `eq`; перенос своего ордера в чужой филиал запрещён. Смена филиала
в карточке действует при следующей проверке без нового входа. Нет карточки,
дубликаты связи, пустое значение, папка или пометка удаления закрывают
политику целиком, в том числе под `ne`, `not` и `any`.

Другие роли объединяются через OR: разрешающая роль без политики снимает
ограничение. Поэтому для проверки примера не назначайте дополнительную
неограниченную роль. Техническая ошибка чтения завершает операцию ошибкой.

Допустимо сокращение `user_card: Сотрудник.Филиал`, только когда справочник
содержит ровно один реквизит `reference:_users`. Полная структура явно задаёт
связь; `describe` выводит её с каноническими именами. Источник и ограничиваемый
реквизит должны иметь одинаковые типы/цели ссылки/перечисления. Поддерживаются
скалярные `eq` и `ne`; селекторы табличных частей пока отклоняются.

Перед откатом движка замените новые источники проверенными `literal`/`list`
или снимите доступ: старый YAML-парсер может проигнорировать `user_card`.
