# Правка каркаса

Ты — разработчик каркаса. Работай по `CONTRIBUTING.md`: маршрут
`TRIAGE → PLAN → BUILD → REVIEW → MERGE`; isolated worktree, ветка от
`origin/master`, один коммит на задачу, `gofmt -w . && go test ./...`
перед коммитом, трейлер `Generated-with: Codex`.

## Канал

- `go test ./internal/<пакет> -run <тест>`, `go test -run <префикс> -count=3`.
- Прогон каркаса: `onebase check --project examples/sppr`, `onebase test
  --project examples/sppr --sqlite :memory:` (ожидается 4 теста, 31 проверка,
  0 провалов).
- Права ролей применяются в REST (`internal/api/v2.go`), гейт этапов — слой
  хранения (`internal/storage/stage.go`); DSL прав не проверяет.
- Headless `procrun` без контекста роли: правку проверки прав делай в
  том же маршруте, что и запись.

## Задачи каркаса (план 222 §5)

1. Правило аудита «сторона проверки»: каркас проверяет сторону каркаса;
   строки `РезультатыПроверки` целевого проекта пишутся обработкой каркаса,
   вызванной на целевом проекте (`procrun`), не REST.
2. Обработка `ЗаписатьСвязи` со списком связей, идемпотентная; Gherkin-шаги
   в `examples/sppr/features/` и `features/шаги.yaml`.
3. Role-scoped запись строк регистров: REST-маршрут записи регистра и/или
   контекст пользователя в headless (`--user`), RBAC в слое записи.
4. Канал переноса форм и плана обмена целевого проекта в базу (MCP `describe`
   их не видит) — расширить `describe`/`ИмпортОписания`.
5. Ограничения, которые не чинятся (период регистра — дата, индексов
   табличных частей нет, ресурсы накопления числовые), — в `TRIAGE` и
   документацию, не в обход.

## Гейты

- Каждое утверждение документации подтверждается прогоном; неподтверждённое —
  дефект каркаса, правь в той же задаче.
- Тест обязан ловить смену формата входных данных; тест без такой проверки
  неполон.
- Green CI обязателен; `docs/` и `README.md` обновляются в том же коммите,
  скан `release` и `go test ./internal/cli` не нарушаются.
