# План 121 — Этапы: декларативные состояния, гейт переходов и «где застряло»

Дата проектирования: 2026-08-12.
Статус: ⬜ **Проект** (не начато). Вырос из разбора плана 85: см. «Отношение к
плану 85» ниже.

## Контекст

Состояние объекта («Черновик → На согласовании → Утверждён → Отгружен») есть
почти в каждой прикладной конфигурации, но платформа про него ничего не знает.
Она видит обычный реквизит-перечисление, а порядок этапов и допустимые переходы
живут в коде модуля — каждый раз заново и каждый раз только на том пути записи,
где автор конфигурации вспомнил их проверить.

Из-за этого не работают три вещи, которые пользователь считает само собой
разумеющимися: **нельзя перескочить этап** (гарантированно, а не «если вызвали
через форму»), **видно, кто и когда двигал объект**, и **видно, где всё
застряло** — сколько объектов на каждом этапе и сколько времени они там висят.

### Два факта задают всю экономику плана

1. **Гейт можно поставить там, где его нечем обойти, — но точек ДВЕ, а не
   одна.** Четыре независимых пути записи (`entityservice`, DSL, обмен, запись
   справочника) сходятся не в одну функцию, а в две: `storage/crud.go:76`
   `db.upsert` (создание и записи без версии) и
   `storage/optimistic_lock.go:36` `UpsertVersioned`, который делает
   собственный `UPDATE … WHERE id AND _version` **мимо** `upsert` — и именно
   через него идут все правки существующих объектов из формы, REST и DSL.
   Прецедент зафиксирован комментарием в самом файле: хук FTS-индексации
   однажды не задел этот путь, и в поисковой выдаче оставался стёртый
   пользователем телефон. Обе точки **уже прочитали старое значение** — ровно
   то, чего требует проверка перехода. Гейт и запись истории обязаны стоять в
   обеих (аудит и FTS там уже продублированы — этап ляжет рядом); гейт только в
   `upsert`, как и проверка выше storage, был бы дефектом класса issue #611:
   написан, зелёный в тестах на создание, а на правке существующего объекта из
   формы не вызывается.

2. **История переходов — это дифф, который уже считается.** `AuditDiff` на
   `crud.go:185` и `optimistic_lock.go:115-118` отдаёт `{поле, было, стало}`,
   актор лежит в контексте.
   Отдельный сбор данных не нужен — нужна безусловная запись подмножества
   этого диффа (только поле-этап) в собственную таблицу. Собственную, а не
   `_audit`, по двум причинам: журнал аудита **выключаем** (`audit.go:262,278`
   молча ничего не пишут при `!s.Enabled`), а «где застряло» — не аудит, а
   рабочий отчёт, который должен работать всегда и иметь свой индекс.

## Цель

- **декларация**: у сущности объявляются упорядоченные этапы и допустимые
  переходы — на существующем поле-перечислении, **без нового вида объекта
  метаданных**;
- **гейт**: недопустимый переход отвергается в слое storage — в обеих точках
  записи (`upsert` и `UpsertVersioned`), то есть на всех путях сразу;
- **история**: платформа сама пишет `_stage_history` (кто, когда, из какого в
  какой), безусловно и в той же транзакции;
- **отчёт «где застряло»**: сколько объектов на этапе, сколько времени висят,
  что просрочено;
- **схема**: этапы со стрелками и подсветкой текущего — на уже вендоренном
  ECharts.

### Чего этот план не делает

Ни экземпляров процессов, ни объекта «Задача», ни адресации, ни
автопродвижения, ни `bpm/*.yaml`, ни параллельных ветвей с кворумом. Всё это —
предмет плана 85, и он остаётся замороженным.

## Синтаксис / метаданные

Блок `stages` у сущности, рядом с `fulltext`/`tile_view`/`based_on`
(`metadata/yaml.go:57-83`):

```yaml
name: Заявка
fields:
  - { name: Состояние, type: enum:СостояниеЗаявки }
stages:
  field: Состояние                  # поле-перечисление, ведущее этапы
  order: [Черновик, НаСогласовании, Утверждена, Отклонена]
  transitions:                      # допустимые переходы; всё, чего нет, — запрещено
    - { from: Черновик,       to: [НаСогласовании] }
    - { from: НаСогласовании, to: [Утверждена, Отклонена] }
    - { from: Отклонена,      to: [Черновик] }
  deadline_days: { НаСогласовании: 2 }   # опц.: сколько ждём на этапе → просрочка
  enforce: warn                          # warn (умолчание) | strict
```

`enforce: warn` — нарушение пишется в лог и в `onebase check`, но запись
проходит. `strict` — запись отвергается. Умолчание `warn` выбрано осознанно:
иначе включение блока в существующей конфигурации ломает уже работающие
данные и обработки (см. «Обратная совместимость»).

Значения этапов не дублируются — они берутся из перечисления, объявленного в
`enums/`. `order` задаёт порядок для отчёта и схемы, `transitions` — правила.

## Хранилище / SQL

`_stage_history` — системная таблица, создаётся `EnsureStageHistorySchema` по
образцу `storage/audit.go:72`:

| Колонка | Смысл |
|---|---|
| `id` | PK |
| `entity_name`, `record_id` | объект |
| `field` | поле-этап (сущность может вести несколько) |
| `from_stage`, `to_stage` | было / стало (`from_stage` пуст при создании) |
| `at` | момент перехода |
| `user_id`, `user_login` | актор из `auditUserFromCtx` |

Индексы: `(entity_name, record_id, at)` — история объекта;
`(entity_name, field, to_stage, at)` — «сколько объектов сейчас на этапе и с
какого момента» без сканирования.

Время на этапе считается как разница между текущим моментом и последней
записью по объекту. Арифметика дат в запросах уже есть (issue #707, PR #727).

## Изменения в коде

- **`internal/metadata/`** — `rawEntity.Stages`, модель `Stages`, валидация
  (`validate.go`): поле существует и это `enum`; все значения `order` и
  `transitions` есть в перечислении; недостижимые этапы и переходы «из ниоткуда»
  — ошибка; сущность без `stages` не меняется ни на байт.
- **`internal/storage/crud.go` И `internal/storage/optimistic_lock.go`** — гейт
  ставится в **обе** точки записи, общей функцией `checkStageTransition(oldRow,
  fields, entity)`. В `upsert` — между чтением `oldRow` (`:79-85`) и построением
  запроса; в `UpsertVersioned` — между чтением `oldRow` (`:43-46`) и `UPDATE`.
  При `strict` вернуть `i18nerr` (тот же механизм, что у проверки цикла иерархии
  в `upsert:118`), при `warn` — записать предупреждение. После успешной записи —
  безусловная запись в `_stage_history`, рядом с аудитом в обеих точках
  (`crud.go:175-190` и `optimistic_lock.go:115-118`). Не дать этим двум местам
  разъехаться — главный урок этого файла: FTS и аудит туда уже дописывали
  вдогонку.
- **`internal/storage/stage_history.go`** (новый) — `EnsureStageHistorySchema`,
  `LogStageChange`, чтение истории объекта, агрегат «по этапам» для отчёта.
- **Подъём базы** — вызвать `EnsureStageHistorySchema` во всех местах, где уже
  вызывается `EnsureAuditSchema`: `backup/universal.go` (иначе таблица не
  появится после restore), `migrate`, `run`, `deploy`, dev-сервер. **Это самый
  вероятный пропуск плана** — список перечислен поимённо, компилятор о нём
  молчит.
- **`internal/ui/`** — история переходов в карточке объекта; схема этапов на
  ECharts (серия `graph`, узлы из `order`, рёбра из `transitions`, подсветка
  текущего) — рядом с уже подключённым `echartsJSON` (`templates.go:587`);
  отчёт «где застряло».
- **`internal/configcheck/`** — `onebase check` сообщает о нарушениях `warn` в
  существующих данных и о недостижимых этапах.
- **`internal/cli/describe.go`, `impact.go`, `aiguide.go`** — новый блок в
  выдаче структуры и в `AGENTS.md`, чтобы ИИ-помощник его использовал.
- **`internal/i18n`** — новые строки в 16 локалей (гейт `i18ncheck` в джобе
  `build` не пропустит коммит без них).

## Обратная совместимость

Три места, где план может сломать работающее:

1. **Существующие конфигурации.** Блока `stages` у них нет → поведение
   неизменно. Прямая проверка: `examples/*` должны проходить `onebase check` и
   свои тесты без правок.
2. **Данные, нарушающие объявленные переходы.** У объектов, созданных до
   объявления `stages`, история пуста, а текущее состояние может быть
   недостижимо по правилам. Отсюда умолчание `enforce: warn` и отдельный отчёт
   `onebase check`: сначала показать нарушения, включать `strict` осознанно.
3. **Отчёт «сколько висит» для старых объектов.** Истории нет → показывать
   «неизвестно», а не считать от нуля. Дата первой записи в `_stage_history`
   становится точкой отсчёта.

## Риски и решения

| Риск | Решение |
|---|---|
| Обмен данными (план 86): объект приезжает из другой базы с «недопустимым» переходом | путь `exchange/package.go:732` идёт через тот же `upsert` — при `strict` пакет упадёт. Решение: обмен пишет с флагом «переход внешний», гейт пропускает, история фиксирует источник |
| Проведение и пометка удаления (план 50) меняют объект, не трогая этап | гейт срабатывает только при **изменении** поля-этапа — эти пути его не касаются |
| Маскирование поля-этапа (план 88) | схема и отчёт обязаны идти через тот же слой, что списки; поле под маской → этап не показывается, а не «показывается пустым» |
| Кто вправе двигать этап | в первой версии — обычные права на запись объекта. Права «на переход» (роль X может только Согласование→Утверждена) — отдельный вопрос, сознательно вне плана |
| `_stage_history` растёт | индекс по `(entity_name, record_id, at)`; чистка — вместе с политикой хранения аудита, отдельной задачей |

## Тесты

- **матричный** `dbtest.ForEachDialect` (обязателен по CLAUDE.md — трогаем
  семантику SQL): гейт, запись истории, агрегат «по этапам» одинаковы на SQLite
  и PostgreSQL;
- гейт срабатывает на **каждом** из четырёх путей записи: `entityservice`, DSL
  (`Документы.X.Записать`), обмен, запись справочника — по тесту на путь;
  проверка идёт **через публичную точку входа**, а не вызовом приватной функции
  (CLAUDE.md, повод — issue #611). Тесты `entityservice` и DSL обязаны править
  **существующий** объект, а не только создавать новый: правка существующего
  идёт через `UpsertVersioned` (вторая точка записи), и тест только на создание
  пропуск гейта в ней не заметит;
- `warn` пропускает и предупреждает, `strict` отвергает;
- история пишется при выключенном журнале аудита;
- откат транзакции откатывает и историю;
- конфигурация без `stages` ведёт себя ровно как раньше (регресс на `examples/*`).

## Отношение к плану 85

План 85 (бизнес-процессы и задачи) предлагает движок карты маршрута с
`bpm/*.yaml`, экземплярами процессов, задачами и автопродвижением. Разбор
2026-08-12 показал: спроса на движок нет (208 issue от 18 авторов — ни одного
запроса на функциональность плана 85; сценарий документооборота при этом в
аудитории живёт — на OneBase строится СЭД DocFlow, но её автор просит
общеплатформенные фиксы, а не движок БП), сценарий согласования уже собирается
прикладным слоем (`examples/callcenter/src/Согласование.module.os`, 114 строк),
а цена движка занижена — по оценке, примерно вдвое — из-за сквозных подсистем.

Этот план забирает из 85 то, что даёт ценность **само по себе и для любого
документа**, а не только для того, под который нарисована карта маршрута:
гарантию переходов, историю и ответ на вопрос «где застряло». Новый вид объекта
метаданных не заводится, откат — удаление блока `stages` из YAML.

Следующий кирпич, если понадобится (отдельным планом): **предикат
существования по регистру в строковых политиках** — «вижу строку, если в
регистре есть запись, связывающая меня с её значением». Сейчас `RowValue`
знает только `user`/`user_attr`/`literal`/`list` (`auth/row_access.go:31-35`),
а предикат через ссылку — один шаг, связь один-к-одному
(`storage/predicate.go:128`). Это механизм ролевой адресации из 1С, сделанный
как общее правило видимости; он закрывает целый класс задач вне всякого BPM
(«менеджер видит клиентов своей группы», «кладовщик — документы своих складов»)
и является предусловием для платформенной «Задачи», если та когда-нибудь
понадобится.
