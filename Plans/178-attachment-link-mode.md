# План 178 — Вложения: режим ссылки и открытие по месту

Заявка: #1480. Вариант 1 развилки триажа — сначала план полного двойного режима
`stored` / `link`, затем реализация срезами.

## Контекст

Сегодня режим один: платформа хранит копию. Выбор файла всегда уходит
multipart-загрузкой (`internal/ui/handlers_attachments.go`, `attachmentUpload`),
просмотр всегда идёт скачиванием с `Content-Disposition: attachment`
(`attachmentDownload`), а панель вложений (`internal/ui/templates.go`, шаблон
`ob-attachments`) рисует только ссылку скачивания. Автор заявки получает три
копии одного файла: исходник на диске, копию в `~/.onebase/files/` и скачанную
обратно — и так при каждом просмотре.

Модель хранения к изменению готова наполовину. У вложения есть `loc`
(`internal/storage/attachments.go`, колонка добавлена планом 110) со значениями
`''` (легаси, читается как disk), `disk` и `s3`; `OpenAttachment` и
`MaterializeAttachment` диспетчеризуют по нему и **падают с ошибкой на
неизвестном значении**. Третье значение добавляется безопасно по построению:
код, который его не знает, не выдаст мусор, а откажет.

Примитивы «открыть в программе ОС» и «выбрать файл, не загружая его» в
репозитории тоже уже есть: `launcher.OpenPath` (`explorer` / `open` /
`xdg-open`) и `launcher.BrowseFile` (нативный диалог через PowerShell, zenity,
osascript) в `internal/launcher/openpath.go`. Оба сегодня вызываются только из
лаунчера, и в их комментариях прямо записана граница доверия: «аргументы — из
флагов CLI администратора на его же машине». Это не мелочь, а ровно та граница,
которую заявка предлагает перейти.

## Что на самом деле решается

Наивное чтение заявки — «добавить в `loc` значение `link` и хранить путь» —
ломается на трёх вопросах. Ответить на них надо до первой строки кода, потому
что ответы фиксируются в данных, а данные откатывать нечем.

**1. Чья это файловая система.** Путь без указания машины бессмыслен:
`C:\Users\Иван\Документы\скан.pdf` на соседнем рабочем месте либо не
существует, либо ведёт на чужой файл с тем же именем. Хранить путь без
владельца — заложить мину, которая сработает на втором пользователе или при
переносе базы.

**2. Кто открывает.** Заманчиво сделать `POST /ui/attachments/{aid}/open`,
который на сервере зовёт `launcher.OpenPath`. Этого делать нельзя.
`xdg-open`/`explorer`/`open` на `.desktop`, `.bat`, `.lnk`, `.command` — это не
«показать файл», это запуск программы. Путь во вложение кладёт пользователь с
правом записи, значит такой endpoint превращает право «писать в справочник» в
исполнение произвольного кода на машине сервера, причём от имени сервисной
учётки. **Сервер не открывает ссылки никогда** — это инвариант плана, а не
предпочтение.

**3. Где это физически возможно.** Открыть файл в родной программе может только
клиент, имеющий доступ к ОС: нативное окно WebView2
(`internal/launcher/window_webview.go`, сборка `-tags webview` под Windows;
`launcher.NativeIsolatedSupported()`). Обычная вкладка браузера этого не умеет
и уметь не будет — ни File System Access API, ни что-либо ещё не запускает
внешнюю программу.

Отсюда решение плана: **ссылка принадлежит клиентской машине, открывает её
только клиент, сервер путь хранит и никогда не трогает.**

## Модель данных

`loc` получает значение `link`. Три колонки добавляются через
`AddColumnIfMissing` — тем же приёмом, что и сам `loc`:

```
link_path        TEXT NOT NULL DEFAULT ''   -- путь, как его увидел клиент
link_origin      TEXT NOT NULL DEFAULT ''   -- идентификатор рабочего места
link_captured_at TIMESTAMP                  -- когда путь захвачен
```

`link_origin` — не имя машины и не логин, а случайный UUID рабочего места,
который нативный клиент хранит у себя рядом с профилем окна
(`ONEBASE_WEBVIEW_PROFILE`) и присылает при захвате пути. Совпал с текущим —
путь наш, открытие разрешено. Не совпал — UI показывает «файл добавлен на
другом рабочем месте», кнопка открытия неактивна. Этого достаточно, чтобы
никогда не открыть чужой путь, и не требует ни инвентаризации машин, ни
доверия к именам хостов.

`size_bytes` и `mime_type` у ссылки — **снимок на момент захвата, а не истина**:
файл могли заменить или удалить. UI обязан подписывать их как «на момент
добавления», иначе список будет врать тем увереннее, чем он старше.

Что не меняется: `''`, `disk` и `s3` ведут себя как раньше; неизвестный `loc`
по-прежнему ошибка.

## Границы, которые план фиксирует явно

Сервер не читает и не открывает `link_path`. Для `loc='link'`:

- `OpenAttachment` и `MaterializeAttachment` возвращают типизированную ошибку
  «вложение-ссылка не имеет серверного содержимого»;
- `ПутьКВложению` (`internal/ui/dsl_attachments.go`) возвращает эту же ошибку, а
  не путь. Прикладной код, который сегодня делает
  `ПутьКВложению → ПисьмоEmail.ПрисоединитьФайл`, на ссылке обязан получить
  внятный отказ, а не пустую строку;
- публичные ссылки плана 127 (`/pub/<токен>`) на вложения-ссылки не выдаются;
- резервная копия и перенос базы переносят **запись** о ссылке, но не файл;
  восстановление на другой машине оставляет её нерабочей, и это должно быть
  видно в UI сразу, а не при первом клике.

Ни один из пунктов не дыра. Это одна и та же честная фраза «мы не храним этот
файл», сказанная в пяти местах. План требует, чтобы каждое из них говорило её
словами.

## Срезы

### Срез A — модель, запись и честный отказ (ведущий)

- Колонки и значение `loc='link'`; `EnsureAttachmentTable` дополняется.
- `SaveAttachmentLink(ctx, owner…, path, origin, snapshot)` рядом с существующей
  загрузкой; право — `write` на владельца, как у загрузки.
- Валидация пути на входе: непустой, абсолютный, длина в пределах, без
  управляющих символов. Существование файла сервер **не проверяет** — он не
  имеет к нему доступа и не должен делать вид, что имеет.
- Отказы: `OpenAttachment`, `MaterializeAttachment`, `ПутьКВложению`, `/pub`.
- UI панели вложений отличает ссылку от хранимого: иконка, подпись пути,
  «добавлено на другом рабочем месте» при чужом `link_origin`.
- Запись ссылки доступна только клиенту, который умеет её открыть: в обычном
  браузере кнопка «Добавить ссылку» не показывается, а прямой POST отклоняется.

### Срез B — клиентская возможность открыть

- Первый `Bind` в нативном окне (`window_webview.go` сегодня использует только
  `Navigate`; `third_party/webview_go` `Bind` поддерживает). Появляется ровно
  две функции: `obPickLocalFile()` → `{path, size, mime}` через
  `launcher.BrowseFile`, и `obOpenLocalFile(path)` → `launcher.OpenPath`.
- `obOpenLocalFile` принимает **только** путь, который клиент сам же захватил в
  этом окне: сверка со списком путей, пришедших с сервера в текущей странице, и
  с `link_origin`. Произвольная строка из JS не открывается — иначе XSS на
  странице становится запуском программы.
- Рабочее место получает свой UUID при первом запуске окна и хранит его рядом с
  профилем.
- Сборки без `-tags webview` и обычный браузер: обе функции отсутствуют, UI это
  видит и не рисует кнопок.

### Срез C — выбор режима

Заявка просит выбор «на уровне реквизита, формы или базы». Реквизит здесь не
ложится: вложения в OneBase привязаны к записи целиком, а не к реквизиту
(`_attachments.owner_kind/owner_name/owner_id`), отдельного реквизита-файла нет.
Поэтому уровней два, и они честнее отражают модель:

- база: `attachments.mode: stored | link | ask` в конфигурации, дефолт `stored`;
- сущность: переопределение в метаданных справочника/документа.

`ask` показывает обе кнопки и оставляет выбор пользователю. Смена режима не
трогает уже созданные вложения: у каждого свой `loc`, и это главная причина,
почему режим не хранится где-то отдельно от записи.

### Срез D — открытие из списка

Сегодня список о вложениях не знает вовсе: панель `ob-attachments` живёт только
на форме записи. Срез добавляет **опциональную** колонку списка: один пакетный
запрос на страницу списка (`owner_id IN (…)`), без запроса на строку. Клик:
одно вложение — открыть сразу (ссылку — через срез B, хранимое — скачать);
несколько — открыть карточку на панели вложений. Колонка выключена по
умолчанию: платить запросом за каждый список ради сущностей без вложений нельзя.

### Срез E — inline-просмотр хранимых вложений (независимый)

Это узкий вариант 2 из триажа, и он полезен всем, включая браузер. Для
безопасных MIME (`application/pdf`, `image/*`, `text/plain`) отдавать
`Content-Disposition: inline` с жёстким `Content-Security-Policy` и
`X-Content-Type-Options: nosniff`; остальное — как сейчас, вложением. Срез
независим от A–D и может идти первым, если нужен быстрый эффект.

## Тесты

- `internal/storage`: round-trip ссылки (сохранение, чтение, список); `''`,
  `disk`, `s3` не задеты; `OpenAttachment`/`MaterializeAttachment` на `link`
  дают ошибку, а не пустой ридер; матрица на обоих диалектах.
- `internal/ui` через публичный HTTP: POST ссылки без клиентской возможности —
  отказ; с ней — запись; GET панели показывает ссылку и чужое рабочее место;
  `/pub` на ссылку — отказ; download на ссылку — отказ.
- DSL через публичный путь: `ПутьКВложению` на ссылке — ошибка с текстом,
  письмо такую не прикрепляет.
- `internal/launcher`: whitelist `obOpenLocalFile` — путь не из текущей
  страницы не открывается; сборка без webview не регистрирует Bind.
- Список (срез D): один запрос на страницу независимо от числа строк.
- Срез E: `inline` только для разрешённых MIME, `nosniff` и CSP на месте.

## Verification

1. Нативное окно, режим `link`: добавить файл ссылкой — копии в
   `~/.onebase/files/` не появилось, размер каталога не вырос.
2. Открыть из панели — файл открылся в программе ОС; изменить файл на диске,
   открыть снова — открылась новая версия, запись в базе прежняя.
3. Переименовать файл — UI говорит «файл не найден», запись остаётся.
4. Открыть ту же базу в обычном браузере — ссылка видна, кнопка открытия
   неактивна, скачивание не предлагается.
5. Открыть базу на другом рабочем месте — «добавлено на другом рабочем месте».
6. Перенести базу на другую машину — ссылки видны и помечены нерабочими,
   хранимые вложения работают.
7. `onebase check` на конфигурации с `attachments.mode: link` в многопользовательской
   установке — предупреждение о границе.

## Эстимейт

| Срез | Содержание | Оценка |
|---|---|---|
| A | модель, запись, отказы, панель | ~2 дня |
| B | Bind, выбор и открытие, рабочее место | ~2 дня |
| C | режимы базы и сущности | ~1 день |
| D | колонка и открытие из списка | ~1,5 дня |
| E | inline-просмотр хранимых | ~1,5 дня |

Итого ~8 дней. Срезы A и B неразделимы по смыслу (запись без открытия
бесполезна), C–E независимы и могут идти в любом порядке.

## Риски и откат

- **Главный риск — путь без владельца.** Снимается `link_origin` в срезе A; без
  него любая последующая правка уже записанных ссылок будет миграцией данных.
- **Второй — соблазн открыть на сервере.** Снимается тем, что серверного
  endpoint открытия в плане нет вовсе и `OpenAttachment` на `link` отказывает.
  Если такой endpoint когда-нибудь появится, он должен проходить отдельный
  разбор безопасности, а не «до кучи».
- Откат: срезы A–D отключаются режимом `stored` и не трогают существующие
  вложения — у них свой `loc`. Уже созданные ссылки после отката видны и
  помечены как неподдерживаемые, данные не теряются. Срез E откатывается
  возвратом `Content-Disposition: attachment`.
