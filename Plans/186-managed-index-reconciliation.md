# План 186 — безопасное согласование управляемых индексов с конфигурацией

Дата проектирования: 2026-09-27. Статус: 📋 проектирование; этот PR не меняет продуктовый код.
Ведущая заявка: [#1566](https://github.com/ivanarama/onebase/issues/1566).
Выбран вариант 1 доверенного триажа: отдельный план учёта управляемых индексов и перехода старых баз до реализации. [#1439](https://github.com/ivanarama/onebase/issues/1439) описывает существующий `indexes:` и не вводит второй механизм миграции.
Основание инвентаризации: `main` `b752bfd83c4f1935d6bbff10a99d45d14365f0b8`.

## Контекст и текущий контракт

`indexes:` позволяет объявить обычный или уникальный индекс сущности. `ensureEntityIndexes` в `internal/storage/migrate.go` создаёт желаемые индексы через `CREATE [UNIQUE] INDEX IF NOT EXISTS`, затем вызывает `dropStaleUniqueCodeIndexes`. Последняя функция в `internal/storage/code_unique.go` перебирает только индекс кода/номера и пары «разрез + код/номер». Уникальный индекс по произвольному полю остаётся после `unique: true → false` или удаления `indexes:`. На следующей записи БД всё ещё отвергает дубль, хотя YAML уже разрешает его. Это воспроизведено триажем #1566 на SQLite; PostgreSQL в том прогоне не проверялся.

`stableIndexName` (`internal/storage/ddl.go`) строит имя `idx_ob_…` из таблицы, порядка колонок и признака уникальности. Имя и совпадение определения не доказывают происхождение: администратор мог создать такой же индекс вручную, а `IF NOT EXISTS` может скрыть одноимённый индекс с другим определением. Текущая `Migrate` не оборачивает всё изменение схемы одной транзакцией. Уже есть отдельный `migrate --dry-run` для реструктуризации полей, но он не показывает действия с индексами.

## Синтаксис / YAML и наблюдаемая семантика

Формат YAML остаётся прежним:

```yaml
name: Контрагенты
fields:
  - {name: ИНН, type: string}
indexes:
  - {fields: [ИНН], unique: true}
```

Для **доказанно управляемого** индекса повторный `Migrate` точно отражает YAML, если тот же прогон не меняет колонку, от которой зависит индекс:

| Изменение конфигурации | После успешной миграции |
|---|---|
| `unique: true → false` | Уникальный индекс снят, обычный создан; повтор ИНН допустим. |
| Удалён `indexes:` или запись в нём | Прежний управляемый индекс снят. |
| Изменены поля, порядок или уникальность | Сначала создано новое определение, затем снято старое. |
| Конфигурация не менялась | Нет DDL и изменений в реестре. |

`numerator.unique` участвует в том же наборе желаемых индексов. Совпадающие объявления `numerator.unique` и `indexes:` дают один индекс; снятие одного объявления не снимает индекс, пока остаётся другое. Внешние индексы, первичные ключи, индексы ограничений, регистров, табличных частей, этапов и FTS не входят в этот механизм. Уникальный индекс по `NULL` сохраняет текущую семантику двух диалектов: несколько незаполненных значений допустимы.

**Инварианты.** Только запись реестра владения, созданная вместе с DDL или явно подтверждённая оператором, разрешает автоматический `DROP`. Перед любым `DROP` фактические таблица, схема, имя, уникальность и *упорядоченные* колонки должны совпасть с сохранённой подписью; иной объект или сбой интроспекции останавливает миграцию. Совпадение имени `idx_ob_…` само по себе не даёт права удалить. Неоднозначный legacy-индекс не замалчивается: миграция возвращает понятный отказ с таблицей и именем до снятия какого-либо ограничения. Отказ при создании нового UNIQUE из-за дублей оставляет прежние индексы и записи реестра; повторный запуск после исправления данных безопасен. Любое изменение колонки, затрагивающее индекс, проходит отдельный preflight **до первого DDL данного вызова `Migrate`**; индексная фаза после реструктуризации не может служить защитой от уже выполненного `DROP`.

## Хранилище / SQL, владение и legacy-переход

Новая служебная таблица `_managed_entity_indexes` хранит `(table_name, index_name)` как ключ, версию формата, вид индекса, упорядоченные колонки, нормализованную подпись физического определения и источник `created`/`adopted`. Схема PostgreSQL задаётся текущей `search_path` и проверяется через `current_schema()`; SQLite использует свою базу. Реестр создаётся через `EnsureServiceSchema` и публичную `Migrate`, как другие служебные таблицы. Факт наличия записи без соответствующего физического индекса или расхождение подписи — ошибка, требующая явного разбора; реестр не исправляется по догадке.

Для нового индекса: после блокировки и чтения каталога проверить отсутствие одноимённого объекта, создать индекс и запись реестра в **одной транзакции**. При существующем одноимённом объекте без записи реестра сравнить определение и показать, что индекс неуправляемый; несовпадающее определение — отказ, а не успех `IF NOT EXISTS`. Для удаления: перечитать каталог и реестр под той же блокировкой, сверить подпись и желаемый набор, выполнить `DROP INDEX` и удалить запись реестра в той же транзакции. PostgreSQL не использует `CONCURRENTLY` внутри этой транзакции; риск блокировки таблицы и окно обслуживания документируются.

На старой базе реестр отсутствует. Унаследованный `idx_ob_…` нельзя объявлять своим по имени или автоматически записывать в реестр. `migrate --dry-run` показывает текущий и желаемый набор, точное определение, предполагаемое действие и статус владения. Для legacy-кандидата он выдаёт шаблон JSON-манифеста принятия. Кандидат допускается лишь если это обычный индекс сущности без выражения/условия/constraint backing, его колонки принадлежат этой сущности, имя точно равно `stableIndexName` от фактической структуры, а схема и таблица совпадают. Манифест содержит таблицу, имя, фактическое определение и SHA-256 его канонической подписи. Оператор после сверки с каталогом и резервной копии запускает `onebase migrate --adopt-indexes <manifest.json>`; каждый указанный объект перепроверяется непосредственно перед записью. Манифест подтверждает владение только перечисленными объектами, не включает wildcard. После принятия устаревший индекс может быть снят в том же атомарном согласовании. Если прежняя конфигурация уже потеряна, такой манифест позволяет принять видимый в каталоге индекс без восстановления старого YAML. Индекс с другим именем/структурой остаётся внешним; для него используется ручная операция администратора вне автоматического DROP.

Обычная миграция не удаляет legacy-кандидат. Если он конфликтует с желаемой конфигурацией (например, старый UNIQUE после снятия `unique: true`), она останавливается с инструкцией для `--dry-run`/принятия, не сообщает об успешном снятии уникальности и не открывает запись дублей. Доказательство происхождения старого объекта без записи реестра в принципе невозможно; явное принятие — осознанная граница доверия.

## Граница реструктуризации колонок

Сейчас `Migrate → restructureTable → retypeSQLite/dropColumn → dropIndexesOnColumn` удаляет в SQLite **любой** индекс колонки до `ensureEntityIndexes`; при удалении ссылочной колонки `dropColumnRebuildSQLite` ещё и пересоздаёт всю таблицу. Поэтому `DROP` из этого пути нельзя считать частью нового согласования или ограничивать только проверкой в поздней индексной фазе. На PostgreSQL путь `ALTER COLUMN TYPE` ведёт себя иначе, но контракт отказа должен быть одинаковым.

Перед любым `Ensure*Schema`, `CREATE TABLE`, `ADD/RENAME/RETYPE/DROP COLUMN` и записью карты полей `DB.Migrate` строит read-only план изменений существующих таблиц сущностей и читает **все** их индексы из каталога, включая внешние, legacy, зарегистрированные, constraint-backed, partial и expression. Для каждого запланированного `Rename`, `Retype` или `Drop` проверить зависимости по колонкам, выражению и предикату; неизвестная зависимость или ошибка интроспекции — отказ. Если колонку использует хотя бы один индекс любого происхождения, ранний preflight останавливает прогон с именами таблицы, колонки, индекса и причиной **до любого DDL**. Текущий `dropIndexesOnColumn` нельзя вызывать для индексов сущностей без этого gate; запретить или заменить прямой вызов так, чтобы никакой обходной путь (`retypeSQLite`, обычный `dropColumn`, SQLite rebuild) не снимал индекс. Тот же gate выполняется непосредственно перед структурным DDL под блокировкой таблицы/базы; при новой зависимости откатить транзакцию затронутой таблицы и остановиться. Если базу нельзя надёжно заблокировать и повторно проверить, отказать. Ранний gate предотвращает известный отказ до остальных работ `Migrate`, но не объявляет всю миграцию атомарной при внешнем DDL между фазами.

Управляемый индекс, который мешает смене колонки, оператор снимает отдельной **предыдущей** миграцией: убрать соответствующий `indexes:`/`numerator.unique`, успешно согласовать индекс и реестр, проверить исчезновение ограничения, затем менять колонку и при необходимости вернуть индекс отдельной миграцией с проверкой данных для UNIQUE. Это промежуточное ослабление ограничения требует остановки записей/окна обслуживания; один прогон с удалением индекса из YAML и ретайпом или удалением поля не считается двумя этапами и получает отказ. Legacy-кандидат сначала принимается по манифесту, затем снимается отдельной миграцией; внешний индекс администратор разбирает вручную. Пока такой порядок не соблюдён, публичный `DB.Migrate` возвращает ошибку, а не молча теряет UNIQUE. Автоматическое атомарное снятие и восстановление индекса **внутри** ретайпа можно спроектировать позже, но данный план на него не полагается.

Для SQLite rebuild из-за удаления ссылочной колонки preflight дополнительно сохраняет определения **всех** индексов таблицы, даже не зависящих от удаляемой колонки. В той же транзакции после пересоздания сравнить их физические подписи с исходными и откатить всё при потере/изменении любого внешнего, legacy или управляемого индекса; неподдающееся точной проверке определение означает отказ до DDL. На PostgreSQL проверить сохранность незатронутых индексов после структурного изменения до commit. Так отсутствие индекса на самой удаляемой колонке не даёт rebuild права повредить остальные.

## Честный `migrate --dry-run`

Сейчас `runMigrate` вызывает `openCLIStorage` **до** чтения `--dry-run`: он публикует `_schema_revision` на старой SQLite-базе, а обычные `ConnectSQLite`/`Connect` выполняют записывающую настройку соединения. При `--config-source=database` дополнительно вызывается `configdb.EnsureSchema`. Поэтому существующее обещание «база не изменена» неверно даже без индексных действий. Нельзя заменить вызов на `openCLIStorageReadOnly`: тот всё равно проходит через `openCLIStorageMode`, где `dblock.AcquireSQLiteSharedTarget` создаёт родительский каталог и `<db>.onebase.lock`, а `backup.HasPendingRestoreSQLite` открывает существующую базу в `mode=rw` и может восстановить/checkpoint hot WAL.

Разобрать флаг до открытия базы и сделать отдельный путь preview: те же проверки interrupted restore и совместимости ревизии, но **без публикации ревизии, `Ensure*Schema`, `configdb.EnsureSchema`, `ConnectSQLite` с `journal_mode=WAL` и `Connect` с `DROP/CREATE CAST`**. Для существующей SQLite-базы новый preview-lease канонизирует путь и берёт эксклюзивную lifetime-блокировку через **уже существующий** `<db>.onebase.lock`, открывая его без `O_CREATE` и не вызывая `MkdirAll`. Если lock-файла нет или блокировка недоступна, preview отказывает без создания его за пользователя; обходить общий механизм блокировки нельзя. Для отсутствующей базы/родительского каталога строится план пустой базы только по метаданным в памяти; перед выдачей плана отсутствие цели перепроверяется, появление файла прекращает preview.

Отдельный **не пишущий** restore-gate preview не вызывает `backup.HasPendingRestoreSQLite`. Под удерживаемым lease он проверяет существование и тип основного файла и побочных `<db>-wal`, `<db>-shm`, `<db>-journal` до открытия SQLite. Любой такой побочный файл, в том числе hot WAL с непрочитанным restore marker, даёт безопасный отказ с инструкцией сначала выполнить штатное recovery вне dry-run; preview не запускает checkpoint и не игнорирует содержимое WAL через `immutable=1`. Только при отсутствии побочных файлов открыть основной файл `mode=ro&immutable=1`, не создавая файл/служебную папку, и прочитать marker в `_settings`, ревизию и каталог в одном snapshot. После чтения повторить проверку побочных файлов, идентичности основного файла и его SHA-256; обнаруженная перемена закрывает preview. Если стабильное чтение без записи нельзя доказать, вернуть ошибку, а не неполный план. Для PostgreSQL отдельный opener без setup-DDL читает restore marker, ревизию, проект и каталог в одной `READ ONLY` транзакции; режим `database` загружает только уже существующую `_onebase_config`, при её отсутствии даёт понятную ошибку без её создания. И `PlanMigration`, и новый индексный план используют этот read-only snapshot; любая попытка записи в preview считается ошибкой реализации. Обычный `migrate` и `--adopt-indexes` сохраняют свои write-gates и повторяют preflight после блокировки, не доверяя устаревшему dry-run.

## Изменения в коде и порядок выполнения

- `internal/storage/ddl.go`, `migrate.go`, `code_unique.go`, новый узкий модуль реестра: вычисление желаемого набора, чтение фактических индексов отдельно для SQLite и PostgreSQL, сравнение определения и план действий. Сохранить существующее имя индекса; изменение алгоритма имени вызвало бы массовые коллизии. Валидация `internal/metadata/validate.go` должна ловить два несовместимых объявления с одним физическим именем до DDL. **Уже в первом срезе** убрать прямой вызов `dropStaleUniqueCodeIndexes` из `ensureEntityIndexes`: подбор сгенерированного имени не доказывает владение ни обычным индексом кода/номера, ни индексом «разрез + код/номер». Пока второй срез не ввёл проверяемый DROP по реестру, эти индексы сохраняются; конфликт с желаемой конфигурацией даёт явный отказ до индексного DDL, а не ложное сообщение об успешном снятии UNIQUE.
- `internal/storage/schemaapply.go`, `sqlite_rebuild.go`, `migrate.go`: добавить общий preflight зависимостей структурных изменений **перед всем DDL** и повтор под блокировкой непосредственно перед изменением колонки; убрать безусловный `DROP` из `dropIndexesOnColumn` на пути сущностей. Для SQLite rebuild проверять восстановление всех незатронутых индексов до commit. Публичный `DB.Migrate` соблюдает эти правила без участия CLI.
- Перенести согласование индексов сущностей из пообъектного `ensureEntityIndexes` в фазу после подготовки таблиц и колонок. Сначала собрать и проверить весь набор действий, затем выполнить **все изменения управляемых индексов этого вызова `Migrate` одной транзакцией**. Это защищает от случая, когда новый UNIQUE второй сущности не создаётся, а ограничение первой уже снято. Структурные изменения колонок с зависимыми индексами уже отвергнуты ранним preflight; предыдущие, не связанные с индексами DDL в `Migrate` сохраняют существующую границу атомарности — не объявлять всю миграцию базы транзакционной.
- Сериализовать конкурирующие `DB.Migrate` в рамках базы на весь вызов: PostgreSQL — session-level advisory lock на выделенном соединении с ключом текущей схемы, SQLite — эквивалентная блокировка мигратора. В транзакции каждой структурно изменяемой таблицы взять её DDL/write lock **до повторного чтения каталога** и удержать до commit; индексная фаза берёт свой transaction/write lock и заново проверяет каталог и реестр. Session lock координирует миграторы OneBase, а table/write lock закрывает гонку с внешним DDL в критическом промежутке. `DROP` без совпавшей строки реестра, чужая схема, constraint-backed/partial/expression index, ошибка чтения каталога и конфликт имени завершаются без индексного DDL. Учитывать отложенный `ErrCodeUniqueNotReady`: уже действующий индекс нумератора сохраняется до устранения пустых значений.
- `internal/cli/migrate.go`, `baseresolve.go`, `internal/dblock`, `internal/backup` и отдельные read-only openers в CLI/storage: разобрать `--dry-run` до открытия, добавить не создающий файлов preview-lease и отдельную проверку restore/WAL без recovery, расширить план реструктуризации действиями с индексами и отказами preflight, добавить явное принятие legacy-манифеста. Команда не должна сначала выполнить обычную `Migrate`, а затем обнаружить неверный манифест; индексный preflight и блокировка предшествуют индексным изменениям. Для API `DB.Migrate` без CLI правила владения и отказа те же.
- `DEVELOPER.md`, заметка следующего выпуска и `CHANGELOG.md`: объяснить автоматическое снятие управляемых индексов, процедуру принятия старого индекса, необходимость backup, lock/время простоя и невозможность вернуть прежнюю гарантию уникальности после записи дублей простым откатом бинаря.

## Небольшие PR-срезы и публичные тесты

1. **Реестр, интроспекция и ранняя защита реструктуризации.** Служебная таблица, проверка фактического определения, создание нового индекса и записи реестра в одной транзакции, отказ при одноимённом чужом объекте. В этом же срезе выключить прежний безусловный `dropStaleUniqueCodeIndexes`; до второго среза автоматического удаления индексов сущностей нет. Матричные тесты вызывают публичный `DB.Migrate` на SQLite и PostgreSQL (`dbtest.ForEachDialect`): новое объявление, повторная миграция, чужой индекс с иным определением, отсутствие ложной записи реестра после отказа. На базе, созданной старым DDL без реестра, отдельно снять `numerator.unique` и изменить `scope`: legacy UNIQUE по коду/номеру и по паре «разрез + код/номер» должны остаться физически целыми; конфликт вместо ложного успеха возвращает ошибку о сохранённом legacy-ограничении. Отдельные сценарии `Migrate` с `AllowDestructive=true` меняют `string → bool` и удаляют поле под внешним UNIQUE, зарегистрированным UNIQUE и legacy-индексом; каждый должен получить ошибку **до** изменения типа/колонки, данных, индексов, реестра и карты полей. Проверить и путь SQLite `dropColumnRebuildSQLite` на ссылочном поле: незатронутый внешний индекс сохраняется либо вся транзакция откатывается. Для индексированного `Rename` также требуется явный отказ до DDL.
2. **Атомарное согласование.** Включить удаление только зарегистрированных индексов и общий индексный batch; объединить `numerator.unique` с `indexes:`. Матричные тесты через `DB.Migrate` и `Upsert`: `true → false`, удаление `indexes:`, смена состава/порядка, повторный запуск, сохранение внешнего индекса и продолжающего действовать YAML-индекса. На двух сущностях намеренно создать дубли для нового UNIQUE второй; проверить, что старый UNIQUE первой и реестр остались без изменений. Проверить staged-путь: первая миграция снимает зарегистрированный индекс, вторая меняет колонку, третья создаёт новое определение; попытка объединить первые два шага в один вызов отклоняется без DDL. Отдельно сохранить прежний тест `ErrCodeUniqueNotReady` и перекрытие ручного объявления с нумератором.
3. **Переход старых баз и выпуск.** `--dry-run` печатает ownership/legacy/collision, отказы структурного preflight и манифест; `--adopt-indexes` требует точного fingerprint, принимает только разрешённые кандидаты и атомарно согласует их. Публичные тесты CLI на временной SQLite-базе и матричные тесты `DB.Migrate` для legacy-индекса, созданного прежним DDL: без подтверждения нет DROP и есть явный отказ; с подтверждением снимается только указанный индекс; подмена определения между dry-run и apply отвергается; внешний индекс сохраняется. CLI-тесты сверяют побайтовый снимок основного файла, `<db>-wal`, `<db>-shm`, `<db>-journal`, `<db>.onebase.lock` и существование родительского каталога, а также схему, данные, `_schema_revision` и `_onebase_config` до/после `--dry-run` на старой и пустой SQLite-базе, на отсутствующем файле и в обоих `--config-source=file|database`; там, где database-конфигурации нет, команда отказывает без создания таблицы. Отдельно проверить существующую базу без lock-файла, отсутствующий каталог и hot WAL с marker: preview отказывает без новых файлов и без recovery/checkpoint, а после штатного recovery вне preview работает с неизменным снимком. Для PostgreSQL проверить тот же read-only режим под ролью без DDL и неизменность каталога/ревизии. PostgreSQL-ветка выполняется в CI с `TEST_DATABASE_URL`. Обновить документацию и выпуск.

## Verification, риски, откат и критерии завершения

На копии реальной базы: выполнить `onebase migrate --dry-run`, сверить таблицу/схему/индекс с каталогом и подтвердить, что preview не изменил ревизию/схему, снять backup, явно принять только подтверждённые legacy-индексы, выполнить `onebase migrate`, повторить dry-run и проверить записи с одинаковым ИНН через обычный путь записи. Индексированную колонку менять только отдельными миграциями со снятием индекса заранее и остановленными записями. Для новой базы проверить те же переходы без принятия. Проверки PR: `go test ./internal/storage ./internal/cli` с SQLite, те же пакеты с `TEST_DATABASE_URL` на PostgreSQL, `go build ./...`, `onebase check --project <fixture>`, миграция и повторный dry-run. Фикстура намеренно содержит чужой индекс.

Риск ошибочного `DROP` необратим после появления дублей; поэтому реестр, точная проверка каталога, ранний preflight, транзакция, backup и явное принятие старых объектов обязательны. Конкурирующая запись может изменить данные между preflight и DDL; блокировка до структурных изменений и повторная проверка должны завершиться без ослабления старой гарантии. Staged-изменение индексированной колонки само создаёт окно без прежнего индекса: на это время записи надо остановить; если это невозможно, изменение откладывается. Долгий `CREATE/DROP INDEX` может блокировать рабочие записи — применять в окне обслуживания. При отказе транзакция возвращает прежний набор индексов; после успешного снятия откат к старому бинарю **не** восстанавливает уникальность при дублях: сначала остановить записи, разобрать дубли и выполнить обратную миграцию из backup/проверенной конфигурации.

Готово, когда `Migrate` на обоих диалектах точно отражает YAML для доказанно управляемых индексов без одновременного изменения зависимых колонок, при таком изменении заранее отказывает без потери любых индексов, legacy-переход никогда не удаляет индекс без точного согласия, `--dry-run` действительно не пишет в старую/пустую базу, все перечисленные публичные тесты проходят, а документация и заметка выпуска описывают операционную процедуру.

Оценка: 3–4 дня на реестр, интроспекцию и ранний gate реструктуризации, 2–3 дня на атомарное согласование, 3–4 дня на legacy/CLI с read-only preview, документацию и матрицу; всего ~8–11 дней.
