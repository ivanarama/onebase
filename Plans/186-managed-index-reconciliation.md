# План 186 — безопасное согласование управляемых индексов с конфигурацией

Дата проектирования: 2026-09-27. Статус: 📋 проектирование; этот PR не меняет продуктовый код.
Ведущая заявка: [#1566](https://github.com/ivanarama/onebase/issues/1566).
Выбран вариант 1 доверенного триажа: отдельный план учёта управляемых индексов и перехода старых баз до реализации. [#1439](https://github.com/ivanarama/onebase/issues/1439) описывает существующий `indexes:` и не вводит второй механизм миграции.
Основание инвентаризации: `main` `b752bfd83c4f1935d6bbff10a99d45d14365f0b8`.

## Контекст и текущий контракт

`indexes:` позволяет объявить обычный или уникальный индекс сущности. `ensureEntityIndexes` в `internal/storage/migrate.go` создаёт желаемые индексы через `CREATE [UNIQUE] INDEX IF NOT EXISTS`, затем вызывает `dropStaleUniqueCodeIndexes`. Последняя функция в `internal/storage/code_unique.go` перебирает только индекс кода/номера и пары «разрез + код/номер». Уникальный индекс по произвольному полю остаётся после `unique: true → false` или удаления `indexes:`. На следующей записи БД всё ещё отвергает дубль, хотя YAML уже разрешает его. Это воспроизведено триажем #1566 на SQLite; PostgreSQL в том прогоне не проверялся.

`stableIndexName` (`internal/storage/ddl.go`) строит имя `idx_ob_…` из таблицы, порядка колонок и признака уникальности. Имя и совпадение определения не доказывают происхождение: администратор мог создать такой же индекс вручную, а `IF NOT EXISTS` может скрыть одноимённый индекс с другим определением. Текущая `Migrate` не оборачивает всё изменение схемы одной транзакцией. Уже есть отдельный `migrate --dry-run` для реструктуризации полей, но он не показывает действия с индексами.

## Синтаксис / YAML и наблюдаемая семантика

Формат YAML остаётся прежним:

```yaml
name: Контрагенты
fields:
  - {name: ИНН, type: string}
indexes:
  - {fields: [ИНН], unique: true}
```

Для **доказанно управляемого** индекса повторный `Migrate` точно отражает YAML:

| Изменение конфигурации | После успешной миграции |
|---|---|
| `unique: true → false` | Уникальный индекс снят, обычный создан; повтор ИНН допустим. |
| Удалён `indexes:` или запись в нём | Прежний управляемый индекс снят. |
| Изменены поля, порядок или уникальность | Сначала создано новое определение, затем снято старое. |
| Конфигурация не менялась | Нет DDL и изменений в реестре. |

`numerator.unique` участвует в том же наборе желаемых индексов. Совпадающие объявления `numerator.unique` и `indexes:` дают один индекс; снятие одного объявления не снимает индекс, пока остаётся другое. Внешние индексы, первичные ключи, индексы ограничений, регистров, табличных частей, этапов и FTS не входят в этот механизм. Уникальный индекс по `NULL` сохраняет текущую семантику двух диалектов: несколько незаполненных значений допустимы.

**Инварианты.** Только запись реестра владения, созданная вместе с DDL или явно подтверждённая оператором, разрешает автоматический `DROP`. Перед любым `DROP` фактические таблица, схема, имя, уникальность и *упорядоченные* колонки должны совпасть с сохранённой подписью; иной объект или сбой интроспекции останавливает миграцию. Совпадение имени `idx_ob_…` само по себе не даёт права удалить. Неоднозначный legacy-индекс не замалчивается: миграция возвращает понятный отказ с таблицей и именем до снятия какого-либо ограничения. Отказ при создании нового UNIQUE из-за дублей оставляет прежние индексы и записи реестра; повторный запуск после исправления данных безопасен.

## Хранилище / SQL, владение и legacy-переход

Новая служебная таблица `_managed_entity_indexes` хранит `(table_name, index_name)` как ключ, версию формата, вид индекса, упорядоченные колонки, нормализованную подпись физического определения и источник `created`/`adopted`. Схема PostgreSQL задаётся текущей `search_path` и проверяется через `current_schema()`; SQLite использует свою базу. Реестр создаётся через `EnsureServiceSchema` и публичную `Migrate`, как другие служебные таблицы. Факт наличия записи без соответствующего физического индекса или расхождение подписи — ошибка, требующая явного разбора; реестр не исправляется по догадке.

Для нового индекса: после блокировки и чтения каталога проверить отсутствие одноимённого объекта, создать индекс и запись реестра в **одной транзакции**. При существующем одноимённом объекте без записи реестра сравнить определение и показать, что индекс неуправляемый; несовпадающее определение — отказ, а не успех `IF NOT EXISTS`. Для удаления: перечитать каталог и реестр под той же блокировкой, сверить подпись и желаемый набор, выполнить `DROP INDEX` и удалить запись реестра в той же транзакции. PostgreSQL не использует `CONCURRENTLY` внутри этой транзакции; риск блокировки таблицы и окно обслуживания документируются.

На старой базе реестр отсутствует. Унаследованный `idx_ob_…` нельзя объявлять своим по имени или автоматически записывать в реестр. `migrate --dry-run` показывает текущий и желаемый набор, точное определение, предполагаемое действие и статус владения. Для legacy-кандидата он выдаёт шаблон JSON-манифеста принятия. Кандидат допускается лишь если это обычный индекс сущности без выражения/условия/constraint backing, его колонки принадлежат этой сущности, имя точно равно `stableIndexName` от фактической структуры, а схема и таблица совпадают. Манифест содержит таблицу, имя, фактическое определение и SHA-256 его канонической подписи. Оператор после сверки с каталогом и резервной копии запускает `onebase migrate --adopt-indexes <manifest.json>`; каждый указанный объект перепроверяется непосредственно перед записью. Манифест подтверждает владение только перечисленными объектами, не включает wildcard. После принятия устаревший индекс может быть снят в том же атомарном согласовании. Если прежняя конфигурация уже потеряна, такой манифест позволяет принять видимый в каталоге индекс без восстановления старого YAML. Индекс с другим именем/структурой остаётся внешним; для него используется ручная операция администратора вне автоматического DROP.

Обычная миграция не удаляет legacy-кандидат. Если он конфликтует с желаемой конфигурацией (например, старый UNIQUE после снятия `unique: true`), она останавливается с инструкцией для `--dry-run`/принятия, не сообщает об успешном снятии уникальности и не открывает запись дублей. Доказательство происхождения старого объекта без записи реестра в принципе невозможно; явное принятие — осознанная граница доверия.

## Изменения в коде и порядок выполнения

- `internal/storage/ddl.go`, `migrate.go`, новый узкий модуль реестра: вычисление желаемого набора, чтение фактических индексов отдельно для SQLite и PostgreSQL, сравнение определения и план действий. Сохранить существующее имя индекса; изменение алгоритма имени вызвало бы массовые коллизии. Валидация `internal/metadata/validate.go` должна ловить два несовместимых объявления с одним физическим именем до DDL.
- Перенести согласование индексов сущностей из пообъектного `ensureEntityIndexes` в фазу после подготовки таблиц и колонок. Сначала собрать и проверить весь набор действий, затем выполнить **все изменения управляемых индексов этого вызова `Migrate` одной транзакцией**. Это защищает от случая, когда новый UNIQUE второй сущности не создаётся, а ограничение первой уже снято. Предыдущие, не связанные с индексами DDL в `Migrate` пока сохраняют существующую границу атомарности — не объявлять всю миграцию базы транзакционной.
- Сериализовать конкурирующие миграции в рамках базы до чтения каталога: PostgreSQL — advisory transaction lock с ключом, включающим текущую схему; SQLite — write lock до первого чтения в индексной фазе. `DROP` без совпавшей строки реестра, чужая схема, constraint-backed/partial/expression index, ошибка чтения каталога и конфликт имени завершаются без индексного DDL. Учитывать отложенный `ErrCodeUniqueNotReady`: уже действующий индекс нумератора сохраняется до устранения пустых значений.
- `internal/cli/migrate.go`: расширить существующий `--dry-run` (сейчас он вызывает отдельный `PlanMigration` и показывает только реструктуризацию полей) действиями с индексами, добавить явное принятие legacy-манифеста. Команда не должна сначала выполнить обычную `Migrate`, а затем обнаружить неверный манифест; индексный preflight и блокировка предшествуют индексным изменениям. Для API `DB.Migrate` без CLI правила владения и отказа те же.
- `DEVELOPER.md`, заметка следующего выпуска и `CHANGELOG.md`: объяснить автоматическое снятие управляемых индексов, процедуру принятия старого индекса, необходимость backup, lock/время простоя и невозможность вернуть прежнюю гарантию уникальности после записи дублей простым откатом бинаря.

## Небольшие PR-срезы и публичные тесты

1. **Реестр и интроспекция, без автоматического снятия произвольных индексов.** Служебная таблица, проверка фактического определения, создание нового индекса и записи реестра в одной транзакции, отказ при одноимённом чужом объекте. Матричные тесты вызывают публичный `DB.Migrate` на SQLite и PostgreSQL (`dbtest.ForEachDialect`): новое объявление, повторная миграция, чужой индекс с иным определением, отсутствие ложной записи реестра после отказа. CLI `migrate --dry-run` ничего не меняет.
2. **Атомарное согласование.** Включить удаление только зарегистрированных индексов и общий индексный batch; объединить `numerator.unique` с `indexes:`. Матричные тесты через `DB.Migrate` и `Upsert`: `true → false`, удаление `indexes:`, смена состава/порядка, повторный запуск, сохранение внешнего индекса и продолжающего действовать YAML-индекса. На двух сущностях намеренно создать дубли для нового UNIQUE второй; проверить, что старый UNIQUE первой и реестр остались без изменений. Отдельно сохранить прежний тест `ErrCodeUniqueNotReady` и перекрытие ручного объявления с нумератором.
3. **Переход старых баз и выпуск.** `--dry-run` печатает ownership/legacy/collision и манифест; `--adopt-indexes` требует точного fingerprint, принимает только разрешённые кандидаты и атомарно согласует их. Публичные тесты CLI на временной SQLite-базе и матричные тесты `DB.Migrate` для legacy-индекса, созданного прежним DDL: без подтверждения нет DROP и есть явный отказ; с подтверждением снимается только указанный индекс; подмена определения между dry-run и apply отвергается; внешний индекс сохраняется. PostgreSQL-ветка выполняется в CI с `TEST_DATABASE_URL`. Обновить документацию и выпуск.

## Verification, риски, откат и критерии завершения

На копии реальной базы: выполнить `onebase migrate --dry-run`, сверить таблицу/схему/индекс с каталогом, снять backup, явно принять только подтверждённые legacy-индексы, выполнить `onebase migrate`, повторить dry-run и проверить записи с одинаковым ИНН через обычный путь записи. Для новой базы проверить те же переходы без принятия. Проверки PR: `go test ./internal/storage ./internal/cli` с SQLite, те же пакеты с `TEST_DATABASE_URL` на PostgreSQL, `go build ./...`, `onebase check --project <fixture>`, миграция и повторный dry-run. Фикстура намеренно содержит чужой индекс.

Риск ошибочного `DROP` необратим после появления дублей; поэтому реестр, точная проверка каталога, транзакция, backup и явное принятие старых объектов обязательны. Конкурирующая запись может изменить данные между preflight и DDL; блокировка индексной фазы и проверка создания UNIQUE должны завершиться без ослабления старой гарантии. Долгий `CREATE/DROP INDEX` может блокировать рабочие записи — применять в окне обслуживания. При отказе транзакция возвращает прежний набор индексов; после успешного снятия откат к старому бинарю **не** восстанавливает уникальность при дублях: сначала остановить записи, разобрать дубли и выполнить обратную миграцию из backup/проверенной конфигурации.

Готово, когда `Migrate` на обоих диалектах точно отражает YAML для доказанно управляемых индексов, legacy-переход никогда не удаляет индекс без точного согласия, чужие индексы сохраняются, все перечисленные публичные тесты проходят, а документация и заметка выпуска описывают операционную процедуру.

Оценка: 2–3 дня на реестр и интроспекцию, 2–3 дня на атомарное согласование, 2–3 дня на legacy/CLI/документацию и матрицу; всего ~6–9 дней.
