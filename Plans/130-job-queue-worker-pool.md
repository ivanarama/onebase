# План 130 — Очередь фоновых заданий с пулом исполнителей

Дата проектирования: 2026-08-18. Issue #848 (выделено из #742 после плана 123).

## Контекст

Заявка #848: пульт управления парком баз обходит ~360 узлов обмена круглосуточно,
без окна простоя. Замеры с боевой базы: одновременных обменных сеансов в среднем
~12, p95 = 19, пик 31. Нынешняя модель «одно задание — один прогон» растягивает
такой цикл примерно в 12 раз — для непрерывного обмена это не вариант.

Почему это не доделка планировщика (разбор из #848, сверен с кодом):

- Один прогон на задание — осознанное свойство: `beginJob` → `ErrJobAlreadyRunning`
  (`internal/scheduler/scheduler.go:599`). Оно защищает cron-задания от наложения
  на себя, снимать его нельзя.
- Упирается в бэкенд: 16–32 конкурентных исполнителя требуют PostgreSQL и
  параллельных соединений. На SQLite пул фиксирован одним соединением
  (`storage/sqlite.go`, `SetMaxOpenConns(1)`).
- Значит — новая подсистема: очередь задач, пул исполнителей, аренда и изъятие
  зависшего, ретраи, отмена, поведение при рестарте, наблюдаемость.

## Что мешает в текущем коде (сверено с `0bcddb49`)

1. **Нет очереди как таковой.** Единственная durable-сущность исполнения —
   `_scheduled_runs` (`storage/scheduled.go`), это журнал результатов, а не
   очередь: в нём нет ни «ждёт исполнителя», ни попыток, ни аренды, ни захвата.
2. **Нет параллельного исполнения одного задания.** `RunNow` идёт через тот же
   `beginJob` (`scheduler.go:775`), то есть по требованию задание тоже строго
   однопоточно (это и записано контрактом плана 123).
3. **Исполнение задания не отделено от журнала прогонов.** Единственный путь
   исполнения — `executeJob` (`scheduler.go:831`), который владеет и записью
   прогона, и single-flight. Очереди нужен голый «исполни обработку задания с
   этими параметрами», а собственный журнал у неё свой.
4. **Параметры фиксированы конфигурацией.** `job.Params` берутся из YAML
   (`runProcessor`, `scheduler.go:925`), передать параметры конкретному прогону
   нечем — а очередь без параметров задачи бессмысленна: 360 задач отличаются
   ровно узлом.

## Модель данных

Таблица `_job_queue` (служебная, заводится `EnsureServiceSchema`):

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | UUID | идентификатор задачи, он же возвращается в DSL |
| `job_name` | TEXT | регламентное задание из `scheduled/*.yaml` |
| `params` | TEXT | JSON параметров задачи (перекрывают `params` задания) |
| `key` | TEXT | ключ идемпотентности; пусто = без дедупликации |
| `status` | TEXT | `pending` / `running` / `done` / `dead` / `cancelled` |
| `attempts` / `max_attempts` | INTEGER | счётчик попыток и предел |
| `available_at` | BIGINT | с какого момента задачу можно брать (backoff ретрая) |
| `created_at` / `started_at` / `finished_at` | BIGINT | эпоха, миллисекунды |
| `lease_until` | BIGINT | аренда исполнителя; продлевается heartbeat'ом |
| `worker` | TEXT | кто взял (host/pid) — для разбора инцидента |
| `cancel_requested` | BOOLEAN | запрошена отмена уже исполняемой задачи |
| `error` / `output` | TEXT | последняя ошибка и склейка `Сообщить()` |

Индексы: `(status, available_at)` — очередь на выборку; `(status, lease_until)` —
изъятие зависших; частичный UNIQUE по `key` среди `pending`/`running` — ключ
идемпотентности занят, только пока задача жива.

Время — BIGINT-эпоха в миллисекундах (у приёмки секунды, `storage/intake.go`):
арифметика в Go, никакой зависимости от разбора dialect-таймстампов. Миллисекунды,
а не секунды, потому что длительность задачи — рабочая величина этой подсистемы.

**Терминальных статусов три** (`done`, `dead`, `cancelled`), и отдельного
`error` среди них нет намеренно: упавшая задача возвращается в `pending` с
`available_at` в будущем, а в `dead` уходит, только когда попытки исчерпаны.
Иначе «ошибка» означала бы то «будет повтор», то «конец», и админка не смогла бы
показать разницу.

## Синтаксис

Глобал `ФоновыеЗадания` / `BackgroundJobs` по образцу `РегламентныеЗадания`:

```
// продюсер (обычно cron-задание): разложить работу по очереди
Для Каждого Узел Из Узлы Цикл
    ФоновыеЗадания.Поставить("ОбменСУзлом",
        Новый Структура("Узел", Узел.Код),
        "обмен-" + Узел.Код);          // ключ идемпотентности
КонецЦикла;

// наблюдение
Задача = ФоновыеЗадания.Задача(Ид);
Если Задача <> Неопределено И Задача.Статус = "dead" Тогда … КонецЕсли;
Ожидают = ФоновыеЗадания.Глубина();    // сколько ждёт исполнителя
ФоновыеЗадания.Отменить(Ид);
```

`Поставить(Имя[, Параметры][, Ключ])` → строка-идентификатор. Параметры —
Структура или Соответствие; перекрывают `params` задания поимённо.

`Задача(Ид)` → Структура `Задание, Статус, Ключ, Попытки, МаксПопыток, Создана,
Начало, Конец, ДоступнаС, Ошибка, Вывод` либо `Неопределено`, если очередь такой
задачи не помнит (подрезана ретенцией или чужой id).

`Отменить(Ид)` → Булево: `pending` снимается сразу, `running` получает пометку
отмены (исполнитель увидит её на ближайшем heartbeat и отменит контекст),
терминальная задача возвращает Ложь.

**Ключ идемпотентности**: пока задача с этим ключом жива (`pending`/`running`),
повторный `Поставить` не создаёт дубль, а возвращает идентификатор живой задачи.
Ровно то, что нужно продюсеру, который тикает раз в минуту по 360 узлам и не
должен множить работу, если предыдущий круг ещё не добежал.

## Принятые решения

1. **Единица работы — регламентное задание + параметры задачи.** В очередь
   кладётся имя из `scheduled/*.yaml`, а не имя обработки. Это переиспользует
   уже существующий объект конфигурации со своим таймаутом, правами и валидацией
   в `onebase check`, и укладывается в благословлённый планом 123 паттерн
   «`enabled: false` — задание только по требованию». Обработка как отдельная
   исполняемая единица завела бы вторую сущность мимо метаданных, со своей
   политикой прав (`processors: X: [run]`) и своим таймаутом.
2. **Очередь не пишет в `_scheduled_runs`.** Журнал задачи — сама строка
   `_job_queue`. Причина арифметическая: 360 задач на круг в режиме 24/7 дают
   ~100 тыс. строк в сутки, а ретенция журнала прогонов — 90 дней
   (`RunHistoryMaxAge`), то есть 9 млн строк ради данных, которые уже есть в
   очереди. У очереди своя ретенция (`retention_days`, по умолчанию 14) и свой
   prune терминальных задач.
3. **Захват — `FOR UPDATE SKIP LOCKED` на PostgreSQL**, одним `UPDATE …
   WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING`. На SQLite тот же
   `UPDATE … WHERE id IN (SELECT … LIMIT n) RETURNING` без `SKIP LOCKED`:
   писатель там всё равно один, и захват сериализуется файловой блокировкой.
   `RETURNING` работает на обоих (`storage/seq.go`, `storage/numerator.go`).
4. **SQLite — деградация до одного исполнителя, а не отказ.** Запрошенные
   `workers: 16` превращаются в 1, и это громко сказано: `WARN` при старте и
   плашка в мониторе очереди. Тихая очередь на SQLite была бы худшим из
   вариантов, отказ — сломал бы примеры, демо и локальную разработку, где
   прикладной код обязан оставаться тем же.
5. **Пул включён по умолчанию, малый.** Без блока `queue:` в `app.yaml` — 4
   исполнителя на PostgreSQL, 1 на SQLite. Очередь готова к работе сразу; кому
   нужен режим 24/7 на 16–32, поднимает число в конфигурации.
6. **Аренда вместо «кто взял, тот и владеет навсегда».** Исполнитель держит
   `lease_until` и продлевает его каждые `lease/3`. Задача, чья аренда истекла
   (процесс убит, узел отвалился), возвращается в `pending` следующим кругом
   развёртки — это и есть «изъятие зависшего» из #848. Из-за этого контракт
   доставки — **at-least-once**: обработчик обязан быть идемпотентным, и это
   сказано в справке прямым текстом.
7. **`Поставить` внутри транзакции разрешён** — в отличие от
   `РегламентныеЗадания.Запустить`, где он запрещён (план 123, п. 7). Разница
   принципиальная: `Запустить` требует, чтобы задание УВИДЕЛО данные инициатора
   немедленно, а `Поставить` только записывает строку. Строка ложится в
   транзакцию инициатора и станет видимой исполнителю после коммита — то есть
   откат инициатора снимает и задачу. Это ровно то поведение, которого ждёшь от
   «записал документ и поставил задачу на обмен».
8. **Нативные Go-задания в очередь не кладутся.** `DemoReset`, автобэкап и
   прочие `RegisterGoJob` живут своим циклом с журналом прогонов и статусом
   `accepted`; исполнение их через очередь означало бы второй владелец цикла.
   `Поставить` на такое имя — внятный отказ.
9. **Отмена — кооперативная.** `pending` снимается прямо в базе; `running`
   получает `cancel_requested`, исполнитель видит пометку на heartbeat и
   отменяет контекст задачи. Убить чужой процесс очередь не может и не должна.

## Тесты

Через публичную точку входа (правило #611): DSL-код и пул целиком, а не
приватные функции.

- Матричные (`dbtest.ForEachDialect`, SQLite + PG): постановка и чтение задачи;
  идемпотентность ключа (второй `Поставить` возвращает тот же id); захват
  переводит в `running` и наращивает попытки; ретрай возвращает в `pending` с
  `available_at` в будущем; исчерпание попыток даёт `dead`; развёртка истёкшей
  аренды; prune терминальных.
- **Параллелизм** (главное свойство фичи): пул на N исполнителей на задаче,
  которая держится в исполнении, — одновременно исполняются ровно N, N+1-я ждёт.
  Без этого теста фича не доказана.
- Конкурентный захват на PostgreSQL (`-tags=integration`): два пула на одной
  базе не берут одну задачу дважды — это и есть проверка `SKIP LOCKED`.
- Дренаж: остановка сервера дожидается взятых задач; по таймауту дренажа взятые
  возвращаются в `pending`, а не остаются `running` навсегда.
- Отмена: `pending` → `cancelled` сразу; `running` → отменяется по heartbeat.
- DSL: `Поставить` в открытой транзакции + откат → задачи нет (п. 7);
  `Поставить` на нативное Go-задание → отказ; `Задача(чужой-uuid)` →
  `Неопределено`; `Глубина()` считает ожидающих.
- SQLite-деградация: запрошено 16 → работает 1, предупреждение выдано.

## Verification

1. Конфигурация-пример: задание `ОбменСУзлом` (`enabled: false`, параметр
   `Узел`), продюсер-задание по cron кладёт задачи на N узлов.
2. `onebase run` на PostgreSQL с `queue: {workers: 8}` → в мониторе очереди
   видно 8 задач в работе одновременно, глубина убывает.
3. Убить процесс на середине круга, поднять заново → задачи с истёкшей арендой
   вернулись в `pending` и добежали; дублей по ключу не возникло.

## Риски и ограничения

1. **At-least-once, а не exactly-once.** Изъятие зависшего по аренде и дренаж по
   таймауту означают повтор уже начатой работы. Обработчик обязан быть
   идемпотентным — сказать в справке и в примере.
   Оборотная сторона аренды: после жёсткого падения процесса его задачи ждут
   истечения `lease_sec` и только потом возвращаются в очередь. Раньше их
   отдавать нельзя — на той же базе может работать другой инстанс, которому они
   принадлежат. Значение аренды и есть допустимый простой после падения.
2. **Пул тратит соединения.** N исполнителей — это до N параллельных соединений
   к PostgreSQL плюс веб-нагрузка; при `workers` больше `db.pool_max_conns`
   очередь будет голодать на пуле соединений. Предупреждать при старте.
3. **Долгая транзакция на SQLite стопорит очередь** — то же ограничение
   единственного соединения, что и у планировщика.
4. **Приоритетов нет** — строгий FIFO по `available_at, created_at`. Заводить
   приоритет до живого сценария не стоит: он меняет и индекс, и семантику
   голодания.
5. **Ретенция удаляет историю задач.** `retention_days` по умолчанию 14; кому
   нужен долгий след — пишет его прикладными данными, как и для прогонов.

## Не делаем

- Приоритеты и отдельные именованные очереди (`queue: обмен`) — до живого
  сценария; сейчас одна очередь на базу.
- Распределённого координатора и leader election (этап G плана 76): несколько
  инстансов на одной базе очередь переживает за счёт `SKIP LOCKED` и аренды, но
  продюсера-cron они запустят каждый свой — за дедупликацию отвечает ключ.
- Ожидания завершения задачи в DSL — против однопоточной модели сессии
  (та же причина, что в плане 123).
- Цепочек и зависимостей задач.
