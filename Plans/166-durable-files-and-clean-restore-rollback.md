# План 166 — долговечный каталог файлов и чистый rollback восстановления

Дата проектирования: 2026-09-08.
Статус: 📋 **проектирование**, продуктовый код в этом PR не меняется.
Заявка: [#1268](https://github.com/ivanarama/onebase/issues/1268).
Выбранный вариант: **1** — сначала отдельный технический план; ведущая заявка
#1268 получает первый срез «долговечный каталог файлов + чистый rollback/FK»
(пункты 1 и 5), а YAML, legacy `text→uuid` и строгая ссылочная типизация
выносятся в отдельные связанные заявки и независимые PR.

На момент проектирования открыт продуктовый PR
[#1333](https://github.com/ivanarama/onebase/pull/1333). Он реализует пункты 1
и 3, то есть не выбранную границу. После слияния этого плана PR #1333 нужно
перерезать: оставить и довести решение каталога, удалить из него миграцию
`text→uuid`, добавить чистый rollback/FK и только затем вернуть в REVIEW.

## Контекст

Одна заявка объединила пять отказов, найденных в цепочке Linux/ARM64 →
PostgreSQL → импорт `.obz`:

1. PostgreSQL получает каталог вложений из `os.UserHomeDir()`. У system user
   может быть объявлен `/home/onebase`, которого на диске нет; восстановление
   пытается создать дерево под `/home` и получает `permission denied`.
2. Сообщалось о повреждении отступа верхнеуровневого `llm:` в `app.yaml`, но
   текущий `updateYAMLMapping` повторно разбирает результат до записи и тест
   сохранения проходит. Без исходного файла и версии writer не установлен.
3. `renameSnakeCols` копирует legacy `TEXT` в новую UUID-колонку без явного
   приведения. PostgreSQL отвергает операцию; SQLite не раскрывает расхождение.
4. `normalizeRefID` в пути движений оставляет не-UUID строку как есть. SQLite
   записывает её в ссылочное измерение, а PostgreSQL позже отклоняет такой
   `.obz`. Импорт не знает метаданный тип каждой колонки заранее.
5. `DemoReset` откладывает PostgreSQL `fkCleanup` раньше rollback-defer.
   Из-за LIFO при ошибке сначала закрывается транзакция, потом cleanup пытается
   выполнить `ALTER TABLE` через закрытый `txCtx`; десятки `tx is closed`
   маскируют первичную ошибку.

Это не одна атомарная починка. Пункты затрагивают разные владельцы поведения:
выбор локального хранилища, YAML writer, миграцию схемы, runtime-типизацию и
транзакционный протокол restore. Общий PR нельзя безопасно откатить и нельзя
закрыть одним публичным regression-тестом.

## Объём и маршрутизация

### Ведущая #1268

В #1268 остаются только пункты 1 и 5. Один продуктовый PR должен одновременно
дать службе долговечное место для файлов либо понятный fail-closed отказ и
сохранить исходную ошибку `DemoReset` без повторного обращения к закрытой
транзакции. Только этот PR использует `Fixes #1268`.

До его обновления должны существовать три ведомые заявки со ссылками на #1268
и этот план:

| Ведомая граница | Рабочий заголовок | Исходный пункт | Начальное состояние |
|---|---|---:|---|
| YAML | `Configurator: воспроизвести и устранить повреждение top-level app.yaml` | 2 | `hold`, пока нет точного входного/выходного файла и версии |
| миграция | `PostgreSQL: fail-closed перенос legacy text-ссылок в UUID` | 3 | `hold` до слияния плана; реализацию из #1333 перенести сюда |
| типизация | `RefEntity: не позволять SQLite создавать непереносимые ссылки и валидировать импорт` | 4 | `hold` до отдельной инвентаризации всех write/import paths |

Это организационный precondition, а не разрешение PLAN-этапу создавать новые
issues. Номера подставляются в #1333 и в будущие PR только после фактического
создания заявок. Текст пункта 3 нельзя потерять при перерезании #1333, но и
нельзя оставить в ведущем PR «заодно».

### Вне объёма первого PR

- исправление `updateYAMLMapping` без воспроизводимого артефакта;
- изменение политики допустимых legacy UUID и автоматическое обнуление данных;
- общий coercion framework для метаданных и import JSONL;
- перенос уже существующих файлов между каталогами;
- новый backend вложений или изменение режимов `disk` / `db` / `s3`;
- неблокирующий хвост ревью #1333 о том, должен ли PostgreSQL connect требовать
  каталог в режиме, который локальные файлы не использует. Его следует
  маршрутизировать отдельной заявкой, если ранний fail-closed создаёт реальную
  несовместимость; он не возвращает временный fallback.

## Наблюдаемая семантика и инварианты

### Каталог файлов PostgreSQL

1. `os.TempDir()` никогда не становится неявным местом постоянных вложений или
   блобов. Очистка temp не должна оставлять в БД метаданные без содержимого.
2. Явный `ONEBASE_FILES_DIR` имеет приоритет. Значение — абсолютный путь к
   отдельному постоянному каталогу этой установки; относительный путь, файл
   вместо каталога и недоступный предок дают понятную ошибку до первой записи.
3. Без override существующий реальный home сохраняет прежнюю раскладку
   `<home>/.onebase/files/<database>`; обновление не переносит и не дублирует
   существующие данные.
4. Объявленный, но отсутствующий home не считается пригодным. Вместо попытки
   `mkdir /home/...` и вместо temp-fallback запуск завершается fail closed с
   указанием `ONEBASE_FILES_DIR`.
5. Значение override является точным корнем `FilesDir`, без скрытого добавления
   имени базы. Так оператор может заранее выдать права и смонтировать volume;
   документация обязана предупредить, что один путь нельзя делить между
   независимыми базами.
6. `SetFilesDir` остаётся явным process-level override для launcher/recovery и
   тестов. Новый env-default не должен перекрывать более поздний вызов.
7. `defaultFilesDirForSQLite` и временные каталоги DSL не меняются: дефект
   подтверждён на PostgreSQL-сервисе, а расширять миграцию путей на SQLite без
   отдельного решения опасно.

Минимальное решение уже очерчено в #1333: общий resolver для `ConnectWithPool`
и `ConnectWithSchema`, абсолютный `ONEBASE_FILES_DIR`, проверка реального home и
отказ вместо temp. При перерезании нужно сохранить этот контракт и тесты, но
не тащить `migrate.go`/`migrate_snake_pg_test.go` в ведущий PR.

### Rollback и FK

Для PostgreSQL удаление и восстановление FK выполняются внутри той же
транзакции, что импорт. Отсюда два взаимоисключающих пути:

- **успех:** `DisableFKForImport(txCtx)` → импорт → явный `fkCleanup()` на ещё
  открытом `txCtx` → валидация FK → commit;
- **ошибка до commit:** rollback открытой транзакции сам возвращает DDL и FK;
  после rollback `fkCleanup()` больше не вызывается.

Для SQLite `PRAGMA foreign_keys` нетранзакционна, поэтому его cleanup остаётся
внешним и обязан выполниться после успеха и после rollback. Один общий флаг
`fkDisabled` сейчас смешивает эти два контракта; их следует разделить явным
владением cleanup либо маленьким локальным lifecycle-объектом в `DemoReset`.

Инварианты:

1. cleanup PostgreSQL вызывается не более одного раза и только пока `txOpen`.
2. При раннем возврате первичной остаётся ошибка импорта/миграции; rollback
   может быть присоединён через `errors.Join`, но `tx is closed` и повторные
   `restore FK …` отсутствуют.
3. Частичный сбой внутри `DisableFKForImport` остаётся fail closed: функция
   пытается восстановить уже снятые constraints в открытой транзакции, затем
   весь tx откатывается.
4. Ошибка в явной повторной установке/валидации FK на успешном пути отменяет
   весь import и возвращается как `restore and validate FK constraints`.
5. После любого определённого rollback соединение пригодно для нового запроса,
   все исходные FK существуют с прежним `convalidated`, а новая файловая
   snapshot не опубликована.
6. Неопределённый commit outcome продолжает разрешаться через
   `ResolveCommitError`; новый cleanup не выполняет DDL после этой границы.

## Совместимость и миграция

- Установка с существующим home продолжает видеть прежний каталог; копирования
  данных и SQL-миграции нет.
- Установка без home после обновления перестаёт падать поздно внутри restore и
  падает раньше с actionable error, пока оператор не задаст постоянный root.
  Это намеренная fail-closed несовместимость вместо риска потери файлов.
- Если оператор задаёт `ONEBASE_FILES_DIR`, он сначала переносит существующее
  дерево в остановленном сервисе, сохраняет владельца и режимы, затем меняет
  environment и проверяет чтение старого вложения. OneBase не объединяет два
  дерева автоматически.
- Backup/restore format, `_attachments.loc`, `_blobs.loc`, PostgreSQL schema и
  содержимое `.obz` не меняются.
- Изменение порядка cleanup не меняет успешный restore: FK по-прежнему
  проверяются до commit. Меняется только ошибочный путь — исчезают вторичные
  запросы в уже закрытую транзакцию.
- Текущий PR #1333 нельзя force-merge до plan handoff. Его следует обновить
  обычным коммитом/процедурой FIX так, чтобы история ревью показала удаление
  пункта 3 и добавление пункта 5; новая HEAD проходит REVIEW заново.

### Срез B — ведомая миграция `text→uuid` (~1 день)

Перенести `migrate.go` и `migrate_snake_pg_test.go` из #1333 в отдельный PR.
Политика остаётся fail closed: валидный UUID (с допустимым ASCII-пробелом)
переносится, пустое/пробельное/повреждённое значение обрывает миграцию до
`DROP COLUMN`; исходная колонка и значение сохраняются. Автоматического NULL
или генерации UUID нет.

Публичная приёмка идёт через `MigrateRegisters` на PostgreSQL и проверяет
данные/наличие обеих колонок после ошибки, а не только SQL helper.

### Срез C — ведомая строгая `RefEntity`-типизация (~3–5 дней после аудита)

Сначала перечислить все публичные write paths движений и import boundary.
Каноническое правило: ссылочное поле принимает UUID, пустую ссылку по явно
заданному контракту или типизированный `Ref`; произвольная строка отклоняется
одинаково до SQL на SQLite и PostgreSQL. Import выполняет ту же проверку до
INSERT и сообщает таблицу, строку и колонку, не санитизируя данные молча.

Публичная приёмка: один DSL-модуль через настоящий `WriteMovements` получает
одинаковый отказ на обоих диалектах; валидный SQLite `.obz` импортируется в PG,
а архив с не-UUID ссылкой отклоняется до частичной публикации snapshot.

### Срез D — ведомая YAML-регрессия (после получения артефакта, ~1–2 дня)

Сначала приложить точные bytes входного и записанного `app.yaml`, версию
бинарника и действие UI. Если текущий `updateYAMLMapping` воспроизводит дефект,
чинить найденный writer и сохранять comments/style настолько, насколько это

тестом. Проверка только «indent верхнего уровня равен нулю» недостаточна:
результат обязан повторно парситься в `project.AppConfig` и сохранять соседние
ключи.

## Тесты и verification

### Автоматические проверки среза A

1. `storage.Connect` с синтаксически валидным DSN, отсутствующим HOME и пустым
   `ONEBASE_FILES_DIR` возвращает ошибку resolver до сетевого dial и содержит
   имя переменной. Это публичная regression-точка; прямые тесты helper допустимы
   только как дополнительные таблицы абсолютного/относительного пути.
2. С существующим home resolver сохраняет старый
   `<home>/.onebase/files/<database>`. Явный абсолютный override побеждает home,
   очищается через `filepath.Clean` и не попадает под `os.TempDir()`.
3. Integration-тест `DemoReset` создаёт настоящий universal archive, заменяет
   одну data JSONL строку значением, которое PostgreSQL отвергнет после
   `DisableFKForImport`, и пересчитывает manifest, чтобы ошибка случилась именно
   внутри транзакционного импорта, а не в zip/manifest validation.
4. Тест вызывает публичный `DemoReset`, проверяет первичный контекст ошибки и
   отсутствие `tx is closed`/вторичной серии `restore FK`; затем через catalog
   убеждается, что исходный FK существует и валиден, и выполняет обычный запрос
   тем же `storage.DB`.
5. В каталоге назначения заранее лежит sentinel-вложение. После неуспешного
   reset оно остаётся прежним, staged snapshot/intent убраны.
6. SQLite `DemoReset`-тест подтверждает, что `PRAGMA foreign_keys` после ошибки
   снова `ON`: разделение PG lifecycle не должно сломать нетранзакционный путь.

1. Создать system user без home и постоянный каталог/volume, принадлежащий ему.
2. Без `ONEBASE_FILES_DIR` убедиться в раннем понятном отказе и отсутствии

3. Задать абсолютный `ONEBASE_FILES_DIR`, выполнить загрузку вложения,

5. После отказа выполнить запрос к базе и повторный reset валидным архивом.

## Риски и откат

- **Ошибочный temp fallback.** Даже «только для demo» теряет данные после
  очистки. Предохранитель — отрицательный тест и запрет в документации.
- **Один override на несколько баз.** Файлы смешаются по UUID/owner. Путь
  трактуется как точный root, а deployment обязан выдавать уникальный volume
  на базу/службу.
- **Слишком ранний fail-closed.** S3-инсталляция без локальных файлов может
  перестать подключаться. Это уже выделенный хвост ревью #1333: не ослаблять
  fallback до temp, а при подтверждении переносить проверку к первой операции,
  действительно требующей disk root.
- **Cleanup не вызван на PG success.** Constraints останутся снятыми в
  коммите. Предохранитель — catalog assertion после успешного и ошибочного
  reset и прежняя валидация до commit.
- **SQLite cleanup потерян при разделении.** `foreign_keys=OFF` переживёт
  операцию. Предохранитель — отдельный SQLite error-path test.
- **Первичная ошибка снова замаскирована.** Порядок `errors.Join` и количество
  cleanup проверяются на публичном `DemoReset`, а не на приватном defer helper.
- **Потеря готовой работы #1333.** Пункт 3 переносится в ведомую ветку только
  после создания её issue; до этого исходный commit остаётся доступен по SHA
  `7e4716efc8ffc746ec10dd6f76d0ad35e66f0590`.

Откат среза A не требует миграции БД: вернуть предыдущий бинарник, убрать env
override только после возврата файлов в старый root и проверить чтение
вложения. Изменение cleanup откатывается одним кодовым PR; формат backup и
данные не менялись. Если новый код не успел записать файлов, достаточно вернуть
старую конфигурацию пути.

  теряются при закрытии ведущей issue;
- #1333 больше не содержит `migrate.go` и пункта 3, явно реализует вариант 1 и
  содержит regression для пункта 5;
- отсутствующий home никогда не выбирает temp; существующий home совместим, а
  абсолютный persistent override документирован и проверен;
- ошибочный PostgreSQL `DemoReset` возвращает первичную ошибку без запросов в
  закрытый tx, сохраняет FK и старую файловую snapshot;
- успешный restore по-прежнему валидирует FK до commit, SQLite всегда возвращает
  `PRAGMA foreign_keys=ON`;
- каждый ведомый PR имеет собственную issue, публичную приёмку и отдельный
  откат; только срез A закрывает #1268;
- `go test ./...`, обязательная PostgreSQL-матрица и CI проходят на свежем
  `main`; продуктовый код не входит в plan-PR.
