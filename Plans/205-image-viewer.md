## Синтаксис / YAML и пользовательская семантика

Новый параметр `zoom:` не нужен. Заполненное поле существующего типа `image`
получает действие просмотра по умолчанию, в том числе в read-only форме.
Видимость и права поля остаются входным ограничением.

```yaml
name: Снимок
fields:
  - {name: Дата, type: date}
  - {name: Фото1, title: "Камера 1, 1-е взвешивание", type: image}
  - {name: Фото2, title: "Камера 2, 1-е взвешивание", type: image}
detail_panel:
  title: Дата
  tabs:
    - {name: "Фото 1", fields: [Фото1]}
    - {name: "Фото 2", fields: [Фото2]}
```

1. Клик по непустому превью/фону карточки открывает диалог; Enter и Space на
   кнопке просмотра делают то же. Курсор — `zoom-in`. Кнопки просмотра внутри
   формы имеют `type="button"`; действие не отправляет форму и не выбирает строку.
2. Заголовок — локализованная подпись именно текущего поля, а не UUID или подпись
   записи. Для managed-элемента используется действующая подпись этого элемента
   с fallback к `Field.DisplayName`. Подпись вставляется текстом, без HTML.
3. Начальный масштаб `s = min(1, W/w, H/h)`, где `w/h` — naturalWidth/Height,
   `W/H` — свободная область после заголовка и панели действий. Маленькую картинку
   не растягиваем; крупная целиком видна без обрезания. При resize пересчитываем
   режим «Вписать»; ручной масштаб сохраняем, ограничивая положение изображения.
4. Колесо над областью картинки и кнопки «+»/«−» меняют масштаб с шагом 1,25,
   от вписанного до 8× исходного. Точка под курсором остаётся на месте, насколько
   позволяют границы. Ctrl/Meta+колесо остаётся браузеру. Кнопки «100 %» и
   «Вписать» дают предсказуемое возвращение к исходнику и общему виду.
5. При увеличении доступны полосы прокрутки и перетаскивание pointer-событиями;
   touch позволяет перемещать увеличенное изображение, кнопки дают доступный зум.
   Стрелки предназначены для смены фотографии; прокрутка доступна полосами,
   pointer и PageUp/PageDown внутри области просмотра.
6. Esc, «×» и осознанный клик по фону вне картинки закрывают только просмотрщик.
   Для фона проверяем, что pointerdown и pointerup произошли на фоне: окончание
   drag за пределами картинки не закрывает окно. Кнопки/ссылки заголовка фоном
   не считаются. Формовые диалоги сохраняют собственный контракт закрытия.
7. `←`/`→` и кнопки переключают заполненные картинки этой записи в установленном
   порядке; на концах кнопки выключены, циклического перехода нет. После смены
   картинки масштаб снова «Вписать». При одной картинке переключение выключено.
8. Есть «Открыть в новой вкладке» и «Скачать». Новая вкладка использует обычный
   `/ui/_image/<uuid>` с `target="_blank" rel="noopener noreferrer"`. Скачивание
   идёт через тот же защищённый route с явным `?download=1`, без копирования в
   публичное хранилище и без Blob/ObjectURL на клиенте.
9. Пока изображение загружается, виден статус. Сбой сети, 403/404 либо ошибка
   декодирования показывают доступную ошибку; закрытие и смена фото работают.
   Старый onload/onerror не может заменить новое изображение после переключения.

### Состав галереи и идентичность

Галерея ограничена **одной записью и текущим представлением**. Она включает
поля-картинки, разрешённые и включённые в это представление, включая его
неактивные закладки. Поля, не включённые в managed-форму, состав панели или
карточки, автоматически не добавляются. Стрелки не переходят к другой записи.

- Автоформа: порядок видимых полей формы; managed-форма: порядок элементов и
  страниц формы. Повтор одного поля на нескольких элементах дедуплицируется по
  имени поля, начальная подпись берётся у нажатого элемента.
- Панель: порядок закладок, затем fields внутри каждой закладки. Используется
  весь текущий авторизованный payload, а не только `img` активной закладки.
- Карточка: сначала `tile.ImageFields`, затем image-поля `tile.Fields`, без
  повторов имени поля. Нельзя собирать галерею обходом всей `.tile-grid`.
- Разные поля с одинаковым UUID остаются разными позициями: подпись важна для
  оператора. Идентичность — контекст записи + имя поля, а не подпись или URL.
- NULL/пустые, скрытые, замаскированные значения и невалидные UUID не становятся
  триггерами. Галерея не восстанавливает UUID из скрытых backing-полей.
  Проверка UUID — дополнение к авторизованной проекции, а не замена маскированию.

Не расширяем DOM перечнем всех картинок базы. Карточка сериализует только уже
показанные в ней разрешённые поля; панель сохраняет ленивую загрузку. При смене
активной записи/замене live-контейнера её открытый просмотрщик закрывается.
Загрузка/очистка фото в форме актуализирует данные при следующем открытии.
Если текущее фото изменено программным патчем при открытом просмотрщике, окно
закрывается; старый UUID не остаётся доступен из его кнопок. Просмотр не меняет
hidden input, dirty-state или серверный form instance/revision.

### Доступность и область модального окна

Предлагается один контроллер на документ и native `<dialog>.showModal()` с
подписанными элементами, `aria-labelledby`, статусом `aria-live`, фокусом на
кнопке закрытия и возвратом фокуса к исходному триггеру. При удалённом триггере
фокус возвращается к живому контейнеру формы/списка. Учитываем reduced motion.

Окно занимает доступный viewport **документа-владельца**: в standalone/shell это
его окно, в popup iframe — область iframe. Подъём через cross-frame postMessage
не входит в этот план; iframe не должен закрываться, терять фокус или отправлять
данные родителю из-за просмотра. Это явная граница первой реализации.

Native top layer не решает конкуренцию глобальных listeners. Общий проверяемый
гейт `obHasBlockingModal` должен видеть просмотрщик, а managed capture-Esc,
автоформа и родительский capture-listener iframe обязаны отдать ему первый Esc.
Второй Esc после закрытия возвращается обычному поведению. Навигационные и
табличные shortcuts не срабатывают под диалогом. Открытие запрещено поверх
активного подтверждения закрытия; при просмотре из формы внутри picker закрытие
просмотрщика оставляет picker и введённые данные на месте.

## Хранилище / SQL, совместимость и миграция

Схема БД, тип `image`, UUID, blob owner и существующие данные не меняются.
Нет DDL, миграции, новых зависимостей или нового сервиса выдачи изображений.
PostgreSQL и SQLite используют текущий blob backend. Исходные файлы не
пережимаются; предварительная загрузка всех фотографий не нужна.

Для `GET /ui/_image/<uuid>?download=1` расширяем `imageServe`: **после той же
проверки доступа** выставляем `Content-Disposition: attachment` с безопасным
именем `image-<uuid>.<ext>`. Расширение берём из фиксированной таблицы MIME;
для неизвестного типа — `.bin`. Не принимаем имя файла или MIME из query.
Без точного `download=1` сохраняется inline-поведение. `nosniff`, sandbox-CSP,
Content-Type и существующий private cache остаются; проверяем разделение inline
и attachment по полному URL. Байты идут тем же потоком, без буферизации всего
файла в памяти и без второго обходного auth-handler.

Отсутствие JS оставляет корректное хранение UUID и загрузку формы; превью можно
оформить безопасной ссылкой на исходник с JS-перехватом. Включение действия не
делает read-only форму редактируемой. Новые подписи добавляются в `en.json`
по правилам i18n; существующие локали обновляются только по необходимости.
Не менять generated assets вручную. Изменение встроенного JS получает новый
ETag штатным механизмом; проверить отсутствие устаревшего JS после обновления.

## Последовательность PR-срезов и публичные тесты

### Срез 1 — исходник, масштаб и формы (2–3 дня)

Общий диалог, cleanup, ошибки, фокус, Esc, зум/панорамирование, новая вкладка,
streaming download и галерея авто/managed-форм. Поддержать загрузку, очистку,
read-only и popup; интеграцию capture-Esc сделать в этом же срезе.

Публичная приёмка: через HTTP загрузить две картинки, сохранить форму и открыть
её в браузере; click/Enter/Space открывают нужное фото, стрелки меняют подпись,
зум изменяет фактический размер, scroll/pointer позволяют увидеть дальний угол.
Проверить маленький и большой PNG, portrait, GIF/JPEG, ошибку загрузки, быстрые
переходы до load, resize и повторное открытие. Esc в dirty managed-форме и iframe
закрывает только viewer, значения и родительский picker остаются. Upload/clear
через UI дают свежую галерею и не отправляют форму. Read-only пользователь может
просматривать разрешённое фото, но не загружать/очищать.

Через настоящий router проверить inline и download ответы: те же байты,
403/404 для запрещённого/отсутствующего UUID, неизменные защитные заголовки,
безопасное имя. Playwright `download` проверяет сохранённый файл; новая вкладка
имеет правильный URL и отсутствующий opener. Запреты тестируются с заведёнными
пользователями, ролью до запуска сервера и RLS, а не в базе без auth.

### Срез 2 — панель деталей и разные закладки (1–1,5 дня)

Стабильный field-key, адаптер всего разрешённого payload и lifecycle lazy/live
панели. Старые клиенты игнорируют новое JSON-поле. Не превращать панель обратно
в безусловную загрузку всех записей списка.

Публичная приёмка: список документа/справочника с двумя закладками, по картинке
первой открыть viewer и стрелкой перейти ко второй без предварительного клика
по второй закладке. Пустое и hide/mask-поле не попадают в галерею; одинаковые
подписи и повтор одного поля на страницах не ломают идентичность. Смена строки,
свежий lazy-ответ или live-замена не возвращают старую картинку. Проверить общий
путь `GET /ui/<kind>/<entity>/<id>/detail-panel`: запрещённая строка/read-hook
не раскрывает UUID. Проверить число запросов при выключенной панели.

### Срез 3 — карточки и итоговая браузерная матрица (1–1,5 дня)

Кнопка поверх `.tile-img`, адаптер image-полей карточки, клавиатурная изоляция
и окончательная документация пользовательской возможности.

Публичная приёмка: две записи с разными фото, одна с двумя image-полями.
Клик/Enter/Space по картинке оставляет URL, выбор строки и dirty-state прежними;
стрелки не показывают фото соседней записи. Ссылка «Открыть» карточки и обычная
навигация строк продолжают работать. Пустой фон не создаёт действия. Пройти
все поверхности в Chromium; на Windows/WebView2 отдельно проверить native
диалог, клавиатуру, download и новую вкладку, на узком touch-viewport — кнопки
масштаба и перемещение. После этого добавить `docs/features.md` для новой
пользовательской возможности и согласованную справку формата.

Срезы выпускаются последовательно; после merge предыдущего следующий получает
свежий main и повторную проверку пересечения JS/templates. Это план реализации,
не предположение о уже существующем автоматическом handoff нескольких PR одной
issue. Промежуточные PR ссылаются на #1744; закрывающее ключевое слово оставляется
за последним срезом, выполнившим весь контракт.

## Тесты и Verification

Go-регрессии дополняют существующие image-serve/auth/security и detail-panel
тесты, но вызывают router/HTTP, а не частные методы нового viewer. Проверка
строк шаблона может быть вспомогательной, не единственным доказательством.
Не придумывать общую SQL-матрицу для JS; доступ к blob проверить на обоих
действующих backend-путях там, где уже есть fixture SQLite/PostgreSQL.

```sh
go test ./internal/ui
go run ./tools/plannum
go build ./...
# Из e2e/, с установленными штатными зависимостями:
npm test -- tests/image-viewer.spec.js
npm test -- tests/live-list.spec.js tests/choice-filter.spec.js tests/attachments.spec.js
```

Фикстура браузерного теста: отдельная тестовая конфигурация/копия с двумя image
полями и managed-формой, две записи, PNG 1600×1200 и маленький 64×48, admin,
read-only пользователь и пользователь с запрещённой строкой/полем. Разворачивать
через штатные migrate/user/role/run и HTTP upload/save. Существующий
`scripts/e2e-server.sh` допускает `OB_PROJECT`, запускает аутентификацию и
`e2e/playwright.config.js` работает с одним сервером последовательно.
Если нужны разные layouts/роли, использовать отдельные прогоны конфигураций;
не менять общую базу параллельно. Не внедрять viewer DOM через `page.evaluate`.

Ручной end-to-end: конфигурация из раздела YAML → migrate → создать пользователя
и роль → run → создать «Снимок» с двумя фото → сохранить → открыть из формы,
панели и карточки → приблизить штрих/номер → переключить фото → скачать и
сравнить байты → закрыть Esc/«×»/фоном → убедиться, что исходная форма/строка
не изменилась. Повторить после upload/clear, с правами только чтения и с отказом
доступа. Для динамического UI использовать штатные действия обновления.

## Риски, откат и критерии завершения

| Риск | Проверка / ограничение |
|---|---|
| Esc закрывает dirty-форму или родительский iframe | Capture-приоритет viewer проверяется реальным браузером уже в срезе 1 |
| Стрелки раскрывают скрытое фото либо чужую запись | Только авторизованная проекция текущего представления; отрицательные HTTP/browser сценарии |
| Drag заканчивается закрытием | Закрытие фона требует down+up на фоне, drag активен отдельно |
| Stale load/ответ/DOM меняет открытое фото | Поколение открытия, проверка owner и cleanup listeners/pointer capture/scroll lock |
| Очень большое изображение расходует память | Загружается только текущее фото, нет eager preload, ошибка декодирования остаётся закрываемой; предел 8× не уменьшает цену самого bitmap |
| Download взаимодействует с sandbox/inline/cache | Attachment-проверка в Chromium и WebView2; не ослаблять sandbox ради скачивания |
| Платформы различаются в native dialog | Штатный Chromium CI плюс Windows/WebView2 и touch приёмка; fallback не добавляется без воспроизводимого дефекта |

Откат каждого среза — revert его UI/HTTP-изменений с обычными проверками; нет
данных для обратной миграции. Откат среза 1 после последующих требует сначала
откатить зависимые адаптеры. Inline-выдача UUID и исходные картинки продолжают
работать. Перед релизом зафиксировать результаты platform-приёмки; неоправданное
ослабление auth/CSP или raw gallery-проекция — блокер ревью.

Готово, когда все три поверхности выполняют общий контракт, пройдены положительные
и отрицательные браузерные сценарии, download совпадает по байтам, несохранённые
данные/родительские окна сохраняются, скрытые UUID не появляются в DOM/payload,
нет продуктовых миграций и каждый срез прошёл обычные REVIEW/CI/человеческий ship.

## Эстимейт

Срез 1: 2–3 дня; срез 2: 1–1,5; срез 3: 1–1,5; общая Windows/WebView2/touch
приёмка и доработка: 1–1,5. **Всего 5–7,5 рабочих дней**. Оценка не обещает
cross-frame fullscreen, pinch-жесты, редактор изображений, просмотр вложений
или картинок из richtext: у них другая модель доступа и отдельный контракт.
