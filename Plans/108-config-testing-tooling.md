# Этап 108 — Тест-инструментарий уровня конфигурации

## Контекст

У OneBase есть отличные примитивы для запуска кода офлайн (`procrun`, `eval`) и
статической проверки (`check`), но **нет встроенного способа писать и гонять
тесты уровня конфигурации** — того, что в мире 1С закрывают внешними Vanessa /
xUnitFor1C. Для маленьких проектов достаточно самодельной обработки `Тесты` +
bash-обёртки. Для больших проектов и особенно на PostgreSQL этого мало.

Что уже работает без платформы (≈80%):
- юнит-тесты чистых функций — обработка с ассертами + `procrun` (ненулевой код
  возврата при провале);
- точечные проверки — `eval '<выражение>' --json`;
- статика — `check` (синтаксис, схема, **тексты запросов**).

Что userland сделать **не может** (и ради чего нужна поддержка платформы):

1. **Изоляция данных между тестами.** На SQLite обходятся копированием файла БД;
   на PostgreSQL так нельзя. Нужен откат транзакции/savepoint вокруг каждого
   теста либо эфемерная схема/БД на прогон. И то, и другое управляет
   соединением — это может дать только раннер платформы.
2. **Швы для внешних эффектов.** `Письмо.Отправить()`, `ТгВызов`,
   `ВыполнитьКоманду`, ИИ-вызовы бьют наружу — код рассылок/интеграций
   фактически не тестируем без реального SMTP/сети. У `eval` уже есть
   `RestrictedProfile` (сеть/ФС/ОС запрещены); нужен шаг дальше — тест-профиль
   с **моками-рекордерами**, чтобы ассертить «письмо ушло бы на X с вложением Y».
3. **Управление временем.** Тесты «за N дней до окончания», «не слали 180 дней»
   зависят от `ТекущаяДата()`/`ТекущаяДатаВремя()` — платформенных функций.
   Заморозить/подменить часы может только платформа.
4. **Дискавери тестов + машиночитаемый вывод для CI** (JUnit XML / TAP), счётчики,
   единые встроенные ассерты, чтобы каждый проект не переизобретал ассерт-модуль.

Мотивация из практики: даже тривиальные тесты в реальной конфигурации напоролись
на баги платформы, которые `check` не ловит или ловит поздно — issues #477
(резолвер `unknown function` при локальном вызове с межмодульным вызовом в
аргументе), #478 (`ambiguous column name: id`), #479 (`= NULL` вместо `IS NULL`).
Благословлённый путь тестов заодно закалит эти углы и даст регресс-покрытие.

**Не-цели:** BDD/Gherkin и UI-сценарии в стиле Vanessa. CLI-first дизайн
(офлайн-БД + `procrun`/`eval` + ненулевой код) делает CI тривиальным; держимся
xUnit-уровня (код), не UI-прогонов.

## Синтаксис / YAML

### Дискавери тестов

Тест — это обработка (`processor`) с признаком теста либо файл по конвенции.
Предлагается конвенция каталога и/или флага:

- любой процессор из `tests/` c процедурой `Выполнить`, **или**
- процессор с `kind: test` в YAML.

`tests/ТестыТелефонов.yaml`:
```yaml
name: ТестыТелефонов
kind: test          # помечает как тест — попадает в `onebase test`
```

Внутри — обычный DSL плюс встроенные ассерты (см. ниже).

### CLI

```
onebase test --project . --sqlite :memory:        # все тесты, свежая БД
onebase test --project . --run ТестыТелефонов      # фильтр по имени/маске
onebase test --project . --db "$PG_DSN" --isolation transaction
onebase test --project . --format junit --out report.xml   # для CI
```

Флаги:
- `--isolation transaction|schema|none` — как изолировать данные между тестами
  (по умолчанию `transaction`);
- `--format pretty|tap|junit` (по умолчанию `pretty`, ненулевой код при провале);
- `--run <маска>`, `--out <файл>`.

### Встроенные ассерты

Модуль `Утверждать` (глобально доступен в тестовом профиле):
```bsl
Утверждать.Равно(Факт, Ожидание, Описание);
Утверждать.Истина(Условие, Описание);
Утверждать.Ложь(Условие, Описание);
Утверждать.Заполнено(Значение, Описание);
Утверждать.ВызвалоИсключение("МодульИлиФункция", Описание);
```
Провал ассерта помечает текущий тест как failed и продолжает (soft-assert) либо
прерывает — по флагу.

### Моки внешних эффектов (тест-профиль)

В тестовом профиле сеть/ФС/ОС/почта/ИИ по умолчанию замоканы рекордерами:
```bsl
Процедура Выполнить()
  Мок.Email.Очистить();
  ПровестиРассылку();                       // код, дергающий Письмо.Отправить()
  Утверждать.Равно(Мок.Email.Количество(), 3, "3 письма");
  Утверждать.Равно(Мок.Email[0].Кому, "a@b.ru", "адрес");
КонецПроцедуры
```
Аналогично `Мок.Http`, `Мок.ОС`, `Мок.ИИ`.

### Управление временем

```bsl
Часы.Установить(Дата(2026, 7, 29));   // ТекущаяДата()/ТекущаяДатаВремя() замрут
ЗапуститьКонтрольОкончаний();
Часы.Сбросить();
```

## Хранилище / SQL

Изоляция данных:

- **`transaction` (по умолчанию):** раннер открывает транзакцию (или `SAVEPOINT`)
  перед каждым тестом и откатывает после. Требует, чтобы весь ввод-вывод теста шёл
  через одно соединение раннера. Работает и на SQLite, и на PostgreSQL.
- **`schema` (PostgreSQL):** на прогон создаётся временная схема (или БД из
  `TEMPLATE`), в конце — `DROP`. Полезно для тестов, которые сами управляют
  транзакциями (проведение, вложенные `SAVEPOINT`).
- **`none`:** без изоляции (для чистых юнит-тестов, где нет записи).

Миграции применяются один раз к тестовой БД перед прогоном.

## Изменения в коде

- **`internal/cli/test.go`** — новая команда `test`: дискавери (`tests/` +
  `kind: test`), прогон, форматтеры вывода. Рядом с `internal/cli/eval.go` и
  логикой `procrun`.
- **`internal/dsl/interpreter/env.go`** — тестовый профиль поверх
  `RestrictedProfile`: инъекция `Утверждать`, `Мок.*`, `Часы.*`; перехват
  внешних вызовов на рекордеры. Тесты профиля — рядом с `sandbox_test.go`.
- **Слой хранилища/сервер (`internal/entityservice`, `internal/launcher/server.go`)**
  — точка, где раннер оборачивает каждый тест в транзакцию/`SAVEPOINT` и
  откатывает; для `--isolation schema` — создание/удаление временной схемы.
- **`internal/processor`** — распознавание `kind: test` в YAML процессора.
- **Форматтеры** JUnit/TAP — небольшой пакет (`internal/testing/report`).
- **Часы:** заменить прямые вызовы времени в рантайме на инъектируемый источник
  (clock) — точечно там, где `ТекущаяДата()`/`ТекущаяДатаВремя()` резолвятся.

## Тесты

- Юнит: дискавери (находит `tests/` и `kind: test`, игнорирует обычные
  процессоры); форматтеры (JUnit/TAP валидны); парсинг флагов.
- Интеграция: прогон примера-проекта на SQLite и на PostgreSQL; проверка, что
  `transaction`-изоляция откатывает записи между тестами (тест A пишет — тест B
  не видит); что `schema`-изоляция создаёт/удаляет схему; что моки перехватывают
  `Письмо.Отправить()`/`ВыполнитьКоманду`; что `Часы.Установить` замораживает
  время; что провал ассерта → ненулевой код возврата.
- Регресс: мини-проект, воспроизводящий #477/#478/#479, помеченный как тест —
  чтобы фиксы этих issue закрывались тестом.

## Verification

1. В демо-проекте создать `tests/` с юнит- и интеграционным тестом.
2. `onebase test --project . --sqlite :memory:` — pretty-вывод, счётчики,
   ненулевой код при подложенном провале.
3. `onebase test --db "$PG_DSN" --isolation transaction` — прогон на PostgreSQL,
   БД чистая после прогона.
4. `onebase test --format junit --out report.xml` — валидный JUnit для CI.
5. Тест рассылки: без реального SMTP `Мок.Email` фиксирует адресатов/вложения.
