# Этап 212 — Контракт параметров открытия списков и отчётов

Повторное HTTP-воспроизведение через штатный router и SQLite 29.10.2026:

| Запрос | Нынешний результат | Требуемый результат |
|---|---|---|
| Список, `f.Мастер=alpha` | Только alpha | Только alpha |
| Список, `f.мастер=alpha` | alpha и beta | Только alpha |
| Отчёт, `Мастер=m-1`, без `__run` | default-master | m-1 в форме |
| Отчёт, `Мастер=m-1&__run=1` | m-1 | m-1 |
| Отчёт, `мастер=m-1&__run=1` | default-master | m-1 |

Существующий `TestFormURLCarriesFilterAndReportParams` подаёт готовый JS-объект
с правильным регистром. Он не проверяет `Структура` → JSON: DSL сохраняет имена
ключей в нижнем регистре. В этом проходе заново проверены HTTP и исходники;
полный сценарий уведомления DSL → браузер пока не выполнялся и обязателен при
поставке кода. Глобальное хранение ключей `Структуры` менять нельзя.

## Синтаксис / YAML

Новых типов метаданных и настроек БД нет. Существующие команды сохраняют форму:

```bsl
ОтправитьУведомление(ТекущийПользователь().Имя, "ui.открытьФорму",
  Новый Структура("вид,сущность,отбор", "document", "Заявка",
    Новый Структура("Мастер", "alpha")))
```

Для отчёта используются `параметры` и необязательное `сформировать=true`.
URL остаются `f.<Имя>` для списка и `<Имя>` для объявленного параметра отчёта.
Для даты списка поддержан только явный диапазон `f.<Имя>.from` / `.to`.
Из DSL такой диапазон задаётся плоскими ключами `Дата.from`, `Дата.to`.
Одиночное `f.Дата=...` возвращает 400 с подсказкой про `.from`/`.to`; оно не
превращается молча в фильтр за день. Это сознательный выбор ограниченного
контракта: не вводить второе толкование времени рядом с планами 206 и 208.

## Наблюдаемая семантика и инварианты

### Имена и ошибки

1. Разрешать имя на сервере по метаданным конкретной сущности/отчёта. Сначала
   точное совпадение; иначе единственное совпадение `strings.EqualFold`.
   Ноль совпадений — 400 «неизвестный отбор/параметр», несколько — 400
   «неоднозначное имя». Например, при `Мастер` и `МАСТЕР` точные ключи работают,
   а `мастер` неоднозначен. Не использовать порядок map или объявления полей.
2. Сначала разобрать и проверить ключи **отдельно внутри каждого источника**,
   затем объединять канонические значения по приоритету источников. В query
   либо отдельно в POST повтор одного ключа и два ключа, разрешившиеся в одно
   поле (`Мастер` и `мастер`), — 400 даже при равных значениях. Одно точное имя
   не подавляет конфликтующий alias. Корректный POST не скрывает ошибочные
   дубли/aliases в query. При этом один параметр в query и один в POST —
   разрешённое перекрытие при отправке формы на исходный URL, а не дубликат.
   Для отчёта использовать `r.URL.Query()` и отдельно `r.PostForm` после
   `ParseForm`; слитый `r.Form` не подходит для проверки дублей источника.
   Маркеры `__has.<Имя>` разрешать отдельно тем же resolver: повтор/aliases
   одного маркера внутри источника — 400, но одно значение и один presence
   marker того же параметра образуют штатную пару формы. Они не считаются
   дублем друг друга. Их имена должны однозначно разрешаться в метаданных.
3. Префикс списка `f.` и суффиксы `.from`/`.to` чувствительны к регистру;
   сопоставление без регистра касается только имени метаданных между ними.
   При точном совпадении всего остатка с именем поля сначала трактовать его как
   имя поля; затем проверять диапазон. Коллизию реального имени `Дата.from` с
   границей поля `Дата` отвергать как неоднозначную, а не выбирать по порядку.
4. В списке проверять все ключи пространства `f.`. Прочие служебные параметры
   списка (`q`, `sort`, `page`, `limit`, `activity` и уже действующие UI-ключи)
   сохраняют прежнее поведение. Неизвестные внешние query-ключи вне `f.`
   не превращаются в отбор. В отчёте необъявленный обычный параметр — 400.
   Действующие управляющие ключи отчёта: `__run`, `__preset`, `__variant`,
   `__settings`, `__preset_action`, `__preset_name`, `__preset_default`,
   `__has.<объявленное имя>`; дополнить только конкретными transport/CSRF
   ключами, реально добавляемыми соответствующей формой. Произвольный
   неизвестный `__...` тоже ошибка. При добавлении новых служебных ключей
   этот общий allowlist обновляется вместе с HTTP-тестами.
5. Неизвестный/неоднозначный отбор возвращает 400 до запроса данных. Не открывать
   вместо ошибки более широкий список. Ошибка не раскрывает скрытые поля:
   авторизация сущности, доступных реквизитов и RLS выполняются как прежде.

### Значения, даты и диапазоны

- Идентификаторы ссылок передаются без замены на представление. Для строк,
  чисел и bool использовать существующие преобразования соответствующего
  маршрута; `false`, `0` и пустая строка не отбрасываются как falsy в JS.
- `null`/`undefined` в объекте команды означают отсутствие ключа, как сейчас.
  Явная пустая строка передаётся. В списке пустое значение снимает этот отбор;
  в отчёте оно сохраняет очистку параметра и не возвращает default.
- `.from`/`.to` допускаются только для date. Пустая граница означает отсутствие
  этой границы, обе пустые — отсутствие отбора. Форматы и включённость границ
  остаются такими же, как у существующей панели дат. Реализация обязана
  инвентаризировать и проверить действующий parser/SQL на SQLite и PostgreSQL;
  не принимать неразбираемое значение или `from > to` как отсутствие фильтра.
  Непустой ошибочный диапазон — 400. Смешение scalar и range — 400.
- Даты отчёта остаются скалярными параметрами существующего типа date. Нет
  нового «дня», преобразования зон или новой точности хранения. Покрыть текущий
  формат панели, offset, границу суток и пустую дату отдельной матрицей.

### Открытие и запуск отчёта

Один resolver собирает значения для первого GET, `__run=1`, POST запуска,
экспорта и повторного запуска после настроек. Сначала отдельно валидировать
query и POST по правилам выше, затем для каждого канонического параметра
выбирать **POST значение/маркер присутствия → query значение/маркер → default
только при отсутствии в обоих источниках**. Порядок полей внутри источника
не влияет на результат. Настройки/пресеты не возвращают default поверх
явного пустого значения или снятого флага.

Штатная HTML-форма отчёта использует `method=POST` без отдельного `action`:
она отправляется на тот же URL, поэтому URL-параметр и новое значение в теле
могут присутствовать одновременно. Не очищать query string ради обхода
проверки дублей и не требовать изменения URL пользователем.

Для checkbox сохранить `__has.<Имя>`: POST marker без значения означает снятый
флаг и перекрывает также старое true из URL. Маркер не обязан сопровождаться
значением. Значение и его presence marker в одном источнике — один параметр,
а не две конкурирующие записи. Применяются существующие преобразования
пустого значения по типу; новые значения данных этим правилом не вводятся.

| Query | POST | Результат после проверки каждого источника |
|---|---|---|
| `Мастер=m-1` | `Мастер=m-2` | m-2, HTTP 200; штатное редактирование |
| `Мастер=m-1` | `мастер=m-2` | m-2 при единственном имени в метаданных; межисточниковый регистр не создаёт дубликат |
| `Мастер=m-1` | `Мастер=` | Явная очистка; m-1 и default не возвращаются |
| `Флаг=true` | Только `__has.Флаг=1` | Снятый флаг; true из URL и default не возвращаются |
| `Флаг=true` | `__has.Флаг=1&Флаг=true` | Отмеченный флаг; штатная пара marker/value допустима |
| `Мастер=m-1` | Параметр и его marker отсутствуют | m-1 из query |
| Параметр и его marker отсутствуют | Параметр и его marker отсутствуют | default |
| `Мастер=m-1&мастер=m-1` | `Мастер=m-2` | 400: POST не скрывает aliases внутри query |
| `Мастер=m-1` | `Мастер=m-2&Мастер=m-2` | 400: повтор внутри POST |

В таблице `Мастер` и `Флаг` — единственные соответствующие имена метаданных.
При реальной неоднозначности имён действует ошибка из раздела «Имена и ошибки».
Та же последовательность нужна для запуска, экспорта и повторного открытия;
после выбора источника значения не собираются заново из слитого `r.Form`.

Без `__run` показывается форма с этими значениями, запрос отчёта не запускается
из-за наличия параметров. С `__run=1` строится тот же набор значений. Для
отчётов без параметров сохраняется существующее автоматическое построение.
Пресеты/варианты меняют компоновку по нынешним правилам; defaults не затирают
явные параметры, а URL не получает права менять недоступные настройки.

## Хранилище / SQL

Миграций, новых индексов и переписывания данных нет. Сопоставление имён
завершается до построения `storage.ListParams`/параметров отчёта. SQL получает
каноническое имя из доверенных метаданных; имя из URL не становится SQL.
Набор строк после RLS и ограничения доступа остаются обязательной частью теста.

## Тесты

Обязательная матрица: точное имя/другой регистр; нет совпадений/два совпадения;
дубли ключей и aliases внутри query и POST отдельно, допустимое перекрытие
между ними и приоритет POST marker над query value;
string/reference/number/bool; отсутствующее/пустое/null;
список/date scalar/range/ошибочная граница/обратный диапазон; отчёт без/с
`__run`, GET/POST/Excel/PDF/settings/preset; роль с RLS и недоступным полем.
Даты проверяются в UTC и Europe/Moscow, а не по часовому поясу машины теста.

Сквозная регрессия исполняет исходник DSL (`Новый Структура`, уведомление),
берёт реальную JSON payload, вызывает настоящий `formURL` в Node/браузере и
следует по его URL через router с SQLite и PostgreSQL. Проверяет строки
результата и DOM значений, а не только строку построенного URL. Unit-тесты
resolver дополняют, но не заменяют этот сценарий.

Обязательные проверки каждого кодового среза: выбранные UI/DSL/storage тесты,
репозиторные contract gates, `go test ./...`, `go build ./...`, CI всех
обязательных платформ. Для plan-only PR: `go run ./tools/plannum`, проверка
локальных ссылок и `git diff --check`; код в этом PR не меняется.

## Совместимость, риски и откат

Старые корректные URL с точными именами сохраняются. URL с иным регистром
начинают применять задуманный отбор; неизвестный ключ в `f.` или параметрах
отчёта и одиночная дата теперь дают явную ошибку. Такие ошибки и заполнение
отчёта до запуска должны быть описаны в CHANGELOG до поставки. Не добавлять
скрытый режим, игнорирующий плохие ключи: он вернул бы исходную потерю отбора.

Основные риски: конфликт имён по регистру, служебный query-key ошибочно принят
за параметр, очищенный bool/default и разное понимание даты в двух БД.
Закрываются матрицей и инвентаризацией всех потребителей до смены сигнатур.
Откат — revert соответствующего кода/документации без отката данных. При
неясном контракте срез возвращается на review, ведомая остаётся на hold.
