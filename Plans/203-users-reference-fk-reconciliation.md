# Этап 203 — Внешние ключи ссылок на учётки при эволюции схемы

## Контекст и решение

Источник: [issue #1712](https://github.com/ivanarama/onebase/issues/1712),
каноничный триаж `5848361646` от 26.09.2026. Одобрен вариант **1** по рекомендации:
сначала отдельный план, затем реальные FK на PostgreSQL и SQLite, проверка
существующих битых ссылок и объяснимый отказ **без автоматической очистки данных**.
Проверка только в `auth.Repo.Delete` (вариант 2) не принята: целостность должна
сохраняться также при прямом SQL и записи через другие публичные пути.

План сверён с `main` **85855213b6655c1e67698173713a60e617377e4d** 09.10.2026.
Это проект реализации; перечисленные ниже новые API, проверки и гарантии пока
не реализованы. Разрыв установлен по коду, полноценный сценарий обновления и
удаления учётки в этом PLAN не запускался. Исходные номера строк в issue уже
сдвинулись: ориентиром служат названия функций.

Предварительная [#1711](https://github.com/ivanarama/onebase/issues/1711) —
подготовка auth-схемы до прикладных миграций/тестов — отдельная работа, не часть
этого plan-PR. До интеграционных срезов проверить её фактическую поставку и
паритет CLI/server/test. Наличие `_users` в свежей базе нельзя предполагать:
текущий `EnsureServiceSchema` её не создаёт, а `applyAllMigrations` начинает
с `DB.Migrate`. У самого storage-теста auth-схему следует создавать явно через
`auth.NewRepo(db).EnsureSchema`, без зависимости от порядка пакетов.

## Синтаксис / YAML и наблюдаемая семантика

Существующий формат сохраняется; нового флага обхода целостности не вводится:

```yaml
fields:
  - name: Автор
    id: author-user
    type: reference:_users
```

После успешной миграции новое и давно существующее поле одинаково защищены FK
на `_users(id)`. `NULL` остаётся допустимой пустой ссылкой в nullable-колонке;
обязательность/ключи регистра не ослабляются. Пустая строка и нулевой UUID,
если физически присутствуют и не указывают на существующую учётку, являются
битыми значениями: миграция не преобразует их в `NULL`. Прикладные writer-ы
продолжают использовать существующий контракт пустой ссылки.

Удаление учётки, на которую есть защищённая ссылка, отклоняется БД; `Repo.Delete`
возвращает существующий `auth.ErrUserReferenced`. Нет `CASCADE`, `SET NULL` или
автоматического удаления зависимых объектов. Учётка без прикладных ссылок
удаляется по прежним правилам (включая защиту последнего администратора).
Служебные каскады сессий/ролей не меняются.

При нарушениях миграция выдаёт объект, колонку и количество битых ссылок с
ограниченным списком идентификаторов записей (до 5); не публикует логины,
пароли, имена или содержимое бизнес-объектов. Пользователь исправляет данные
явно и повторяет миграцию. Ошибку чтения каталога/данных нельзя трактовать как
«FK уже есть» или «нарушений нет».

### Инварианты

1. Успешное применение означает наличие эквивалентного, действующего и
   проверенного FK; имени ограничения недостаточно. Повторный запуск — no-op.
2. Проверка и DDL выполняются под одной сериализацией. Любая конкурентная
   запись либо остаётся валидной, либо отвергается; окно между preflight и DDL
   не допускает успешной миграции с новой битой ссылкой.
3. Установка FK атомарна в пределах одного источника: его колонки, данные,
   ограничения, индексы, триггеры и карта `_schema_fields` при ошибке возвращаются
   в согласованное исходное состояние. Это не обещание общей транзакции всей
   `applyAllMigrations`: уже завершённые независимые таблицы могут сохраниться.
4. SQLite сохраняет входящие ссылки, строки ТЧ, self-reference, orphan-колонки
   от отложенного drop и неизвестные платформе элементы физической схемы.
   Если безопасный перенос определения невозможен, операция прекращается
   до DDL с диагностикой; молча упрощать схему запрещено.
5. `--allow-destructive` не разрешает очистить ссылки или обойти FK-preflight.
   Dry-run не устанавливает FK и не меняет данные; вывод отличает отсутствие
   колонки от отсутствия ограничения и называет необходимую перестройку.
6. Вложенная транзакция не разрешает тайно отключить FK SQLite. Смена режима
   соединения восстанавливается при любом исходе; соединение с выключенным
   enforcement не возвращается в рабочий пул.

Внутри этого плана: физические metadata-колонки с `RefEntity=_users` в шапках
справочников/документов, ТЧ, измерениях/ресурсах/реквизитах накопительных и
информационных регистров, ресурсах/субконто бухрегистров. Последние границы
нужны, чтобы обещание защиты удаления не осталось верным только для шапки.
Дескрипторы строятся из фактически поддержанных метаданных и проходят через
общий reconciler; нет поиска произвольных `_id` по всему каталогу БД.

Вне периметра: общий ремонт всех бизнес-FK, ссылки внутри JSON/констант,
архивов и внешних систем, удаление/слияние учёток, новые правила RBAC.
Защита таких значений этим планом не заявляется. Reconciler не меняет
существующие бизнес-FK и служебные auth-каскады. Если импорт временно снимает
FK, его успешное завершение обязано восстановить покрываемые ограничения;
отдельно проверить совместимость restore/DemoReset, не изобретать обход отказа.

## Хранилище / SQL и механизм применения

Предлагаемый шов storage: дескриптор `UsersReference{Object, Table, Column}`,
read-only `PlanUsersReferenceConstraints(ctx, refs)` и
`EnsureUsersReferenceConstraints(ctx, refs) error`. Названия проектные.
Внутри storage нет импорта auth: создание `_users` остаётся ответственностью
композиционного корня (#1711). При отсутствии цели — явный отказ.

Preflight читает non-NULL источники через `NOT EXISTS` по `_users(id)`.
Параметры/идентификаторы проходят штатные dialect/quote helpers; проверка
ограничения сравнивает schema, source/target columns, target table, delete
policy и validated/enabled state. Уже существующий эквивалентный ключ с другим
именем сохраняется. Несовместимый FK не удаляется автоматически. Для нового
PG-ключа использовать устойчивый `ForeignKeyName`, сохраняя лимит имени в байтах.

### PostgreSQL

Одна транзакция на источник: детерминированный порядок блокировок, повторное
чтение каталога, preflight и `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY`.
Advisory-lock сериализует cooperating migrations, но не обычный SQL:
эффективная защита от конкурентной записи/удаления должна обеспечиваться
табличными блокировками и самим FK-DDL, включая `_users` как цель.
При lock timeout/cancel — rollback, без «продолжим как будто всё успешно».
Обычный валидированный ADD выбран базовым вариантом; `NOT VALID` не считается
готовым результатом. Для больших таблиц это осознанное окно обслуживания,
а асинхронная валидация — отдельное будущее решение.

### SQLite

Сначала различить отсутствующую колонку и старую колонку без FK. Быстрый
`ADD COLUMN ... REFERENCES _users(id)` с nullable/default NULL допустим только
при подтверждённых условиях безопасного additive-пути. Существующая колонка
или одновременная реструктуризация требуют полноценной перестройки.

Определение берётся из физической схемы, а не заново из YAML: сохранить все
колонки/default/NOT NULL/PK/UNIQUE/CHECK/FK, хвост определения таблицы,
пользовательские индексы и триггеры. Разбор должен отвергать неподдерживаемый
DDL до изменений; простая строковая замена не является достаточным контрактом.

Опасный путь — `DROP` исходной таблицы при `foreign_keys=ON`: он способен
задействовать входящие действия удаления. Поэтому безопасный rebuild требует
отдельного верхнеуровневого maintenance-scope: забрать физическое соединение,
снять FK-enforcement **до начала транзакции**, занять writer-lock, повторить
preflight, CREATE временной таблицы → явный INSERT всех сохраняемых колонок →
проверка числа/значений строк → замена → восстановление индексов/триггеров →
`foreign_key_check` до commit. Не переименовывать исходную таблицу первой:
входящие определения должны продолжать указывать на исходное имя.

До временного отключения обязательны отсутствие внешней активной транзакции
и исключение конкурирующих миграций на этом соединении. Проектируемый scope
должен быть согласован с `WithTxScope`; нельзя менять PRAGMA внутри savepoint
и рассчитывать на действие настройки. Если вызов уже вложен, отклонить
небезопасный rebuild до DDL либо поднять его к верхнему миграционному scope.

При любой ошибке откатить DDL/копирование и восстановить прежний enforcement.
Если восстановление не доказано, закрыть/вывести соединение из обращения и
вернуть ошибку. После успешного commit включить FK и подтвердить режим новым
запросом. Другие соединения продолжают enforcing FK; отдельные матричные
сценарии должны проверять их конкурентную запись и конечную целостность.
Существующие сторонние нарушения `foreign_key_check` — диагностированный
отказ, не повод молча пропустить проверку. Не использовать `DROP ... IF EXISTS`
для чужой временной таблицы: уникальное имя и проверка владения.

## Совместимость и миграция

YAML и хранимые UUID не меняются. Новая версия может отказать в старте базы с
битыми ссылками, которую старая версия запускала: это ожидаемая, документируемая
смена поведения. Перед обновлением: backup, read-only аудит, ручное исправление
ссылок, maintenance window и dry-run; никогда автоматический `doctor --fix`.

Переименование поля по устойчивому ID переносит колонку с FK; после rename
reconciler сверяет фактическую цель, не требует совпадения прежнего имени.
Смена string→reference при том же SQLite TEXT должна запускать FK-проверку,
хотя обычный retype не меняет SQL-тип. Reference→string/drop используют
существующую политику изменения схемы; отложенный destructive-drop сохраняет
колонку и её действующее ограничение до явного разрешения удаления.

Создание, обновление, CLI/server/test и восстановление должны сходиться к
одному набору constraints. При импорте старого архива с несовместимыми учётками
нельзя обещать успешный restore ценой выключенного FK или очистки ссылок:
вернуть ошибку с существующим атомарным откатом восстановления.

## Тесты, гонки и критерии завершения

Матрица `dbtest.ForEachDialect` (storage-тесты снаружи `package storage`):
свежая сущность, добавленная колонка, legacy-колонка без FK, поле без `id`,
поле с `id`, rename/retype и повторный migrate. Данные: валидный UUID, `NULL`,
битый UUID и SQLite `''`; после refusal все исходные значения сохранены.
Для удаления выбрать обычную учётку при наличии другой админской учётки:
не спутать FK-отказ с защитой последнего администратора. На отказе удаления
проверять сохранность самой учётки и связанных сессий/ролей.

Конкурентные сценарии на независимых подключениях: две миграции одного поля;
writer, вставляющий битую ссылку между preflight и DDL; удаление учётки во время
миграции. Барьеры/таймауты детерминированы; после завершения отсутствие dangling
refs проверяется отдельным запросом. Для SQLite crash/late DDL-failure проверять
весь источник и зависимые таблицы, не только наличие нового FK.

Дополнить живые query-тесты: full_name при непустом имени, fallback login при
пустом имени, пустая nullable-ссылка, неизменность `_id`/представления после
перестройки. Это реальный `Compile` + SQL execution, а не сравнение SQL-строки.
Driver-коды проверять на реальном отрицательном DELETE/INSERT, не искусственном
конструировании `PgError`.

Завершение: вся покрываемая inventory защищена валидированными constraints;
матрица свежей/обновлённой схемы проходит на PG и SQLite; нет потерь данных при
отказе/гонке/rebuild; dry-run и diagnostics честны; restore сохраняет свой
rollback; пользовательская документация описывает отказ и порядок подготовки.
PG-подтесты в CI реально исполнены. Успешный PLAN не является выполнением этих
критериев и не закрывает #1712.

Будущая реализация проверяется на двух отдельных временных базах:

1. Собрать `go build -o /tmp/onebase-203 ./cmd/onebase`; подготовить минимальный
   проект справочника с обычным строковым полем и двумя учётками, мигрировать.
2. Добавить `Автор: reference:_users`, выполнить dry-run и обычный migrate:
   `/tmp/onebase-203 migrate --project <project> --sqlite <db>` либо `--db <dsn>`.
3. Записать объект с автором через публичный CRUD. Попытаться удалить автора
   штатным управлением пользователями; проверить объяснимый отказ и сохранность
   объекта, учётки, ТЧ, сессий и ролей. Отвязать автора и повторить удаление.
4. На отдельной legacy-базе создать прежнюю колонку без FK, заполнить валидными
   и битыми ссылками. Проверить отказ без изменений, исправить данные явно,
   повторить миграцию дважды и убедиться в idempotency и отказе прямого SQL.
5. Выполнить матричные тесты затронутых пакетов с `TEST_DATABASE_URL`:
   `go test -count=1 ./internal/storage ./internal/auth ./internal/query ./internal/dbcheck ./internal/cli`.
   Затем обязательные репозиторные build/CI-гейты. PG skip не принимать за успех.

В этом plan-PR выполняются только `go run ./tools/plannum`, проверка относительных
ссылок и diff/UTF-8. Продуктовые сценарии выше — требования к будущим срезам.

## Риски, откат и эстимейт

Главные риски: блокировки больших PG-таблиц, свободное место для SQLite-copy,
неполный перенос чужого DDL, входящие каскады, ошибка восстановления PRAGMA,
несогласованный порядок auth/restore и ложное «готово» после одного диалекта.
На неизвестном DDL или нехватке места — отказ до подмены; на позднем сбое —
rollback. Для больших баз заранее измерить время/размер на копии данных.

Откат не чистит записи. Ошибочная миграция откатывает свой источник транзакционно.
После успешной установки предпочтителен откат бинаря с сохранёнными защитными
constraints: проверить совместимость на копии. Если требуется именно вернуть
прежнюю схему, оператор использует проверенный backup либо явную отдельную
миграцию снятия только новых FK (SQLite снова требует безопасный rebuild);
автоматического «отката отключением foreign_keys» нет. Снятие защиты — решение
оператора, не побочный эффект обычного downgrade.

Оценка: **8–13 рабочих дней** после готовности #1711, включая публичную матрицу,
гонки и restore. Резерв зависит от нестандартного DDL и размеров SQLite-баз.
Исследование произвольных расширений схемы не должно разрастаться внутри среза:
поддержанные формы фиксируются тестами, остальные получают безопасный отказ.
