# Этап 198 — Безопасное редактирование записи регистра сведений

## Контекст

Ведущая заявка: [#1921](https://github.com/ivanarama/onebase/issues/1921).
Администратор независимого регистра должен открыть строку списка, исправить
ресурсы либо период/измерения и записать результат, не вводя всё повторно.
Повторное добавление сегодня делает upsert; удаление и добавление при смене
ключа не образуют одну пользовательскую атомарную операцию.

Принят **вариант 2** доверенного триажа `6046947402`: сначала этот отдельный
технический план полного редактирования, затем небольшие последовательные
PR. Решение закреплено `decision:2` и последующим комментарием владельца
`6055950105`. План не закрывает issue. Каждый кодовый срез проходит отдельное
REVIEW точного HEAD и обязательный CI; поставка проходит обычный human ship.

Ниже факты проверены по `main` **85e4caf09e928484a97e0ed5f28beccc7a906f2d**
08.10.2026. Статусы старых планов не использованы как доказательство реализации.
[#1920](https://github.com/ivanarama/onebase/issues/1920) про DSL-запросы и
PR #1922 про ширину списка независимы; ожидать их для storage/HTTP-контракта
не требуется. В этом plan-PR меняются только этот документ и индекс планов.

## Наблюдаемая семантика и инварианты

1. Независимый регистр (`Recorder == false`) открывается из списка кнопкой
   «Изменить», двойным щелчком или Enter/F2 на выбранной строке. Одиночный
   щелчок сохраняет существующее выделение и панель деталей. Форма заполнена
   точной исходной записью, а представления ссылок служат только подписями.
2. Исходная идентичность — **полный физический ключ**: все измерения и, если
   `Periodic`, период. Пустое строковое измерение является значением ключа,
   не отсутствующим отбором. UUID, десятичные числа и даты не проходят через
   представление ссылки, `float64` или форматированную дату списка.
3. Для того же ключа нужны `read` и `write`, без `delete`. Обновляется ровно
   исходная запись, только если версия, прочитанная формой, ещё действительна.
   Отсутствующая строка не превращается в новую через upsert.
4. Для смены ключа нужны `read`/`write` исходной строки, `delete` исходной строки
   и `write` предложенной новой строки. Старый DELETE, новый INSERT и все
   записи очереди обмена находятся в одной rollback-области. Новый INSERT
   никогда не обновляет конфликтующую строку. При отказе сохраняются обе
   исходные строки и прежняя очередь обмена.
5. Устаревшая форма не перезаписывает изменения из другой формы, DSL, обмена
   или другого штатного writer-а. Удаление/повторное создание по прежнему
   ключу и изменение A → B → A также отменяют старую форму. Время `updated_at`
   не используется как уникальная версия.
6. Авторизация проверяется заново на POST. Токен формы не предоставляет права.
   SQL-предикаты RLS проверяются по точной исходной строке и фактически
   записанному результату; проверка Go не заменяет SQL-семантику типов/NULL.
7. Защищённый период или измерение запрещают открытие edit-формы и поддельный
   POST, как нынешний exact DELETE. Скрытые/маскированные ресурсы не попадают
   в Values, ref options, DOM, токен или ошибку. Их отсутствие в POST означает
   сохранить текущее серверное значение; отправка такого поля вручную — отказ.
8. Регистры `Recorder == true` в ручном списке доступны только для чтения.
   Новые edit-маршруты, а также прежние `/new` и `/delete` отклоняют ручную
   мутацию независимо от видимости кнопок. Проведение и его storage-путь
   сохраняются. Строка с фактическим `recorder`, оставшаяся после смены
   метаданных на независимый регистр, тоже не редактируется вручную.
9. Конфликт не вызывает автоматической повторной записи или перезагрузки с
   подстановкой новой версии. Введённые разрешённые значения остаются на форме;
   пользователь явно открывает актуальную запись и повторяет изменение.
10. Один успешно использованный edit-токен не может повторно записать строку:
    её версия уже изменилась. Потерянный HTTP-ответ не даёт оснований повторять
    POST с новой версией. Отмена формы ничего не пишет.

## Синтаксис / YAML и HTTP-форма

Новых YAML-флагов нет: `periodic`, `recorder`, dimensions/resources и действующие
permissions/row filters/field access задают поведение. Независимый регистр с
физическим PK поддержан; непериодический legacy-регистр без измерений и PK
не получает edit-кнопку и возвращает понятный отказ, без автоматической
смены схемы или выбора произвольной строки.

Предлагаемые маршруты:

```text
GET  /ui/inforeg/{name}/edit?key=<base64url versioned key document>
POST /ui/inforeg/{name}/edit
     edit_token=<server-authenticated expectation>
     <разрешённые period/dimensions/resources>
```

Документ locator содержит версию формата и полный ключ из
`InfoRegKeyValuesField`/`period_key`; это машинные значения, не отображение.
Base64url служит транспортом, не шифрованием и не авторизацией. Key выдаётся
только после read RLS и проверки масок. GET проверяет read/write, маски ключа,
Recorder и exact SQL RLS до выдачи формы. На locator наложены ограничения
размера, строгая схема, полный набор измерений и единственное значение каждого
параметра; unknown/duplicate/null/missing fields отвергаются. Имена служебных
полей отделены от пользовательских имён; коллизия метаданных диагностируется.

После чтения сервер выдаёт подписанный HMAC-SHA256 `edit_token`: версия
формата, identity базы/регистра, digest метаданных, физический исходный ключ,
UUID edit-версии, identity текущей сессии и expiry **30 минут**. Ресурсов в
токене нет. Секрет сервера берётся из crypto/rand и не попадает в HTML/логи;
проверка подписи constant-time. Перезапуск сервера инвалидирует открытые
формы, а изменение схемы — metadata digest. Токен не заменяет CSRF. Для
нескольких процессов нужен общий signing key; до поддержки такого deployment
маршрут включается только в существующем одиночном runtime, без скрытого
fallback к неподписанному ожиданию.

При отключённой аутентификации binding строится по отдельному случайному
HttpOnly/SameSite cookie формы, а не по общему пустому user id. Он не вводит
новых прав и сохраняет действующий режим базы; обычный CSRF-гейт остаётся.

Форма показывает точный период с временем и долями секунд. Нельзя использовать
нынешний `type=date` как единственное значение при редактировании периодической
строки: это обрежет исходное время. Незатронутые ключевые поля сохраняют
lossless machine value; явно изменённая дата проходит строгий разбор с
существующей локальной семантикой ввода, отказом для неоднозначного времени
DST и без округления. Ссылки записывают UUID; option с выбранным UUID загружается
через действующий gated reference loader, не теряется из-за ограничения списка.
Decimal и boolean валидируются по типу; ошибки не превращаются в string/false.
Richtext использует существующий редактор, лимиты и санитайзер. Непериодическая
форма отвергает присланный period. Маска никогда не записывается как значение.

Ответы: malformed input/токен — 400; истёкшая форма или metadata change — 409
с предложением открыть заново; нет права — 403; для неограниченного пользователя
отсутствие записи — 404, изменённая версия/занятый доступный ключ — 409.
Для restricted RLS отказ по отсутствующей/скрытой строке не различается;
конфликт со скрытой целевой строкой не раскрывает её ключ, ресурсы или владельца
и использует общий access-denied ответ. При ошибке повторный рендер использует
только разрешённые поля запроса и безопасный контекст списка.

## Хранилище / SQL, конкуренция и миграция

### Локальная версия записи

Добавить служебную `_edit_revision` TEXT-колонку в таблицы регистров сведений.
Значение — новый UUID из crypto/rand на каждый успешный INSERT/UPDATE штатного
writer-а, включая запись прежних ресурсов теми же значениями. Он не связан с
датой, `_exchange_applied` или версией отправителя. Подчинённые регистры также
имеют колонку, чтобы смена режима не требовала другой схемы.

На миграции старой базы: добавить колонку без разрушительной default-миграции,
заполнить NULL/пустые версии индивидуальными UUID и проверить полный backfill
в одной `WithTxScope`. Не перезаписывать уже действительные версии при обычном
повторном migrate. UUID генерируются платформой, не за счёт расширения PG.
Открывать edit можно только для валидной версии. Если metadata field конфликтует
с зарезервированным именем, миграция останавливается с диагностикой, не удаляет
или переименовывает бизнес-колонку.

Нужен исчерпывающий writer inventory с проверками: `infoRegSet`/conditional
upsert, `WriteInfoMovements`, `InfoRegApplyExchange`, record-set replacement,
seed/загрузка, restore. DELETE версии не сохраняет; повторный INSERT получает
новую. SQL-DML, принимающий клиентскую `_edit_revision`, запрещён в штатных
публичных путях. Приёмочная гарантия относится к поддерживаемым writers
платформы; ручной SQL администратора требует закрытия активных edit-форм.
Одновременные writers из старого и нового бинаря не поддерживаются. Если
найден неохваченный штатный writer, edit-маршрут нельзя включить до его исправления.

`CreateInfoRegisterSQL`, обычная реструктуризация и `fixInfoRegPKSQLite` должны
согласованно учитывать служебную колонку. Без изменения ключа версия сохраняется;
при изменении ключевой схемы metadata digest отменяет старые формы. SQLite
пересоздание копирует колонку либо выдаёт новые версии всем перенесённым строкам;
никогда не оставляет строку без версии. Ошибка миграции откатывает данные и DDL.

### Предлагаемый storage-контракт

Имена ниже проектные, не утверждение о существующем API:

```go
type InfoRegEditKey struct { Dimensions map[string]any; Period *time.Time }
type InfoRegEditRecord struct { Key InfoRegEditKey; Revision string; Row map[string]any }
type InfoRegEditExpectation struct { Key InfoRegEditKey; Revision string }
// Exact SQL read с readFilter, физическим ключом, ресурсами и локальной версией.
InfoRegReadForEdit(ctx, ir, key, readFilter) (*InfoRegEditRecord, error)
// Conditional UPDATE/DELETE и insert-only доступны shared edit-service в tx.
```

Ключ проходит через нынешние `resolveInfoRegLookupKey`/`resolveInfoRegWriteKey`
и `physicalDimWhere`; никаких `RegFilter` вместо exact key. SQLite legacy
NUMBER сохраняет exact-first spelling, даже если рядом существуют `1` и `1.0`.
Для целевого ключа PostgreSQL учитывает реальные NUMERIC typmods и timestamp
precision: строковые `1.00`/`1`, округление `1.001` и timezone-эквивалентные
даты не должны делать различным один PK. Сравнение source/target проводится
в storage по фактическому DB-ключу после нормализации, не по JSON/Go map.

### Одна атомарная операция

Общий `infoRegEdit` рядом с `infoRegWrite/infoRegRemove` выполняет:

1. Разбор токена, полный typed input, проверку метаданных/прав и создание
   `WithTxScope`, включая nested savepoint. Это общая service-граница:
   HTTP-хендлер не пишет SQL и не вызывает `InfoRegSet` напрямую.
2. `LockInfoRegisterForPolicyWrite` **до первого transactional pre-read**,
   включая unrestricted admin. Это защищает отсутствующий целевой ключ от
   конкурентной обычной вставки; одна row lock этого не гарантирует.
3. Exact-read исходной строки с SQL read/write predicates, существующей
   edit-версией и отказом при recorder. Ошибки чтения возвращаются, а не
   трактуются как отсутствие. Сверка expectation; загрузка скрытых ресурсов
   только внутри сервера; слияние разрешённых изменённых ресурсов.
4. DB-нормализация предложенного ключа; если это прежний PK, shared write
   получает режим `expected existing`: conditional UPDATE по полному исходному
   ключу, SQL write RLS и `_edit_revision = expected`, ровно одна строка,
   новая UUID-версия. Обычный upsert-контракт старого `/new`/DSL не меняется.
5. Если PK другой — проверка delete-policy исходной строки и write-policy
   предложенной строки; conditional DELETE RETURNING по исходному ключу,
   revision и SQL delete RLS, ровно одна строка; **insert-only** нового ключа.
   Любая unique collision возвращает конфликт и откатывает DELETE.
6. SQL exact-check результата через write predicate, повторный typed RLS
   check как дополнительная защита; регистрация save для того же ключа либо
   tombstone старого и save нового. Старую identity брать из DELETE RETURNING,
   новую — из storage read-back, как действующий exchange-контракт.
7. Закрыть/вычитать все курсоры внутри tx/scope до RELEASE/COMMIT. Ошибка
   policy, unique, exchange, canceled context или commit не даёт успеха HTTP.
   Успех — redirect к списку с прежним безопасным фильтром/страницей.

Уникальный конфликт на PG не продолжают обрабатывать запросами в aborted tx:
сначала rollback edit-scope, затем безопасное отображение ошибки. Lock timeout
и SQLite busy возвращают retryable сообщение, но не повторяют mutation сами.
Конкурентные A→B и B→A сериализуются одной register-lock; захваты нескольких
регистров этим маршрутом не вводятся. Исчезновение source никогда не разрешает
insert-only как восстановление. Неизменённый `infoRegExistingPolicyRow` нельзя
оставить shared authority: его exact-read/error fix поставляется с service-срезом.

### Обмен и переносимость

Для непериодического регистра перенос регистрирует два разных object_id:
delete старого ключа и save фактического нового. Нужен round-trip пакета через
публичный обмен, не только проверка двух вызовов helper-а. Ошибка регистрации
любого из них откатывает оба изменения и строки `_exchange_changes`.

Для периодического регистра `RegisterInfoRegOnSave` сейчас явно возвращает
nil без регистрации. План сохраняет эту существующую границу и предупреждение
`check`: он **не обещает доставки** переноса периодического ключа. Добавление
периодического exchange identity является отдельным контрактом; локальный
edit периодических регистров от него не зависит.

`_edit_revision` не экспортируется в UI/REST/DSL бизнес-проекции или обмен и
не является версией источника. Universal backup, использующий `SELECT *`,
явно фильтрует эту локальную колонку; restore игнорирует её в входящем payload
и генерирует новые версии. Старый backup восстанавливается без поля;
SQLite↔PostgreSQL round-trip не требует новой версии формата. Restore выполняется
при закрытом доступе к базе и инвалидирует server signing key/формы. Нативный
backup может содержать колонку; при запуске восстановленной базы создаётся
новый signing key, поэтому старый токен не оживает.

до завершающего D issue не считается полностью реализованной. Не добавлять
закрывающее issue ключевое слово в A–C. Каждый PR самодостаточен для проверки
и отката; нет скрытого активного пишущего endpoint до готовности сервиса.

| Срез | Поставляемый результат | Публичная приёмка |
|---|---|---|
| **A: версия и точное чтение**, 2–3 дня | DDL/backfill/rebuild/restore и версии всех штатных writers; gated exact-read; публичная схема прежняя | `dbtest.ForEachDialect`: public migrate/set/exchange/record-set/backup paths меняют revision; no-op запись и delete/reinsert отменяют ожидание; повторный migrate сохраняет revision; legacy backup и cross-dialect restore; API/DSL результаты без служебного поля |
| **B: общий edit-service**, 3–4 дня | Exact pre-read вместо широкого fallback, same-key expected write и move-key с rollback/RLS/exchange; публичных edit-маршрутов пока нет | Матрица публичных storage операций на двух подключениях: occupied target, source changed/deleted, A→B→A, одинаковое ожидание двух writers, concurrent ordinary INSERT, numeric/date normalization, nested scope rollback. Shared UI/DSL write/delete regression через зарегистрированные HTTP/DSL входы; обмен export/import даёт tombstone/save |
| **C: форма с неизменяемым ключом**, 2–3 дня | GET/POST edit, signed/session-bound expectation, заполненная форма и ресурсы; UI ключ пока read-only, смена ключа в forged POST запрещена; запрет ручных new/delete при Recorder | Реальный router: открыть список→форму→записать ресурс при write без delete; stale/source missing/replay/token tamper/expiry/session mismatch/schema change/CSRF. Read/write RLS, resource mask, forged protected field, Recorder, исходные дата/UUID/decimal, richtext limits. Browser: открыть/отменить/сохранить, отсутствие утечки в DOM |
| **D: полный перенос и UX**, 2–3 дня | Период/измерения редактируемы при допустимом контракте; полный атомарный перенос, клавиши, сохранение list context и документация | HTTP/UI матрица same-key без delete и move с write+delete; deny только старой/новой строки; visible/hidden occupied target; period/time/precision, composite/ref/number/empty keys; failure injection обмена после первого события; browser dblclick/Enter/F2/кнопка, фильтр/страница после redirect, кнопки delete/picker не запускают edit |

Для B через public storage API проверять состояние самой строки и outbox
после rollback, а HTTP-authorization дополнительно проверять в C/D через
полный router. Тест приватного `infoRegEdit` сам по себе не является приёмкой.
Concurrency использует barrier/отдельные подключения, не sleep/один DB handle;
нужен случай stale write непосредственно перед COMMIT и занятый новый ключ после
открытия формы. При вложенной tx вызывающий может обработать конфликт и
продолжить внешнюю транзакцию, а provisional строки/обмен всё равно отсутствуют.

Общая матрица для A–D:

- независимый periodic/non-periodic, составные измерения, boolean, reference
  UUID, date, NUMBER/decimal, пустое string; SQLite legacy spelling и PG scale;
- два одинаковых ожидания, delete/reinsert, resource change/revert, concurrent
  insert целевого ключа, rollback/timeout/cancellation и потерянный ответ;
- admin, read-only, write без delete, delete без write, разные read/write/delete
  RLS, новая строка вне write RLS, защищённое измерение/period/resource;
- запрет Recorder на списке и всех ручных маршрутах, сохранность проведения;
- периодические записи с одинаковыми измерениями в разные моменты времени,
  иной TZ процесса, non-midnight/subsecond и DST; ресурс без прав не раскрывается
  через подпись ссылки или повторный рендер;
- реальный exchange load/save непериодического регистра и неизменная
  диагностика исключённого периодического exchange.

## Verification

При реализации каждого среза запускать `go build ./...`, тесты затронутых
пакетов и обязательный CI protected main. SQL-семантика покрывается одним
`dbtest.ForEachDialect` телом для SQLite и PostgreSQL при заданном
`TEST_DATABASE_URL`; зелёный SQLite без PG не считается полной матрицей.
Для C/D обязательны браузерные сценарии обычного UI, включая auth и CSRF.

Ручная итоговая проверка на тестовой конфигурации:

1. Создать две записи разных ключей с различными ресурсами; открыть первую
   из списка, сохранить ресурс без delete-права и убедиться, что другая цела.
2. Открыть одну запись в двух вкладках. Первая пишет, вторая получает conflict;
   повторить с удалением и созданием того же ключа, затем с изменением и откатом
   ресурса другим writer-ом. Второй вкладке не выдаётся новая версия молча.
3. Выдать write+delete, перенести ключ в свободный: старая запись исчезает,
   новая содержит ресурсы; пакет непериодического обмена повторяет результат.
4. Перенести в занятый ключ: обе записи/ресурсы/очередь остаются прежними.
   Повторить под RLS и с имитацией ошибки регистрации второго exchange event.
5. Проверить период с временем/долями секунды, числовой и ссылочный ключ,
   маски ресурсов, protected key и Recorder. Старый период/UUID не теряется
   при сохранении только ресурса. Forged POST не обходит ограничения UI.
6. Restore старого backup и cross-dialect backup, повторный migrate и
   перезапуск сервера: данные доступны, старые формы отменены, служебных
   значений в публичных результатах нет.

В этом plan-PR достаточно `go run ./tools/plannum`, проверки новых локальных
ссылок/индекса, `git diff --check` и подтверждения allowlist `Plans/`. Описанные
будущие product-тесты ещё не реализованы и не выдаются за выполненные.

## Риски, откат и критерии завершения

Основная стоимость — writer/migration coverage, а не кнопка. Register-level
lock сохраняет текущую модель корректности, но сериализует writers и может
давать timeout на крупных регистрах. Не переходить на per-key advisory locks
без отдельного доказательства совместимости со всеми штатными DML writers.
Backfill больших регистров выполняется в обслуживании, не в HTTP-запросе;
estimate уточнить на объёме реальной базы до выпуска A.

Служебная версия увеличивает число изменений схемы. Нельзя обещать downgrade
с открытыми формами или параллельные старые writers. При rollback закрыть edit
маршруты, остановить writers, сохранить backup и откатить код: добавленная
колонка остаётся, её удаление не требуется. Старый ручной upsert доступен для
независимых регистров. Исправлять последствия удачной бизнес-операции нужно
отдельным новым изменением, не обратным проигрыванием старого edit-токена.
Откат интерфейса не удаляет перенесённые бизнес-строки и не отменяет доставленный
exchange. Возврат к новой версии начинает runtime с новым signing key,
доводит/backfill проверяет схему и не принимает прежние ожидания.

Критерии завершения #1921: A–D в main, полный HTTP/UI сценарий обеих операций,
SQLite/PG матрица конкуренции и доступа зелёная, rollback включает outbox,
безусловный ручной запрет Recorder доказан, документация честно называет
периодический exchange неподдержанным, все штатные writers инвалидируют формы,
backup/restructure не теряют данные. Финальный delivery PR связывает issue;
merge этого плана сам по себе заявку не закрывает.
