# План 133 — Строитель HTML-таблиц: экранирование по построению

Дата проектирования: 2026-08-18.
Статус: ⬜ **Проект** (не начато). Issue #988, находка А4.

## Контекст

HTML отчётов, кросс-таблиц и предпросмотра макетов собирается конкатенацией
строк, а безопасность держится на дисциплине: каждое значение автор рендера
обязан **вручную** пропустить через `html.EscapeString`. По движку таких вызовов
**78**; в двух табличных рендерерах — 16, по 8 на файл.

Итог сборки конвертируется в `template.HTML`, что отключает автоэкранирование
`html/template`. Таких конверсий в непроверочном коде **8**, и у каждой стоит
`//nolint:gosec` с обоснованием «экранировано руками»:

| Место | Что собирает | Источник значений |
|---|---|---|
| `internal/ui/report_compose_render.go:38` | таблица скомпонованного отчёта | данные базы |
| `internal/ui/report_cross_render.go:62` | кросс-таблица | данные базы |
| `internal/ui/templates.go:736` | скрытые поля формы (`listHidden`) | параметры запроса |
| `internal/ui/templates.go:894` | `pageRaw` — **пользовательский** HTML | DSL `ДобавитьСыройHTML` |
| `internal/launcher/configurator_load.go:278` | предпросмотр макета документа | макет конфигурации |
| `internal/launcher/configurator_load.go:301` | предпросмотр макета печатной формы | макет конфигурации |
| `internal/ui/icons.go:92` | SVG-иконка Lucide | имя символа из спрайта |
| `internal/dsl/interpreter/htmltemplate_builtins.go:49` | результат `БезопасныйHTML` | DSL, после санитайзера `richtext` |

Уточнение к числам заявки: там значилось 15 мест, в сверке — 6. Оба мимо: сырой
`grep template.HTML` даёт 22 совпадения, но 14 из них — комментарии, объявления
типов, возвращаемые типы и тесты. Конверсий ровно восемь.
`internal/dsl/interpreter/htmltemplate_builtins.go`, названный в сверке, в
репозитории **есть** — он пришёл с планом 125 (`ee8c2dc6`) и даёт восьмую
конверсию; в первой редакции этого плана он был потерян, и отсюда же взялось
число «семь».

## Проблема

Ни одно из этих мест сегодня не сломано — проверено чтением. Проблема не в
текущем состоянии, а в том, **чем оно держится**.

1. **Гарантия невыразима в типах.** `strings.Builder` принимает и
   экранированную строку, и сырую — разницы он не видит. Забытый
   `html.EscapeString` в новой ячейке не вызовет ни ошибки компиляции, ни
   падения теста: HTML останется валидным, отчёт отрисуется, а внутри окажется
   чужой `<script>`.
2. **Плотность ошибки высокая.** В `report_compose_render.go` восемь вызовов
   экранирования на 140 строк, часть — вложенными в `fmt.Fprintf` с четырьмя
   подстановками (`group`, `detail`, `subtotal`). Дописать девятую ячейку по
   образцу и пропустить обёртку — работа на десять секунд.
3. **`//nolint:gosec` глушит единственный автоматический сигнал.** Директива
   стоит на строке конверсии и обоснована для СЕГОДНЯШНЕГО содержимого
   builder'а. Она останется на месте и после того, как в тот же builder добавят
   неэкранированное значение, — обоснование не перепроверяется.
4. **Разметка `pageRaw` — отдельный класс.** Это единственное место, куда
   попадает пользовательский ввод (DSL `ДобавитьСыройHTML`). Там защищает не
   экранирование, а allowlist-санитайзер `sanitizePageHTML`, и смешивать эти два
   механизма в одном плане нельзя: у них разные инварианты.

## Решение

Пакет `internal/htmlbuild` с единственной обязанностью: **значение попадает в
разметку только экранированным**. Не «удобный хелпер», а тип, через который
неэкранированное значение физически не проходит.

### Ключевое решение: разделить типы

```go
package htmlbuild

// Safe — фрагмент, про который УЖЕ доказано, что он безопасен: литерал
// разметки из кода или результат работы этого пакета. Конструируется только
// через Markup (для литералов) и методы строителя.
type Safe string

// Markup помечает строковый ЛИТЕРАЛ как доверенную разметку. Единственная
// дверь для сырого HTML — и потому единственное место, которое имеет смысл
// искать грепом при ревью.
func Markup(literal string) Safe { return Safe(literal) }

type Table struct{ b strings.Builder }

// Text добавляет значение — ВСЕГДА экранированным. Другого способа положить
// значение в ячейку у пакета нет.
func (t *Table) Cell(class string, style Style, v any) *Table
func (t *Table) HeaderCell(class string, style Style, v any) *Table
func (t *Table) RowStart(class string, attrs Attrs) *Table
func (t *Table) RowEnd() *Table

// Attrs — атрибуты строки. Имя атрибута из фиксированного набора, значение
// экранируется; произвольное имя не принимается.
type Attrs map[Attr]any

// HTML отдаёт результат. Единственная конверсия в template.HTML на весь
// движок — и единственный //nolint:gosec, обоснование которого проверяется
// тестами этого пакета, а не глазами автора рендера.
func (t *Table) HTML() template.HTML
```

Разница с сегодняшним днём принципиальная: сейчас автор рендера **может**
забыть экранирование; после — не может, потому что API для этого нет. Чтобы
положить в ячейку сырой HTML, придётся написать `htmlbuild.Markup(...)`, что
видно и в диффе, и грепом.

### Стиль и атрибуты

CSS-значения уже проходят через `internal/csssafe` (`csssafe.Color`), и это
правильный уровень: цвет из данных не должен попадать в `style` как есть.
Строитель принимает `Style` как структуру, а не строку, — тогда
`joinStyles`/`cssOf` перестают быть местом, где можно склеить что угодно:

```go
type Style struct {
	Align      Align   // фиксированный набор: left|right|center
	Color      string  // через csssafe.Color
	Background string  // через csssafe.Color
	Bold       bool
	Italic     bool
	PaddingLeft int    // число, форматируется пакетом
	Hidden     bool
}
```

`padding-left:%dpx` сейчас собирается `fmt.Sprintf` в трёх местах — число,
поэтому безопасно, но это ровно та строка, в которую однажды подставят значение
из данных.

## Что переносится, а что нет

**В периметр плана (4 из 8 конверсий):**

* `report_compose_render.go` и `report_cross_render.go` — ядро, ради которого
  всё затевается; 16 из 78 вызовов экранирования;
* `templates.go:736` (`listHidden`) — значения приходят из параметров запроса,
  то есть снаружи;
* `printform.LayoutTemplate.PreviewHTML` — источник обоих предпросмотров в
  `configurator_load.go`. Конверсий там две, а собирающий код один.

**Вне периметра, осознанно:**

* **`templates.go:894` (`pageRaw`)** — там не экранирование, а allowlist-санитайзер
  для пользовательского HTML. Задача другая (что РАЗРЕШЕНО оставить), инвариант
  другой; смешение сделало бы оба слабее. Отдельный план, если понадобится.
* **`icons.go:92`** — в разметку идёт имя символа, найденное в спрайте; всё
  остальное заменяется фолбэком, то есть множество значений конечно и задано
  кодом. Переносить нечего.
* **`htmltemplate_builtins.go:49`** (`БезопасныйHTML`) — по той же причине, что
  и `pageRaw`: там не экранирование, а санитайзер `richtext`. Инвариант «что
  разрешено оставить», а не «всё превратить в текст», и строитель его выразить
  не может.

## Гейт, без которого план бесполезен

Строитель, которым **можно не пользоваться**, — это стиль, а не гарантия. Через
полгода появится новый рендер, автор соберёт HTML привычной конкатенацией, и всё
вернётся. Поэтому в план входит правило линтера:

```yaml
# .golangci.yml — forbidigo
- p: 'template\.HTML\('
  msg: 'сырой HTML собирается только через internal/htmlbuild; см. план 133'
```

с исключением для самого `internal/htmlbuild` и для двух мест вне периметра
(`pageRaw`, `icons.go`) — точечными, с обоснованием, а не «по каталогу».

Правило важнее самого пакета: оно превращает «мы договорились экранировать» в
«иначе не собирается».

## Тесты

Проверять надо не «строитель экранирует» — это тривиально и будет зелёным всегда.
Проверять надо, что **обойти его нельзя** и что перенос ничего не изменил.

1. **Инъекция через каждый вход.** Значение `<script>alert(1)</script>`,
   `"><img src=x onerror=1>`, `%3Cscript%3E` — в ячейку, в заголовок, в ключ
   группы, в атрибут строки, в цвет, в подпись показателя. В выводе не должно
   быть ни одного неэкранированного `<`.
2. **Инъекция через данные, а не через код.** Отчёт по справочнику, у которого
   в наименовании лежит `<script>`: полный путь от записи в базу до HTML в
   ответе. Юнит-тест строителя такого не покажет — он проверяет строитель, а не
   то, что рендер им пользуется.
3. **Побайтовое совпадение до и после переноса.** Golden-файлы вывода
   `renderComposedTable`/`renderCrossTable`/`PreviewHTML` снимаются ДО правки и
   сверяются после: перенос обязан быть чистым рефакторингом. Это же ловит
   потерянный `data-collapse-to` и прочие атрибуты, от которых зависит JS
   сворачивания групп.
4. **Гейт линтера срабатывает.** Тестовый файл с `template.HTML(` вне пакета
   должен валить `golangci-lint`. Без этой проверки правило может оказаться
   выключенным настройкой и никто не заметит.
5. **`csssafe` остаётся на пути.** Цвет `red;background:url(javascript:...)`
   через `Style.Color` не должен доходить до разметки.
