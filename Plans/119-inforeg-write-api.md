# План 119 — Программная запись регистров сведений

Дата проектирования: 2026-08-11.
Статус: ⬜ **Проект** (не начато). Issue #743.

## Контекст

Пользователь переносит конфигурацию без единого документа: 9 справочников, 13
регистров сведений, регламентные задания и HTTP-сервис. Регистры сведений там —
основной рабочий инструмент (лог обмена, состояние узлов, статистика, свойства
компьютеров), и пишет в них код, а не человек. Оказалось, что заполнить регистр
сведений из конфигурации нечем.

Состояние на 2026-08-11 (ссылки проверены):

| Кусок | Где | Состояние |
|---|---|---|
| Upsert записи | `storage/inforeg.go:59` `InfoRegSet` | есть, обслуживает форму, обмен и движения |
| Удаление по ключу | `storage/inforeg.go:269` `InfoRegDelete` | есть |
| Чтение точной записи | `storage/inforeg.go:20` `InfoRegGetExact` | есть, используется обменом |
| Запись из формы | `ui/handlers_registers.go:294-362` | есть, с полным набором проверок (см. ниже) |
| Движения документа | `entityservice/service.go:871` → `WriteInfoMovements` | есть, только для подчинённых регистратору |
| Обмен | `InfoRegApplyExchange`, `RegisterInfoRegOnSave` | есть |
| **Запись из DSL** | — | **нет вообще** |
| Чтение из DSL | язык запросов: `РегистрСведений.X.СрезПоследних()` | есть |
| Аналог для накопления | `ui/dsl_registers.go:13` `accumRegsRoot` | есть, но **только чтение** (`Остатки`/`Движения`/`ВыбратьПоРегистратору`) |
| Инъекция глобалов | `ui/handlers_dsl.go:272` (`РегистрыНакопления`), `api/server.go:55` (`BuildJobDSLVars` → планировщик) | заданиям достаётся тот же набор |

Асимметрия голая: **читать** регистр сведений из конфигурации можно, **писать** —
нельзя ничем, кроме рук и обмена. Независимый (не подчинённый регистратору)
регистр программно не заполняется вовсе. В 1С для этого есть
`СоздатьМенеджерЗаписи()` и `СоздатьНаборЗаписей()`.

Вторая половина issue #743 — молчаливая потеря `Движения` вне проведения —
закрыта отдельно (PR #746) и в этот план не входит.

## Цель

1. Из модуля можно записать, прочитать и удалить запись независимого регистра
   сведений.
2. Путь из DSL несёт **те же** проверки, что путь из формы, — не «тоже
   проверяет», а вызывает ту же функцию.
3. Подчинённые регистратору регистры программной записью не портятся.

## Принятые решения

1. **Права и строковые политики — обязательная часть API, а не обвязка вокруг.**
   Форма перед записью делает четыре вещи (`handlers_registers.go:294-342`):
   `requirePerm(... "write")`, проверку строковой политики для **существующей**
   записи по ключу (`infoRegExistingPolicyRow` + `rowAllowedFor`), проверку для
   **новой** записи и запись вместе с `RegisterInfoRegOnSave` в одной
   транзакции. DSL-путь обязан делать всё то же. Пропуск проверки существующей
   записи означал бы, что чужую (недоступную по строковой политике) строку можно
   перезаписать вслепую — знать её содержимое для этого не нужно.
2. **Общая функция, а не копия.** Проверки и запись выносятся в
   `infoRegWrite(ctx, ir, dims, res, period, gate)`; форма и DSL зовут её. Копия
   разошлась бы: именно так появились #609 и #649 — «второй путь чтения», в
   котором забыли гейт.
3. **Подчинённые регистратору регистры отклоняются явно.** Если у регистра есть
   движения по регистратору, программная запись мимо документа рассинхронизирует
   его с проведением: перепроведение снесёт запись без предупреждения. Отказ с
   текстом «регистр подчинён регистратору, пишите движениями в
   ОбработкаПроведения» честнее тихой потери — той самой, что чинили в #743.
   > Определение подчинённости: сегодня в `metadata.InfoRegister` (`types.go:373`)
   > признака нет — регистр «подчинён» фактически, если по нему есть движения.
   > Первый этап вводит явный флаг (см. «Открытые вопросы»).
4. **Периодичность проверяется на входе.** Для `Periodic: true` период
   обязателен (как в форме, `handlers_registers.go:304`), для непериодического —
   запрещён. Молча проигнорированный период дал бы запись не туда, где её потом
   ищут `СрезПоследних`.
5. **Регистр доступен и заданиям.** Глобал регистрируется там же, где
   `РегистрыНакопления` (`handlers_dsl.go:272`), а планировщик получает то же
   окружение через `BuildJobDSLVars` (`api/server.go:55`). Это и есть основной
   сценарий заявки — задание пишет состояние узла.

## Синтаксис

Форма 1С, знакомая переносящему конфигурацию:

```
// Запись одной строки
Запись = РегистрыСведений.СостояниеОбменов.СоздатьМенеджерЗаписи();
Запись.Узел = Узел;                       // измерение
Запись.Состояние = "Готов";               // ресурс
Запись.Период = ТекущаяДатаВремя();       // только для периодического
Запись.Записать();

// Чтение по ключу: заполняет ресурсы, если запись есть
Запись = РегистрыСведений.СостояниеОбменов.СоздатьМенеджерЗаписи();
Запись.Узел = Узел;
Запись.Прочитать();
Если Запись.Выбран() Тогда
    Сообщить(Запись.Состояние);
КонецЕсли;

// Удаление по ключу
Запись.Удалить();
```

Набор записей — для пакетной перезаписи по отбору:

```
Набор = РегистрыСведений.ЛогОбмена.СоздатьНаборЗаписей();
Набор.Отбор.Узел = Узел;                  // отбор только по измерениям
Набор.Прочитать();                        // текущее содержимое по отбору
Набор.Очистить();
Стр = Набор.Добавить();
Стр.Узел = Узел;
Стр.Событие = "Старт";
Набор.Записать();                         // замещает содержимое по отбору
```

`Записать()` набора — «удалить по отбору, вставить накопленное», в одной
транзакции. Это семантика 1С, и она же спасает от полузаписи.

## Хранилище / SQL

Новых таблиц и колонок нет: `InfoRegSet`/`InfoRegDelete`/`InfoRegGetExact`
покрывают всё, кроме выборки по частичному отбору для набора записей — там
нужен `InfoRegSelect(ctx, ir, dimFilter, period)` (SELECT по подмножеству
измерений) и `InfoRegDeleteByFilter`. Оба — рядом с существующими, тем же
`dimWhere`.

Транзакция набора записей: `store.WithTx` вокруг delete-by-filter + N upsert,
как это уже делает форма вокруг записи и `RegisterInfoRegOnSave`.

## Этапы

- **119A — менеджер записи.** `СоздатьМенеджерЗаписи`, `Записать`/`Прочитать`/
  `Удалить`/`Выбран`, вынос общей функции записи, отказ для подчинённых
  регистров. Закрывает заявку по существу: 13 мест переносимой конфигурации —
  это одиночные записи.
- **119B — набор записей.** `СоздатьНаборЗаписей`, отбор по измерениям,
  `Прочитать`/`Очистить`/`Добавить`/`Записать`, `InfoRegSelect` и
  `InfoRegDeleteByFilter`, транзакция замещения.
- **119C — линт и справка.** `configcheck` на подчинённые регистры,
  дескрипторы `langref`, документация.

## Тесты

Только через **публичные точки входа** (правило CLAUDE.md, повод — #611).

- Запись/чтение/удаление — прогоном обработки через `RunProcessorOffline` (тот
  же путь, что `onebase procrun`), с реальной БД: образец — новый
  `ui/movements_discarded_test.go`.
- **Матрица диалектов обязательна** (`dbtest.ForEachDialect`): план добавляет
  SQL (выборка и удаление по частичному отбору), а upsert регистров сведений уже
  имеет диалектные ветки. Правило CLAUDE.md про «трогаешь семантику SQL — пиши
  матричный тест».
- Периодический регистр: запись без периода отклонена; запись с периодом
  читается `СрезПоследних` (проверять запросом, а не прямым SELECT — иначе тест
  не докажет, что запись легла туда, где её ищет прикладной код).
- **Права и строковые политики — HTTP-прогоном под ролью**, а не вызовом
  проверки напрямую: DSL под ролью без `write` на регистр получает отказ; чужая
  по строковой политике запись не перезаписывается. Иначе получится зелёный тест
  на коде, которого нет в проде.
- Подчинённый регистратору регистр: программная запись отклонена с внятным
  текстом.
- Набор записей: замещение по отбору не трогает строки вне отбора; сбой в
  середине не оставляет полузаписи (откат транзакции).

## Verification

1. Конфигурация с непериодическим регистром `СостояниеОбменов` и обработкой,
   которая пишет туда строку → `onebase procrun` → `onebase query` показывает
   запись.
2. Периодический регистр: две записи разными периодами → `СрезПоследних`
   отдаёт позднюю.
3. Регламентное задание пишет в регистр (основной сценарий заявки) → запись
   появляется, `Движения` там по-прежнему отклоняются (PR #746).
4. Роль без права записи на регистр → обработка получает отказ.
5. Регистр с движениями по регистратору → программная запись отклонена.

## Риски и ограничения

1. **Второй путь записи** — главный. Смягчается решением №2 (общая функция) и
   тестами прав через HTTP. Стоит завести AST-чокпоинт по образцу
   `ui/row_access_chokepoint_test.go`: вызов `InfoRegSet`/`InfoRegDelete` в обход
   `infoRegWrite` — либо гейт, либо запись в список исключений с обоснованием.
2. **Рассинхрон с проведением** у подчинённых регистров — закрывается решением
   №3, но только если признак подчинённости определён надёжно (открытый вопрос).
3. **Обмен.** Форма регистрирует изменение в планах обмена
   (`RegisterInfoRegOnSave`). DSL-запись обязана делать то же, иначе узлы
   разъедутся молча — ровно тот класс, что план 86 закрывал.
4. **Блокировки.** Пакетная перезапись набора под конкурентную нагрузку — это
   delete+insert по отбору; на SQLite пул в одно соединение делает конкуренцию
   вырожденной, на PostgreSQL нужен явный порядок захвата, иначе взаимоблокировка
   двух заданий по одному регистру.

## Открытые вопросы

- **Как определять подчинённость регистратору?** Сегодня признака в метаданных
  нет: `metadata.InfoRegister` (`types.go:373`) — это `Periodic`, `Dimensions`,
  `Resources`. Варианты: явный ключ `recorder: true` в YAML (честно, но требует
  правки существующих конфигураций); вывод по факту наличия движений (хрупко:
  пустой регистр выглядит независимым); запрет смешивания на уровне `check`.
  Рекомендация — явный ключ с умолчанием «независимый», потому что молчаливый
  вывод здесь ошибается в опасную сторону.
- Нужен ли `НаборЗаписей` в 119A, или одиночного менеджера хватает? По заявке —
  хватает, но лог обмена (13 регистров) просит пакетную запись.
- `Записать(Замещать)` — второй аргумент 1С. Поддерживать или всегда замещать?
- Читать регистр из DSL объектом (а не запросом) — надо ли? `СрезПоследних`
  уже есть в языке запросов; дублирование в объектной модели даст второй путь
  чтения со своими масками.

## Не делаем сейчас

- Виртуальные таблицы регистра сведений в объектной модели DSL (есть в запросах).
- Программную запись регистров **накопления** мимо проведения — там регистратор
  обязателен по построению, и правильный ответ уже дан в #743/PR #746.
- Редактор регистров сведений в конфигураторе сверх существующего.
