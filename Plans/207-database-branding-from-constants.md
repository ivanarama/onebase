# Этап 207 — Представление базы из строковых констант

## Контекст и решение

Ведущая заявка: [#2331](https://github.com/ivanarama/onebase/issues/2331).
Одна конфигурация обслуживает несколько баз кооперативов. Пользователь должен
видеть название именно своей базы в общей шапке и заголовке браузера, менять
его данными и сохранять открытые формы при обновлении оформления.

Выбран **вариант 1** канонического триажа `6364169193`; границы первой поставки
уточнены доверенным решением владельца
[6373613310](https://github.com/ivanarama/onebase/issues/2331#issuecomment-6373613310).
Составное название вычисляет прикладной DSL и записывает в явно выбранную
строковую константу. Платформа читает готовые название и эмодзи. Произвольный
`name_expr`, выполнение DSL при рендере и граф зависимостей не вводятся.

Это технический план, а не реализация. План-PR меняет только `Plans/`;
слияние плана не закрывает #2331. Возможность готова после срезов A–C ниже.
Дополнительная подпись, favicon, акцент, маркер тестовой базы и редактор с
предпросмотром относятся к отдельной следующей поставке и не блокируют #2331.

## Синтаксис / YAML и наблюдаемая семантика

Предлагаемый контракт `config/app.yaml`:

```yaml
name: Контроллинг                 # статическое имя приложения и fallback
logo: assets/logo.png             # существующий необязательный путь
branding:
  name_constant: ЗаголовокБазы
  icon_constant: ЗначокБазы
  icon_mode: emoji                # legacy (по умолчанию) | emoji | logo
```

`name_constant` и `icon_constant` — имена уже объявленных констант типа `string`,
а не выражения, пути к объектам или произвольные имена из HTTP-запроса.
`name_constant` можно задать отдельно. `icon_constant` разрешён только для
`icon_mode: emoji`; этот режим требует имя константы. `logo` требует заданный
статический `logo:`. Неизвестный mode, отсутствующая декларация и другой тип —
понятная ошибка `onebase check` с путём ключа. Разрешение имён следует
регистронезависимой семантике метаданных, чтение использует каноничное имя.
Отсутствие блока и пустой `{}` эквивалентны прежнему поведению. Некорректная
конфигурация, загруженная в обход check, не ломает страницу: resolver отключает
некорректную часть и использует fallback, выдавая диагностический код без данных.

Прикладной пример:

```text
Константы.ЗаголовокБазы = "СТ «Ромашка»";
Константы.ЗначокБазы = "🏡";
```

Обновлять оба значения согласованно прикладной код должен в одной транзакции.
Два отдельных autocommit — два самостоятельных состояния, промежуточное
представление допустимо. Сборку заголовка из enum/карточки кооператива и её
вызов из прикладных обработчиков реализует конфигурация, не runtime renderer.

### Инварианты имени и значка

- Название — строка: TrimSpace, затем от 1 до 160 Unicode code points.
  Нестроковое значение, `NULL`, пустота, превышение лимита, управляющие символы,
  разделители строк U+2028/U+2029 и bidi override/isolate означают fallback.
  Не приводить число/объект к строке и не обрезать ошибочное значение молча.
  Обычные `<`, `>`, кавычки и `&` в названии допустимы как **текст**.
- Статический fallback имени — прежний `name`, а при его пустоте `onebase`.
  Ошибка чтения БД приводит к fallback обоих динамических значений без 500.
- Значок — короткая строка символов, предназначенная для эмодзи: 1–16 code
  points и максимум 64 UTF-8 байта после TrimSpace; разрешены базовые символы
  Unicode `So`, модификаторы emoji U+1F3FB–U+1F3FF, VS16 U+FE0F и ZWJ U+200D.
  Первый/последний элемент не ZWJ; ZWJ соединяет базовые символы с их
  модификаторами; VS16/модификатор идут только после базового символа;
  одиночные модификаторы и разорванные соединения отвергаются.
  Это ограниченный символьный формат, не обещание поддержки каждого emoji
  стандарта: keycap с ASCII-цифрами в v1 не поддержан. 🏡, 🚗, флаги из пары
  региональных символов и ZWJ-семейство поддержаны. HTML, URL, произвольные
  буквы, controls и bidi запрещены. Ошибка — стандартный значок, не HTML.
- Проверки выполняются сервером; начальный HTML использует `html/template`,
  live patch — `textContent` и `document.title`, никогда `innerHTML` или
  `template.HTML`. URL картинки остаётся фиксированным `/ui/logo`.

| Настройка | Значок в шапке |
|---|---|
| Блока нет либо mode `legacy` | Точное прежнее поведение: logo при наличии, затем ⚡ |
| mode `emoji`, константа корректна | Только эмодзи вместо logo/⚡ |
| mode `emoji`, значение пусто/ошибочно/недоступно | Прежний logo при наличии и ⚡ |
| mode `logo`, настроенный файл доступен | Только logo, без ⚡ |
| mode `logo`, картинка не загрузилась | ⚡ через обработчик ошибки картинки без reload |

Отказ имени и отказ значка независимы, кроме общей ошибки чтения.
`<title>` содержит только разрешённое название, без эмодзи, как и раньше без
значка. Все обычные страницы и `/ui/app` используют один resolver. Заголовки
внутренних вкладок продолжают описывать открытый объект, а не имя базы.

### Доступ и отображение до входа

Явное указание констант в `branding` означает публикацию **только этих значений**
всем допущенным пользователям данной базы. Их нельзя использовать для секретов.
Обычный пользователь не получает права читать остальные константы и менять
их: `/ui/constants` сохраняет действующий admin-only контракт. Новое чтение
не вызывает `ListConstants` и не принимает имён констант в query/body.

До входа, на login/2FA challenge, при истёкшей сессии и на служебных публичных
страницах показывается статическое оформление, без чтения выбранных данных и
без branding-подписки. Успешная аутентификация включает динамическое
представление. База без пользователей с явным open-access считается доступной:
оформление видно, как и остальные данные UI. Проверять `auth.UserFromContext`
или подтверждённый `auth.OpenAccessFromContext`, не просто отсутствие user.

Новый `GET /ui/branding` монтируется в той же защищённой группе, что SSE.
Ответ — только `{name, icon, mode, logo}` с результатом resolver, включая fallback;
`Cache-Control: no-store`, JSON content type, без значений других констант,
DSN и внутренних имён. Неавторизованный ответ/redirect клиент не применяет как
JSON и сбрасывает динамический chrome к исходному статическому fallback.

## Хранилище / SQL, commit и изоляция

Схема `_constants` не меняется, миграции пользовательских данных нет. Новое
`DB.GetConstants(ctx, names []string)` читает максимум два настроенных имени
одним параметризованным SELECT. Один statement даёт согласованный снимок пары
на SQLite и PostgreSQL. Отсутствующие строки считаются пустыми. Чтение при
каждом полном HTTP-рендере и live GET — без кэша; при отсутствии динамических
настроек новых SQL-запросов нет. Сбой best-effort чтения внутри существующей
транзакции изолируется savepoint по принятому storage-паттерну, чтобы fallback
не переводил PostgreSQL-транзакцию в aborted.

Предлагаемые новые границы API, названия уточняются в реализации без изменения
контракта:

```go
// storage, callbacks получают только имя, не значение; unsubscribe идемпотентен.
func (db *DB) SubscribeConstantCommits(fn func(name string)) (unsubscribe func())
func (db *DB) GetConstants(ctx context.Context, names []string) (map[string]any, error)
// interpreter: источник записи не связан с reference presentation.
func (r *ConstantsRoot) WithWriteCtxSource(src CtxSource) *ConstantsRoot
// ui: отдельное immutable значение на запрос, не обновление s.cfg.
type DatabaseBranding struct { Name, Icon, Mode string; Logo bool }
func (s *Server) resolveDatabaseBranding(ctx context.Context) DatabaseBranding
```

`SetConstant` после успешного Exec регистрирует value-free callback через
`DeferUntilTxCommit`; если транзакции нет, вызывает его после завершённого
успешного autocommit. Неуспешный Exec, outer rollback и rollback savepoint не
публикуют событие. RELEASE savepoint переносит callback во внешний scope,
а не публикует досрочно. Callback выполняется после освобождения транзакции,
не читает БД и не задерживает успешную запись ожиданием браузера. Неоднозначная
ошибка commit не считается доказанным успехом: событие не публикуется,
актуальное committed состояние восстанавливается fresh read.

DSL `ConstantsRoot.Set` берёт **текущий** `CtxSource.Ctx()` непосредственно
перед записью. При отсутствии источника сохраняется статический контекст для
старых callers. `Common.Build` подключает его для всех типов констант, даже
без reference presenter. После записи локальный cache сохраняет read-your-writes;
rollback hooks восстанавливают предыдущее cache-значение в обратном порядке
для каждого savepoint. Публичный тест обязан начать транзакцию уже **после**
построения DSL окружения: тест только с заранее транзакционным ctx не ловит
текущий разрыв. Проверить явную и заимствованную из entityservice транзакции,
вложенный rollback и незакрытую транзакцию при завершении исполнения.

Server подписывается на конкретный `*storage.DB`, фильтрует настроенные имена и
публикует в **свой** Hub событие `Event{System: "database-branding-changed"}`.
Событие не несёт значения, имена и права; при закрытии Server подписка снимается.
Список observers синхронизирован; callback вызывается вне mutex. Повторные
уведомления допустимы, клиент объединяет их. Ни общего mutable AppName, ни
глобального cache/observer между базами нет. Одинаковый YAML у баз A/B не
создаёт общей identity, данные и уведомления B не попадают в A.

Hub внутрипроцессный. Запись через `procrun`, отдельный worker или другой
`*storage.DB` видна в БД, но не может магически попасть в этот Hub. Поэтому
для полной поддержки DSL в первой поставке обязателен резервный fresh GET:
раз в 30 секунд в видимом верхнем окне, немедленно при `visibilitychange`
на visible, `pageshow` и восстановлении сети. Это сверка состояния, не кэш.
Прямой SQL вне API не получает немедленного события, но тоже обнаруживается
сверкой. Гарантия для видимого окна при доступном сервере — следующий успешный
GET, для отдельного процесса обычно до 30 секунд; фоновые окна ограничены
throttling браузера и догоняют при активации. Мгновенная межпроцессная доставка
потребовала бы отдельного брокера и не заявляется этой поставкой.

## Открытые окна, reconnect и безопасность live patch

1. Initial HTML получает resolver в `render`. Без новых настроек JS не
   включает запросы branding. Shell и самостоятельная страница имеют одинаковый
   chrome contract; скрытые chrome iframe не создают собственные SSE или polling.
2. Каждый `EventSource.onopen`, включая **первый**, инициирует fresh GET:
   это закрывает окно между SSR и установкой подписки. Служебный system-frame
   вызывает тот же refresh независимо от Dev mode, не `location.reload()`.
3. `System` проверяется отдельно от обычного `Name`: DSL
   `ОтправитьУведомление` с похожим именем не может подделать system-frame.
   Переиспользовать существующий SSE; не создавать второй поток. Для branding
   не добавлять доверие к произвольным `window CustomEvent`/postMessage.
4. В одном верхнем окне только один in-flight GET. Событие в процессе чтения
   ставит dirty; после завершения идёт ещё один GET. Старый ответ не может
   перезаписать более новый параллельный; повторные кадры объединяются.
   После transient network error — bounded backoff 1–30 секунд, с отменой
   таймера при pagehide и повторной сверкой после восстановления.
5. Менять только текст названия, узел значка/logo и `document.title`.
   Не менять контейнер `main`, iframe `src`, tab storage, active tab, DOM формы,
   focus, dirty state и несохранённые значения. В iframe не пересылать новый
   доверенный system-frame через существующий канал обычных DSL notifications.
6. При истечении сессии динамический chrome очищается до статического;
   новый пользователь получает собственный fresh read после входа. При смене
   базы навигацией никакой persisted branding из local/sessionStorage не
   используется. Внутренние labels вкладок объектов остаются прежними.

Отсутствующий EventSource не ломает страницу: работает initial render и
резервная сверка. Серверная ошибка чтения возвращает безопасный fallback;
сетевой сбой оставляет последнее подтверждённое оформление до retry, кроме
отказа авторизации. Логи содержат только код причины/настройку, не значение.

## Последовательность небольших PR-срезов и публичные тесты

### A. Начальный рендер из констант и корректная DSL-запись — 3–4 дня

- `project.AppConfig`, `configcheck` и `run`/`dev`: новая настройка, проверка
  имён/типов/mode; единый mapper. Проверить конфигурацию из каталога и БД.
- Storage: узкий SELECT; DSL setter: живой контекст и rollback cache.
- UI: request-scoped resolver, head/nav, `/ui/branding`, fallback и доступ.
  Общее статическое имя приложения не менять. Live promises в документации
  этого среза ещё не заявлять; #2331 не закрывать.
- Публичная приёмка: CLI `onebase check --project <fixture>` принимает валидный
  YAML и диагностирует ошибочные ссылки/тип/mode. Через собранный `onebase run`
  открыть `/ui/`, `/ui/app`, самостоятельный список/форму; изменить константы
  admin POST `/ui/constants` и обработкой DSL через штатную кнопку UI;
  следующий GET видит новый заголовок. Проверить no-settings HTML, 2FA issuer,
  OpenAPI title и «О программе» против прежнего статического имени.
- Матрица SQLite/PostgreSQL: обработка с явными Begin/Commit/Rollback,
  savepoint rollback, read-after-write и запуск без транзакции. Окружение
  создаётся до Begin. Проверить БД и HTTP GET после результата; для заимствованной
  транзакции запускать хук записи документа через публичный путь, не setter.
- Проверки: `go test ./internal/project ./internal/configcheck ./internal/dslvars
  ./internal/dsl/interpreter ./internal/ui`, затронутые storage-тесты;
  `go build ./...`. Интеграционная часть требует `TEST_DATABASE_URL`,
  отсутствие PostgreSQL не считать выполненной матрицей.

### B. Commit → существующий SSE → точечное обновление — 2–3 дня

- Storage observer на `SetConstant`; регистрация/освобождение в Server;
  system-frame в `handlers_events.go`; client dispatcher и serial refresh
  в `ui.js`. Никаких значений в событиях и публикаций до commit.
- Публичная матрица на двух СУБД: две авторизованные сессии открывают
  `/ui/app` и отдельную страницу, подписываются `/ui/events`; admin меняет
  константы через форму и DSL-обработку. До внешнего commit нет события
  и нового представления; после commit есть сигнал и GET показывает значения.

## Совместимость, миграция, риски и откат

Новых таблиц/колонок и переименований нет. Новые константы создаёт прикладная
конфигурация обычным механизмом метаданных/migrate; существующие значения не
изменяются автоматически. Upgrade без `branding` сохраняет прежнюю шапку.
При downgrade сначала убрать новый блок из конфигурации: старый check может
его диагностировать как неизвестный; удалять данные констант не требуется.

| Риск | Ограничение и проверка | Откат |
|---|---|---|
| Секрет попал в общую шапку | Явный allowlist настроенных констант, только авторизованные/open-access, документация публикации; отрицательные HTTP-тесты | Убрать ссылки из YAML, очистить ошибочно опубликованные данные обычным администрированием |
| Преждевременный сигнал/выход DSL из tx | Live CtxSource и готовые outer/savepoint hooks; публичная двухдиалектная матрица | Откатить соответствующий срез; отключить branding, не переписывать `_constants` |
| Пропуск SSE, отдельный процесс, crash после commit | GET на каждом open/активации и 30-секундная сверка | Initial render остаётся рабочим, данные сохранены |
| Перемешивание базы/устаревшие ответы | Store-scoped observers, отдельный Hub, no-store/no persistence, serial dirty refresh | Отключить новую настройку и подписку |
| Лишние SQL/GET и burst | Один SELECT максимум двух имён; zero reads без настройки; debounce/single-flight; измерение на двух базах | Вернуться к статическому представлению, cache в v1 не добавлять |
| XSS, подделка кадра, сломанная картинка | Template escaping/textContent, символный формат, server-only System, фиксированный logo route | Fallback к legacy, без HTML из данных |
| Подмена issuer/служебного имени | Отдельный DatabaseBranding, неизменный cfg.AppName; тесты 2FA/OpenAPI | Убрать branding; статические потребители уже сохранены |

Расширение второй поставки добавляет поля к отдельному DTO/блоку `branding`,
а не перегружает AppName. Favicon/акцент потребуют собственной проверки URL/CSS
и доступа; они не возвращаются недоказанными полями первой версии. План не
создаёт автоматически issue второй поставки и не авторизует её реализацию.
