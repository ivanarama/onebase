# План 170 — зависимый отбор в подборе ссылочных полей

Дата проектирования: 2026-09-09.
Статус: 📋 **проектирование**, продуктовый код в этом PR не меняется.
Заявка: [#1303](https://github.com/ivanarama/onebase/issues/1303).
Выбранный вариант: **1** — после отдельного плана реализовать ограниченный
декларативный набор `eq`, `in_hierarchy` и служебный признак `is_folder`
проверяемыми срезами; произвольный DSL в подборе не выполнять.

Открытый PR [#1408](https://github.com/ivanarama/onebase/pull/1408) остаётся
прототипом на `hold` и не заменяет этот план. Из него можно перенести идеи
серверной первой отрисовки, общего фильтра для выдачи и счётчика и обновления
зависимого `<select>`, но не его расширение объёма до подчинённых справочников:
это не требуется выбранным вариантом, а прототип реализует только равенство и
не защищает обновление списка от устаревших ответов.

## Контекст

Ссылочный picker управляемой формы сейчас знает только целевой справочник,
поисковую строку и пагинацию. `GET /ui/_ref-options/{entity}` передаёт их в
`referenceOptionsPage`, а тот независимо вызывает `List` и `CountList`. Форма
не может выразить «неисправности текущего направления», поэтому оператор видит
весь справочник и различает одинаковые представления только по искусственно
денормализованной подписи.

Для сценария #1303 одного равенства недостаточно. Поле `Направление` выбранной
неисправности должно ссылаться на текущую группу или любого её потомка, а сами
группы не должны быть вариантами выбора. Нужен небольшой статический контракт,
который `onebase check` проверяет до запуска, а сервер переводит в параметризованный
SQL одинаково для SQLite и PostgreSQL.

## Объём и нецели

В объём входят managed-формы сущностей, ссылочные поля объекта и ссылочные
реквизиты формы, первая серверная отрисовка, диалог подбора, обновление при
смене ведущего поля, `List`/`CountList`, конфигуратор форм и документация.

В первый контракт не входят:

- произвольные выражения, процедуры формы, `OR`, отрицание и пользовательский SQL;
- фильтры колонок табличной части: им нужен отдельный row-local контекст;
- автоматическое объявление владельца/подчинения справочника и импорт `Owners`
  из 1С — это самостоятельная возможность из прототипа #1408;
- проверка значения при сохранении объекта. `choice_filter` ограничивает UX
  выбора, но не является бизнес-валидацией или правом доступа;
- изменение обычных фильтров списков, REST API v2 и языка запросов.

## Публичный YAML-контракт

`choice_filter` — упорядоченный список из 1–8 условий у элемента
`kind: ПолеВвода`, который через `data_path` выбирает ссылку на справочник.
Условия соединяются только через `AND`:

```yaml
- id: ЗаявленнаяНеисправность
  kind: ПолеВвода
  data_path: Объект.ЗаявленнаяНеисправность
  choice_filter:
    - field: Направление
      op: in_hierarchy
      from: Объект.Направление
    - field: is_folder
      op: eq
      value: false
```

Простая связь двух справочников использует тот же формат:

```yaml
choice_filter:
  - field: Контрагент
    op: eq
    from: Объект.Контрагент
```

Правила версии 1:

1. `field` — реквизит **выбираемого** справочника. Единственное служебное поле
   — `is_folder`, доступное только у иерархического справочника.
2. Ровно одно из `from` и `value` обязательно. `from` имеет явный префикс
   `Объект.` или `Форма.`; bare-имена и более глубокие пути отклоняются, чтобы
   источник нельзя было неоднозначно переинтерпретировать в будущем.
3. `eq` с `from` в первом срезе сравнивает ссылочные реквизиты, причём обе
   стороны обязаны ссылаться на один вид объекта. Литерал разрешён только как
   boolean `value` для `is_folder`; строки и UUID-константы пока не входят в API.
4. `in_hierarchy` требует `from`, ссылочный `field` и иерархический справочник,
   на который одинаково ссылаются `field` и источник. Корень входит в поддерево.
5. Для элемента с `choice_filter` обязателен непустой уникальный `id`. Он, имя
   формы и сущность-хозяин образуют серверную идентичность контракта; `data_path`
   и переведённый заголовок такой идентичностью не являются.
6. Неизвестный ключ YAML, оператор, дублирующийся `field`, несовместимый тип,
   отсутствующий источник/цель, `in_hierarchy` по неиерархическому справочнику
   или фильтр на нессылочном поле дают блокирующую ошибку `onebase check` с кодом
   `form.choice-filter` и точным путём формы/элемента.

Структуры контракта (`FormChoiceCondition`, enum операторов) должны быть
типизированными полями `metadata.FormElement`, а не значениями `Props`. Это
делает YAML round-trip и `onebase schema form` частью компилируемого API.

## Наблюдаемая семантика и инварианты

### Фильтрация

1. Все условия `choice_filter`, поиск, исключение папок режима picker и RLS
   соединяются через `AND`. Отбор не ослабляет и не заменяет RLS.
2. Один и тот же собранный предикат применяется к выдаче и `CountList`; `total`
   всегда относится к отфильтрованному набору до `limit/offset`.
3. Пустой динамический источник даёт пустую выдачу (`items: [], total: 0`), а
   не полный справочник. Это fail-closed UX: сначала выбирают направление.
4. `eq` использует типизированное параметризованное сравнение. Некорректный UUID
   не превращается в строковый SQL и не расширяет выборку.
5. `in_hierarchy` включает корень и всех потомков по `parent_id`. Несуществующий
   корень даёт пустой результат. Рекурсивный CTE использует `UNION`, а не
   `UNION ALL`, поэтому ошибочный цикл в данных завершается и не дублирует строки.
6. `is_folder: false` исключает группы; `true` оставляет только группы. Условие
   допустимо только для иерархической целевой сущности.

### Серверная первая отрисовка

Первая HTML-отрисовка собирает фильтр из серверных значений `Объект.*` и
`Форма.*`, а не сначала показывает общий список. Новый объект с пустым источником
получает только пустой option. Существующее выбранное значение вне актуального
фильтра остаётся видимым и выбранным с машинным признаком
`data-ob-choice-outside-filter="1"`: простое открытие/сохранение формы не должно
молча стереть старые данные. В picker это значение кандидатом не считается.

После изменения источника текущий выбор сохраняется, если он присутствует в
последнем подтверждённом наборе; иначе очищается с обычным `change`-событием.
Так сохранение старой записи безопасно, а смена направления не оставляет
невидимую несовместимую ссылку.

### Trust boundary HTTP

Браузер передаёт идентичность формы/элемента и только карту текущих значений
объявленных `from`. Он **не** передаёт доверенные `field`, `op` или SQL-фрагмент.
`refOptionsJSON` заново находит форму в registry, элемент по стабильному `id`,
проверяет, что route `{entity}` совпадает с целевой ссылкой элемента, и строит
условия из серверных метаданных. Запрос без form-контекста сохраняет нынешнее
нефильтрованное поведение для старых/autogen picker-ов.

Неизвестный контекст, лишний источник или несовпадение целевой сущности дают
`400`; отсутствие значения известного источника — корректную пустую страницу.
Действующие проверки `can(..., read)`, `rowFilterFor`, маскирование и максимальный
limit остаются обязательными. Отбор не является авторизацией: прямой POST формы
и другие API должны опираться на RLS и бизнес-валидацию, а не на `choice_filter`.

### Защита от гонок в браузере

У каждого зависимого `<select>` свой монотонный номер запроса и
`AbortController`, когда он доступен. Перед fetch фиксируется fingerprint всех
его источников. Ответ применяется только если одновременно совпали номер,
fingerprint и живой DOM-элемент; более старый ответ не может вернуть варианты
предыдущего направления или очистить новый выбор. Тот же fingerprint добавляется
к уже существующему `requestSeq` диалога picker. Ошибка сети сохраняет текущий
выбор и показывает состояние ошибки, но не откатывается к локальному полному
списку: такой fallback обходил бы объявленный фильтр.

|---|---|---|

| `internal/configcheck/full.go`, новый узкий checker | нет проверки связей выбора | blocking-проверка цели, источника, типов, operator и стабильного `id` |
| `internal/storage/crud.go` | `Filters` умеет равенство, folder scope и `List`/`CountList` собирают условия раздельно | отдельные trusted choice predicates и общий builder WHERE для обоих запросов |
| `internal/storage/predicate.go` | структурные RLS-предикаты знают `eq/in`, но не иерархию | переиспользовать разрешение полей/типов; не расширять публичную RLS-грамматику без необходимости |
| новый файл `internal/storage/choice_filter.go` | отсутствует | компиляция `eq`, `is_folder` и cycle-safe `in_hierarchy` для SQLite/PostgreSQL |
| `internal/ui/handlers.go` | initial/page helpers знают только search/pagination | единый helper фильтрованной первой страницы и идентичный count |
| `internal/ui/handlers_entity.go` | endpoint доверяет только entity/q/limit/offset | разрешение form+element на сервере и разбор только значений источников |
| `internal/ui/templates_managed.go` и render context | `<select>` несёт только `data-ref-entity` | стабильная identity, source descriptors, filtered initial options и outside-filter marker |
| `internal/ui/static/ui.js` | picker имеет sequence только для поиска; зависимого refresh нет | refresh по источникам, abort+sequence+fingerprint, без полного fallback |
| `internal/launcher/forms_*` | конструктор не знает новое поле | редактирование и byte-semantic round-trip списка условий без потери порядка |
| `docs/forms.md`, `onebase schema form` | ключ не описан | контракт, ограничения, пример #1303 и оговорка «не авторизация» |

Табличные части намеренно отсутствуют в таблице: их DOM имена индексированы по
строке, а серверная первая отрисовка требует иной identity. Их нельзя добавить
случайным обобщением `dpFieldName`, которое сейчас просто берёт сегмент после
последней точки.

## Совместимость и миграция

- Все поля новые и optional. Без `choice_filter` HTML, endpoint и SQL остаются
  прежними; миграции схемы БД нет.
- YAML с новым ключом требует версии OneBase, реализующей план; старый бинарник
  не должен молча отбросить его при сохранении через конфигуратор.
- Порядок условий сохраняется при load/save, хотя SQL-семантика — AND. Это даёт
  стабильный diff и предсказуемые сообщения `check`.
- Существующие значения вне фильтра не переписываются при миграции и видимы при
  первой отрисовке. Новое ограничение действует только на дальнейший выбор.
- API `/ui/_ref-options/{entity}` остаётся совместимым: старые параметры и JSON
  ответа не меняются; новый контекст opt-in.
- SQLite и PostgreSQL получают одинаковую семантику. Никакого client-side
  обхода дерева и предварительной выгрузки всех UUID нет.

## Последовательность небольших PR-срезов

### Срез A — типизированный контракт и storage (~2 дня)

Добавить структуры metadata/check и внутренний `ChoicePredicate` для
`ListParams`. Вынести общий сборщик WHERE, которым пользуются `List` и
`CountList`, реализовать параметризованные `eq`, `is_folder` и рекурсивный
`in_hierarchy`. UI пока не посылает предикат.

Публичные тесты среза:

- временный проект проходит `onebase check` с обоими примерами и получает
  `form.choice-filter` для каждого нарушенного правила;
- `dbtest.ForEachDialect` вызывает публичные `DB.List` и `DB.CountList` на дереве
  глубины 3: корень включён, соседняя ветка исключена, группы отбрасываются,
  `total == len` без pagination и остаётся полным при `limit`;
- отдельный матричный случай с циклом завершается без дублей, а неизвестный root
  возвращает ноль.

### Срез B — server-authoritative picker и первая отрисовка (~2–3 дня)

Разрешать form/element в registry, собирать filter из серверных метаданных и
значений источников, применять его в initial options и JSON endpoint. Добавить
render context и машинные data-атрибуты, но не автоматический refresh.

Публичные тесты среза:

- HTTP-тест через настоящий маршрут `/ui/_ref-options/{entity}` доказывает AND
  с поиском и RLS, одинаковый `total`, пустой source и `400` для подменённых
  entity/element/лишнего source;
- render-тест настоящей managed-формы проверяет, что первая HTML-страница не
  содержит чужую ветку, а сохранённое legacy-значение снаружи фильтра показано
  ровно один раз с marker;
- запрос без нового контекста повторяет старый ответ — compatibility regression.

### Срез C — live refresh, конфигуратор и документация (~2–3 дня)

Добавить refresh зависимых select/picker с abort+sequence+fingerprint, редактор
списка условий в конструктор форм, `docs/forms.md`, схему и небольшой пример
конфигурации. После этого feature считается доступной пользователю.

Публичные тесты среза:

- Playwright меняет источник A→B при искусственно задержанном ответе A и
  проверяет, что список/выбор остаются для B; сетевой отказ не показывает
  локальный полный список;
- Playwright открывает существующую запись с out-of-filter значением, сохраняет
  без изменений, затем меняет источник и видит очистку только после актуального
  ответа с `change`;
- launcher round-trip создаёт условия мышью, сохраняет форму, перечитывает YAML
  и получает тот же порядок/типы; `onebase schema form` содержит новый ключ;
- `onebase check --project <fixture>` и e2e сценарий #1303 выбирают только листья
  текущего направления и его потомков.

Каждый срез проходит `go test` затронутых пакетов; после среза C дополнительно
`go test ./internal/...`, штатный e2e job и `onebase check` на изменённом примере.

## Риски и меры

| Риск | Мера |
|---|---|
| клиент подменяет поле/operator | сервер восстанавливает контракт по form+element; клиент шлёт только значения source |
| RLS теряется при новом builder | отдельный AND-инвариант и HTTP-тест с запрещённой строкой |
| `List` и `CountList` расходятся | один WHERE builder и тест pagination/total на двух диалектах |
| рекурсивный CTE зависает на цикле | `UNION` с dedupe и матричный cycle-test |
| медленное дерево | индекс `parent_id` уже часть иерархии; inspect query plan на 1.5k/50k узлов, без client expansion |
| поздний ответ возвращает старый список | per-select abort, sequence и source fingerprint |
| открытие старой записи стирает ссылку | selected legacy option сохраняется только на первой render и явно маркируется |
| feature принимают за контроль доступа | docs и код разделяют choice predicate, RLS и save-validation |
| прототип расширяет scope | переносить коммиты выборочно; owner/import/configurator entity changes не входят |

## Откат

До использования конфигурациями код откатывается удалением optional metadata и
UI/storage веток без миграции. После использования сначала удалить
`choice_filter` из форм и прогнать `onebase check`, затем откатывать бинарник:
старый конфигуратор не должен сохранять незнакомый ключ. Данные не мигрируют;
out-of-filter ссылки остаются исходными. При регрессии live refresh можно
отключить клиентскую реакцию на change, сохранив серверно отфильтрованные initial
options и picker — trust boundary и RLS при этом не ослабляются.

## Критерии завершения и verification

План завершён, когда:

1. оба YAML-примера проходят `onebase check`, а все неверные комбинации дают
   детерминированный `form.choice-filter`;
2. первая отрисовка, picker и `total` показывают только строки, удовлетворяющие
   AND из `eq`/`in_hierarchy`/`is_folder`, поиска и RLS;
3. SQLite и PostgreSQL проходят одну matrix suite, включая root, descendants,
   sibling, missing root и cycle;
4. A→B→A с переставленными ответами не применяет stale response и не очищает
   актуальный выбор;
5. legacy out-of-filter значение видно при открытии и не теряется от обычного
   save, но очищается после осознанной смены источника, если больше недопустимо;
6. конфигуратор round-trip и `onebase schema form` сохраняют публичный контракт;
7. #1408 перерезан по плану либо закрыт в пользу новых срезов; owner/import
   изменения не попали в реализацию #1303 «заодно».

Ручная проверка повторяет исходный сценарий: в дереве из 35 направлений и 1411
неисправностей выбрать направление, открыть picker, увидеть только листья его
поддерева, найти «-», быстро сменить направление во время загрузки и убедиться,
что поздний ответ старого направления не появился.

Оценка: **6–8 дней** на три среза, включая matrix/e2e и конфигуратор; ещё
0.5–1 день на проверку query plan и browser race под искусственной задержкой.
