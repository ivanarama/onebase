# План 159 — местное время без зоны (календарная дата и стенные часы)

## Контекст

Две заявки об одном и том же, с разных сторон:

- [#1167](https://github.com/ivanarama/onebase/issues/1167) (`scadapy`,
  PostgreSQL): почасовой ряд залит ETL со смещением `+00`, а OneBase показывает
  время на три часа больше. `ALTER … TYPE timestamp without time zone` не
  помогает.
- [#1169](https://github.com/ivanarama/onebase/issues/1169): у даты рождения и
  даты приказа не нужно время — ни в интерфейсе, ни в хранении; предложен флаг
  `time: false` на элементе формы.

Корень общий: **в платформе есть ровно один тип `Дата`, и это момент времени.**
На PostgreSQL реквизит создаётся как `TIMESTAMPTZ`
(`internal/storage/dialect.go:100`, через `fieldType` в
`internal/storage/ddl.go:19`), на SQLite — ISO-текст в UTC. Показ приводится к
зоне процесса: `fmtDateValue` (`internal/ui/templates.go:118`) делает
`t.In(time.Local)`, ввод разбирается `ParseInLocation(…, time.Local)`
(`internal/ui/form_attr_values.go:48`, `handlers_entity.go:541`).

Круг замкнут и **сам по себе непротиворечив**: что записано через форму, то и
прочитано. Приведение к местной зоне сделано намеренно — без него на хосте со
смещением съезжал календарный день (#1071, #1076). Ломается круг там, где
значение приходит не из формы:

- заливка ETL/SQL со своим смещением (#1167);
- перенос базы между зонами;
- значение, у которого времени нет по смыслу (#1169) — «14.03.1985» это не
  момент, а календарный день, и приводить его к зоне не к чему.

### Решение и почему такое

Разбор развилки — в комментариях к обеим заявкам. Нумерация в таблице ниже — по
разбору #1167; в разборе #1169 то же решение стоит под номером **3** (вариант 2
там — флаг `time: false` на элементе формы, то есть другой подход целиком).
Рассматривались три варианта:

| | Что делаем | Цена |
|---|---|---|
| 1 | Ничего; ответить «грузите в зоне сервера» | ноль, но класс задач «дата без времени» остаётся нерешаемым |
| 2 | **Новый тип поля «местное время без зоны», существующий `Дата` не трогаем** | новый тип через все слои; старые базы не шевелятся, откат — коммитом |
| 3 | Переключить сам `Дата` на стенные часы | миграция всех баз и перетрактовка уже записанных значений; откат — только из бэкапа |

**Делаем 2.** Вариант 3 отвергнут не по объёму, а по необратимости: он молча
меняет смысл уже записанных данных у пользователей, а данные, в отличие от кода,
коммитом не откатываются.

Важная поправка к тому, как вариант 2 был сформулирован в разборе #1167:
тип — **не «дата без времени», а «местное время без зоны»**. Чистый `DATE` не
удержит почасовой ряд из #1167, где значение несёт час суток. Точность
объявляется отдельно и покрывает оба случая.

## Синтаксис (что делает пользователь)

```yaml
fields:
  - name: ДатаРождения
    type: localdate                 # точность по умолчанию — день
  - name: ДатаВремяЗначения
    type: localdate
    precision: second               # день + час/минута/секунда, без зоны
```

Семантика одной фразой: **что записано, то и показано, на любом хосте и в любой
зоне.** Ни запись, ни чтение, ни показ не приводят значение к зоне процесса.

Существующий `type: date` не меняется вовсе: это по-прежнему момент времени
(`TIMESTAMPTZ`), и все написанные конфигурации работают как раньше.

### Спорное место — имя типа

`localdate` выбрано за то, что оно не врёт при `precision: second` (в отличие от
`dateonly`) и стоит в одном ряду с существующими английскими значениями
(`string`, `date`, `number`, `bool`, `richtext`, `image`). Альтернативы, которые
рассматривались и отклонены: `walltime` (непрозрачно для не-англоязычного
конфигуратора), `plaindate` (не покрывает `second`), `date_local` (единственное
значение с подчёркиванием во всём наборе).

**Имя — предмет решения человека до начала среза 1**: после выхода оно попадёт
в чужие конфигурации и станет неизменяемым.

## Хранилище / SQL

| Точность | PostgreSQL | SQLite |
|---|---|---|
| `day` (по умолчанию) | `DATE` | `TEXT`, `YYYY-MM-DD` |
| `second` | `timestamp without time zone` | `TEXT`, `YYYY-MM-DDTHH:MM:SS` |

Миграции существующих баз нет: тип новый, старые колонки не трогаются. Ретайп
`date` → `localdate` в этом плане **не поддерживается** и должен отвергаться на
`onebase check` с внятным текстом: перетрактовка уже записанных моментов — это
как раз вариант 3, от которого отказались. Молчаливый ретайп в этом репозитории
уже однажды портил данные (#607), повторять нельзя.

## Изменения в коде

Осей две, и они независимы: новая **константа типа поля** в метаданных и новый
**тип значения** в Go. Ниже они разведены намеренно — места ищутся у них
одинаково (руками), а спасают они от разного.

### Ось 1 — константа `FieldTypeLocalDate`

Её обязана увидеть каждая ветка по метаданным — `f.Type ==
metadata.FieldTypeDate` или `switch f.Type`. Таких мест на сегодня **52 в 30
файлах** (без тестов):

| Пакет | Мест | Чем занято |
|---|---|---|
| `internal/ui/` | 22 | показ, ввод, списки, отчёты, конструктор запросов |
| `internal/storage/` | 14 | DDL, чтение/запись, предикаты, нумератор (`numbering.go:55`), свёртка (`rollup.go:639`) |
| `internal/metadata/` | 4 | объявление константы, значения по умолчанию, подпись поля |
| `internal/exchange/` | 4 | сериализация в пакет обмена, регистр сведений |
| `internal/entityservice/` | 3 | период движений, значения по умолчанию |
| `internal/query/` | 2 | тип колонки результата |
| `api/v2.go:1187`, `configcheck/lint.go:2096`, `bench/bench.go:81` | по 1 | схема REST, валидация, бенч |

**Компилятор не поймает здесь ни одного места.** `FieldType` — строковый тип
(`internal/metadata/types.go:15`), проверки полноты `switch` в Go нет: новая
константа компилируется везде, а каждое неучтённое место молча уезжает в
`default`. `api/v2.go:1187` отдаст в схеме `{"type":"string"}` вместо
`{"format":"date-time"}`, `ui/field_display.go:37` — `fmtReportCell(v)` вместо
форматирования даты. Ни одна из этих веток не упадёт и не пожалуется.

Значит, ревизия — работа руками, и её нельзя срезать: `grep -rn FieldTypeDate`
по `internal/` и `cmd/` в начале каждого среза, разобранные места перечислены в
описании PR, каждое решение закрыто тестом.

### Ось 2 — отдельный тип значения (`metadata.LocalTime`)

Значения ходят между слоями как `any`, и разбираются утверждением типа:
`fmtDateValue(v any)` (`ui/templates.go:118`) и `fmtReportCell(v any)`
(`ui/widget_helpers.go:222`) типа поля не знают вовсе; `normalizeFieldValue(f,
v any)` (`storage/crud.go:556`) и `exchange/package.go:899` знают, но значение к
ним всё равно приходит как `any`. Обе группы делают `v.(time.Time)` и приводят
результат к местной зоне.

Поэтому `storage` сканирует новые колонки не в `time.Time`, а в отдельный тип
(рабочее имя `metadata.LocalTime`). Что это даёт:

- существующие ветки `case time.Time` продолжают работать с моментами и никакого
  `LocalTime` не видят;
- ветка приведения к зоне для нового типа недостижима: `In(time.Local)` не к
  чему применить;
- **пропущенное место ломается заметно, а не правдоподобно.** На общем
  `time.Time` забытая ветка покажет корректную на вид дату, сдвинутую на
  смещение пояса: ошибка выглядит как ответ, и заметить её можно только сверкой
  с исходным значением (#1071, #1076). С отдельным типом то же место дойдёт до
  `fmt.Sprintf("%v", v)` в хвосте `fmtDateValue` и напечатает структуру вместо
  даты — видно с первого взгляда и ловится первым же тестом.

Компилятор молчит и здесь: утверждение типа на `any` — не ошибка компиляции, а
несработавшая ветка. Тип не помогает **найти** места; он делает так, что
ненайденное не выдаёт себя за правильный ответ. Ищет по-прежнему grep из оси 1.

Цена: новый тип значения расходится по сигнатурам, и его приходится отдельно
учить сериализации — `exchange/package.go:899` и схема REST как раз про это.

## Срезы (по одному PR)

**Срез 1 — тип и хранилище.** Метаданные, `precision`, DDL обоих диалектов,
валидация на `onebase check`, отказ от ретайпа. Матричный тест
`dbtest.ForEachDialect`: колонка создаётся нужного типа, значение
записывается и читается без сдвига в пяти поясах (UTC, +03, −05, +05:45, +14).
Интерфейса ещё нет — поле доступно из DSL и REST.

**Срез 2 — чтение, запись, запросы.** `LocalTime` через `storage` → `query` →
`interpreter`. Части даты (`Год`/`День`/`Час`), `НачалоДня`, арифметика,
сравнение в запросах. Сюда же `internal/entityservice/`: период движений
(`SetPeriodFromFields`) и значения по умолчанию — без этого документ, у которого
дата объявлена новым типом, проводится с периодом `time.Now()`. Матричные тесты
на данных, а не на компиляции SQL.

**Срез 3 — формы и списки.** Показ и ввод в автоформах и управляемых формах,
точность управляет наличием часов и минут, `kind: ПолеДаты` для `day`.
**Закрывает #1169.**

**Срез 4 — периферия и обмен.** `internal/exchange/` (сериализация в пакет
обмена, регистр сведений), конвертер 1С, `describe`, `ai-guide`/`AGENTS.md`,
список типов в Конфигураторе, раздел в `DEVELOPER.md`, `docs/features.md`.
Последний PR закрывает обе заявки: `Fixes #1167`, `Fixes #1169`.

Порядок жёсткий: срез 2 без среза 1 бессмыслен, срез 3 без среза 2 покажет
пустоту. Срез 4 можно двигать, но не пропускать — иначе повторится #1177:
возможность есть, а найти её неоткуда.

## Тесты

- матричные (`dbtest.ForEachDialect`) на каждом срезе — правило CLAUDE.md
  «трогаешь семантику SQL — пиши матричный тест» здесь центральное: весь смысл
  типа в том, что PostgreSQL и SQLite ведут себя одинаково;
- пояс в тестах закрепляется явно (`time.FixedZone`), обе стороны сравнения —
  литералы. Тест, где ожидаемое значение строится через `time.Local` и
  сверяется со значением, полученным через `time.Local`, — тождество, зелёное в
  любом поясе; ровно на этом обжёгся PR #1170;
- отдельный тест на отказ ретайпа `date` → `localdate`;
- сквозной прогон через публичную точку входа: `migrate` → запись через REST →
  чтение запросом → показ на форме, при `TZ=America/New_York`.

## Эстимейт

Крупный. Срез 1 — 1–2 дня, срез 2 — 3–4 дня (самый рискованный: там же живут
`toTime`, запросы и период движений), срез 3 — 1–2 дня, срез 4 — 1–2 дня
(добавился обмен). Итого 6–10 рабочих дней, четыре PR.

Первая редакция плана обещала «около недели», но считала по заниженному вдвое
объёму (~26 мест вместо 52, без `exchange` и `entityservice`). После пересчёта
верхняя граница — две рабочие недели, а не одна.

## Что осталось за рамками

- **Ретайп `date` → `localdate`** и обратный. Нужна миграция данных с явным
  указанием, в какой зоне трактовать записанное; отдельный план.
- **Переключение самого `Дата`** (вариант 3) — не делаем, см. «Решение».
- **Предупреждение о дубле при вводе** и прочие вопросы форм из #1169, не
  связанные со временем.
- **`ТекущаяДата()` для нового типа**: сейчас возвращает момент. Нужна ли
  парная функция стенных часов — решать в срезе 2, по факту написанных модулей.
