# Этап 176 — Контекст записи и явный режим загрузки

## Контекст

План относится к issue #1435 и фиксирует выбранный в каноническом триаже
вариант 1: добавить явный, доступный хуку только для чтения контекст записи с
признаком загрузки. Вариант с `computed` в метаданных и вариант одной лишь
документации в этот этап не входят.

Сейчас вызывающий код заполняет `runtime.Object`, после чего `ПриЗаписи`
(`OnWrite`) исполняется над тем же объектом и его результат считается финальным.
Поэтому загрузчик может передать рассчитанные внешней системой `СуммаНДС` и
`СпособУчетаНДС`, а общий хук документа тут же пересчитает их как значения
интерактивной формы. Хук не знает, откуда пришла запись, и интеграция вынуждена
угадывать внутренние управляющие поля конфигурации.

Проверка текущего кода показывает две важные границы:

- `internal/entityservice.Service.Save` обслуживает формы, REST v1/v2, ИИ и
  часть DSL-объектов; `SaveRequest` не несёт режима записи, а `BuildVars`
  создаёт одинаковое окружение для любого вызова;
- документный `docWriter` в `internal/ui/dsl_documents.go` пока сохраняет
  напрямую, отдельно запускает `runOnWriteCtx` и тоже не передаёт происхождение
  операции. Каталожный `catWriter` уже использует `entityservice.Save`.

Это не план пропуска хука. `ПриЗаписи`/`OnPost` продолжают выполняться, а
конфигурация сама решает, какие пересчёты допустимы при загрузке. Режим не должен
обходить проверки enum/required, RLS, optimistic lock, проведение, регистрацию
обмена, аудит и веб-хуки.

## Наблюдаемая семантика и инварианты

1. Каждая запись имеет ровно один внутренний `WriteContext` с режимом
   `normal` или `load`. Нулевое значение означает `normal`.
2. В `ПриЗаписи` и `ОбработкаПроведения` доступен глобал
   `КонтекстЗаписи` (`WriteContext`) со свойством только для чтения
   `Загрузка` (`Loading`). В обычном режиме оно равно `Ложь`, в режиме загрузки
   — `Истина`.
3. Присваивание `КонтекстЗаписи.Загрузка = ...`, динамическая запись свойства и
   вызов неизвестного метода завершаются DSL-ошибкой; молчаливый no-op запрещён.
4. Режим загрузки меняет только данные, видимые прикладному хуку. Сам хук и все
   платформенные проверки и побочные эффекты выполняются в прежнем порядке и в
   прежней транзакции.
5. Режим задаётся на конкретной операции. Вложенная запись из хука получает
   обычный режим, пока прикладной код явно не передал `РежимЗаписи.Загрузка`
   именно во вложенный `Записать`/`Провести`; ambient-наследования нет.
6. Обычный HTTP-пользователь не может объявить свою запись загрузкой через
   поле тела, query-параметр или cookie-сессию. REST v2 принимает такой режим
   только от Bearer API token и только при отдельном объектном праве `load`.
7. Неизвестный режим всегда даёт явный отказ до открытия транзакции записи.
   Значение не нормализуется к `load` по принципу truthy и не откатывается
   молча к `normal`.
8. Аудит сохраняет факт `write_mode=load` рядом с уже известным пользователем;
   обычные записи не раздувают журнал новым полем. Секрет токена и значения
   объекта в эту отметку не попадают.

## Синтаксис / YAML

### DSL

По умолчанию существующий код не меняется:

```os
Док = Документы.Поступление.Создать();
Док.Записать();
```

Загрузчик передаёт типизированный режим явным аргументом:

```os
Док = Документы.Поступление.Создать();
Док.СуммаНДС = ДанныеЭДО.СуммаНДС;
Док.Записать(РежимЗаписи.Загрузка);
```

Хук не пропускается, а ветвится по read-only контексту:

```os
Процедура ПриЗаписи()
    Если Не КонтекстЗаписи.Загрузка Тогда
        ПересчитатьИтоги();
    Иначе
        ПроверитьЗагруженныеИтоги();
    КонецЕсли;
КонецПроцедуры
```

Английские алиасы: `WriteMode.Load`, `WriteMode.Normal`,
`WriteContext.Loading`. `РежимЗаписи.Обычный` можно передать явно, но он
эквивалентен отсутствующему аргументу.

Аргумент поддерживают объектные методы `Записать`/`Write` и
`Провести`/`Post` документов и справочников. Ноль или один аргумент допустимы;
лишние аргументы и значения другого типа — ошибка. Единая сигнатура нужна,
чтобы каталог с `ПриЗаписи` не получил второй несовместимый контракт.

Новых YAML-полей нет. Режим относится к вызову, а не к метаданным объекта или
реквизита. Вариант `computed:` остаётся вне этого плана.

### REST v2

Интеграционный клиент передаёт:

```http
Authorization: Bearer <api-token>
X-OneBase-Write-Mode: load
```

Заголовок действует на `POST`/`PUT` объекта и на проведение документа. Для
cookie-сессии, open-access режима или Bearer-пользователя без объектного права
`load` ответ — `403`; неизвестное значение заголовка — `400`. Отсутствующий
заголовок и значение `normal` сохраняют прежнюю семантику. REST v1 не получает
новый режим: он остаётся session-only совместимым API.

В permissions роли действие добавляется рядом с `write` и `post`, например:

```yaml
permissions:
  documents:
    Поступление: [read, write, load]
```

Право `load` не заменяет `write`/`post`: для загрузочной записи требуются оба
действия, нужные обычной операции, плюс `load`. OpenAPI v2 описывает заголовок,
допустимые значения, ответы `400/403` и эту комбинацию прав.

## Хранилище / SQL

Схема бизнес-данных не меняется, миграции не нужны. Режим живёт только на время
вызова в Go-DTO и DSL-окружении. Отметка аудита записывается в существующий
структурированный payload/детали записи; если текущий тип события не допускает
дополнительных деталей, сначала расширяется его сериализация без DDL.

Нельзя хранить режим в `runtime.Object.Fields`: псевдореквизит может попасть в
storage, конфликтовать с пользовательским именем и быть подменён входным JSON.
Нельзя использовать и один только `context.Context`: режим должен быть явной
частью DTO, проверяемой компилятором на каждом write-boundary.

## Инвентаризация затронутых границ

- `internal/entityservice/service.go` — `SaveRequest`, единая валидация режима,
  сборка vars и запуск `OnWrite`/`OnPost`;
- новый небольшой файл `internal/entityservice/write_context.go` — закрытые
  enum-типы `WriteMode`, `WriteSource`, конструкторы обычного/загрузочного
  контекста и проверка допустимых сочетаний;
- `internal/ui/dsl_documents.go`, `internal/ui/dsl_catalogs.go` — разбор
  необязательного типизированного аргумента и передача контекста; прямой
  документный путь не должен потерять режим до `runOnWriteCtx`;
- `internal/ui/handlers_dsl.go` и сборка глобалов — `РежимЗаписи`/`WriteMode`,
  а также read-only объект `КонтекстЗаписи`/`WriteContext` только на время
  entity hook;
- `internal/api/v2.go`, `internal/api/server.go` и auth-context — разбор
  заголовка, доказательство Bearer-аутентификации, проверка права `load` и
  передача `WriteContext` в `SaveRequest`;
- `internal/auth` — распознавание действия `load` в объектных permissions без
  автоматической выдачи существующим ролям;
- генерация OpenAPI и справочники DSL/`DEVELOPER.md` — публичный контракт,
  пример безопасного хука и предупреждение, что загрузка не отменяет
  валидацию.

Системные writer-ы, которые намеренно обходят обычный `Save` (репликация,
restore, миграции, predefined sync), в этот API автоматически не включаются:
их отдельные доверенные контракты нельзя случайно переименовать в пользовательский
`load`. Если им потребуется исполнять entity hook, они должны будут выбрать
режим явно в отдельной заявке.

## Совместимость и миграция

- Существующие вызовы без аргумента и все `SaveRequest` с нулевым контекстом
  работают как `normal`; действующие хуки получают `Загрузка = Ложь` и
  продолжают пересчитывать поля как раньше.
- Новое право никому не выдаётся автоматически. Старые роли и API tokens
  сохраняют обычную запись, но получают `403` только если начнут посылать новый
  заголовок `load`.
- Поля JSON/YAML не переименовываются, данные не преобразуются, откат бинаря не
  требует обратной миграции.
- Контекст нельзя использовать как доказательство корректности внешних данных:
  он сообщает намерение доверенного writer-а. Обязательные проверки загруженных
  сумм остаются ответственностью конфигурации и должны быть показаны в
  документации рядом с примером.
- Русские и английские имена регистронезависимы по обычным правилам DSL; иных
  строковых значений режима нет.

## Последовательность небольших PR-срезов

### Срез 1 — внутренний контракт и hook context

Добавить типизированный `WriteContext` в `entityservice.SaveRequest`, строгую
валидацию нулевого/обычного/загрузочного режима и read-only DSL-объект. Ввести
`КонтекстЗаписи` при запуске `OnWrite` и `OnPost`, не меняя ни одного публичного
способа включения загрузки. Все существующие callers пока передают normal.

Публичная проверка среза: тест через настоящий `Service.Save` запускает
`ПриЗаписи`, который читает `КонтекстЗаписи.Загрузка`; normal даёт `Ложь`,
явный внутренний load — `Истина`, попытка присваивания откатывает всю запись.

### Срез 2 — DSL-вход

Добавить `РежимЗаписи` и необязательный аргумент в writers документов и
справочников. Пронести режим и через прямой `docWriter`, и через
`entityservice.Save`; явно зафиксировать отсутствие наследования вложенными
записями.

Публичная проверка среза: `RunProcessor` создаёт документ с внешними суммами и
вызывает `Записать(РежимЗаписи.Загрузка)`. Реальный `ПриЗаписи` сохраняет их,
normal-вызов пересчитывает; тот же тест покрывает `Провести`, каталог, неверный
тип/лишний аргумент и вложенную запись с normal по умолчанию.

### Срез 3 — доверенный REST v2

Сохранить в auth-context вид аутентификации, добавить permission `load`, разбор
заголовка и передачу режима во все мутирующие object handlers v2. Обновить
OpenAPI. Нельзя определять Bearer по одному наличию строки Authorization после
аутентификации: решение должно опираться на проверенный middleware principal.

Публичная проверка среза: `httptest` идёт через смонтированный router. Матрица
проверяет Bearer token с `write+load`, token только с `write`, cookie-сессию,
open access, неизвестный режим, create/update/post и отсутствие заголовка.
Успешная загрузка наблюдается по сохранённым полям после реального `OnWrite`.

### Срез 4 — документация, аудит и сквозной паритет

Документировать DSL/REST-контракт и пример проверки внешних итогов, добавить
`write_mode=load` в существующее событие аудита и сквозной parity-тест формы,
DSL и REST на одной конфигурации.

Публичная проверка среза: форма и REST без заголовка дают одинаковый normal-
результат, DSL и авторизованный REST load сохраняют внешнее значение, во всех
четырёх ветках хук действительно исполняется, а audit entry различает только
две загрузочные операции.

Каждый срез должен собираться и проходить отдельно. Закрывающее `Fixes #1435`
ставится только на последнем PR после готовности предыдущих зависимостей.

## Тесты

- Юнит-тесты `internal/entityservice`: нормализация нулевого режима, отказ на
  неизвестном enum, неизменность порядка hook → final validation → persistence,
  rollback при попытке изменить read-only context.
- DSL-тесты `internal/ui`: настоящий `RunProcessor`, `Записать`/`Провести`,
  русские и английские алиасы, документы и справочники, nested-write isolation.
- REST-тесты `internal/api`: полная auth/permission-матрица через HTTP router,
  OpenAPI contract, `400/403`, create/update/post и обратная совместимость.
- Аудит: load-метка только после успешной фиксации, отсутствие записи после
  rollback, отсутствие тела объекта и токена в деталях.
- Матричный storage-тест не нужен, пока SQL и транзакционный порядок не
  меняются. Если реализация затронет audit SQL или save sequencing, тот же
  сценарий запускается через `dbtest.ForEachDialect` на SQLite и PostgreSQL.

Минимальные команды каждого среза:

```bash
go test ./internal/entityservice ./internal/ui ./internal/api ./internal/auth
go test ./...
go build ./...
```

## Verification

1. В тестовой конфигурации создать документ с `ПриЗаписи`, который в normal
   пересчитывает НДС, а в load проверяет и сохраняет внешний НДС.
2. Записать `400 + НДС 80` обычной формой: наблюдать прежний normal-пересчёт.
3. Запустить обработку с `Записать(РежимЗаписи.Загрузка)`: после повторного
   чтения из БД наблюдать ровно `80`, при этом счётчик вызовов хука увеличен.
4. Повторить через REST v2 с Bearer token и правом `load`; затем убедиться, что
   cookie-запрос и token без `load` получают `403` и ничего не записывают.
5. Намеренно передать неизвестный режим и присвоить
   `КонтекстЗаписи.Загрузка`: обе операции отклоняются до commit.
6. Проверить журнал аудита: успешные load-записи помечены, normal-записи и
   откаты не получают ложной отметки.

## Риски и откат

- Главный риск — превратить load в обход бизнес-правил. Его ограничивают
  непропускаемый хук, отдельное REST-право, Bearer-only вход, аудит и отсутствие
  автоматического наследования.
- Расхождение прямого `docWriter` и `entityservice.Save` может дать разные
  значения контекста. Сквозной parity-тест обязателен до публикации DSL API.
- Добавление аргумента к динамическому `CallMethod` легко принять молча. Writers
  должны централизованно проверять количество и тип аргументов.
- Если auth-context не отличает token от session после middleware, проверка по
  HTTP-заголовку создаст ложную границу доверия. Вид principal фиксируется при
  успешной аутентификации и читается handler-ом только оттуда.
- Откат выполняется срезами в обратном порядке: сначала запретить REST `load`,
  затем убрать DSL-аргумент, затем удалить hook context. Данных и DDL для отката
  нет; уже сохранённые бизнес-значения остаются обычными данными и требуют
  предметной сверки, а не автоматического пересчёта.

## Критерии завершения

- `КонтекстЗаписи.Загрузка` одинаково наблюдается в `OnWrite`/`OnPost` на
  entityservice и прямом document writer path и недоступен для изменения.
- Existing no-argument DSL, UI, REST v1/v2 и внутренние callers сохраняют
  прежнюю normal-семантику.
- Режим load доступен через явный DSL enum и защищённый REST v2 header; обычный
  пользователь не может его подделать.
- Все платформенные проверки, транзакционные гарантии и побочные эффекты
  подтверждены тестами для обоих режимов.
- Публичная документация и OpenAPI объясняют, что load не означает skip hooks,
  и показывают безопасную проверку внешних данных.
- `go test ./...`, `go build ./...` и обязательный CI зелёные на каждом срезе.

## Эстимейт

- внутренний контекст и read-only DSL-представление — 1–1.5 дня;
- DSL writers и parity-тесты — 1.5–2 дня;
- REST v2, auth permission и OpenAPI — 1.5–2 дня;
- аудит, документация и сквозная проверка — 1 день.

Итого: 5–6.5 рабочих дней без изменения схемы данных.
