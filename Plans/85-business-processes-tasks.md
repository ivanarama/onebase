Дата проектирования: 2026-07-08.

маршрута не строится до срабатывания триггеров ниже. Ценную часть плана

## Решение 2026-08-12 (заморозка)

Разбор показал три вещи:

- **Спроса на движок нет.** 208 issue от 18 авторов — ни одного запроса про
  бизнес-процессы, согласование, маршруты. Важная оговорка: сценарий
  документооборота в аудитории при этом живёт — на OneBase строится СЭД
  DocFlow (~23 issue её автора упоминают продукт, #147 прямо называется
  «ограничения, блокирующие DocFlow»), но просил он общеплатформенные фиксы
  UI/прав/аудита, а не движок БП/задач. План заведён внутренним ревью (коммит
  `121bd4fd`), а не пользователем; тем же коммитом строка в
  `35-1c-feature-inventory.md` переписана с «низкий приоритет» на «план 85».
  Нетронутая строка `35:160` при этом требует принимать решение «по реальному
  запросу пользователя». Внешний сигнал ровно один — ТЗ КЦ ICE-32 (пробел G3),
  и он закрыт без правки движка.
- **Оценка занижена вдвое.** Раздел «Изменения в коде» оплачивает шесть
  пунктов и ни одной сквозной подсистемы. Новый вид объекта обязан прописаться
  примерно в 20 пакетах: `backup/universal.go` перечисляет миграторы поимённо
  (пропуск = молчаливая потеря `_bpm_*` при restore), `storage/schemaplan.go`
  принимает только entities/registers/infoRegs, `storage/fts.go` типизирован на
  `*metadata.Entity`, `internal/exchange` регистрирует изменения отдельной
  функцией на вид, а `converter/parser1c/metadata.go:298` сознательно пропускает
  `BusinessProcesses`/`Tasks` — импорт из 1С попутно не приедет. Реалистичная
  оценка (экстраполяция по прецедентам бухрегистра и ExchangePlan, не
  измерение) — 30–45 рабочих дней, а не 2–3 недели.
- **Форма выбрана неудачно.** Карта маршрута как объект конфигурации означает
  «правка маршрута = выпуск новой версии». Сама 1С в «1С:Документообороте» от
  этого ушла: реальные маршруты живут шаблонами процессов, настраиваемыми
  пользователем, то есть **данными**. При этом ценность объекта «Задача» в 1С —
  не поля, а косвенная адресация через регистр адресации; официальная
  формулировка 1С прямо говорит, что задачи «могут использоваться отдельно от
  бизнес-процессов». То есть порядок в плане 85 обратный: задача — примитив,
  карта маршрута — надстройка.

### Триггеры разморозки

Браться за движок при любом из событий:

1. **второй независимый запрос уровня ТЗ** (не от внутреннего ревью);
2. требование **«маршрут меняет бизнес-пользователь без выпуска новой версии
   конфигурации»** — тогда план переписывается на «маршрут как данные»
   (справочник маршрутов + регистр состояния + интерпретатор), а не `bpm/*.yaml`;
3. требование **параллельного согласования с кворумом** («согласуют трое,
   достаточно двух») — здесь нужна транзакционная семантика подачи голоса,
   прикладным слоем она делается, но неочевидно и с тихими отказами;
4. процесс идёт **цепочкой разных документов** (заказ → заказ на производство →
   выпуск → отгрузка) — тогда нужны структура подчинённости и составной предмет,
   и это более крупная работа, чем нынешний план: `subject:` типизируется ровно
   одним документом.

### Что сделать до этого

- `121-stages.md` — этапы, гейт, история, «где застряло»;
- предикат существования по регистру в строковых политиках (ролевая адресация
  как общее правило видимости) — предусловие для платформенной «Задачи»;
- починить виджет «Мои задачи» в `examples/tasks`: он показывает задачи всех
  (нет условия по пользователю, у ролей нет `row_access`), а сам виджет выведен
  на главную. Ловушка: просто дописать `row_access` не выйдет — `Исполнитель`
  там ссылка на справочник без привязки к логину; сначала связать исполнителя
  с пользователем (поле-логин, как в callcenter), потом политика. Утечки сверх
  ролевой модели тут нет (роли и так дают всем `read` на все Задачи) — это
  дефект образца, который скопируют;
- дать маршруту в `examples/callcenter` пользовательскую точку входа: каталога
  `forms/` там нет вовсе, `ОтправитьНаСогласование`/`ВыполнитьЗадачу` вызывают
  только Go-тесты — то есть «заход 0» ни разу не проверен живым пользователем;
- прогнать маршрут под реальным залогиненным пользователем и закрыть слепую
  зону тестов: все четыре approval-теста (`ui/callcenter_validation_test.go`)
  работают с пустым контекстом, `ИмяПользователя()` возвращает `""`, поэтому
  гейты «инициатор/исполнитель = текущий пользователь»
  (`Согласование.module.os:18-21`, `:62-65`) всегда проходят по обходной ветке
  «пустой логин» и по-настоящему не проверялись ни разу.

## Контекст

В инвентаре 1С-фич БизнесПроцессы/Задачи помечены «низкий приоритет». Но как
только OneBase используют для реального документооборота (согласование заявок,
маршрут «черновик → на согласовании → утверждён → проведён», делегирование), эта
подсистема становится центральной: без неё маршрутизация зашивается вручную в
`.os`-хуки и дублируется в каждой конфигурации.

Кирпичи для реализации уже есть: справочники/документы, регистр сведений
(состояние), DSL-хуки и модули менеджера, регламентные задания (план 17),
вебхуки (план 29), уведомления, RBAC + строковые политики (план 79).
Бизнес-процессы связывают их в декларативный маршрут.

## Цель

- декларативная **карта маршрута** (точки/переходы/условия) как объект
  конфигурации;
- объект **Задача** — адресованная пользователю/роли единица работы с состоянием,
  сроком, предметом (ссылка на документ);
- список «Мои задачи» в UI, выполнение/переадресация, автопереходы по условию;
- интеграция с проведением: «документ проводится только из точки Утверждён».

## Синтаксис / метаданные

Объект `bpm/<имя>.yaml` — карта маршрута:

```yaml
name: СогласованиеЗаявки
subject: Документ.Заявка          # предмет процесса
points:
  - { id: start,    kind: start }
  - { id: approve,  kind: task, assignee: { role: Руководитель }, name: Согласовать }
  - { id: revise,   kind: task, assignee: { field: Автор },       name: Доработать }
  - { id: done,     kind: end }
transitions:
  - { from: start,   to: approve }
  - { from: approve, to: done,   when: "Результат = 'Утверждено'" }
  - { from: approve, to: revise, when: "Результат = 'Отклонено'" }
  - { from: revise,  to: approve }
```

DSL для старта/движения из хуков документа:

```
БП = БизнесПроцессы.СогласованиеЗаявки.Старт(ЭтотОбъект);
```

Точки-задачи адресуются пользователю (`field:` реквизит), роли (`role:`) или
вычисляемому выражению; переходы срабатывают по `when`-условию на DSL.

## Хранилище / SQL

- `_bpm_instances` — экземпляр процесса: карта, предмет, текущая точка,
  состояние (`running`/`done`/`aborted`), автор, времена;
- `_bpm_tasks` — задачи: экземпляр, точка, исполнитель (kind+id), состояние
  (`open`/`done`/`redirected`), срок, результат;
- индексы под «мои открытые задачи» (исполнитель+состояние).

## Изменения в коде

- `internal/metadata/` — модель карты маршрута (`BusinessProcess`), валидация
  точек/переходов/адресации;
- `internal/bpm/` — движок: старт, генерация задач точки, выполнение задачи,
  вычисление переходов (через DSL-интерпретатор для `when`), автопродвижение;
- `internal/dsl/interpreter/` — объект `БизнесПроцессы.X.Старт/…` и `Задачи`;
- `internal/ui/` — «Мои задачи», карточка задачи (выполнить/переадресовать),
  визуализация маршрута; учёт RBAC + строковых политик (план 79: пользователь
  видит только адресованные ему/его области задачи);
- интеграция с `entityservice`: гейт проведения по точке маршрута (опц.);
- уведомления/вебхуки (планы 20/29) на назначение задачи.

## Тесты

- прохождение маршрута: старт → задача → условный переход → конец;
- адресация: задача попадает только нужному исполнителю (роль/реквизит/выражение);
- условия переходов на DSL, ветвление, возврат на доработку (цикл);
- права: чужие задачи не видны/не выполнимы (RLS);
- перезапуск/восстановление состояния экземпляра.

## Verification

1. Карта согласования заявки; создать заявку → у руководителя появилась задача.
2. «Утвердить» → процесс дошёл до конца, документ разрешено провести;
   «Отклонить» → задача автору на доработку, цикл повторяется.
3. Под чужой учёткой задача не видна.

## Эстимейт

2–3 недели по этапам: модель+валидация (2–3 дня), движок точек/переходов
(4–5), DSL-объекты (2), UI «Мои задачи»+маршрут (4–5), права/уведомления/
интеграция проведения (2–3), тесты (3). Начать с минимального среза
(start/task/end + условные переходы + «Мои задачи»), затем параллельные ветки,
сроки, эскалации.
