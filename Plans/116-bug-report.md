# План 116 — «Сообщить об ошибке»: отчёт об инциденте одним файлом

Дата проектирования: 2026-08-07.
Статус: ✅ Реализовано 2026-08-07 (этапы 116A–116E).

> **Что разошлось с планом.**
> 1. **Номер.** План писался как 115, но в апстриме этот номер занял
>    `115-process-hardening.md` — переномерован в 116 при вливании свежего `main`.
> 2. **План 92 приехал по дороге.** Ветка начиналась от `main`, где
>    `internal/selfupdate` был ещё без каналов и политики, поэтому 116A–116E
>    делались с константным адресом трекера. К моменту вливания свежего `main`
>    PR #606 оказался смёржен, и источник переключён на
>    `selfupdate.LoadPolicy(dir).RepoOr("")` — в закрытом контуре администратор
>    указывает зеркало, и отправлять пользователя в апстрим оттуда неверно.
>    Заодно в окружение отчёта добавлен канал обновлений из `state.json`
>    (без похода в сеть — читаем то, что записал лаунчер).
> 3. Настройку контактов через `onebase.policy.yaml` так и не делали: хватает
>    двух уровней — `app.yaml → support` (внедренец) и константа платформы.
> 4. `version.SupportContact` **пуст**: реального адреса для тех, у кого нет
>    аккаунта GitHub, на момент реализации не определено. Пока он пуст, форма
>    честно предлагает только трекер — то есть исходную проблему.
> 5. Замену `http.Error(…, 500)` на `s.serverError` сделали разом по всем файлам
>    `internal/ui`, а не «по мере касания»: замена механическая и полная.
> 6. Добавились два дедупа, которых не было в плане: `launcher.tailFile` →
>    `bugreport.TailFile` и поле `support` в форме свойств конфигуратора (без него
>    сохранение свойств затирало бы контакт — `saveAppConfig` переписывает
>    `app.yaml` целиком; заведена отдельная issue #656).

## Контекст

Тестировщик не смог завести issue: у него нет аккаунта GitHub. Это не частный
случай — у пользователя прикладной конфигурации (бухгалтер, оператор КЦ) аккаунта
нет и не будет, а внедренец между ним и разработчиком платформы вообще не читает
upstream-трекер. Канала обратной связи не существовало физически: в UI ни одной
ссылки на issues, нет сбора диагностики, нет `.github/ISSUE_TEMPLATE/`, нет
`CONTRIBUTING.md`.

Вторая половина проблемы — даже добросовестный пользователь не знает, что
приложить. Версия видна только на «О программе», журнал лежит в
`~/.onebase/logs/<id>.log`, и открыть его из интерфейса нельзя ничем.

**Сделано.** Кнопка «Сообщить об ошибке» собирает структурированный отчёт (версия,
окружение, конфигурация, код инцидента со стеком, по желанию — хвост журнала),
показывает его целиком, даёт отредактировать и сохранить файлом. Отправляет файл
пользователь сам.

**Чего сознательно нет.** Платформа не отправляет отчёт по сети. Ни одного нового
исходящего соединения не появилось.

## Принятые решения

1. **Файл, а не отправка.** Единственный вариант, работающий в закрытом контуре
   (issue #299) и не требующий ни приёмника, ни секретов в бинаре, ни защиты от
   спама. Сборка (`Markdown`) отделена от доставки (`WriteBundle`), поэтому
   онлайн-транспорт надстраивается позже без переделки.
2. **Код инцидента вместо «расскажите, что было».** Сервер держит в памяти
   последние ошибки и паники, каждой присваивает `E-3F7A2C`. Код виден
   пользователю в ответе и подставляет в отчёт стек и место.
3. **Три входа: лаунчер, Предприятие, CLI.** Сбой бывает до старта базы (работает
   лаунчер) и до старта лаунчера (`onebase support`).
4. **Журнал — только администратору.** Лог содержит пути, имена баз, иногда SQL.
   Обычный пользователь отдаёт отчёт с кодом инцидента. Прецедент —
   `TestAbout_RegularUserDoesNotSeeServerPaths`.
5. **Обязательный предпросмотр с правкой.** Текст ошибки может содержать данные
   (DSL `Сообщить`, сообщения валидации со значениями). Автомаскирование дало бы
   ложную гарантию, поэтому пользователь видит отчёт целиком и правит его.
6. **Инциденты живут в памяти.** Файловое хранилище стало бы новым журналом со
   своим сроком хранения и своим вопросом про ПДн.
7. **Имя CLI — `support`.** `onebase report` занято группой команд отчётов.

## Состав отчёта

```markdown
# OneBase — сообщение об ошибке

**Что делал:** …   **Что ожидал:** …   **Что получилось:** …

## Инцидент E-3F7A2C
Время / Место (метод + путь без строки запроса) / Ошибка / стек

## Окружение
Платформа / ОС / СУБД / Конфигурация

## Журнал (по галочке)
## Куда отправить
```

Чего в отчёте нет никогда: DSN и пароля БД, логина пользователя, значений полей,
содержимого таблиц, токенов. Маскирование ПДн (план 88) не обходится — отчёт не
читает данные.

## Изменения в коде

### `internal/incident` (новый)

`Store` — кольцевой буфер (устройство повторяет `ui.MessageStore`), `Record` с
`ID/Time/Kind/Where/Text/Stack/User`, `Recent(user, n)`, `Get(id)` (терпим к
регистру и пробелам — код переписывают с экрана руками), `WhereOf`, `WithCode`.
`Recoverer(store, userOf)` заменил `chi middleware.Recoverer` в `internal/api` и
`internal/launcher`; `http.ErrAbortHandler` пробрасывается дальше и инцидентом не
считается.

Строка запроса в `Where` отбрасывается целиком, а не маскируется по ключам: в
фильтрах списков едут введённые пользователем значения.

### `internal/ui`

`serverError(w, r, err)` — единая замена `http.Error(w, s.errText(r, err), 500)`
(59 мест, 18 файлов). Коды 400/403/404 не трогали: отказ в доступе — не инцидент.
Паника фоновой выгрузки отчёта (`export_jobs.go`) регистрируется отдельно — chi
Recoverer горутину не прикрывает.

Страница: `GET/POST /ui/report-problem`, `POST /ui/report-problem/download`,
шаблон `tpl_report_problem.go`, пункт в меню «Система» и кнопка на «О программе».
Чужой инцидент по угаданному коду не подтягивается (`maySeeIncident`).

### `internal/bugreport` (новый)

`CurrentEnv`, `Markdown`, `Redact` (построчно `RedactDSN` + `RedactURI`),
`WriteBundle` (zip, детерминированный порядок записей, обрезка вложений с начала),
`TailFile`, `StartupLogPath`, `Contacts`/`PlatformContacts`.

Связь с планом 92 — только чтение, без сети: канал берётся из
`selfupdate.LoadState()` (то, что записал лаунчер), адрес трекера — из
`selfupdate.LoadPolicy(dir).RepoOr("")`, чтобы зеркало закрытого контура не
отправляло пользователя в апстрим.

### `internal/launcher`

`GET/POST /report-problem`, `POST /report-problem/save`; кнопка в тулбаре, пункт
меню конфигуратора, ссылка на «О программе». Пакет ложится в
`~/.onebase/reports/` и папка открывается `OpenPath` (через переменную
`openReportDir` — иначе `go test` открывал бы проводник).

### `internal/cli/support.go` (новый)

`onebase support [--out] [--base] [--message] [--project] [--no-logs]`. Без
`--base` берутся три самых свежих по времени записи журнала базы.

### Дедупы

`ui.maskDSN` и `launcher.maskDSN` (байт в байт одинаковые) → `logging.RedactDSN`;
`launcher.tailFile` → `bugreport.TailFile`.

### `app.yaml → support`

Поле `project.AppConfig.Support`, проброшено в `ui.Config.AppSupport`
(`cli/run.go`, `cli/dev.go`), в форму свойств конфигуратора и в `saveAppConfig`.

## Тесты

1. `incident`: формат и уникальность кодов, усечение буфера, фильтр `Recent` по
   пользователю, `Get` терпит регистр/пробелы, обрезка стека.
2. `incident.Recoverer`: паника → 500 с кодом и стеком в буфере;
   `http.ErrAbortHandler` пробрасывается и инцидентом не становится; успешный
   ответ инцидента не создаёт.
3. `WhereOf` отбрасывает строку запроса.
4. `bugreport.Markdown`: окружение и инцидент на месте, логина нет.
5. `Redact`: пароль DSN, `password=`, `?token=` вычищены, полезное сохранено.
6. `Contacts`: порядок конфигурация → платформа → трекер, предупреждение про
   аккаунт, отсутствие блока без контактов.
7. `WriteBundle`: zip читается обратно, пустые вложения пропускаются, большое
   обрезается с начала (важен конец журнала).
8. `TailFile`: число строк, нет файла / пустой файл / пустой путь.
9. Рендер `page-report-problem`: неадмин без галочки журнала, админ с ней,
   список инцидентов и запасное поле для кода, предпросмотр редактируемый,
   кнопки не обещают отправку.
10. `reportProblemDownload` отдаёт ровно отредактированный текст; пустой — 400.
11. `maySeeIncident` не пускает к чужому инциденту (с непустым `authRepo` —
    иначе `isAdmin` отвечает «да» всем).
12. Лаунчер: рендер формы/предпросмотра/ошибки, ссылка в тулбаре, `baseLogTail`
    маскирует пароль, сквозной путь форма → предпросмотр → zip на диске.
13. CLI: `onebase support` пишет пакет, читает `app.yaml`, путь по умолчанию,
    `sanitizeLogLabel`.
14. `go run ./tools/i18ncheck` — OK.

## Verification (ручная, по протоколу AGENTS.md)

```bash
taskkill /IM onebase.exe /F 2>nul
go build -o onebase.exe ./cmd/onebase
go test ./internal/incident/ ./internal/bugreport/ ./internal/ui/ ./internal/launcher/ ./internal/cli/
```

1. Запустить лаунчер → «Сообщить об ошибке» → выбрать базу → «Сформировать
   отчёт» → «Сохранить пакет…» → открылась папка, внутри zip с `report.md`,
   `logs/base.log`, `startup.log`.
2. В Предприятии: Система → Сообщить об ошибке → заполнить → «Сформировать
   отчёт»: видны версия, ОС, СУБД, конфигурация; DSN и логина нет.
3. Спровоцировать ошибку → на экране код `E-…` → в форме этот инцидент первый
   в списке, стек подставлен.
4. Войти не-админом → галочки журнала нет, форма работает.
5. `onebase support --out C:\tmp\r.zip` при остановленном сервере → файл создан.
6. `config/app.yaml` с `support:` → контакт виден первым.

Проверено вживую: `onebase support` (пакет с `report.md` + 3 журнала +
`startup.log`), `GET/POST /ui/report-problem` и скачивание файла на запущенной
базе `examples/trade`.

## Риски и ограничения

1. **Текст ошибки может содержать данные.** Защита — предпросмотр с правкой, а не
   автомаскирование; в форме об этом сказано прямо.
2. **Формулировки без обещаний** — «Сохранить» / «Скопировать», не «Отправить».
3. **Инциденты не переживают перезапуск** — в форме написано «за текущий сеанс».
4. **`version.SupportContact` пуст** — см. расхождение 4.
5. **Ротации журналов нет** (`runner.go` пишет в append без ограничения) — для
   отчёта не критично (`TailFile` читает с конца), но дефект смежный.
6. **`saveAppConfig` в конфигураторе переписывает `app.yaml` целиком** по фикс-
   ированному списку полей: `support` мы добавили, но `email`, `webhooks`, `llm`,
   `attachments` эта форма по-прежнему теряет. Отдельный дефект, вне плана 116.

## Не делаем сейчас

- **Отправку по сети** — ни POST на приёмник, ни Telegram, ни SMTP.
- **Автоотправку при панике** — это телеметрия, которой в проекте нет
  принципиально.
- **Скриншот экрана** — браузерный API плюс отдельный разговор про ПДн на снимке.
- **Файловое хранилище инцидентов** — новый журнал с вопросом ретенции.
