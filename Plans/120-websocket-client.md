# План 120 — WebSocket-клиент: исходящее соединение как транспорт приёмки

Дата проектирования: 2026-08-11.
Статус: ✅ **Сделан** 2026-08-13, этапы A/B/C разом. Issue #738.
Открытые вопросы закрыты ответами автора заявки 2026-08-11 (см. раздел в конце);
отклонения реализации от проекта — там же.

## Контекст

Заявка (#738): «Добавить websocket-клиент на сервер OneBase (коннект,
реконнект, обработка входящих, рассылка формам, обработка сообщений от форм по
внутр. шине, запись исходящих). Формы, которые хотят получать события, либо
подписываются динамически, либо статически описываются в yaml».

Разбор по коду показал, что **половина запрошенного уже построена**, и это
меняет размер задачи.

Состояние на 2026-08-11 (ссылки проверены):

| Кусок запроса | Где сегодня | Состояние |
|---|---|---|
| Рассылка событий формам | `internal/realtime/hub.go:108` `Publish`, `:66` `Subscribe` | **есть**: шина сервер → браузер |
| Доставка в браузер | `ui/handlers_events.go:32` SSE-эндпоинт `GET /ui/events` | **есть** |
| Публикация из кода | `ОтправитьУведомление(Кому, Событие, Данные)` → `hubNotifier` (`handlers_events.go:20`) | **есть** |
| Приём внешних сообщений | `internal/intake/intake.go` — идемпотентность, DLQ, обработчик в транзакции | **есть**, транспорт за швом |
| Шов транспорта приёмки | `intake.go:73` `MessageSource`; `metadata/intake.go:52` `Transport: http \| amqp` | **есть**, ждёт вторую реализацию |
| Исходящее WS-соединение | — | **нет**; в `go.mod` библиотеки веб-сокетов нет |
| Отправка в WS из кода | — | нет |
| Предохранитель сети | `ui/network_guard.go:19` (`net.enabled`) | есть, распространяется на HTTP/email/ИИ |

То есть просят не подсистему целиком, а **два недостающих куска**: долгоживущее
исходящее соединение и мост «входящее сообщение → прикладной обработчик». Рассылку
формам обработчик сделает существующим `ОтправитьУведомление`.

## Цель

1. База умеет держать исходящее WS-соединение к внешнему серверу с
   переподключением.
2. Входящее сообщение попадает в прикладной обработчик **через приёмку**
   (`intake`), то есть с идемпотентностью, карантином и записью в транзакции.
3. Из кода можно отправить сообщение в это соединение.
4. Формы получают события существующей шиной, без второго механизма подписки.

## Принятые решения

1. **WS — это транспорт приёмки, а не новая подсистема.** `metadata.Intake`
   уже имеет `Transport: http | amqp`; добавляется `ws`. Иначе пришлось бы
   заново строить идемпотентность (повторная доставка после реконнекта — норма
   для WS, а не исключение), карантин упавших сообщений и запись бизнес-объекта
   в одной транзакции. Всё это в `intake` уже есть и покрыто планом 90.
   Самодельный обработчик получил бы дубли на каждом переподключении.
2. **Никакого второго механизма подписки форм.** Запрошенная «рассылка формам»
   делается так: обработчик приёмки зовёт `ОтправитьУведомление(Кому, Событие,
   Данные)`, форма получает событие уже работающей шиной. Статическое описание
   подписки в YAML не заводим: адресация уже есть (кому — пользователь/роль),
   а второй путь доставки разошёлся бы с первым.
3. **Соединение живёт в процессе сервера, а не в задании.** Регламентное
   задание — разовый прогон с защитой от наложения (`scheduler.go:463`
   `ErrJobAlreadyRunning`); держать в нём бесконечный цикл значит занять слот
   задания навсегда и потерять соединение при любой ошибке. Нужен собственный
   supervisor с жизненным циклом сервера (старт после загрузки конфигурации,
   остановка по graceful shutdown).
4. **Под предохранителем `net.enabled` — безусловно.** Исходящее долгоживущее
   соединение — сетевая операция, и она не должна отличаться от HTTP-клиента.
   При выключенном предохранителе соединение не поднимается, а в журнале
   остаётся явная запись — не тихое «не работает».
5. **В песочнице запрещено.** Недоверенному коду (ИИ/marketplace) исходящий
   канал не даётся: `SandboxProfile.DenyNet` закрывает и его.
6. **Обратное давление обязательно.** Внешний сервер может слать быстрее, чем
   обработчик пишет в БД (на SQLite пул — одно соединение). Нужны ограниченная
   очередь и явное поведение при переполнении (замедлить чтение либо отправить
   в карантин), а не рост памяти до OOM.

## Синтаксис / YAML

Транспорт объявляется в существующем описании приёмки:

```yaml
# intakes/событияобмена.yaml
name: СобытияОбмена
transport: ws                     # было: http | amqp
url: wss://hub.example.com/stream # адрес внешнего сервера
auth: token                       # как у http-приёмки
secret: ${env:WS_TOKEN}
subscribe:                        # необязательное сообщение при подключении
  type: subscribe
  topics: [orders, nodes]
reconnect:
  initial: 1                      # секунды, экспоненциальный рост
  max: 60
idempotency:
  key: event_id
handler: ОбработатьСобытие        # процедура Обработать(Конверт) — как у http
```

Отправка из кода:

```
ВебСокет.СобытияОбмена.Отправить(ЗначениеВJSON(Данные));
Если НЕ ВебСокет.СобытияОбмена.Подключён() Тогда
    Сообщить("Канал не поднят");
КонецЕсли;
```

## Изменения в коде

- `internal/wsclient/` (новый) — соединение, реконнект с экспоненциальной
  выдержкой и джиттером, ограниченная входящая очередь, метрики состояния;
- `internal/intake/` — реализация `MessageSource` для ws (ядро приёмки не
  трогаем, это и есть смысл шва);
- `internal/metadata/intake.go` — поля `URL`, `Subscribe`, `Reconnect`,
  валидация `transport: ws`;
- `internal/api/server.go` — старт/остановка supervisor'а рядом с планировщиком
  (`server.go:55` — образец подключения);
- `internal/ui/handlers_dsl.go` — глобал `ВебСокет`/`WebSocket` для отправки;
- `internal/ui/admin_*.go` — состояние соединений в админке (подключено, когда
  последнее сообщение, сколько переподключений);
- `go.mod` — библиотека веб-сокетов (кандидаты: `github.com/coder/websocket`,
  бывш. `nhooyr.io/websocket` — минимальная и без зависимостей;
  `github.com/gorilla/websocket` — распространённее). Выбор — открытый вопрос;
- `internal/configcheck/lint.go`, `internal/cli/schema.go` — схема и линт;
- `DEVELOPER.md`, `docs/features.md`, `internal/i18n/locales/*.json`.

## Этапы

- **120A — соединение и приёмка.** `wsclient` с реконнектом, `MessageSource` для
  `intake`, поле `transport: ws`, старт/стоп с сервером, предохранитель.
  Закрывает главное: входящие события доходят до прикладного кода надёжно.
- **120B — отправка из DSL.** Глобал `ВебСокет`, очередь исходящих, поведение
  при обрыве (ошибка немедленно либо буфер до реконнекта — решить явно).
- **120C — наблюдаемость.** Состояние соединений в админке, счётчики
  переподключений и карантина, запись в журнал.

## Тесты

- **Реальный WS-сервер в тесте** (`httptest` + апгрейд), а не мок клиента:
  проверяется поведение на разрыве, а не наши представления о нём.
- Реконнект: сервер рвёт соединение → клиент переподключается с ростом паузы;
  сообщение, доставленное повторно после реконнекта, **не** создаёт второй
  бизнес-объект (идемпотентность приёмки — то, ради чего выбран `intake`).
- Обработчик падает → сообщение в карантине, соединение живо.
- Предохранитель `net.enabled` выключен → соединение не поднимается, в журнале
  явная причина; проверять через публичную точку (старт сервера), а не вызовом
  guard'а.
- Переполнение входящей очереди ведёт себя как решено в п.6, а не растит память.
- Graceful shutdown закрывает соединение и не оставляет горутин (`goleak`-стиль
  проверка, если она уже принята в проекте, — иначе счётчик горутин до/после).
- Отправка при оборванном соединении даёт предсказуемый результат (120B).

## Verification

1. Внешний WS-эхо-сервер (скрипт в `tools/` или `httptest` вручную) →
   конфигурация с `transport: ws` → сообщение доходит до обработчика, создаётся
   объект.
2. Убить сервер, поднять заново → в журнале переподключение, поток
   восстановился без перезапуска базы.
3. Послать то же сообщение дважды → второй раз «Дубль», объект один.
4. Выключить `net.enabled` → база стартует, соединение не поднимается, причина
   видна в админке.
5. Из обработчика вызвать `ОтправитьУведомление` → открытая форма получает
   событие (существующая шина, без правок).

## Риски и ограничения

1. **Новая зависимость.** Первая в проекте библиотека веб-сокетов. Требует
   решения по выбору и проверки джобом `vuln`.
2. **Долгоживущие горутины.** До сих пор в процессе живут планировщик и SSE-хаб;
   ошибка в supervisor'е даёт утечку горутин и сокетов, невидимую в тестах без
   явной проверки.
3. **Секреты в конфигурации.** `secret: ${env:...}` уже поддержан приёмкой —
   не изобретать второй способ и не давать класть токен открытым текстом.
4. **Multi-tenant.** Лаунчер держит несколько баз; соединение принадлежит базе,
   и при остановке базы его надо закрывать. Иначе остановленная база продолжит
   принимать события.
5. **Заявка неполна.** Формулировка «обработка сообщений от форм по внутр. шине»
   допускает разные прочтения; ниже — вопросы автору.

## Открытые вопросы — закрыты автором заявки (#738, 2026-08-11)

- **Кто инициатор соединения?** → OneBase — именно клиент. WS-сервер не нужен.
- **Что за протокол поверх WS?** → чистый JSON: конверт приёмки, план 90 как есть.
- **Нужна ли гарантия доставки исходящих?** → нет: «обрыв — ошибка — пауза —
  реконнект»; буфер и повтор не делаем, `Отправить` падает сразу.
- **Статическая подписка форм в YAML?** → не нужна: адресат уже есть в
  `ОтправитьУведомление`, второй механизм не заводим.
- **Сколько соединений?** → до нескольких (у автора до 3 ws-серверов): по
  одному соединению на каждый шлюз с `transport: ws`.

## Отклонения реализации от проекта (2026-08-13)

1. **Шов `MessageSource` не использован.** На деле это заглушка с единственным
   методом `Name()` без реализаций: даже http-транспорт живёт как
   `dispatchIntake` в диспетчере `/hs/*`, а не за швом. Изобретать интерфейс
   ради одного потребителя не стали: ws-транспорт сделан симметрично http —
   supervisor в `ui` (`intake_ws.go`) зовёт тот же `intake.New(...).Ingest`.
   Ядро приёмки не тронуто, что и было целью шва.
2. **Обратное давление — синхронной обработкой, а не ограниченной очередью.**
   Решение 6 допускало «замедлить чтение»: следующее сообщение не читается,
   пока обработчик не вернулся, — очереди в памяти нет вовсе, переполняться
   нечему, TCP-окно давит на сервер.
3. **`auth: token` → заголовок `Authorization: Bearer`.** `X-Webhook-Token` —
   соглашение нашего http-транспорта; внешний ws-сервер о нём не знает,
   Bearer — общепринятый для исходящих клиентов. `hmac` для ws запрещён
   валидацией: подписывать нечего (нет тела запроса).
4. **Библиотека — `github.com/coder/websocket` v1.8.15** (бывш.
   nhooyr.io/websocket): без транзитивных зависимостей, MIT.
5. **Сброс выдержки реконнекта** — только после соединения, прожившего ≥30с:
   сброс «по факту подключения» дал бы горячий цикл на сервере, который
   принимает и сразу рвёт.

## Не делаем сейчас

- **WS-сервер** (входящие подключения к базе) — см. первый открытый вопрос.
- Замену SSE на веб-сокеты для браузера: SSE работает, переход не даёт нового
  качества и ломает существующие подписки.
- Прикладной протокол поверх WS (подтверждения, порядок, курсоры) — если
  внешняя сторона его требует, это отдельный разговор.
