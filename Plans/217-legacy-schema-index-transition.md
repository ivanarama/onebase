План не закрывает ни одну из четырёх заявок и не разрешает операции на рабочих БД.

База исследования: `main@f42c89aea07e12725671b1ee554ddbac4eedd4b9`, 03.11.2026.
Ниже разделены наблюдения по исходникам и будущие критерии приёмки.
Новых прогонов миграций или PostgreSQL для этого plan-PR не выполнялось.
Перед каждым кодовым срезом перепроверить соответствующие границы свежего main.

После введения `SQLIdent` длинные имена сокращаются одинаково на SQLite и PG.
Но прежний PostgreSQL обрезал физический идентификатор до 63 **байт**, а строковый
ключ `_schema_fields.table_name` мог оставаться полным логическим именем.
Переименование таблицы также не меняет исторический хеш `idx_ob_*`.
Независимая защита индексов теперь пересекается с этими преобразованиями:

- #2370: `indexName` удаляет legacy hierarchy/predefined индекс после снимка
  сохранности; guard видит исчезновение прежнего имени и откатывает миграцию.
- #2371: legacy-хеш от прежнего имени таблицы не проходит классификацию;
  снятый UNIQUE остаётся как external, вторичные индексы ТЧ могут дублироваться.
- #2372: перенос карты только по прежнему физическому имени не находит полный
  текстовый PG-ключ; rename по устойчивому `field_id` превращается в add.
- #2373: любой `Opaque` индекс считается зависящим от каждой колонки;
  штатный partial predefined индекс блокирует изменение обычного реквизита.

## Синтаксис / YAML и наблюдаемая семантика

Формат YAML/DSL не меняется. Пример перехода одной и той же карточки:

```yaml
name: СправочникСОченьДлиннымИменемИзКонфигурации1С
fields:
  - name: Наименование
    type: string
  - name: Примечание # прежде Описание; id остаётся прежним
    id: descr
    type: string
predefined:
  - name: Основная
    Наименование: Основная
```

После миграции `descr` указывает на колонку нового имени с прежним значением;
`id` строк, ссылки, predefined-признаки и ограничения сохраняются.
Повторная миграция не создаёт второй индекс и не меняет карту снова.
Для таблицы короче 63 байт отдельно поддерживается случай длинного имени индекса.

`migrate --dry-run` остаётся только чтением, в том числе без служебных таблиц.
Он показывает исходную логическую идентичность, найденное физическое имя,
источники карты, предполагаемые преобразования индексов и блокировки.
В нём нельзя показывать «add пустого поля», если доказан rename по id.

Снятый из YAML legacy UNIQUE без реестра приводит к `blocked-legacy` с точным
манифестом для явного принятия. Он не становится молча external и не удаляется.
`--adopt-indexes` разрешает только проверенный объект каталога из манифеста;
`--allow-destructive` отдельно разрешает допустимые разрушительные изменения
полей, но не принятие индекса и не обход владения. Как сейчас, сочетание
`--dry-run` и `--adopt-indexes` отвергается.

## Инварианты идентичности и владения

1. Храним отдельно полный логический ключ, физическое legacy-имя таблицы,
   каноническое `SQLIdent`, legacy-ключи карты и имена индексов. Набор допустимых
   физических имён диалектный; набор текстовых ключей карты включает полное имя
   и на PG. Поиск в `pg_class` с неусечённым именем не служит доказательством.
2. Соответствие старого и нового объекта должно быть однозначно во всей
   конфигурации: учитываются короткие владельцы, общая PG-обрезка, существующие
   old/new таблицы, колонки и schema-wide имена индексов. Коллизия — отказ до DDL.
3. Карта переносится целиком: `field_id`, `column_name`, `field_type`, включая
   удалённые поля и отложенный retype. При нескольких источниках объединение
   допустимо лишь для непересекающихся записей либо побайтно одинакового дубля
   одного id/column/type. Разные определения одного id или несколько id одной
   физической колонки — отказ; чужую карту не перезаписываем.
4. Префикс `idx_ob_` и совпадение хеша дают лишь кандидата legacy, не владение.
   Проверяем схему, таблицу, ordered columns, uniqueness, key options, полное
   определение и ограничения constraint/partial/expression. Для смены владения
   пользовательского UNIQUE нужен точный действующий adoption.
5. Существующая подписанная запись `_managed_entity_indexes` сверяется с каталогом
   до преобразований и повторно под блокировками. Нынешний запрет переноса
   подписанного managed-владения через rename сохраняется: такой исторический
   случай получает явный отказ до DDL. План не вводит автоматическую переподпись
   старого реестра и не выдаёт новый hash за доказательство прежнего владения.
   Поддержанный legacy без реестра проходит только описанный explicit adoption;
   запись нового managed-объекта возникает по фактически прочитанному каталогу.
6. Для системных hierarchy/predefined и вторичных индексов ТЧ/регистров применяем
   узкий перечень проверенных шаблонов платформы. Полное определение, владелец и
   действующая структура должны совпадать; одно ожидаемое имя недостаточно.
   Изменённый или сомнительный объект не удаляется, переход блокируется.
7. Preservation guard допускает только конкретный доказанный переход
   old definition → new definition под той же блокировкой и транзакцией.
   Для остальных индексов остаётся точное равенство имени/fingerprint.
   Нельзя исключать все платформоподобные имена из снимка.
8. Только полностью проверенный predefined partial-индекс имеет зависимости
   `{_predefined_name, _is_predefined}`. Это не общий SQL-парсер и не снятие
   `Opaque`: внешние/изменённые partial и expression индексы по-прежнему
   блокируют потенциально зависимый DDL. Индекс этапов не включаем в это
   исключение; существующие ограничения плана этапов сохраняются.

## Хранилище / SQL и транзакционная граница

Новая постоянная таблица не требуется. Существующие `_schema_fields` и
`_managed_entity_indexes` не меняют формат. Сам физический rename, перенос карты,
нормализация индексов, apply зависимых колонок и регистрация/adoption образуют
одну транзакционную единицу для поддержанного перехода.

Сейчас это **не** одна транзакция `Migrate`: `prepareEntityLegacyIdents` имеет
собственный `WithTxScope`, затем идут scopes сущностей, затем общий index batch.
`MigrateRegisters` и `MigrateAccountRegisters` также нельзя считать атомарными
только по наличию `WithTxScope` у entity-пути. Исправление helper без изменения
вызывающей границы не удовлетворяет плану.

Порядок выполнения поддержанного перехода:

1. Без записи собрать полную конфигурацию владельцев, каталог, все ключи карты,
   ownership и adoption; рассчитать будущую карту и индексные действия.
   До DDL отказать при конфликте любого участника перехода.
2. Под существующим migration lock открыть общий `WithTxScope` для перехода;
   заблокировать исходные и целевые существующие таблицы в стабильном порядке.
   Перечитать всё доказательство и каталог. Новое/изменённое определение — стоп.
3. Перенести таблицы и карту, выполнить необходимые изменения колонок по id;
   нормализовать проверенные системные индексы, проверить их after-definition.
   Ожидаемые изменения явно учесть в preservation snapshot.
4. Согласовать управляемые индексы в том же scope: точный adoption исходного
   объекта, CREATE и read-back новой подписи перед любым DROP. Объект без
   подтверждённого полномочия на DROP сохраняется; отказ откатывает переход.
5. Проверить данные, карту, индексные определения, отсутствие дублей и только
   затем commit. Любая ошибка, cancellation или сбой commit означает rollback
   DDL, map и registry этой единицы. Borrowed transaction использует свой scope.

В B/C необходима внутренняя оболочка перехода вокруг существующих фаз, а не
ранний commit rename. Для entity batch с legacy-переходом она включает все
затронутые сущности и итоговое согласование индексов; несвязанные миграции без
перехода сохраняют прежнюю семантику. Контракт отложенных ошибок numerator
(#1080/#1105) нельзя потерять: обычный путь по-прежнему готовит схему для
`renumber`; переход, который нельзя безопасно завершить при not-ready,
получает явный отказ без частичного rename. Это изменение диагностики описать
в release note и покрыть сочетанием нескольких сущностей.

Для регистров/итогов общий scope вводится только вместе с матрицей своего caller;
до этого A/B должны обнаруживать и отказывать в таком переходе до DDL. Никакого
обещания rollback всей произвольной команды из нескольких миграций не даём:
точный список участвующих объектов выводится в preview.

## Совместимость, миграция и восстановление

- Короткие текущие имена и свежие БД сохраняют нынешний результат. Не меняются
  алгоритмы SQLIdent/хеша, синтаксис indexes/numerator и форматы YAML/DSL.
- Исторические исходники fixtures берутся из `13214448` и состояния после
  #1949/#2145. Отдельно моделируем старую базу **без** реестра: текущая fixture
  `managed_index_identity_matrix_test.go:22` создаёт подписанный реестр и пишет
  на PG усечённый ключ карты; это полезный negative control, но не #2372.
- Неподдержанный signed transfer не «лечится» удалением записи реестра или
  `--allow-destructive`. Нужна отдельная процедура/решение; автоматический
  executor не угадывает владельца.
- Для базы, где #2372 уже создала пустую новую колонку, запретить автоматическое
  слияние old/new данных и удаление старой колонки. Выдать диагностику с обоими
  именами; восстановление из проверенного backup либо отдельная согласованная
  операция сопоставления. Повтор исправленной миграции не обещает восстановить
  уже потерянную историю карты.
- Обновлять только после backup и репетиции на копии. После выполненного DDL
  откат бинаря не восстанавливает схему/данные. Основной rollback — восстановить
  согласованный backup базы вместе с конфигурацией, проверить строки/ограничения,
  запустить прежнюю версию на копии, затем переключить базу. Сохранить журнал
  dry-run и версии; ручной DROP INDEX в рабочей БД не является рецептом.

## Последовательность небольших PR-срезов и публичные тесты

Срезы идут A → B → C → D → E. B раньше C: распознавание индекса и adoption должны
видеть исходную логическую идентичность и корректную карту, иначе C подпишет
не тот объект. D использует системный classifier C. Каждый PR отдельно проходит
REVIEW точного HEAD, все обязательные CI и человеческое разрешение поставки.

| Срез | Поставляемый результат и границы PR | Публичная проверка / безопасный промежуточный релиз |
|---|---|---|
| A (~2–3 дня) | Read-only inventory/classifier, реальные historical fixtures, preview источников и отказов; никаких разрешений нового DDL | `PlanLongIdents`, `PlanEntityIndexes`, CLI `migrate --dry-run`; old logical/physical map, legacy-hash варианты, снимок до/после preview абсолютно одинаков; прежние отказы apply сохраняются |
| B (~3–5 дней) | #2372: перенос доказанной карты вместе с таблицей и rename по id, общий scope entity-перехода; для ещё не поддержанных индексных/регистровых переходов явный отказ до DDL | `Migrate`, `Upsert`, `GetByID`, `UpsertTablePartRows`/`GetTablePartRows`; полное PG имя в TEXT-карте, id/значения/deferred type сохранены; конфликт и injected failure откатывают всё; C/D случаи пока безопасно блокируются |
| C (~4–6 дней) | #2370/#2371: historical hash candidates, exact adoption, системные hierarchy/predefined/ТЧ индексы и expected transitions preservation; закончить scope для поддержанных регистров | `PlanEntityIndexes` + `Migrate` и register entrypoints; две миграции, одно нужное определение, UNIQUE остаётся до adoption и снимается только после точного разрешения; чужие индексы без изменений |
| D (~1,5–2,5 дня) | #2373: dependency proof только для точного platform predefined partial; безопасность SQLite rebuild и PG ALTER | `Migrate` rename/retype/drop обычного поля, затем `Upsert`/чтение и `SyncAllPredefined`; служебные зависимости и altered partial по-прежнему блокируют DDL; ограничения stage не ослаблены |
| E (~2–3 дня) | Общий upgrade fixture четырёх дефектов, CLI dry-run/adoption/apply, документация, release/CHANGELOG и операторская проверка backup | CLI `migrate`, `check`, запуск `run` на копии; старый формат → B/C/D вместе → повтор; реальный PostgreSQL обязателен, остановка и восстановление проверены |

Если B или C нельзя безопасно выпустить отдельно без скрытой потери карты или
ограничений, соответствующий неподдержанный переход остаётся заблокированным
до следующего среза. Не выпускать частично работающий destructive-переход ради
формального закрытия одной заявки. Не открывать четыре параллельных FIX.

| Fixture / действие | Проверяемый результат |
|---|---|
| Короткая таблица, длинный hierarchy или predefined index: полный SQLite / усечённый PG | #2370: migrate дважды, old index исчез лишь в доказанном переходе, current ровно один, строки/id/ссылки неизменны |
| Длинные кириллические таблицы, границы 62/63/64 байта и UTF-8 rune boundary | Current naming детерминирован; общая обрезка двух logical owners, совпадение с коротким владельцем и old/new с данными дают отказ без изменений |
| Pre-registry UNIQUE с хешем полного логического имени; отдельно реально исторический усечённый вход | #2371: desired/missing/nonunique YAML, numerator unique и fields indexes; manifest содержит точного кандидата, снятие без adoption блокируется, дубликатная запись всё ещё запрещена |
| Тот же UNIQUE после точного adoption, плюс stale/mismatched manifest | Разрешённый constraint меняется, дубль после снятия принимается; stale SHA/schema/table/columns/order/unique/key options не принимаются и не меняют БД |
| Длинная ТЧ, регистры накопления/сведений, бухрегистр и итоги отдельно | Системный индекс не дублируется, данные/PK/FK/итоги сохранены; неподдержанный fixture получает отказ до любого rename, а не успешную миграцию |
| Полный logical TEXT key карты на PG + rename `descr` Описание→Примечание | #2372: прежнее значение читается из новой колонки, одна актуальная колонка, одна карта; deleted/deferred rows не потеряны |
| Полный + усечённый + current ключи карты | Одинаковые строки безопасно сводятся, disjoint rows сохраняются, различный type/column одного id и несколько id одной колонки дают отказ; source keys не теряются при rollback |
| Существующая signed registry, подменённая подпись, неверный owner/schema | Signed rename остаётся refused; ни реестр, ни индекс не переподписываются для обхода |
| Predefined + rename/retype/drop обычного поля | #2373: штатная операция проходит при своих обычных permissions, значения корректны; destructive требует прежнего explicit opt-in |
| Predefined с добавленной зависимостью predicate, expression, чужим именем/опциями; stage индекс | Подозрительный объект не получает exemption; dependent DDL останавливается; служебные predefined-колонки защищены |
| Похожий `idx_ob_*`, внешний UNIQUE, constraint-backed индекс, имя на другой таблице/схеме | Никакого adoption или DROP по одному префиксу/хешу; unrelated fingerprints/definitions сохраняются |
| Ошибка после rename таблицы, переноса карты, rename колонки, CREATE, registry write, перед DROP и commit | Весь transition scope откатан: исходные имена, значения/id, schema map, registry, определения и число индексов совпадают; borrowed outer transaction остаётся пригодной |
| Изменение каталога вторым соединением между preview и apply; две миграции одновременно | Recheck под locks отвергает устаревшее доказательство; ни частичного перехода, ни deadlock на втором SQLite connection |

Снимок каждой проверки содержит строки с id и значениями, карту полей, реестр,
точные определения и количество индексов, PK/FK. Уникальность проверять реальной
повторной записью, а не только наличием UNIQUE в DDL. SQLite failure injection —
через существующий DB execution hook/тестовый fault seam, PG — в отдельном scope:
SQL-ошибка не должна оставлять caller transaction в aborted состоянии.

## Verification и критерии завершения

В кодовых PR запустить `go build ./...`, `go vet` затронутых пакетов,
`go test ./internal/storage ./internal/metadata ./internal/cli` и `onebase check`
для `examples/trade`. Общую матрицу запускать с заданным `TEST_DATABASE_URL`
на настоящем PostgreSQL; секрет подключения не печатать. Проверить также
существующие `TestManagedIndexes_*`, `TestMigrateRenamesLegacyLongIdents_Matrix`,
`TestCurrentLegacyPreflight*`, `TestStagesSurviveFieldRename` и borrowed-scope
регрессии. Обязательные CI остаются по branch protection, включая Windows.

На временной копии historical fixture:

1. Сохранить backup и контрольный снимок. Вызвать CLI dry-run; сверить, что БД
   не менялась и показаны реальные source keys / индексные кандидаты.
2. Выполнить обычную миграцию без manifest: случай removed legacy UNIQUE должен
   отказать до перехода; проверить неизменность исходного снимка.
3. Проверить определения и принять только нужные кандидаты через отдельный
   `--adopt-indexes`; повторить migrate. Сравнить значения/id/карты/ограничения.
4. Выполнить второй migrate, `check`, публичное чтение/запись, запуск сервера;
   проверить отсутствие дублей индексов и ожидаемый исход duplicate write.
5. На другой копии смоделировать отказ/прерывание и восстановить backup;
   подтвердить доступность прежних данных и ограничений после восстановления.

Готово, когда все четыре сценария проходят совместно на SQLite и PG, отрицательные
контроли сохраняют отказ, каждый поддержанный caller доказал rollback своего
scope, нет автоматического signed ownership transfer, preview соответствует
apply, а документация называет оставшиеся отказы и восстановление. Только после
этого кодовые PR могут закрывать соответствующие заявки. Ведомые `hold` снимает
дальнейший уполномоченный маршрут; этот plan-PR их не изменяет.

## Риски, откат и эстимейт

Основные риски: ложная атрибуция внешнего индекса; смешение логического ключа и
физического имени PG; ранний commit rename; SQLite rebuild с потерей индексов;
непреднамеренная смена поведения отложенной ошибки numerator; manifest,
подписывающий уже не тот каталог. Их закрывают точный classifier, отказ при
неоднозначности, единый scope перехода и общая матрица до/после.

Эстимейт A–E: **12,5–19,5 инженерных дней**, плюс независимые REVIEW/CI и
проверка восстановления оператором. Реальные historical fixtures и scope
регистров — главные источники неопределённости; неподдержанные варианты должны
остаться явными отказами, а не расширяться по предположению. Откат кода — revert
отдельного среза до миграции базы; после миграции нужен описанный backup restore.
