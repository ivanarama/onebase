# План 153 — Значения по умолчанию у реквизитов

Дата проектирования: 2026-08-22.
Статус: ✅ **Реализовано** 2026-08-22 (этапы A–D), ветка `feature/153-attribute-defaults`.

Что вышло иначе, чем задумывалось:

- `текущийпользователь` даёт **логин** и применим только к строковому реквизиту.
  Связи «учётная запись платформы ↔ элемент прикладного справочника
  пользователей» в движке нет (строковые политики сопоставляют их по логину),
  и выдумывать её ради дефолта неправильно — ссылку подставляет конфигурация в
  `ПриСозданииНового`.
- Умолчания формы ввода (дата документа, признак активности), жившие в
  HTTP-обработчике, остались **только у формы**: распространить их на DSL и
  REST значило бы изменить поведение существующих конфигураций молча. Они
  вынесены в именованную `applyFormEntryDefaults` и включаются флагом
  `DefaultsOptions.FormEntry`.
- Путей создания оказалось четыре, а не три: `Справочники.X.Создать()` в DSL —
  отдельная фабрика (`internal/ui/dsl_catalogs.go`), она тоже переведена на
  общую точку.
- `default` у реквизита **табличной части** не поддержан и явно отвергается на
  `onebase check`. Строка ТЧ добавляется после создания объекта из трёх разных
  мест (SlickGrid, DSL `Товары.Добавить()`, обработчик события формы), общей
  точки у них нет; принять ключ и не применять его — тот самый молчаливый
  отказ, против которого весь план.
- В `storage.ListParams` добавлен `ExcludeMarked`: источнику `единственный`
  нужно отбросить помеченные на удаление, а фильтра для этого не было.

Повод — вопрос с внедрения: «в конфигурации одна организация, почему её не
подставляют в новый документ?». За вопросом стоит не подстановка единственного
значения, а отсутствие механизма значений по умолчанию как такового: у реквизита
сущности нет ключа `default`, а хука «при создании нового» в движке нет вовсе.
Прикладной слой вынужден заполнять реквизиты вручную — в `ПриОткрытииФормы`
каждой формы и добивать в `ПриЗаписи` каждого документа. В конфигурации ПуТ это
даёт около тридцати мест с одинаковым кодом; при добавлении документа про них
забывают, и документ уходит в базу с пустой организацией.

## Контекст

Аналог в 1С — «Значения заполнения» реквизита плюс `ОбработкаЗаполнения` и
персональные настройки пользователя («Основная организация», «Основной склад»).
Подстановки «если элемент справочника один — возьми его» в 1С из коробки нет, и
это не недосмотр: см. раздел «Про `единственный`».

Ценность механизма не в экономии кликов, а в том, что обещание «этот реквизит
по умолчанию такой» становится **свойством конфигурации**, проверяемым
`onebase check`, а не побочным эффектом кода конкретной формы. Сегодня документ,
созданный из UI, из DSL и через REST, получает разные значения одних и тех же
реквизитов — просто потому, что дефолты прописаны только в форме.

## Что мешает в текущем коде (проверено по `f89e174e`)

1. **Объявить дефолт негде.** `metadata.Field` (`internal/metadata/types.go:29`)
   знает `ID`, `Name`, `Title`, `Type`, `RefEntity`, `EnumName`, `Length/Scale`,
   `AllowInlineCreate`, `Required` — про значение по умолчанию не знает ничего.
   У константы ключ есть: `metadata.Constant.Default` (`types.go:116`, тег
   `yaml:"default"` в `yaml.go:568`), применяется при инициализации хранилища
   (`internal/storage/constants.go:26`). То есть прецедент разбора и типизации
   литерала в репозитории уже есть — расширяется, а не изобретается.
2. **Дефолты сегодня захардкожены в обработчике формы.**
   `internal/ui/handlers_entity.go:274-286` кладёт в `values` текущую дату во
   все поля типа `date` документа и `true` в поле активности. Это единственное
   место в движке, где что-то подставляется при создании, и оно живёт в HTTP-слое
   UI.
3. **Хука «при создании нового» нет.** `ОбработкаЗаполнения` существует
   (`entityservice.Service.Fill`, `internal/entityservice/service.go:1021`), но
   вызывается только на вводе на основании и копировании —
   `handlers_entity.go:292` (`?based_on=`) и `:299` (`?copy=`). Для пустого
   нового документа не вызывается ничего. Имя `ПриСозданииНового` встречается в
   репозитории только в маппинге событий импортёра 1С
   (`internal/onec_forms/events_map.go`) — то есть конфигурации из 1С этот
   обработчик приносят, а исполнять его некому.
4. **Путей создания три, и они независимы** (при реализации нашёлся четвёртый —
   `Справочники.X.Создать()`)**.** UI-форма
   (`handlers_entity.go:232`), DSL `Документы.X.Создать()`
   (`internal/ui/dsl_documents.go:130` — отдельная реализация мимо
   `entityservice`), REST `createObject` (`internal/api/handlers.go:232`) и
   `createObjectV2` (`internal/api/v2.go:154`). Это тот же расклад, который дал
   #366 (DSL-путь не звал `OnUnpost`) и разбор недели 16.08 (#962, «запись
   документа живёт в трёх реализациях»). **Дефолты, приделанные к форме, дадут
   четвёртое расхождение.**
5. **Прецедент правильного решения тоже есть.** Автозаполнение полей по
   строковой политике (`access.AutoFillPredicateFields`,
   `internal/access/row_access.go:355`) вынесено в отдельный пакет и
   вызывается из preflight'а (`internal/api/row_access.go:126`) — логика одна,
   точек вызова несколько. Тем же способом строим и это.

## Синтаксис / YAML

Ключ `default` у реквизита сущности, значение — источник из закрытого списка:

```yaml
# documents/реализациятоваров.yaml
fields:
  - name: Дата
    type: date
    default: сейчас
  - name: Организация
    type: reference:Организация
    default: константа.НашаОрганизация
  - name: Ответственный
    type: string
    default: текущийпользователь
  - name: СпособУчетаНДС
    type: enum:СпособУчетаНДС
    default: ВТомЧисле
  - name: Склад
    type: reference:Склад
    default: единственный
```

Источники (регистронезависимо, как весь DSL):

| Источник | Типы полей | Значение |
|---|---|---|
| литерал | `string`, `number`, `bool`, `enum:*` | как есть, с проверкой типа и принадлежности перечислению |
| `сегодня` / `today` | `date` | начало текущего дня |
| `сейчас` / `now` | `date` | текущие дата-время |
| `константа.<Имя>` | любой, совпадающий с типом константы | текущее значение константы |
| `текущийпользователь` | `string` | логин текущего пользователя (см. «Что вышло иначе») |
| `единственный` | `reference:*` | единственный доступный элемент, иначе пусто (см. ниже) |

Список закрытый: неизвестный источник — **ошибка `onebase check`**, а не молча
пустое поле. Опечатка `константы.НашаОрганизация` должна ловиться до рантайма,
иначе механизм даёт худший вид отказа — тихий.

Совместимость типов проверяется там же: `default: сейчас` на `string`,
`константа.X` другого типа, значение вне перечисления — ошибки конфигурации.

Дефолты применяются **только при создании нового объекта** и только к полям,
которые не заданы явно. Ввод на основании, копирование и `Заполнить()`
отрабатывают после дефолтов и перетирают их — источник данных главнее.

## Хук `ПриСозданииНового`

В модуле объекта (`src/<имя>.os`, там же где `ПриЗаписи`):

```
Процедура ПриСозданииНового(Объект)
    Если ЗначениеЗаполнено(Объект.Организация) Тогда
        Объект.Склад = ЗначениеРеквизитаОбъекта("Склад", НастройкаПользователя());
    КонецЕсли;
КонецПроцедуры
```

Порядок: декларативные `default` → `ПриСозданииНового` (может перебить всё) →
`ОбработкаЗаполнения`/копирование, если создание идёт на основании.

Хук нужен именно как хук: персональные настройки («у Пети свой склад») остаются
**прикладными**. Движку для них хватает `ТекущийПользователь()`
(`internal/dsl/langref/functions.go:1579`, уже есть), `default: константа.X`
для глобального умолчания и этой точки входа — конфигурация читает свой
инфорегистр `СрезПоследних` и подставляет. Встроенного справочника настроек в
движке не заводим: набор настроек, права на них и форма у каждой конфигурации
свои. Прецеденты — планы 85 (задачи) и 89 (версионируемые правила), оба закрыты
прикладным паттерном без правки ядра.

## Про `единственный`

Источник осознанно сделан **опт-ином на конкретном реквизите**, а не поведением
по умолчанию для всех ссылочных полей. Причины, в порядке весомости:

1. **Поведение зависело бы от данных, а не от конфигурации.** Пока организация
   одна — поле заполняется само и человек перестаёт на него смотреть; заведут
   вторую — поле молча станет пустым, а привычка останется. Для необязательного
   реквизита это документы с пустой организацией, обнаруженные на отчётности.
2. **Записанное значение неотличимо от выбранного человеком.** Для
   «Ответственный» это мелочь, для «Организация»/«Склад» — расхождение в учёте.
3. **«Единственный» — неочевидное условие.** Фиксируем явно и в
   `DEVELOPER.md`: не помечен на удаление, не группа (для иерархических),
   активен (если у сущности объявлен `activity`), видим текущему пользователю
   по строковым политикам (план 79). Последнее означает, что для разных
   пользователей одна кнопка даёт разный документ — это допустимо только когда
   конфигурация попросила явно.
4. **Цена на горячем пути.** Открытие нового документа — самая частая операция.
   Запрос делаем `LIMIT 2` (не `COUNT`), и только для полей с этим источником —
   у формы с шестью ссылками не должно появиться шести лишних запросов.

Включение «по умолчанию с возможностью отключить» отвергнуто: это молчаливое
изменение поведения всех существующих конфигураций.

## Изменения в коде

**Метаданные и валидация**
- `internal/metadata/types.go` — `Field.Default string` (сырая строка из YAML).
- `internal/metadata/yaml.go` — чтение тега `default` у реквизита сущности и у
  реквизита табличной части (там дефолт осмыслен для новой строки ТЧ; см. этапы).
- `internal/metadata/validate.go` — разбор источника, проверка совместимости с
  типом поля, существования константы/перечисления/значения.
- `internal/configcheck` — сообщение с именем сущности и реквизита.

**Применение (новый пакет или файл в `entityservice`)**
- `ApplyDefaults(ctx, entity, obj *runtime.Object, env)` — единственная
  реализация. `env` даёт доступ к константам, текущему пользователю и хранилищу
  (для `единственный`). Заполняет только незаполненные поля.
- `entityservice.Service.NewObject(ctx, entity) (*runtime.Object, error)` —
  публичная точка «создать новый объект с дефолтами и хуком», по образцу
  существующего `Service.Fill` (`service.go:1021`).

**Точки вызова (все три пути)**
- `internal/ui/handlers_entity.go:274` — заменить захардкоженную подстановку
  даты и активности на вызов `NewObject`; текущее поведение сохранить дефолтами
  «по умолчанию» для полей `date` документа и поля активности, чтобы
  конфигурации без ключа `default` не изменили поведение.
- `internal/ui/dsl_documents.go:130` — `Документы.X.Создать()`.
- `internal/api/handlers.go:232` и `internal/api/v2.go:154` — REST create.

**Хук**
- `ПриСозданииНового` в списке хуков модуля объекта, исполнение —
  через `Service.runHook` с общим дедлайном (`service.go:108`), чтобы не
  повторить историю #962 с хуками мимо дедлайна.
- `internal/dsl/langref` — описание хука в справке и `docs/dsl-reference.md`.

**Документация**
- `DEVELOPER.md` — таблица источников и условие «единственный».
- `docs/features.md` — раздел `status: testing`.
- `CHANGELOG.md` — абзац про изменение поведения: значения, ранее не
  заполнявшиеся, теперь заполняются.

## Тесты

- `metadata` — разбор `default` для каждого источника; ошибки валидации на
  неизвестный источник, несовместимый тип, отсутствующую константу,
  значение вне перечисления.
- Применение — таблица «источник → ожидаемое значение», отдельно случай
  «поле уже заполнено — дефолт не перетирает».
- **Матричный тест** `dbtest.ForEachDialect` на `единственный`: ноль элементов,
  один, два, один + один помеченный на удаление, один неактивный. Источник
  ходит в БД, значит расхождение диалектов возможно — правило CLAUDE.md.
- **По одному тесту на каждый из трёх путей создания** через публичную точку
  входа: HTTP-запрос формы, DSL-процедура с `Создать()`, REST `POST`. Именно
  здесь фикс проверяется как пользователь — прецедент #611.
- `единственный` под строковой политикой: два элемента в базе, один видим
  пользователю → подставляется; оба видимы → пусто.
- `ПриСозданииНового`: перебивает декларативный дефолт; ошибка в хуке
  возвращается пользователю, а не роняет форму; `ОбработкаЗаполнения` после
  него перетирает значения.

## Verification

1. `examples/trade`: `default: сейчас` на дате, `константа.X` на организации,
   `текущийпользователь` на ответственном.
2. `onebase check --project examples/trade` — зелёный; затем испортить источник
   опечаткой и убедиться, что `check` краснеет с внятным сообщением.
3. `onebase run` → «Создать» документ в браузере: поля заполнены.
4. `onebase procrun` с процедурой, вызывающей `Документы.X.Создать()` и
   печатающей реквизиты — те же значения, что в форме.
5. `curl -X POST /api/v2/documents/...` с телом без этих полей — в ответе те же
   значения.
6. Завести второй элемент справочника со `единственный` — поле пустое, форма
   работает.

## Этапы и эстимейт

| Этап | Содержание | Оценка |
|---|---|---|
| A | `Field.Default`, источники литерал/`сегодня`/`сейчас`/`константа.X`/`текущийпользователь`, валидация в `check`, `ApplyDefaults` + `NewObject`, вызов из трёх путей, тесты | 2–3 дня |
| B | Хук `ПриСозданииНового`, порядок с `ОбработкаЗаполнения`, справка DSL | 1–2 дня |
| C | Источник `единственный` с матричным тестом и учётом строковых политик | 1 день |
| D | `DEVELOPER.md`, `docs/features.md`, `CHANGELOG.md`, пример в `examples/trade` | 0.5 дня |

Этапы A и B закрывают запрос целиком; C — удобство для маленьких конфигураций,
и его можно не делать, если A окажется достаточным.

## Что осознанно не делаем

- **Встроенный справочник настроек пользователя.** Прикладная область, см. выше.
- **Дефолты «по умолчанию включены» для всех ссылочных полей.** См. «Про
  `единственный`».
- **Вычисляемые выражения в `default`** (`default: "=Организация.Склад"`).
  Для этого есть `ПриСозданииНового`; выражения в YAML превращают метаданные во
  второй язык без отладчика и справки.
