# План 157 — Программное открытие формы из DSL (`ОткрытьФорму`)

Дата проектирования: 2026-08-26.
Статус: 📋 **проектирование**, код не начат.
Уровень: **движок** — DSL (билтин), `internal/ui` (side-channel события и
предзаполнение формы), клиентский JS, права/RLS.
Заявка: [#1134](https://github.com/ivanarama/onebase/issues/1134) (автор
`boffik`) — зонтичная, закрывается не первым срезом, а всем планом.
Зависит от: план [46](46-tablepart-commands-and-picker.md) — двухфазная схема
подбора, тот же механизм side-channel и та же терминальная семантика.

## Зачем

Конвертированная из 1С конфигурация падает на `ОткрытьФорму(...)`: билтина в
движке нет вовсе. По репозиторию имя встречается дважды и только в комментариях
(`internal/ui/picker.go:28`, `Plans/46-tablepart-commands-and-picker.md:106`) —
как пояснение к аналогии, а не как реализация. Проверка конфигурации
останавливается на «неизвестная функция» (`internal/configcheck/check.go:873`).

Без программной навигации не переносятся два типовых сценария 1С:

- «создать документ на основании и открыть его на правку с заполненной шапкой»;
- «из списка открыть карточку с преднастроенным отбором».

Первый не закрывается ничем: обработчик может создать и записать объект
(`Документы.X.Создать/Записать`), но пользователя к нему не приведёт — он
останется на исходной форме и увидит только `Сообщить`. Второй частично
закрывается ручной навигацией.

## Граница плана

**Срез 1 (этот план целиком описывает его, остальные — эскизом):** открыть
форму объекта или нового объекта из обработчика события управляемой формы, с
предзаполнением реквизитов шапки значениями из `Структура`.

```
ОткрытьФорму("Документ.ЗаказПокупателя.ФормаОбъекта", Знач)   // существующий
ОткрытьФорму("Документ.ЗаказПокупателя.ФормаОбъекта", Парам)  // новый + предзаполнение
```

**Срез 2 (не в этом заходе):** возврат значения — `Оповещение`, модальность,
«открыл → выбрал → вернулся». Требует модели продолжения, которой в платформе
нет: обработчик завершается вместе с HTTP-запросом, состояния «ждём ответа
пользователя» не существует.

**Срез 3 (не в этом заходе):** открытие списка с отбором и открытие
произвольных форм — отчётов, обработок, форм регистров.

**Не делаем и не планируем здесь:** открытие нескольких форм за один вызов
(payload одиночный, как `pickerData`), открытие форм чужой базы, произвольный
URL вместо имени формы.

## Механизм

Ровно тот же, что у подбора (план 46), и это главное решение плана: не
изобретать вторую схему навигации.

**Фаза 1.** DSL-обработчик вызывает `ОткрытьФорму(Путь, Параметры)`. Билтин
ничего не открывает — складывает payload в side-channel, как `ПоказатьПодбор`
(`internal/ui/picker.go:62`, регистрация — `handlers_managed_events.go:356` и
`:1016`). Семантика **терминальная**: код после вызова выполнится, но на UI не
повлияет; в `ai-guide` это надо написать прямо, иначе повторится грабля подбора.

**Фаза 2.** После `interp.Run` сервер кладёт payload в ответ события новым полем
`openForm` рядом с `pickerData` (`formEventResponse`,
`internal/ui/handlers_managed_events.go:52`). Клиент, увидев его, уходит на
адрес формы.

Адреса уже есть, изобретать нечего:

| Что открываем | Маршрут |
|---|---|
| существующий объект | `/ui/{kind}/{entity}/{id}` (`server.go:386`) |
| новый объект | `/ui/{kind}/{entity}/new` (`server.go:372`) |

**Предзаполнение — единственная по-настоящему новая часть.** Сегодня
`/ui/{kind}/{entity}/new` не умеет принимать значения: в обработчике формы из
query читается только `_popup` (`handlers_entity.go:355`). Значения нельзя
просто пробросить в query-строку: это открытый канал, где пользователь
подменит любое поле, включая те, которых нет на форме.

Поэтому предзаполнение живёт на сервере: билтин кладёт значения в
серверную сессию (короткоживущий одноразовый ключ), клиент получает в
`openForm` только адрес и этот ключ, форма при отрисовке ключ гасит. Так же,
как ведёт себя `pickerData`: данные готовит сервер, клиент носит ссылку на них.

## Безопасность

Предзаполнение — это запись значений в объект **по имени поля из DSL**. Без
проверок это дыра, и проверок нужно три:

1. **Существование и тип.** Имя поля есть в метаданных сущности, значение
   приводится к типу поля. Неизвестное поле — ошибка конфигурации на
   `onebase check`, а не молчаливое игнорирование.
2. **Права на объект.** Открытие формы обязано пройти ту же проверку доступа,
   что и прямой переход по адресу. Иначе `ОткрытьФорму` становится обходом прав:
   пользователь без доступа к документу получает его форму «изнутри» обработчика.
3. **RLS.** Предзаполненное значение не должно выводить объект из области
   видимости пользователя (например, подстановка чужой организации в поле,
   по которому режет RLS). Проверять на **записи**, а не на открытии: форма
   ещё ничего не сохранила, и запрет на этом шаге был бы ложным.

Отдельно: `ОткрытьФорму` не должен становиться способом обойти
`ОбработкаПроверкиЗаполнения` и обязательность реквизитов — форма открывается
как обычно, со всеми проверками при записи.

## Что придётся тронуть

- `internal/ui/openform.go` (новый) — payload, билтин, валидация полей по
  метаданным. Зеркало `picker.go`.
- `internal/ui/handlers_managed_events.go` — поле `OpenForm` в
  `formEventResponse`, регистрация билтина в обеих точках (`:356`, `:1016` —
  их две, и вторую легко забыть).
- `internal/ui/handlers_entity.go` — приём предзаполнения на `/new` и на форме
  существующего объекта.
- `webassets/.../managed.js` — переход по `openForm` в ответе события.
- `internal/configcheck` — `ОткрытьФорму` в списке известных функций плюс
  проверка первого аргумента: путь формы разбирается статически, опечатка в
  `"Документ.ЗаказПокупатля.ФормаОбъекта"` обязана падать на `check`, а не в
  рантайме у пользователя.
- `internal/cli/aiguide.go` — раздел о навигации и терминальной семантике.
- `internal/converter` — маппинг вызова из XML-выгрузки 1С.

## Проверки

- Матричных тестов SQL здесь нет — семантика не задевает БД.
- Тест идёт **через публичный путь**: POST события формы → в ответе `openForm`
  → GET по этому адресу → предзаполненные значения в отрисованной форме.
  Вызов билтина напрямую не считается (грабля #611).
- Обязательный негативный тест: предзаполнение поля, которого нет; поля, к
  которому нет прав; открытие формы объекта, недоступного пользователю.
- `onebase check --project examples/trade` после добавления в конфигурацию
  примера с `ОткрытьФорму`.

## Что нужно узнать до кода

Автор заявки не сказал, какой именно код падает при конвертации. Разница
принципиальная: если в конфигурации только `ОткрытьФорму(...)` без обратного
вызова — срез 1 закрывает сценарий целиком; если рядом стоит
`ОткрытьФорму(..., Оповещение)` или `ОповеститьОВыборе`, то без среза 2 польза
близка к нулю, и порядок срезов надо пересматривать. **Спросить в #1134 до
начала работ.**

## Нарезка на заявки

Срез 1 разбирается на три независимо реализуемых куска — их и заводить
заявками, по одной за раз:

1. Билтин `ОткрытьФорму` + `openForm` в ответе события + переход в JS
   (без предзаполнения — открывается пустая форма или существующий объект).
2. Предзаполнение реквизитов шапки через серверный одноразовый ключ + проверки
   из раздела «Безопасность».
3. Статическая проверка пути формы в `configcheck`, раздел в `ai-guide`,
   маппинг в конвертере.
