## Синтаксис / YAML

Нового синтаксиса DSL, YAML и флагов совместимости не требуется. Существующие
запросы получают исправленный результат, например:

```text
ВЫБРАТЬ Наименование ИЗ Справочник.Товар
ГДЕ Ссылка В (ВЫБРАТЬ Товар ИЗ РегистрНакопления.РегА.Остатки())

ВЫБРАТЬ П.Наименование, П.Цена
ИЗ (ВЫБРАТЬ Наименование, Цена ИЗ Справочник.Товар) КАК П
ГДЕ П.Цена > 5 УПОРЯДОЧИТЬ ПО П.Цена
```

При остатках «Болт: 7, Гайка: 1» первый запрос возвращает Болт и Гайку;
NOT IN без NULL — только Шайбу. При ценах 2, 9, 100 второй возвращает 9, 100
в числовом порядке. Добавление `LEFT JOIN (ВЫБРАТЬ 1 КАК Х) КАК Ф ПО Ф.Х = 1`
не должно менять доказанный тип `Цена` физического источника, если состав
колонок Ф доказан и не содержит `Цена`.

## Наблюдаемая семантика и инварианты

### 1. Потребитель проекции и ссылка

Для каждой SELECT-области определить назначение результата, а не проверять
`scopeID > 0` или одну только глубину:

- IN/NOT IN, производный FROM/JOIN и скалярный подзапрос в сравнении потребляют
  **значения**. Голая ссылка экспортирует UUID/FK под прежним логическим
  выходным именем. Квалифицированное поле и `Поле.Ссылка` остаются идентификаторами.
- Внешний пользовательский SELECT сохраняет прежнее представление голой ссылки.
  Явное `Поле.Наименование` всегда остаётся текстом, включая вложенный запрос.
- Скалярный подзапрос, непосредственно используемый для пользовательского
  представления во внешней проекции, сохраняет прежний вывод. Это существующий
  контракт `TestUnionReferenceReviewMatrix`, а не повод заменить все дочерние
  SELECT на UUID. Для цепочки скалярных обёрток назначение наследуется от
  реального потребителя; неизвестное составное выражение не получает новую
  типизацию по догадке.
- UNION наследует назначение всего compound SELECT: ветви верхнего вывода
  сохраняют представления, ветви производного/предикатного UNION — значения.
  Коррелированный доступ разрешается по прежнему ближайшему владельцу.
- В value-проекции группировка голой ссылки использует ту же идентичность UUID.
  Два объекта с одинаковым наименованием остаются двумя группами. Сортировка
  выбранной ссылки/алиаса согласована с экспортированным значением; для
  сортировки по представлению используется явное поле представления. Внешнее
  группирование/сортировка представлений сохраняет прежний контракт.
- Не добавлять авто-JOIN ради голого UUID; сохранять JOIN, необходимый для
  явной навигации, корреляции, прав и масок. Навигация по присоединённой ссылке
  внутри собственного ON, отвергаемая сегодня, не становится разрешённой.

NULL-ссылка остаётся SQL NULL, не UUID нулей и не пустой строкой. IN/NOT IN
сохраняют SQL three-valued logic: NULL в подзапросе может исключить строки
из NOT IN; не переписывать это молча в NOT EXISTS. Скалярный подзапрос с нулём
строк даёт NULL; многозначный — существующее поведение СУБД, без нового LIMIT 1.

### 2. Имена, владельцы и типы

Предлагаемая внутренняя модель (имена типов уточнить в кодовом PR):
`derivedOutputSchema{completeNames, columns}` и сведения по каждой колонке:
логический/эмитированный ключ, количество вхождений, доказанный FieldType,
цель ссылки при доказанности, происхождение, способ представления, nullable.
Это описание компилятора, не новый публичный формат Result и не схема БД.

1. Сначала вывести фактически экспортируемые имена, затем типы. Явный alias
   резервируется даже у неизвестного выражения. Имя известно, тип неизвестен —
   это не отсутствие колонки. Уникальный владелец без типа ещё не разрешает CAST.
2. Простое поле, скобки вокруг него и MIN/MAX сохраняют доказанный тип;
   цель reference сохраняется только при экспортировании идентификатора.
   Представление ссылки имеет текстовый тип, даже если исходное поле reference.
   Произвольная функция, арифметика, CAST и неописанный агрегат не получают
   тип из имени либо из соседнего источника. Новое доказательство литералов
   допустимо только с отдельными положительными/отрицательными тестами;
   для `1 КАК Х` уже достаточно доказать отсутствие имени `Цена`.
3. Состав `*`/`А.*` полный только при точном раскрытии реальных выходов
   источников, включая VT. При неполном раскрытии невозможно доказать отсутствие
   одноимённого поля; сохраняется отказ от вывода владельца/типа.
4. У неквалифицированной колонки владелец единственный, только если остальные
   источники доказанно не экспортируют её имя. Полностью неизвестный источник
   препятствует такому выводу. Квалифицированная колонка разрешается в своём
   источнике; локальный alias затеняет родительский даже при неизвестном типе.
5. Дубликаты aliases, логические/физические совпадения, сокращение SQLIdent,
   системные `id`/`posted` и сочетание со звёздочкой не должны восстанавливать
   уже отвергнутый тип. Не забирать тип у одноимённого поля внешней области.
6. Реальная неоднозначность не исправляется выбором первого источника.
   Сохраняется диагностируемая неоднозначность; при введении ранней ошибки
   Compile она должна иметь явный тест и описание совместимости. Не требовать
   нового отказа Compile для любого выражения с неизвестным типом: обычный
   SQL может исполниться без дополнительных преобразований.
7. Числовая физическая проекция SQLite остаётся точным TEXT. CAST применяется
   только при доказанной числовой семантике потребляющего оператора. MIN/MAX
   доказанного number также должны работать численно на SQLite; это явная
   дельта, требующая тестов 2/9/100, а не простое копирование метаданных.

Общий resolver должен обслуживать SQL-преобразования и существующий
`buildScalarColumnTypes`, сохраняя date/localdate и доказательство выходных
ключей. Можно внедрять через адаптеры; нельзя удалять защиту коллизий ради
«единой карты типов». Публичные RefColumns/BoolColumns/DateColumns/TypedColumns
не расширять на сложные проекции в рамках этого плана.

### 3. Числа, текст и соединения

- Доказанный number на SQLite получает прежний CAST в WHERE/HAVING/ORDER BY
  и числовой MIN/MAX; PostgreSQL использует свои numeric-колонки. Сравнение
  с литералом, параметром и другой числовой колонкой проверяется отдельно.
- Для string/enum восстанавливается прежняя граница пустого текста:
  `NULL <> "Закрыт"` главного источника в разрешённом сравнении учитывается как
  пустой текст; присоединённый/производный источник получает только существующее
  расширение WHERE с литералом/параметром. Сам вывод NULL не меняется.
- ON получает только отдельное числовое правило: доказанные числовые операнды
  SQLite приводятся перед сравнением, включая числовой алиас производной
  таблицы. Не применять CAST ко всей секции FROM, именам таблиц, aliases,
  значениям ссылок или тексту с цифрами. Нужна точная граница ON-предиката.
- В ON не добавляется COALESCE строк. NULL не совпадает с NULL, LEFT JOIN
  сохраняет неприсоединённую строку. Сравнение текстовых колонок разных
  источников также не получает общее правило «NULL равен пустой строке».

### 4. UNION

Имена берутся из первой ветви, типы сопоставляются **по позиции всех ветвей**.
Числовой тип доказан только при согласованных number-проекциях; reference —
только при согласованной цели и способе представления. NULL-литерал допускает
доказанный тип другой ветви при явной проверке nullable. Разные цели ссылок,
number/string или неизвестное выражение не дают доказанного общего типа.

Для доказанного числового compound ORDER BY SQLite нужен внешний SELECT над
исходным UNION/UNION ALL с CAST ключа сортировки: CAST непосредственно в ORDER
BY compound SELECT может быть запрещён SQLite. Внутренние ветви сохраняют
значения, DISTINCT/ALL и имена; внешний слой не добавляет скрытые колонки в
публичный результат. LIMIT/OFFSET применяются после общей сортировки ровно
один раз; ordinal/alias и несколько ключей разрешаются по первой проекции.
Не помещать CAST в сами числовые проекции ради сортировки: это меняет точность
вывода и дедупликацию. Для недоказанного смешанного UNION не обещать числовой
порядок и не приводить текст насильно; сохраняется исходная SQL-семантика.

## Хранилище / SQL, совместимость и миграция

DDL, обновления сохранённых данных, перестройка итогов и миграция YAML не нужны.
Существующие запросы продолжают компилироваться в поддержанной области, но
намеренно меняют неверные строки/итоги, числовой порядок и value-проекции ссылок.
Обходы `З.Товар`/`Товар.Ссылка` остаются рабочими. Голая ссылка производной
таблицы, ранее дававшая представление, после среза A даёт UUID; для старого
намеренного текста следует явно выбрать `.Наименование`.

Отдельная активная [#1351](https://github.com/ivanarama/onebase/issues/1351)
и её [PR #1442](https://github.com/ivanarama/onebase/pull/1442) посвящены
публичной типизации сложных результатов/диагностике. Их маршрут, ветку и
protocol-review не менять и не объединять с этой работой. Перед каждым
кодовым срезом сверять его diff с принятыми изменениями #1351. Общий resolver
не должен обходить существующие ограничения дескрипторов либо обещать DSL-ссылку
там, где Run отдаёт сырой UUID. Конфликт контрактов выносится отдельно до push.

Обновление заметок о поведении — в кодовых PR (`CHANGELOG.md`,
`docs/dsl-reference.md` и справочник языка по фактической дельте).
PLAN меняет только этот документ и его строку в индексе.

обязательный CI и человеческий ship. Следующий начинается после принятого
предшественника с актуального main. Оценки включают тесты и документацию.

зафиксировать её ограничение тестом, не менять тип на основании соседнего поля.

## Тесты

Все новые regression-тесты — внешний `package query_test`,
`dbtest.ForEachDialect`, `query.Compile → query.Run`. Пакетные приватные тесты
resolver допустимы как дополнение. SQL-asserts показывают причину, но приёмка
проверяет фактические строки, имена, порядок и типы значений. Для типов, чья
драйверная форма различается сегодня, явно сохранить разрешённые формы; не
требовать нового decimal/DSL-reference результата от Run ради этой работы.

Общая fixture: три товара с устойчивыми UUID и ценами 2/9/100; два с одинаковым
наименованием; документы с суммами 9/100 и отсутствующей ссылкой; строки NULL,
пусто и «Закрыт»; накопительный/информационный регистры и их поддержанные VT.
Права и маски проверяются доступными интеграционными fixture, не отключаются.

| Область | Обязательные проверки фактического результата |
|---|---|
| Ссылки A | IN → два товара; NOT IN без NULL → третий; NOT IN с NULL → SQL unknown, без «лишних» товаров; scalar comparison → правильный UUID; LEFT → сохранённая неприсоединённая строка; INNER → только совпавшие; GROUP → два разных UUID с одинаковым именем |

## Verification

Для каждого кодового среза:

```bash
go build ./...
go test ./internal/query ./internal/access ./internal/storage ./internal/dsl/interpreter
go run ./cmd/onebase check --project examples/trade
```

В окружении CI с отдельной PostgreSQL test-базой задать `TEST_DATABASE_URL`
и повторить `go test -count=1 ./internal/query` с проверкой реального запуска
обоих диалектов. Успешный SQLite-прогон при пропущенной PG-ветке не завершает
матричную приёмку. Добавить точные имена новых тестов в описание кодового PR.

Пользовательский smoke: создать маленькую конфигурацию fixture, выполнить
`onebase check`, `migrate`, наполнить её обычными публичными средствами,

Проверить NULL отдельно от пустого текста и одинаковые представления ссылок.
Не выполнять destructive cleanup на пользовательской базе для проверки NOT IN.

Проверки самого plan-PR: `go run ./tools/plannum`, `git diff --check`,
существование относительных файловых ссылок и уникальный номер по main и
открытым plan-PR. Продуктовые тесты не заменяются успешной проверкой Markdown.

## Риски, откат и критерии завершения

- Основной риск A — изменение предназначенного для вывода скалярного SELECT;
  защищается явным consumer-use и прежними presentation-тестами.
- Основной риск B/C — ложный владелец/тип из неполной схемы; неизвестные имена,
  дубликаты и звёздочки сохраняют консервативное доказательство. Не смешивать
  известность имени, известность типа и публичный дескриптор результата.
- CAST SQLite сохраняет имеющуюся NUMERIC-семантику сравнений, не обещает
  произвольной decimal-точности арифметики. Проверить большие числа и дроби;
  новый механизм точной арифметики этим планом не вводится.
- Внешний UNION wrapper может изменить план выполнения: проверить SQL и
  EXPLAIN на fixture, наличие LIMIT/OFFSET и отсутствие лишних публичных колонок.
  Широкая оптимизация производительности остаётся отдельной работой #2255.
- Все срезы откатываются revert соответствующего кодового PR в обратном порядке
  зависимостей. Данные и DDL не меняются; возвращаются прежние ошибки запросов.
  До нового исправления пользоваться квалифицированной ссылкой/явным текстом,
  а результаты NOT IN проверять на копии данных.

План принят только после отдельного REVIEW/CI и merge человеком через обычный
конвейер. Реализация завершена, когда A–E приняты, общая матрица прошла SQLite
и PostgreSQL, обе заявки воспроизводятся правильно, документация описывает
фактическую дельту, а #1351 не получила скрытого изменения своего контракта.
Промежуточные кодовые PR ссылаются на #2247/#2248 без закрывающих ключевых слов;
только финальный кодовый PR после общей приёмки закрывает обе заявки.
