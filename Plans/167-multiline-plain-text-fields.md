# План 167 — многострочный обычный текст во всех формах записи

Дата проектирования: 2026-09-08.
Статус: 📋 **проектирование**, продуктовый код в этом PR не меняется.
Заявка: [#1390](https://github.com/ivanarama/onebase/issues/1390).
Выбранный вариант: **2** — сначала отдельный технический план, затем единый
`multiline` у строкового поля с наследованием в авто- и managed-формах.

## Контекст

Обычный `string` сейчас всегда редактируется однострочным `<input>` в
автоформе сущности и в форме новой записи регистра сведений. Это делает
непригодными памятки, комментарии и другой текст из нескольких абзацев. Тип
`richtext` задачу не решает: он хранит HTML, подключает Quill и требует иной
модели доверия к содержимому.

В managed-форме уже существует `FormElement.Multiline`, но контракт неполон:

- он действует только в ветке найденного поля сущности;
- для объявленного реквизита формы, включая `save: false`, рендерер всегда
  выбирает однострочный `<input>`;
- `height` элемента не используется, а textarea всегда получает `rows="5"`;
- булево поле не отличает отсутствующий `multiline` от явно заданного
  `multiline: false`, поэтому корректное наследование с переопределением
  выразить нельзя;
- преобразование managed-форм через `internal/onec_forms` не переносит
  `multiline`, хотя прямой YAML-загрузчик `metadata.FormElement` его читает.

Поле хранения (`metadata.Field`) общего типа используется также в табличных
частях и накопительных регистрах. Добавить туда признак без проверки контекста
нельзя: конфигурация будет обещать многострочный ввод там, где отдельной формы
записи нет или редактором служит ячейка SlickGrid.

## Выбранный контракт

### Граница действия

`multiline` — признак представления обычного текста, а не новый тип данных.
Он разрешён только при `type: string`:

1. в `fields` справочника или документа;
2. в `dimensions` и `resources` регистра сведений.

Для табличных частей, накопительных регистров, их `attributes`, ссылок,
перечислений, чисел, дат, `bool`, `image` и `richtext` значение
`multiline: true` должно быть отвергнуто `onebase check` с путём к полю. Это
не даёт неисполняемому presentation-признаку приниматься молча. Отсутствие
ключа и `multiline: false` совместимы с прежним поведением.

`metadata.Field.Multiline bool` хранит итоговый признак поля. В SQL и DSL поле
остаётся `string`: длина, индексы, поиск, сериализация, API и формат backup не
меняются.

### Наследование в managed-форме

Локальная настройка элемента должна различать три состояния. Поэтому
`FormElement.Multiline` становится `*bool` с `yaml:"multiline,omitempty"`, а
рендерер использует один helper, например
`effectiveFormElementMultiline(entity, form, element)`:

| Источник данных | `multiline` элемента | Результат |
|---|---:|---|
| `Объект.<Поле>` или legacy-путь без корня | не задан | значение `Field.Multiline` |
| `Объект.<Поле>` | `true` / `false` | явное локальное переопределение |
| `Форма.<Реквизит>` | не задан | однострочный ввод |
| `Форма.<Реквизит>` | `true` | textarea независимо от `save`, в том числе при `save: false` |
| `Форма.<Реквизит>` | `false` | однострочный ввод |

Наследование применяется только к `ПолеВвода` с обычным строковым полем или
строковым реквизитом формы. Оно не перехватывает специальные редакторы ссылок,
enum, даты, чисел, флажка, файла, картинки, richtext и `ПолеКода`.
`Список.*`, поля таблиц и неизвестный `data_path` также не наследуют признак.

Явный `false` нужен не ради текущей автоформы, а чтобы форма могла компактно
показать канонически многострочный реквизит в отдельном контексте. При переходе
с `bool` на `*bool` все конструкторы и тестовые литералы обязаны задавать
указатель только для явного значения; `nil` означает именно наследование.

### Высота и HTML

- `height` многострочного элемента задаёт число видимых текстовых строк и
  попадает в HTML-атрибут `rows`.
- Положительное значение используется как есть. Ноль/отсутствие даёт дефолт
  **5 строк**. Отрицательная высота отклоняется валидацией формы.
- В автоформе элемента нет, поэтому поле с `Field.Multiline` получает те же
  5 строк.
- Ширина остаётся текущей (`width: 100%`), браузер может увеличивать textarea
  по вертикали. `height` других видов элементов этим планом не переопределяется.
- Значение выводится через `html/template`, поэтому остаётся обычным
  экранированным текстом. HTML не становится доверенным, Quill и санитайзер
  richtext не подключаются.
- Имена, `required`, `readonly`, `accesskey`, `hint`, `ПриИзменении`, маска
  доступа и обычная отправка формы сохраняют действующую семантику. Новый
  helper выбирает только вид контрола.

## Синтаксис / YAML

Автоформа сущности:

```yaml
name: Клиенты
fields:
  - name: Информация
    type: string
    multiline: true
```

Форма новой записи регистра сведений:

```yaml
name: ПамяткиОператора
dimensions:
  - name: Вид
    type: string
resources:
  - name: Текст
    type: string
    multiline: true
```

Managed-форма наследует поле, если ключ у элемента отсутствует:

```yaml
- kind: ПолеВвода
  name: Информация
  data_path: Объект.Информация
  height: 8
```

Явное переопределение и нехранимый реквизит формы:

```yaml
attributes:
  - name: Подсказка
    type: string
    save: false
elements:
  - kind: ПолеВвода
    name: Подсказка
    data_path: Форма.Подсказка
    multiline: true
    height: 6
  - kind: ПолеВвода
    name: КороткоеПредставление
    data_path: Объект.Информация
    multiline: false
```

## Хранилище / SQL

Изменений схемы БД нет. `multiline` не входит в DDL, не меняет тип колонки и не
требует data migration. Старые конфигурации и базы открываются без преобразования.

Переводы строк проходят по существующему пути HTML form → строковое значение →
storage. План не вводит отдельной нормализации CRLF/LF и не переписывает уже
сохранённые данные. Если единая нормализация понадобится для API/DSL/обмена, это
отдельный контракт, а не побочный эффект рендерера.

## Совместимость и миграция

- Для старых YAML `Field.Multiline == false`, а `FormElement.Multiline == nil`;
  HTML остаётся байт-в-байт прежнего вида за исключением неизбежного
  форматирования шаблона.
- Старое `multiline: true` элемента продолжает давать textarea. После перехода
  на указатель оно обязано пройти direct load, OneBase YAML round-trip и
  рендерер без ручной миграции файла.
- Явное старое `multiline: false`, которое раньше совпадало с отсутствием,
  приобретает полезный смысл override. Это совместимое усиление: до появления
  `Field.Multiline=true` результат всё равно однострочный.
- Добавление/удаление field-level ключа не затрагивает данные. Откат бинарника
  допустим только после удаления нового ключа из конфигурации: старый
  `onebase check` справедливо сочтёт его неизвестным.
- Экспорт в 1С не должен превращать `height > 1` в многострочность и наоборот.
  При отсутствии явного эквивалента в поддерживаемой XML-схеме конвертер обязан
  сохранить известные данные OneBase либо выдать видимое предупреждение, но не
  обещать ложный round-trip.

## Последовательность небольших PR-срезов

### Срез A — метаданный контракт и инструменты (~1.5–2 дня)

1. Добавить `Field.Multiline`, parsing и контекстную validation.
2. Перевести element-level значение на tri-state и ввести effective/rows helpers
   без включения новой ветки HTML.
3. Обновить configcheck, JSON Schema, конфигуратор и OneBase YAML bridge
   `internal/onec_forms`.
4. Зафиксировать отсутствие SQL-изменений и запрет недействующих контекстов.

Публичная приёмка: временный проект проходит `onebase check` с multiline у
строкового поля сущности и ресурса регистра сведений; та же команда отвергает
число, поле ТЧ и накопительный регистр. Сохранение объекта через HTTP
конфигуратора и YAML → IR → YAML сохраняет `true`, `false` и absence раздельно.

### Срез B — автоформы сущности и регистра сведений (~1 день)

1. В `page-form` добавить plain textarea для разрешённого поля.
2. В `page-inforeg-form` применить тот же контракт к dimensions/resources.
3. Не менять списки, фильтры, табличные части и richtext assets.

Публичная приёмка: GET реальной формы сущности и
`/ui/inforeg/<name>/new` возвращает textarea с `rows="5"`; POST нескольких
абзацев и повторный GET формы сущности показывают сохранённый обычный текст
экранированным. Конфигурация без ключа на тех же маршрутах возвращает input.

### Срез C — managed-формы, высота и документация (~1.5–2 дня)

1. Подключить effective-helper в `page-managed-form`.
2. Покрыть наследование `Объект.*`, explicit false и `Форма.*` с `save:false`.
3. Использовать `height` как rows, сохранить required/readonly/events.
4. Добавить подтверждённый element-level round-trip XML либо явное
   предупреждение об отсутствии соответствия; обновить документацию.

Публичная приёмка: GET managed-формы через `renderEntityForm` показывает
унаследованную textarea нужной высоты; `multiline: false` возвращает input;
нехранимый `Форма.Подсказка` с `multiline: true` приходит в обработчик события
с несколькими строками и не появляется среди сохраняемых полей объекта.

Первые два среза используют `Refs #1390`. Только последний срез, после зелёной
сквозной проверки всех путей, использует `Fixes #1390`.

## Тесты

- `internal/metadata`: загрузка entity/info-register YAML; запреты неверного
  типа и контекста; tri-state element YAML.
- `internal/configcheck` и `internal/cli`: `onebase check`/JSON Schema принимают
  только поддержанный контракт и называют точный путь ошибки.
- `internal/launcher`: HTTP round-trip редактора сущности/регистра не стирает
  `multiline`; смена типа со string снимает недействующий ключ.
- `internal/onec_forms`: YAML round-trip `nil/true/false`; XML fixture для
  явного `MultiLine`, если он поддерживается форматом, без эвристики по height.
- `internal/ui`: HTTP GET/POST автоформы сущности; GET формы регистра сведений;
  managed GET/event-submit для наследования, override, `save:false`, rows,
  readonly и escaping.
- Регрессия обязана идти через публичный handler/CLI, а не только выполнять
  `tpl.ExecuteTemplate` или вызывать helper напрямую.

Проверки каждого среза: `go test ./internal/metadata ./internal/configcheck
./internal/cli ./internal/launcher ./internal/onec_forms ./internal/ui`, затем
`go test ./...`. PostgreSQL integration не обязателен для UI-признака без DDL,
но общий CI остаётся обязательным.

## Verification

1. Создать каталог с `Информация: string, multiline: true`, выполнить
   `onebase check`, миграцию SQLite и открыть автоформу новой/существующей записи.
2. Ввести три строки с символами `<>&`, сохранить, открыть запись повторно:
   строки видны в textarea, символы не исполняются как HTML.
3. Создать регистр сведений с многострочным строковым ресурсом, открыть форму
   новой записи и сохранить несколько абзацев.
4. В managed-форме проверить четыре случая: inheritance, `true`, `false`,
   `Форма.* save:false`; для `height: 8` DOM содержит `rows="8"`.
5. Удалить все новые ключи и сравнить формы с прежним поведением; richtext и
   `ПолеКода` по-прежнему используют собственные редакторы.
6. Запустить `onebase check` на отрицательных примерах (number, ТЧ,
   накопительный регистр) и убедиться, что каждый даёт понятную ошибку.

## Риски и откат

- **Неявное разрастание существующих managed-форм.** Его ограничивает
  наследование только при новом field-level `true`; explicit false даёт
  локальный откат.
- **Потеря явного false при конвертации.** Tri-state проверяется на прямом YAML
  и на IR round-trip; bool без presence-флага не допускается.
- **Два разных разрешателя data_path.** Effective-helper переиспользует
  `managedFormElementEntityField`, чтобы `Форма.X` не наследовала одноимённое
  `Объект.X`.
- **Молчаливый ключ в неподдержанном месте.** Context-aware lint/validation и
  CLI schema должны падать до запуска UI.
- **Смешение plain text и richtext.** Новая ветка не загружает Quill, не
  использует `template.HTML` и имеет тест на escaping.

Каждый срез откатывается кодовым revert без миграции данных. После отката всего
механизма из YAML удаляются `Field.multiline`; сохранённые строки остаются
обычными строками и снова открываются однострочным контролом.

## Критерии завершения

- `multiline: true` у разрешённого обычного строкового поля проходит все
  загрузчики, schema и конфигуратор, не меняя DDL;
- автоформы сущности и регистра сведений показывают textarea, старые поля — input;
- managed-форма различает absence/true/false, наследует только `Объект.*`,
  поддерживает многострочный `Форма.* save:false` и применяет `height` как rows;
- неподдержанные типы и позиции отклоняются до runtime;
- plain text остаётся HTML-экранированным и не включает richtext/code editor;
- все новые гарантии покрыты публичными CLI/HTTP тестами, `go test ./...` и
  обязательный CI проходят на свежем `main`;
- продуктовый код не входит в plan-PR, а issue закрывает только финальный
  продуктовый срез.
