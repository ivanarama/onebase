# План 219 — Вопросы для ТЗ нового проекта по методологии СППР

В СППР ТЗ = **логическая модель** (этап 2). Ответы на вопросы ниже напрямую
раскладываются в объекты базы проектирования, поэтому вопросы сгруппированы по
этапам и по полям объектов, которые нужно заполнить.

Маршрут: процессы → функции/профили → архитектура (объекты метаданных,
подсистемы) → интерфейс → права → тестовые сценарии → справка.

## 0. Проект (справочник `Проекты`)

1. Какое прикладное решение разрабатываем — **наименование проекта**, имя
   конфигурации, наименование, краткое имя?
2. Это отдельный продукт, библиотека (проект-библиотека) или надстройка над
   существующим проектом? Если библиотека — какой уровень вложенности?
3. С какими проектами связываемся (зависимости, заимствования)?
4. Кто **ответственный за проект**?
5. Режим разработки: хранилище / Git-репозиторий / без изменений? Адрес
   репозитория, каталог, имя ветки, путь к проекту в репозитории?
6. Версия платформы? Каталог ИБ для загрузки метаданных, пользователь, пароль?
7. Нужны ли обработчики обновления, рассылка уведомлений о сборках, публикация
   патчей? Куда выгружается дистрибутив?
8. Часовой пояс, основной календарь, интервал рабочего времени (для расчёта
   сроков и учёта времени)?
9. Какие **разделы проекта** заводим (функциональные areas — они же единицы
   ответственности)?
10. Тестирование включаем? Эталонная база? Расписание ночного контура CI?

## 1. Этап 1 — описание автоматизируемых процессов (справочник `Процессы`)

Главный вопрос: **что именно автоматизируем** и кто сейчас это делает руками.

1. Перечислите процессы предприятия, подлежащие автоматизации. Какие процессы
   **не** автоматизируем и почему (граница системы)?
2. Для каждого процесса:
   - начало процесса (сигнал/событие запуска) и завершение (признак «процесс
     закрыт»);
   - перечень шагов: последовательность, **альтернативные** шаги (группы, где
     выполняется один из нескольких — по какому условию), смысловые блоки;
   - какие шаги — самостоятельные (вложенные) процессы;
   - **тип шага** (шаг процесса / вложенный процесс);
   - **описание шага**;
   - **требования к системе** на этом шаге (что система обязана обеспечить:
     рассчитать, провести, заблокировать, отправить, сохранить);
   - **исполнитель шага** (должность/подразделение);
   - **функция**, реализующая шаг;
   - **формы**, которыми пользователь пользуется на шаге.
3. Какие исходные данные нужны для начала работ и в какой форме они поступают
   (из внешнего окружения: почта, файлы, другие системы)?
4. Какие внешние системы/люди участвуют как источники и потребители?
5. Где сейчас «узкое место» и что должно измениться после автоматизации
   (кратко, по каждому процессу)?

## 2. Этап 2 — логическая модель (справочник `Функции системы`)

Функция 1-го уровня = сама система. Декомпозиция: группы 2-го уровня = крупные
задачи, полностью покрывающие функциональность.

### 2.1. Дерево функций

1. Назначение системы в одном абзаце (что она даёт и чего она не делает)?
2. Какие **группы функций 2-го уровня** (2–6, отглагольные наименования)? Они
   должны покрывать всю функциональность без пересечений.
3. Каждая группа: декомпозиция на 2–6 дочерних функций; функции одной схемы
   равны по объёму и уровню абстракции; информационные связи между ними
   минимизированы (общие расчёты/печать выносим в отдельные функции).
4. Разные функции должны выполняться **разными исполнителями** — какие
   службы/должности «идеального предприятия» за что отвечают?
5. Для каждой функции: она **конечная** или требует декомпозиции? Признаки
   конечности: нет промежуточных результатов, ценных другим функциям; все
   потоки преобразуются не более одного раза; функция исполняется «в один
   прием».
6. **Коды** функций (`Полный код`) — какая схема нумерации?

### 2.2. Карточка каждой конечной функции (заполнить для всех)

1. Наименование в отглагольной форме + **Код** + описание (назначение и краткая
   характеристика дочерних функций).
2. **Результат работы функции** (что материально получается на выходе: документ,
   запись, расчёт, отчёт, решение).
3. **Тип функции**: Функция / Учетный механизм (расчёт, регистрация движений) /
   Отчёт (аналитика, контроль). Учётные механизмы обычно не видны в интерфейсе.
4. **Входящие данные**: функции-источники, конкретные данные, и вид связи —
   `Вход` (потоки, которые функция преобразует) или `Управление` (правила,
   условия, режимы, которые функция соблюдает, но не меняет).
5. **Потребители** результата: какие функции используют результат и как?
6. **Исполнители**: какие профили пользователей участвуют (ресурс, стрелка
   снизу схемы).
7. **Исходящие объекты метаданных** — чем функция оперирует (для проектирования
   прав доступа).
8. **Отчёты, сервисные объекты** — инструменты выполнения функции.
9. Отображается ли функция **в интерфейсе** и как именно называется?
10. **Ответственный** за реализацию функции.

### 2.3. Проверки модели (по ним же аудит)

- У каждой функции есть хотя бы один выход и хотя бы одно управляющее воздействие.
- Каждая связь — выход ровно одной функции; вход/управление — произвольное число функций.
- Нет функций с одинаковой функциональностью; нет «висячих» функций без
  исполнителя; декомпозиция не глубже 4 уровней.

## 3. Этап 3 — профили пользователей (справочник `Профили пользователей`)

1. Перечислите **профили** (неделимые единицы обязанностей). На крупном
   предприятии профиль = должность; на маленьком — пользователю можно назначить
   несколько профилей.
2. Кому какой **раздел проекта** и проект назначен (профиль привязывается ровно
   к одному проекту)?
3. Есть ли системный профиль (тип `Система`) для функций без участия человека
   (обмен, регламентные задания, расчёты)?
4. Описание каждого профиля: квалификация, должностные обязанности, что видит и
   что может менять.
5. Разделение компетентностей: получение отчёта ≠ настройка отчёта; заполнение
   документа ≠ администрирование. Где нужны отдельные профили?
6. Требуется ли **изменение реального процесса** ради системы (пользователю
   нужно решение, а данных ему не дают)?

## 4. Этап 4 — архитектура (Подсистемы, Объекты метаданных, Реквизиты)

1. **Подсистемы** и их иерархия — декомпозиция функций даёт дерево подсистем.
   Кто **ответственный** за подсистему?
2. Для каждой функции — чем она реализуется: справочник / документ / регистр
   сведений / регистр накопления / план видов характеристик / константа /
   обработка / отчёт / план обмена / роль.
3. Для каждого объекта метаданных: Имя, Синоним, Комментарий, Пояснение,
   **Ответственный**.
4. Реквизиты: состав, типы значений, ссылочные типы (цепочки связанных данных),
   табличные части, измерения/ресурсы.
5. Предопределённые данные (справочники) и значения перечислений.
6. **Движения по регистрам**: регистратор (документ), вид движения
   (Приход/Расход, Запись), словесное описание движения. Для каждого документа —
   по каким регистрам он проводит.
7. Разделение данных: общие (неразделённые) от библиотек или РИБ?
8. Синхронизация: регламентная загрузка метаданных, согласование изменений для
   новых объектов (Требуется / Не требуется)?

## 5. Этап 5 — интерфейс (Формы объектов метаданных)

1. Какие функции отображаются в интерфейсе и как они названы?
2. Для каждого объекта метаданных — какие формы нужны: форма списка, форма
   элемента, форма группы, форма выбора?
3. Какие результаты функций-источников должны быть видны на каких формах?
4. Какие формы общие, какие — конкретные?
5. Какие команды (кнопки, пункты меню) пользователь использует на каждой форме
   и какой профиль их видит?

## 6. Этап 6 — права доступа (роли, Виды доступа)

1. Правило: одна роль ≈ одна конечная функция. Перечислите роли по конечным
   функциям.
2. Права по исходящим объектам функции: создание/редактирование/чтение;
   функции-потребители получают права чтения объектов потребляемой функции.
3. Используется ли БСП (нужны ли ПолныеПрава и служебные роли)?
4. **Виды доступа** (критерии ограничений): кто видит «свои» данные — по
   Объекту, По условию, по Пользователям, по Внешним пользователям, по какому
   ещё признаку (подразделение, проект, контрагент, регион)? Для каждого вида
   доступа — типы объектов метаданных, к которым он применяется.
5. Какие роли компонуем в какие профили пользователей?
6. Что маскируется/скрыто от каких профилей (персональные данные)?

## 7. Этап 8 — управление проектом и изменениями

1. **Целевые задачи** выпуска: перечень направлений работ, ответственный, сроки,
   статусы.
2. **Идеи** (что предложено) и **ошибки** (что воспроизводится) — как
   регистрируем и описываем (описание идеи/воспроизведения + описание
   реализации/исправления)?
3. **Технические проекты**: цели, концепция, участники, версия конфигурации,
   целевая задача, приоритет (очередность), плановые сроки, ветка разработки,
   вид деятельности, демонстрационная база, статус, публикация.
4. **Проектные решения** техпроекта: какие процессы, функции, профили, сценарии,
   разделы проекта, обработчики обновления, ключевые операции затронуты;
   результаты проверки формальных правил.
5. **Задачи**: исполнители, контролирующий (без него нельзя отметить выполнение),
   плановая дата начала, крайняя дата, вышестоящая задача, предшествующие/
   последующие, дочерние. Есть ли **шаблоны процессов** для типовых серий задач
   (длительность в днях, назначение по предмету)?
6. Планирование занятости и рабочих планов; учёт времени по видам деятельности.
7. Какие объекты ставим **на контроль** (кто контролирует изменения)?

## 8. Этап 11 — тестирование (сценарии, процессы, Gherkin)

1. Какие **сценарии работы пользователей** нужны по каждой функции (минимум —
   ключевые пользовательские сценарии)? Группа сценария привязана к функции.
2. Для каждого сценария: наименование, проект, раздел проекта, **ответственный**,
   **профиль пользователя** запуска, функция, группа, флаги
   «разрешено использовать в процессах» / «в других функциях», описание.
3. Шаги Gherkin: какие действия, какие окна/поля/кнопки, какие проверки
   («Тогда…»), нужны ли параметры, таблицы, условия, циклы, подсценарии.
4. **Процессы** как последовательность сценариев: блоки-этапы, параметры между
   шагами, порядок, какие сценарии участвуют.
5. Настройки сценариев: профиль, эталонная база, параметры запуска, публикуется
   ли в релизе.
6. Что гоняем в ночном контуре CI, что — в дневных сборках?
7. Где хранятся сценарии: справочник СППР или git-репозиторий?

## 9. Этап 7 — справка и документация

1. Тексты справки по каждой функции, объекту метаданных и форме (стиль и
   компоновка).
2. Что входит в сопровождающую документацию, куда выгружается (ветка/хранилище)?

## 10. Аудит формальных правил

Какие правила проверки активны и с какой важностью (Ошибка / Предупреждение /
Информация), например: функция без исполнителя; функция без подтверждённого
тестового сценария; функция без исходящих объектов; сценарий без функции;
объект метаданных без функции; роль без профиля; профиль без ролей; объект
без ответственного. Есть ли правила, специфичные для этого проекта?

## Минимальный комплект для первой итерации

Чтобы запустить первый срез, достаточно ответов на:

- §0.1–0.4 (проект и границы),
- §1.2 (процессы: шаги + требования к системе + исполнители),
- §2.1–2.2 (дерево функций + карточки конечных функций + профили §3),
- §4.1–4.2 (подсистемы и объекты метаданных по конечным функциям),
- §6.1 (роли по конечным функциям),
- §8.1–8.2 (сценарии по ключевым функциям).
