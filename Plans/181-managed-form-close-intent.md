# Этап 181 — Единый асинхронный контракт закрытия управляемой формы

## Контекст

План ведёт [#1530](https://github.com/ivanarama/onebase/issues/1530) и собирает в
один контракт её прикладные сценарии [#1559](https://github.com/ivanarama/onebase/issues/1559),
[#1558](https://github.com/ivanarama/onebase/issues/1558) и
[#1621](https://github.com/ivanarama/onebase/issues/1621). Выбран вариант 1:
сначала единый путь закрытия, затем кнопки и диалог, затем runtime-свойство
формы. Продуктовый код нельзя раскладывать по этим заявкам независимо: крестик,
Esc, «ОК», popup и команда `ui.закрытьФорму` обязаны спрашивать одну и ту же
прикладную логику.

Состояние кода и маршрутов проверено по `main`
`764be3342567b3d809d37bcebb2b6a38e08c57fa` (2026-09-21); этот документ не
содержит реализации.

На текущем `main` событие `ПередЗакрытием` известно словарю и конвертеру, но
намеренно входит в `metadata.UncalledFormEvents()`. Закрытие раздроблено:

- оболочка удаляет iframe синхронно в `internal/ui/tabs.go:closeTab`;
- крестик формы посылает родителю `obCloseTab`, а standalone-форма переходит по
  ссылке;
- Esc отдельно реализован в `static/ui.js` и `static/managed.js`;
- popup создания ссылки закрывается своим `obRefCancel`/`cleanup`;
- `ui.закрытьФорму` приходит через SSE и снова вызывает `closeTab`;
- `beforeunload` умеет только показать системное предупреждение о dirty-форме.

Ни один путь не вызывает серверный модуль формы. Более того, существующий
`obFire` гасит сетевую ошибку в баннере и не возвращает вызывающему коду
решение, поэтому его нельзя просто поставить перед `closeTab`: оболочка не
узнает, разрешил ли сервер закрытие.

Цель этапа — сделать закрытие явным асинхронным намерением (`close intent`):
запросить решение у живой формы, при необходимости сохранить данные, выполнить
`ПередЗакрытием`, и только после положительного ответа уничтожить iframe,
закрыть popup либо уйти со standalone-страницы.

В объём не входят:

- попытка выполнить DSL при закрытии вкладки браузера, завершении WebView2,
  падении процесса или обрыве сети: браузер не даёт надёжного асинхронного окна;
- гарантия целостности бизнес-процесса самим фактом закрытия UI — обязательный
  итог обращения по-прежнему должен храниться и проверяться серверными данными;
- событие `ПриЗакрытии`: после уничтожения окна надёжного подтверждённого канала
  уже нет, поэтому оно остаётся невызываемым и продолжает диагностироваться;
- произвольная настройка состава нижней панели. В этом этапе есть только
  платформенные действия `save`, `ok`, `close` и их видимость;
- изменение схемы базы данных.

## Пользовательский контракт

### `ПередЗакрытием`

Событие объявляется так же, как остальные события формы:

```yaml
events:
  ПередЗакрытием: ПередЗакрытиемФормы
```

Основная сигнатура совместима с привычным кодом 1С:

```os
Процедура ПередЗакрытиемФормы(Отказ)
    Если НЕ ЗначениеЗаполнено(Объект.ФилиалАйсберг) Тогда
        Сообщить("Не заполнено значение: ФилиалАйсберг");
        Отказ = Истина;
    КонецЕсли;
КонецПроцедуры
```

Поддерживаются ровно два варианта:

- без параметров — закрытие отменяет необработанный `ВызватьИсключение`;
- один параметр `Отказ` (`Cancel` как английский alias) — закрытие отменяют и
  истинное итоговое значение параметра, и исключение.

Параметр является выходным именно для этой платформенной точки входа. Нельзя
имитировать его обычной переменной в корневом scope: сейчас параметры процедуры
живут в дочернем кадре интерпретатора, и присваивание `Отказ = Истина` снаружи
не видно. Реализация добавляет проверяемый API вызова entry-процедуры с возвратом
итоговых binding-значений; общую семантику пользовательских вызовов процедур
этот срез не меняет.

Обработчику доступны текущие поля и табличные части формы, `Объект`,
`ЭтотОбъект`, `Сообщить` и те же server-side пользователь/RBAC-контексты, что у
обычного form-event. Дополнительно доступны read-only строки
`ПричинаЗакрытия` / `CloseReason`:

| Значение | Источник |
|---|---|
| `cross` | крестик формы или вкладки |
| `escape` | Esc вне редактора и модального окна |
| `close` | нижняя кнопка «Закрыть» |
| `ok` | нижняя кнопка «ОК» |
| `post_and_close` | существующая команда «Провести и закрыть» |
| `programmatic` | `ui.закрытьФорму` |
| `popup_cancel` | отмена/крестик popup |

Причина нужна прикладной проверке и аудиту, но не является доказательством
полномочий: клиентский enum валидируется allow-list, а права, пользователь и
объект определяются сервером.

`Отказ = Истина` возвращает форму без общей красной ошибки; сообщения из
`Сообщить` показываются как обычно. Исключение возвращает ошибку и также
оставляет форму открытой. Изменённое обработчиком состояние формы применяется
из ответа даже при отказе — по тому же правилу, что текущий
`formEventState.response(false)`.

### Нижний ряд действий

Обычная managed-форма объекта получает справа внизу единый платформенный ряд:

```text
[Записать] [ОК] [Закрыть]
```

- `Записать` запускает существующую запись и оставляет форму открытой;
- `ОК` сохраняет без проведения и запрашивает закрытие только после успешной
  записи;
- `Закрыть` на чистой форме сразу запрашивает `ПередЗакрытием`, а на изменённой
  сначала предлагает «Да / Нет / Отмена»;
- «Да» сохраняет и продолжает закрытие только после успеха;
- «Нет» не пишет объект, но всё равно запускает `ПередЗакрытием` с текущими
  значениями; только разрешённый ответ действительно отбрасывает ввод;
- «Отмена» не вызывает сервер и оставляет форму как есть.

Кнопки `Записать` и `ОК` видны только при `CanWrite`; `Закрыть` доступна и на
read-only форме. Для обычной managed-формы объекта все три действия включены по
умолчанию. Их можно скрыть действующим блоком `actions`:

```yaml
actions:
  save:
    visible: true
  ok:
    visible: true
  close:
    visible: true
```

Верхняя кнопка «Записать» после появления стандартного нижнего ряда удаляется,
чтобы на форме не было двух одинаковых действий. Проведение, удаление, печать и
«Ввести на основании» остаются в верхней панели. «Провести и закрыть» сохраняет
своё бизнес-действие, но физическое закрытие переводится на тот же close-intent
и не может обойти `ПередЗакрытием`.

Popup создания/выбора сохраняет специализированный ряд «Записать и выбрать /
Отмена»: общий `ОК` там изменил бы смысл результата. Его `Отмена`, крестик, Esc
и успешное «Записать и выбрать» всё равно проходят общий close-controller.
Формы обработок не получают `Записать`/`ОК`, но их выход также использует общий
контракт.

### Видимость вложений

Второй критерий #1621 независим от механики закрытия и не должен потеряться в
большом срезе. Действующий типизированный `actions` расширяется ещё одним ключом:

```yaml
actions:
  attachments:
    visible: false
```

Отсутствие ключа и `visible: true` сохраняют нынешнее поведение. `false` скрывает
только блок «Вложения» у этой managed-формы; API вложений, файлы и права не
удаляются. Ключ не влияет на autogen-формы, popup и новую запись, где блок и так
не рисуется. Это отдельный маленький PR-срез, а не условие выпуска close-intent.

### `ЭтаФорма.РазрешитьЗакрытие`

Финальный срез добавляет на runtime-экземпляр управляемой формы свойство:

```os
Процедура ПриОткрытии()
    Если ТекущийПользователь().Админ = Ложь Тогда
        ЭтаФорма.РазрешитьЗакрытие = Ложь;
    КонецЕсли;
КонецПроцедуры
```

Умолчание — `Истина`. Значение принадлежит серверному экземпляру формы и не
принимается из hidden input или произвольного JSON клиента. Ответы событий
добавляют актуальную close-policy в тот же объект состояния, из которого клиент
применяет values/tableparts/elementStates.

При `Ложь` оболочка не удаляет вкладку, Esc и `ui.закрытьФорму` получают отказ,
а крестик и нижняя кнопка «Закрыть» скрыты или disabled. `ОК` остаётся доступной
как явное бизнес-действие: после записи `ПередЗакрытием` может поставить
`ЭтаФорма.РазрешитьЗакрытие = Истина`; окончательное разрешение вычисляется
после обработчика как
`Отказ = Ложь AND РазрешитьЗакрытие = Истина`. Если обработчик ничего не
изменил, форма остаётся открытой.

Свойство требует серверного runtime-экземпляра `ЭтаФорма`, спроектированного в
плане 172 / PR #1426. До готовности его базовых срезов свойство не подменяется
недоверенным клиентским флагом: первые срезы этого плана поставляются без него,
а последний имеет явную зависимость от runtime-instance.

## HTTP- и клиентский протокол

### Один серверный endpoint

Вводятся отдельные маршруты, а не удалённый вызов `obFire('ПередЗакрытием')`:

```text
POST /ui/{kind}/{entity}/form-close-intent
POST /ui/processor/{name}/form-close-intent
```

Отдельный endpoint нужен по трём причинам: отсутствие обработчика означает
«разрешить», `Отказ` является выходным параметром, а положительный ответ даёт
право уничтожить UI ровно один раз. Обычный `/form-event` по-прежнему не
позволяет произвольно дёрнуть lifecycle-event по присланному имени.

Тело form-urlencoded содержит текущий snapshot тем же способом, что
`/form-event`, включая `_id`, `_version`, поля, ТЧ/ValueTable и mapped service
fields, плюс:

```text
_close_intent_id = случайный UUID
_close_reason    = cross|escape|close|ok|post_and_close|programmatic|popup_cancel
_close_mode      = discard|save|post|save_and_select
```

Параметры не принимаются из query string. `discard` означает «не выполнять
запись перед событием», а не «пропустить событие». Для `save`, `post` и
`save_and_select` сервер сначала выполняет обычный save pipeline — права, row
filters, required, version, `ПередЗаписью`/`ПриЗаписи`, проведение, запись и
`ПослеЗаписи`. Только успешная запись продолжает `ПередЗакрытием` уже на
актуальном объекте. Если закрытие затем отклонено, запись не откатывается:
пользователь просил сохранить, и форма остаётся открытой с сохранённой версией.

HTML-submit и close-intent обязаны вызывать один внутренний save-service. Копия
логики `submit`/`submitEdit` в новом handler запрещена: иначе разойдутся права,
хуки, optimistic version и поведение новой записи.

Ответ расширяет существующий `formEventState.response`, а не создаёт вторую
сериализацию формы:

```json
{
  "ok": true,
  "values": {},
  "tableparts": {},
  "messages": [],
  "savedId": "...",
  "version": 4,
  "close": {
    "intentId": "...",
    "allowed": true,
    "saved": true,
    "formUrl": "/ui/document/обращение/..."
  }
}
```

`ok=false` означает ошибку исполнения/записи/протокола; `ok=true` вместе с
`close.allowed=false` — штатный `Отказ` или запрет runtime-policy. В обеих
ветках клиент сначала применяет возвращённое состояние и сообщения, и лишь при
точном совпадении `intentId` плюс `allowed=true` передаёт одноразовое разрешение
конкретному адаптеру закрытия.

### Идемпотентность и гонки

На странице допускается ровно один незавершённый close-intent. Повторный клик,
двойной Enter или одновременно пришедшая `ui.закрытьФорму` получают тот же
Promise; новые кнопки временно disabled. Это закрывает обычный double-click, но
само по себе не закрывает потерянный HTTP-ответ после записи.

Поэтому сервер держит ограниченный replay-ledger close-intent:

- ключ: текущая auth/session identity + route entity/form/record + UUID intent;
- значение: SHA-256 нормализованного POST и готовый terminal HTTP status/body;
- первая попытка резервирует ключ до запуска save/DSL;
- параллельный точный повтор ждёт первую и получает побайтово тот же ответ;
- тот же UUID с другим payload даёт конфликт до записи и DSL;
- записи живут не дольше 10 минут, имеют per-user/global limit и очищаются LRU;
- в журнале/метриках не хранится сырой payload.

Клиент после сетевого сбоя или своего timeout ничего не закрывает. Ручной retry
с неизменившимся snapshot повторяет тот же intent UUID и безопасно получает
replay; после любого редактирования создаётся новый UUID. Автоматического
fail-open и автоматического бесконечного retry нет. После рестарта сервера
ledger теряется — форма остаётся открытой, а пользователь видит просьбу
проверить результат записи перед новой попыткой.

Серверный DSL использует существующие `beginOperation(opFormEvent)`, общий
processor-concurrency pool и `limits.request_timeout_sec`. Клиент получает
advertised deadline в bootstrap и ставит AbortController чуть позже серверного
предела; 429, timeout, network error, не-JSON, stale correlation и уничтоженный
frame всегда означают «не закрывать».

### Адаптеры закрытия

В браузере есть один `requestFormClose(intent)` и несколько последних шагов:

- **shell:** `tabs.go` отправляет запрос точному `iframe.contentWindow`, ждёт
  ответ с теми же source/origin/correlation и только затем удаляет tab/frame;
- **standalone:** после разрешения форма делает same-origin переход к списку
  или явно переданному безопасному return URL; `window.close()` не используется;
- **popup:** родитель не делает `cleanup()` по `obRefCancel`, пока iframe не
  ответил на close-intent; успешный save-and-select передаёт результат вместе с
  тем же разрешением;
- **programmatic:** `ui.закрытьФорму` лишь инициирует этот протокол для каждой
  совпавшей вкладки, а не доказывает, что её можно удалить;
- **close others/all:** вкладки запрашиваются последовательно, чтобы не показать
  несколько модалов сразу; отказ одной не закрывает её и не обходится повтором;
- **крестик, средняя кнопка, Esc и нижние кнопки:** все вызывают тот же controller.

Esc сначала сохраняет нынешний приоритет: modal → ref dropdown → активный
SlickGrid editor → поле ввода → форма. Пока пользователь отменяет ячейку или
закрывает внутренний picker, close-intent не создаётся.

`window.beforeunload` остаётся последней синхронной страховкой только для dirty:
он показывает системный браузерный диалог при reload/закрытии окна, но не делает
fetch и не обещает выполнить `ПередЗакрытием`. Dirty-флаг снимается только после
подтверждённой записи или непосредственно перед уже разрешённым уничтожением;
ошибка и отказ его не сбрасывают.

## Изменения в коде

- `internal/ui/form_close_intent*.go` (новый узкий слой): parse/validate intent,
  replay-ledger, оркестрация optional save → `ПередЗакрытием` → response.
- `internal/ui/handlers_entity.go`: выделить общий результат записи новой и
  существующей формы, который используют HTML submit и close-intent без копии
  permission/hook/version логики.
- `internal/ui/handlers_managed_events.go`: вынести безопасную сборку текущего
  объекта, DSL vars и `formEventState` в переиспользуемую функцию; close response
  проходит только через `formEventState.response`.
- `internal/ui/form_event_eligibility.go`: отдельный resolver lifecycle-hook на
  уровне формы; присланные `_element/_event` для close endpoint отсутствуют.
- `internal/dsl/interpreter`: sandbox-вызов entry procedure с доступом к
  итоговому binding единственного output-параметра; тесты `Возврат`, exception,
  timeout и strict lexical scope.
- `internal/metadata/form_uncalled_events.go`: после появления реального
  dispatcher добавить `ПередЗакрытием` к серверно вызываемым событиям; сторож
  обязан удалить его из docs-перечня, но не затронуть `ПриЗакрытии`.
- `internal/ui/server.go`, `ops.go`: два маршрута, те же body limits, deadline,
  concurrency, метрики и slow-operation logging, что у form-event/save.
- `internal/ui/static/ui.js`: общий controller, correlation/origin checks,
  beforeunload fallback и popup handshake.
- `internal/ui/static/managed.js`: snapshot формы, применение полного ответа,
  dirty/modal/save modes и интеграция с существующим grid/file-read barrier.
- `internal/ui/tabs.go`: `closeTab` становится Promise-returning single-flight;
  cross/middle/context/all/SSE больше не удаляют frame напрямую.
- `internal/ui/templates_managed.go`: bootstrap close URL/deadline, нижний ряд,
  data-атрибуты действий и актуальная close-policy.
- `internal/metadata/form_module.go`,
  `internal/dsl/loader/managed_form_loader.go`, `internal/configcheck/lint.go`:
  allow-list `actions.save|ok|close|attachments`, прежний `delete` сохраняется.
- `internal/ui/templates.go`: общий `ob-attachments` принимает вычисленную
  видимость формы; autogen-вызовы сохраняют нынешнее умолчание.
- runtime-срез свойства переиспользует `ЭтаФорма`/instance/response revision из
  плана 172; отдельный client-authoritative флаг не создаётся.
- `docs/forms.md`, `docs/forms-1c-converter.md`, DSL langref/ai-guide,
  `docs/features.md`, `CHANGELOG.md` и обязательный `en`-перевод описывают один
  контракт, намеренную активацию старых обработчиков и предел `beforeunload`.

## Тесты

### Сервер и DSL

- публичный HTTP-тест реальной managed-формы отправляет текущие header/ТЧ,
  вызывает `ПередЗакрытием(Отказ)` и проверяет allow, `Отказ`, исключение и
  сообщения;
- отдельная форма с нулевой сигнатурой подтверждает сценарий #1559;
- отсутствие handler/AST разрешает закрытие, неизвестная/лишняя сигнатура
  диагностируется до удаления UI;
- read/write/RLS, masked fields, new/existing object, stale `_version`, body
  limit, processor trust gate и timeout проходят теми же публичными маршрутами;
- `save` и `post` не закрывают при ошибке и не вызывают `ПередЗакрытием` до
  успешной записи; после успеха handler видит присвоенный ID/номер/версию;
- отказ после успешного save оставляет запись в БД, возвращает новую version и
  сохраняет форму открытой;
- два одновременных запроса с одним intent исполняют save/DSL один раз и получают
  один terminal response; изменённый payload с тем же UUID отвергается;
- output-binding интерпретатора проверяется через публичный sandbox API, а не
  чтением приватной карты env.

### Browser behavior

- Node-harness нажимает крестик формы, крестик/среднюю кнопку вкладки, Esc,
  context «закрыть/другие/все» и доставляет `ui.закрытьФорму`; каждый путь ждёт
  ровно одно решение и не удаляет iframe при deny/error/timeout;
- повторный клик и одновременная server command используют один Promise;
- source/origin, неизвестный correlation и поздний ответ старого iframe не
  закрывают новую/соседнюю вкладку;
- dirty-модал проверяет Да/Нет/Отмена; save failure оставляет ввод и dirty,
  успешный save обновляет new ID/version/URL до `ПередЗакрытием`;
- «ОК» закрывает только после успешной записи; «Записать» никогда не закрывает;
  «Провести и закрыть» не обходит controller;
- popup Cancel/cross/Esc и save-and-select проходят handshake, а отмена
  close-confirm не оставляет listener;
- `beforeunload` остаётся установленным, но ни один unit-test не считает его
  заменой async close-intent.

### Рендер и конфигурация

- нижний ряд находится справа внизу и содержит один экземпляр каждой кнопки;
  permission/`actions.*.visible` дают ожидаемую матрицу;
- `actions.attachments.visible:false` скрывает блок только выбранной managed-
  формы, не меняя attachment endpoint;
- `onebase check --lint` принимает четыре известных action и предупреждает об
  опечатке, которая иначе молча ничего не сделает;
- сторож `UncalledFormEvents` и фрагмент `docs/forms.md` сходятся после удаления
  только `ПередЗакрытием`;
- runtime-тест свойства доказывает независимость двух пользователей/вкладок и
  отказ поддельного client `allow=true`.

## Совместимость, риски и откат

- **Ранее мёртвый handler оживает.** Конфигурация с `ПередЗакрытием` могла
  годами хранить непроверенный код. Это намеренное изменение поведения и
  обязательная строка CHANGELOG; перед обновлением handler следует проверить.
- **Один путь забыли.** Центральный controller плюс behavior-матрица запрещают
  прямые `remove()/cleanup()/location.assign` в перечисленных путях.
- **Save и close разошлись.** Единственный внутренний save-service и публичные
  parity-тесты не дают close endpoint получить облегчённую проверку прав/хуков.
- **Форма заперлась из-за сети.** Fail-closed сохраняет данные; пользователь
  видит причину и retry. Аварийный выход — закрытие окна браузера с нативным
  dirty-warning, а не скрытый fail-open.
- **Повторил побочный эффект.** Single-flight закрывает клики, replay-ledger —
  потерянный ответ; handler всё равно следует писать идемпотентным на случай
  рестарта сервера.
- **`РазрешитьЗакрытие` подделано.** Оно живёт только в server instance плана
  172; клиент отображает policy, но не является её источником.
- **Откат.** A–C откатываются кодом без миграции БД/YAML; неизвестные `actions`
  старый runtime игнорирует. D откатывается вместе с использованием runtime API
  в конфигурации — тихого client fallback для opt-in формы нет.

## Критерии завершения

- Все перечисленные OneBase-пути закрытия доходят до одного async controller и
  не уничтожают UI без совпавшего положительного server decision.
- `ПередЗакрытием()` и `ПередЗакрытием(Отказ)` получают текущую форму; exception,
  `Отказ`, timeout и сеть всегда оставляют её открытой.
- Dirty-диалог имеет «Да / Нет / Отмена»; «ОК» и «Да» закрывают только после
  успешной записи, обычное «Записать» остаётся открытым.
- Нижний ряд `Записать / ОК / Закрыть` и
  `actions.attachments.visible:false` покрывают оба критерия #1621 без второго
  механизма кнопок.
- Double-click/повтор потерянного ответа не выполняет save/hook дважды в пределах
  replay TTL; конфликт payload fail-closed.
- `beforeunload` честно остаётся fallback и нигде не описан как гарантированный
  вызов прикладного кода.
- `ЭтаФорма.РазрешитьЗакрытие` серверно авторитетно и независимо для двух
  пользователей/вкладок; его отсутствие до среза D не заменено hidden-флагом.
- `onebase check`, руководство, converter mapping, docs и UI называют один и
  тот же поддерживаемый контракт; `ПриЗакрытии` остаётся в списке невызываемых.
