# План 84 - Enterprise-аутентификация (2FA / SSO / LDAP)

Дата проектирования: 2026-07-08.
Статус: ✅ **Реализовано** (2026-08-03, ветка `plan84`), кроме LDAP — он в плане и
был отложен «до спроса».

## Что сделано

- ✅ **TOTP (RFC 6238)** — `internal/auth/totp.go`: секрет base32, otpauth-ссылка,
  проверка с допуском ±1 шаг. Код одноразов: номер использованного шага пишется в
  `_users.totp_last_step` условным UPDATE, поэтому переигрывание отсекается
  атомарно даже при параллельных запросах.
- ✅ **Резервные коды** — `_auth_backup_codes` (только хэши). Одноразовость
  обеспечивает сам `DELETE ... WHERE code_hash = ?` по числу изменённых строк;
  перевыпуск отменяет прежний комплект.
- ✅ **Секрет TOTP шифруется** мастер-ключом плана 83 (`enc:`); без ключа 2FA
  работает, но профиль и журнал предупреждают о хранении открытым текстом.
- ✅ **Шаг 2FA во входе** — сессия не создаётся, пока код не предъявлен: между
  паролем и сессией живёт короткий challenge в памяти процесса (`challenge.go`,
  кука `onebase_2fa`, 5 попыток). Работает в форме `/login`, в JSON API
  (`/auth/login` → `2fa_required` + `/auth/2fa`) и во входе в конфигуратор.
- ✅ **Принудительная настройка** — учётка, которой политика предписывает 2FA,
  вместо ввода кода получает QR и включает второй фактор прямо на входе; сессия
  выдаётся только после подтверждения (в конфигураторе — отказ с указанием
  настроить 2FA в Предприятии, там показываются QR и резервные коды).
- ✅ **OIDC (Authorization Code + PKCE)** — `oidc.go`, `oidc_client.go`,
  `handlers_oidc.go`: discovery с кэшем, JWKS/RS256(384/512), проверка
  `iss`/`aud`/`exp`/`iat`/`nonce`, state в куке + серверное состояние, userinfo
  как запасной источник claim'ов. Реализация на stdlib — внешней зависимости в
  контуре аутентификации не появилось.
- ✅ **Проекция учёток и маппинг ролей** — `sso_provision.go`: поиск по
  (провайдер, `sub`), связывание с существующей учёткой по подтверждённой почте,
  опциональное автосоздание. Роли из правил синхронизируются при каждом входе
  (исчезла группа — снимается роль), назначенные вручную не трогаются;
  последнего администратора маппинг не разжалует.
- ✅ **Политики** — `auth.policy` в `_settings`: `sso_only`, `require_2fa_admins`,
  `require_2fa_roles`. Аварийный обход `sso_only` — `ONEBASE_ALLOW_PASSWORD_LOGIN=1`
  у процесса базы; включить политику без работающего провайдера админка не даёт, а
  удаление последнего провайдера её снимает.
- ✅ **UI** — «Профиль → Второй фактор» (QR, резервные коды, отключение) и
  «Администрирование → Аутентификация» (политики + CRUD провайдеров с правилами
  вида `groups = erp-buh -> Бухгалтерия`, подсказкой `redirect_uri` и шифрованием
  введённого `client_secret`).
- ✅ **Ротация мастер-ключа** видит секреты провайдеров: `auth.providers` попал в
  `SecretCarriers` и в `onebase secret rotate`.

### Отличия от проекта

- Политики и провайдеры живут в `_settings`, а не в `app.yaml`: это свойство
  инстанса (issuer, client_secret, требования к учёткам конкретной установки), и
  переезжать вместе с конфигурацией в `.obz` им нечего. Так же сделан лимит
  сессий плана 78.
- Резервные коды — отдельная таблица, а не колонка `_users.backup_codes`: гашение
  кода должно быть атомарным, а read-modify-write по колонке допускает повторное
  использование одного кода в двух параллельных запросах.
- Добавлен флаг провайдера «сам обеспечивает второй фактор»: без него локальная
  политика 2FA действует и после SSO, иначе единый вход стал бы её обходом.
- QR рисуется библиотекой `rsc.io/qr` (BSD, без транзитивных зависимостей) —
  единственная новая зависимость; сам OIDC зависимостей не потребовал.
- ⬜ LDAP/AD не делался (в плане — «ниже приоритетом, при спросе»).

## Контекст

Аутентификация сейчас: логин+пароль, серверная сессия (токен вне URL/логов,
план 53), rate-limit логина, CSRF и security-заголовки; для REST — Bearer
API-токены (план 26). Этого достаточно для фрилансера/малого бизнеса, но по мере
движения платформы к серьёзному многопользовательскому применению (RLS план 79,
масштаб план 76, изолированные сессии план 78) не хватает корпоративного
минимума:

- **второй фактор** для привилегированных учёток (админ конфигуратора,
  бухгалтерия);
- **единый вход (SSO)**, чтобы не заводить отдельные пароли, а пускать через
  корпоративный провайдер;
- опционально каталог пользователей (LDAP/AD).

Всё — строго **opt-in**: базы без включённой фичи работают как сейчас.

## Цель

- TOTP-2FA (RFC 6238) для учёток, где включён; резервные коды;
- вход через внешнего OIDC-провайдера (Google/Microsoft/Keycloak и совместимые),
  маппинг на локальную учётку и роли;
- (опц.) LDAP/AD bind как источник учёток;
- админ-политики: «требовать 2FA для ролей X», «разрешить только SSO».

## Хранилище / метаданные

- `_users`: `totp_secret` (enc:, план 83), `totp_enabled`, `backup_codes` (хэши);
- `_auth_providers` в `_settings`: тип (`oidc`/`ldap`), issuer/client_id/секрет
  (через резолвер секретов), правила маппинга `claim → роль`;
- политика в `app.yaml`/админке: `auth: { require_2fa_roles: [...], sso_only: bool }`.

## Дизайн

**2FA (TOTP).** Профиль пользователя: «Включить 2FA» → QR (otpauth://) →
подтверждение кодом. При входе после пароля — шаг ввода кода; резервные коды
одноразовые. Секрет TOTP шифруется (план 83).

**SSO (OIDC).** Стандартный Authorization Code + PKCE. Кнопка «Войти через …» →
редирект к issuer → callback: валидация id_token, поиск/создание локальной
учётки по `email`/`sub`, назначение ролей по правилам маппинга. Сессия — та же
серверная, что сейчас.

**LDAP (опц.).** Проверка пароля bind'ом к каталогу; локальная учётка —
проекция. Ниже приоритетом, чем OIDC (многие корпоративные каталоги уже за OIDC).

## Изменения в коде

- `internal/auth/` — TOTP (генерация/проверка/резервные коды), провайдеры
  (`oidc.go`, `ldap.go`), маппинг ролей, политики;
- `internal/ui/admin.go` — управление провайдерами и политиками;
- `internal/ui/` — шаг 2FA при входе, кнопки SSO, профиль (вкл. 2FA);
- `internal/api/` — учесть, что API-токены (план 26) остаются альтернативой для
  сервис-доступа независимо от 2FA/SSO;
- зависимость OIDC — минимальная (стандартная библиотека OAuth2/OIDC), внести в
  `go.mod` под vuln-скан (govulncheck-job).

## Тесты

- TOTP: валидный/просроченный/переигранный код, резервные коды одноразовы;
- политика `require_2fa`: учётка без 2FA в защищённой роли не входит до настройки;
- OIDC (мок issuer): callback создаёт/находит учётку, применяет маппинг ролей;
  битый/просроченный id_token → отказ;
- `sso_only`: локальный пароль отклоняется.

## Verification

1. Включить 2FA у админа → повторный вход требует код; резервным кодом тоже.
2. Настроить мок-OIDC → «Войти через …» заводит учётку и роли по claim.
3. База без включённых провайдеров/2FA — вход как раньше.

## Эстимейт

7–10 дней: TOTP+резервные коды+UI (2–3), OIDC (3–4), политики/маппинг/админка
(1–2), тесты (2). LDAP — отдельные +2–3 дня, при спросе. Держать всё opt-in и не
регрессировать текущий вход — главный критерий приёмки.
