## Синтаксис / YAML и поддерживаемые условия

Основные параметры `-InstallDir`, `-Project`, `-Agents`, `-DryRun` и Unix-аналоги
сохраняются. Установщик ставит отсутствующий CLI либо использует имеющийся;
молчаливого обновления или замены существующего CLI нет. Параметры передаются
массивом аргументов, без повторного разбора shell.

| Граница | Принимаемый контракт |
|---|---|
| Windows | Windows PowerShell 5.1 и PowerShell 7 на Windows; относительные пути от текущего расположения PowerShell, независимо от каталога процесса |
| Unix | macOS/Linux, POSIX sh; относительные пути от рабочего каталога вызывающего процесса; существующие имена ассетов amd64/arm64 |
| Имена путей | Пробелы, кириллица и апостроф передаются буквально. Неиспользуемые shell-метасимволы не исполняются |
| Dry-run | Нет сети, запуска CLI, создания staging, публикации и записей проекта. Отчёт использует то же разрешение путей, что реальный запуск |
| Нефайловый PowerShell provider | Явный отказ до загрузки и записи; не подменять путь текущим каталогом процесса |
| Существующий CLI | Не менять файл, права или ссылку; проверить выбранный CLI и поддержку нужной команды. Непригодный CLI требует явного действия пользователя |

Для Windows разрешать путь через
`$ExecutionContext.SessionState.Path.GetUnresolvedProviderPathFromPSPath(...)`
с проверкой FileSystem provider. Поддерживаемые абсолютные/UNC и относительные
пути проверять на штатном provider; неоднозначные drive-relative формы (`D:foo`)
отклонять с пояснением. Не создавать отсутствующий проект ради разрешения пути.
Печатную PowerShell-команду формировать одинарным литералом с удвоением `'`.
Для POSIX-команды использовать корректное shell-экранирование, а не двойные
кавычки вокруг произвольного пути. Исполняемый вызов не строить из этой строки.

## Хранилище / SQL и инварианты файлов

Схема БД и пользовательские данные не меняются. До успешной проверки кандидата
нет финальной публикации и вызова `vibe-init`. Контрольная сумма относится к
точному имени архива; отсутствующие/дублирующиеся ассеты и записи архива дают
отказ. Из архива читается единственный точный CLI, чужие пути не извлекаются.

Публикация остаётся create-only полным файлом на том же файловом разделе:
Windows — complete-file Move с отказом при существующем target, Unix —
существующая публикация через hard link без перезаписи победителя гонки.
Удаление перед rename, fallback с перезаписью и запуск непроверенного кандидата
не допускаются. На неподдерживаемой файловой системе — отказ с действием
пользователя, а не ослабленная публикация.

Временные каталоги приватны. Cleanup удаляет только проверенные пути, созданные
текущим запуском; прежние бинарь, ссылка и файлы проекта не входят в cleanup.
Проверка reparse point/ссылки в управляемом месте установки сохраняется.
После публикации `vibe-init` может отказать: уже установленный проверенный CLI
остаётся, отчёт различает установку и регистрацию; автоматического удаления
проекта или бинаря нет.

## Безопасная загрузка

Production-режим допускает только HTTPS для release metadata, архива,
контрольной суммы и каждого перехода. TLS-сертификаты проверяются штатно;
HTTP downgrade, file/ftp, URL с userinfo и автоматическое отключение проверки
сертификата запрещены. Обычные HTTPS-переходы GitHub → CDN поддерживаются;
цепочка конечна (не более 10 переходов), цикл даёт отказ.

Для `curl` — HTTPS-only `--proto` и `--proto-redir`. В PowerShell не полагаться
на автоматическое следование редиректу: общий загрузчик должен проверять схему
каждого перехода, включая относительный Location. Один контракт применяется
ко всем трём загрузкам, а не только к первоначальному API URL.

Существующие публичные `internal/bootstraptest/bootstrap_test.go` используют
локальный HTTP release-fixture. Сохранить их через отдельный явно тестовый
флаг `--allow-insecure-loopback-fixture` / `-AllowInsecureLoopbackFixture`.
Он допустим только вместе с явно заданным HTTP `ReleaseApi` на числовом
loopback (`127.0.0.1` или `[::1]`). Все ассеты и редиректы обязаны оставаться
на том же origin, включая порт; DNS-имена, внешний HTTP, userinfo и переход
на иной origin отклоняются. Обычные инструкции установки этот флаг не используют.
Без флага даже локальный HTTP отклоняется. Это не универсальный `insecure`.

SHA-256 из того же релиза обнаруживает повреждение и несоответствие ассета,
но не заменяет доверие к каналу/издателю. Новый формат подписи релизов здесь
не вводится. Переход на HTTPS-only — намеренное изменение для автоматизаций,
которые ранее передавали HTTP endpoint; предупреждение обязательно в CHANGELOG.

## Медленная сеть, noexec и PATH-симлинки

Убрать прежний общий предел 120 секунд. В обеих реализациях зафиксировать
connect timeout 15 секунд, отсутствие прогресса 60 секунд, общий конечный
предел 30 минут на файл и максимум два повтора только сетевых сбоев с новым
приватным файлом. HTTP 4xx, checksum/архив, политика URL и проверка бинаря
не повторяются. Передача с постоянным прогрессом дольше 120 секунд проходит;
зависший peer и прерванная передача завершаются без публикации. Лимиты выводить
в диагностике, не скрывать ошибки бесконечными повторами. Общие значения
не распространять на выполнение `vibe-init`.

На Unix staging нового бинаря размещать в приватном каталоге рядом с местом
установки, на его файловом разделе. Системный `/tmp` с noexec не должен мешать
проверке `--version`. Если noexec имеет сам целевой раздел, сообщать о запрете
исполнения, не пытаться обходить его копированием в другое место. До проверки
допустимо создание каталога установки/staging, но не финального CLI и проекта;
пустой ранее отсутствовавший каталог можно оставить и указать это в отчёте.
Существующий рабочий CLI не требует staging и загрузки.

PATH-симлинк допустим только как обнаруженная существующая установка:
разрешить относительную/абсолютную цепочку (не более 40 звеньев), отклонить
цикл, dangling target, каталог и неисполняемый итоговый файл. Выбранную ссылку
и итоговый путь отразить в отчёте; выполнить проверенный абсолютный target
массивом аргументов. Не заменять ссылку/target и не устанавливать второй CLI
молча при ошибке. Проверять идентичность доступного target перед передачей
управления; универсальную защиту от враждебной одновременной подмены PATH
не обещать. Явный управляемый InstallDir по-прежнему не разрешает symlink
в месте финальной публикации.

## Тесты и Verification

Сначала расширить существующие публичные тесты, которые запускают настоящие
`install.ps1`/`install.sh` и native fixture CLI. Не подменять установщик тестом
приватной функции. На каждом отказе сверять прежние байты бинаря, ссылки,
guides/MCP и отсутствие вызова `vibe-init`, временных файлов и записей вне staging.

- Windows 5.1/7: процесс запущен из A, `Set-Location` в B, относительные
  InstallDir/Project создаются в B; абсолютный/UNC путь, PSDrive FileSystem,
  отказ Registry provider и drive-relative формы. Пробелы/кириллица/апостроф,
  литеральные shell-символы, argv fixture и выполнение напечатанной команды
  в изолированном профиле. Dry-run не делает файловых/сетевых изменений.
- Transport: корректный HTTPS fixture с доверенным тестовым CA; metadata,
  archive и checksum по отдельности редиректят в HTTP, цикл/лишние hops,
  invalid TLS, недопустимые схемы и подменённый origin. Нельзя использовать
  `-k`, отключать TLS validation или считать mocked curl доказательством запрета.
  HTTP loopback позитивный только с флагом; внешний origin и redirects запрещены.
- Slow link: реальная передача дольше старого 120-секундного предела в отдельной
  acceptance job; стабильная медленная скорость проходит, остановка прогресса
  и общий deadline отказывают. Короткие unit-fixtures проверяют счётчик повторов,
  но не заменяют эту длительную передачу.
- Linux: настоящий mount с noexec на TMPDIR при исполняемом InstallDir проходит;
  noexec InstallDir даёт точный отказ. Нужен изолированный Linux job с правом
  mount; отсутствие полномочий — незавершённая приёмка, не зелёный skip.
- macOS/Linux: PATH-ссылки на рабочий fixture, относительная многошаговая цепочка,
  цикл/dangling/неисполняемый target. Ссылка/target неизменны; тот же CLI получает
  argv. Старый CLI без vibe-init отказывает без скачивания и правок проекта.
- Все ОС: существующий CLI, dry-run, checksum/архив, конкурентный победитель,
  отказ публикации, очистка staging, точные release asset mappings сохраняются.
  Платформенный mapping не выдавать за запуск arm64 на реальном arm64 runner.

Сквозной D: чистый профиль Windows/macOS/Linux, проект с пробелами и кириллицей,
bootstrap → принятый `vibe-init` → выбранные проектные конфиги MCP → штатное
доверие клиента → read-only check/describe. Повтор сохраняет байты; чужие серверы
и guides работают. Использовать форматы и ZCode priority из плана 202 без
новой регистрации глобальных клиентов. Реальные client smoke результаты
собирать в #2083, не заменять ими отдельные транспортные негативные проверки.

## Риски, совместимость, откат и эстимейт

Риски: Windows providers/старый PowerShell, разница curl/PowerShell redirects,
целевой filesystem без hard links, права mount в CI, PATH TOCTOU и неполная
продуктовая команда в старом релизе. У каждого есть отрицательная проверка
и явная граница поддержки; обходов с перезаписью и незащищённым транспортом нет.

При поставке каждого среза писать CHANGELOG о прежнем/новом поведении и действиях
при обновлении; QUICKSTART должен отличать установленный CLI от готового проекта.
Откат — вернуть принятые скрипты/релиз по решению сопровождающего; существующий
CLI и проект автоматически не удалять. HTTPS-only не откатывать молча ради
старого HTTP mirror. Уже опубликованную установку восстанавливает пользователь
по отдельной инструкции, после сверки текущих файлов.

Оценка A–D: **6,5–10 рабочих дней**, плюс доступность Windows 5.1/7, macOS,
Linux noexec runner и фактическая готовность #2082/#2083. Работу закрывать
после принятых срезов и общей приёмки; merge этого plan-only PR #2392 не закрывает.
