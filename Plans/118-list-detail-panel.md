# План 118 — Боковая панель деталей активной записи списка

Дата проектирования: 2026-08-09.
Статус: 🟡 **118A и 118B сделаны**, 118C–118D не начаты. Issue #670.

## Контекст

Пользователь (issue #670) просит: смотреть все колонки списка неудобно, особенно
когда среди них картинки; нужна боковая панель с данными активной записи — «как
в лаунчере OneBase со списком баз и деталями справа», — и возможность разносить
данные внутри панели по закладкам, чтобы вынести картинки отдельно.

Два факта задают всю экономику плана:

1. **Данные для панели уже есть.** `store.List` тянет все реквизиты шапки, а
   `list_form`/`tile_view` лишь сужают показ. Панель, построенная из тех же
   `Rows`, не требует ни одного нового SQL-запроса.
2. **Безопасность тоже уже есть, и это не совпадение.** Те же `Rows` прошли
   RBAC, строковые политики (план 79) и маскирование (план 88). Пока панель не
   заводит второго пути чтения, обойти гейт нечем — а `storage/crud.go:388`
   вдобавок отказывается отдавать список без вычисленного строкового фильтра.

Жалоба про картинки подтверждается и по вёрстке, и по стоимости: `N` строк × `M`
image-полей = `N×M` HTTP-запросов, каждый со своими SQL.

## Что этот план НЕ покрывает: событие строки табличной части

Заявку #670 естественно прочитать двояко, и вторую половину закрывает не этот
план. «Панель деталей активной записи **списка**» (master-detail: слева список
объектов, справа карточка выбранного) — здесь. «Реакция на переход по строкам
**табличной части** внутри открытой формы» — это событие
`ПриАктивизацииСтроки`, и оно закрыто отдельно, как дефект: событие было
объявлено в метаданных и полностью обработано на сервере, но клиент его никогда
не отправлял (`ui/static/managed.js` дёргал только
`ПриДобавленииСтроки`/`ПриУдаленииСтроки`).

Разграничение важно для реализатора: панель списка — это серверный рендер +
клиентская отрисовка из уже отданных `Rows`, без событий формы; надпись или
картинка, пересчитываемая при движении по ТЧ, — это round-trip события формы.
Механизмы разные, и сливать их в один не надо.

## Цель

1. У списка появляется боковая панель с данными выбранной записи, включая
   реквизиты, которых нет в колонках.
2. Внутри панели — закладки; картинки выносятся в отдельную.
3. Ни одного нового пути чтения данных: панель наследует права, строковые
   политики и маскирование автоматически, а не «тоже их применяет».
4. Существующие конфигурации не меняют вид молча.

## Принятые решения

Зафиксированы здесь, чтобы реализатор их не переигрывал.

1. **Панель строится из уже отрисованных `Rows`, а не отдельным запросом.**
   Это не оптимизация, а требование безопасности: второй путь чтения пришлось бы
   заново проводить через `requirePerm` → `applyRowFilter` → `maskRecords`, и
   именно такие «вторые пути» дали #609 и #649. Ленивое дочитывание допускается
   только для вкладок с ТЧ и вложениями (этап 118D) и только отдельным
   хендлером, поставленным на все три AST-стража.
2. **Панель выключена по умолчанию**, включается пользователем кнопкой в
   `.view-switch`, состояние — per-entity, как выбор режима вида. Иначе третья
   колонка молча появляется во всех списках всех конфигураций. Блок
   `detail_panel:` задаёт **состав**, а не факт включения (и может включить
   принудительно).
3. **Закладки переиспользуют механизм управляемых форм**, а не заводят свой:
   разметка `.managed-tabs`/`.managed-tab-btn` и переключатель
   `obManagedSwitchTab` уже написаны и умеют помнить активную вкладку. Ловушка:
   `managed.js` на `page-list` **не подключён** (`templates_managed.go:663`
   против `templates.go:614`) — переключатель надо вынести в общий `ui.js`, а не
   копировать.
4. **Приоритет источников зеркалит `resolveListColumns`**: управляемая
   ФормаСписка со `СтраницыФормы` → `detail_panel:` → автокомпоновка. Один
   принцип на два похожих механизма вместо двух разных.
5. **Панель живёт СНАРУЖИ контейнера `[data-ob-live]`.** Живой список (план 87)
   по SSE-событию подменяет `innerHTML` контейнера целиком
   (`ui.js:2672-2687`), поэтому панель внутри него пересоздавалась бы, теряя
   вкладку и скролл, а `_listSel` указывал бы на оторванный `<tr>`.
6. **Состояние выбора остаётся одно.** Панель подключается к существующему
   `_listSel`, а не заводит свой «активный элемент»: иначе «⚙ Действия» и
   контекстное меню разъедутся с панелью — классический источник жалоб «удалил
   не то».

## Синтаксис / метаданные

Согласовано с тем, как объявлен `tile_view` (короткий английский ключ, значения
— русские имена реквизитов) и управляемые формы (локализация через `titles`).

```yaml
detail_panel:
  title: Наименование      # шапка панели; по умолчанию — представление записи
  width: 320               # ширина по умолчанию, px
  tabs:
    - name: Основное
      titles: {ru: Основное, en: General}
      fields: [Артикул, Цена, Поставщик]
    - name: Изображения
      fields: [Фото, ФотоУпаковки]
    - name: Описание
      fields: [Описание]
```

Короткая форма без закладок — как `tile_view.fields`:

```yaml
detail_panel:
  fields: [Артикул, Цена, Поставщик, Фото]
```

Правила, проверяемые `onebase check`:

- `fields` ссылаются на существующие реквизиты шапки; ключи `tableparts:` и
  `attachments:` внутри вкладки **зарезервировать сразу**, реализовать в 118D;
- ни `fields`, ни `tabs` не заданы → автокомпоновка: image-поля во вкладку
  «Изображения», richtext — в свою, остальное — «Основное»;
- `detail_panel` **не расширяет права**: поле, скрытое маской, не появляется в
  панели, даже будучи перечисленным явно; замаскированное показывается
  замаскированным.

Эквивалент через управляемую форму списка выражается уже существующими
`СтраницыФормы`/`Страница` — добавлять в язык форм нечего.

## Дизайн

`page-list` получает флекс-обёртку: слева `.card[data-ob-live]` (без изменений),
справа `<aside class="ob-detail">` — **вне** контейнера живого списка. Значения
рисуются на клиенте из payload'а, положенного сервером рядом со строкой;
переключение вкладок — вынесенный в `ui.js` `obManagedSwitchTab`; ширина —
ресайзер по образцу `cfgMakeResizer` с сохранением в `localStorage`.

Ни одного нового HTTP-маршрута, ни одного нового SQL-запроса, ни одной новой
точки маскирования на первом этапе.

## Попутные дефекты, которые план закрывает

- **Д1. Конфигуратор молча стирает ключи сущности.** `saveEntity`
  (`launcher/configurator_types.go:74-97`) перечисляет ключи явно, а сохранение
  реквизитов идёт через `Unmarshal`→`Marshal` этой структуры. Сегодня так уже
  теряются `tile_view`, `indexes`, `list_mode`, `list_refresh_on`,
  `notify_changes`, `description` — ровно та авария, которую чинили для
  `hierarchical`/`numerator`/`predefined` (комментарий на `configurator_types.go:67`).
  Roundtrip-тест (`save_entity_roundtrip_test.go:19`) эти ключи не покрывает,
  поэтому дефект невидим. Без правки `detail_panel` унаследует ту же болезнь,
  а тест писать пришлось бы всё равно — поэтому Д1 входит в план, а не выносится.
- **Д2. Картинки в списке дороги.** `N` строк × `M` image-полей = `N×M`
  запросов `/ui/_image/<uuid>`, каждый с проверкой ссылки через до трёх
  `store.List`. Вынос картинок во вкладку панели убирает их из списка совсем —
  это и есть то, о чём просит автор issue.
- **Д3. Четвёртый форматтер значений.** Значение по типу уже форматируется в
  трёх местах: колонка списка (`templates.go:1303`), плитка (`:1259`), форма
  (`:1540`). Панель, написанная отдельно, станет четвёртым и разъедется по
  датам, числам и перечислениям. Форматирование выносится в общий partial и
  переиспользуется во всех четырёх — иначе план создаёт ровно тот долг, который
  план 117 описывает как «пять копий одного кода».

## Тесты

Только через **публичные точки входа** (правило CLAUDE.md, повод — #611).

- `resolveDetailPanel` — приоритет источников. Образцы уже написаны для колонок:
  `TestResolveListColumnsEntityListForm`, `TestResolveListColumnsManagedListForm`
  (`ui/tile_view_test.go:117,140`).
- Рендер `page-list`: панель есть, вкладки с ожидаемыми заголовками, только

- Живой список: панель отрисована вне `[data-ob-live]` — статический ассерт по
  HTML, как в `static_test.go:43`.
- Д1: сохранение реквизитов сущности сохраняет `detail_panel` **и** шесть

## Риски и ограничения

1. **Узкий экран.** У платформы один брейкпоинт (`templates.go:737`, ≤820px), и
   у обоих эталонов `@media` нет вовсе — копировать нечего. Третья колонка на
   телефоне недопустима; нужно отдельное решение (скрыть либо шторка снизу).
2. **Расширение видимости.** `list_form` сегодня сознательно сужает состав
   колонок; панель покажет то, что из списка убрали. Это не пробой RBAC — маска
   уже применена, — но это изменение поведения существующих конфигураций.
   Смягчается решением №2 (выключено по умолчанию).
3. **Вес страницы.** Payload со всеми реквизитами всех строк раздувает HTML.
   Нужен лимит: richtext в payload — только plain-срез, как `richPlain` в
   колонках.
4. **Ссылки в панели без идентификатора.** `resolveRefs`
   (`ui/handlers.go:806-812`) затирает UUID подписью до шаблона. Панель напечатает
   «ООО Ромашка», но не сделает ссылку на карточку, пока UUID не сохраняется
   отдельно. Тихо не сломается — заметят как недоделку.
5. **Три AST-стража.** Любая новая функция, читающая `store.List`/`GetByID`/
   `GetFieldsByIDs` — в том числе **хелпер**, — обязана наложить маску или
   попасть в список исключений с обоснованием. Это не риск утечки, это
   гарантированный красный CI у реализатора, который об этом не знал.
6. **i18n-гейт.** Новые подписи требуют перевода хотя бы в одной нерусской
   локали, иначе `i18ncheck` роняет джоб `build`.
