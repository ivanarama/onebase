# План 131 — Включение и выключение регламентных заданий администратором

Дата проектирования: 2026-08-18. Статус: ✅ **Реализовано** 2026-08-18. Issue #991.

## Контекст

В 1С «Использование» регламентного задания — состояние информационной базы:
администратор управляет им в пользовательском режиме, решение переживает
обновление конфигурации. В OneBase `enabled` читался только из YAML
(`metadata/scheduled.go`), единственный рантайм-гейт — `if !job.Enabled {
continue }` в `buildCron` планировщика. Живой кейс: ProgBase поставляется с
`ТелеграмПоллинг` `enabled: false` — включить бота администратору рабочей базы
без правки исходников и рестарта было нельзя.

Границы:

- **Делаем**: per-base решение поверх YAML-дефолта — тумблер в админке
  `/ui/admin/scheduled` с показом источника состояния, CLI для скриптов,
  перенос в `.obz`.
- **Не делаем**: редактирование расписания из пользовательского режима (это
  свойство конфигурации, меняется разработчиком); включение/выключение
  по расписанию (cron-планировщик заданий); per-user состояния.

## Хранение

Ключи `_settings`: `scheduled.enabled.<jobkey>`, где jobkey =
lower(trim(YAML `name`)) — нормализация как `jobKey` планировщика, регистр
не ломает совпадение. Значение `"1"`/`"0"` (как `net.enabled`). Три состояния:
нет ключа → действует YAML; `"1"` → включено администратором; `"0"` →
выключено. Битое значение = «решения нет». Орфанные ключи (задание удалено из
конфигурации) безвредны и не чистятся.

`Name` — только YAML-поле, от имени файла не выводится → ключ стабилен при
переименовании файла задания.

`internal/storage/scheduled_switch.go`: `GetScheduledEnabled`, `SaveScheduledEnabled`,
`DeleteScheduledEnabled` (отсутствие ключа — не ошибка),
`ScheduledEnabledOverrides` (карта по префиксу, для списка).

## Планировщик

Гейт перенесён из `buildCron` в колбэк тика: cron регистрирует ВСЕ задания с
непустым расписанием, а фактическая включённость проверяется на каждом тике
свежим SELECT (`tickEnabled`, таймаут 5 c, сбой чтения → YAML-дефолт + warn).
Поэтому тумблер, записанный UI/CLI в работающую базу (даже другим процессом),
подхватывается со следующего тика без рестарта и без invalidation-плumbing'а.
Чтение одно на срабатывание тика — пренебрежимо (прецедент per-run чтения
NetGuard/ExecGuard). Проверка стоит до `beginJob`: выключенный тик не занимает
single-flight и не пишет строку в `_scheduled_runs`.

`Scheduler.db` бывает `nil` (тесты, backup) — все чтения nil-safe: без базы
действует YAML-дефолт.

Нативные Go-задания (AutoBackup, DemoReset — всегда `Enabled: true`) гейтятся
только административным решением: «выключить автобэкап» становится осознанным
действием администратора.

`RunNow` не проверяет включённость — «Запустить сейчас» доступен и выключенному
(было и до плана; закреплено регрессионным тестом).

Для UI — единая точка три-состояния: `JobStates(ctx) []JobState` и
`JobStateByName(ctx, name)` (`OverrideSet/OverrideOn/EffectiveOn`). `Jobs()` и
`GetJob` не менялись.

## Побочный фикс: пустое расписание

Латентный баг: `enabled: true` + пустое расписание валило загрузку базы
(«empty spec string» у `AddFunc`), хотя `ValidateSchedule` обещает «в cron
просто не заводится» — обещание выполнялось только для `enabled: false` (молча
пролетало через `continue`). Теперь пустое расписание = задание остаётся в
списке (видимость, RunNow), но в cron не попадает — «по требованию». Невалидные
НЕпустые расписания валидируются на загрузке для всех независимо от enabled
(#965), поэтому «зарегистрировать все непустые» живые конфигурации не ломает.

## UI

Роуты `POST /ui/admin/scheduled/{name}/toggle` и `…/reset`. Список и карточка
показывают четыре состояния: «✓ активно»/«— отключено» (конфигурация) и
«✓ включено администратором»/«— выключено администратором» (решение базы).
Тумблер — в списке и в карточке; «Вернуть как в конфигурации» — в карточке при
наличии решения. Flash-сообщения через `?msg=`/`?err=` (303-редирект, паттерн
расширяемых форм). Действия аудируются: `scheduled.enable` / `scheduled.disable`
/ `scheduled.reset` (`EntityKind: "scheduled"`, `NewValue: "on"/"off"/""`) —
«кто выключил автобэкап» должен быть отвечаемым вопросом. Права — isAdmin.

## CLI

`onebase jobs enable|disable|reset|status <Имя>` с флагами `--sqlite/--db`
(переиспользует `openSettingsDB`). Имя по конфигурации не валидируется —
headless-семантика как у `settings` (орфанный ключ безвреден), проверка имён
потребовала бы `--project`, который скриптам развёртывания чужд. `status`
печатает только решение базы («включено/выключено администратором» /
«административного решения нет, действует конфигурация») — эффективное
состояние без YAML неизвестно.

## Перенос в `.obz`

Префикс `scheduled.enabled.` переезжает безусловно, в любом режиме
восстановления: состояние заданий — не идентичность базы (в отличие от
`exchange.this_node`, который едет только при полном восстановлении), и копия
должна вести задания как источник — иначе восстановленный «выключенный
автобэкап» молча оживает. Экспорт — в `settings/safe.jsonl`; импорт заменяет
решение целевой базы решением источника (`clearPortableSettings` чистит
префикс до импорта). Demo-reset, восстанавливая демо-базу из эталонного
архива, возвращает её тумблеры к эталонным — ожидаемо правильно.

## Тесты

Все через публичные точки входа (правило #611):

- **storage** — матрица `dbtest.ForEachDialect`: три-состояние round-trip,
  нормализация имени, Overrides возвращает только своё семейство, Delete без
  ключа не ошибка.
- **scheduler** — тик с `@every` уважает решение (включение выключенного,
  выключение включённого, гейт нативного Go-задания), RunNow для выключенного,
  JobStates во всех четырёх комбинациях + nil-db, пустое расписание без ошибки
  загрузки (регрессия).
- **ui** — POST-хендлеры через chi routeCtx: toggle пишет решение и страница
  показывает источник, reset убирает, неизвестное имя 404, не-админ 403,
  аудит непуст.
- **cli** — RunE команд + перечитывание отдельным подключением: enable/disable/
  reset, reset без решения не ошибка, пустое имя отклоняется.
- **backup** — раунд-трип: решения в `settings/safe.jsonl`, импорт заменяет
  решение целевой базы решением источника (режим по умолчанию, без exchange).

## Verification

1. База с заданием `enabled: false` → админка → тумблер «Включить» →
   страница показывает «включено администратором», со следующего тика задание
   работает; перезапуск сервера состояние сохраняет; обновление конфигурации —
   тоже.
2. `onebase jobs status <Имя> --sqlite …` до/после тумблера.
3. Бэкап `.obz` → restore в пустую базу → тумблеры на месте.

## Риски и ограничения

- **Гейт только в пределах процесса.** Проверка на тике не заменяет leader
  election: несколько инстансов на одной базе работают как раньше (общая
  открытая проблема планировщика, этап G плана 76).
- **Fail-open при сбое чтения** — вернуться к YAML-дефолту: без БД прогон всё
  равно не запишется (`InsertScheduledRun`), так что ложных прогонов не будет.
- **Тумблер не отменяет уже идущий прогон** — решение действует со следующего
  тика. Осознанно: прерывание идущего обмена — отдельная механика.
- `templates.go`/`en.json`/`Plans/README.md` — конфликтующие файлы почти
  каждого содержательного PR (известная особенность репо).
