Дата проектирования: 2026-08-13. Контракт уточнён 2026-08-16 (сверка с кодом
до начала реализации — договорённость «поправим до PR, а не после» из треда).
Статус: ✅ **Реализовано** 2026-08-17. Issue #742.
Реализация изначально была за внешним контрибьютором (@rsyuzyov, договорённость
в треде #742); он к ней не приступал, и чтобы не держать заявку, её сделали

статус `accepted` убран из контракта как недостижимый для DSL-задания, классов

Границы «делаем / не делаем» не менялись.

## Контекст

Заявка #742: из DSL нельзя запустить регламентное задание — `Scheduler.RunNow`
существует, но зовётся только кнопкой админки (`ui/admin_scheduled.go:55`).
Разбор в треде дал границу:

- **Делаем**: «запустить сейчас, не дожидаясь» + идентификатор прогона, по
  которому можно спросить статус. Закрывает «обмен по требованию», триггер из
  HTTP-сервиса и тесты.
- **Не делаем**: параллелизм. Один прогон на задание — осознанное свойство
  планировщика (`beginJob` → `ErrJobAlreadyRunning`, `scheduler.go:548`);
  пул исполнителей — отдельная заявка (очередь фоновых заданий на PG-бэкенде).
- **Не делаем**: ожидание завершения в DSL — сессия однопоточная, ожидание
  займёт её целиком, а таймаут превратит нормальный долгий обмен в ошибку.
- **Результат задания** — через данные (регистр сведений, запись из кода дал
  план 119), не через журнал прогонов: `_scheduled_runs` — журнал исполнения,
  а не транспорт бизнес-данных.

## Что мешает в текущем коде (сверено с `3c79f25e`, 2026-08-16)

1. **`RunNow` не возвращает идентификатор прогона.** Сигнатура
   `RunNow(_ context.Context, jobName string) error` (`scheduler.go:702`);
   UUID прогона рождается позже, внутри горутины (`InsertScheduledRun`,
   `storage/scheduled.go:49` — `uuid.New()` на `:51`). Вызвавшему нечем
   коррелировать запуск с записью журнала.
2. **Прогон нельзя прочитать по id.** Единственный читатель —
   `ScheduledRuns(ctx, jobName, limit)` (список по имени задания); SELECT по
   `id` отсутствует. Из DSL-запросов таблица тоже недоступна: FROM принимает
   только `ТипМетаданных.Имя`, системные таблицы не разворачиваются.
3. **Ошибка `InsertScheduledRun` тихо съедает запуск**: `executeJob` логирует
   и выходит — вызвавший получил `err == nil`, а прогона нет ни в работе, ни
   в журнале. При синхронной вставке до старта горутины (см. ниже) этот случай
   становится обычной ошибкой вызова.
4. **`_scheduled_runs` не заводится `EnsureServiceSchema`**
   (`storage/service_schema.go` — там audit, settings, numerator, stage history,
   exchange, intake, webhook log, report presets, constants; таблицы прогонов
   нет). Матричный тест из раздела «Тесты» получит от `dbtest` базу без неё и
   упадёт на `no such table` — ровно грабли #827 из CLAUDE.md. Таблицу надо
   добавить туда же.

## Синтаксис

Глобал-объект по образцу `РегистрыСведений` (план 119): русское и английское
имена, методы регистронезависимы.

```
// запустить сейчас; управление возвращается сразу
ИдПрогона = РегламентныеЗадания.Запустить("ОбменСУзлами");

// позже (другой вызов, таймер формы, следующий запуск своего задания):
Прогон = РегламентныеЗадания.Прогон(ИдПрогона);
Если Прогон = Неопределено Тогда
    // журнал ещё/уже не содержит такой прогон
ИначеЕсли Прогон.Статус = "success" Тогда
    // результат читаем из регистра сведений — туда его положило задание
КонецЕсли;
```

Английские имена: `ScheduledJobs.Start(...)`, `ScheduledJobs.RunInfo(...)`.

`Прогон(...)` возвращает Структуру:
`Задание, Статус (running|success|error|timeout|interrupted),
Начало, Конец, ДлительностьМс, Ошибка, Вывод` — ровно колонки
`_scheduled_runs`; `Неопределено`, если прогона с таким id нет.

Статуса `accepted` в этом списке нет намеренно: он ставится только в ветке
нативных Go-заданий (`scheduler.go:788`), а DSL-задание проходит через
`scheduledRunStatus`, который возвращает лишь `timeout|interrupted|error|success`.
Обещать его прикладному коду — обещать недостижимое.

Ошибки `Запустить(...)` — исключение DSL (`RaiseUserError`), три случая с
различимым текстом (столько же классов отказа даёт `beginJob`):

- задание не найдено — ошибка конфигурации, чинится правкой кода;
- задание уже выполняется (`ErrJobAlreadyRunning`, `scheduler.go:551`) —
  штатная гонка с cron-тиком, перехватывается `Попытка/Исключение`. Отдельный
  метод `Выполняется(Имя)` не заводим: между проверкой и запуском гонка
  остаётся, метод только маскировал бы её;
- планировщик останавливается (`ErrSchedulerStopping`, `scheduler.go:542`) —
  сервер уходит на выключение. Прикладному коду ловить бессмысленно, но текст
  обязан отличаться от «уже выполняется»: иначе диагностика при shutdown
  выглядит как гонка, которой нет.

Пустое имя задания (`scheduler.go:547`) до планировщика доводить не нужно —
проверяется в глобале и даёт ошибку конфигурации.

## Принятые решения

1. **Семантика — ровно кнопка «Запустить сейчас» админки.** Никаких новых
   режимов исполнения: тот же `beginJob` (single-flight), тот же контекст от
   `rootCtx` планировщика (отмена вызвавшего запроса на задание не влияет —
   осознанно, как в `RunNow` сегодня), тот же таймаут задания.
2. **Параметры запуска не передаются.** `params` — из YAML задания, как и в
   cron-запуске. Работу «какие узлы обходить» задание берёт из данных
   (регистр сведений); передача параметров конкретному прогону — новая
   механика, в «честный объём» не входит. Согласовано в #742.
3. **`enabled: false` не блокирует запуск** — как в админке (`RunNow` ищет по
   `s.jobs` без проверки `Enabled`). Это даёт полезный паттерн «задание без
   расписания, запускаемое только по требованию». Фиксируем тестом, чтобы
   поведение не «починили» случайно.
4. **Идентификатор прогона создаётся синхронно.** `RunNow` меняет сигнатуру на
   `RunNow(ctx, jobName) (uuid.UUID, error)`: id генерируется до горутины,
   `InsertScheduledRun` принимает готовый id и выполняется до возврата
   управления. Это (а) даёт что вернуть в DSL, (б) превращает «тихо съеденный»
   сбой вставки в честную ошибку вызова, (в) чинит гонку «Запустить вернулся,
   а `Прогон(Ид)` ещё не видит строку». Единственный внешний вызов —
   `admin_scheduled.go:64` — обновляется тривиально. Go-задания
   (`executeGoJob`) должны отдавать id тем же путём.

   **Каким контекстом делать вставку — не деталь реализации, а часть
   контракта.** Сегодня `RunNow` контекст вызывающего игнорирует намеренно
   (`_ context.Context`, комментарий на `scheduler.go:711`: запрос отменится
   после редиректа), и это скрывает проблему: админка передаёт туда
   `r.Context()` (`admin_scheduled.go:64`), а он просто не используется. Как
   только вставка станет синхронной, этот контекст станет боевым, и вариант
   «взять ctx вызывающего» ломается сразу тремя способами:

   - `storage.DB.Exec` подхватывает транзакцию из контекста
     (`storage/tx.go` — ветка `ctx.Value(txKey{})`, есть и в SQLite, и в PG).
     Значит запуск из кода, идущего внутри транзакции (проведение документа,
     запись объекта), уложит строку прогона **в транзакцию инициатора**. Само
     задание живёт на `rootCtx` и её не видит: финальный `UpdateScheduledRun`
     не найдёт строку и вернёт «run not found», а откат инициатора сотрёт
     запись уже отработавшего задания;
   - отмена HTTP-запроса инициатора убьёт вставку — то есть «нажал и ушёл со
     страницы» станет отказом запуска;
   - дедлайн операции инициатора сделает поведение зависящим от того, сколько
     он до этого работал.

   Решение контракта: **вставка идёт под job-контекстом от `beginJob`**, то
   есть порядок такой — `beginJob` (он же занимает single-flight) → синхронная
   вставка под `jobCtx` → старт горутины. Контекст вызывающего используется
   только там, где он и должен: ничего не отменяет и в транзакцию не попадает.
   Если вставка не удалась, `done()` обязан быть вызван до возврата ошибки —
   иначе имя задания останется занятым в `activeJobs` навсегда, и следующий
   запуск (в том числе cron-тик) будет вечно получать «уже выполняется».

5. **Права: доступно любому коду конфигурации.** Код задания фиксирован
   конфигурацией, запуск по требованию не расширяет привилегий — задание и так
   стартует по cron без пользователя. Админ-роль не требуется (в отличие от
   кнопки админки, где она — свойство раздела, а не операции).
6. **В песочнице запрещено.** Недоверенному коду (ИИ/marketplace,
   `RestrictedProfile`) глобал не даётся: запуск задания исполняет доверенный
   код конфигурации с полным окружением — это эскалация из песочницы. Точку
   применения выбрать при реализации там же, где режутся остальные
   привилегированные глобалы sandbox-контекстов; тест — из sandbox-контекста
   объект недоступен.
7. **Запуск из открытой транзакции инициатора — отказ, а не ожидание.** На
   SQLite пул фиксирован одним соединением (`storage/sqlite.go` —
   `SetMaxOpenConns(1)`, там же объяснено почему). Если инициатор держит
   транзакцию, горутина задания не получит соединения и будет голодать до
   своего таймаута (по умолчанию час), а инициатор будет ждать её — на ровном
   месте получается взаимная блокировка, которая выглядит как «сервер завис».
   На PG до дедлока не доходит, но задание всё равно не увидит незакоммиченных
   данных инициатора, то есть типичный сценарий «записал документ и тут же
   запустил задание, чтобы оно его обработало» тихо не сработает.

   Поэтому `Запустить` при открытой транзакции вызывающего даёт понятное
   исключение вместо запуска. Практическое следствие, которое надо назвать в
   справке прямо: **из `ОбработкаПроведения` задание запустить нельзя** —
   проведение всегда идёт в транзакции. Запускать следует после записи, из
   кода формы или обработки.

## Изменения в коде

- `internal/scheduler/scheduler.go` — `RunNow` возвращает `(uuid.UUID, error)`;
  проброс готового id в `executeJob`/`executeGoJob` → `InsertScheduledRun`.
- `internal/storage/scheduled.go` — `InsertScheduledRun` принимает id;
  новый `ScheduledRunByID(ctx, id uuid.UUID) (*ScheduledRun, error)`
  (`sql.ErrNoRows` → `nil, nil`).

  образцу `dsl_inforegs.go`: методы `Запустить/Start`, `Прогон/RunInfo`,
  ошибки через `interpreter.RaiseUserError`.

## Тесты

Через публичную точку входа (правило #611): DSL-код, зовущий
`РегламентныеЗадания.…`, а не приватные методы планировщика.

- Запустить → вернулся UUID; прогон появляется в `_scheduled_runs` со
  `status='running'` **до** возврата из `Запустить`; поллинг `Прогон(Ид)` до
  `success`.
- Задание пишет в регистр сведений → после `success` инициатор читает
  результат запросом (сквозной сценарий из #742).
- Запуск занятого задания (первое спит) → исключение, перехватываемое
  `Попытка`; текст различим с «не найдено».
- Несуществующее имя → исключение.
- `enabled: false` → запускается.
- Упавшее задание → `Прогон(Ид).Статус = "error"`, `Ошибка` непуста.
- `Прогон` с чужим/случайным UUID → `Неопределено`, не исключение.
- Sandbox-контекст → глобал недоступен.
- Запуск из кода, идущего в открытой транзакции (проведение документа) →
  понятное исключение, прогон не заводится, транзакция инициатора не
  испорчена. Тест обязателен: без него правило из п. 7 живёт только в тексте,
  а нарушение проявится зависанием на SQLite, которое трудно связать с
  причиной.
- `ScheduledRunByID` — прогнать через `dbtest.ForEachDialect` (SQLite + PG).

## Риски и ограничения

1. **Смена сигнатуры `RunNow`** — публичный метод пакета; вызовов два
   (админка, тесты планировщика), но проверить `grep -rn "RunNow("` перед
   мержем. Учесть, что это не только правка сигнатуры: вставку прогона надо
   вынести из `executeJob`/`executeGoJob` наружу, сохранив `trackActiveRun` и
   существующее поведение обеих веток. Перекладка владения циклом прогона —
   основной объём работы в этом пункте, эстимейт ниже это учитывает.
2. **Single-flight гарантирован только в пределах процесса.** `activeJobs` —
   карта в памяти планировщика (`scheduler.go:549`), ни advisory lock, ни
   leader election не сделаны (этап G плана 76 открыт). При нескольких
   инстансах на одной базе `Запустить` даст параллельные прогоны одного
   задания вопреки `ErrJobAlreadyRunning`, и `Прогон(Ид)` останется корректным
   только для того инстанса, где запуск случился. Для одиночного сервера
   контракт верен; для схемы 24/7 с blue-green это надо знать заранее.
3. **Различение ошибок по тексту исключения.** DSL сегодня не даёт
   типизированных исключений; «не найдено», «уже выполняется» и «планировщик
   останавливается» различаются текстом. Если появятся типизированные
   исключения — сюда первым делом.
4. **Спам запусков из кода формы.** Single-flight гасит параллельные дубли
   одного задания; количество разных заданий ограничено конфигурацией. Общего
   rate-limit не заводим, пока нет живого сценария злоупотребления.
5. **`Вывод` прогона может быть большим** (колонка `output` копит `Сообщить()`
   задания без ограничения размера) — возвращаем как есть, но в справке
   предупредить.
6. **Журнал прогонов не чистится и не лечится.** Ретенции у `_scheduled_runs`
   нет вовсе (ни одного `DELETE`), а после жёсткого завершения процесса строка
   навсегда остаётся в статусе `running` — снимающего его `UPDATE` при старте
   в коде нет. Запуск по требованию делает обе проблемы заметнее: прикладной
   цикл «жду терминальный статус» на таком прогоне зависнет навсегда. В объём
   плана 123 это не входит (заведено отдельной заявкой), но код, ожидающий
   завершения через `Прогон(Ид)`, обязан иметь собственный предел ожидания —
   это надо сказать в справке.

## Не делаем

- Параллельные прогоны одного задания, пул исполнителей, очередь — отдельная
  заявка «Очередь фоновых заданий на PG-бэкенде» (#742 → новая issue), там же
  замеры нагрузки (≈12 одновременных обменов, пик 31, режим 24/7).
- Ожидание завершения (`ЗапуститьИЖдать`) — против однопоточной модели сессии.
- Передачу параметров прогону.
- Отмену прогона из DSL (`Прервать(Ид)`) — до живого сценария.

## Эстимейт

| Кусок | Оценка |
|---|---|
| `RunNow` → id (перекладка вставки прогона наружу, обе ветки), `ScheduledRunByID`, `_scheduled_runs` в `EnsureServiceSchema`, адаптация админки | 1–1,5 дня |
| Глобал `РегламентныеЗадания` + инжекция + песочница + отказ при открытой транзакции | 0,5–1 день |
| Тесты (вкл. сквозной с регистром сведений и матричный), справка, доки | 1 день |

Итого ≈ 2,5–3,5 дня. Первоначальная оценка 1,5–2 дня считала первый пункт
правкой сигнатуры; после разбора видно, что это перенос владения циклом
прогона плюс служебная схема, поэтому оценка поднята.
