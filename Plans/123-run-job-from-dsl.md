# План 123 — Запуск регламентного задания из DSL

Дата проектирования: 2026-08-13.
Статус: ⬜ **Проект** (не начато). Issue #742.
Реализация: внешний контрибьютор (@rsyuzyov) — договорённость в треде #742;
план фиксирует контракт, чтобы PR не разошёлся с замыслом платформы.

## Контекст

Заявка #742: из DSL нельзя запустить регламентное задание — `Scheduler.RunNow`
существует, но зовётся только кнопкой админки (`ui/admin_scheduled.go:55`).
Разбор в треде дал границу:

- **Делаем**: «запустить сейчас, не дожидаясь» + идентификатор прогона, по
  которому можно спросить статус. Закрывает «обмен по требованию», триггер из
  HTTP-сервиса и тесты.
- **Не делаем**: параллелизм. Один прогон на задание — осознанное свойство
  планировщика (`beginJob` → `ErrJobAlreadyRunning`, `scheduler.go:548`);
  пул исполнителей — отдельная заявка (очередь фоновых заданий на PG-бэкенде).
- **Не делаем**: ожидание завершения в DSL — сессия однопоточная, ожидание
  займёт её целиком, а таймаут превратит нормальный долгий обмен в ошибку.
- **Результат задания** — через данные (регистр сведений, запись из кода дал
  план 119), не через журнал прогонов: `_scheduled_runs` — журнал исполнения,
  а не транспорт бизнес-данных.

## Что мешает в текущем коде (проверено по `bf2bc770`)

1. **`RunNow` не возвращает идентификатор прогона.** Сигнатура
   `RunNow(_ context.Context, jobName string) error` (`scheduler.go:701`);
   UUID прогона рождается позже, внутри горутины (`InsertScheduledRun`,
   `storage/scheduled.go:49` — `uuid.New()` там же). Вызвавшему нечем
   коррелировать запуск с записью журнала.
2. **Прогон нельзя прочитать по id.** Единственный читатель —
   `ScheduledRuns(ctx, jobName, limit)` (список по имени задания); SELECT по
   `id` отсутствует. Из DSL-запросов таблица тоже недоступна: FROM принимает
   только `ТипМетаданных.Имя` (`query.go:3673`), системные таблицы не
   разворачиваются.
3. **Ошибка `InsertScheduledRun` тихо съедает запуск**: `executeJob` логирует
   и выходит — вызвавший получил `err == nil`, а прогона нет ни в работе, ни
   в журнале. При синхронной вставке до старта горутины (см. ниже) этот случай
   становится обычной ошибкой вызова.

## Синтаксис

Глобал-объект по образцу `РегистрыСведений` (план 119): русское и английское
имена, методы регистронезависимы.

```
// запустить сейчас; управление возвращается сразу
ИдПрогона = РегламентныеЗадания.Запустить("ОбменСУзлами");

// позже (другой вызов, таймер формы, следующий запуск своего задания):
Прогон = РегламентныеЗадания.Прогон(ИдПрогона);
Если Прогон = Неопределено Тогда
    // журнал ещё/уже не содержит такой прогон
ИначеЕсли Прогон.Статус = "success" Тогда
    // результат читаем из регистра сведений — туда его положило задание
КонецЕсли;
```

Английские имена: `ScheduledJobs.Start(...)`, `ScheduledJobs.RunInfo(...)`.

`Прогон(...)` возвращает Структуру:
`Задание, Статус (running|success|accepted|error|timeout|interrupted),
Начало, Конец, ДлительностьМс, Ошибка, Вывод` — ровно колонки
`_scheduled_runs`; `Неопределено`, если прогона с таким id нет.

Ошибки `Запустить(...)` — исключение DSL (`RaiseUserError`), два случая с
различимым текстом:

- задание не найдено — ошибка конфигурации, чинится правкой кода;
- задание уже выполняется (`ErrJobAlreadyRunning`) — штатная гонка с
  cron-тиком, перехватывается `Попытка/Исключение`. Отдельный метод
  `Выполняется(Имя)` не заводим: между проверкой и запуском гонка остаётся,
  метод только маскировал бы её.

## Принятые решения

1. **Семантика — ровно кнопка «Запустить сейчас» админки.** Никаких новых
   режимов исполнения: тот же `beginJob` (single-flight), тот же контекст от
   `rootCtx` планировщика (отмена вызвавшего запроса на задание не влияет —
   осознанно, как в `RunNow` сегодня), тот же таймаут задания.
2. **Параметры запуска не передаются.** `params` — из YAML задания, как и в
   cron-запуске. Работу «какие узлы обходить» задание берёт из данных
   (регистр сведений); передача параметров конкретному прогону — новая
   механика, в «честный объём» не входит. Согласовано в #742.
3. **`enabled: false` не блокирует запуск** — как в админке (`RunNow` ищет по
   `s.jobs` без проверки `Enabled`). Это даёт полезный паттерн «задание без
   расписания, запускаемое только по требованию». Фиксируем тестом, чтобы
   поведение не «починили» случайно.
4. **Идентификатор прогона создаётся синхронно.** `RunNow` меняет сигнатуру на
   `RunNow(ctx, jobName) (uuid.UUID, error)`: id генерируется до горутины,
   `InsertScheduledRun` принимает готовый id и выполняется до возврата
   управления. Это (а) даёт что вернуть в DSL, (б) превращает «тихо съеденный»
   сбой вставки в честную ошибку вызова, (в) чинит гонку «Запустить вернулся,
   а `Прогон(Ид)` ещё не видит строку». Единственный внешний вызов —
   `admin_scheduled.go:55` — обновляется тривиально. Go-задания
   (`executeGoJob`) должны отдавать id тем же путём.
5. **Права: доступно любому коду конфигурации.** Код задания фиксирован
   конфигурацией, запуск по требованию не расширяет привилегий — задание и так
   стартует по cron без пользователя. Админ-роль не требуется (в отличие от
   кнопки админки, где она — свойство раздела, а не операции).
6. **В песочнице запрещено.** Недоверенному коду (ИИ/marketplace,
   `RestrictedProfile`) глобал не даётся: запуск задания исполняет доверенный
   код конфигурации с полным окружением — это эскалация из песочницы. Точку
   применения выбрать при реализации там же, где режутся остальные
   привилегированные глобалы sandbox-контекстов; тест — из sandbox-контекста
   объект недоступен.

## Изменения в коде

- `internal/scheduler/scheduler.go` — `RunNow` возвращает `(uuid.UUID, error)`;
  проброс готового id в `executeJob`/`executeGoJob` → `InsertScheduledRun`.
- `internal/storage/scheduled.go` — `InsertScheduledRun` принимает id;
  новый `ScheduledRunByID(ctx, id uuid.UUID) (*ScheduledRun, error)`
  (`sql.ErrNoRows` → `nil, nil`).
- `internal/ui/admin_scheduled.go:55` — адаптация к новой сигнатуре
  (id админке пока не нужен, поведение не меняется).
- `internal/ui/dsl_scheduled.go` (новый) — глобал `РегламентныеЗадания` по
  образцу `dsl_inforegs.go`: методы `Запустить/Start`, `Прогон/RunInfo`,
  ошибки через `interpreter.RaiseUserError`.
- `internal/ui/handlers_dsl.go` (~:270) — инжекция
  `vars["РегламентныеЗадания"]` / `vars["ScheduledJobs"]` рядом с
  `РегистрыСведений`. Доступно тем же наборам контекстов, что и остальные
  глобалы (формы, модули, проведение, приёмка, сами задания — задание может
  запустить следующее).
- `internal/dsl/interpreter/langref/` — справка по обоим методам.
- `internal/i18n/locales/*.json` — новые строки (если появятся в шаблонах).
- `DEVELOPER.md` — раздел «Регламентные задания»: запуск из кода.
- `docs/features.md` — секция для пользователей (`status: testing`).

## Тесты

Через публичную точку входа (правило #611): DSL-код, зовущий
`РегламентныеЗадания.…`, а не приватные методы планировщика.

- Запустить → вернулся UUID; прогон появляется в `_scheduled_runs` со
  `status='running'` **до** возврата из `Запустить`; поллинг `Прогон(Ид)` до
  `success`.
- Задание пишет в регистр сведений → после `success` инициатор читает
  результат запросом (сквозной сценарий из #742).
- Запуск занятого задания (первое спит) → исключение, перехватываемое
  `Попытка`; текст различим с «не найдено».
- Несуществующее имя → исключение.
- `enabled: false` → запускается.
- Упавшее задание → `Прогон(Ид).Статус = "error"`, `Ошибка` непуста.
- `Прогон` с чужим/случайным UUID → `Неопределено`, не исключение.
- Sandbox-контекст → глобал недоступен.
- `ScheduledRunByID` — прогнать через `dbtest.ForEachDialect` (SQLite + PG).

## Verification

1. `examples/`-конфигурация с заданием без расписания (`enabled: false`),
   пишущим отметку в регистр сведений; кнопка формы зовёт
   `РегламентныеЗадания.Запустить`.
2. Нажать кнопку → в админке `/ui/admin/scheduled/<Имя>` виден прогон; форма
   по таймеру дожидается `success` через `Прогон(Ид)` и показывает отметку из
   регистра.
3. Нажать дважды подряд на долгом задании → второе нажатие получает
   перехватываемое исключение «уже выполняется».

## Риски и ограничения

1. **Смена сигнатуры `RunNow`** — публичный метод пакета; вызовов два
   (админка, тесты планировщика), но проверить `grep -rn "RunNow("` перед
   мержем.
2. **Различение ошибок по тексту исключения.** DSL сегодня не даёт
   типизированных исключений; «не найдено» vs «уже выполняется» различаются
   текстом. Если появятся типизированные исключения — сюда первым делом.
3. **Спам запусков из кода формы.** Single-flight гасит параллельные дубли
   одного задания; количество разных заданий ограничено конфигурацией. Общего
   rate-limit не заводим, пока нет живого сценария злоупотребления.
4. **`Вывод` прогона может быть большим** (колонка `output` копит `Сообщить()`
   задания) — возвращаем как есть, но в справке предупредить.

## Не делаем

- Параллельные прогоны одного задания, пул исполнителей, очередь — отдельная
  заявка «Очередь фоновых заданий на PG-бэкенде» (#742 → новая issue), там же
  замеры нагрузки (≈12 одновременных обменов, пик 31, режим 24/7).
- Ожидание завершения (`ЗапуститьИЖдать`) — против однопоточной модели сессии.
- Передачу параметров прогону.
- Отмену прогона из DSL (`Прервать(Ид)`) — до живого сценария.
- Метод `Выполняется(Имя)` — см. «Синтаксис».
