# План 191 — Составные типы и «любая ссылка»

Дата проектирования: 2026-09-29. Основание — пробел P1-2 ревью ERP-готовности
([PR #1787](https://github.com/ivanarama/onebase/pull/1787), план 188);
владелец 29.09.2026 поставил его первым в очередь планов. Маршрут — дочерний план
PR #1787.

## Контекст

У реквизита может быть ровно один ссылочный тип: `metadata.Field.RefEntity` — строка,
колонка — `<имя>_id` с внешним ключом на одну таблицу (`storage/ddl.go`,
`CreateTableSQL`). Выразить нельзя:

- документ расчётов во взаиморасчётах — «реализация, поступление или корректировка»;
- контрагента «организация или физическое лицо»;
- основание документа — «любой документ»;
- значение субконто, вид которого зависит от счёта (план 193 — регистр бухгалтерии v2);
- значение характеристики (P1-3), где тип задаёт вид характеристики.

Конвертер выгрузки 1С сводит составной тип к строке (`internal/converter/parser1c/typemap.go`,
`MapType`: «составной тип → string»): после импорта в поле лежит текст без типа, без
ссылочной целостности, без выбора из списка. Обходной путь в конфигурациях — строка с
UUID — теряет то же самое.

## Выбранный вариант и объём

Составной тип вводится как **отдельный вид поля**, а не как расширение `RefEntity`.
Новый вид отвергается проверкой конфигурации везде, где его ещё не поддерживает
очередной срез: у `RefEntity` 331 вхождение в 75 файлах, и поле, которое код одиночной
ссылки молча принял бы за строку, — худший исход. Каждый срез расширяет список
разрешённых мест и приносит тесты этого места.

Объём плана:

- составной **ссылочный** тип — явный список справочников и документов;
- «любая ссылка» и её сужения — «любой документ», «любой справочник»;
- **примитивы в составе** (строка, число, дата, булево) — последний срез: они нужны
  значениям характеристик (P1-3), а их хранение и типизация в запросах дороже ссылок.

Вне плана: перечисления в составе, «любая ссылка» на регистры и системные таблицы
(`_users`), составной тип у констант.

## Синтаксис

```yaml
fields:
  - name: ДокументРасчётов
    type: [reference:РеализацияТоваров, reference:ПоступлениеТоваров]
  - name: Контрагент
    type: [reference:Организации, reference:ФизическиеЛица]
  - name: Основание
    type: reference:~any_document    # любой документ конфигурации
  - name: Объект
    type: reference:~any             # любой справочник или документ
  - name: Справочник
    type: reference:~any_catalog     # любой справочник конфигурации
```

`type` принимает строку (как сейчас) или список. Список из одного элемента равен
одиночному типу и так и нормализуется; в ссылочном списке допустимы только явно
названные объекты. Wildcard задаётся отдельными точными строковыми формами
`reference:~any`, `reference:~any_document`, `reference:~any_catalog`.
Знак `~` недопустим в имени объекта (`metadata/ident.go`, `identRe`), поэтому эти
формы не совпадают с существующей одиночной ссылкой. Неизвестный wildcard-токен
отвергается при загрузке, а не трактуется как имя объекта.

Строки `reference:any`, `reference:any_document`, `reference:any_catalog` сохраняют
прежний смысл: одиночные ссылки на объекты с именами `any`, `any_document`,
`any_catalog`. Имена не резервируются; при отсутствии соответствующего объекта
работает обычная проверка одиночной ссылки, без fallback к wildcard.

Состав «любой» вычисляется по конфигурации при загрузке, поэтому новый документ
автоматически входит в «любой документ». Wildcard остаётся составным полем с
признаком `AnyRef`, даже если сейчас в конфигурации один подходящий объект:
нормализация явного списка из одного элемента к нему не применяется.

В модели: `FieldTypeComposite` («composite»), `Field.RefEntities []string` — развёрнутый
состав, `Field.AnyRef` — признак «любой» и его сужение (для сообщений, конфигуратора и
`describe`). `RefEntity` у составного поля пуст: код одиночной ссылки его не видит.

## Наблюдаемая семантика и инварианты

1. **Значение** — пара «тип, идентификатор». Пусто — `Неопределено` (согласуется с
   планом 159, #1274: у составного типа нет «пустой ссылки» одного вида).
2. **Тип значения проверяется при записи** на всех путях (форма, DSL, REST, обмен):
   ссылка не из состава — ошибка с именем реквизита и списком допустимых типов, а не
   запись. При изменении состава миграция проверяет и уже сохранённые пары до
   принятия новой конфигурации; сужение не оставляет неподдерживаемые типы в базе
   (порядок и отказ описаны ниже).
3. **Ссылочная целостность без внешнего ключа.** Внешний ключ на несколько таблиц в SQL
   невозможен, поэтому существование объекта проверяется при записи (как
   `fk_diagnosis.go` сейчас объясняет нарушение ключа, только до записи), а
   `CheckRefs` (`storage/deletion.go`) ищет ссылки в составных колонках — иначе
   «Удалить помеченные» удалит объект, на который они указывают.
4. **`ТипЗнч`** значения составного реквизита — тип конкретной ссылки
   (`ДокументСсылка.РеализацияТоваров`), как у одиночной (`interpreter.Ref` уже несёт
   `Type` и `Kind`).
5. **Одиночные ссылки не меняются** ни в хранении, ни в поведении.

## Хранилище

Две колонки на реквизит:

| Колонка | Тип | Смысл |
|---|---|---|
| `<имя>_id` | UUID | идентификатор объекта |
| `<имя>_type` | TEXT | имя объекта конфигурации (как `recorder_type` у движений) |

Индекс — по `<имя>_id` (выборка по ссылке селективна и без типа). Внешнего ключа нет
(инвариант 3). Имя `_type` выбрано по образцу существующих `recorder_type`; переименование
объекта конфигурации платформа не переносит (таблица создаётся заново), и у `_type` та
же граница, что у `recorder_type`.

Примитивы (срез 6) получат по колонке на объявленный примитивный член: `<имя>_str`,
`<имя>_num`, `<имя>_date`, `<имя>_bool`, а `_type` — значения `~string`/`~number`/`~date`/`~bool`.
Знак `~` недопустим в именах объектов (`metadata/ident.go`, `identRe`), поэтому тип-примитив
не совпадёт с объектом конфигурации, названным `string`.

**Смена типа реквизита** (расширение реструктуризации, план 81).
Это новая операция изменения ссылочного состава и ограничений, а не обычный
ретайп SQL-колонки: сейчас `restructureTable` пропускает таблицу без устойчивых
`Field.ID`, а `applyRetype` при одинаковом SQL-типе возвращается до DDL. Эти пути
сами по себе не снимают внешний ключ и не проверяют смену состава.

Одиночная ссылка → составной тип:

- сохранить `<имя>_id`, добавить `_type` и заполнить прежним `RefEntity` только
  строки с непустым идентификатором; пустое значение остаётся пустой парой;
- PostgreSQL: найти фактический внешний ключ этой колонки в каталоге
  `pg_constraint` с учётом таблицы и схемы, выполнить явный
  `ALTER TABLE … DROP CONSTRAINT …`; имя ограничения не угадывать, `CASCADE`
  не использовать. Если ограничение затрагивает другие колонки, остановить
  миграцию с диагностикой, не снимать его целиком;
- SQLite: реализовать пересоздание таблицы с переносом всех колонок и строк,
  исключив только прежний FK составного реквизита. Сохранить прочие FK, PK,
  UNIQUE, индексы и триггеры; учесть входящие ссылки на пересоздаваемую таблицу.
  Нельзя удалять данные каскадом или пытаться отключить `foreign_keys` внутри
  уже начатой транзакции. После пересоздания проверить `foreign_key_check`;
- добавление колонки, заполнение пары, снятие FK и запись фактического состояния
  схемы выполнить атомарно; ошибка откатывает данные и DDL, повторный `DB.Migrate`
  после успеха не меняет их.

Операция обязательна и для старых реквизитов **без `Field.ID`**: при неизменном
имени найти колонку по `metadata.ColumnName`, прежний одиночный тип доказать
сохранённой подписью схемы либо фактическим FK и его таблицей-целью. Расширить
учёт схемы для таких полей, чтобы хранить применённый состав и после снятия FK.
Неоднозначный или отсутствующий источник прежнего типа — отказ до DDL, а не
пропуск миграции или угадывание. Переименование без устойчивого id этот путь
не обещает.

**Смена состава существующего составного поля.** До изменения подписи схемы и
активации новой конфигурации проверить все сохранённые пары по новому развёрнутому
списку типов: тип входит в состав, объект существует, пусто только при обоих
пустых членах пары. Проверка выполняется при каждом `DB.Migrate`, включая поля
без id, явные списки и сужение `reference:~any`/`reference:~any_document`/
`reference:~any_catalog`;
удаление вида объекта из конфигурации также меняет допустимый состав.

При переходе `[A, B]` → `[A, C]` и наличии непустых значений B — **отказ** с
именем таблицы/поля, запрещёнными типами и числом строк. Ни данные, ни применённая
подпись схемы не меняются; новая конфигурация не становится рабочей и не строит
`CASE` по суженному составу. `--allow-destructive` не разрешает стереть такие
значения. Администратор сначала явно заменяет или очищает их через прежнюю
конфигурацию и повторяет миграцию; автоматического B → C нет, даже при одинаковом
UUID. Если все пары допустимы, смена состава проходит без преобразования данных.
Проверка и применение защищены от конкурентной записи старым составом: на время
операции записи блокируются, а ошибка оставляет прежнее применённое состояние.

Составной → одиночная — только если все непустые значения нужного типа и объекты
существуют; после проверки восстановить FK на одну таблицу (SQLite — пересозданием)
и убрать `_type` в той же атомарной операции. Иначе отказ с числом несовпадающих
строк. Строка → составной автоматически не переносится.

## Запросы

- **Выборка** `Т.Поле` — представление, как у одиночной ссылки: для явного состава —
  `CASE Т.поле_type WHEN … THEN (SELECT наименование/номер …) END`; для «любой ссылки» —
  пакетное разыменование в Go по типам после выборки (десятки `CASE` по всем объектам
  конфигурации не нужны). `RefColumns` (`query.Result`) отдаёт DSL типизированную ссылку.
- **Сравнение** с параметром-ссылкой — `(поле_type = $тип AND поле_id = $id)`;
  `В (&Список)` — по парам. Сравнение только по UUID запрещено: одинаковый
  идентификатор в двух таблицах — обычное дело после переноса данных из 1С, где объект
  нового вида часто создают с GUID исходного объекта другого вида.
- **Новые конструкции:** `Поле ССЫЛКА Документ.X` (проверка типа), `ВЫРАЗИТЬ(Поле КАК
  Документ.X)` (соединение с таблицей X с проверкой типа — открывает `ВЫРАЗИТЬ(…).Дата`
  и ссылки второго уровня плана 194), `ТИПЗНАЧЕНИЯ(Поле) = ТИП(Документ.X)`.
- **Группировка** — по обеим колонкам.
- **Права.** `ВЫРАЗИТЬ` добавляет объект X в `Result.Sources` (объектный RBAC, план 54),
  разыменование представления — только тех объектов, которые пользователю разрешены
  (иначе представление закрытого документа утекло бы через составное поле). Строковые
  политики (RLS) по составному полю отвергаются валидацией политики до отдельного
  решения: сравнение с `user_attr`/константой определено для одиночных ссылок.

## Совместимость

- Существующие конфигурации и данные не меняются: составной тип появляется только там,
  где его объявили.
- Старые `reference:any`, `reference:any_document`, `reference:any_catalog` остаются
  одиночными ссылками с прежними `RefEntity`, колонкой `_id` и физическим FK;
  колонка `_type` для них не появляется. Новые wildcard-формы с `~` объявляются
  явно; совпадение с именем существующего объекта не требует миграции или выбора.
- Пока срез не дошёл до места (ТЧ, регистр, обмен, RLS), `onebase check` отвергает
  составной тип в нём с текстом «составной тип пока не поддерживается в …» — а не
  принимает молча.
- Импорт из 1С начинает давать составные поля после среза 5; до него — строка, как сейчас,
  с тем же примечанием в отчёте конвертера.

## Срезы

Каждый срез — отдельный PR. Тесты — через публичные точки входа: `DB.Migrate`, DSL
(`Справочники.X`/`Документы.X` — создать, записать, прочитать), `onebase query`,
HTTP-обработчики форм и REST, `ForEachDialect` для SQL.

1. **Модель, хранение, DSL** — реквизиты шапки справочников и документов.
   Тесты: запись и чтение значения каждого типа из состава, `ТипЗнч`; чужой тип и
   несуществующий объект отвергаются на записи; `Удалить помеченные` отказывает, пока на
   объект ссылается составное поле; ТЧ, регистр и RLS с составным типом не проходят
   `check`. Регрессии совместимости через публичные `onebase check` и
   `onebase describe`: конфигурация со справочниками `any`, `any_document`,
   `any_catalog` и тремя одноимёнными одиночными ссылками проходит проверку;
   описание сохраняет прежние `RefEntity` и одиночный вид каждого поля.
   Отдельно проверить все три новые формы с `~`: состав и `AnyRef` в описании,
   отбор документов/справочников, сохранение wildcard при одном подходящем
   объекте, отказ для неизвестного токена и wildcard внутри явного списка.
   Отсутствующий объект `any*` даёт ошибку одиночной ссылки, а не wildcard.
   Матричные тесты миграций через `DB.Migrate` на SQLite и PostgreSQL:
   - старая конфигурация с тремя одиночными `reference:any*` после повторной
     миграции сохраняет значения, физические FK на соответствующие таблицы
     и отсутствие `_type`; чужая ссылка по-прежнему отвергается;
   - явно объявленные `reference:~any*` получают пару `_id`/`_type` без FK;
     запись и чтение через DSL соблюдают состав каждого wildcard, включая
     конфигурацию, где одновременно существуют старые одиночные ссылки;
   - одиночная A → `[A, B]` с `Field.ID` и без него: старые значения и пустые пары
     сохранены; физический FK на колонке отсутствует (`pg_constraint` /
     `PRAGMA foreign_key_list`); запись ссылки B через публичный путь проходит;
   - пересоздание на SQLite сохраняет прочие ограничения, индексы, триггеры и
     входящие ссылки; `foreign_key_check` чист; повторная миграция идемпотентна;
   - `[A, B]` → `[A, C]` при данных B, а также сужение «любой ссылки» — отказ до
     активации новой конфигурации, точное число строк, данные и подпись состава
     прежние даже с `--allow-destructive`; после явной замены B миграция успешна;
   - расширение `[A, B]` → `[A, B, C]` и сужение при отсутствии исключаемых значений
     успешны; тип B не подменяется C по совпадающему UUID;
   - составной → одиночная восстанавливает физический FK и сохраняет данные,
     при чужом типе отказывает; ошибка посреди DDL откатывает всю операцию.
2. **Запросы.** Тесты: выборка даёт представление и типизированную ссылку в DSL;
   сравнение с параметром не находит объект другого типа с тем же UUID; `ССЫЛКА`,
   `ВЫРАЗИТЬ(…).Реквизит`, `ТИПЗНАЧЕНИЯ`; пользователь без права на X не видит
   представления X через составное поле, а `ВЫРАЗИТЬ(… КАК X)` для него — отказ RBAC.
3. **Формы и REST.** Тесты: HTTP — форма с составным полем рисует выбор типа, запись из
   формы сохраняет пару; REST v2 отдаёт и принимает `{"type","id"}`, OpenAPI описывает
   состав. Проверка в браузере (headless Edge + CDP) до готовности: выбор типа, подбор,
   открытие выбранного объекта.
4. **Табличные части и регистры.** Тесты: ТЧ с составным полем через форму и DSL;
   измерение регистра накопления составного типа — `Остатки()`/`Обороты()` с итогами и
   без группируют по паре; регистр сведений — `СрезПоследних` по составному измерению.
5. **Перенос.** Тесты: обмен переносит пару и восстанавливает ссылку у получателя;
   универсальная копия — круговой перенос; конвертер строит список типов из выгрузки 1С
   с составным ссылочным реквизитом.
6. **Примитивы в составе.** Тесты: запись и чтение каждого примитива и ссылки в одном
   поле; сравнения в запросе с учётом типа; форма даёт выбрать «Число» или «Документ X».

## Риски и откат

- **Ширина изменения.** Главный риск — код одиночной ссылки, который примет составное
  поле за строку. Защита — отдельный вид поля и отказ `check` вне разрешённых мест;
  каждый срез расширяет список вместе с тестами.
- **Представление «любой ссылки»** в больших выборках — пакетное разыменование по типам
  одним запросом на тип; замер в срезе 2 на 100 тыс. строк.
- **Целостность без внешнего ключа** держится на проверке записи и `CheckRefs`; прямой
  SQL в обход платформы её нарушит — как и сейчас у регистров, где внешних ключей нет.
- **Откат.** Каждый срез удаляется вместе с разрешением в `check`: конфигурации,
  успевшие объявить составной тип в этом месте, перестают проходить проверку — это
  видно до запуска, а не после.

## Критерии завершения

- составной ссылочный тип и «любая ссылка» работают в шапке, ТЧ, регистрах, запросах,
  формах, REST, обмене и конвертере; примитивы в составе — после среза 6;
- ни одно место, не поддерживающее составной тип, не принимает его молча;
- `DEVELOPER.md` описывает синтаксис и запросы, `docs/features.md` — раздел о составных
  типах (пользовательская возможность).
