# Этап 161 — Живой транзакционный контекст для DSL-запросов

## Контекст

План ведёт issue #1216. В ней `procrun` с явной `НачатьТранзакцию()` выполнял
`Новый Запрос` через контекст, сохранённый до открытия транзакции. На SQLite
транзакция удерживала единственное соединение, запрос пытался получить второе и
процесс доходил до `fatal error: all goroutines are asleep - deadlock!`. На
PostgreSQL тот же разрыв не блокировал процесс, но запрос не видел собственные
незакоммиченные записи.

Выбран вариант 3 из доверенного triage issue: сначала описать единый механизм и
публичную матричную проверку, затем менять поведение небольшими срезами. Владелец
повторно подтвердил вариант 3 после появления plan-этапа. Аварийная страховка
«штатная ошибка вместо фатального зависания» вынесена в самостоятельную issue
#1272 и не дублируется этим планом: она может войти до или после реализации
живого контекста.

После triage часть решения уже появилась в `main` вместе с PR #1259:

- `internal/dsl/interpreter/query_proxy.go` содержит
  `NewQueryFactoryGuardedSource`, а `queryProxy.execute` получает контекст из
  `CtxSource` непосредственно перед компиляцией и выполнением SQL;
- `internal/ui/handlers_dsl.go:buildDSLVarsTx` передаёт `TxState` в
  `dslvars.Common`, но затем отдельно заменяет обе фабрики запросов на
  `NewQueryFactoryGuardedSource`;
- поэтому UI, `RunProcessorOffline`/`procrun` и производственный сборщик
  окружения регламентных заданий уже идут по живому пути;
- `internal/dslvars.Common.Build` при этом всё ещё создаёт фабрику через
  `NewQueryFactory(c.Ctx, ...)`, хотя выше уже вычисляет `ctxSource`. Общий
  конструктор тем самым сохраняет старую семантику и вынуждает UI держать
  корректирующее переопределение;
- `internal/cli/eval.go` создаёт статическую фабрику напрямую. Это корректная
  отдельная граница: sandbox `eval` не инжектирует транзакционные builtin'ы и не
  имеет меняющегося `TxState`.

Цель этапа — сделать живой контекст свойством единой точки сборки DSL-окружения,
а не особенностью одного вызывающего кода, и закрепить пользовательский контракт
тестом через реальный offline-путь.

## Наблюдаемая семантика и инварианты

1. `Новый Запрос`, выполненный внутри открытой DSL-транзакции, использует
   контекст этой транзакции и видит записи, сделанные ранее в ней же.
2. Контекст выбирается в момент `Выполнить()`, а не при сборке карты переменных и
   не при создании объекта `Запрос`. Объект, созданный до
   `НачатьТранзакцию()`, при выполнении внутри транзакции должен войти в неё;
   объект, выполненный после commit/rollback, должен использовать текущий
   нетранзакционный контекст.
3. Компилятор запроса, SQL-выполнение и `QueryGuard` получают один и тот же
   актуальный контекст. Нельзя применить RLS/маскирование с одной identity или
   транзакцией, а строки прочитать с другой.
4. На SQLite запрос внутри транзакции не обращается к пулу за вторым соединением
   и не зависает. На PostgreSQL он имеет ту же семантику read-your-writes.
5. Rollback после успешного чтения удаляет сделанную в транзакции запись;
   матричный тест обязан проверять не только чтение, но и отсутствие записи
   после отката.
6. Дедлайны, отмена, audit/RBAC/RLS-значения базового контекста сохраняются при
   переключении `TxState`. Транзакционный контекст добавляет transaction value,
   но не создаёт новую identity.
7. Вызовы без меняющегося `CtxSource` сохраняют прежнее поведение. Статический
   контекст остаётся допустимым для `eval`, простых unit-тестов и других
   read-only окружений без DSL-транзакций.
8. Вложенная `НачатьТранзакцию()` продолжает означать savepoint на том же
   соединении; запрос не открывает отдельную транзакцию и не меняет правила
   commit/rollback из `interpreter.TxState`.

## Инвентаризация затронутых границ

### Фабрика и выполнение запроса

- `internal/dsl/interpreter/query_proxy.go` — статические конструкторы
  `NewQueryFactory*`, source-aware конструктор, `queryProxy.context()` и
  `execute()`. Здесь живёт правило «контекст берётся при выполнении».
- `internal/dsl/interpreter/query_test.go` либо новый узкий
  `query_context_test.go` — unit-контракт на смену источника между созданием
  фабрики/объекта и `Выполнить()`.

### Сборка DSL-окружения

- `internal/dslvars/dslvars.go` — `Common.Ctx`, `Common.CtxSource` и создание
  `__factory_Запрос`/`__factory_Query`. Это каноническая общая точка для UI,
  обработок и scheduler fallback.
- `internal/ui/handlers_dsl.go:buildDSLVarsTx` — полная UI/offline-сборка,
  компилятор RLS и `dslQueryGuard`. Ручная замена фабрики здесь должна исчезнуть
  после того, как `Common` сможет получить optional compiler/guard и создать
  правильную фабрику сам.
- `internal/ui/offline.go:RunProcessorOffline` и `Server.RunProcessor` —
  публичная программная точка входа для регрессии `procrun`; production CLI
  `internal/cli/procrun.go` только открывает проект/БД и вызывает её.
- `internal/scheduler/scheduler.go` — production использует внешний
  `ui.Server.BuildJobDSLVars` и получает тот же `TxState`; локальный fallback
  `dslvars.Common` остаётся статическим, пока caller не передал `CtxSource` и не
  инжектировал транзакционные функции.
- `internal/cli/eval.go` — проверяемая, но не изменяемая граница: restricted
  sandbox без `НачатьТранзакцию`, поэтому `context.Background()` не является
  источником дефекта #1216.

### Хранилище и диалекты

- `internal/storage/tx.go` — `ContextWithTx`, `HasTx`, `Query`/`QueryContext` и
  выбор `sql.Tx` вместо пула. Менять этот слой для живого контекста не требуется:
  он уже корректно маршрутизирует операции по transaction value.
- `internal/storage/sqlite.go` — `SetMaxOpenConns(1)` делает потерю контекста
  блокировкой и остаётся важным условием регрессионного теста.
- `internal/dbtest/dbtest.go:ForEachDialect` — обязательный общий harness:
  SQLite выполняется всегда, PostgreSQL — в integration job при
  `TEST_DATABASE_URL`.

## Синтаксис / YAML

Новых конструкций DSL и полей YAML нет. Проверяемый пользовательский сценарий
использует существующий синтаксис:

```bsl
НачатьТранзакцию();
Элемент = Справочники.ТестовыеДанные.Создать();
Элемент.Наименование = "видно внутри транзакции";
Элемент.Записать();

Запрос = Новый Запрос;
Запрос.Текст =
"ВЫБРАТЬ Данные.Ссылка
|ИЗ Справочник.ТестовыеДанные КАК Данные
|ГДЕ Данные.Наименование = &Имя";
Запрос.УстановитьПараметр("Имя", "видно внутри транзакции");
Результат = Запрос.Выполнить();

ОтменитьТранзакцию();
```

До rollback `Результат` содержит созданную строку. После завершения обработки
строки в базе нет.

## Хранилище / SQL

Схема БД, миграции и генерируемый SQL не меняются. Изменяется только receiver
уже скомпилированного SQL: при активной DSL-транзакции `storage.DB.QueryAll`
получает context с `storage.Tx` и выполняет запрос через это соединение.

Нельзя решать задачу увеличением SQLite-пула: это скроет deadlock, но сохранит
чтение вне транзакции и разную видимость данных между SQLite и PostgreSQL.

## Совместимость и миграция

- Миграции данных и конфигураций не нужны.
- Для окружений с `CtxSource` изменение поведения намеренное: запрос начинает
  видеть собственные незакоммиченные записи. Это ожидаемая транзакционная
  семантика и совпадает с уже действующим UI/offline-путём после #1259.
- Вне транзакции SQL, параметры, порядок строк, нормализация типов и
  маскирование не меняются.
- Статические конструкторы `NewQueryFactory`, `NewQueryFactoryWithCompiler` и
  `NewQueryFactoryGuarded` сохраняются для совместимости внутренних и внешних
  Go-вызовов. Новый source-aware convenience API добавляется рядом, без смены
  существующих сигнатур.
- #1272 остаётся defense-in-depth для ошибочно статического caller'а. Его
  реализация не должна становиться способом проверить #1216: основной тест
  обязан успешно прочитать строку, а не только получить управляемую ошибку.
- В release note нужно явно назвать изменение read-your-writes для DSL-запросов
  внутри транзакции. В `docs/features.md` запись не требуется: это исправление
  контракта, а не новая пользовательская возможность.

## Последовательность PR-срезов

### Срез 1 — Source-aware контракт фабрики

1. Добавить симметричный convenience-конструктор
   `NewQueryFactorySource(ctxSrc CtxSource, db QueryDB, reg QueryRegistry)` (и,
   только если реально нужен вызывающему коду,
   `NewQueryFactoryWithCompilerSource`). Все source-aware варианты должны
   сходиться в одну реализацию `queryProxy` с `ctxSrc`, без копирования `execute`.
2. Добавить unit-тест с изменяемым `CtxSource` и spy `QueryDB`: фабрика и объект
   создаются на контексте A, источник переключается на B до `Выполнить()`, а
   compiler, SQL и guard наблюдают B. Отдельная проверка оставляет статический
   конструктор на A.
3. Не менять storage, пул SQLite или семантику статических конструкторов.

Публичная проверка среза: `go test ./internal/dsl/interpreter -run
TestQueryFactory.*Context`.

### Срез 2 — Единая сборка окружения и end-to-end матрица

1. Расширить `dslvars.Common` optional-полями `QueryCompiler` и `QueryGuard`.
   `Build()` создаёт фабрику из уже нормализованного `ctxSource`: при отсутствии
   `CtxSource` это `NewStaticCtx(c.Ctx)`, при наличии — живой источник caller'а.
2. В `buildDSLVarsTx` передать UI compiler/guard в `Common` и удалить позднюю
   ручную замену `__factory_Запрос`/`__factory_Query`. Обе локали имени обязаны
   ссылаться на одну и ту же фабрику.
3. Добавить `internal/ui/offline_query_tx_matrix_test.go` через
   `dbtest.ForEachDialect`. Тест поднимает минимальный проект, мигрирует сущность,
   запускает обработку через `RunProcessorOffline`, делает «begin → write →
   query → rollback» и проверяет: внутри видна ровно одна строка, выполнение
   завершается в ограниченный deadline, после rollback строк нет.
4. Второй сценарий создаёт объект `Запрос` до `НачатьТранзакцию()`, выполняет
   после записи и подтверждает инвариант выбора контекста именно в момент
   `Выполнить()`.
5. Зафиксировать wiring scheduler тестом или существующим compile-time
   контрактом: production `BuildJobDSLVars` проходит через тот же `Common` с
   `TxState`; статический fallback и `cli eval` не получают ложную поддержку
   транзакций.

Публичная проверка среза: `go test ./internal/ui -run
TestRunProcessorOffline_QueryReadYourWrites` и полный `go test ./...`; в
PostgreSQL job тот же тест выполняется с `TEST_DATABASE_URL`.

## Риски и защита от регрессий

- **Контекст RLS/пользователя потерян при переключении.** Unit-spy проверяет
  identity/value и deadline, а UI использует один context для compiler, SQL и
  guard.
- **Тест зелёный на приватной функции, но CLI всё ещё сломан.** Основная
  регрессия идёт через `RunProcessorOffline`, ту же точку, которую вызывает
  `procrun`; unit-тест лишь локализует контракт фабрики.
- **SQLite-тест зависает вместо диагностичного падения.** Вызов получает
  `context.WithTimeout`; тест имеет собственный короткий deadline и требует
  успешного результата, поэтому #1272 не может замаскировать потерю контекста.
- **PG и SQLite закрепляют разные ожидания.** Одна функция
  `dbtest.ForEachDialect` исполняет одно тело и одинаковые assertions.
- **Поздний query использует уже завершённую транзакцию.** Контекст берётся при
  каждом `Выполнить()`, а тест «создан до begin» дополняется unit-переключением
  обратно на статический контекст после commit/rollback.
- **Расширение `Common` неожиданно меняет read-only callers.** При nil
  `CtxSource` используется `NewStaticCtx(c.Ctx)`; regression unit сравнивает
  статический и живой пути.

## Откат

Оба среза откатываются обычным revert без миграции. Если после среза 2 найдена
несовместимость, сначала возвращается ручное source-aware переопределение в
`buildDSLVarsTx`, затем откатывается изменение `dslvars.Common`; source-aware
API и тест фабрики можно оставить, если они сами корректны. Временное наличие
#1272 снижает риск фатального SQLite-сбоя, но не считается заменой отката.

## Verification

1. На SQLite запустить matrix-тест без `TEST_DATABASE_URL`: оба offline-сценария
   завершаются до deadline, видят строку внутри транзакции и не находят её после
   rollback.
2. С `TEST_DATABASE_URL` повторить тот же тест на эфемерной PostgreSQL-схеме;
   assertions совпадают с SQLite.
3. Запустить минимальную обработку через настоящий `onebase procrun`: создать
   запись в явной транзакции, прочитать `Новый Запрос`, вывести найденное
   количество, откатить. Команда завершается штатно и база остаётся без записи.
4. Выполнить запрос вне транзакции через `onebase eval --sqlite ...` и
   подтвердить прежний результат restricted sandbox.
5. Запустить `go test ./internal/dsl/interpreter ./internal/dslvars
   ./internal/ui ./internal/scheduler`, затем `go test ./...`.

## Критерии завершения

- source-aware и статический контракты фабрики выражены отдельными публичными
  Go-конструкторами и покрыты unit-тестом;
- `dslvars.Common` использует нормализованный `CtxSource` для запросов и умеет
  принять UI compiler/guard без позднего переопределения карты;
- UI, `procrun` и production scheduler получают фабрику из одной точки сборки;
- матричный публичный тест доказывает read-your-writes и rollback на SQLite и
  PostgreSQL;
- нет изменений схемы, продуктового синтаксиса или статического `eval`;
- обязательные тесты репозитория зелёные, а release note описывает изменение
  транзакционной видимости.
