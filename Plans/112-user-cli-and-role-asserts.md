## Контекст

Обсуждение выросло из практики: `onebase generate` отдаёт базу под ручной тест,
но пользователей приходится заводить руками через веб-админку — единственный путь
их создания сегодня (`auth.Repo.CreateManaged` подключён только к
`internal/ui/admin.go` и `internal/launcher/roles_handlers.go`). CLI для этого нет.

Параллельно всплыл вопрос: харнесс `onebase test` (план 136) **не умеет
тестировать роли**. Причины структурные:

- раннер гоняет `kind: test` офлайн через `RunProcessor`, инжектит только
  `Утверждать` + `Часы` + `Мок`; понятия «текущий пользователь» на этом пути нет
  (`ТекущийПользователь()` — переменная веб-пути, `internal/ui/handlers_dsl.go`);
- проверки прав `user.Has(kind, entity, op)` живут в HTTP/UI-слое (middleware,
  навигация, хендлеры), а DSL-путь записи исполняется привилегированно (от
  системы) — и это правильно: логика проведения пишет движения в регистры, к
  которым у пользователя прямого доступа нет.

Роли при этом **уже декларативны** — лежат в `roles/*.yaml`, синкаются в БД
(`SyncRoles`) при `run`/`dev`. То есть «создавать роли» руками не надо; вручную
остаётся заведение аккаунтов и назначение ролей.

## Решение

### 1. `onebase user` — офлайн-CLI

Стандартные `addBaseFlags`/`resolveBase`/`bc.OpenDB` (как `procrun`/`migrate`) —
операция локальная и офлайновая, над файлом/DSN базы. Подкоманды:

```
onebase user list   [--project . | --sqlite f | --id base]
onebase user add    <login> --name "Полное имя" [--admin] [--generate | --password-stdin]
onebase user passwd <login> [--generate | --password-stdin]
onebase user role assign <login> <РольИзRolesYAML>
onebase user role revoke <login> <Роль>
onebase user rm     <login>            # уважает инварианты «последний админ/юзер»
```

- **Пароли не через argv.** `--generate` (по умолчанию, если источник пароля не
  задан) генерирует стойкий случайный пароль и печатает его в stdout — ровно под
  боль «сгенерили базу, нужен юзер». `--password-stdin` — читает из stdin для
  скриптов/CI. Интерактивный no-echo prompt отложен (потребовал бы `x/term`).
- **Инварианты и политика — из `auth.Repo`.** `CreateManaged` (первый юзер обязан
  быть админом, bcrypt, парольная политика из env), `Delete` (последний
  админ/юзер), `UpdatePassword`. CLI не переизобретает SQL по `_users`.
- **Роли.** Перед `role assign` синкаем `roles/*.yaml` в базу (`LoadRolesYAML` +
  `SyncRoles`), затем `AssignRole` по имени роли (резолв name→id).
- **Аудит.** Каждое изменение логируется `db.LogAction(..., userLogin="cli")` —
  создание пользователя через CLI не должно быть невидимым. Нужен
  `EnsureAuditSchema` + `authRepo.EnsureSchema` до операций.

### 2. `Утверждать.РольМожет / РольНеМожет`

Декларативный ассерт поверх настоящего движка прав — честный (тот же
`auth.PermissionHas`, что и рантайм), дешёвый, детерминированный, без сервера и
без заведения пользователей:

```
Утверждать.РольМожет("Кладовщик", "документ", "РеализацияТоваров", "провести", "кладовщик проводит");
Утверждать.РольНеМожет("Кладовщик", "справочник", "Организация", "изменять", "не редактирует орг.");
```

- Аргументы: `(ИмяРоли, Вид, Объект, Операция [, Описание])`. Вид принимает
  русско/англо-слова (`документ`/`document`, `справочник`, `регистр`,
  `регистрсведений`, `отчёт`, `обработка`) — нормализуется существующим
  `permissionKindFromKey`. Операция принимает канон (`read/write/post/unpost/
  delete/run`) и русские синонимы (`провести`→post, `изменять`→write, …).
- Источник ролей — **`roles/*.yaml`** (то, что автор редактирует и задеплоит), а
  не БД: работает на `:memory:`, синк не нужен.
- Ошибка резолва (неизвестная роль/вид) — **провал ассерта с внятным detail**, а
  не паника: это баг автора теста, показать громко.

**Слои:** `interpreter` не должен зависеть от `auth`. Поэтому в `interpreter`
объявляется узкий интерфейс `RoleChecker`, а конкретную реализацию (загрузка
`roles/*.yaml` + `auth.PermissionHas`) инжектит раннер из пакета `ui` (он уже
импортирует и `auth`, и `interpreter`). Вне `onebase test` (checker == nil) —
ассерт проваливается с пояснением «проверка ролей доступна только в onebase test».

## Безопасность (обоснование CLI)

Граница доверия — **файл базы / креды PostgreSQL**, а не наличие CLI. У кого есть
`base.db` — у того уже есть всё: читать любые данные, `UPDATE _users SET
is_admin=1` сырым SQL. `onebase user add` над `--sqlite/--db` **не опускает
планку** — делает через `auth.Repo` то же самое корректно (bcrypt, политика,
инвариант «первый — админ», аудит) вместо кривого ручного SQL. Тот же класс
операции, что `migrate`/`procrun`.

Линии, которые держим:

- только офлайн/локально; **никакой** сетевой ручки создания юзеров без авторизации
  (веб-путь уже закрыт админкой — CLI его не дублирует как незащищённый эндпоинт);
- пароль не в argv (leak в history/`ps`) — только `--generate`/`--password-stdin`;
- аудит CLI-операций;
- **никаких дефолтных `admin/admin`** в генерённых базах — сидирование только явно.

## Шаги реализации

1. **auth: экспортируемые хелперы прав** — `KindFromWord`, `NormalizeOp`,
   метод `(*Role).Allows(kindWord, entity, op) (bool, error)`. Юнит-тест матрицы.
2. **interpreter: ассерт ролей** — интерфейс `RoleChecker`, поле в `AssertRoot`,
   методы `РольМожет/РольНеМожет`, обновить панику-«неизвестный метод». Тест с
   фейковым checker.
3. **ui: инъекция в раннер** — загрузка `roles/*.yaml`, реализация `RoleChecker`,
   проброс в `runOneTest`. Интеграционный тест в `testrun_test.go`.
4. **cli: команда `user`** — файл `internal/cli/user.go`, подкоманды, пароль-флоу,
   синк ролей, аудит. Тест на SQLite (add → list → role assign → passwd).
5. **Документация** — `docs/features.md` (секция про `onebase user`, status:
   testing), регенерация `AGENTS.md` (`onebase ai-guide`), упоминание асcертов
   ролей в справке `onebase test`.

## Не-цели (обоснованный отказ)

- **Офлайн «run as role» с проверкой прав в DSL-пути записи.** Тестировал бы
  реимплементацию проверки, а не настоящий чокпоинт (реальный риск RBAC — путь в
  обход, а не неверная матрица), давал бы ложную уверенность и ломал бы
  привилегированную модель серверного DSL. Enforcement остаётся протестирован в
  Go-тестах на HTTP-границе (`nav_rbac_test`, `subsys_access_test`,
  `attachments_rbac_test`, `field_access_test`, `row_access_chokepoint_test`).
- **Ассерты row-/field-level доступа** (`RowAccess`/`FieldAccess`) — отдельная,
  более хитрая мишень (зависит от данных строки/пользователя). Кандидат в v2.
- **Интерактивный no-echo prompt пароля** — потребовал бы `golang.org/x/term`;
  `--generate`/`--password-stdin` закрывают потребность без новой зависимости.
