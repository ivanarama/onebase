# Этап 200 — Ограниченные lock-слоты REST-кэша pipelinehealth

## Контекст и выбранное решение

Ведущая заявка: [#1721](https://github.com/ivanarama/onebase/issues/1721).
Проверено по `main` `788ed47c55d59b670118050066382fb17aa3e6bd`, 08.10.2026.
Это технический план, реализация ещё не выполнена.

Кэш REST-транспорта сохраняет отдельный `<digest>.json.lock` для каждого ключа.
Число ключей растёт с URL, страницами пагинации и SHA коммитов; число
lock-файлов растёт вместе с ним. Закрытие процесса освобождает блокировку ядра,
но файл остаётся. Ограничить нужно именно количество lock-файлов: ротация
ответов `.json` и общий лимит дискового кэша — самостоятельная задача.

Канонический triage — комментарий `5849207027` автора `ivanarama`.
Выбран вариант 1: сначала план, затем ограниченное число постоянных lock-слотов
в новом namespace. Источник выбора — последующий доверенный комментарий
[5990545321](https://github.com/ivanarama/onebase/issues/1721#issuecomment-5990545321)
от 05.10.2026; он имеет приоритет над `decision:1` и рекомендацией triage.
Владелец принимает холодный кэш и **явно отказывается от обязательной очистки
старого namespace в этой работе**. Поэтому отдельная manual-заявка на очистку
не является условием реализации. Online-unlink и sweep по mtime не одобрены.

На Unix удаление открытого lock-файла разрывает связь имени с inode:
владелец/ожидатель может остаться на старом inode, а новый процесс — захватить
новый файл по тому же имени. Возраст файла не доказывает отсутствие процессов.
Windows использует другой механизм, но общий контракт не должен зависеть от
того, разрешила ли ОС конкретный unlink.

## Синтаксис / YAML и наблюдаемое поведение

CLI сохраняется: `pipelinehealth -transport rest -cache-dir <root> -json`.
`PIPELINEHEALTH_CACHE_DIR`, вычисление default root и приоритет аргумента
не меняются. `-cache-dir` означает корень кэша, внутри которого появляется
фиксированный дочерний каталог `rest-v2-lock256`.

Новое поведение:

- В одном новом namespace возникает не более 256 lock-файлов независимо от
  числа URL, токенов, страниц и запусков. Файлы создаются лениво и сохраняются
  после release, отмены ожидания и аварийного завершения.
- Первый запрос нового бинаря не использует прежний кэш и получает свежий
  ответ. Дальше сохранённое тело используется только после явного HTTP 304.
- Разные ключи одного слота сериализуются. Разные слоты могут работать
  параллельно. Никакие ошибки HTTP, декодирования, блокировки или записи
  не превращаются в успешное чтение устаревшего ответа.
- Старый бинарь продолжает работать в прежнем root. Старые и новые бинарники
  могут одновременно обращаться к GitHub, но не читают и не заменяют одни
  и те же файлы ответов. Между разными namespace взаимное исключение не нужно.
- JSON результата checker’а, trusted owner, allowlist выбора и локальные
  GraphQL mutation/proof-гейты сохраняют свою семантику.

GraphQL — текущий default transport. Закреплённый операторский checker релиза
`delivery-first-20261003-v16` запускается с `-transport graphql`; этот план
не переводит расписание на REST и не заменяет его health_command. Изменение
репозитория само по себе не обновляет установленный бинарь.

## Хранилище / SQL

Схема БД и прикладные конфигурации не меняются. Новый файловый протокол:

```text
<root>/                          # старые файлы остаются на месте
  <old-digest>.json
  <old-digest>.json.lock
  rest-v2-lock256/
    <digest>.json
    .pipelinehealth-cache-<random>  # временная запись текущего процесса
    locks/
      00.lock
      ...
      ff.lock
```

Ключ ответа сохраняет существующий точный контракт:

```text
authScope = hex(SHA256(lower(apiHost) + "\n" + trim(token)))
digest = SHA256(authScope + "\napplication/vnd.github+json\n2022-11-28\n" + requestURL)
entry = <root>/rest-v2-lock256/hex(digest).json
slot = digest[0]                 # первый байт SHA-256, диапазон 0..255
lock = <root>/rest-v2-lock256/locks/<slot как два lowercase hex символа>.lock
```

Все реализации этого namespace обязаны использовать один алгоритм и 256
слотов. Число слотов не является параметром CLI/env. Изменение hash/числа
слотов/области блокировки требует нового namespace; тот же каталог с новым
числом слотов даёт разные lock-пути для одного entry и запрещён.

Версия JSON-записи `cacheEntryVersion=1` может остаться прежней: меняется
файловый протокол координации, а не структура `Version/URL/ETag/Body`.
Auth scope остаётся частью ключа; токен и его открытое значение не попадают
в имена или сообщения диагностики. Общие слоты для разных auth scopes
допускают лишнее ожидание, но не совместное использование response body.

Каталоги нового namespace и `locks` получают 0700, создаваемые файлы 0600
в пределах существующей платформенной модели прав. На Windows это не обещание
отдельного ACL-механизма. Используется доверенный operator-selected root;
новое расширение политики symlink/ACL здесь не вводится.

## Семантика и инварианты

1. Для каждого entry существует единственный стабильный lock-путь в его
   namespace. Пока namespace используется, lock-файл не удаляется,
   не переименовывается и не заменяется, включая restart и cleanup.
2. Один writer держит эксклюзивную kernel lock с момента **до чтения entry**
   до завершения HTTP, проверки ответа и атомарной замены entry. Сужать область
   только до `write` нельзя: ожидатель должен увидеть ETag предыдущего writer.
3. Reader/writer одного ключа и разных ключей одного слота соблюдают ту же
   блокировку. Отмена ожидания закрывает только собственный дескриптор;
   она не удаляет файл и не отменяет lock другого процесса.
4. Смерть владельца освобождает kernel lock. Следующий процесс продолжает на
   том же постоянном lock-файле. Частично записанный response не принимается:
   действуют temporary + sync + atomic replace и проверки JSON/version/URL/ETag.
5. Несколько слотов одного запроса не захватываются; рекурсивный захват того же
   слота из HTTP callback запрещён. Детерминированные коллизии означают очередь,
   а не дедлок по двум locks. Строгая справедливость kernel lock не обещается.
6. Старый и новый протоколы не делят ни entries, ни locks, ни temp-файлы.
   Новые версии с этим протоколом делят один namespace и стабильно тот же слот.
7. Предел 256 относится к `rest-v2-lock256/locks/*.lock` одного root.
   Суммарное число старых файлов, entries и отдельных operator roots этим
   изменением не ограничивается.

HTTP timeout сейчас входит в общий 45-секундный context ожидания/запроса.
Сохранить это поведение. Коллизии могут исчерпать budget; ошибка видна оператору,
stale fallback запрещён. Если измерения показывают неприемлемую задержку,
останавливается выпуск с этим namespace; менять константу на лету нельзя.

## Совместимость, миграция и откат

Миграция выполняется автоматически новым REST constructor: пустой новый
namespace, обычный HTTP 200, затем conditional requests. Копирование старых
entries, hardlink/symlink alias и чтение старого root из нового клиента запрещены.
Общие env/CLI настройки не требуют изменения. Старый root сохраняется byte-for-byte
за исключением действий запущенных старых клиентов.

Проверить смешанную работу frozen legacy-клиента с per-URL lock в root и нового
клиента в child namespace. Legacy helper воспроизводит старый протокол только
в тестах; не добавлять runtime fallback, читающий старые entries. Дополнительно
оператор проверяет настоящие два бинаря в изолированном каталоге.

Откат: вернуть предыдущий бинарь, не переименовывая каталогов и не удаляя files.
Он снова использует прежний root, но всё равно валидирует ответ серверным
200/304. Новые процессы могут закончить работу независимо. Обслуживание старого
root возможно только отдельным решением оператора после остановки всех старых
экземпляров; этот план не создаёт для этого обязательную задачу.

Выпуск нового checker’а и изменение закреплённого пути health_command — отдельная
операторская поставка проверенного релиза. FIX не подменяет установленный checker
командой `go run` из случайного checkout и не меняет транспорт scheduler’а.

## Последовательность небольших PR-срезов и публичные тесты

### A — Доказать межпроцессный baseline (1.5–2 дня)

Добавить subprocess harness в `tools/pipelinehealth`: разные OS-процессы
используют один root и настоящий production loader `loadPulls`, а затем
`loadIssues` с локальным авторизованным HTTP сервером и одинаковыми fixtures.
Использовать имеющийся `newGitHubRESTClientWithBase` как composition seam для
base URL тестового сервера; не вызывать `acquireCacheFileLock`/`write` вместо
loader и не добавлять production-флаг для произвольного API-host.

Через управляемые ответы HTTP установить A-owner, B-waiter, C-contender.
Родитель принимает сообщения готовности по pipes и удерживает первый response
barrier. Проверить: пока A удерживает запрос, B/C не входят в HTTP critical
section; после release каждый получает корректный snapshot, ожидатель отправляет
ETag. Убить A во время HTTP и убедиться, что B продолжает в пределах budget,
entry остаётся валидным или отсутствует, а не частично записанным.
Отдельно проверить истечение действующего 45-секундного budget ожидающего
loader (он отменяет context ожидания) и успешный последующий запуск.
Loader сейчас не принимает внешний context: не подменять этот сценарий
прямым вызовом private lock-функции. Для этого теста child deadline больше
45 секунд; kill ожидающего процесса проверяется отдельным коротким сценарием.
Уничтожение owner и waiter подтверждается `Wait`, не только отправкой сигнала.
Все children имеют deadline и cleanup; порядок не основывается на `time.Sleep`.

**Публичный путь/приёмка:** production loaders → `getJSON` → kernel lock → HTTP
→ disk → следующий loader. Этот срез проходит на старом протоколе без изменения
runtime; проверка bounded count включается вместе с реализацией в B.
Mac/Linux и настоящий Windows runner запускают одни и те же subprocess сценарии.

### B — Новый namespace и 256 постоянных слотов (2–3 дня)

Одним атомарным кодовым срезом переключить **и entries, и locks**. Добавить
константы namespace/числа слотов, единый digest helper и secure directory setup;
не менять JSON envelope, алгоритм replacement и critical section. Дополнить
срез A проверками миграции, отсутствия unlink и ограничения числа файлов.

**Публичные regressions через loaders:**

- Выполнить последовательность с >256 уникальными endpoint keys (например
  1024 PR/issue comment URLs из paginated fixture), затем повторить из других
  процессов. Все данные совпадают с сервером; в `locks` не более 256 файлов,
  не появляется новый per-entry `.json.lock`. Смена test auth token создаёт
  отдельные entries, но не расширяет множество имён locks.
- Найти два fixture keys с одним первым байтом digest, вызвать два loaders:
  сервер фиксирует непересекающиеся critical sections, каждый key получает
  своё тело. Для разных слотов удержать оба responses одновременно и доказать
  параллелизм. Это защищает от случайного глобального lock.
- Повторить owner/waiter/contender и kill/cancel из A. После многих новых ключей,
  release и restart исходный lock-файл остаётся тем же объектом: file identity
  на Unix и эквивалентная file-id проверка на Windows дополняют HTTP наблюдение.
- Seed старого root: legacy `.json`, `.json.lock`, temp и посторонний файл.
  Новый loader не посылает legacy ETag, создаёт новый namespace, не удаляет
  и не меняет seed. Legacy и новый subprocess одновременно возвращают
  правильные результаты без записи в namespace друг друга.
- Сохранить существующие проверки 200→304, изменённого 200, повреждённых
  envelope/body, auth isolation, malformed JSON, HTTP 503 и invalid 304.
- Добавить в срезе B недостающие сценарии через production loaders
  `loadPulls`/`loadIssues`: неверная `Version` и несовпадающий `URL` в cache
  envelope, а также HTTP timeout в пределах действующего 45-секундного budget.
  Невалидный entry не передаёт ETag и требует свежего ответа; timeout возвращает
  ошибку без cached success. Отсутствие token в output обязательно.
- Ошибка создания namespace/locks и persist возвращается из loader; очередной
  успешный запуск не принимает повреждённый entry. Нельзя молча использовать
  legacy каталог, другой lock-путь либо unprotected HTTP path.

Слой unit tests фиксирует digest→slot golden vectors и точный формат имени;
это дополнение к внешнему поведению, не единственное доказательство работы.

### C — Доставка и операторская проверка (1–1.5 дня)

Сверить документацию с контрактом B и добавить проверку собранного CLI
`-transport rest -cache-dir <isolated root> -json` на read-only GitHub аккаунте.
Два запуска нового бинаря и совместный запуск предыдущего бинаря должны дать
согласованные по протоколу JSON snapshots, корректный exit status и ожидаемые
каталоги; логировать только counts/status, без bodies/tokens. Живые снимки
могут отличаться из-за изменения очереди: сравнение допускает только
объяснимые реальные изменения, не требует идентичности всего JSON по времени.

**Публичная приёмка:** настоящий CLI с настоящими аргументами; отдельно убедиться,
что `-transport graphql` и fixture mode не создают REST namespace.
Subprocess regressions из A/B выполняются в CI без живого GitHub/token.
Доказательство работы Windows — исполнение, а не только cross-build.

## Тесты и Verification

Для каждого кодового среза: `go test ./tools/pipelinehealth`,
`go test -race ./tools/pipelinehealth` на поддерживаемом Unix runner и
`go build ./tools/pipelinehealth`. Межпроцессные сценарии запускать повторно
с явным deadline на Linux, macOS и Windows. Полный обязательный CI остаётся
обычным условием merge каждого PR; план не ослабляет branch protection.

Ручной сценарий в отдельном временном root:

1. Зафиксировать старые бинарь/root и counts, выполнить legacy REST запуск.
2. Запустить новый CLI с тем же root; убедиться в создании `rest-v2-lock256`,
   холодном первом запросе, unchanged legacy файлах и успешном JSON output.
3. Выполнить concurrent/restart сценарий, проверить только новый `locks`:
   максимум 256 имён `00.lock`…`ff.lock`, отсутствие per-entry locks.
4. Под нагрузкой измерить время и число ошибок относительно baseline;
   коллизии допустимы, потеря взаимного исключения/повреждение/новый stale
   success недопустимы. Задокументировать workload и результат.
5. Вернуть старый бинарь; проверить успешное чтение прежнего namespace.
   Каталоги не переименовывать и не удалять при работающих процессах.

## Риски, откат и критерии завершения

Основной риск — несовпадающая формула слота или частичное переключение entries
и locks. Запрещён промежуточный runtime, где новые locks защищают старые entries.
Hash collisions дают задержку и могут исчерпать 45-секундный budget; нагрузочные
измерения обязательны до поставки. Тестовый legacy helper может отклониться
от настоящего старого бинаря: поэтому CLI mixed-version проверка дополняет CI.
Предел locks не устраняет рост самих `.json`; это явно сохраняется как ограничение.

Завершение: A/B/C влиты отдельными проверенными срезами; bounded count доказан
для нескольких процессов; kernel-lock lifecycle подтверждён на Unix/Windows;
старые files сохранены, cold migration и rollback воспроизведены; HTTP/auth
regressions зелёные; документация точна. Установленный checker обновляется
только в отдельно проверенном операторском релизе, если это нужно оператору.

Этот plan PR не закрывает #1721. После обычного REVIEW и человеческого `ship`
MERGE плана возвращает issue в FIX по `Plan-Issue`/`Plan-Path`. Реализация A/B/C
при дальнейшей нарезке соблюдает отдельные approvals/handoff, не предполагает
наличия уже поставленного автоматического механизма из плана 163.

## Эстимейт

Около **4.5–6.5 рабочих дней**: A 1.5–2, B 2–3, C 1–1.5.
Ожидание CI, независимого REVIEW, человеческого ship и операторского релиза
в оценку не входит. Переработка namespace при неприемлемом contention требует
нового измерения и уточнения плана до выпуска, а не незаметной смены алгоритма.
