# План 218 — Проектная база СППР (design ledger) поверх OneBase

Дата проектирования: 2026-11-09.
Статус: ⬜ Проект, **прикладной слой** (промежуточные срезы A/B — чистая
конфигурация, без правки движка; срезы C/D — платформенные доработки).

## Контекст

Методика проектирования прикладных решений (СППР) описывает проектирование как
**управляемый цикл вокруг базы проектирования**: функциональная модель (дерево
функций со связями ICOM), объекты метаданных, задачи/ошибки с правилами
переходов статусов, формальные правила аудита, тестовые сценарии (Gherkin),
планирование занятости, контроль состояния объектов. Агенты (LLM) не могут эту
методику «помнить» — им нужен **структурированный источник состояния**: где
функция, кто её реализует, чем подтверждено, что просрочено, какое правило
нарушено.

OneBase уже даёт почти всё, что нужно для такой базы, на уровне конфигурации:

| Механик СППР | Примитив OneBase |
|---|---|
| Дерево функций | иерархический справочник (`hierarchical: true`) |
| Связи функций (ICOM: вход/выход/управление/ресурс) | регистр сведений с двумя ссылочными измерениями + перечисление вида связи |
| «Функция зафиксирована на дату» | периодический регистр + срез последних (`СрезПоследних`) |
| Объекты метаданных и их реквизиты | справочник + табличная часть |
| Задачи, ошибки, потоки статусов | документы + блок `stages` (гейт переходов в слое хранения, история переходов, «где застряло», `deadline_days`) |
| Связи задач (родитель/предшествующая/последующая) | табличная часть + справочник связей |
| Правила аудита как данные, версии правила, уровень BLOCK/WARN/INFO, дата вступления | паттерн плана 89 (реестр-справочник + периодический регистр версий + документ публикации) |
| Тестовые сценарии и их результаты | `onebase test` (`kind: test`, TAP/JUnit, моки, `Часы.Установить`) — план 108 |
| Права доступа, профили, видимость функций | роли + RLS + маскирование (планы 04/79/88) |
| Контроль состояния объекта «кем и когда» | периодический регистр + журнал регистрации |
| Дашборд, «где застряло», отчёты | виджеты/домашняя страница, `/ui/stages`, СКД-отчёты |
| Поиск по базе проектирования | полнотекстовый индекс + `ПолнотекстовыйПоиск()` + `/api/v2/search` |
| Раздача базы проектирования между узлами | планы обмена (`.obx`, hub-and-spoke, `ONEBASE_EXCHANGE_TOKEN`) |
| Планирование занятости и затрат | периодический регистр планов + документ учёта времени |
| Автоматизация ритуалов | регламентные задания (cron) + ИИ-функции (`ЗапросИИ`, `ЗапросИИДжейсон`) |

Пробелы, которые OneBase **не** закрывает (ими заняты срезы C/D): отрисовка
ICOM-диаграмм, «ключевые операции» как штатный объект UI, экспорт HELP/RTFS из
базы проектирования, интеграция метаданных целевого проекта (файлов конфигурации)
в базу проектирования, запись данных через MCP.

Задача плана — собрать **прикладную конфигурацию «проектная база СППР»**, в которой
агент через `onebase` CLI / REST / MCP читает состояние проектирования и пишет
результаты своей работы, а платформа гарантирует правила переходов и правила
аудита. Конфигурация — не «ещё один ERP», а инструмент проектирования.

## Правила, из которых собираем (свои, не перенос текста методики)

Тексты СППР — собственническая документация и в репозиторий не попадают. Данные
модели выводятся из открытых стандартов и публично известных формулировок:

- IDEF0: роль стрелок **вход / управление / ресурс / выход**, нумерация
  поддекомпозиции `[1.2.3]`, правило «механизм не входит в дерево функций»,
  «вход одной функции является выход другой», «стрелка не идёт из пустого
  элемента», «у декомпозиции — ровно один родительский контекст»,
  «декомпозиция не ниже 4 уровня».
- Формальные правила аудита (из открытых формулировок): отсутствие у объекта
  ссылки на функцию; функция без подтверждённого тестового сценария; функция без
  исполнителя; сценарий без функции; документ без утверждённой функции;
  ссылка на неутверждённую функцию; нарушение связности ICOM; объект, снятый с
  контроля и изменённый после этого; просроченный этап.
- Статусы: функции `Черновик → НаСогласовании → Утверждена → Отменена`;
  задачи `Новая → Принята → ВРаботе → НаПроверке → Выполнена → Отменена`;
  ошибки `Зарегистрирована → НаРассмотрении → ВРаботе → Исправлена → Проверена →
  Возвращена → Отменена`; контроль объекта `Добавлено / Проверено / НеПроверено /
  СнятоСКонтроля`.
- Тестовые сценарии — Gherkin (OTF/Gherkin), компилируются в test-обработки.

## Модель (срезы A и B)

Справочники:

- `Проект` (иерархический) — цель, сроки, руководитель.
- `Функция` (иерархический) — код, наименование, тип (`Функция`/`МеханизмВстроенный`/
  `Отчёт`), результат, отображается в интерфейсе, наименование интерфейса,
  ответственный, трудозатраты; статус по маршруту `stages` (`strict`).
- `ОбъектМетаданных` — имя, тип (`Справочник`/`Документ`/`Регистр…`/`Отчёт`/
  `Обработка`/`Роль`/`Подсистема`/…), путь файла, функция, статус, контроль,
  ответственный; ТЧ `Реквизиты` (имя, тип, обязательность).
- `Подсистема` (иерархический) + ТЧ `Объекты`.
- `Роль` (соответствует `roles/*.yaml` целевого проекта) + ТЧ `Функции`.
- `ПрофильПользователя` (иерархический) — роль, ТЧ `Пользователи`, ТЧ `Функции`.
- `Сценарий` — функция, вид (`Сценарий`/`Процесс`), текст Gherkin, ТЧ `Шаги`.
- `ПравилоПроверки` — код, объект проверки, важность, текст запроса, владелец,
  предопределённость, активность.
- `Механизм`, `ВидДеятельности`, `Исполнитель`, `Очередь`.

Документы: `Задача` (тип, функция, срок, приоритет, оценка, ТЧ `Связи` +
`stages strict`), `Ошибка` (функция, объект, решение + `stages`),
`УчётВремени` (движение в регистр затрат), `Комментарий` (протокол по задаче),
`ПубликацияПравила` (движение в регистр действующих правил).

Регистры сведений: `СвязиФункций` (ICOM), `Трассировка` (функция ↔ файл ↔
коммит ↔ задача), `РезультатыПроверки`, `ДействующиеПравила` (periodic),
`КонтрольОбъектов` (periodic), `ВерсииОбъектов` (periodic),
`ИсторияСтатусовЗадач` (пишется проведением задачи: автор, старый и новый
статус; ключ записи — задача + номер перехода, потому что строки одного
провода пишутся в одну секунду и период их не разделяет; платформенная
история этапов доступна карточке, регистр доступен агенту запросом), `ЗатратыВремени` (пишется проведением учёта времени),
`ПланыЗанятости` (periodic), `ОчередьЗадач`.

Отчёты: дерево функций, покрытие функций объектами, трассировка функции,
результаты аудита, просроченные задачи, задачи по исполнителям. Регламентное
задание «Аудит правил» (cron `0 8 * * *`) применяет действующие версии правил и
пишет результаты.

## Этапы

**Срез A (прикладной, MVP)** — каркас `examples/sppr` (в репозитории, проверен):
справочники, документы, регистры, роли, подсистемы, отчёты, виджеты и домашняя
страница, регламентный аудит, демо-инициализация, экспорт связей в mermaid,
пользовательское руководство `docs/help/`, `AGENTS.md` с порядком работы агента.
Проверено на бинаре из репозитория (`dev-78a096c`):

```bash
onebase check  --project examples/sppr                       # ошибок нет
onebase test   --project examples/sppr --sqlite :memory:      # 9 проверок: гейт этапов, права ролей, трассировка, аудит
onebase migrate --sqlite /tmp/sppr.db --project examples/sppr
onebase procrun --sqlite /tmp/sppr.db --project examples/sppr --proc ЗаполнитьДемоданные
onebase procrun --sqlite /tmp/sppr.db --project examples/sppr --proc АудитПравил   # нарушений 1 (функция 1 без сценария)
```

Срез A **не** включает отрисовку графа: экспорт связей отдаёт текст mermaid
обработкой `ЭкспортIDEF0`, отрисовка — срез D.

Правила каркаса, которые показывает проверенный каркас (стоят как раздел
`AGENTS.md`):

* модуль проведения называется по имени документа без разделителей и строчными
  буквами: `публикацияправила.posting.os`, `задача.posting.os`;
* имена параметров обработок и имена переменных не должны совпадать с
  ключевыми словами языка (`Функция`, `И`), компилятор запроса превращает их в
  `AND`;
* строгий гейт этапов действует и при создании объекта: создать объект сразу
  «Утверждена» нельзя, первый статус — `order[0]`;
* текст запроса правила аудита самодостаточен: параметров нет, условие
  записано литералом, иначе регламентное задание не может его выполнить;
* поле иерархии (`hierarchical: true`) в запросе не читается — порядок дерева
  задаётся кодом функции (`1`, `1.1`), родственный контекст читается карточкой;
* виджеты бывают `kpi | list | chart | actions | recent`, параметры виджета
  записываются отображением `params: {Имя: значение}`;
* перегрузка обработки без аргументов не вызывает перегрузку с аргументами
  (одна цепочка вызовов даёт рекурсию) — общий код выносится в отдельную
  процедуру.

**Срез B (мост метаданных)** — сделан как прикладная обработка, без правок
движка: `onebase describe --project <целевой> > desc.json`, затем обработка
`ИмпортОписания` (файловый параметр) вызывает модуль `Импорт`, который пишет
`ОбъектМетаданных`, табличную часть `Реквизиты` и `Трассировка`. Переносятся
справочники, документы, оба регистра, перечисления, константы, отчёты,
обработки, подсистемы, виджеты, роли, регламентные задания, журналы и модули;
состав полей и имена процедур модуля с подписью параметров идут в табличную
часть, тип виджета — в описание. Импорт идемпотентен (проверено на собственном
описании `examples/sppr`: 76 объектов, повторный прогон — 0 новых), функцию
-владельца не назначает и уже записанный объект не перетирает. Разделы
`builtins`/`language` — контракт языка, не импортируются. То, чего `describe`
не видит (`Plans/*.md`, пакеты Go, CLI-команды, документация), заводится руками
из значений перечисления `ТипОбъектаМетаданных`.
Следующий шаг после импорта — расстановка функций: обработка
`РасставитьФункции` закрепляет импортированные объекты за узлами декомпозиции
списком пар «имя:тип» (регламентное задание и обработка с одним именем —
разные объекты, модуль проведения документа носит имя документа), помечает их
контролем «Проверено» и пишет трассировку. Отчёт «Покрытие функций» считает
объекты, сценарии и задачи различными ссылками: соединение функции с тремя
источниками одним запросом даёт произведение строк.

Проверено полным прогоном на живом стенде (`ЗаполнитьДемоданные` →
`Саморазвитие` → `ИмпортОписания` → `РасставитьФункции` →
`РасставитьФункцииДемо` → `АудитПравил`): мост принёс 81 объект, расстановка
закрепила 12 узлов (151 строка трассировки), аудит дал два нарушения — пакеты
`internal/exchange` и `internal/aiassist`, закрепление которых сознательно
оставлено, чтобы правило «объект без функции» оставалось видимым. Дерево
развития платформы (узлы 2.x, 3.x) заводит обработка самого проекта; её
демо-наполнение не входит в каркас.
Правила аудита над целевым проектом (7 глав методики): «объект без функции»
и «функция без сценария» опубликованы и работают; «роль без функции»,
«подсистема без объекта», «файл без записи трассировки» — следующие.

**Срез C (прикладной + минимальный движок)** — Gherkin → test-обработки: движок
`internal/gherkin` (разбор `.feature`, реестр шагов, компиляция) и CLI-команда
`onebase gherkin compile` сделаны; они дают тест-обработки каркаса. Разбор
читает русские и английские ключевые слова, теги, Предысторию, Сценарии,
Структуры сценария с Примерами, таблицы и docstring-шага. Реестр
(`features/шаги.yaml`) связывает текст шага с DSL: `тип: действие` выполняет
код, `тип: проверка` вычисляет значение и даёт `Утверждать.Равно`, `.Истина`,
другие; параметры шага пишутся `<Имя>`, значение подставляется с учётом места —
внутри строкового литерала DSL (текст запроса) значение идёт SQL-литералом в
одинарных кавычках, вне литерала — строкой DSL. Компиляция отказывается, если
шаг не сопоставлён с реестром или сценарий без шагов-проверок, и отказ отменяет
запись всего прогона: половина теста записанного компилятора нет. Строка
Примеров даёт свою обработку с суффиксом значений строки; имена тестов режутся
по рунам; шаг-таблица печатается в модуле комментарием. Каркас даёт три
скомпилированные обработки (`ТестРасстановкаФункций_Объект` и две строки
Примеров), прогон `onebase test` — 4 теста, 31 проверка, провалов нет; JUnit
пишет `onebase test --format junit`. Страницы со списком тестов в UI нет
(`onebase test` и карточка обработки), галочка «результат теста подтверждает
функцию» — следующая.

**Срез D (движок)** — отрисовка IDEF0: тип диаграммы «граф» (узлы+рёбра из
регистра), экспорт mermaid/graphviz через `ВыполнитьКоманду` (флаг админа,
по умолчанию выключен); ключевые операции (точки расширения UI:
`ПередНачатомДействия`/`ПослеВыполненияДействия`) и журнал ключевых операций;
экспорт помощи (`docs/help/*.md`) в HELP/RTFS целевого проекта; MCP-инструмент
записи **данных** проектной базы (сейчас флаги записи MCP касаются конфигурации,
данные через MCP не пишутся).

## Оценки

| Срез | Оценка |
|---|---|
| A (каркас `examples/sppr`) | 2–3 дня, чистая конфигурация |
| B (мост метаданных + правила аудита) | сделано: мост как обработка, 2 правила опубликованы; правила над целевым проектом — дальше |
| C (Gherkin-конвейер) | 1–2 недели, движок (парсер `.feature` → DSL) |
| D (графы, ключевые операции, HELP, MCP-запись данных) | по плану-вне-срока, каждая возможность отдельно |

## Риски

- **Не переносить тексты методики.** Данные модели — своя реализация открытых
  стандартов; ссылки на главы СППР в документации репозитория не допускаются.
- **Слизать с TCM/Reqify.** Ценность не в «ещё одном трекере», а в связке
  *функция ↔ объект ↔ трассировка ↔ тест ↔ результат аудита* с гейтом статусов.
  Ключевые операции и HELP — следующие, самые дорогие и наиболее «книжные»
  срезы; начинать с них нельзя.
- **`stages` со `strict` отвергает legacy-состояния.** Для новой базы `strict`
  безопасно; для наполненной из импорта — начинать с `warn` и разбирать строку
  «Вне маршрута» в `/ui/stages` (написано в документации блока).
- **Регистры не заменяют граф.** Связи ICOM хранятся регистром; отрисовка —
  отдельная, самая дорогая часть (срез D), и каркас не должен выглядеть как
  «методика готова».
- **Запись в проектную базу из агента.** MCP по умолчанию read-only; запись
  данных требует флагов (`--allow-write`, `--allow-procrun`) и явного решения
  (срез D). Без этого агенты читают, а writes идут через CLI/REST.
- **ИИ-функции в аудите** (классификация формулировок функции) дают галлюцинации:
  решения аудита пишутся детерминированным запросом, ИИ — только подсказка.
- Не смешивать базу проектирования с поставкой: `.obz`-бэкап, роли и права —
  отдельное решение; обмен базами — планами обмена (hub-and-spoke).
