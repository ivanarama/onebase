# План 222: инструкция агента — синхронизация разработки compsem с базой СППР

Цель: агент, который разрабатывает конфигурацию `examples/compsem`, обязан
держать проектную базу `examples/sppr` в актуальном состоянии по каждому этапу
разработки и одновременно контролировать саму базу: она тоже в разработке, её
документация (`sppr2doc/*`, `examples/sppr/docs/help/*`,
`examples/sppr/AGENTS.md`) опережает реализацию. Где база не соответствует
документации, агент правит базу в той же задаче.

## 1. Контур: этап разработки → данные базы

| Этап (ТЗ `examples/compsem/tz.md`) | Что обязано лежать в базе | Как заводится | Чем проверять |
|---|---|---|---|
| §1 Процессы (3 процесса) | справочник `Процесс` — **в базе его нет** (заполняется после доработки каркаса) | карточки функций + задачи с триггером процесса | аудит «процесс без функций» (появится после доработки) |
| §2.1 Дерево (40 узлов: `0`, `1`–`6`, 33 конечных) | справочник `Функция`: `Код` = код ТЗ, `Родитель`, `Тип`, `Результат`, `Ответственный`, `Статус`, `Трудозатраты` | REST v2 под ролью Проектировщик | отчёты `ДеревоФункций`, `ПокрытиеФункций`; аудит декомпозиции (2–6 дочерних) |
| §2.2 Карточки (Вход, Управление, Выход, потребители) | регистр `СвязиФункций`: вид `Источник` = Вход, `Управление` = Управление, `Выход` = результат и потребители | запись строки умеет только обработка базы (headless `procrun`): каркас обязан принять список связей параметром; REST v2 регистров не пишет | аудит «связь без функции-источника», `ЭкспортIDEF0`, `GET /api/v2/inforeg/СвязиФункций` |
| §4 Архитектура (20 справочников, 14 регистров, документы, отчёты, обработки, роли, регламентные задания) | справочник `ОбъектМетаданных` (импорт из `onebase describe`) + ТЧ `Реквизиты` + регистры `Трассировка`, `ВерсииОбъектов`, `КонтрольОбъектов` | `onebase describe` → `ИмпортОписания` → пары «имя:тип» в `РасставитьФункции` | аудит «объект без функции», «функция без объекта», «объект без файла»; отчёт `ТрассировкаФункции` |
| §5 Интерфейс (формы, FastActions, поле профиля) | `Функция.ОтображаетсяИнтерфейсе`, `НаименованиеИнтерфейса`; сами формы — **в базе не видны** (`describe` не выдаёт форм) | правка функции; формы — после доработки моста | аудит «функция без интерфейса» (Информация) |
| §6 Права (роли, профили) | справочник `Роль` (импорт), `Исполнитель`, `ПрофильПользователя`, ТЧ `Функции` роли | импорт + закрепление функций за ролью | аудит «роль без функции» (Информация), проверка матрицы прав тестом каркаса |
| §8 Тесты (10 сценариев) | справочник `Сценарий` (реквизит `Функция`, ТЧ `Шаги`, `Актуален`); feature-файлы живут в `examples/compsem/features/` | `onebase gherkin compile --project examples/compsem` + запись сценария под ролью Тестировщик | аудит «функция без сценария» (Обязательное), `onebase test --project examples/compsem` |
| §10 Аудит (73 правила) | справочник `ПравилоПроверки` (код, объект, важность, текст запроса, источник) + документ `ПубликацияПравила` → регистр `ДействующиеПравила` | правила над данными базы: запрос в `ТекстЗапроса`; правила над конфигурацией compsem: проверка на стороне compsem, результат пишется в базу обработкой procrun (REST v2 регистров не пишет) | регламентное задание `АудитПравил`, отчёт `РезультатыАудита` |
| §7 Управление (план, исполнители, агент `pi`) | документ `Задача` (+ `Функция`, `Исполнитель`, `Тип`, `Статус`, `Срок`, `Оценка`), регистры `ОчередьЗадач`, `ИсторияСтатусовЗадач`, `ЗатратыВремени`, `ПланыЗанятости` | REST v2 под ролью Разработчик: `POST /api/v2/document/Задача` + `POST …/post`; проведение пишет `ИсторияСтатусовЗадач`; позиции очереди и планы занятости задаёт планировщик | отчёты `ПросроченныеЗадачи`, `ЗадачиПоИсполнителям` |
| §9 Справка | трассировка документов `docs/help/*` — в описании `describe` разделов документации нет | после доработки моста | трассировка документации |

## 2. Цикл синхронизации (обязателен после каждого изменения compsem)

```bash
onebase check  --project examples/compsem                       # конфигурация валидна
onebase describe --project examples/compsem > /tmp/compsem-desc.json
onebase procrun --project examples/sppr --sqlite examples/sppr/sppr.db \
    --proc ИмпортОписания --file Файл=/tmp/compsem-desc.json --set Проект=<id>
onebase procrun --project examples/sppr --sqlite examples/sppr/sppr.db --proc РасставитьФункции
onebase procrun --project examples/sppr --sqlite examples/sppr/sppr.db --proc АудитПравил
onebase test   --project examples/sppr --sqlite :memory:        # каркас зелёный
```

Порядок наполнения базы (по `examples/sppr/docs/help/assign.md`):
`ЗаполнитьДемоданные` → `ИмпортОписания` → `РасставитьФункции` → `АудитПравил`.

Правила записи: роль-scoped записи идут через REST v2 под токеном роли
(`Проектировщик`, `Разработчик`, `Тестировщик`, `Руководитель`); headless
`procrun` разрешён только обработкам каркаса. Функцию утверждает Руководитель,
правило аудита публикует Руководитель, очередь задач и статусы агент не
перекрашивает.

### 2.1 Интерфейсы, которыми агент работает с базой

| Данные базы | Интерфейс | Проверено |
|---|---|---|
| справочники (`Функция`, `ОбъектМетаданных`, `Сценарий`, `Роль`, `Проект`, `Исполнитель`, `ПравилоПроверки`, `Очередь`) | REST v2 `POST/PUT/DELETE /api/v2/catalog/{Имя}[/{id}]` под Bearer-токеном роли | маршруты `crud("catalog")` и `item("catalog")` в `internal/api/v2.go` |
| документы (`Задача`, `Ошибка`, `ПубликацияПравила`, `УчётВремени`, `Комментарий`) и проведение | REST v2 `POST/PUT/DELETE /api/v2/document/{Имя}`, `POST /api/v2/document/{Имя}/{id}/post`, `…/unpost` | маршрут `actionPath("postDocument")` в `internal/api/v2.go` |
| регистры, которые пишет проведение (`ИсторияСтатусовЗадач`, `ДействующиеПравила`, `ЗатратыВремени`) | REST v2: создание документа + проведение; движение пишет `src/<документ>.posting.os` | posting-модули базы: `задача.posting.os`, `публикацияправила.posting.os`, `учётвремени.posting.os` |
| регистры без регистратора (`Трассировка`, `СвязиФункций`, `ОчередьЗадач`, `КонтрольОбъектов`, `РезультатыПроверки`, `ВерсииОбъектов`, `ПланыЗанятости`) | только обработки базы: headless `onebase procrun --proc ИмпортОписания / РасставитьФункции / АудитПравил` (DSL `СоздатьМенеджерЗаписи`) | ни один `inforegs/*.yaml` базы не имеет `recorder: true`; писатели — `src/импорт.module.os`, `src/расставитьфункции.proc.os`, `src/аудит.module.os`, `src/саморазвитие.proc.os` |
| чтение регистров и отчётов | headless `onebase query "<ВЫБРАТЬ…>" --project examples/sppr --sqlite …`; HTTP `GET /api/v2/inforeg/{Имя}`, `GET /api/v2/report/{Имя}` | у `/api/v2/inforeg/{name}` в OpenAPI-реестре единственный метод `get` (write-маршрута регистра нет) |
| структура конфигурации целевого проекта | headless `onebase describe --project examples/compsem` | CLI-команда |
| проверка конфигурации, тестов, компиляция Gherkin | headless `onebase check`, `onebase test`, `onebase gherkin compile` | CLI-команды |
| GUI управляемых форм (`onebase run --port 8080`) | интерфейс человека; агент им не работает | `docs/rest-api-v2.md`: права роли и RLS действуют на маршрутах v2 |
| MCP-сервер `onebase mcp --project … --sqlite …` | read-only по умолчанию, запись открывается точечно (`--allow-procrun`, `--allow-write`) | `docs/mcp.md`, `onebase mcp --help` |

Прямых SQL-правок файла базы (`examples/sppr/sppr.db`) агент не делает: они
обходят проверки проведения, RLS и аудит. Headless-прогон обработок матрицу прав
роли не применяет — роль-scoped запись возможна только через REST v2.

### 2.2 Интерфейс проверенного результата: логика → итог или отказ

Агенту нужен интерфейс, который прогоняет внутреннюю логику конфигурации и
возвращает проверенный результат либо отказ при нарушении логики разработки
(гейт этапов, права роли, целостность записи). Он собирается из четырёх
проверенных каналов; каждый даёт отказ своим сигналом.

| Канал | Что прогоняет | Проверенный результат | Отказ |
|---|---|---|---|
| `onebase test --project X --sqlite f` | обработку `Выполнить()` каждой `kind: test` обработки: запись справочников/документов, проведение, обращение к регистрам, `Утверждать.*` | по строке на каждую проверку (`ok — <описание>`), итог «Тестов: N, успешно: N, провалено: 0», код 0 | код 1; провал проверки печатается как `ОШИБКА — <модуль>:<строка>: <сообщение>`; запрет перехода этапа печатается словами гейта |
| `onebase procrun --project X --sqlite f --proc <Имя> --file/--set` | логику обработки над реальной базой (импорт, закрепление, аудит) | вывод `Сообщить()`, код 0 | код 1, сообщение `ошибка выполнения: <модуль>:<строка>: <текст>` из `ВызватьИсключение` |
| `onebase check --project X`, `onebase gherkin compile --project X` | статику конфигурации (YAML-схема, `.os`, запросы) и соответствие шагов Gherkin реестру | `OK: ошибок не найдено`, код 0 | код 1 со списком ошибок; компиляция Gherkin отказывает, если шаг не сопоставлен с реестром или в сценарии нет проверок |
| REST v2 под токеном роли (`POST/PUT /api/v2/catalog/{Имя}`, `POST /api/v2/document/{Имя}`, `POST …/post`) | запись и проведение под правами роли и RLS | JSON `{data, meta}`, код 200 | `403 {"error":"forbidden"}` (в т.ч. `forbidden source: <источник>`), `400` на неизвестное имя измерения, `404`; проведение под гейтом отказами отвечает по коду |
| `onebase query "ВЫБРАТЬ …" --project X --sqlite f` | срез данных: справочники, документы, регистры | строки результата (JSON), код 0 | код 1: справочник/документ пишутся именем или `Справочник.Имя`/`Документ.Имя`, регистр — только `РегистрСведений.Имя` (иначе `no such table`); разрешены только SELECT |

Запрет перехода этапа (план 121) стоит в слое хранения (`internal/storage/stage.go`,
`Stages.Strict()`), поэтому он действует на всех путях записи — форма, DSL,
headless-прогон, REST, обмен. Проба 2026-11-10 (`/tmp/probe2`, strict-гейт
`Новая → Принята → НаПроверке`): легальный переход дал `ok`, перескок
`Новая → НаПроверке` дал `ОШИБКА — src/провал.proc.os:8: Записать(Заявка):
переход «Новая» → «НаПроверке» у объекта Заявка не разрешён`, итог
«провалено: 1», код 1.

Права роли headless-прогон не применяет: у `procrun` нет параметров
`--user`/`--role` (`internal/cli/procrun.go`), в слое DSL проверок ролей нет
(`grep` по `internal/dsl` пустой). Проба: роль `Читатель` с правом
`Проект: [read]`, обработка headless записала справочник — успех. Значит
роль-scoped запись идёт только через REST v2; пользователи и роли заводятся
офлайном (`onebase user add`, `onebase user role assign`), токен выдаёт
владелец в UI `Система → API-токены`.

Требование к каркасу: результат каждого прогона, которым агент закрывает срез
(импорт, закрепление, аудит, проверка целевой конфигурации), обязан быть
записан в `РезультатыПроверки` строкой «функция — правило — объект —
результат», а отказ обязан порождать документ `Ошибка`. Записи, подтверждённой
только намерением, в контуре нет.

### 2.3 Профили агентов, подключаемых к программе

Матрица профилей, ролей, интерфейсов, операций и ожидаемых отказов —
[`docs/agent-roles.md`](../docs/agent-roles.md). Процедуры — канонические скилы
(`.claude/skills/<этап>/SKILL.md`) и тонкие адаптеры Codex
(`.agents/skills/<этап>/SKILL.md`):

| Этап | Роль агента | Операции |
|---|---|---|
| `$design-base-sync` | Проектировщик | функции, ICOM, объекты метаданных, трассировка, задача «Базовая синхронизация» |
| `$acceptance-run` | Тестировщик | Gherkin, тесты, аудит правил, результаты проверок, документ `Ошибка` |
| `$lead-desk` | подготовка под ролью руководителя-человека | проекты публикаций правил, планы занятости, очередь; утверждение и публикация — человек |
| `$knowledge-intake` | Владелец знания compsem | приём дельты по манифесту, проверка форматов, загрузка, статус приёмки, золотые кейсы |
| `$night-ops` | Оператор compsem | ночной прогон книги и экзамена, отчёт объёмов/скорости, регистрация отказов |
| `$base-observer` | Наблюдатель | read-аудит среза, функций, результатов, соответствия каркасной документации |
| `$framework-fix` | каркас | закрытие дыр §5: регистровая запись под ролью, обработка результатов целевого среза, канал форм и плана обмена, роль-scoped headless |

Исполнители продукта (`Ядро`, 2.x–5.x) — не агент-профиль: их исполняет
конфигурация (регламентные задания и обработка разбора); агент результат Ядра
своей ролью не подписывает.

## 3. Контроль самой базы (база в разработке)

Агент обязан проверить утверждения документации на каждом цикле:

1. `onebase check --project examples/sppr` — без ошибок.
2. `onebase test --project examples/sppr --sqlite :memory:` — все проверки зелёные.
3. Каждое утверждение `examples/sppr/docs/help/*.md` сверяется с кодом
   (`processors/`, `src/`, `catalogs/`, `reports/`) и с фактом прогона.
4. Методологические правила (`sppr2doc/`) проверяются аудитом базы: декомпозиция
   2–6 дочерних, связь выходит ровно из одной функции, у функции есть выход и
   управление, роль закреплена за функцией, сценарий у утверждённой функции.
5. Расхождение «документ ≠ реализация» правится в той же задаче: минимальная
   правка конфигурации базы, тест в `features/` + `features/шаги.yaml`,
   обновление `docs/help/*`, `onebase check` + `onebase test`, один коммит по
   задаче с трейлером `Generated-with: Codex`.
6. Ограничение движка (не конфигурации) — заявка в конвейер (`TRIAGE`), обходы
   в базе запрещены.

## 4. Проверенные факты платформы (пробы, 2026-11-10)

Проба: `check` + `migrate` + `procrun` + `query` на минимальном проекте
(`registers/`, `inforegs/`, `documents/`, `src/<документ>.posting.os`).

| Факт | Доказательство | Последствие для ТЗ и базы |
|---|---|---|
| Строковые ресурсы в регистре накопления работают (запись и чтение) | движение записано проведением документа, `ВЫБРАТЬ Р.Объект, Р.Текст ИЗ РегистрНакопления.Пробы` вернул строку | сомнение из ревью снято: строковый ресурс допустим; `Лента_событий` ведётся регистром сведений ради среза последних, а не из-за типа ресурса |
| `recorder: true` в регистре накопления принимается, движение пишет документ-регистратор | прогон провёл документ, строка появилась | запись движений через регистратора — соглашение проекта, платформа не запрещает движение от непрофильного документа |
| Регистр накопления без регистратора принимает движения чужого документа | движение записано документом, не указанным как регистратор | правило «движение регистратора без записи подчинённого регистра» — аудит базы, платформа его не проверяет |
| `СрезПоследних` для регистра накопления не компилируется | `run query: SQL logic error: near "(": syntax error` | срез последних — только регистр сведений; ТЗ §4 уже использует `recorder: true` + срез по `Момент` |
| `onebase describe` не выдаёт разделы форм и плана обмена | `describeOutput` (`internal/cli/describe.go`) перечисляет справочники, документы, регистры, перечисления, константы, отчёты, обработки, подсистемы, журналы, виджеты, страницы, HTTP-сервисы, роли, регламентные задания, модули; `forms` встречаются только вложенно в обработках и документах | формы и план обмена compsem не попадают в базу; мост обязан дорасти |
| Гейт этапов действует на headless-записи DSL | проба `/tmp/probe2` (strict-гейт `Новая → Принята → НаПроверке`): перескок отвергнут `ОШИБКА — src/провал.proc.os:8: Записать(Заявка): переход «Новая» → «НаПроверке» у объекта Заявка не разрешён`, код 1; легальный переход — `ok`, код 0; `internal/storage/stage.go` (`Stages.Strict()`, цикл «прочитать → проверить → записать → история») | статусы функций/задач/ошибок нельзя «перекрасить» обработкой: отказ даёт слой хранения, агент обязан идти маршрутом |
| Headless-прогон прав роли не применяет | проба `/tmp/probe2`: роль `Читатель` с `Проект: [read]`, обработка headless записала справочник (`ok`); у `procrun` нет `--user`/`--role`; `grep` по `internal/dsl` ролевых проверок не нашёл | роль-scoped запись — только REST v2; headless годен для каркасных обработок, где роль не нужна (импорт, расстановка, аудит) |
| `onebase test` даёт проверенный результат и отказ кодом | проба `/tmp/probe2`: 3 обработки `kind: test`, итог «Тестов: 3, успешно: 2, провалено: 1», «Проверок: 2, провалено: 0», код 1; провал печатается сообщением гейта с модулем и строкой | тест — канал приёмки: отказ фиксируется кодом возврата и строкой проверки; в базе compsem тесты обязаны ловить отказ формата поставки |

### 6.1 Скелет compsem (путь A, 2026-11-11)

Создан скелет `examples/compsem`: 11 перечислений, 10 справочников (правила с
табличными частями «Позиции» и «Действия», рецепты с элементами), 6 регистров
сведений, 2 документа, 5 ролей, отчёт «Словарь форм», модуль знания,
модуль проведения текста, обработки загрузки знания и 5 Gherkin-тестов
(14 проверок, провалено 0). `onebase check --project examples/compsem` —
`OK: ошибок не найдено`; база каркаса зелёная (тестов 4, проверок 31).

Замер по фактической поставке (`procrun` на `/tmp/compsem.db`):

| Метрика | Значение | Комментарий |
|---|---|---|
| строк `rules.txt` | 615 | все прочитаны, 9 колонок обязательны |
| кодов правил | 46 | код = `ключ-часть речи`, повторные строки обновляют одну карточку |
| строк `Позиции_правил` | 3 719 | свёртка col5 (требования) и col7 (порядок печати) |
| форм записано | 7 948 | словарь точных форм (`Формы_лексикона`) |
| форм в поставке | 9 630 | токенов парадигм |
| форм без леммы | 1 679 | 132 леммы парадигм отсутствуют в `words.txt`: словарь покрывает 82,5 %, горячий путь обязан это мерить |

Правило: загрузка знаниевого файла даёт измеримый итог (правила, позиции, формы
и покрытие), отказ на неполной строке — код 1. Покрытие форм без леммы —
открытая позиция поставщика (приложение §6): поставка обязана передавать
леммы всех форм, импорт их не выдумывает.
