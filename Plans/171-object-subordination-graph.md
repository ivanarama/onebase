# Этап 171 — Структура подчинённости объектов

## Контекст

План связан с issue #1411 и фиксирует выбранный владельцем вариант 1:
сначала отдельный технический план, затем платформенный MVP с ленивым графом
ссылок из шапок, табличных частей и регистров, fail-closed доступом и переходами
в стандартные формы. Ограниченный вариант только для шапок и прикладной
DSL-прототип не принимаются.

Сейчас платформа хранит две разные части задачи, но не соединяет их:

- `metadata.Entity.BasedOn` и `runtime.Registry.ReceiversOf` описывают только
  разрешённые пары **типов** для команды «Ввести на основании»;
- `storage.DB.CheckRefs` обходит ссылочные поля сущностей, табличных частей,
  регистров накопления, регистров сведений и бухгалтерских регистров, но
  возвращает только счётчики для запрета удаления;
- `entityservice.Service.Fill` загружает источник и запускает
  `ОбработкаЗаполнения`, однако сам по себе не сохраняет идентификатор основания;
- автоформа и managed-форма получают `Receivers` в
  `internal/ui/handlers_entity.go` и показывают только создание нового объекта в
  `internal/ui/templates.go` и `internal/ui/templates_managed.go`;
- стандартная карточка уже адресуется как `/ui/{kind}/{entity}/{id}`, а
  `rowDecision`, `readableFieldsByIDs` и `maskedRecordLabel` дают готовые
  fail-closed примитивы доступа и безопасного представления.

Следствие: `based_on` не является ребром между экземплярами. Структура показывает
только реальные сохранённые ссылки. Совпадение типов в `based_on` классифицирует
реальное ребро как «основание / введён на основании», но не создаёт фантомную
связь. Если конфигурации нужна цепочка экземпляров, она сохраняет ссылку на
основание в реквизите; новый такой реквизит начинает участвовать без правки
платформы.

## Выбранная семантика

### Узел и его идентичность

Узел графа имеет ключ `(kind, entity, id)`, где `kind` — `catalog` или
`document`, `entity` — каноническое имя метаданных, `id` — UUID записи. В ответе
UI присутствуют только:

- локализованное имя типа и безопасное представление записи;
- стандартный URL карточки;
- системные признаки `deletion_mark` и, для документа, `posted`;
- вид связи: `based_on`, `reference` или `register`;
- `has_children`/`truncated`, необходимые ленивому дереву.

Имена ссылочных полей и их значения наружу не отдаются: для навигации они не
нужны и могут раскрыть скрытую структуру роли. Несколько попаданий в один ключ
объединяются; виды связей агрегируются в стабильном порядке, а узел не
дублируется из-за нескольких строк ТЧ или движений.

Точное совпадение ссылки само является раскрытием значения. Поэтому ребро из
поля с эффективным решением `mask_*` или `hide` не строится вовсе: недостаточно
не показать имя поля, иначе структура превратится в oracle «ссылается ли скрытый
реквизит на этот UUID». Это правило действует и на входящие ссылки, и на поиск
основания вверх.

### Направления рёбер

Для каждого раскрытого узла сервер строит только один уровень, без рекурсивного
SQL:

1. **Вниз — входящие ссылки.** Если запись сущности ссылается на текущий объект
   из реквизита шапки, узлом становится эта запись. Для ссылки из ТЧ узлом
   становится владелец строки по `parent_id`. Если тип найденного документа
   содержит текущий тип в `BasedOn`, ребро помечается `based_on`, иначе
   `reference`.
2. **Вниз через регистры.** Для совпавшей ссылки в регистре накопления,
   подчинённом регистратору регистре сведений или бухгалтерском регистре узлом
   становится валидный документ-регистратор (`recorder`/`recorder_type` либо
   `регистратор`/`регистратор_тип`). Вид ребра — `register`. Независимая строка
   регистра сведений с `NULL`-регистратором, свёрточный синтетический
   регистратор, неизвестный тип и сирота не являются объектами с карточкой и
   потому не создают узел.
3. **Вверх — основание.** У документа просматриваются его реальные ссылочные
   реквизиты шапки и ТЧ. Цель становится родительским узлом только тогда, когда
   её тип перечислен в `document.BasedOn`. Обычные ссылки документа на склад,
   организацию и контрагента вверх не разворачиваются: иначе любой документ
   связывался бы через общий справочник почти со всей базой. Для корневого
   справочника входящие ссылки по пункту 1 остаются доступны.

Таким образом, открытие любого документа показывает и фактические основания, и
его потомков; открытие элемента справочника показывает непосредственно
ссылающиеся на него объекты. Рёбра симметрично дедуплицируются в рамках
отрисованного дерева, но их деловой смысл остаётся направленным.

### Порядок и ограничения

- Один HTTP-запрос возвращает не более 100 **доступных уникальных** соседей и
  признак `truncated`; наличие недоступных строк не влияет на этот признак.
- Каждый физический источник отдаёт страницы по keyset-cursor в порядке
  спроецированного ключа `(kind, canonical entity, id)`. Сервер делает
  детерминированное k-way merge этих потоков; номер источника и вид отношения
  служат tie-breaker только для одинакового ключа. Поэтому все попадания одного
  узла оказываются рядом и его `relations` полностью агрегируются до проверки
  лимита.
- Для каждого следующего уникального ключа UI проверяет target RBAC/RLS и
  отбрасывает недоступный узел, не расходуя лимит. Страницы источников читаются
  дальше, пока не найден 101-й доступный уникальный узел либо пока не исчерпаны
  все источники. В ответ идут первые 100; только наличие 101-го доступного узла
  выставляет `truncated=true`. Даже произвольное число скрытых target-записей в
  начале порядка не может спрятать доступные записи после них или дать ложное
  усечение.
- Клиент сортирует полученные узлы по локализованному имени типа,
  представлению и UUID. Состав усечённой сотни определяется серверным порядком,
  поэтому одинаковый снимок даёт одинаковый результат.
- UI раскрывает не более восьми уровней. На каждой ветви хранится множество
  посещённых ключей: повторный ключ показывается как «цикл» без кнопки
  раскрытия. Сервер сам не рекурсирует, поэтому поддельный клиент не может
  заставить один запрос обойти лимит глубины.
- Ошибка хотя бы одного обязательного источника, разбора политики или загрузки
  представлений завершает весь JSON-ответ ошибкой. Частичный граф с молча
  пропущенным источником запрещён.

## HTTP и пользовательский интерфейс

Добавляются две read-only точки входа:

```text
GET /ui/{kind}/{entity}/{id}/subordination
GET /ui/{kind}/{entity}/{id}/subordination/children
```

Первая отдаёт обычную HTML-страницу с корневым узлом. Вторая возвращает один
уровень JSON; параметры корня берутся только из path, пользователь не передаёт
SQL-имена или имя поля. Маршруты регистрируются рядом с карточкой в
`internal/ui/server.go`. Ответ детей имеет версионируемую внутреннюю форму:

```json
{
  "node": {"kind":"document","entity":"ЗаказПокупателя","id":"..."},
  "children": [
    {
      "kind":"document",
      "entity":"РеализацияТоваров",
      "id":"...",
      "type_label":"Реализация товаров",
      "label":"РТ-00042 от 09.09.2026",
      "url":"/ui/document/реализациятоваров/...",
      "relations":["based_on"],
      "deletion_mark":false,
      "posted":true,
      "has_children":true
    }
  ],
  "truncated": false,
  "limit": 100
}
```

`has_children` допускается вычислять ограниченным probe-запросом; он проходит те
же фильтры доступа, что и загрузка детей. Если probe заметно удваивает стоимость,
первый срез возвращает `has_children: true` для ещё не раскрытых узлов, а пустой
ответ при раскрытии превращает его в лист — это не меняет полноту и не раскрывает
скрытые связи.

На карточке существующей записи автоформы и managed-формы всегда появляется
команда «Структура подчинённости». Она ведёт на HTML-страницу; на новой,
несохранённой или popup-форме команды нет. Дерево загружается по раскрытию узла,
показывает отдельные состояния загрузки, пустого результата, усечения, цикла и
ошибки. Ссылка узла содержит `target="_blank"` и `rel="noopener"` и ведёт ровно
в стандартную форму элемента/объекта. Текст, подписи статусов и aria-label
проходят через i18n; данные вставляются через шаблонное экранирование или
`textContent`, не через `innerHTML`.

## Контракт хранения и изменения в коде

### 1. Единая инвентаризация источников ссылок

В `internal/storage` выделяется внутренний описатель источника ссылки, общий для
`CheckRefs` и нового чтения. Он хранит логическое семейство, имя метаданных,
таблицу, колонку ссылки, метаданные предиката и способ спроецировать владельца:

- `entity.id` для шапки;
- `tablepart.parent_id` с JOIN на таблицу сущности-владельца;
- `recorder + recorder_type` для накопления и регистра сведений;
- `регистратор + регистратор_тип` для бухгалтерии.

`CheckRefs` сохраняет публичную сигнатуру и fail-closed поведение. Он использует
тот же описатель для `COUNT(*)`, поэтому добавление нового семейства ссылок не
может попасть в удаление и выпасть из структуры либо наоборот.

Новый API уровня storage получает целевой `(entityName, id)`, `RefSources`,
типизированный набор предикатов чтения по каждому источнику, размер внутренней
страницы и opaque keyset-cursor этого источника. Он возвращает страницу сырых
ключей кандидатов, происхождение и следующий cursor, но не формирует
UI-подписи и не решает, сколько из них доступно как target. Размер страницы —
ограничение одного SQL-запроса, а не глобальный лимит HTTP-ответа.
`storage` не импортирует `query`: ключ фильтра объявляется рядом с API и содержит
собственные `kind/name`, иначе возникнет цикл зависимостей. Предикаты компилируются
через существующий `PredicateSQLQualified`:

- для шапки — на alias исходной сущности;
- для ТЧ — на JOIN alias владельца, а не на строку ТЧ;
- для регистра — на синтетические метаданные
  `RegisterPredicateEntity`/`InfoRegisterPredicateEntity`/
  `AccountRegisterPredicateEntity`.

Placeholder-нумерация и UUID проходят текущий `Dialect`/`idArg`; строковая
конкатенация разрешена только для имён таблиц и колонок, уже полученных из
валидированных метаданных. Каждый источник делает `SELECT DISTINCT` по
спроецированному ключу владельца и виду отношения, продолжает строго после
cursor, сортирует по тем же полям и применяет только внутренний page size,
закрывает SQL-курсор и проверяет `rows.Err()`. OFFSET запрещён: concurrent
delete не должен перескочить через ещё не прочитанный ключ. Межисточниковая
дедупликация выполняется потоковым merge после source-side RLS; HTTP-предел
применяется только после target RBAC/RLS в UI. Повторные строки регистра и
недоступные target-записи не могут вытеснить доступный уникальный узел.

Для подъёма к основанию добавляется отдельная ограниченная выборка ссылок текущей
записи и её ТЧ. Список допустимых целевых типов вычисляется из `BasedOn` до SQL;
произвольные ссылочные поля не запрашиваются.

### 2. Оркестрация и доступ в UI

В `internal/ui` появляется сервис построения одного уровня графа. До чтения он:

1. канонизирует `kind/entity`, проверяет существование метаданных и UUID;
2. требует объектное и построчное право `read` на корень;
3. получает решения чтения для каждого потенциального source family и, там где
   текущая модель адресует поля (шапки и поддерживаемые регистры), эффективное
   решение доступа к конкретному ссылочному полю; объектный запрет либо
   `mask_*`/`hide` превращает источник в гарантированно пустой, ошибка политики —
   в ошибку всего запроса;
4. для каждого регистра до вызова storage и до проекции регистратора требует
   полный доступ не только к совпавшему ссылочному полю, но и к обеим компонентам
   пары регистратора: `recorder` + `recorder_type` у регистра накопления и
   регистра сведений, `регистратор` + `регистратор_тип` у бухгалтерского
   регистра. Решения берутся из существующих `RegisterPredicateEntity`,
   `InfoRegisterPredicateEntity` и `AccountRegisterPredicateEntity`; `mask_*`
   либо `hide` любой компоненты исключает весь этот source, а ошибка или
   неоднозначное решение закрывает весь ответ;
5. передаёт в storage только прошедшие эти проверки source predicates и
   allowlist полей;
6. держит cursor каждого источника, сливает страницы по ключу узла и полностью
   агрегирует виды отношений для очередного ключа;
7. группирует очередную ограниченную порцию уникальных ключей по целевой
   сущности и батчами вызывает `readableFieldsByIDs`, включая поля
   представления, `deletion_mark` и `posted`;
8. отбрасывает записи, не прошедшие target RBAC/RLS, затем строит подпись только
   через `maskedRecordLabel` и продолжает чтение, пока не наберёт 101 доступный
   ключ либо не получит `exhausted` от каждого source-cursor.

Отношение видно, только если пользователю доступны строка-источник отношения,
само ссылочное поле в полном виде и получившийся объект-узел. Для шапки
используется `fieldDecisions`, для регистров — существующие synthetic metadata и
register field decisions. Для полей ТЧ такого решения в текущей модели **нет**:
`field_access` адресует только `Entity.Fields`, а `metadata.Validate` отвергает
`pii: true` на поле ТЧ. Поэтому MVP не создаёт вымышленную synthetic metadata и
не обещает маскирование отдельного поля ТЧ. Ссылка из ТЧ участвует в графе после
объектного права и row predicate сущности-владельца, а также target RBAC/RLS;
раскладка формы и отсутствие колонки в ней не считаются политикой доступа.
Конфигурация, которой нужно скрывать сам факт такой ссылки, должна до появления
отдельного контракта хранить её в защищаемом реквизите шапки либо не включать в
доступную пользователю ТЧ. Расширение грамматики `field_access` на
`tp.<ТЧ>.<Поле>`, поддержка PII и проведение этого решения через все read-path
ТЧ — отдельный план, не скрытый срез этапа 171. Любая ошибка существующей
политики, cursor или SQL закрывает весь ответ; откат к нефильтрованному запросу
запрещён.

Доступ к регистрам проверяется их собственным read-решением. Проверка составной
пары регистратора выполняется **до SQL и проекции**: нельзя сначала получить
`recorder`/`recorder_type`, а затем замаскировать результат, потому что сам узел,
точный UUID, тип и URL уже раскрывают обе компоненты. Для каждого из трёх
семейств UI получает field decisions по его synthetic metadata и допускает
источник только при полном доступе к совпавшему ссылочному полю и обеим
компонентам регистратора. Ошибка вычисления любого из этих решений возвращает
ошибку всего endpoint, а не пропускает один регистр. Лишь после этого и source
RLS storage проецирует пару; затем отдельно проверяется target-доступ к
документу-регистратору. Одинаковый документ, найденный через шапку, ТЧ и
несколько регистров, получает один узел.

### 3. UI и статика

Изменяются только границы `internal/ui`:

- `server.go` — маршруты;
- новый обработчик/сервис графа и его httptest;
- `handlers_entity.go` — флаг доступности команды для сохранённой карточки;
- `templates.go` и `templates_managed.go` — одинаковая команда;
- отдельный экранируемый шаблон страницы;
- `static/ui.js` либо небольшой отдельный модуль — lazy-load, visited set,
  depth/width states и безопасное создание DOM;
- `internal/i18n/locales/en.json` и машинные локали по принятому процессу для
  новых пользовательских строк.

Существующие URL карточек и команда «Ввести на основании» не меняются.

## Совместимость и миграция

Новой таблицы, колонки, фонового индекса и записи при чтении нет. Миграция БД не
требуется; PostgreSQL и SQLite используют один контракт с диалектными
placeholder/UUID. Существующие конфигурации продолжают работать без новых ключей.

`based_on` остаётся разрешением ввода и классификатором отношения, а не
автоматической историей происхождения. Это намеренно совместимо: старые объекты,
для которых основание никогда не сохранялось ссылкой, не получают придуманную
связь. Для цепочки в `examples/trade` добавляются явные ссылочные реквизиты на
основание и недостающие пары `based_on`; это аддитивная миграция примера через
обычный `onebase migrate`.

MVP не добавляет `_refs`. Если on-the-fly обход упрётся в объём данных, индекс
ссылок проектируется отдельным планом с транзакционной записью, backfill и
проверкой согласованности. Контракт HTTP и ключ узла при этом не меняются.

  ресурсов, атрибутов и субконто;
- ТЧ возвращает UUID владельца, регистр — UUID/тип регистратора;
- независимый инфорегистр, синтетический/неизвестный регистратор и сирота не
  создают навигационный узел;
- source predicate реально отсекает строку до помещения в cursor-поток;
- cursor проходит несколько страниц без пропуска/повтора, k-way merge собирает
  все виды отношений одного ключа, порядок стабилен;
- сломанная таблица/колонка и `rows.Err()` дают ошибку, а `CheckRefs` сохраняет
  прежний fail-closed результат.

### Срез B — защищённый JSON одного уровня

- Добавить UI-сервис оркестрации, HTML-заглушку страницы и JSON endpoint.
- Реализовать root/source/target RBAC+RLS, безопасные подписи и системные флаги.
- Зафиксировать лимит, дедупликацию и формат ошибки.

Публичные проверки среза:

- `httptest` вызывает реальный GET route с обычным пользователем;
- запрещённый корень не читается, запрещённый source row не создаёт отношение,
  запрещённый target node отсутствует;
- фильтры проверяются отдельно для сущности, ТЧ-владельца и каждого семейства
  регистра;
- masked/hidden ссылочное поле шапки или поддерживаемого семейства регистра не
  создаёт ребро и не влияет на `truncated`;
- table-driven HTTP-тесты для регистра накопления, регистра сведений и
  бухгалтерского регистра независимо ставят `mask_*` и `hide` на каждую
  компоненту пары (`recorder`, `recorder_type` / `регистратор`,
  `регистратор_тип`): source не доходит до SQL/projection, а точные тип, UUID и
  URL регистратора отсутствуют в JSON;
- ошибка вычисления field decision совпавшего поля либо любой компоненты
  регистратора в каждом из трёх семейств даёт fail-closed ошибку всего GET, а
  не частичный `200` с результатами остальных источников;
- ссылка ТЧ проверяется только политикой строки владельца и target-доступом:
  synthetic field decision не создаётся, `pii` на поле ТЧ по-прежнему
  отвергается `metadata.Validate`, а похожее имя поля шапки не применяется к ТЧ;
- masked/hidden поле представления не попадает в `label`, UUID недоступного узла
  и счётчик скрытых соседей не попадают в JSON;
- ошибка одной политики или SQL не превращается в частичный `200`;
- target-записи, скрытые в начале сортировки и занимающие больше одной
  storage-страницы, не мешают найти доступные записи после них;
- 101 доступный сосед даёт 100 узлов и `truncated=true`, а 100 доступных плюс
  произвольное число скрытых — `truncated=false`.

### Срез C — дерево в обеих карточках

- Подключить команду авто- и managed-формы.
- Реализовать ленивое дерево, состояния, цикл и глубину восемь.
- Добавить кликабельные URL, признаки удаления/проведения, i18n и доступность.

Публичные проверки среза:

- рендер обеих карточек проверяет наличие команды только у сохранённой записи;
- node-тест клиентского модуля раскрывает уровень по GET, не делает повторный
  запрос для посещённого ключа и останавливается на глубине восемь;
- URL узла ведёт в `/ui/{kind}/{entity}/{id}`, открывается с
  `target="_blank" rel="noopener"`;
- подпись из JSON вставляется как текст: HTML payload не исполняется;
- пустой, усечённый и ошибочный ответы имеют видимые и доступные состояния.

### Срез D — сквозной пример trade

- Добавить в `examples/trade` явные ссылки и `based_on`, необходимые цепочке
  «заказ покупателя → поступление → реализация → возврат».
- Засеять четыре связанных записи через публичные точки записи.
- Проверить навигацию от среднего документа в обе стороны и переход в каждую
  карточку.

Публичные проверки среза:

- `onebase check --project examples/trade` и миграция свежей SQLite-базы;
- HTTP/E2E-сценарий под ролью пользователя раскрывает цепочку ленивыми GET и
  открывает конечные стандартные формы;
- добавленный тестовый ссылочный реквизит в YAML участвует без изменения списка
  типов в Go;
- тот же сценарий с запретом на один промежуточный документ скрывает его и не
  раскрывает путь через него.

Каждый срез отдельным PR сохраняет сборку и тесты зелёными. Срез B зависит от A,
C — от B, D — от C; продуктовая возможность считается готовой только после D.

## Риски и меры

- **Полный обход таблиц и N+1.** В MVP число SQL-источников пропорционально
  числу ссылочных полей. Keyset-страницы ограничивают каждый SQL-запрос, подписи
  и target-доступ проверяются батчами; при большом числе скрытых targets сервер
  обязан читать следующие страницы ради корректного результата. Для одного
  HTTP-запроса вводятся отдельные защитные пределы времени/числа прочитанных
  строк: их достижение даёт fail-closed ошибку, а не частичный `200` или ложный
  `truncated`. В тесте фиксируется отсутствие N+1 и верхняя граница запросов для
  заданного числа страниц. Персистентный индекс не маскируется под «оптимизацию
  без контракта».
- **Утечка через наличие связи или усечение.** Source RLS применяется до
  дедупликации/лимита; защищённое ссылочное поле и защищённая компонента пары
  регистратора исключают register-source до SQL и проекции, target RLS
  применяется до счётчика доступных узлов. Поток продолжается до 101-го
  доступного либо исчерпания всех cursor. `truncated` считается только по
  доступным узлам. Любая ошибка политики, включая вычисление field decision
  регистратора, закрывает весь ответ.
- **Нет field-level политики ТЧ.** Этап не трактует layout как авторизацию и не
  изобретает synthetic `field_access`: поля ТЧ сегодня не адресуются этим
  механизмом, а `pii` на них запрещён. Граф применяет row policy владельца и
  target-доступ; расширение защиты отдельных колонок ТЧ требует отдельного
  сквозного контракта всех путей чтения.
- **Расхождение с удалением.** Общий описатель источников используется и
  `CheckRefs`, и графом; матричный тест сравнивает покрытые семейства.
- **Взрыв графа через общие справочники.** Вверх проходят только реальные ссылки
  на типы из `BasedOn`; обычные ссылки на организацию/склад/контрагента не
  разворачиваются из документа. Для корневого справочника прямые входящие связи
  остаются полезны и ограничены сотней.
- **Циклы и повторные пути.** Сервер выдаёт один уровень, клиент хранит visited
  set на ветви, глубина ограничена. Ключ включает kind/entity/id, поэтому UUID из
  разных типов не смешивается.
- **Регистры без карточек.** Они никогда не показываются как узлы: только как
  доказательство связи с валидным документом-регистратором.
- **Нестабильные подписи.** Используются текущие `Presentation`/`LabelFields` и
  `maskedRecordLabel`; UUID остаётся последним детерминированным tie-breaker.

## Откат

Срезы не меняют пользовательские данные и схему. Откат C убирает команду,
шаблон, JS и маршруты; откат B/A удаляет read-only API. Добавленные поля примера
можно оставить неиспользуемыми или удалить обычной управляемой миграцией только
из демонстрационной базы. Никакого backfill или восстановления `_refs` нет.

При аварийной деградации после релиза сначала скрывается команда и отключаются
два GET-маршрута; существующие карточки, удаление и «Ввести на основании» не
затрагиваются. Нельзя оставлять endpoint доступным без UI, если причина отката —
нарушение RLS.

## Критерии завершения

- На сохранённой карточке документа и элемента справочника в авто- и
  managed-форме есть команда структуры подчинённости.
- Дерево лениво показывает фактические основания и доступные входящие ссылки из
  шапок, ТЧ и регистров; новая YAML-ссылка начинает работать без Go-allowlist.
- Каждый узел уникален, ограничен по ширине/глубине, защищён от циклов и ведёт в
  стандартную форму в новой вкладке.
- Root, source и target RBAC/RLS проверены через публичный HTTP-путь; скрытые
  поля шапок и поддерживаемых регистров не текут через подписи или сам факт
  ребра; для всех трёх семейств регистров подтверждён полный доступ к обеим
  компонентам регистратора до SQL/projection, а для ТЧ явно соблюдается текущая
  граница row-level без несуществующей field-level гарантии; ошибки работают
  fail-closed.
- SQLite/PostgreSQL матрица покрывает все семейства физических ссылок и не
  расходится с `CheckRefs`.
- `examples/trade` демонстрирует цепочку «заказ покупателя → поступление →
  реализация → возврат» и проходит `onebase check` плюс сквозной HTTP/E2E-тест.
- `go test ./...`, обязательные статические проверки и проверка нумерации планов
  проходят; документация публичного поведения обновлена в том же завершающем
  срезе.

## Verification

1. Создать свежую SQLite-базу из `examples/trade`, выполнить миграцию и запустить
   сервер.
2. Записать и провести четыре документа цепочки с явными ссылками на основания.
3. Открыть поступление, вызвать «Структура подчинённости», раскрыть заказ вверх и
   реализацию/возврат вниз.
4. Открыть каждый узел и убедиться, что загружена стандартная форма правильного
   kind/entity/id; проверить серую пометку удаления и статус проведения.
5. Повторить под ролью, которой запрещён один документ и одна строка регистра:
   соответствующие узлы, косвенный путь и признак усечения не должны раскрыть их
   наличие.
6. Добавить в тестовую конфигурацию новый документ со ссылочным реквизитом,
   мигрировать базу и убедиться, что он появился без изменения платформенного
   списка типов.
7. Создать цикл из двух разрешённых ссылок и более 100 доступных потомков:
   цикл не раскрывается повторно, глубина ограничена, отображается стабильное
   сообщение об усечении.
