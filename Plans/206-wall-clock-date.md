# План 206 — местное время без зоны (календарная дата и стенные часы)

## Контекст

Две заявки об одном и том же, с разных сторон:

- [#1167](https://github.com/ivanarama/onebase/issues/1167) (`scadapy`,
  PostgreSQL): почасовой ряд залит ETL со смещением `+00`, а OneBase показывает
  время на три часа больше. `ALTER … TYPE timestamp without time zone` не
  помогает.
- [#1169](https://github.com/ivanarama/onebase/issues/1169): у даты рождения и
  даты приказа не нужно время — ни в интерфейсе, ни в хранении; предложен флаг
  `time: false` на элементе формы.

Корень общий: **в платформе есть ровно один тип `Дата`, и это момент времени.**
На PostgreSQL реквизит создаётся как `TIMESTAMPTZ`
(`internal/storage/dialect.go:100`, через `fieldType` в
`internal/storage/ddl.go:19`), на SQLite — ISO-текст в UTC. Показ приводится к
зоне процесса: `fmtDateValue` (`internal/ui/templates.go:118`) делает
`t.In(time.Local)`, ввод разбирается `ParseInLocation(…, time.Local)`
(`internal/ui/form_attr_values.go:48`, `handlers_entity.go:2341`).

Круг замкнут и **сам по себе непротиворечив**: что записано через форму, то и
прочитано. Приведение к местной зоне сделано намеренно — без него на хосте со
смещением съезжал календарный день (#1071, #1076). Ломается круг там, где
значение приходит не из формы:

- заливка ETL/SQL со своим смещением (#1167);
- перенос базы между зонами;
- значение, у которого времени нет по смыслу (#1169) — «14.03.1985» это не
  момент, а календарный день, и приводить его к зоне не к чему.

### Решение и почему такое

Разбор развилки — в комментариях к обеим заявкам. Нумерация в таблице ниже — по
разбору #1167; в разборе #1169 то же решение стоит под номером **3** (вариант 2
там — флаг `time: false` на элементе формы, то есть другой подход целиком).
Рассматривались три варианта:

| | Что делаем | Цена |
|---|---|---|
| 1 | Ничего; ответить «грузите в зоне сервера» | ноль, но класс задач «дата без времени» остаётся нерешаемым |
| 2 | **Новый тип поля «местное время без зоны», существующий `Дата` не трогаем** | новый тип через все слои; старые базы не шевелятся, откат — коммитом |
| 3 | Переключить сам `Дата` на стенные часы | миграция всех баз и перетрактовка уже записанных значений; откат — только из бэкапа |

**Делаем 2.** Вариант 3 отвергнут не по объёму, а по необратимости: он молча
меняет смысл уже записанных данных у пользователей, а данные, в отличие от кода,
коммитом не откатываются.

Важная поправка к тому, как вариант 2 был сформулирован в разборе #1167:
тип — **не «дата без времени», а «местное время без зоны»**. Чистый `DATE` не
удержит почасовой ряд из #1167, где значение несёт час суток. Точность
объявляется отдельно и покрывает оба случая.

## Синтаксис (что делает пользователь)

```yaml
fields:
  - name: ДатаРождения
    type: localdate                 # точность по умолчанию — день
  - name: ДатаВремяЗначения
    type: localdate
    precision: second               # день + час/минута/секунда, без зоны
```

Семантика одной фразой: **что записано, то и показано, на любом хосте и в любой
зоне.** Ни запись, ни чтение, ни показ не приводят значение к зоне процесса.

Существующий `type: date` не меняется вовсе: это по-прежнему момент времени
(`TIMESTAMPTZ`), и все написанные конфигурации работают как раньше.

### Спорное место — имя типа

`localdate` выбрано за то, что оно не врёт при `precision: second` (в отличие от
`dateonly`) и стоит в одном ряду с существующими английскими значениями
(`string`, `date`, `number`, `bool`, `richtext`, `image`). Альтернативы, которые
рассматривались и отклонены: `walltime` (непрозрачно для не-англоязычного
конфигуратора), `plaindate` (не покрывает `second`), `date_local` (единственное
значение с подчёркиванием во всём наборе).

**Имя — предмет решения человека до начала среза 1**: после выхода оно попадёт
в чужие конфигурации и станет неизменяемым.

## Хранилище / SQL

| Точность | PostgreSQL | SQLite |
|---|---|---|
| `day` (по умолчанию) | `DATE` | `TEXT`, `YYYY-MM-DD` |
| `second` | `timestamp without time zone` | `TEXT`, `YYYY-MM-DDTHH:MM:SS` |

Новый тип добавляется новыми колонками; существующие значения не переводятся.
Ретайп `date` → `localdate` и обратный **не поддерживается**. Это отказ при
планировании и применении миграции существующей базы, а не на `onebase check`:
`check` проверяет текущий YAML на новой временной SQLite-базе и не знает
прежнего типа рабочей колонки. Один и тот же YAML с `localdate` допустим для
нового поля и запрещён для замены существующего `date`.

Источник прежнего типа — сохранённая логическая подпись схемы рабочей базы.
Для полей с устойчивым `id` она уже находится в
`_schema_fields.field_type` (`storage/schemaplan.go`); сравниваются эта подпись
и желаемые метаданные, а не только SQL-тип. На SQLite оба типа могут быть
`TEXT`, поэтому SQL-интроспекция сама по себе переход не доказывает.
Для временных полей без `id` срез 1 добавляет карту
`_schema_temporal_types(table_name, column_name, field_type)` с ключом
`(table_name, column_name)`: тип и точность записываются при создании колонки
в одной транзакции с DDL. Карта сохраняется и после удаления `id` из YAML;
при переименовании с `id` обновляется вместе с основной картой. Две карты
должны согласовываться; расхождение — отказ, а не перезапись старого типа.

Если колонка уже существует, а достоверной прежней подписи нет, объявить её
`localdate` нельзя: миграция отказывает до регистрации текущего YAML как
исходной схемы. Добавление или удаление `id` не обходит этот гейт. Создание
новой колонки разрешено; прежние `date`-поля без смены типа продолжают работать.
После создания `localdate` его сохранённая подпись запрещает и обратный
переход в `date`, в том числе без `id`.

`PlanMigration` и публичный `migrate --dry-run` сообщают ошибку с таблицей,
полем и парой типов. Обычный `migrate` и остальные входы миграции выполняют
тот же preflight для всей конфигурации **до любых DDL, изменений данных или
карт типов**; apply повторяет проверку прежней подписи в транзакции.
`--allow-destructive` не разрешает эти переходы. Это защищает и случай, когда
запрещённое поле идёт после другого запланированного изменения: отказ не
должен оставлять частично применённую миграцию. Молчаливый ретайп уже портил
данные (#607), повторять нельзя.

## Период движений

Период регистра остаётся моментом `time.Time`. Источник — отдельный реквизит
`type: date`, выбранный через общий `Entity.DocumentDateField()`, уже
используемый в `SetPeriodFromFields`. Приоритет имён регистронезависимый:
`Дата`, затем `Date`, `Период`, `Period`; только при отсутствии этих date-полей
берётся первое `date` в порядке метаданных. `localdate` в этот отбор не входит,
даже если называется `Дата`. Срез 2 сохраняет этот общий выбор для периода,
даты запрета и свёртки; самостоятельный поиск первого date-поля запрещён.
Например, документ может иметь `ДатаПроведения: date` и `ДатаПриказа: localdate`. Первое поле
задаёт период движений, второе хранит календарную дату. Для периода требуется
заполненный момент: `time.Time` либо значение с явным смещением/UTC; строку
без зоны нельзя молча разобрать через `time.Local`.

Срез 2 запрещает автоматическое проведение документа с `localdate`, если
отдельного `date`-источника периода нет или он не заполнен: понятная ошибка
до записи документа и движений вместо fallback в `time.Now()`. Это правило
проверяется в публичных путях проведения UI, REST и DSL, включая отдельный
путь `Документы.X.Провести`. Конфигурационная проверка обнаруживает отсутствие
`date`-источника у такого проводимого документа; заполненность и тип значения
проверяются при проведении. Явная запись `LocalTime` в период движения также
отклоняется, а не преобразуется в момент по зоне хоста.

Преобразование стенных часов в момент (выбор зоны, неоднозначное или
несуществующее время при смене DST) в этот план не входит. Наличие отдельного
`date`-источника сохраняет определённый момент без такого преобразования.

## Изменения в коде

Осей две, и они независимы: новая **константа типа поля** в метаданных и новый
**тип значения** в Go. Ниже они разведены намеренно — места ищутся у них
одинаково (руками), а спасают они от разного.

metadata.FieldTypeDate` или `switch f.Type`. На встроенном main
`b57ebffa3054646ae4658770c094c0adfbaae7be` команда
`rg -n FieldTypeDate internal cmd -g '*.go' -g '!**/*_test.go'` находит
**77 вхождений в 40 файлах**. Это инвентаризация текстовых вхождений, включая
объявления и служебные поля, а не число отдельных реализаций:

`{"format":"date-time"}`, `ui/field_display.go:37` — `fmtReportCell(v)` вместо
форматирования даты. Ни одна из этих веток не упадёт и не пожалуется.

Значит, ревизия — работа руками, и её нельзя срезать: повторять указанную
команду `rg` в начале каждого среза, перечислять разобранные места в описании
PR и проверять каждое решение через публичный путь. Одного поиска константы
недостаточно: отдельно проверять перенос Descriptor, строковые имена типов,
`case time.Time`, `DocumentDateField` и generic-ветки сериализации. Новые
вхождения после синхронизации получают явное решение: поддержка с сохранением
точности либо понятный отказ; молчаливый fallback в строку/nil запрещён.

### Ось 2 — отдельный тип значения (`metadata.LocalTime`)

Значения ходят между слоями как `any`, и разбираются утверждением типа:
`fmtDateValue(v any)` (`ui/templates.go:118`) и `fmtReportCell(v any)`
(`ui/widget_helpers.go:222`) типа поля не знают вовсе; `normalizeFieldValue(f,
v any)` (`storage/crud.go:556`) и `exchange/package.go:899` знают, но значение к
ним всё равно приходит как `any`. Обработка `time.Time` зависит от слоя:
UI приводит значение к местной зоне для показа; `normalizeDate`
(`storage/crud.go:573–583`) получает `time.Time` из значения даты, возвращая
уже переданный `time.Time` без изменения зоны; сериализация exchange
(`package.go:899–903`) делает `v.(time.Time)` и пишет
`t.UTC().Format(time.RFC3339)`.

Поэтому `storage` сканирует новые колонки не в `time.Time`, а в отдельный тип
(рабочее имя `metadata.LocalTime`). Что это даёт:

- существующие ветки `case time.Time` продолжают работать с моментами и никакого
  `LocalTime` не видят;
- ветка приведения к зоне для нового типа недостижима: `In(time.Local)` не к
  чему применить;
- отдельный тип позволяет отличить стенные часы от момента в явных ветках.
  Сам по себе он не гарантирует заметную ошибку: generic-ветка может вернуть
  строку, а typedempty/граница DSL — `nil`. Эти пути нужно обработать явно и
  проверить; успешная компиляция или отсутствие сдвига зоны этого не доказывают.

Компилятор молчит и здесь: утверждение типа на `any` — не ошибка компиляции, а
несработавшая ветка. Тип не помогает **найти** места и не заменяет ревизию
и приёмку из оси 1.

Цена: новый тип значения расходится по сигнатурам, дескрипторам и форматам
обмена. Схема REST, пакет exchange и XDTO требуют отдельных решений.

### Типизированные пустые значения и точность

Срез 2 добавляет в `typedempty.Descriptor` отдельную временную точность
`day|second`; существующий `Scale` остаётся числовой точностью. `FromField`,
`Descriptor.Field`, описания строк ТЧ/ValueTable и `query.Result.TypedColumns`
переносят её без потери. `LocalTime` хранит ту же точность, включая каноническое
пустое значение; `typedempty.Value/Normalize` и `ui/declaredDSLValue` возвращают
типизированное пустое `LocalTime`, а не `nil` или `time.Time{}`. Значение
`second` не может незаметно стать `day`. Ошибочная/противоречивая точность
даёт ошибку на входе, не молчаливое приведение.

Как и сейчас, SQL NULL остаётся nil в хранилище: пустое значение создаётся
только при типизированном чтении из DSL. Простое чтение не записывает ноль
обратно. Явно записанное пустое LocalTime отличимо от NULL; `ТипЗнч`,
`ЗначениеЗаполнено`, копирование строки и сравнения получают согласованный
контракт пустого значения без обращения к зоне процесса.

Для прямых проекций query сохраняет тип/точность и нормализует непустые
значения в LocalTime; DSL материализует NULL через тот же Descriptor.
UNION, выражения и производные источники не получают выдуманный descriptor:
действующая граница нетипизированного результата сохраняется, документируется
и проверяется отдельно; она не обещает типизированное пустое LocalTime.

В срезе 3 `FromFormType` поддерживает точные написания `localdate` и
`localdate(day)` для дня, `localdate(second)` для секунд — как для реквизита
формы, так и колонки ValueTable. Это отдельный синтаксис `type`, а не замена
числового `FormAttribute.Precision`. Неизвестный параметр отклоняется загрузкой
и `check`. До среза 3 объявления localdate в реквизитах формы/ValueTable
отклоняются явно; связанные с полем сущности контролы включаются срезом 3.

### Границы периферии v1

- `access/user_card` и соответствующее чтение storage не поддерживают localdate
  как источник или цель отбора. Срез 1 запрещает такую политику в `check`,
  срез 2 подтверждает отказ публичным защищённым запросом. Нельзя свести
  LocalTime к моменту или пропустить ограничение доступа через generic-ветку.
- Константы и параметры обработок с localdate вне v1: срез 1 добавляет явный
  отказ загрузки/`check` до `processor.VirtualEntity` (его default сейчас
  превращает неизвестный тип в string). `typedempty.FromConstant` и scheduler
  не должны отдавать nil/сырую строку для такого объявления: при обходе загрузки
  срез 2 обеспечивает ошибку публичного выполнения до запуска прикладного кода.
  Обычные date-константы, расписания и подстановки момента сохраняют поведение.
- XDTO в срезе 4 явно отклоняет чтение и запись сущности/ТЧ с localdate обеих
  точностей. Проверка метаданных выполняется до выдачи XML и до создания
  объекта/изменения БД; ошибка называет поле, тип и точность. Нельзя терять
  precision через `fieldText`/`parseValue` или объявлять generic-строку поддержкой
  формата. Поддержка localdate в XDTO потребует отдельного согласования формата;
  пакет exchange из среза 4 при этом обязан поддержать round-trip day/second.

## Срезы (по одному PR)

**Срез 1 — тип и хранилище.** Метаданные, `precision`, DDL обоих диалектов,
валидация текущих метаданных на `onebase check`, сохранение логических типов
и отказ от ретайпа в preflight/apply миграции по разделу «Хранилище / SQL».
Явные запреты объявлений вне v1: localdate-константы, параметры обработок,
user_card и, до среза 3, реквизиты форм/ValueTable. Матричный тест
`dbtest.ForEachDialect`: колонка создаётся нужного типа, значение
записывается и читается без сдвига в пяти поясах (UTC, +03, −05, +05:45, +14).
Интерфейса ещё нет; публичные DSL/REST-сценарии принимаются в срезе 2.
До их готовности неподдержанный вход обязан отказать явно.

**Срез 2 — чтение, запись, запросы.** `LocalTime` через `storage` → `query` →
`typedempty` → `interpreter`, включая объектные поля, строки ТЧ, описания
колонок query и их типизированные пустые значения с day/second. Части даты
(`Год`/`День`/`Час`), `НачалоДня`, арифметика,
сравнение в запросах. Сюда же `internal/entityservice/`: отдельный
`date`-источник периода движений, отказ при его отсутствии/незаполненности
в документах с `localdate`, запрет неявного преобразования `LocalTime` в

SQL, включая проведение в разных TZ по разделу «Период движений» и публичную
приёмку типизированных пустых. Здесь же runtime-защита отказов access и

**Срез 3 — формы и списки.** Показ и ввод в автоформах и управляемых формах,

## Тесты

- матричные (`dbtest.ForEachDialect`) на каждом срезе — правило CLAUDE.md
  «трогаешь семантику SQL — пиши матричный тест» здесь центральное: весь смысл
  типа в том, что PostgreSQL и SQLite ведут себя одинаково;
- пояс в тестах закрепляется явно (`time.FixedZone`), обе стороны сравнения —
  литералы. Тест, где ожидаемое значение строится через `time.Local` и
  сверяется со значением, полученным через `time.Local`, — тождество, зелёное в
  любом поясе; ровно на этом обжёгся PR #1170;
- матричная приёмка через публичный `migrate`: создать существующую базу с
  `date`, записать известный момент, заменить YAML на `localdate`, вызвать
  `migrate --dry-run` и обычный `migrate` (также с `--allow-destructive`) и
  подтвердить отказ, неизменность значений, схемы и карт типов на SQLite/PG.
  Повторить для `localdate` → `date`, с `id`, без `id`, с добавлением/удалением
  `id` и с ещё одним изменением перед запрещённым полем. На свежей базе тот
  же YAML с `localdate` должен успешно мигрировать; существующая колонка без
  достоверной подписи не должна присваивать себе новый тип из YAML;
- матричная приёмка проведения через публичные UI/REST/DSL-точки входа:
  один документ с `ДатаПроведения: date` = `2026-01-01T00:00:00+03:00` и
  отдельным `localdate` проводится в отдельных процессах с `TZ=UTC`,
  `TZ=Europe/Moscow`, `TZ=America/New_York`. Сохранённый период во всех
  случаях — один момент `2025-12-31T21:00:00Z`; выборки оборотов с одинаковыми
  границами-моментами возвращают одинаковые движения. Документ только с
  `localdate`, пустой `date`-источник, период без зоны и явный `LocalTime` в
  периоде должны давать отказ без записи документа/движений. Повторить с
  `СрокОплаты: date` перед `Дата: date` и localdate рядом: период, дата запрета
  и свёртка выбирают Дата. Проверить по отдельности Date, Период, Period,
  регистр имён и fallback к первому date только при отсутствии всех приоритетных
  имён; localdate с именем Дата не должен вытеснять date-источник;
- матричная приёмка typedempty через публичные REST/DSL и `Запрос.Выполнить`:
  для day и second проверить NULL, явно пустое и непустое значение на поле
  объекта, строке ТЧ и прямой колонке query; ТипЗнч/ЗначениеЗаполнено, копирование
  и повторная запись сохраняют тип/точность. После одного чтения SQL NULL
  остаётся NULL. Отдельно проверить задокументированный нетипизированный
  результат UNION/выражения; private-вызова typedempty.Value недостаточно;
- срез 3: загрузка формы → GET → POST DSL-события → повторный GET для
  `localdate(day)` и `localdate(second)` в реквизите формы и колонке ValueTable,
  включая пустое значение, часы/секунды и неизвестную точность;
- публичные `check`/загрузка и исполнение обработки/задания отклоняют localdate
  в параметрах и константах до прикладных побочных эффектов. Защищённый
  list/query с localdate в user_card отклоняется, а не возвращает лишние строки;
- срез 4: публичные XDTO Write/Read для объекта и ТЧ с day/second дают явную
  ошибку до XML/записи; БД не меняется. Публичный экспорт/импорт пакета exchange
  на SQLite/PG сохраняет оба значения и точности в разных TZ;
- сквозной прогон через публичную точку входа: `migrate` → запись через REST →
  чтение запросом → показ на форме, при `TZ=America/New_York`.

## Эстимейт

Крупный. Срез 1 — 1–2 дня, срез 2 — 3–4 дня (самый рискованный: там же живут
`toTime`, запросы и период движений), срез 3 — 1–2 дня, срез 4 — 1–2 дня
(добавился обмен). Итого 6–10 рабочих дней, четыре PR.

Первая редакция плана обещала «около недели», но считала по заниженному вдвое
объёму (~26 мест вместо 52, без `exchange` и `entityservice`). После пересчёта
верхняя граница — две рабочие недели, а не одна. Оценка 6–10 дней остаётся
ориентиром для этих четырёх срезов с указанными отказами v1; расширение XDTO,
констант или параметров обработок в неё не включено.

## Что осталось за рамками

- **Ретайп `date` → `localdate`** и обратный. Нужна миграция данных с явным
  указанием, в какой зоне трактовать записанное; отдельный план.
- **Переключение самого `Дата`** (вариант 3) — не делаем, см. «Решение».
- **Предупреждение о дубле при вводе** и прочие вопросы форм из #1169, не
  связанные со временем.
- **`ТекущаяДата()` для нового типа**: сейчас возвращает момент. Нужна ли
  парная функция стенных часов — решать в срезе 2, по факту написанных модулей.
