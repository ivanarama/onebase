## Синтаксис / YAML и наблюдаемая семантика

Новые типы, опции YAML и функции DSL не нужны. `type: date` остаётся моментом,
а не календарной датой без зоны. Пользователь продолжает писать:

```text
ВЫБРАТЬ Год(ДатаНачала), НачалоДня(ДатаНачала) ИЗ Справочник.Тариф
ВЫБРАТЬ СуммаОстаток ИЗ Регистр.Авансы.Остатки(КонецДня(&НаДату))
```

Инварианты:

1. Строка с offset задаёт момент независимо от зоны процесса; календарная
   функция видит его в `time.Local`. Оба формата с зоной — RFC3339 и формат
   регистра с пробелом — имеют одинаковую семантику.
2. Legacy-строка без зоны трактуется так же, как `storage.ParseRegPeriod`:
   `ParseInLocation(..., time.Local)`. `2026-01-01` — полночь 1 января в зоне
   приложения, `2026-01-01 12:34:56` — эти местные стенные часы. Сохраняются
   остальные уже поддерживаемые этим parser локальные формы; не добавляется
   отдельный список несовместимых правил только для SQL.
3. SQL NULL остаётся NULL. Пустая/неразбираемая строка в SQL-скаляре остаётся
   NULL, не превращается в нулевую дату. Пустая дата первого года проверяется
   отдельно по действующему контракту; её не заменяют сегодняшней датой или
   историческим местным смещением в отображении.
4. Календарный результат в SELECT остаётся местной меткой. Перевод границы
   обратно в момент выполняется лишь в доказанном контексте сравнения, как
   предусмотрено #1833. Строки и недоказанные выражения не получают тип date.
5. Сравнения периодов VT выполняются по моменту: два представления одного
   момента равны; знак offset и повторяющийся час DST не меняют порядок.
   Сравнение двух местных строк через `ob_local_datetime` для этого непригодно.
6. `Остатки(дата)` включает равную границу. `МоментВремени` сохраняет условие
   исключения собственного регистратора при равном моменте; равенство периода
   в этом условии тоже сравнивается по моменту. Обороты и начальный/конечный
   остатки сохраняют существующие `<`, `<=`, `>=`, знаки приход/расход.
7. SQL и Go не округляют доказанные дробные секунды при сравнении. Для единого
   UTC-ключа пригодна фиксированная дробь 9 знаков из #2188; `datetime()` и
   `julianday()` не являются точной заменой. Отдельно зафиксировать потерю
   дроби штатным `normalizeSQLiteArgs`: эта работа не обещает восстановить
   точность, уже утраченную при записи или привязке time.Time.
8. Итоги и расчёт по движениям дают одни суммы. UTC-месяц итогов не заменяется
   местным месяцем; исключение быстрого пути при RLS/отборе сохраняется.
   Запреты доступа, маскирование и предикаты строк не ослабляются.

Для неоднозначного/несуществующего местного часа без offset сохраняется
действующее разрешение `ParseRegPeriod`/Go в той же зоне. Тест проверяет
согласованность путей, не обещает восстановить несуществующую информацию о
первом или втором часе. С offset два повторяющихся часа различаются строго.
Смена TZ процесса по-прежнему меняет трактовку legacy беззонных данных.

## Хранилище / SQL, совместимость и миграция

Основная стратегия — исправление чтения, без перезаписи исходных дат, DDL
колонок и смены смысла `date`. PostgreSQL сохраняет нативные TIMESTAMPTZ и
сравнение моментов; матрица проверяет его как равноправный диалект.

Произвольные физические формы SQLite сравниваются единым UTC-ключом с обеих
сторон. Для срезов этот же порядок применяется внутри выбора последней/первой
строки. Нормализация только параметра корректна лишь при доказанной единственной
форме хранения колонки; текущие данные такого доказательства не дают.

Нормализация колонки функцией может убрать range scan обычного индекса.
До выпуска измерить EXPLAIN QUERY PLAN и длительность для 10 тыс./100 тыс.
движений с одним и несколькими измерениями, равенством/диапазоном, RLS,
итогами и без. Сохранить результаты до/после, выбранный план и стоимость;
не утверждать сохранение индекса по одному лишь виду SQL. Если цена
неприемлема, остановить срез и вынести выбор индексируемого представления в
отдельное решение; не возвращать строковое сравнение ради зелёного benchmark.
Expression-index/новая колонка не входят в этот план автоматически.

Если исправление legacy-месяца изменит `monthKeyExpr`, необходим отдельный
срез: версия fingerprint итогов накопления и бухгалтерии, транзакционный
пересчёт и безопасная инвалидизация старого состояния перед fast path.
До готовности этого среза affected SQLite fast path отключается, применяется
исправленный расчёт по движениям. Это лучше неверных сумм; отключение и его
стоимость описываются явно. Простая замена сравнения в хвосте не лечит старый
неверный месяц. Если матрица докажет неизменность разбиения, пересчёт не нужен.
Прямые SQL-изменения тестовых периодов требуют явного пересчёта итогов перед
проверкой fast path; fixture не должен проверять заведомо устаревшие итоги.

## Verification и критерии завершения

Для каждого среза: сборка, тесты затронутых storage/query/DSL-пакетов, общие
проверки проекта; матричный прогон SQLite **и** PostgreSQL с заданным
`TEST_DATABASE_URL`. Пропущенный PostgreSQL не считается проверенным.
Существующие `date_funcs_local_matrix_test.go` и DSL-проверка согласованности
`Строка(Д)`/`Час(Д)` сохраняют поведение #2268. `onebase check --project
examples/trade` и публичный CLI smoke выполняются после изменений реализации.

Приёмочная конфигурация: справочник Тариф с date-реквизитом, накопления Авансы
с ресурсом Сумма, периодический регистр сведений. Через CLI `migrate`, `query
--json --sql` и HTTP-отчёт проверить исходные два сценария; временные legacy
вставки делать только в тестовой копии. Восстановить прикладной отчёт без
обхода `ЕстьNULL(ДатаНачала, ДатаНачала)` и без обращения к физической таблице;
сохранить RBAC/RLS при этом переходе. Ожидаемые строки/суммы задать заранее.

Завершено, когда обе репродукции исправлены в main, каждое принятое изменение
имеет конкретный PR/HEAD, общая матрица и обязательный CI зелёные, fast path
совпадает с эталоном, известна цена плана запроса и опубликована заметка об
изменении отчётов. #2290 не закрывать после одного A или только #2188:
закрывающее ключевое слово принадлежит последнему принятому продуктовой

## Риски и откат

Главные риски: неверный остаток при смешанных форматах; DST-неоднозначность;
потеря индекса; несовпадающие месяцы итогов; конфликт двух реализаций типов
SELECT. Защита — общий parser, UTC-порядок, отдельная проверка сортировки
срезов, общий интеграционный прогон и явное владение существующими PR.

Откат отдельного среза — revert его кода и документации, исходные даты не
перезаписаны. Если менялся fingerprint итогов, старые агрегаты не объявлять
валидными при rollback: пересчитать в контракте возвращённой версии либо
использовать медленный путь до пересчёта. Откат SQL-чтения возвращает старую
ошибку отчётов; временные обходы применяются только проверенные для конкретной
конфигурации и с прежними ограничениями доступа. Никакой массовой «починки»
дат обновлением offset при откате нет.

## Эстимейт

A: 1–2 дня; согласование и интеграционная приёмка B: 1–2 дня без времени
ожидания владельцев/CI; C1: 1–2 дня; C2: 1.5–3 дня; D: 1–2 дня.
Итого ориентир 5.5–11 дней непокрытой работы и приёмки с учётом возможного
закрытия C/D существующими PR; дополнительный C3 с пересчётом итогов — 1–2 дня
только при доказанной необходимости. Оценка уточняется по красным строкам
матрицы после B, не является разрешением переписать уже занятую реализацию.
