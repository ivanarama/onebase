# Этап 172 — Динамическая структура управляемых форм

## Контекст

План ведёт issue [#1263](https://github.com/ivanarama/onebase/issues/1263).
Выбран вариант 1 из канонического triage: сначала зафиксировать отдельным
plan-PR полный структурный API, затем реализовать его небольшими срезами.
Внешние Claude Artifacts из исходной заявки недоступны автоматическим этапам,
поэтому этот файл является самодостаточным источником требований и решений.

Сейчас `metadata.FormModule.Elements` — статическое дерево, общее для всех
пользователей. Обработчик `/form-event` возвращает значения, табличные части,
условное оформление и `elementStates`, но не изменение структуры. Клиент
`internal/ui/static/managed.js` умеет обновить существующий DOM-узел; элемент,
которого не было в первичной разметке, он создать или вернуть не может. Нельзя
во время жизни формы добавить, удалить или переместить поле, группу, страницу,
кнопку либо таблицу.

Цель этапа — дать модулю управляемой формы ограниченный 1С-подобный объект
`ЭтаФорма.Элементы`, провести изменения через авторитетное серверное дерево и
применять их в браузере без перезагрузки и потери несохранённого ввода.

В объём не входят:

- изменение YAML-файла или метаданных конфигурации из runtime-кода;
- создание новых реквизитов сущности, формы или табличных частей — динамический
  элемент можно связать только с уже объявленным путём данных;
- произвольный HTML/JavaScript из DSL;
- сохранение раскладки между разными открытиями формы или её экспорт в 1С;
- динамика autogen-форм и списков: первый контракт работает только для
  `layout_kind: managed` объектных форм и управляемых форм обработок.

## Выбранный пользовательский контракт

### Инициализация

Добавляется серверное событие формы `ПриСозданииНаСервере`. Оно выполняется один
раз при создании экземпляра формы, после проверки права чтения и существующего
`ПриЧтенииНаСервере`, но до HTML-рендера. Для новой записи событие получает уже
применённые значения по умолчанию. Существующее клиентское `ПриОткрытии` остаётся
послерендерным и тоже может менять структуру через обычный `form-event`.

Во всех обработчиках управляемой формы доступны:

- `Объект` / `ЭтотОбъект` — как сейчас, данные записи;
- `ЭтаФорма` / `ThisForm` — runtime-экземпляр формы;
- `ЭтаФорма.Элементы` / `ThisForm.Elements` — коллекция элементов текущего
  экземпляра, а не глобальный `metadata.FormModule`.

Пример минимального API:

```os
Процедура ПриСозданииНаСервере()
    Группа = ЭтаФорма.Элементы.Найти("ДополнительныеПоля");
    Если Группа = Неопределено Тогда
        Группа = ЭтаФорма.Элементы.Добавить(
            "ДополнительныеПоля", "ГруппаФормы", ЭтаФорма.Элементы.Корень);
        Группа.Заголовок = "Дополнительно";
    КонецЕсли;

    Поле = ЭтаФорма.Элементы.Добавить(
        "КомментарийДинамический", "ПолеВвода", Группа);
    Поле.ПутьКДанным = "Объект.Комментарий";
    Поле.УстановитьДействие("ПриИзменении", "КомментарийИзменён");
КонецПроцедуры

Процедура ПереключитьСостав()
    Поле = ЭтаФорма.Элементы.Найти("КомментарийДинамический");
    Если Поле <> Неопределено Тогда
        ЭтаФорма.Элементы.Переместить(Поле, ЭтаФорма.Элементы.Корень, 0);
        Поле.Видимость = Не Поле.Видимость;
    КонецЕсли;
КонецПроцедуры
```

Коллекция предоставляет `Найти(Имя)`, `Добавить(Имя, Вид, Родитель[, Позиция])`,
`Удалить(Элемент)` и `Переместить(Элемент, Родитель[, Позиция])`. Обращение
`ЭтаФорма.Элементы.<Имя>` эквивалентно `Найти`. Элемент предоставляет свойства
`Имя`, `Вид`, `Родитель`, `Дочерние`, `Заголовок`, `ПутьКДанным`, `Видимость`,
`Доступность`, `ТолькоПросмотр` и метод
`УстановитьДействие(Событие, Процедура)`.

Идентичность (`Имя`, внутренний ID), `Вид` и `ПутьКДанным` становятся
неизменяемыми после успешного завершения текущего обработчика. Для их замены
нужно удалить элемент и добавить новый. Это исключает неоднозначность между
сбором POST-данных, проверкой прав и уже созданным DOM-контролом.

## Наблюдаемая семантика и инварианты

1. Имена элементов уникальны без учёта регистра во всём экземпляре формы.
   Внутренний wire-ID выдаёт сервер; клиент не выбирает ID и не может сослаться
   на элемент другого экземпляра.
2. Разрешены только виды из `metadata.IsKnownFormElementType`. Родитель обязан
   быть контейнером по `FormElement.IsContainer`; цикл, превышение глубины или
   повторное включение узла отклоняются до изменения дерева.
3. `ПутьКДанным` ссылается только на существующее поле сущности, реквизит формы,
   табличную часть или её колонку. Динамика раскладки не расширяет модель данных
   и не обходит RBAC, field masking, `required`, `readonly_when` и write-гейты.
4. Событие и процедура проверяются теми же allowlist и AST-поиском, что статические
   handlers. `/form-event` разрешает событие динамического элемента только если
   оно присутствует в авторитетном серверном экземпляре. Присланные клиентом
   имя, вид, handler или дерево никогда не считаются источником истины.
5. `metadata.FormModule` и его `Elements` после загрузки неизменяемы. Каждый GET
   получает глубокую копию runtime-дерева; изменения одного пользователя,
   вкладки или записи не видны другим и не создают data race.
6. Мутации дерева транзакционны в памяти: обработчик работает с рабочей копией.
   Исключение, timeout или превышение лимита отбрасывает весь структурный diff.
   Изменения данных следуют существующей семантике события, включая уже
   выполненную запись перед последующей ошибкой. При этом допущенное к исполнению
   событие всегда потребляет одну ревизию независимо от исхода: ревизия является
   номером попытки события, а не только версии структурного дерева.
7. События одного экземпляра сериализованы. Запрос несёт ожидаемую ревизию и
   случайный 128-битный `eventNonce`. Сервер резервирует пару
   `(fromRevision, eventNonce)` до запуска DSL и сохраняет ограниченный replay-
   результат: точный terminal HTTP status/body и `toRevision`. Повтор той же
   пары с теми же identity и payload возвращает сохранённый ответ без исполнения
   DSL; тот же nonce с другим payload либо иной nonce со старой ревизией даёт
   конфликт. Клиентская очередь не отправляет два структурных события
   параллельно и при потере ответа повторяет запрос только с прежним nonce.
8. DOM-патч не теряет введённые, но ещё не записанные значения, dirty-state,
   активный элемент, выделение строк и прокрутку. Перемещение переиспользует
   существующий DOM-узел. Удаление сохраняет клиентское значение по data path до
   конца экземпляра; повторное добавление того же пути его восстанавливает.
9. SlickGrid создаётся для вставленной таблицы ровно один раз, при удалении
   уничтожается и вычищается из `_obGrids/_obGridViews`, а при перемещении не
   пересоздаётся. DOM-таблица `no_grid: true` следует тем же данным и правам.
10. Полный reload/redirect создаёт новый экземпляр и снова выполняет
    `ПриСозданииНаСервере`. Runtime-изменения не переживают закрытие формы,
    рестарт процесса или истечение экземпляра; это документированная семантика,
    а не частичная персистентность.
11. Старые формы с `runtimeRequired=false`, их запросы без instance-полей и
    ответы без `structure` работают как прежде. Для opt-in формы запрос без
    instance-полей, неизвестная или истёкшая instance-ссылка дают явную просьбу
    перезагрузить форму и не откатываются к статическому handler или
    недоверенному клиентскому дереву.

## Runtime-состояние и HTTP-контракт

В `internal/ui` вводится ограниченное хранилище `managedFormInstances`.
Экземпляр содержит случайный 128-битный ID, владельца/сессию, entity, form,
record ID (либо признак new), fingerprint базового `FormModule`, runtime-дерево,
монотонную `revision`, ограниченный replay-ledger событий, последний доступ и
mutex. Состояние не пишется в БД. Запись ledger хранит hash точного запроса и
готовый terminal-ответ; её размер входит в общий per-instance limit и живёт не
дольше экземпляра.

Предохранители должны быть константами с тестами: не более 256 элементов,
глубина 16, 64 операций одного события, 256 КиБ серверного patch-ответа,
30 минут idle TTL и ограниченное число экземпляров на пользователя. Очистка —
ленивая плюс при остановке сервера. Исчерпание лимита заканчивает обработчик
ошибкой без частичного патча.

Первичный HTML получает скрытые `_form_instance` и `_form_revision`. Они входят
в существующее отображение служебных имён, чтобы конфигурация не могла создать
одноимённые реквизиты. Обычный event/save POST передаёт оба значения, а каждый
`form-event` дополнительно несёт `_form_event_nonce`, который браузер создаёт
один раз и сохраняет для всех сетевых повторов этого события. Сервер связывает
экземпляр с текущей авторизационной идентичностью, точными entity/form/record и
fingerprint; один токен нельзя переиспользовать на другой форме.

Под mutex сервер сначала проверяет identity, revision и hash полного payload,
затем резервирует nonce и потребляет ревизию, и только после этого запускает
DSL. Параллельный повтор той же пары ждёт завершения уже зарезервированной
попытки, а не запускает вторую. Успех фиксирует structural diff;
исключение/timeout отбрасывает его, но обе ветви сохраняют terminal-ответ в
replay-ledger. Потерянный ответ поэтому не даёт повторно выполнить
`Объект.Записать()` или другой эффект. Если процесс завершился между эффектом и
сохранением ответа, исчезает и сам in-memory instance: повтор со старым token
отклоняется до DSL и требует reload.

Успешный `form-event` добавляет к существующему JSON:

```json
{
  "structure": {
    "base": "sha256:...",
    "fromRevision": 3,
    "toRevision": 4,
    "ops": [
      {"op":"insert","id":"dyn-7","parentId":"root","beforeId":"","html":"..."},
      {"op":"move","id":"static-12","parentId":"dyn-7","beforeId":""},
      {"op":"set","id":"dyn-7","visible":true,"enabled":true,"title":"Дополнительно"},
      {"op":"remove","id":"static-19"}
    ]
  }
}
```

`html` формируется только серверным `html/template` из типизированного элемента.
DSL не передаёт HTML. Все узлы первичного и фрагментарного рендера имеют
`data-ob-form-node` с wire-ID. Клиент проверяет непрерывность ревизий и
известность parent/before/id; любой разрыв прекращает применение, показывает
ошибку и предлагает reload вместо частичного DOM.

Порядок применения ответа: сохранить локальное состояние → проверить и применить
структурный diff → инициализировать новые контролы → применить `elementStates`,
ref options, tableparts/formTables и values → восстановить фокус/selection/scroll.
Так новый узел сразу получает итоговые данные того же обработчика.

Обычный save использует runtime-дерево только после успешной проверки экземпляра.
Оно становится источником размещённых и writable data paths для существующих
`form_partial_write`, `form_required` и table-authority проверок. Удалённое поле
считается не размещённым и не затирается отсутствующим POST-значением.

## Инвентаризация затронутых границ

- `internal/metadata/form_module.go`: новое известное событие, общие правила
  идентичности/контейнеров и безопасное глубокое копирование `FormElement`.
- Новый узкий слой `internal/ui/form_instance*.go`: дерево экземпляра, индексы,
  diff, лимиты, ревизии, владение и lifecycle. Он не меняет registry metadata.
- Новый DSL-proxy рядом с `internal/ui/dsl_form_object.go` и инъекция в
  `handlers_managed_events.go`/`form_server_events.go`: `ЭтаФорма`, коллекция и
  элемент. `Объект` остаётся прежним `formObjectThis`.
- `internal/ui/handlers_managed.go`, `templates_managed.go`: первичный рендер из
  runtime-дерева, устойчивые node-якоря и переиспользуемый рендер одного элемента.
- `internal/ui/handlers_managed_events.go`: instance/revision gate, авторитетный
  resolve handler, атомарный commit diff и поле `structure` ответа.
- `internal/ui/form_event_eligibility.go`, `form_partial_write.go`,
  `form_required.go`, `handlers_entity.go` и processor save/event paths:
  единый snapshot runtime-дерева для event и POST-authority.
- `internal/ui/static/managed.js`: последовательная event-очередь, patch engine,
  сохранение form-state, повторная привязка контролов и lifecycle SlickGrid.
- `internal/dsl/loader/managed_form_loader.go`, `internal/configcheck/*`:
  зарезервированные имена, проверка server-create handler и доступность
  `ЭтаФорма` только в контексте managed-form module.
- `internal/onec_forms/*`: новый server event round-trip там, где формат 1С его
  поддерживает; runtime-элементы никогда не попадают в YAML/XML export.
- `DEVELOPER.md`, DSL langref/ai-guide и пример формы: публичный контракт,
  ограничения lifetime и сценарий add/move/remove.

## Совместимость и миграция

Схема БД и формат `onebase.form/v1` не меняются, миграции данных нет. Статические
`elements:` остаются базовым деревом и продолжают импортироваться/экспортироваться.
Новая возможность opt-in: без `ПриСозданииНаСервере` и обращений к `ЭтаФорма`
ответы и HTML семантически прежние. Loader вычисляет для каждой managed-формы
неизменяемый признак `runtimeRequired`: он включён при объявленном
`ПриСозданииНаСервере` либо любом статически найденном обращении модуля к
`ЭтаФорма`/`ThisForm`. Неоднозначный анализ закрывается в сторону
`runtimeRequired`, а не разрешает legacy-режим.

Новый server event добавляется в словарь известных событий без автоматического
назначения процедуры по совпадению случайного имени: loader связывает только
явно объявленное событие/стандартное имя по действующим правилам. Экспортёр 1С
не материализует runtime diff. Если целевой XML-вариант не представляет новое
событие, экспорт выдаёт явное предупреждение, но сохраняет статическую форму.

На время поэтапной поставки сервер отдаёт `structure` только клиенту, который
прислал instance/revision из первичного HTML. Старый или кастомный клиент может
продолжать статические события только для формы с `runtimeRequired=false`.
Для `runtimeRequired=true` отсутствие instance/revision (а для `form-event` и
nonce), неизвестный или истёкший instance и несовпадение fingerprint
отклоняются до lookup handler и до исполнения DSL; fallback к
`metadata.FormModule` запрещён. Поэтому удалённое из runtime-дерева или
переназначенное событие нельзя вызвать, просто опустив instance-поля. Перевод
уже opt-in формы обратно в статический режим требует явного удаления runtime
API из конфигурации либо отката всего среза, а не автоматического fail-open.

## Последовательность PR-срезов и публичные тесты

### Срез A — чистая runtime-модель и DSL-контракт

- Ввести глубокую копию, индексы, правила add/remove/move/set, лимиты и
  транзакционный diff без подключения к HTTP.
- Реализовать proxy `ЭтаФорма` и проверку видов, data paths и событий.
- Публичный тест: выполнить реальную `.form.os` процедуру через интерпретатор с
  runtime-формой, проверить DSL-результат/ошибку и неизменность исходного
  `FormModule`; параллельный race-тест создаёт независимые экземпляры.

### Срез B — экземпляр и первичный серверный рендер

- Добавить lifecycle store, `_form_instance/_form_revision` и
  `ПриСозданииНаСервере` для object/processor managed forms.
- Рендерить HTML из snapshot экземпляра, сохранив fail-closed порядок
  `ПриЧтенииНаСервере` до инициализации.
- Публичный тест: HTTP GET формы с реальным модулем добавляет поле до ответа,
  второй пользователь его экземпляр не видит; ошибка/timeout возвращает отказ
  без HTML и без оставленного instance-state.

### Срез C — patch round-trip для обычных узлов

- Расширить `form-event` wire-контракт и добавить patch engine для input, label,
  button, group и pages; скрытые `hidden_when` узлы держать в адресуемой
  разметке, чтобы `false` действительно возвращал их без reload.
- Добавить `eventNonce`, резервирование/потребление ревизии до DSL и ограниченный
  replay-ledger точных terminal-ответов для успешных и ошибочных событий.
- Публичные тесты: POST `/form-event` добавляет/перемещает/удаляет узлы и отдаёт
  непрерывные ревизии; Node/DOM behavior-тест применяет настоящий JSON-ответ и
  сохраняет введённое значение, focus, dirty-state и обработчик клика. Сценарий
  «`Объект.Записать()` → исключение → потеря ответа → повтор с тем же nonce»
  доказывает одну запись и побайтово тот же terminal-ответ; повтор с другим nonce
  на старой ревизии не исполняет DSL.

### Срез D — авторитет событий и записи

- Перевести handler lookup, event eligibility, partial write, required и
  processor/entity POST на один проверенный runtime snapshot.
- Добавить per-instance serialization, stale revision conflict, TTL/owner/base
  fingerprint gates и количественные лимиты.
- Публичные тесты: поддельный dynamic handler/чужой instance/stale revision не
  запускает DSL; у `runtimeRequired`-формы запрос без instance token не вызывает
  удалённый либо переназначенный статический handler, тогда как старая статическая
  форма сохраняет legacy-путь; динамически размещённое writable поле записывается
  через обычный HTTP submit, а удалённое поле не обнуляется.

### Срез E — таблицы и SlickGrid

- Поддержать динамические `Таблица`/`ТабличнаяЧасть`/`Колонка`, оба пути
  `no_grid` и SlickGrid, корректные init/destroy/move и ref/enum options.
- Публичный тест: реальный `form-event` вставляет таблицу с текущими строками,
  Node/DOM+SlickGrid harness редактирует её, перемещает без второго init,
  удаляет с destroy и отправляет изменённые строки следующим событием.

### Срез F — статические проверки, converter и документация

- Добавить configcheck/langref/DEVELOPER/ai-guide, пример end-to-end и правила
  импорта/экспорта 1С без материализации runtime tree.
- Публичные проверки: `onebase check` принимает документированный пример и
  отклоняет неизвестный вид/путь/событие; YAML→IR→XML→IR round-trip сохраняет
  статическую форму и server event либо выдаёт документированное предупреждение.

Каждый срез сохраняет старый wire-контракт, проходит `go test ./internal/ui
./internal/metadata ./internal/dsl/loader ./internal/configcheck
./internal/onec_forms` и добавляет тест через пользовательскую HTTP/DSL-точку,
а не только на приватную функцию.

## Риски и откат

- **Утечка структуры между пользователями / data race.** Запрещена мутация
  registry metadata; копирование и ownership проверяются race/HTTP-тестами.
- **Подделка события клиентом.** Дерево и handlers живут только на сервере;
  instance/revision/nonce/entity/form/record проверяются до запуска DSL, а
  `runtimeRequired` не допускает обхода через запрос без instance-полей.
- **Повтор побочного эффекта после потерянного ответа.** Ревизия потребляется и
  nonce резервируется до DSL; terminal-ответ кэшируется. Повтор возвращает его
  без исполнения, а потеря in-memory экземпляра после crash закрывает старый
  token до нового DSL.
- **Потеря несохранённого ввода.** Patch engine сохраняет данные по data path и
  использует move вместо replace; регрессии покрываются browser behavior-тестом.
- **Повторные listeners и утечки SlickGrid.** Инициализация идемпотентна по
  wire-ID, удаление вызывает destroy и чистит все реестры.
- **Неограниченная память/DOM.** TTL, per-user cap, node/depth/op/response limits
  fail closed до commit diff.
- **Обновление конфигурации при открытой форме.** Fingerprint перестаёт
  совпадать, следующий event просит reload и не применяет overlay к новому base.
- **Сложный откат.** Статические формы можно вернуть к прежнему режиму без
  миграции БД/YAML. Для `runtimeRequired`-форм сервер не включает тихий fallback:
  откат требует одновременно убрать runtime API из конфигурации либо вернуть
  весь поддерживающий срез. Runtime instances после этого можно безопасно
  отбросить.

## Критерии завершения

- Из `.form.os` можно до первичного рендера и после него добавить, удалить,
  переместить и показать ранее скрытый элемент через документированный API.
- Изменение видно без reload, не теряет значения/focus/selection и одинаково
  работает для DOM-таблицы и SlickGrid.
- Dynamic handler и обычная запись проходят только через авторитетный snapshot,
  действующие права и непрерывную revision; отсутствие instance у opt-in формы,
  stale revision и изменённый nonce/payload не исполняют DSL.
- Повтор события после потерянного успешного или ошибочного ответа не повторяет
  побочный эффект и возвращает сохранённый terminal-результат того же nonce.
- Два пользователя и две вкладки имеют независимые деревья, исходный
  `FormModule` остаётся неизменным под `go test -race`.
- `onebase check`, converter round-trip, DSL langref, `DEVELOPER.md` и пример
  описывают один и тот же контракт и ограничения lifetime.
- Старые managed/autogen формы, клиенты без `structure` и существующие
  form-event/save тесты проходят без изменения поведения.

## Эстимейт

Ориентир — 12–17 рабочих дней: A 2–3, B 2–3, C 3–4, D 2–3, E 2–3, F 1.
Основная неопределённость — корректный lifecycle SlickGrid и сохранение
несохранённого состояния при составных DOM-патчах; поэтому таблицы вынесены в
отдельный срез после стабилизации авторитетного server contract.
