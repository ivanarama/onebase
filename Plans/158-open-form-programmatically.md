# План 158 — Программное открытие формы из DSL (`ОткрытьФорму`)

Дата проектирования: 2026-08-26.
Статус: 📋 **проектирование**, код не начат.
Уровень: **движок** — DSL (билтин, `ОписаниеОповещения`), `internal/ui`
(side-channel события, popup-режим формы, предзаполнение), клиентский JS,
права/RLS.
Заявка: [#1134](https://github.com/ivanarama/onebase/issues/1134) (автор
`boffik`) — зонтичная, закрывается не первым срезом, а всем планом.
Зависит от: план [46](46-tablepart-commands-and-picker.md) — двухфазная схема
подбора, тот же механизм side-channel и та же терминальная семантика.

## Зачем

Конвертированная из 1С конфигурация падает на `ОткрытьФорму(...)`: билтина в
движке нет вовсе. По репозиторию имя встречается дважды и только в комментариях
(`internal/ui/picker.go:27`, `Plans/46-tablepart-commands-and-picker.md:106`) —
как пояснение к аналогии, а не как реализация. Проверка конфигурации
останавливается на «неизвестная функция» (`internal/configcheck/check.go:873`).

Без программной навигации не переносятся два типовых сценария 1С:

- «создать документ на основании и открыть его на правку с заполненной шапкой»;
- «из списка открыть карточку с преднастроенным отбором».

Первый не закрывается ничем: обработчик может создать и записать объект
(`Документы.X.Создать/Записать`), но пользователя к нему не приведёт — он
останется на исходной форме и увидит только `Сообщить`. Второй частично
закрывается ручной навигацией.

## Что именно просит заявка

Автор ответил на вопрос о форме вызова
([#1134](https://github.com/ivanarama/onebase/issues/1134), 25.08.2026). Оба
места вызова идут **с возвратом значения**, и это меняет порядок срезов
относительно первой редакции плана:

**Вызов А — форма выбора существующего документа.**

```bsl
ПараметрыФормы = Новый Структура("РежимВыбора", Истина);
Оповещение = Новый ОписаниеОповещения("ПослеЗакрытияФормыВыбора", ЭтаФорма);
ОткрытьФорму("Документ.Соревнования.ФормаВыбора", ПараметрыФормы, ЭтаФорма, , , , Оповещение);
```

Обработчик получает ссылку на выбранный документ и заполняет по ней ТЧ.

**Вызов Б — форма нового документа с предзаполнением и возвратом ссылки.**

```bsl
ЗначенияЗаполнения = Новый Структура;
ЗначенияЗаполнения.Вставить("ТипСоревнований", ТекСтрока.ТипСоревнований);
// … ещё шесть реквизитов …
ДопПараметры = Новый Структура("ИндексСтроки", ИндексСтроки);
Оповещение = Новый ОписаниеОповещения("СоздатьСоревнованиеЗавершение", ЭтаФорма, ДопПараметры);
ОткрытьФорму("Документ.Соревнования.Форма.ФормаДокумента",
             Новый Структура("ЗначенияЗаполнения", ЗначенияЗаполнения),
             Элемент, , , , Оповещение);
```

```bsl
Процедура СоздатьСоревнованиеЗавершение(Результат, ДополнительныеПараметры) Экспорт
    ИндексСтроки = ДополнительныеПараметры.ИндексСтроки;
    Объект.Соревнования[ИндексСтроки].СсылкаСоревнования = Результат.Ссылка;
КонецПроцедуры
```

Отсюда три вывода, каждый из которых был бы нарушен первой редакцией плана:

1. **Открытие без возврата значения не закрывает ни один из двух вызовов.** В
   вызове Б форма откроется заполненной, но строка ТЧ останется пустой — а ради
   неё вызов и делается. Первая редакция сама сформулировала критерий («если
   рядом стоит `Оповещение`, польза от среза 1 близка к нулю, и порядок срезов
   надо пересматривать») — здесь он выполнен, порядок пересмотрен ниже.
2. **Предзаполнение — не второй аргумент.** Второй аргумент в 1С всегда
   структура **параметров формы**; значения полей лежат внутри неё под ключом
   `ЗначенияЗаполнения`, рядом с `РежимВыбора`.
3. **Обратный вызов несёт свой контекст.** `ДополнительныеПараметры` (в вызове Б
   — индекс строки ТЧ) обязаны дойти до обработчика: без них он не знает, куда
   класть результат.

## Что в платформе уже есть

Это главный раздел плана: **обе половины механизма уже написаны и работают**,
и задача — свести их, а не спроектировать заново.

### Возврат значения в DSL-обработчик — есть (подбор, план 46)

Двухфазная схема: билтин `ПоказатьПодбор` копит payload в side-channel, сервер
кладёт его в ответ события полем `pickerData` (`formEventResponse`,
`handlers_managed_events.go:52`), клиент открывает диалог. Пользователь
выбирает — JS шлёт выбор обратно как `_pick_result`, сервер разбирает его в
переменную `ПодборРезультат` и зовёт обработчик события `Выбор`
(`handlers_managed_events.go:374-375`; для обработок то же на `:1022-1024`).

То есть «отложенный обработчик, вызываемый с результатом» в платформе
**существует** — и устроен ровно как `ОписаниеОповещения` в 1С: именованная
процедура, вызываемая позже, а не блокирующее ожидание. Комментарий в
`picker.go:27` это прямо и называет: показ диалога — «аналог асинхронного
`ОткрытьФорму(..., Оповещение)` в 1С».

### Открытие формы в модальном окне с возвратом ссылки — тоже есть

Inline-создание элемента из ссылочного поля («+» рядом с полем выбора, как в
1С) — это полный круг «открыл форму → пользователь заполнил → вернулась ссылка»:

| Шаг | Где |
|---|---|
| клиент открывает iframe-модал | `openRefCreate`, `ui.js:3157` |
| маршрут резолвит `kind` и ведёт на форму создания | `refCreateRedirect`, `handlers_entity.go:866` → `/ui/{kind}/{entity}/new?_popup=1` |
| форма рисуется без nav и тулбара, кнопка — «Записать и выбрать» | `IsPopup`, `handlers_entity.go:355`; шаблоны `templates_managed.go:661`, `templates.go:2040` |
| после записи страница шлёт результат родителю | `renderPopupSaved`, `handlers_entity.go:850,1114` → `postMessage({source:"obRefCreate", id, label})` |
| родитель принимает ссылку, модал закрывается | `ui.js:3176`; отказ — `obRefCancel`, `ui.js:3195` / `managed.js:1124` |

Это и есть вызов Б без предзаполнения и без выхода в DSL. Работает сегодня.

### Предзаполнение формы нового объекта — есть

Форма нового объекта принимает query-параметры (`handlers_entity.go:306,313`):

| Параметр | Что делает |
|---|---|
| `?based_on=<сущность>&based_on_id=<uuid>` | ввод на основании: сервер грузит источник и запускает `ОбработкаЗаполнения` у приёмника (`applyFillFromQuery`, `handlers_entity.go:384`), результат перетирает дефолты |
| `?copy=<uuid>` | создание копированием (#762): значения существующей записи без записи в БД |

`applyFillFromQuery` уже проверяет право чтения источника и RLS его строки. Из
DSL то же доступно как `Документы.X.СоздатьДокумент().Заполнить(Источник)`
(`dsl_documents.go:672`) — но только на объекте, без открытия формы.

## Почему возврат значения всё-таки нетривиален

Первая редакция плана обосновывала вынос возврата значения тем, что он «требует
модели продолжения, которой в платформе нет: обработчик завершается вместе с
HTTP-запросом». **Это неверно** — см. раздел выше: и подбор, и popup-модал
возвращают результат в уже существующей модели. Настоящая граница проходит в
другом месте, и проходит она между двумя способами открыть форму:

| Способ | Что с формой-вызывателем | Возврат значения |
|---|---|---|
| **модал** (iframe поверх страницы) | жива: DOM, незаписанные поля и строки ТЧ на месте | возможен — родитель получает `postMessage` и шлёт следующее событие формы |
| **навигация** (переход на адрес формы) | уничтожена вместе со страницей | невозможен без сохранения и восстановления состояния вызывателя |

Отсюда решение плана: **`ОткрытьФорму(..., Оповещение)` открывает форму
модально, а не переходом**. Тогда возврат значения — это существующий круг
`postMessage` → повторное событие формы → именованный обработчик с
`ПодборРезультат`-подобной переменной, и никакой «модели продолжения»
изобретать не нужно.

Дорого здесь другое, и это надо записать честно:

- **Модал существует только для формы нового объекта.** `_popup=1` читается в
  `s.form` (`handlers_entity.go:355`) — обработчике `/new`; у `s.formEdit`
  (существующий объект, `server.go:386`) popup-режима нет. Открыть модально
  карточку существующего документа сегодня нельзя.
- **Обратный канал заточен под одну цель.** `renderPopupSaved` шлёт `{id, label}`,
  а принимающий код (`ui.js:3176`) жёстко кладёт значение в `<select>`
  ссылочного поля. Нужен второй приёмник, отдающий результат в событие формы.
- **`Результат` в 1С — объект, а не строка.** Обработчик читает `Результат.Ссылка`,
  значит DSL должен получить ссылку с видом, а не голый UUID. Вид ссылки
  (`Ref.Kind`) появляется в открытом PR #1143 — если к началу работ он влит,
  брать оттуда; если нет, это зависимость, а не свободный выбор.
- **`ДополнительныеПараметры` обязаны пережить круг.** Их кладёт DSL при
  создании `ОписаниеОповещения`, а читает обработчик после закрытия формы —
  между этими точками два HTTP-запроса и чужая страница в iframe. Хранить их
  на клиенте (в payload `openForm`, возвращаемом обратно нетронутым) проще и
  безопаснее, чем в серверной сессии: это данные прикладного кода, сервер их
  не интерпретирует. Но раз они возвращаются с клиента — **доверять им нельзя**,
  и по ним нельзя принимать решения о доступе.
- **`postMessage` сегодня идёт с `targetOrigin: "*"`** (`handlers_entity.go:1120`,
  `ui.js:2382`, `managed.js:1124`). Пока в сообщении `{id, label}` уже
  выбранного пользователем элемента, цена низкая. Если каналом пойдут значения
  реквизитов и `ДополнительныеПараметры` — сузить до своего origin, иначе любой
  сторонний iframe на странице читает содержимое формы.

## Граница плана

Порядок срезов пересмотрен по ответу автора: возврат значения переехал из
среза 2 в срез 1, потому что без него ни один из присланных вызовов не работает.

**Срез 1 (этот план описывает его целиком).** Открыть **модально** форму нового
объекта с предзаполнением реквизитов шапки и вернуть результат в именованный
обработчик:

```
ОткрытьФорму("Документ.X.ФормаОбъекта", Новый Структура("ЗначенияЗаполнения", Знач), , , , , Оповещение)
```

Закрывает вызов Б заявки целиком. Опирается на существующий popup-модал и
существующую схему отложенного обработчика; нового — билтин, `ОписаниеОповещения`,
предзаполнение popup-формы и второй приёмник `postMessage`.

**Срез 2 (эскизом).** Навигационный режим: `ОткрытьФорму(Путь)` **без**
`Оповещение` — уход на адрес формы вместо модала, плюс открытие формы
**существующего** объекта (`/ui/{kind}/{entity}/{id}`, `server.go:386`) и
popup-режим для неё. Возврата значения здесь нет и быть не может (см. таблицу
выше); это отдельная, более простая семантика, и именно потому она **не первая**
— пользы без возврата мало.

**Срез 3 (эскизом).** `ФормаВыбора` и `РежимВыбора` — вызов А заявки, — открытие
списка с отбором, формы отчётов и обработок.

> Вызов А **частично закрывается уже сегодня**, без единой строки этого плана:
> `ПоказатьПодбор` (план 46) даёт диалог выбора и возвращает выбранное в
> обработчик события `Выбор`. Отличие от `ФормаВыбора` в том, что кандидатов
> собирает DSL-запрос, а не форма списка сущности. Для сценария «выбрать
> соревнование и заполнить по нему ТЧ» этого достаточно — и это стоит сообщить
> автору заявки, не дожидаясь срезов.

**Не делаем и не планируем здесь:** открытие нескольких форм за один вызов
(payload одиночный, как `pickerData`), открытие форм чужой базы, произвольный
URL вместо имени формы, `ОткрытьФормуМодально` (синхронная модальность 1С —
она блокирует поток, у нас блокировать нечего).

## Форма вызова: что обязан разобрать билтин

Разбирают её `configcheck` (план обещает статическую проверку пути) и конвертер
1С — поэтому грамматика нужна до кода, а не после.

**Путь формы бывает трёх- и четырёхсегментным**, и оба вида встречаются в
присланном коде:

| Написание | Что значит |
|---|---|
| `Документ.X.ФормаОбъекта` | алиас: основная форма объекта |
| `Документ.X.ФормаВыбора` / `ФормаСписка` | алиасы: форма выбора / списка |
| `Документ.X.Форма.<ИмяФормы>` | конкретная форма по имени (`…Форма.ФормаДокумента`) |

Первая редакция знала только трёхсегментный вид — обещанная проверка не
разобрала бы `"Документ.Соревнования.Форма.ФормаДокумента"` вовсе, а опечатку в
нём тем более. Разбор обязан покрывать оба вида и опираться на реальный список
форм сущности (`forms/<entity>/*.form.yaml`), иначе проверка сведётся к проверке
префикса.

**Позиционные аргументы 1С** — восемь, и нужные заявке стоят далеко:

```
ОткрытьФорму(ИмяФормы, Параметры, Владелец, Уникальность, Окно,
             НавигационнаяСсылка, ОписаниеОповещенияОЗакрытии, РежимОткрытияОкна)
                                  ↑ 7-й — тот самый Оповещение
```

Требования к билтину:

- **седьмой аргумент нельзя съесть молча.** Молча проигнорированный
  `Оповещение` даёт конфигурацию, которая открывает форму и тихо теряет
  результат — то есть ровно тот дефект, из-за которого заведена заявка, только
  без сообщения об ошибке. Пока срез 1 не готов — внятный отказ; после — работа;
- `Владелец`, `Уникальность`, `Окно`, `НавигационнаяСсылка`,
  `РежимОткрытияОкна` в вебе смысла не имеют. Принимать и игнорировать — можно,
  но это надо **назвать в `ai-guide`**, иначе получится вторая тихая потеря;
- второй аргумент разбирается как **структура параметров формы**: ключ
  `ЗначенияЗаполнения` (вложенная структура «реквизит → значение»), ключ
  `РежимВыбора` (срез 3). Неизвестный ключ — предупреждение `check`, а не
  молчание;
- `Новый ОписаниеОповещения(ИмяПроцедуры, Форма [, ДополнительныеПараметры])`
  — новый конструктор в DSL. Процедура ищется в модуле формы; отсутствие —
  ошибка `check`.

## Механизм

**Фаза 1.** DSL-обработчик вызывает `ОткрытьФорму(...)`. Билтин ничего не
открывает — складывает payload в side-channel, как `ПоказатьПодбор`
(`internal/ui/picker.go`, регистрация — `handlers_managed_events.go:356` и
`:1016`, точек **две**, и вторую легко забыть). Семантика **терминальная**: код
после вызова выполнится, но на UI не повлияет; в `ai-guide` это надо написать
прямо, иначе повторится грабля подбора.

**Фаза 2.** После `interp.Run` сервер кладёт payload в ответ события новым полем
`openForm` рядом с `pickerData` (`formEventResponse`,
`handlers_managed_events.go:52`). Клиент открывает модал с адресом формы — тем
же `openRefCreate`, обобщённым на произвольную сущность и произвольный приёмник
результата.

**Фаза 3.** Пользователь записал объект → `renderPopupSaved` шлёт родителю
результат → родитель отправляет событие формы с именем обработчика из
`ОписаниеОповещения` и с нетронутыми `ДополнительныеПараметры` → сервер зовёт
обработчик, положив в переменную результат (ссылка с видом) и допараметры.
Отказ (`obRefCancel`) — обработчик зовётся с `Неопределено`, как в 1С.

### Предзаполнение: чем закрывать

Порядок проверки — от «ничего не писать» к «писать новое»:

1. **`ОткрытьФорму(Путь, …)` со ссылкой-основанием** обязан идти существующим
   путём: адрес с `based_on`/`based_on_id`, нового канала нет. Права и RLS
   источника уже проверяет `applyFillFromQuery`.
2. **`ЗначенияЗаполнения` с произвольными значениями полей** — к `based_on` не
   сводится: тот несёт только ссылку, а какие поля заполнить, решает
   `ОбработкаЗаполнения` на сервере по метаданным; клиент поле назвать не может.
   Здесь же имена полей приходят из прикладного кода.
3. Поэтому — и только для этого случая — серверный канал: билтин кладёт значения
   в короткоживущую одноразовую запись, клиент получает в `openForm` адрес и
   ключ, форма при отрисовке ключ гасит. Ровно как `pickerData`: данные готовит
   сервер, клиент носит ссылку на них. **В query-строку значения не кладём** —
   это открытый канал, пользователь подменит любое поле, включая отсутствующие
   на форме.

Если на реализации окажется, что `ОбработкаЗаполнения` покрывает и случай 2,
одноразовый ключ не нужен вовсе — это лучший исход. Проверить **до** кода,
первым шагом соответствующей заявки.

## Безопасность

Предзаполнение — это запись значений в объект **по имени поля из DSL**. Без
проверок это дыра, и проверок нужно три:

1. **Существование и тип.** Имя поля есть в метаданных сущности, значение
   приводится к типу поля. Неизвестное поле — ошибка конфигурации на
   `onebase check`, а не молчаливое игнорирование.
2. **Права на объект.** Открытие формы обязано пройти ту же проверку доступа,
   что и прямой переход по адресу (`requirePerm`, `handlers_entity.go:268`).
   Иначе `ОткрытьФорму` становится обходом прав:
   пользователь без доступа к документу получает его форму «изнутри»
   обработчика.
3. **RLS.** Предзаполненное значение не должно выводить объект из области
   видимости пользователя (подстановка чужой организации в поле, по которому
   режет RLS). Проверять на **записи**, а не на открытии: форма ещё ничего не
   сохранила, и запрет на этом шаге был бы ложным.

Плюс два, появившихся вместе с возвратом значения:

4. **`ДополнительныеПараметры` приходят с клиента** — это данные прикладного
   кода, вернувшиеся через браузер. Их нельзя использовать в решениях о
   доступе и нельзя считать неизменёнными.
5. **`postMessage` сузить до своего origin.** Сейчас `"*"` — см. выше.

Отдельно: `ОткрытьФорму` не должен становиться способом обойти
`ОбработкаПроверкиЗаполнения` и обязательность реквизитов — форма открывается
как обычно, со всеми проверками при записи.

## Проверки

- Матричных тестов SQL здесь нет — семантика не задевает БД.
- Тест идёт **через публичный путь**: POST события формы → в ответе `openForm`
  → GET формы по этому адресу → предзаполненные значения в отрисованной форме →
  POST записи с `_popup=1` → POST события с результатом → значение легло туда,
  куда его положил обработчик. Вызов билтина напрямую не считается (грабля #611).
- Сценарий заявки целиком, как регрессионный тест: вызов Б из #1134 — открыть
  форму нового документа с семью предзаполненными реквизитами, записать,
  получить `Результат.Ссылка` в строке ТЧ по индексу из
  `ДополнительныеПараметры`.
- Обязательный негативный тест: предзаполнение поля, которого нет; поля, к
  которому нет прав; открытие формы объекта, недоступного пользователю; отказ
  пользователя (`obRefCancel`) → обработчик получает `Неопределено`.
- Отдельный тест на седьмой аргумент: до реализации среза 1 вызов с
  `Оповещение` обязан давать внятную ошибку, а не тихо открывать форму.
- `onebase check --project examples/trade` после добавления в конфигурацию
  примера с `ОткрытьФорму`.
