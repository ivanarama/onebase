## Контекст и почему прежний план устарел

Ведущая #1531 требует две возможности, которых не даёт подбор:

1. открыть **несохранённый** новый объект с предзаполнением, не создавая
   мусорную запись до решения пользователя;
2. открыть форму из нескольких полей и получить структуру результата обратно.

После первой редакции плана код изменился:

- `formEventState.response()` переносит основное состояние формы в JSON, но не
  является общим финализатором: entity handler и bound processor вызывают его,
  а processor execute-fallback собирает `formEventResponse` напрямую;
- `ПоказатьПодбор` по-прежнему добавляет `pickerData` вручную после
  `response()`, отдельно в success/error ветках entity и bound processor;
- inline-создание ссылки открывает `/ui/_ref-create/{entity}` в iframe, а
  `renderPopupSaved` возвращает `{id,label}` через `postMessage`;
- PR #1476 усилил UX закрытия этого iframe, но текущий отправитель всё ещё
  использует `targetOrigin: "*"`, а получатель не сверяет `event.origin`,
  `event.source` и correlation;
- `ui.открытьФорму` уже существует как SSE-команда для пользователя. Она
  строит адрес только из `вид/сущность/id`, для обработки игнорирует остальные
  поля и может открыть форму не в той вкладке, которая инициировала действие;
- `processorForm` берёт начальные значения только из `params[].default`;
- модули `forms/**/*.form.os` уже обнаруживаются для проверки статических
  запросов и связности событий, но проход неизвестных DSL-вызовов в `CheckDir`
  всё ещё читает только `src/*.os`. Старое утверждение «формы совсем не
  проверяются» теперь неверно, а пробел проверки вызовов остался.

Следовательно, расширять SSE дополнительными полями или пользовательскими
событиями нельзя. Нужен адресованный конкретному HTTP form-event протокол,
который сохраняет DOM и незаписанное состояние вызывающей формы.

## Цели и нецели

План даёт:

- один `ОписаниеОповещения` и один внутренний callback protocol для формы,
  вопроса и будущих асинхронных диалогов;
- модальное открытие новой формы сущности с `ЗначенияЗаполнения`;
- модальную форму обработки с типизированными объявленными параметрами и
  структурой результата;
- отдельную адресованную инициировавшему окну навигацию к сохранённой
  типизированной ссылке;
- статические и runtime-проверки пути, callback-процедуры, параметров, прав и
  RLS.

В этот план не входят:

- произвольный URL, cross-origin iframe и открытие форм другой базы;
- синхронное `ОткрытьФормуМодально` с блокировкой потока;
- несколько диалогов из одного form-event;
- modal-edit существующего объекта, формы списка/выбора, отчёта и страницы;
  существующий `ПоказатьПодбор` остаётся способом выбора строки;
- перенос прикладных значений в query string, fragment, `postMessage` или SSE;
- автоматическое закрытие #1531 первым продуктовым PR: она завершается только
  после всех обязательных срезов и сквозных сценариев ниже.

## Публичный DSL-контракт

### Один callback

```bsl
Контекст = Новый Структура("ИндексСтроки", ИндексСтроки);
Оповещение = Новый ОписаниеОповещения(
    "ПослеЗакрытияРедактора", ЭтаФорма, Контекст);

Параметры = Новый Структура("Город,Улица", Объект.Город, Объект.Улица);
ОткрытьФорму("Обработка.РедактированиеАдреса.Форма",
             Параметры, ЭтаФорма, , , , Оповещение);

Процедура ПослеЗакрытияРедактора(Результат, ДополнительныеПараметры) Экспорт
    Если Результат = Неопределено Тогда
        Возврат;
    КонецЕсли;
    Объект.Город = Результат.Город;
    Объект.Улица = Результат.Улица;
КонецПроцедуры
```

Форма обработки завершает диалог явно:

```bsl
ЗакрытьФорму(Новый Структура("Город,Улица", Параметры.Город, Параметры.Улица));
```

`ОписаниеОповещения` содержит имя процедуры, только `ЭтаФорма` как получателя
v1 и необязательные дополнительные параметры. После возврата платформа вызывает
`ИмяПроцедуры(Результат, ДополнительныеПараметры)`. Имя callback не приходит из
браузера: оно и дополнительные параметры сохраняются сервером при первом
form-event.

Поддерживаемые значения callback-контекста и результата: `Неопределено`,
строка, булево, число, дата, типизированная ссылка, массив, структура и
соответствие из этих значений. Глубина, число элементов и размер ограничены.
Изменяемые runtime-объекты, функции, файлы и host-объекты отвергаются до выдачи
токена.

Отмена всегда вызывает callback с `Неопределено` и исходными дополнительными
параметрами. Повторная доставка результата не вызывает процедуру второй раз.

### Новый объект с предзаполнением

```bsl
Значения = Новый Структура("Контрагент,Дата", Объект.Контрагент, ТекущаяДата());
Оповещение = Новый ОписаниеОповещения("ПослеСоздания", ЭтаФорма, Контекст);
ОткрытьФорму("Документ.Заявка.ФормаОбъекта",
             Новый Структура("ЗначенияЗаполнения", Значения),
             ЭтаФорма, , , , Оповещение);
```

До нажатия «Записать и выбрать» записи в БД нет. Успешный результат — структура
с полем `Ссылка`, содержащим `*interpreter.Ref` с каноническими `Kind`, `Type`
и UUID из PR #1143. Поэтому переносимый пример читает
`Результат.Ссылка`, а `ТипЗнч(Результат.Ссылка)` возвращает
`ДокументСсылка.Заявка`.

### Вопрос использует тот же callback

```bsl
Оповещение = Новый ОписаниеОповещения("ПослеВопроса", ЭтаФорма, Контекст);
ПоказатьВопрос("Продолжить оформление?", "ДаНет", Оповещение);
```

Результат — одна из серверно объявленных строк (`"Да"`, `"Нет"`,
`"Отмена"`, `"ОК"`) либо `Неопределено` при закрытии. Отдельные событие
`Ответ` и переменная `ВопросОтвет` не вводятся. Текст и подписи выводятся через
`textContent`, не как HTML.

### Навигация #1557 — без callback

```bsl
НоваяЗаявка = Документы.А_Заявка.Создать();
НоваяЗаявка.Заполнить(Объект.Ссылка);
НоваяЗаявка.Записать();
ОткрытьФорму(НоваяЗаявка.Ссылка);
```

Перегрузка с единственным типизированным `Ref` создаёт `navigation`-эффект в
ответе **этого** form-event. Она не принимает URL, параметры, оповещение или
несохранённый объект и не использует SSE. Переход выполняется только после
успешного завершения обработчика и транзакции. Инициировавший frame/tab
заменяется целевой формой; при ошибке доступа/записи или отказе защиты
несохранённых данных исходная форма остаётся открытой.

### Разбор пути формы

В первом релизе допустимы только:

| Путь | Значение |
|---|---|
| `Документ.X.ФормаОбъекта` | новая форма объекта документа |
| `Справочник.X.ФормаОбъекта` | новая форма элемента справочника |
| `Документ.X.Форма.<Имя>` / `Справочник.X.Форма.<Имя>` | конкретная managed object-form |
| `Обработка.X.Форма` | основная managed-форма обработки |
| `Обработка.X.Форма.<Имя>` | конкретная managed-форма обработки |

Вид, сущность и форма разрешаются по реестру метаданных регистронезависимо, но
результат хранит каноническое имя. Ноль совпадений и case-only неоднозначность —
ошибка `check`/загрузки, а не выбор «первой» формы. `ФормаСписка` и
`ФормаВыбора` пока дают явную ошибку с подсказкой `ПоказатьПодбор`.

Из восьми позиционных аргументов 1С v1 поддерживает имя, параметры формы,
`ЭтаФорма` как владельца и седьмой аргумент-оповещение. Непустые
`Уникальность`, `Окно`, `НавигационнаяСсылка` и `РежимОткрытияОкна` дают
понятную ошибку; молчаливого игнорирования нет. Пропущенные аргументы остаются
допустимы.

## Единый внутренний протокол

### Ответ события и атомарность

`formEventResponse` получает два независимых эффекта:

```text
interaction: {kind, correlation, launchPath | question}
navigation:  {kind, entity, id, replaceSource}
```

`interaction` обслуживает все callback-сценарии; отдельные `openForm`,
`questionResponse` и processor-SSE не появляются. `navigation` намеренно не
имеет callback.

Эффекты копит отдельный request-scoped sink, доступный только browser form-event
execution. Он не добавляется в общий `buildDSLVarsWithMessagesTx`, чтобы
`ОткрытьФорму` не возникла в scheduler, service и headless-контекстах.

Новый единый `finalizeFormEventResponse` сначала переносит обычное состояние
через `formEventState.response()`, затем — только после `finishDSLExecution` и
только при `ok=true` — прикладывает эффекты. Его обязаны использовать все пути:
entity success/error, bound processor success/error и processor
execute-fallback success/error. Вызов диалога перед поздней ошибкой или rollback
ничего не открывает; выпущенный, но не опубликованный operation сразу
инвалидируется. Второй interaction/navigation в том же обработчике —
детерминированная DSL-ошибка.

На клиенте `obFire` сначала применяет обычный state ответа и только затем
передаёт effect единому dispatcher. Терминальный early-return текущего picker до
применения state не переносится в новый протокол.

Как у `ПоказатьПодбор`, вызов асинхронный: обработчик не приостанавливается.
После него автор должен закончить ветку (`Возврат`). Это фиксируется в
langref/ai-guide; статический lint предупреждает об очевидных операторах после
вызова, но runtime не притворяется синхронным.

### Серверное состояние и одноразовые токены

Новый bounded in-memory `formInteractionStore` хранит только короткоживущие
взаимодействия текущего процесса. Схема БД и пользовательские данные не
меняются. Перезапуск безопасно отменяет незавершённые диалоги.

При выпуске interaction сервер:

1. генерирует независимые 256-bit base64url `launchToken` и correlation;
2. сохраняет target, типизированные начальные значения, callback descriptor,
   дополнительные параметры, пользователя, hash сессии, origin и случайный
   `formInstance` конкретной отрисованной исходной формы;
3. возвращает только correlation и путь вида
   `/ui/_interaction/open/<launchToken>` — ни одного значения в query string;
4. при первом authenticated GET атомарно переводит operation из `issued` в
   `opened`, гасит launch token и рендерит форму; повтор, истечение, другой
   пользователь/сеанс/origin дают одинаковый отказ;
5. после успешного `ЗакрытьФорму`, записи объекта, ответа на вопрос или отмены
   сохраняет типизированный результат и выдаёт отдельный одноразовый
   `completionToken`;
6. исходная форма POST-ит completion token в свой обычный form-event endpoint.
   Сервер атомарно гасит его, сверяет binding и только затем вызывает сохранённую
   процедуру.

Начальные значения целевой формы неизбежно приходят в браузер только
в ответе на authenticated same-origin GET после погашения launch token и
рендерятся в DOM target iframe. Изменённые значения возвращаются
серверу в штатных form-event/POST request body. Прикладные значения не
передаются через URL/query, SSE, `postMessage`, URL history или access-log;
`postMessage` несёт только `{correlation, completionToken}`. Дополнительные
параметры callback и канонический результат остаются в server store: в DOM и
request body попадают только необходимые для показа и отправки значения
целевой формы.
Состояния operation: `issued → opened → completed|cancelled → consumed`; каждый
переход под mutex/atomic API и терминальные состояния одноразовы. Launch token
живёт 5 минут, активный диалог — до 2 часов, completion token — 1 минуту; тесты
используют fake clock. В store лежат хэши токенов, raw token маскируется в
access-log, а interaction-страницы выставляют строгий
`Referrer-Policy`. Store ограничивает число активных записей на сессию и в
процессе; переполнение отказывает до открытия формы.

Текущий auth context содержит пользователя, но не идентификатор сессии. Поэтому
срез A добавляет request-scoped SHA-256 fingerprint серверной session-cookie
(raw cookie не хранится и не логируется). Для режима без login interaction
разрешён только после выдачи отдельного HttpOnly/SameSite session nonce; одного
IP или пустого имени пользователя для binding недостаточно.

### Same-origin и correlation

Обобщённый modal-controller строится поверх `openRefCreate` и сохраняет UX
PR #1476. Для каждого iframe он:

- использует только относительный same-origin `launchPath`;
- отправляет с `targetOrigin = window.location.origin`;
- принимает сообщение только если `event.origin === location.origin`,
  `event.source === iframe.contentWindow` и correlation совпал;
- удаляет listener при cancel/complete/reopen;
- не применяет результат сам, а погашает completion token через form-event.

Результат не доверяется сообщению iframe. После записи сущности сервер сам
кладёт каноническую typed ref в operation; `ЗакрытьФорму` кладёт результат из
выполняемого сервером DSL, а ответ на вопрос сверяется с сохранённым allowlist.
Межфреймовый completion-`postMessage` содержит только
`{correlation, completionToken}`; запрос ответа на вопрос — только допустимую
кнопку и identity interaction. Обычные form-event/POST request body вне
этого ограничения: они содержат поля целевой формы, которые сервер
заново типизирует и валидирует перед использованием.
Типизированная ссылка восстанавливается специальным codec с проверкой kind,
entity, UUID, read-rights и RLS, а не общим JSON-конвертером, который теряет тип.

Неверный origin/source/correlation, повторное сообщение и сообщение после
cleanup ничего не меняют. Это обязательные browser-тесты, а не комментарии в
коде.

## Типизированное предзаполнение и права

### Обработка (#1624)

Ключи второго аргумента разрешены только при case-insensitive единственном
совпадении с `processor.Params`. Допустимы объявленные типы `string`, `text`,
`number`, `date`, `bool`, `choice`, `reference:<Entity>`. Значение приводится
общим строгим decoder-ом; `choice` сверяется с options, ссылка — с ожидаемой
сущностью и `Kind`. Неизвестный ключ, две case-вариации одного ключа, неверный
тип и недоступная ссылка — ошибка всего вызова.

`file`, служебные `_event`/`_pick_result`, поля формы, которых нет в params, и
табличные части не принимаются в первом срезе. Отсутствующий параметр сохраняет
его YAML `default`; явно переданное `Неопределено` остаётся явным пустым
значением. Тот же decoder используется при HTTP-отрисовке и form-event, чтобы
начальное и отправленное значения не расходились.

`canRunExternalProc`/trust проверяются при выдаче и повторно при потреблении
токена: изменение прав между двумя запросами закрывает доступ fail-closed.
Таким образом, дополнительные поля из старого `ui.открытьФорму` не становятся
неограниченными параметрами обработки.

### Новый объект

`ЗначенияЗаполнения` принимает только writable header fields сущности,
разрешённые выбранной object-form. Запрещены ID/version, системные признаки,
вычисляемые/readonly/hidden-by-policy поля, табличные части и произвольные
form attributes. Значения приводятся по метаданному типу; reference проверяет
вид, сущность, право чтения и RLS строки.

Право создания/записи целевой сущности проверяется при выдаче и при открытии.
RLS нового объекта окончательно проверяется штатным write path при записи —
раньше записи строки нет. Обычные required/validation/hooks/numerator/posting
не обходятся. Cancel не вызывает write path и не оставляет строку в БД.

## Совместимость и миграция

- `ui.открытьФорму` и `ui.закрытьФорму` остаются broadcast-SSE командами для
  уведомлений. Их payload и поведение не расширяются, callback через них
  запрещён.
- `ПоказатьПодбор`, событие `Выбор` и `ПодборРезультат` сохраняют публичное
  поведение. Новый код может использовать общий внутренний store, но миграция
  wire-формата picker не является условием этого плана.
- inline `openRefCreate` сохраняет `{id,label}`-совместимость на переходный
  период, но общий controller и sender переводятся на same-origin. После
  миграции wildcard-listener удаляется.
- конфигурации без новых вызовов не меняют поведение; БД-миграции нет.
- `bslIncompatPatterns` и `docs/forms-1c-converter.md` перестают безусловно

  круг реально работает. До этого предупреждение остаётся.

## Тесты

### Unit и race

- parser/resolver всех допустимых путей, неизвестного объекта/формы и
  case-only неоднозначности;
- codec: все разрешённые типы, depth/size limits, запрещённый host-объект;
- store с fake clock: single-use, expiry, wrong user/session/formInstance,
  concurrent consume (ровно один winner), capacity и purge;
- allowlist обработки и объекта: unknown/duplicate-case/type/choice/ref-kind,
  file/service/table-part negatives;
- финализатор при `ok=false` никогда не публикует interaction/navigation;
  entity, bound processor и processor execute-fallback дают одинаковый
  wire-contract и не оставляют живой неопубликованный operation;

### Публичный Go integration path

1. POST исходного form-event.
2. Получить `interaction`, открыть path с токеном и увидеть предзаполненные
   значения в HTML без них в URL.
3. POST обычной формы/`ЗакрытьФорму`, получить completion.
4. POST completion в исходный form-event.
5. Убедиться, что callback изменил именно исходную форму и получил неизменный
   серверный контекст.

Этот путь прогоняется отдельно через entity, bound processor и processor
execute-fallback. В ответе с одновременно изменённым state и interaction
browser сначала применяет state, затем открывает диалог.

Отдельно: cancel без записи; ошибка DSL после вызова; rollback; просрочка;
отзыв прав между issue/consume; RLS ссылки; typed ref из #1143; processor
default против явного `Неопределено`. Сохранение сущности и проверки RLS идут в
SQLite и PostgreSQL CI, потому что именно write path доказывает отсутствие
обхода, хотя сам token store БД не использует.

### Browser/Node

- valid message принимается ровно раз;
- wrong origin, source, correlation и stale listener игнорируются;
- targetOrigin не `*`, result/params отсутствуют в message;
- Esc/«Отмена»/«×» сохраняют поведение PR #1476, focus не уходит из dialog;
- текст вопроса и кнопок не интерпретируется как HTML;
- две формы одного пользователя не перехватывают callback/navigation друг
  друга; dirty guard не теряет ввод.

### Статическая проверка и converter

- `onebase check` реально читает `.form.os` и ловит неизвестный builtin,
  неверный literal path и отсутствующую callback-процедуру;
- корректные `ПоказатьПодбор`, `ОткрытьФорму`, `ЗакрытьФорму` и
  `ПоказатьВопрос` не дают ложных ошибок;
- импорт примера с четырёхсегментным путём и пропущенными аргументами сохраняет
  седьмой `ОписаниеОповещения`; неподдерживаемый непустой аргумент не теряется
  молча.

## Verification

На `examples/callcenter` или минимальном fixture вручную пройти:

1. перенос даты: модал обработки получает текущую дату/причину и возвращает обе;
2. отказ: зависимое уточнение меняется внутри диалога, cancel не меняет заявку;
3. создание документа: форма открывается заполненной, до записи строки нет,
   после записи callback получает `ДокументСсылка.*`;
4. #1557: записать заявку и перейти к ней из формы звонка без SSE;
5. открыть две формы звонка и убедиться, что результат приходит только в
   вызвавшую.

Команды каждого продуктового среза: targeted Go/Node tests, `go test ./...`,
`go build ./...`, `go vet ./...`, `gofmt -l`, `go run ./tools/i18ncheck` и
`onebase check` на fixture. Plan-PR выполняет только документные проверки.

## Риски и откат

- **Replay/cross-tab.** Single-use tokens + binding + correlation + exact
  `event.source`.
- **Утечка параметров.** Межзапросное состояние, дополнительные параметры
  callback и канонический результат остаются в server store. Начальные
  значения выдаются только authenticated same-origin target-форме в HTML/DOM
  после погашения launch token, а изменённые значения возвращаются в штатном
  form-event/POST request body. URL/query, SSE, `postMessage`, URL history и
  access-log прикладных значений не содержат; `postMessage` несёт только
  `{correlation, completionToken}`.
- **Обход прав.** Проверка при issue и consume, штатный write path при записи.
- **Потеря формы.** Callback только в модале; navigation отдельно и через
  существующий dirty guard.
- **Перезапуск процесса.** Незавершённый диалог отменяется fail-closed; данных
  в БД до явной записи нет.
- **Два callback API.** `ОписаниеОповещения` — единственный новый контракт;
  вопрос не получает специального события.

Откат каждого среза кодовый: schema/data migration нет, существующие picker,
SSE и обычные формы сохраняются. Pending tokens можно безопасно отбросить.

## Эстимейт и критерии завершения

Срезы A–D: примерно **8–11.5 дней** с публичными и browser-тестами. #1531
готова только когда:

- общий callback одинаково работает для entity и processor form-events;
- #1528 не вводит отдельный протокол;
- #1557 адресует только инициировавшую форму и не принимает URL;
- в сценарии #1624 форма принимает типизированные объявленные параметры,
  межзапросное состояние хранится за одноразовым server token, а результат
  возвращается same-origin;
- новый объект не записывается до подтверждения и возвращает типизированную
  ссылку;
- query/SSE не несут прикладных значений, `postMessage` содержит только
  `correlation`/`completionToken`;
- configcheck, converter, документация и SQLite/PostgreSQL CI подтверждают
  публичный контракт.
