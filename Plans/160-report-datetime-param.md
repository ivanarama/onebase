# Этап 160 — Параметр отчёта со временем суток (`datetime`)

## Контекст

Заявка #1204: умолчание параметра отчёта теряет время суток. `{{now}}` и
`{{now | minus_hours:6}}` дают один и тот же результат — `2026-08-29`, потому что
`resolveParamTemplateTextAt` (`internal/scheduler/scheduler.go:1140`) на ветке
`case time.Time` безусловно форматирует `v.Format("2006-01-02")`. У виджетов и
регламентных заданий та же подстановка отдаёт полный `time.Time`, а
`docs/features.md` обещает «ту же грамматику подстановок, что параметры виджетов
и регламентных заданий».

Само по себе усечение сегодня безвредно, и правка одного формата ничего не даст:
у отчёта **нет и приёмной стороны** для времени суток.

1. Типа со временем нет: `internal/report/report.go:11` —
   `// string, date, number, bool, select, reference:Entity`.
2. Поле ввода — `<input type="date">` (`internal/ui/templates.go:2354`). Браузер
   отдаёт только `YYYY-MM-DD`, ввести время физически нечем.
3. Разбор на входе — один-единственный формат
   `time.ParseInLocation("2006-01-02", …)`. Значение со временем, пришедшее из
   API или руками в query-строке, разбор не пройдёт и уедет в запрос **строкой**,
   а не `time.Time`.

При этом у обработок ровно это уже сделано: `parseParamValue`
(`internal/ui/handlers_processors.go:885`) разбирает три формата —
`2006-01-02T15:04:05`, `2006-01-02T15:04`, `2006-01-02`. И грамматика подстановок
уже содержит `minus_hours` (`internal/scheduler/scheduler.go:1184`) — фильтр,
осмысленный только при наличии времени суток. То есть внутрисуточный сценарий
движком предусмотрен, у отчётов просто нет типа, чтобы его принять.

Движку запроса время не мешает: параметры уезжают как `any`, `time.Time` со
временем компилятор и обе СУБД принимают. Ограничение целиком в слое параметров
отчёта.

**Почему план, а не фикс на заявке.** Разбор значения параметра отчёта по типу
существует в трёх копиях:

| место | поведение при негодной дате |
|---|---|
| `internal/ui/handlers_reports.go:150` (экран) | тихо оставляет строку |
| `internal/ui/handlers_reports.go:572` (выгрузки Excel/PDF) | тихо оставляет строку |
| `internal/api/v2.go:666` `parseReportParamValue` | `400 expected date YYYY-MM-DD` |

Добавить `datetime` в лоб — значит завести четвёртую копию и получить расхождение
между экраном, выгрузкой и API. Это тот же узор «пять копий вместо chokepoint»,
что разбирался в `entityservice`. Поэтому работа делится на два шага, и первый —
без изменения поведения.

## Синтаксис / YAML

Новый тип параметра отчёта. Всё остальное — как у `date`.

```yaml
name: ЗагрузкаСмены
params:
  - name: НачалоПериода
    type: datetime
    label: С момента
    default: "{{now | minus_hours:6}}"
  - name: КонецПериода
    type: datetime
    default: "{{now}}"
query: |
  ВЫБРАТЬ …
  ГДЕ Док.Дата МЕЖДУ &НачалоПериода И &КонецПериода
```

Форма рендерит `<input type="datetime-local" step="1">`, значение уходит в
query-строку и разбирается как `2006-01-02T15:04:05` /
`2006-01-02T15:04` / `2006-01-02` (последний — чтобы ссылка со старым значением
не ломалась). `step="1"` обязателен: браузерный шаг по умолчанию — 60 секунд, а
`{{now}}` отдаёт секунды; без атрибута почти всякое умолчание получит
`stepMismatch` и форма не отправится.

Тип `date` не меняется: `<input type="date">`, формат `YYYY-MM-DD`, усечение
подстановки до даты остаётся и становится **правилом типа**, а не скрытым
поведением резолвера.

Совместимость: валидатора типов параметра отчёта нет — неизвестный тип падает в
`default:` и работает как строка (`internal/api/v2.go:682`). Значит добавление
типа обратно совместимо: старые конфигурации не затрагиваются, миграция не
нужна.

## Хранилище / SQL

Изменений схемы нет. Значения параметров в БД не хранятся: пресет отчёта держит
только `SettingsJSON` с компоновкой (`internal/storage/settings.go:55`), а
значения параметров живут в query-строке запроса.

## Изменения в коде

### Шаг 1 — одна точка разбора (без изменения поведения)

Новая функция в `internal/report` (не в `ui` и не в `api` — её зовут оба) с
явным профилем вызывающего:

```go
type ParamParseMode uint8

const (
    ParamParseForm ParamParseMode = iota // экран и выгрузки
    ParamParseAPI                        // /api/v2
)

// ParseParamValue разбирает значение параметра отчёта по его типу.
// Ошибку возвращает только для значений, которые тип обязан отвергнуть;
// вызывающий решает, отвечать 400 или откатиться к строке.
func ParseParamValue(raw string, p Param, mode ParamParseMode) (any, error)
```

Режим — часть контракта совместимости, а не способ разнести парсер обратно по
вызывающим:

| тип | `ParamParseForm` (экран и выгрузки) | `ParamParseAPI` |
|---|---|---|
| `date` | валидное → `time.Time`; ошибка остаётся вызывающему для отката к исходной строке | валидное → `time.Time`; ошибка становится 400 |
| `bool` | нынешний набор `true/on/1/да` | нынешний более широкий набор `true/yes/y/on/да/истина` |
| `number` | исходная строка | `float64`, негодное значение → ошибка |
| `string`, `select`, `reference:*`, неизвестный | исходная строка | исходная строка |

Пустое значение по-прежнему обрабатывает вызывающий (`nil`, а для bool в API —
`false`) до парсера. Таким образом, одна функция содержит обе явно названные
политики, но шаг 1 не меняет ни успешные типы значений, ни набор истинных bool.

Переводятся на неё:

- `internal/ui/handlers_reports.go` — сборка `queryValues` в `runReport` с
  `ParamParseForm`; ошибку игнорирует и кладёт исходную строку (нынешнее
  поведение экрана);
- `internal/ui/handlers_reports.go` — та же сборка в
  `reportExportRowsWithContext` с `ParamParseForm`; поведение то же;
- `internal/api/v2.go` `parseReportParamValue` заменяется вызовом с
  `ParamParseAPI`; ошибка уходит наверх, `reportParamsFromQuery` отдаёт 400
  (нынешнее поведение API).

Расхождение «экран прощает, API отвергает» **сохраняется намеренно**: в форме
пользователь правит поле и повторяет, а клиент API должен узнать, что параметр
негоден, а не получить молча отчёт по строке. Шаг 1 фиксирует это в тестах —
сейчас это нигде не записано и держится случайно.

### Шаг 2 — тип `datetime`

- `internal/report/report.go:11` — `datetime` в перечислении типов;
  `ParseParamValue` в обоих режимах разбирает три формата (взять логику
  `internal/ui/handlers_processors.go:885`, а не писать заново), а ошибку экран
  и API обрабатывают по уже зафиксированной политике;
- `internal/ui/handlers_reports.go:473-491` `buildReportParams` — ветка
  `p.Type == "datetime"` → `ui.IsDateTime = true`; поле в `reportParamUI`;
- `internal/ui/templates.go:2353-2355` — `{{else if $p.IsDateTime}}
  <input type="datetime-local" step="1" …>`;
- `internal/scheduler/scheduler.go:1136-1152` — `ResolveParamTemplateText`
  получает тип: `ResolveParamTemplateText(raw, typ string) string`. Если
  результат подстановки — `time.Time`, только новый `datetime` форматируется как
  `2006-01-02T15:04:05`; `date` и **все остальные существующие или неизвестные
  типы** сохраняют прежний `2006-01-02`. Для результатов других Go-типов
  остаётся нынешний `fmt.Sprint`. Оба вызывающих знают тип и правятся:
  `internal/ui/handlers_reports.go:97` (`reportParamDefault`) и
  `internal/api/v2.go:657`;
- `docs/features.md` — раздел про умолчание параметра: обещание грамматики
  становится верным, добавить тип в описание параметров отчёта;
- комментарий `Param.Default` (`internal/report/report.go:14-19`) — снять
  умолчание про дату;
- `internal/cli/aiguide.go` — упомянуть тип, если там перечисляются типы
  параметров отчёта (проверить: сейчас список типов там про поля объектов).

## Тесты

**Шаг 1** (все — на существующем поведении, красные до правки не должны быть):

- `internal/report/params_test.go` — таблица режим × тип × вход × ожидание для
  `date`, `number`, `bool`, `select`, `reference:`, пустой строки и мусора. Она
  отдельно фиксирует строковый `number` и узкий bool-набор формы против
  `float64` и широкого bool-набора API.
- Фиксация расхождения: негодная дата даёт ошибку, и вызывающий-экран кладёт
  строку, а вызывающий-API отвечает 400. Проверять **через публичные точки
  входа** (правило CLAUDE.md): HTTP-хендлер отчёта и `/api/v2` — не звать
  `ParseParamValue` напрямую в тесте на поведение.

**Шаг 2:**

- `internal/scheduler/scheduler_test.go:517` `TestResolveParamTemplateText` —
  расширить: тот же вход при `date` даёт дату, при `datetime` — момент;
  `{{now | minus_hours:6}}` при `datetime` отличается от `{{now}}` (ровно случай
  из #1204). Для `string`, `select`, `reference:*` и неизвестного типа
  `{{now}}` по-прежнему даёт только дату — это регресс-тест обратной
  совместимости.
- `internal/ui` — рендер: параметр `datetime` даёт
  `type="datetime-local" step="1"` и не даёт `type="date"` (по образцу
  `internal/ui/managed_date_field_test.go:47-51`). Отдельная проверка фиксирует,
  что значение с ненулевыми секундами валидно для шага поля.
- `internal/ui` — сквозной: отчёт с параметром `datetime` и умолчанием
  `{{now | minus_hours:6}}` через HTTP-хендлер отдаёт в запрос `time.Time` со
  временем суток. Это и есть проверка фикса #1204 пользовательским путём.
- `internal/api` — `datetime` в query-строке разбирается; негодное значение даёт
  400 с внятным текстом.
- Матричный тест не нужен: семантика SQL не меняется, меняется только тип
  значения параметра на входе. Если при реализации выяснится, что `time.Time` со
  временем иначе биндится в SQLite и PG — тогда `dbtest.ForEachDialect` по
  правилу CLAUDE.md обязателен.

новый формат результата включается только для нового типа `datetime`.

дублирование, а нынешнее расхождение экрана/выгрузки и API превращает в явные
режимы с общей матрицей тестов. Если работа остановится после шага 1, заявка
#1204 останется открытой, но типы значений и поведение конфигураций не изменятся.
