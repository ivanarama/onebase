# Этап 210 — быстрая первая страница справочника без изменения порядка

Дата: 2026-10-27. Статус: проектирование, продуктовая реализация не начата.
Ведущая заявка: [#2255](https://github.com/ivanarama/onebase/issues/2255).
Основание: вариант 2 канонического триажа `6316821997` и последующее
[решение владельца](https://github.com/ivanarama/onebase/issues/2255#issuecomment-6441034806).
Инвентаризация сделана по `main` `47346be8351ff0d584da6083bb1d08b8a5cc9ff4`.
Этот план не закрывает заявку и не разрешает миграцию рабочей базы.

## Контекст и выбранный вариант

Заявка связывает задержки списка, подбора и панели «Отбор» с чтением и
сортировкой большого справочника ради 50 строк. Данные автора: около 2 млн
строк; его рабочая база в этом запуске недоступна. Выбран вариант 2 триажа:
самостоятельный срез ленивой панели, затем проверяемая оптимизация явного
`order_by` с оценкой стоимости индексов. Порядок не зависит от размера базы;
вариант «перестать сортировать после порога» исключён.

Уже поставлено, повторно не реализовывать:

- [#2256](https://github.com/ivanarama/onebase/pull/2256), merge `106e65e7`:
  `loadInitialRefOptions` учитывает `refDropdownFields`. Управляемая форма
  объекта не загружает общие варианты полю, которому нужна только подпись
  выбранной ссылки; собственные choice-фильтры сохраняют свой маршрут.
- [#2271](https://github.com/ivanarama/onebase/pull/2271), merge `00a2dbe0`:
  обычный порядок плоского справочника/документа использует прямую колонку,
  либо разделяет NULL и непустые строки в согласованном read snapshot.
  В заимствованной транзакции применяется один statement с `NULLS LAST`.
  Это делает SQL пригодным для подходящего индекса, но само наличие индекса
  и выгодный план для любого фильтра этим не гарантируются.
- При `OnlyFolders`/`ExcludeFolders` лишний ключ `is_folder` уже исключён.
  Утверждение «OR с IS NULL всегда выключает индекс» не является основанием
  для изменения схемы.

Остаток на указанном SHA:

1. `list` вызывает `loadInitialRefFilterOptions` до рендера. Ограничение полями
   `listFilterPanelFields` уже есть, но каждому видимому ссылочному фильтру
   по-прежнему загружается первая страница, даже при закрытом `<details>`.
2. Ветка `List`: `params.Sort == "" && len(entity.OrderBy) > 0` строит CASE
   пустоты, нормализует пустой текст, приводит число на SQLite и добавляет
   `id ASC`. Обычного индекса по исходной колонке недостаточно для такого
   составного порядка. Иерархический смешанный список имеет дополнительный
   префикс `is_folder DESC`.
3. Собственный список делает также `CountList`, разрешение ссылок и, в режиме
   дерева, отдельное чтение корней. Ускорение сортировки не равно ускорению
   всего HTTP-маршрута. Эти затраты измерять раздельно.

## Наблюдаемая семантика и инварианты

- Первоначальный HTML списка содержит пустой вариант «все» и выбранную ссылку
  с разрешённой сервером подписью. Без выбранного значения запрос первой
  страницы ссылочного справочника отсутствует. Точечное чтение выбранного
  UUID допустимо; недоступная ссылка не раскрывает подпись.
- Первая страница вариантов загружается по первому фокусу/клику на конкретном
  select, включая клавиатуру. Простое открытие панели не запускает загрузку
  всех справочников. Повторный фокус использует успешный ответ в пределах
  текущего DOM; ошибка позволяет повторить запрос. Кнопка подбора работает
  независимо, выбранное значение сохраняется, пока пользователь его не сменит.
- В полёте есть один запрос на select и generation token: старый ответ не
  заменяет новый выбор, сброшенный фильтр или DOM после навигации. Ответ
  другой сущности/контекста не используется. Ошибка не превращается в «все».
- `f.<Поле>`, применение, сброс, URL и персональный набор `list_filters`
  сохраняются. Ссылки на `_users` не направлять в каталоговый endpoint:
  сохранить нынешнюю отдельную обработку пользователей в первом срезе.
- Сортировка остаётся той же: порядок ключей и ASC/DESC из `order_by`, пустые
  в конце, NULL и `""` образуют один класс для текстовых типов и переходят к
  следующему ключу; числовые значения сравниваются численно; `id ASC` завершает
  порядок. Никаких float64-преобразований в Go и изменения хранения чисел.
- Сохранить исключение/включение групп, parent/owner, activity, поисковые и
  choice-фильтры, RBAC/RLS, маскирование до подписи и стабильную пагинацию.
  Пользовательский `Sort` и keyset по id имеют нынешний приоритет.
- Обычный порядок из #2271 и его snapshot/транзакционный контракт не менять.
  Нет миграции NULL в `is_folder`, переписывания бизнес-данных или нового
  порядка при отсутствии индекса.

## Синтаксис / YAML и индексный контракт

Срез панели не требует изменения конфигураций. Для индексной части предложен
явный opt-in сущности (новое поле, до реализации не поддерживается):

```yaml
order_by: [Наименование, -Порядок]
list_order_index: true
```

По умолчанию `list_order_index` выключен: существующие базы не получают
неоценённое построение крупных индексов при первом запуске. Флаг разрешён
только сущности с валидным непустым `order_by`; неподдержанный профиль
диагностируется до DDL. Не расширять `indexes:` до произвольного SQL.

Типизированный descriptor включает версию, identity сущности/полей, физические
имена, диалект, типы ключей, пустоту, направление, collation и режим групп.
Он строится только из проверенных метаданных; SELECT и CREATE INDEX используют
одну эмиссию выражений. Индекс заканчивается `id ASC`. Для иерархии максимум
два профиля: смешанные группы с `is_folder DESC` и порядок без этого ключа.
Не создавать отдельный индекс на каждую комбинацию фильтров/ролей/параметров.
Общий лимит ключей сверять с обоими движками; слишком широкий `order_by`
отклоняет только включение оптимизации, а прежняя конфигурация без opt-in
продолжает работать.

Пример одного строкового ключа, соответствующий текущей семантике:

```sql
ORDER BY CASE WHEN (name IS NULL OR name = '') THEN 1 ELSE 0 END ASC,
         CASE WHEN (name IS NULL OR name = '') THEN NULL ELSE name END ASC,
         id ASC
```

Индекс содержит эти же три ключа, с корректными скобками для диалекта. Для
числа SQLite сохраняет текущий `CAST(col AS NUMERIC)`, PostgreSQL — числовую
колонку; совместимость определяется матрицей результатов, включая значения
около 2^53, отрицательные и дробные значения. Нельзя подменить сортировку
индексом по тексту числа или другим приведением ради EXPLAIN.

Один такой индекс снимает полную сортировку для соответствующего профиля,
но произвольные RLS/owner/parent/LIKE-предикаты могут требовать просмотра
многих записей или другой стратегии. Обещание «никакого SCAN» неверно: SQLite
`SCAN ... USING INDEX` допустим, если читается ограниченный упорядоченный
префикс без временного B-дерева. Для селективных фильтров измерять rows examined,
а проблему поиска `%строка%` не объявлять решённой этим индексом.

## Хранилище / SQL, совместимость и миграция

Существующий `_managed_entity_indexes` хранит format_version/definition/signature
и согласует обычные колоночные индексы. `desiredEntityIndexes` сейчас формирует
`Plain: true`; expression/partial/opaque определения нельзя считать обычными
или удалять по сходству имени. Основа — [план 186](186-managed-index-reconciliation.md),
но реализацию проверять по актуальному коду, не статусу плана.

В отдельном индексном срезе добавить versioned kind для order_by в существующий
реестр. Старые v1-записи и пользовательские индексы остаются неизменными.
Идентичность включает полный descriptor и фактическое каталоговое определение;
одно имя не доказывает владение. Неизвестная версия, внешнее изменение индекса,
коллизия имени или неподдержанная collation останавливают изменение этого
профиля с понятной ошибкой. Чужой индекс не усыновляется автоматически.

`migrate --dry-run` до применения показывает таблицу, точный DDL, число новых
индексов, старый/новый профиль, размер таблицы/текущих индексов, необходимость
перестроения и отсутствие достоверной оценки свободного диска, если она
неизвестна. На тестовой копии измерить длительность CREATE, объём файла/WAL,
временный пик диска и задержку записи. Условия допуска записать в продуктовый
PR; на рабочей базе оператор выбирает окно обслуживания после этих замеров.

Первый выпуск использует обычный транзакционный CREATE в окне обслуживания,
с таймаутом блокировки и отменой; PostgreSQL CONCURRENTLY и фоновая миграция
вне этого плана. Проверить границы существующих транзакций Migrate: не обещать
атомарность всего Migrate, если она обеспечена лишь для согласования индексов.
Внутри index-reconcile сохранить блокировку, CREATE-before-DROP и откат
реестра/DDL одной транзакцией. При изменении порядка сначала создать и проверить
новое определение, затем снять только доказанно принадлежащий старый индекс.
При отключении opt-in удалить только зарегистрированные индексы этого kind.

Данные, API-порядок и формат бэкапа не меняются. Повторная миграция идемпотентна.
Rename/drop/retype поля, смена order_by и восстановление копии должны повторно
согласовать descriptor; SQLite rebuild обязан сохранить внешние индексы либо
явно остановиться. Старый бинарь не должен удалить неизвестный format_version:
перед выпуском проверить downgrade на копии, при несовместимости сначала
отключить opt-in и штатно удалить новые индексы новой версией. Это часть
документированного отката, а не предположение о старом коде.

## Последовательность небольших PR-срезов и публичные тесты

1. **Ленивая панель без схемы** (2–3 дня). В начальном HTML только текущий
   разрешённый выбор, страницы вариантов — по первому фокусу select. Через
   реальный GET списка и GET ref-options доказать отсутствие запросов первых
   страниц до взаимодействия (счётчик на DB/driver-границе, не время теста),
   сохранение выбранного значения вне первых 50, read/RLS, activity, owner,
   маскирование, поля с/без list_filters. Браузер: Tab, мышь, повторный фокус,
   поиск/подбор, ошибка с повтором, сброс, смена фильтра во время fetch и
   навигация. `_users` и формы объектов — регрессии, без изменения контракта.
   Существующий тест ожидает ранние варианты в HTML: заменить именно это
   ожидание публичным сценарием, не только тестом приватного helper.
2. **Контракт сортировки и воспроизводимые измерения** (2–3 дня). Без DDL
   выделить descriptor и эмиссию; через публичный `DB.List` сравнить полные
   последовательности UUID до/после, все страницы при неизменных данных,
   NULL/пустой текст/вторичный ключ/числа/ASC/DESC/группы/id/фильтры/RLS,
   включая borrowed transaction и keyset. Добавить диагностический benchmark,
   который фиксирует фактический SQL/args List, CountList и HTTP отдельно.
   Данные 100 тыс. и 2 млн строк; SQLite и PostgreSQL. Без временных порогов
   в unit-тестах. Результат среза — доказанный SQL и бюджет индексной миграции.
3. **Индексы сортировки по opt-in** (4–6 дней после среза 2). Метаданные,
   descriptor → DDL, версионированное владение, dry-run и миграция вместе.
   Через публичные `DB.Migrate`/`List`, CLI migrate и реальные каталоги обеих
   БД проверить создание/повтор/смену/отключение, внешний одноимённый индекс,
   чужой expression index, ошибку/отмену CREATE, rollback, параллельные
   миграторы, rename/retype/rebuild, restore и downgrade. Тесты утверждают
   идентичность результатов и отсутствие полной временной сортировки в
   целевых профилях; не фиксируют всю текстовую строку EXPLAIN или имя плана.
   Индексный срез не принимается без обоих диалектов и отчёта о стоимости.
4. **Наблюдаемость маршрутов** (1–2 дня, независимый PR после первого среза).
   Использовать существующие slow-operation threshold и duration_ms/route,
   добавив list/ref-options только там, где покрытия нет. Не вводить второй
   произвольный порог «2 секунды». Публичный HTTP-тест с управляемой задержкой
   проверяет один лог выше порога, отсутствие ниже, request_id и маршрут,
   отсутствие SQL args, поискового текста, UUID и защищённых подписей.
   Логирование не является доказательством ускорения и не блокирует поставку
   отдельно проверенных срезов 1–3.

Каждый продуктовый срез проходит собственные REVIEW/CI; этот PR содержит
только Plans/. Не объединять задним числом с уже поставленными #2256/#2271.
При передаче в FIX сохранить #2255 ведущей до приёмки всего основного остатка,
первый ленивый срез не должен объявлять её полностью исправленной.

## Тесты и Verification

Обязательный набор для срезов SQL: `dbtest.ForEachDialect` с заданным
`TEST_DATABASE_URL`; `go test ./internal/storage ./internal/metadata
./internal/configcheck ./internal/ui` и затронутые CLI-тесты, `go build ./...`.
После правок примеров: `onebase check --project examples/trade`. Для панели
добавить браузерный тест через действующий harness, а не проверку строки JS.

Протокол замеров сохраняется в описании продуктового PR или отдельном отчёте:
SHA, версии движков/ОС, размер страниц/данных, DDL, распределение пустых и
повторов, доля групп и селективность фильтров, SQL и очищенные args, EXPLAIN,
пять повторов и медиана, прогретый и воспроизводимо холодный режим на тестовой
копии, размер/время CREATE и стоимость записи до/после. Не очищать OS-кэш
рабочей машины или рабочей БД ради теста.

SQLite: `EXPLAIN QUERY PLAN` фактических statements List. PostgreSQL:
`EXPLAIN (ANALYZE, BUFFERS)` того же SELECT на тестовой копии с актуальной
статистикой; не выключать sequential scan ради успешной картинки.
Проверять плоский/иерархический список, смешанные группы и exclude/only,
с/без parent/owner/RLS, ASC/DESC и два ключа; отдельно расходы CountList.
Первый экран, раскрытие панели и открытие подбора измерять отдельно.

Локальная проверка при подготовке плана: Python sqlite3 `3.53.0`, 100 тыс.
синтетических строк, столбцы `id TEXT PRIMARY KEY, name TEXT, payload TEXT`.
`id` — восьмизначный номер; каждый 97-й name = NULL, иначе каждый 89-й = `""`,
остальные `N` + обратный восьмизначный номер; payload = 120 символов.
При `SELECT id,name,payload ... LIMIT 50` с ORDER BY из примера выше обычный
индекс `(name,id)` дал `SCAN sample` + `USE TEMP B-TREE FOR ORDER BY`;
индекс по тем же CASE/CASE/id дал `SCAN sample USING INDEX order_name` без
временной сортировки. Пять прогретых повторов: примерно 508–659 мс против
0,15–0,40 мс; последовательности id совпали. Это узкий SQL-эксперимент, не
benchmark публичного List, не воспроизведение рабочей базы и не приёмка
PostgreSQL. `TEST_DATABASE_URL` в этом запуске отсутствует; его результаты не
заявляются. Матричные и масштабные замеры остаются обязательством срезов 2–3.

## Риски, откат и критерии завершения

Основные риски: изменение filter/choice-семантики при ленивой загрузке,
потеря выбранной ссылки, гонка fetch, несовпадение DDL и ORDER BY, рост
индексов/задержки записи, блокировка миграции, чужое владение и недостаточный
выигрыш при селективном RLS. Ни один из них не закрывается одним EXPLAIN.

Откат панели — возврат ранней загрузки без изменения URL и значений.
Descriptor без DDL откатывается отдельно. Индексный откат — отключение
opt-in новой версией, dry-run и удаление только её собственных индексов;
данные не меняются, прежний ORDER BY продолжает работать, скорость может
вернуться к исходной. Перед возвратом старого бинаря проверить downgrade,
не удалять индексы вручную по префиксу имени. Диагностика отключается
существующей настройкой порога либо откатом своего отдельного PR.

Готовность основного объёма #2255:

- ненужных чтений первых страниц при первоначальном GET списка нет;
  выбранные значения, клавиатура, фильтры, права и подбор работают;
- публичный List сохраняет результаты и порядок на обоих диалектах;
  все применимые регрессии #2256/#2271 проходят;
- целевые order_by-профили с opt-in на 2 млн строк не делают полной
  временной сортировки ради LIMIT 50, а оставшиеся дорогие фильтры и CountList
  явно перечислены; имеются HTTP-замеры, а не обещание фиксированных мс;
- стоимость CREATE/диска/записи принята по отчёту, dry-run/ошибки/владение/
  повторная миграция/откат проверены; без этого индексный срез не выпускается;
- каждый срез прошёл REVIEW и обязательный CI. Наблюдаемость имеет отдельный
  результат и не выдаётся за ускорение. Исходную issue закрывает только
  итоговый продуктовый PR после сверки всего принятого остатка.

Оценка: 9–14 дней для срезов 1–3; 1–2 дня для независимой наблюдаемости,
всего 10–16 дней без ожидания review и окна обслуживания. Если матрица или
