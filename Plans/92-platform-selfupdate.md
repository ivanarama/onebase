# План 92 — Автообновление платформы: каналы, кнопка в лаунчере, сетевой `onebase update`

Дата проектирования: 2026-08-05.
Статус: ✅ Реализовано 2026-08-06 (этапы 92A/92B/92C).

> **Что разошлось с планом.**
> 1. Вместо модалки сделана страница `/updates`: там и переключатель канала, и
>    список изменений, и предупреждение об остановке баз — в модальном окне это
>    читалось бы хуже, а рендер страницы ещё и тестируется напрямую.
> 2. Вскрылся дефект, которого план не предполагал: `SwapBinary` **копировала**
>    старый бинарь в `.old` и писала новый поверх занятого имени, хотя её же
>    комментарий обещал приём с переименованием. Windows не даёт перезаписать
>    запущенный `.exe`, поэтому лаунчер не мог обновить сам себя («Access is
>    denied»). Теперь имя освобождается переименованием. Нашлось живым прогоном:
>    на CLI-пути дефекта не видно, там обновляется чужая установка.
> 3. Ключи интерфейса заведены только в `en.json` (критерий `i18ncheck` —
>    перевод хотя бы в одной нерусской локали); остальные 14 локалей неполны и
>    без этого плана.
> 4. Подпись артефактов, дельта-обновления и тихое авто-применение по умолчанию
>    не делались — см. «Не делаем сейчас».

## Контекст

Механика подмены бинаря уже написана и покрыта тестами (план 4 из issue #299,
PR #305) — не хватает ровно двух вещей: **источника обновлений из сети** и **UI**.

Что есть:

| Кусок | Где | Состояние |
|---|---|---|
| Извлечение бинаря из ZIP, `VerifySHA256`, `SwapBinary` с сохранением `.old`, `Rollback`, `PollHealthzVersion` (сверяет `X-OneBase-Version`) | `internal/selfupdate/selfupdate.go` | готово |
| `onebase update --from <zip\|exe> --sha256 <hex>` + остановка/запуск системной службы (`sc.exe`/`systemctl`), автооткат если не поднялся `/healthz` | `internal/cli/update.go` | готово, **только офлайн** (файл с флешки) |
| Публикация артефактов | `.github/workflows/release.yml` | каждый push в `main` → pre-release `build-<run_number>` с `onebase-<goos>-<goarch>.zip\|tar.gz` + `.sha256`; тег `v*` → обычный release |
| Версия в бинаре | `internal/version` | `Build` через ldflags (`build-672` / `v0.9.8`) + commit/date из VCS |

**Каналы уже разделены физически** флагом `prerelease` в GitHub Releases —
менять CI не нужно: stable = `/releases/latest` (GitHub сам исключает
pre-release), build = первый элемент `/releases` с `prerelease: true`.

Чего нет: платформа не знает, что вышла новая версия, и не умеет её принести.

### Ритм выпуска (факт на 2026-08-05)

- `build-*` — десятки в день (04.08 вечером: build-668…672 за час), последняя `build-672`;
- `v*` — раз в 3–7 дней, последняя `v0.9.8` от 03.08.

Отсюда два следствия для дизайна: канал по умолчанию — `build` (там живёт
тестирование, на него же ссылается `docs/features.md` через `since: build-NNN`),
но уведомление обязано быть **тихим бейджем**, а не модалкой, иначе оно будет
дёргать пользователя по пять раз за вечер.

## Принятые решения

1. **Канал по умолчанию — `build`**; `stable` — переключатель в настройках.
2. **Скачивание и применение разделены**: загрузка идёт фоном и ничего не
   останавливает; применение — по явной кнопке (или при следующем старте
   лаунчера, если включён `auto_apply`).
3. **Источник — `ivanarama/onebase`** (там реальные `build-672` и `v0.9.8`).
   Переопределяется политикой для закрытых контуров.
4. **Поверхности**: лаунчер и CLI — действие; «О программе» в конфигураторе —
   индикатор + кнопка-ярлык; «О программе» в Предприятии — только индикатор.
5. **Право на обновление = право на запись в каталог бинаря** (см. «Кто может»).

## Каналы и сравнение версий

```
канал stable : GET /repos/<repo>/releases/latest          → tag v0.9.8
канал build  : GET /repos/<repo>/releases?per_page=20     → первый prerelease=true → build-672
```

Правила сравнения (`selfupdate.Newer(current, candidate string) bool`):

- обе версии `build-N` → сравнение чисел (`run_number` монотонен);
- обе версии `vX.Y.Z` → semver;
- **разные схемы** (переключение канала) → всегда «доступна другая версия»,
  формулировка в UI не «новее», а «канал stable предлагает v0.9.8»;
- текущая версия `dev-*` (локальная сборка) → обновления **не предлагаем**
  вообще: пользователь собрал бинарь сам, подменять его нельзя.

Анонимный лимит GitHub API — 60 запросов/час на IP; при проверке раз в 4 часа
запас стократный. Ответ `403 rate limit` трактуется как «проверить не удалось»,
а не как ошибка обновления.

## Хранилище состояния

```
~/.onebase/updates/
  state.json              # см. ниже
  build-672/              # staged: распакованные бинари, sha уже сверена
    onebase.exe
    onebase-gui.exe
  prev/                   # предыдущая версия для отката (бывший .old)
    onebase.exe
    onebase-gui.exe
```

```json
{
  "channel":      "build",
  "checked_at":   "2026-08-05T10:00:00Z",
  "latest":       {"tag": "build-672", "published_at": "…", "notes": "…", "url": "…"},
  "staged":       {"tag": "build-672", "dir": "…/build-672", "verified": true},
  "prev":         {"tag": "build-660"},
  "restart_bases": ["id1", "id2"],
  "auto_apply":   false
}
```

`state.json` — единственный канал связи с процессами баз: «О программе» в
Предприятии читает его и **не ходит в сеть сама** (см. «Почему база не
проверяет обновления»).

## Кто может нажать (главный вопрос безопасности)

Лаунчер слушает `127.0.0.1` на случайном порту (`launcher/server.go:68`), его
страницы идут **без авторизации** (`server.go:126`) — тот, кто его открыл, уже
может создать/удалить/остановить базу и увидеть DSN с паролем. Кнопка
обновления не расширяет власть над его собственным стендом. Опасен другой
сценарий: **бинарь общий** (терминальный сервер, `C:\Program Files`), а реестр
баз у каждого пользователя свой (`~/.onebase/ibases.yaml`, 0700 —
`launcher/store.go:41`). Тогда одно нажатие меняет платформу всем.

Граница уже проведена файловой системой — используем её:

1. **Проба записи в каталог бинаря** (`selfupdate.CanWriteBinaryDir()`: создать
   и удалить временный файл рядом с exe). Нет прав → кнопка неактивна с текстом
   «Обновление платформы недоступно: нет прав на запись в `<путь>`. Обратитесь к
   администратору». Без этой проверки `SwapBinary` всё равно упадёт — просто
   посреди процесса и некрасиво.
2. **Файл политики рядом с бинарём** — `<каталог exe>/onebase.policy.yaml`.
   Именно рядом с exe, а не в профиле: в профиль пользователь пишет сам, это
   была бы не политика.

   ```yaml
   updates:
     ui: false                    # спрятать кнопку в лаунчере и конфигураторе
     check: off                   # запретить сетевые проверки (офлайн-контур)
     channel: stable              # зафиксировать канал
     repo: myorg/onebase-dist     # свой источник
   ```

   Плюс `ONEBASE_UPDATES=off` для развёртывания скриптом.
3. **Честное подтверждение** перед применением: список баз, которые будут
   остановлены, и предупреждение «затронет всех пользователей этой машины;
   откат возможен, но базы, уже открытые новой версией, обратно не мигрируются».

## Модель применения

```
[проверка]  раз в N часов + при старте лаунчера → state.json.latest
     ↓
[скачивание] фоном в updates/<tag>/, sha из ассета .sha256 → staged.verified
     ↓
[применение] ── кнопка «Перезапустить и обновить» ──┐
             └─ при старте лаунчера, если auto_apply ┘
```

Применение (лаунчер):

1. снять снимок запущенных баз (`store.List()` × `runner.IsRunning`) → `state.restart_bases`;
2. `runner.StopAll(ports)` — уже есть, включая добивание по порту и `waitPortFree`;
3. `SwapBinary` для **каждого** бинаря пакета (см. «Два бинаря на Windows»),
   старые уезжают в `updates/prev/`;
4. перезапуск себя: `exec.Command(exe, os.Args[1:]...)` детачем + `srv.Close()` + выход;
5. новый процесс при старте: сверяет `version.String()` со `staged.tag`, чистит
   staging, поднимает базы из `restart_bases`, показывает «Обновлено до build-672».

Если новый лаунчер не стартовал, пользователь остаётся без окна — поэтому шаг 5
дублируется страховкой: при старте старой версии с непустым `staged` и
`prev`-каталогом показываем «обновление не применилось» и предлагаем откат.

### `internal/cli/update.go`

```
onebase update                       # сеть, текущий канал: скачать + применить
onebase update --check [--json]      # только проверить (для мониторинга и планировщика)
onebase update --download            # только скачать в staging
onebase update --channel build|stable
onebase update --rollback            # вернуть предыдущий бинарь
onebase update --from … --sha256 …   # офлайн-путь как сейчас (--sha256 обязателен)
```

Отдельная правка: сейчас `resolveUpdateTarget` **требует** `--service`/`--id`
(`update.go:152`) — для десктопного сценария без службы нужен режим «просто
подменить бинарь»: если служба не указана и не выводится из `--id`, шаги
stop/start пропускаются, а проверка `/healthz` заменяется запуском
`<new> --version`.

- **Предприятие** (`internal/ui`, экран «О программе») — только строка, по

  строки нет.

### Почему база не проверяет обновления сама

Процесс базы не должен ходить на GitHub: это и egress-политика (`net.enabled`),
и офлайн-эксплуатация (issue #299), и лишний шум при десятках сборок в день.
Поэтому Предприятие читает готовый `state.json`, а сеть трогает только лаунчер
или явный вызов `onebase update --check`.

### i18n

Новые строки лаунчера идут через `tr()`/`{{t}}`; `go run ./tools/i18ncheck`
блокирует CI (`ci.yml:31`) — ключи надо добавить во все `internal/i18n/locales/*.json`.

## Тесты

Юнит (`internal/selfupdate`, `httptest`-мок GitHub API — сеть в тестах не трогаем):

1. выбор релиза по каналу: `latest` для stable, первый `prerelease` для build;
2. выбор ассета по GOOS/GOARCH, ошибка при отсутствии сборки под платформу;
3. `ParseSHAFile` для обоих форматов: `sha256sum` (Unix) и `Get-FileHash` (Windows, два пробела, ASCII);
4. `Newer`: `build-660 < build-672`, `v0.9.7 < v0.9.8`, `dev-abc123` → никогда не обновляем;
5. `StageAll`: из ZIP извлекаются оба бинаря; из tar.gz — свой бинарь; превышение `MaxBinaryBytes` → отказ;
6. несовпадение суммы → staging помечается `verified:false` и не применяется;
7. `LoadPolicy`: файл рядом с exe выключает UI/фиксирует канал; `ONEBASE_UPDATES=off` перекрывает файл;
8. `CanWriteBinaryDir` на каталоге 0500 → false (тест пропускается на Windows);
9. `State` — round-trip и устойчивость к битому JSON (не должен ронять лаунчер).

Рендер-тесты лаунчера (в стиле существующих `*_render_test.go`):

10. бейдж не рисуется, когда `latest == current`;
11. кнопка неактивна с пояснением при `CanWriteBinaryDir == false`;
12. блок обновлений отсутствует целиком при `policy.updates.ui == false`.

CLI: `onebase update --check --json` печатает `{"current","latest","channel","update_available"}`
и возвращает код 0 при отсутствии обновления.

## Verification (ручная, по протоколу AGENTS.md)

1. Собрать `go build -ldflags="-X …/internal/version.Build=build-1"`, запустить
   `onebase start` → в шапке бейдж «доступна build-672».
2. `onebase update --check --json` → JSON с current/latest/channel.
3. `onebase update --download` → файлы в `~/.onebase/updates/build-672/`, `verified:true`.
4. Запустить две базы, нажать «Перезапустить и обновить» → базы остановлены,
   окно переоткрылось, «О программе» показывает build-672, обе базы снова
   запущены.
5. `onebase update --rollback` → вернулась build-1, базы поднимаются.
6. Положить `onebase.policy.yaml` с `ui: false` → блок исчез; с `check: off` →
   при обрыве сети старт лаунчера не тормозит (проверить с отключённым адаптером).
7. Скопировать бинарь в каталог без прав на запись → кнопка неактивна с текстом.
8. Переключить канал на `stable` → предлагается `v0.9.8`, формулировка «канал
   stable предлагает…», а не «новее».

## Риски и ограничения (проговорить в UI, не замалчивать)

1. **Миграции.** `onebase run` прогоняет миграции при каждом старте
   (`cli/run.go:163–212`: `Migrate`, `MigrateRegisters`, `MigrateAccountRegisters`).
   Миграции аддитивные, поэтому откат бинаря на практике проходит — но
   гарантировать это в UI нельзя, и для общей PostgreSQL-базы один запуск новой
   версии виден всем пользователям. Перед применением предлагаем
   `onebase backup` (для SQLite — прямо кнопкой, `backup_handlers.go` уже есть).
2. **Два бинаря на Windows.** В архиве `onebase.exe` и `onebase-gui.exe`;
   лаунчер мог быть запущен из GUI, а базы — дочерние процессы **того же файла**
   (`runner.go:84,128`). Менять надо оба, иначе рассинхрон версий.
3. **Подлинность.** ✅ Закрыто #783 (2026-08-16): подписывается файл `.sha256`,
   рядом публикуется `<архив>.sha256.sig` (Ed25519). Цепочка: подпись
   подтверждает сумму, сумма подтверждает архив. Открытый ключ вшивается в
   бинарь при сборке (`-X …selfupdate.PublicKey=…`), приватный живёт секретом
   репозитория. Переход был мягким: подпись проверялась, но не требовалась —
   иначе первая же подписанная версия оборвала бы автообновление всем, кто
   стоял на старых сборках. С #1195 жёсткий режим включён: релизный workflow
   собирает бинари с `RequireSignature=1`, и релиз без `.sig` отвергается.
   Мягкость была дырой ровно того размера, ради которого подпись вводилась:
   обойти её можно было отсутствием подписи. Форки не задеты: без вшитого ключа
   проверки нет вовсе, со своим ключом форк подписывает свои релизы сам.
4. **Самоперезапуск** с переоткрытием окна WebView2 — самая тонкая часть; если
   в 92B она окажется нестабильной, деградируем до «обновление применится при
   следующем запуске» (staged остаётся на диске, применяется на старте).
5. **`install.ps1:6` качает с `ivantit66/onebase`**, где последняя сборка
   `build-9` от 18.07 — новые пользователи ставят протухший форк. Однострочный
   фикс на `ivanarama/onebase`, заодно с этим планом.

## Не делаем сейчас

- **Подпись артефактов** (minisign/cosign) — отдельный шаг, требует ключа в CI
  и решения по его хранению; текущий уровень не хуже ручной установки.
- **Дельта-обновления** — бинарь ~30 МБ, экономия не окупает сложность.
- **Обновление конфигураций** — это другой слой, у него уже есть история версий
  и откат (`config_history.go`).
- **Тихое авто-применение по умолчанию** — только опция `auto_apply` для
  собственных стендов; на канале `build` молча менять платформу нельзя.
