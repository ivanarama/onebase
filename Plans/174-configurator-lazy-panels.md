# Этап 174 — Ленивая загрузка панелей конструктора

Статус: проектирование. Ведущая заявка — [#1471](https://github.com/ivanarama/onebase/issues/1471).

## Контекст

На конфигурации из issue #1471 (118 справочников, 30 документов, более 200
форм) вкладка «Дерево» блокирует главный поток браузера на минуты. Триаж
воспроизвёл проблему на синтетической конфигурации сопоставимого размера:

- начальный документ занимает 22,1 МБ и содержит 188 316 `<option>` и 2902
  `<select>`;
- сервер собирает HTML примерно за 1,1 секунды, а основная задержка приходится
  на разбор и построение DOM в браузере;
- 71 % документа создают повторённые в каждом редакторе списки имён сущностей
  и перечислений;
- одна панель объекта занимает около 178 КБ.

Причина находится в `internal/launcher/configurator_tmpl_tree.go`: `tab-tree`
сразу рендерит `.cfg-panel` для каждого объекта. Для справочников и документов
циклы на строках около 296–311 вызывают `entity-detail`, а остальные виды
объектов имеют такие же заранее отрисованные панели. Функция `selItem` в
`internal/launcher/static/configurator.js` ничего не загружает, а только
переключает класс `active` у уже существующего DOM.

## Выбранный вариант

В issue стоит единственная метка `decision:2`. Это вариант 2 доверенного triage:
дерево и оболочка конструктора приходят первым ответом, а правая панель
конкретного объекта загружается отдельным запросом после выбора узла.

Вариант 1 (единый источник вариантов для всех `<select>`) не выбран. Он может
быть самостоятельной последующей оптимизацией одной уже загруженной панели, но
не должен подменять выбранную архитектуру. План 118 относится к панели записи
в рабочем UI, а план 76 — к дереву рабочего UI; ни один из них не задаёт этот
контракт конструктора.

## Наблюдаемая семантика и инварианты

1. Первый ответ вкладки `?tab=tree` содержит дерево, верхнюю панель и один
   пустой контейнер правой области. Он не содержит форм редакторов всех
   объектов. Размер дерева закономерно растёт с количеством его узлов, но
   начальный HTML больше не растёт с суммарным числом реквизитов, табличных
   частей, модулей и макетов всех объектов.
2. Клик по узлу немедленно выделяет его и показывает состояние загрузки. Затем
   браузер запрашивает ровно одну панель по точному `data-id`. До завершения
   запроса дерево, поиск, сворачивание групп и выбор другого узла остаются
   доступны.
3. Успешный ответ содержит ровно один корневой `.cfg-panel` с тем же точным
   `id`, который был запрошен. Клиент не строит редактор из JSON и не дублирует
   серверную бизнес-логику шаблонов.
4. Загруженная панель остаётся в DOM и повторно не запрашивается в пределах
   страницы. Переключение `A → B → A` сохраняет введённые, но ещё не
   отправленные значения A, раскрытые `<details>`, активную объектную вкладку и
   состояние Monaco/конструктора макета. Выселения кэша в этом плане нет.
5. После посещения всех узлов память может вырасти до нынешнего худшего случая.
   Это осознанная цена сохранения несохранённых правок; стартовая блокировка и
   работа с обычным небольшим набором посещённых объектов при этом устранены.
6. Ответ на устаревший запрос не меняет текущий выбор. При быстрых кликах
   `A → B` поздний ответ A можно сохранить в кэше, но активируется только B.
   Для одного `data-id` одновременно существует не более одного запроса.
7. Ошибка сети или ответ сервера показываются внутри области выбранной панели
   с кнопкой «Повторить». Ошибка одного узла не удаляет уже загруженные панели
   и не блокирует выбор другого. Повтор запускает новый запрос только для
   этого узла.
8. Редирект на вход или HTML страницы входа не вставляется как фрагмент:
   потеря configurator-сессии переводит всё окно на штатный URL входа. Перед
   вставкой проверяются HTTP status, `Content-Type`, точное число корневых
   панелей и совпадение `id`.
9. `?select=<data-id>`, автовыбор только что созданного объекта, контекстное
   меню, поиск, drag-and-drop порядка дерева, верхняя кнопка «Сохранить» и
   `Ctrl+S` сохраняют существующее поведение. Автовыбор теперь завершает
   выделение сразу и асинхронно догружает нужную панель.
10. Существующие POST-обработчики сохранения и формат формы не меняются.
    Делегированный перехват `submit` продолжает отправлять формы с
    `X-Onebase-Ajax: 1`, поэтому динамически вставленная форма сохраняется тем
    же публичным путём, что и до оптимизации.
11. Фрагмент всегда строится из свежего снимка конфигурации на сервере и
    возвращается с `Cache-Control: no-store`. Уже загруженные панели остаются
    снимком момента их загрузки — это не хуже нынешней eager-страницы, которая
    тоже не обновляет соседние панели после сохранения без перезагрузки.

## Синтаксис / YAML

Форматы конфигурации, YAML, DSL и пользовательские URL не меняются.

Добавляется внутренний read-only endpoint конструктора:

```text
GET /bases/{id}/configurator/panel?node=<tree-data-id>
```

Контракт ответа:

- `200 text/html; charset=utf-8` и один `.cfg-panel` для существующего узла;
- `400` для пустого или синтаксически недопустимого идентификатора;
- `404` для допустимого типа, но отсутствующего объекта;
- обычный auth-редирект/отказ существующего `cfgAuthMiddleware` при
  недействительной configurator-сессии;
- `Cache-Control: no-store` для успешных и ошибочных fragment-ответов.

Endpoint принимает не путь к файлу и не имя Go-шаблона. Сервер разбирает
allowlist префиксов и находит точный объект в уже загруженной модели. Имена из
query string нельзя напрямую отражать в HTML или использовать для выбора
динамического шаблона.

Поддерживаемая адресация должна совпасть с фактическими `data-id` дерева:
`e-`, `r-`, `ir-`, `ar-`, `en-`, `cn-`, `rep-`, `mod-`, `proc-`, `pf-`,
`dpf-`, `mkt-`, `sub-`, `wdg-`, `page-`, `journal-`, а также фиксированные
`panel-app` и `home-page`. `panel-admin` остаётся в своём существующем AJAX-
контуре, а управляемые формы продолжают открываться отдельной страницей.

## Хранилище / SQL

Изменений схемы, данных, миграций и SQL нет. Оптимизация касается только
read-only загрузки метаданных и HTML конструктора.

## Инвентаризация затронутых границ

| Граница | Текущее устройство | Требуемое изменение |
|---|---|---|
| `internal/launcher/configurator.go` | `configuratorPage` загружает все данные и `renderCfg` отдаёт целую страницу | Добавить обработчик одного fragment-ответа и общий безопасный поиск панели по node-id |
| `internal/launcher/server.go` | Все маршруты конструктора находятся в группе `cfgDBReadMiddleware` + `cfgAuthMiddleware` | Зарегистрировать новый `GET .../configurator/panel` только внутри этой группы |
| `internal/launcher/configurator_load.go` | `loadCfgData` строит общую модель, обратные связи, списки имён и исходники | На первом этапе переиспользовать модель; не вводить второй неполный загрузчик. При необходимости профилировать отдельной задачей |
| `internal/launcher/configurator_types.go` | `configuratorData` хранит все коллекции и `SelectedTreeID` | Добавить отдельное типизированное представление запроса/результата панели; не смешивать его с доверенным `SelectedTreeID` |
| `internal/launcher/configurator_tmpl_tree.go` | Sidebar и все detail-панели находятся в одном `tab-tree` | Оставить в `tab-tree` дерево и host, а единственные panel-шаблоны извлечь в fragment-шов без копирования разметки |
| `internal/launcher/configurator_tmpl.go` | `cfgTmpl` собирает строковые шаблоны | Подключить новый именованный fragment-template к той же `html/template` и FuncMap |
| `internal/launcher/static/configurator.js` | `selItem` синхронно включает готовую панель; часть сложных редакторов инициализируется один раз на `DOMContentLoaded` | Добавить single-flight loader/cache, защиту от stale response и идемпотентный `cfgHydratePanel(root)` для динамического DOM |
| `internal/launcher/static/configurator.css` | `.cfg-panel` скрыт, `.active` виден | Добавить состояния loading/error/retry и `aria-busy`, не менять раскладку split/sidebar |
| тесты `internal/launcher` | Многие тесты исполняют `tab-tree` и ожидают детали внутри полной страницы | Разделить проверки shell и fragment; прогонять уникальность id/форм и round-trip через реальный fragment endpoint |

Особое внимание нужно инициализации после вставки. Начальный обработчик
редактора главной страницы и `initAllLayoutEditors` сейчас привязаны к
`DOMContentLoaded`. Их следует превратить в идемпотентные функции с параметром
корневого элемента и вызывать как при начальной загрузке, так и из
`cfgHydratePanel`. Глобальные делегированные `submit`, `click`, `contextmenu` и
drag/drop-обработчики повторно регистрировать нельзя.

## Изменения в коде и последовательность PR-срезов

### Срез A — справочники и документы

1. Вынести обёртку `entity-detail` в единственный именованный fragment-template,
   чтобы eager- и lazy-пути не могли разойтись по именам полей или action URL.
2. Добавить точный resolver для `e-<Name>`, handler и защищённый GET-маршрут.
   Resolver обязан различать отсутствие объекта и ошибочный node-id, а также
   гарантировать единственный корень ответа.
3. Убрать eager-панели справочников и документов из начального `tab-tree`.
   Остальные виды пока оставить как есть: срез уже снимает основной объём из
   воспроизведения #1471 и остаётся безопасно откатываемым.
4. Перевести `selItem` для `e-*` на общий `cfgLoadPanel`: мгновенное выделение,
   single-flight promise, проверка ответа, вставка, hydration, кэш и retry.
5. Сохранить загруженные панели в DOM и добавить токен текущего выбора, чтобы
   порядок ответов не определял активную панель.

Публичные тесты среза A:

- HTTP-тест через реальный router вызывает защищённый
  `/bases/{id}/configurator/panel?node=e-...`, проверяет `200`, content type,
  `no-store`, единственный точный root и реальную POST-форму `/fields`;
- таблица негативных HTTP-сценариев проверяет пустой id, неизвестный префикс,
  отсутствующий объект, спецсимволы и потерянную configurator-сессию;
- начальный GET синтетической конфигурации с 118 справочниками и 30 документами
  не содержит `.obj-editor`, `name="field.0.type"` и повторённых списков
  вариантов, но содержит все узлы дерева;
- browser/Node-тест кликает A, затем B до ответа A, убеждается, что активен B,
  и что повторный выбор A не создаёт второй fetch;
- browser/Node-тест меняет значение в A, переключается `A → B → A` и видит то
  же значение; submit динамической формы проходит существующий AJAX-путь.

### Срез B — все остальные панели и масштабный гейт

1. Расширить типизированный resolver на все перечисленные node-id. Для каждого
   вида извлечь существующую разметку в тот же fragment-шов; не создавать
   параллельные «облегчённые» формы.
2. Перевести регистры, перечисления, константы, отчёты, модули, обработки,
   печатные формы/макеты, подсистемы, виджеты, страницы, журналы,
   `panel-app` и `home-page` на общий loader. После этого начальный ответ не
   содержит ни одной объектной detail-панели.
3. Завершить `cfgHydratePanel(root)` для редактора главной страницы, макетов,
   Monaco и остальных не-делегированных инициализаторов. Каждая инициализация
   должна быть повторно безопасной и помечать уже обработанный DOM.
4. Перенести старые DOM-инварианты (`NoDuplicateDOMIDs`, `NoNestedForms`,
   вкладки объектов/отчётов/обработок, round-trip типов) с полного `tab-tree`
   на матрицу fragment-ответов. Shell-тесты отдельно доказывают отсутствие
   eager-разметки.
5. Добавить структурный performance-гейт на публичный GET для синтетической
   конфигурации размера #1471. Он проверяет размер и число тегов, а не
   нестабильное wall-clock время.

Публичные тесты среза B:

- таблица всех поддерживаемых `data-id` доказывает `tree node → HTTP 200 →
  root с тем же id`; список узлов берётся из реально отрендеренного sidebar,
  чтобы новый вид объекта нельзя было добавить только в одну сторону;
- каждый fragment проходит проверки уникальности DOM id, сбалансированных и
  невложенных `<form>`, сохранения неизвестных типов и безопасного HTML-
  экранирования;
- browser/Node-тесты проверяют hydration главной страницы и макета после
  динамической вставки, `Ctrl+S`, deep-link `?select=...`, retry и redirect на
  login;
- на fixture 118+30 объектов по восемь реквизитов начальный ответ не превышает
  2 МБ и 5000 `<option>`, содержит все 148 узлов и ноль field-editor форм.
  Эти бюджеты оставляют запас относительно измеренных 22,1 МБ/188 316, но
  ловят возврат квадратичного eager-рендера;
- запрос одной панели fixture остаётся ограничен данными выбранного объекта;
  добавление реквизитов в непосещённые объекты не меняет размер этого ответа,
  кроме общих списков имён сущностей/перечислений.

Каждый срез заканчивается `go test ./internal/launcher`. Если Node недоступен,
Go-wrapper browser-теста обязан явно пропустить только Node-сценарий, а HTTP и
структурные тесты остаются обязательными. Полный контроль перед завершением:
`go test ./...` и `go build ./...`.

## Совместимость и миграция

- Миграции данных и конфигурации не требуются.
- Все существующие POST URL, имена form-полей, DOM id внутри панели и
  `data-id` дерева сохраняются. Это позволяет оставить обработчики сохранения,
  ссылки `?select=...`, тесты round-trip и внешние закладки без адаптера.
- Конструктор уже зависит от JavaScript для выбора панелей, AJAX-save, Monaco и
  drag-and-drop; новый endpoint не вводит новый поддерживаемый no-JS режим.
- Старые бинарь и конфигурации совместимы в обе стороны, потому что endpoint
  является только серверной частью UI текущей версии и не хранится в проекте.
- Срез A допускает смешанный режим: сущности lazy, остальные панели eager.
  Это временное, но полностью рабочее состояние между PR.

## Риски и защита

| Риск | Защита |
|---|---|
| Потеря несохранённых правок при переключении | Не удалять и не перерендеривать загруженную панель; тест `A → B → A` на изменённом input и активной вкладке |
| Поздний ответ активирует старый узел | Отдельный current-selection token; вставка в кэш разрешена, активация только при совпадении текущего id |
| Двойная инициализация обработчиков | Один `cfgHydratePanel(root)`, idempotency marker на локальных виджетах, глобальные listeners регистрируются только один раз |
| Страница входа попадает внутрь панели | Проверять `response.redirected`, конечный URL, status и content type; при auth-loss навигировать окно |
| Query string выбирает произвольный шаблон или отражается как HTML | Allowlist префиксов + точный поиск модели; сервер сам формирует root id через `html/template` |
| Новый вид узла снова станет eager или не получит endpoint | Контрактная матрица строится из sidebar `data-id` и сравнивается с resolver |
| Нагрузка сервера от повторной загрузки проекта | Single-flight и кэш на странице. Профилировать `loadCfgData`; серверный partial-loader выносить отдельно только при доказанном bottleneck, чтобы не получить две модели конфигурации |
| DOM растёт после обхода всех объектов | Принято ради несохранённых правок; верхняя граница не хуже текущей страницы. Эвикция требует отдельного dirty-state UX и не входит в #1471 |

## Откат

Схема и данные не меняются. Срез A откатывается возвратом eager-вызовов
`entity-detail` и синхронной ветки `selItem`; endpoint после отката клиента
можно удалить отдельно. Срез B откатывается по видам панелей в обратном порядке.
Во время отката нельзя менять POST-контракты сохранения или удалять
пользовательские файлы: достаточно вернуть серверный рендер деталей в
`tab-tree`.

## Критерии завершения

- Оба PR-среза влиты; начальная вкладка не содержит eager detail-панелей ни
  одного вида.
- Синтетический масштабный гейт #1471 проходит бюджеты 2 МБ/5000 options и
  структурный запрет field-editor форм в первом ответе.
- Любой sidebar node либо ведёт на отдельную страницу, либо разрешается в один
  безопасный fragment с совпадающим id; молчаливых пустых панелей нет.
- Быстрые клики, retry, auth-loss, deep-link и сохранение динамической формы
  покрыты тестами публичных HTTP/DOM-точек.
