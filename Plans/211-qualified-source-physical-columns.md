## Подтверждённый дефект и инвентаризация границ

В `internal/query/query.go` предскан `sourceContext` уже различает SELECT-scope,
квалификаторы, производные источники и локальное затенение. Но
`sourcePhysicalColumns` сохраняет только поля, чья SQL-колонка отличается от
логического имени: прежде всего ссылки с `_id`. Для обычного bool карта не
содержит запись. `joinedSourceColumn` возвращает один и тот же `false` при
неизвестном поле и при известном поле без переименования. В ветке `prevDot`
транслятора после этого остаётся fallback к `tr.colMap[lower]` главного источника.
Он превращает `М.МенеджерКонсультант` в `м.менеджерконсультант_id`, хотя у М
булева колонка `менеджерконсультант`. `qualifiedSourceColumn` в
`select_state.go` обслуживает отдельную границу коррелированного главного источника
и не устраняет эту локальную коллизию.

| Граница текущего кода | Изменение или сохраняемый контракт |
|---|---|
| `internal/query/query.go`: `sourceScope`, `sourcePhysicalColumns`, предскан источников, `joinedSourceColumn`, ветка `prevDot` | Различать известное поле с тождественным именем, известное переименование и отсутствие доказанного разрешения; прекратить заимствование чужой колонки |
| `internal/query/column_sources.go`: `columnSourceAt`, `columnTypeAt` | Использовать существующую идентичность источника и знание типа, сохранить неоднозначность и локальное затенение; не вводить независимый поиск по имени поля |
| `internal/query/select_state.go`: `qualifiedSourceColumn`, состояние SELECT | Согласовать физическое разрешение с текущим владельцем, корреляцией и UNION, не переносить состояние соседней ветви |
| `query.go`: `isDerivedColumnAt`, `derivedColumnAt`, `refAttrColumnForPrevQualifier`, `findRefDimAt`, `findJoinedSource` | Сохранить приоритет экспортированной проекции и отдельного пути навигации; прямое `А.Поле` не должно перехватывать `А.Ссылка.Реквизит` |
| `internal/metadata`: `ColumnName` | Единственный существующий контракт физического имени поля; схема и хранение не меняются |
| `query.go`: фильтры источников, `assertRowFiltersApplied`; `joined_ref_security_matrix_test.go` | Не обходить read/RLS и не менять размещение фильтров у LEFT JOIN |
| `internal/cli/query.go`: `runQuery` | Публичная приёмка через загрузку проекта, Compile и Run; CLI сам по себе не является проверкой пользовательских HTTP-прав |
| `column_sources*_matrix_test.go`, `joined_register_columns_matrix_test.go`, `joined_ref_*_matrix_test.go`, `source_columns_matrix_test.go` | Сохранить приёмку #2097/#1926/#1459 вместе с новой регрессией |

## Синтаксис / YAML и наблюдаемая семантика

Новый синтаксис не нужен. Минимальные метаданные:

```yaml
# catalogs/Сотрудники.yaml
name: Сотрудники
fields:
  - name: Наименование
    type: string
---
# catalogs/Мастера.yaml
name: Мастера
fields:
  - name: Наименование
    type: string
  - name: МенеджерКонсультант
    type: bool
---
# documents/Заявка.yaml
name: Заявка
fields:
  - name: Номер
    type: string
  - name: Мастер
    type: reference:Мастера
  - name: МенеджерКонсультант
    type: reference:Сотрудники
```

Здесь три YAML-документа сохраняются в три указанных файла. Создать сотрудника,
двух мастеров с флагами true/false и три заявки: номера `yes`/`no` с соответствующим
мастером, `missing` с пустой ссылкой Мастер. В каждой заявке одноимённый
МенеджерКонсультант ссылается на сотрудника. Проверять имена, значения, число и
кратность строк, не только отсутствие SQL-ошибки.

```text
ВЫБРАТЬ З.Номер КАК Номер, М.МенеджерКонсультант КАК Флаг
ИЗ Документ.Заявка КАК З
ЛЕВОЕ СОЕДИНЕНИЕ Справочник.Мастера КАК М ПО М.Ссылка = З.Мастер
```

| Вариант запроса | Результат после исправления |
|---|---|
| Базовая проекция | `yes → true`, `no → false`, `missing → NULL` |
| Дополнить `ГДЕ М.МенеджерКонсультант = ИСТИНА` | Только `yes → true` |
| Дополнить `ГДЕ М.МенеджерКонсультант = ЛОЖЬ` | Только `no → false`; отсутствие строки JOIN не равно false |
| Дополнить ON условием `И М.МенеджерКонсультант = ИСТИНА` | `yes → true`, `no → NULL`, `missing → NULL`; LEFT JOIN не превращается в INNER JOIN |
| Поменять источники местами: Мастера М LEFT JOIN Заявка З ON З.Мастер = М.Ссылка | Две строки `yes → true`, `no → false` при тех же данных |

Дополнительно отдельная fixture меняет **типы одноимённых полей**: у главного
источника bool/строка/число, у присоединённого reference. Проекция самой ссылки
сохраняет существующее представление результата, а сравнение с UUID и
`А.Ссылка.Реквизит` подтверждают выбор собственной `_id`-колонки. Это другая
ориентация коллизии типов, отличная от перестановки FROM/JOIN в последней строке.

Инварианты разрешения:

1. Для доказанного обычного `квалификатор.поле` имя SQL берётся только у его
   владельца и через `metadata.ColumnName`, включая тождественное отображение.
   Наличие обычного поля — положительный ответ resolver, а не повод искать его
   одноимённую ссылку у главного источника.
2. Поиск следует существующим SELECT-scope и идентичности источника. Локальный
   квалификатор останавливает поиск во внешнем SELECT даже при отсутствующем поле.
   Повторяющиеся источники нельзя слить по одинаковым метаданным; соседний UNION
   не поставляет тип, колонку или навигационный JOIN.
3. Неизвестный квалификатор, отсутствующее поле или неоднозначное происхождение
   не получают чужой `_id`, тип или auto-JOIN. Сохраняется существующее безопасное
   необогащённое имя/контролируемая ошибка; это не обещание нового валидатора всех
   неизвестных полей. Для отрицательных тестов допустим прежний отказ Compile
   либо СУБД, но недопустимо успешное чтение чужой колонки.
4. Производный источник экспортирует свою существующую проекцию, а VT — свои
   логические имена. Не добавлять к ним `_id` по метаданным физической таблицы.
   Сохранить поддержанные `SELECT *`, явные aliases, вложенные и коррелированные
   SELECT, одношаговую навигацию и стандартные поля.
5. Изменяется только неверный выбор физической колонки. Правила NULL/пустого
   текста, IN, CAST, масок, read/RLS и выходных ключей остаются текущими.
   Bool присоединённого источника не получает тип одноимённой reference/number
   главного; обычная строка не получает чужой числовой CAST.

## Изменения в коде и последовательность PR-срезов

**Срез A — конечное исправление #2143 в существующем resolver (2–3 дня).**
Расширить существующую физическую карту обычных источников до положительного
описания известных полей, включая `поле → поле`, либо вернуть из того же пути
различимый статус известного владельца/поля. Конкретная приватная сигнатура
выбирается по свежему коду; обязательны все инварианты выше. Использовать
существующий sourceContext/columnSourceAt для владения, не создавать второй
предскан, реестр типов или поиск во всех Entities по одному имени поля.
В `prevDot` прекратить fallback к главному colMap для принадлежащего другому
источнику поля, включая неизвестное поле локально известного квалификатора.
Не ломать отдельные ветки derived-проекции, VT, системных колонок и навигации.

В этот же PR входят обе ориентации коллизии, projection/WHERE/ON, отсутствие
строки JOIN, shadowing/корреляция/UNION и обязательные read/RLS-контроли.
Проверки безопасности не откладываются на следующий срез. Новый CLI-тест в
`internal/cli` и matrix-тесты в `internal/query` должны воспроизвести исходный
дефект на baseline и проходить после правки на SQLite/живом PostgreSQL.
Продуктовый код вне указанной границы менять лишь при доказанной необходимости;
расширение предмета плана требует отдельного решения.

**Срез B — приёмка потребителей и документация (1–1,5 дня после A).**
Зафиксировать исправленный запрос через публичный `Новый Запрос` в модуле
(`procrun`) и через существующий HTTP-путь выполнения отчёта с реальным субъектом
доступа. Использовать ту же синтетическую конфигурацию, выполнить `onebase check`
со статическим запросом модуля. Проверить фактические строки и сохранение запрета
чтения/строковых фильтров. Описать исправление физического имени в DEVELOPER и
релизной заметке согласно формату проекта, без изменения семантики результата.
Срез B не вводит дополнительного resolver и не расширяет грамматику. Если
интеграционная приёмка выявит обход read/RLS, поставка остатка блокируется,
исправление проходит самостоятельный REVIEW и повтор обеих матриц.

Владелец конечных срезов — #2143. План не создаёт новые задачи автоматически
и не меняет метки/владение #1385, #1183, #1926, #2247/#2248. После merge план
передаётся штатным `Plan-Issue`/`Plan-Path` handoff в FIX; перед каждым срезом
повторно проверяются свежий main и отсутствие параллельной работы. Каждый PR
проходит собственные REVIEW, CI и человеческий ship. Закрытие исходной issue
допустимо только после полной приёмки, не слиянием этого плана.

## Тесты и verification

Срез A: публичный CLI `query --json --sql --limit 0`, `query.Compile → query.Run`
на БД, созданной через публичные Migrate/Upsert. `dbtest.ForEachDialect`
исполняет одинаковые данные и ожидания на SQLite/PostgreSQL. Сравнивать набор
идентификаторов, кратность, true/false/NULL и фактический reference, дополнительно
проверять SQL-имя. SQLite может представить bool числом 0/1: допустима только
явная нормализация bool/0/1 в тесте, UUID или произвольный непустой текст
недопустимы. Не вызывать приватный resolver как единственную приёмку.

Отрицательные и совместимые контроли среза A: разные типы одноимённых полей;
оба порядка источников; переименованные/разнорегистровые aliases; alias,
совпадающий с именем другого реквизита; повторная таблица; локальное затенение
внешнего alias с отсутствующим полем; разрешённая корреляция; соседний UNION;
производная проекция с явным именем и `*`; обычные регистры и VT из #1926;
стандартные колонки и одношаговая навигация из #1459. Неизвестный владелец/поле
не должен компилироваться в заведомо существующую чужую колонку и читать её.

Read/RLS: через публичный Compile с существующими опциями разрешений и
RowFilters проверить запрещённый источник, фильтр, исключающий одного мастера,
сохранение допустимых строк главной таблицы при LEFT JOIN согласно текущему
контракту, отсутствие скрытого значения/представления и контроля через ON.
Срез B повторяет это через HTTP-отчёт под ограниченным пользователем;
административный headless CLI не заменяет этот тест. Ожидания существующей
матрицы прав сохраняются, новое поведение безопасности не изобретается.

Для B добавить `procrun` тестового модуля и HTTP-приёмку отчёта; полный набор

## Хранилище / SQL, совместимость, риски и откат

DDL, миграция данных, индексы, зависимости и generated artifacts не меняются.
Имена SQL существующих исправных запросов и значения хранящихся полей сохраняются;
исправляется ошибочная чужая `_id`-колонка. Опасно трактовать отсутствие записи
в частичной карте как отсутствие поля, затереть экспорт derived/VT или изменить
порядок RLS-фильтрации. Эти риски закрываются положительным знанием владельца
и отрицательными публичными контролями до поставки A.

Откат A — revert его компиляторного изменения с повтором матриц совместимости;
дефект #2143 при этом вернётся, что следует явно сообщить. Откат B — возврат его
интеграционной/документирующей дельты; не удалять сохранённую регрессию A.
Откат БД не требуется. Работать только с изолированными синтетическими БД.

## Критерии завершения и эстимейт

- Обе ориентации коллизии разрешаются по собственному источнику; projection,
  WHERE и ON возвращают точные значения и кратность, включая отсутствие JOIN.
- Scoped fallback не заимствует физическое имя, тип или auto-JOIN у чужой
  таблицы; существующие derived/VT/navigation/read/RLS-контракты сохранены.
- Новая регрессия доказанно падает на baseline, после исправления обе БД
  проходят полную предметную матрицу и приёмку потребителей.
- У каждого среза есть независимые REVIEW и обязательный CI; ship ставит
  человек, merge выполняется штатно. Старые зелёные проверки иных PR не заменяют
  приёмку нового SHA. Исходная issue закрывается после выполнения всего объёма.

Оценка: A — 2–3 дня, B — 1–1,5 дня; всего 3–4,5 дня без ожидания REVIEW/CI/ship.
Проверки самого plan-PR: `go run ./tools/plannum`, существование локальных ссылок,
`git diff --check`, инвентаризация номеров main и всех открытых plan-PR перед push.
