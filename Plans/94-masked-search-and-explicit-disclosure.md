Оператор должен найти заявку по названному клиентом телефону, продолжая видеть
маску в выдаче. Затем он может отдельно раскрыть нужный реквизит с причиной.
Право искать уже раскрывает факт существования доступной записи: это осознанная
новая возможность роли, а не эквивалент обычного `read` или отсутствия утечки.

План фиксирует ограниченный первый контракт: точное совпадение по одному или
нескольким разрешённым строковым полям одного документа/справочника. Поиск по
части телефона, произвольный `ПОДОБНО`, регистры и расширение общего SQL-гейта
отложены. Поэтому исходный запрос формы с тремя `ПОДОБНО` потребует адаптации
на полный телефон и новый явный поиск; он не начнёт работать автоматически.
Это ограничение должно быть видно при ревью плана до реализации.

Это проект поведения, а не описание уже поставленной возможности. Продуктовый

## Наблюдаемая семантика и инварианты

| Действие | Требования | Результат |
|---|---|---|
| Обычное чтение, запрос, экспорт | Существующие read/RLS/field_access | Прежняя маска и прежние запреты |
| Явный защищённый поиск | Аутентифицированный пользователь, read + search_masked, разрешение каждого поля, квота, успешный аудит | До 20 доступных строк с маской |
| Обычный DSL `Объект.Телефон` | Существующая полевая политика, включая роль с disclose | Прежнее маскированное значение |
| Явное раскрытие одного поля | read + disclose, доступ к строке, непустая причина, успешный аудит | Одно полное значение |
| Аудит или квота недоступны | Любые новые привилегированные действия | Ошибка без строк/значений; никакого fallback |

1. `read`, `write`, `disclose` не подразумевают `search_masked`.
   Новый поиск не выдаёт право изменять поле или читать его без маски.
2. Строковый доступ применяется в SQL **до LIMIT**, в одной и той же операции
   чтения. Недоступная строка не участвует ни в выдаче, ни в признаке усечения.
3. Маска применяется до сериализации, построения представления ссылки и передачи
   строки в DSL. Политики `hide`, `mask_*`, сочетания нескольких ролей и
   `MaskAdmin` сохраняют текущий смысл. `hide` для нового поиска запрещён.
4. Источник — только шапка одного catalog/document. ТЧ, регистры, виртуальные
   таблицы, joins, разыменования, подзапросы, UNION, агрегаты, сортировка по ПДн,
   сравнение двух полей и вычисляемые предикаты здесь не разрешаются.
5. Поиск возвращает таблицу: `Ссылка` и явно запрошенные простые поля того же
   объекта, каждое по текущей политике. Нет COUNT, общего числа совпадений,
   OFFSET, произвольной сортировки, неограниченного выгружания или raw-строк.
   Порядок — по id; при чтении 21-й доступной строки ответ даёт только
   `Усечено=true` и первые 20. Этот бит тоже является разрешённым раскрытием.
6. Искомое значение не попадает в аудит, URL, SQL-ошибку, трассировку или лог.
   Параметры передаются отдельно от SQL. Ошибка показывает код и имя поля,
   но не значение или причину другого пользователя.
7. Отдельное раскрытие не меняет объект, кэш, обычный Get или права на будущие
   чтения. Действие всегда относится к конкретным kind/entity/id/field.
8. Получив сырое значение явным раскрытием, доверенный прикладной модуль может
   использовать или вывести его. Здесь нет обещания отслеживать дальнейший
   поток данных: разрешение disclose и проверка прикладного модуля обязательны.

## Синтаксис / YAML

Предлагаемый новый opt-in, добавляемый только после merge реализации:

```yaml
permissions:
  documents:
    А_Заявка: [read, search_masked, disclose]
  field_access:
    documents:
      А_Заявка:
        ТелефонМобильный:
          read: mask_tail
          keep: 4
          search: exact
        ТелефонДомашний:
          read: mask_all
          search: exact
```

`search` отсутствует → `deny`; допустимы только `deny|exact`. Новое разрешение
требует одновременно object-level `search_masked` и `search: exact` для каждого
поля. В одной роли должны быть `read`, `search_masked` и полевая декларация;
объединение несвязанных ролей не создаёт grant. Явное `search: deny` любой
применимой роли перекрывает grant, отсутствие ключа другой роли его не отменяет.
Для администратора новый путь также требует явного opt-in; отсутствие auth/user
не становится системным разрешением. Проверка этого пути не ограничивается
`User.Has`, который сейчас безусловно разрешает операции администратору.

Новый публичный сервис получает типизированный request:
`kind, entity, поля[1..3], значение, колонки[1..10], reason_code`.
Поля объединяются только OR, каждое сравнивается с одним значением через `=`.
Значение — непустая строка до 256 UTF-8 байт; без trim, нечувствительного
сравнения, приведения регистра или нормализации телефона внутри платформы.
Символы `%` и `_` — обычные символы. Нормализация данных/ввода — ответственность
конфигурации. Пустые значения, неизвестные имена и другие типы отклоняются.
`reason_code` в V1 равен `incoming_call` или `customer_request`; свободного
текста поиска нет, чтобы телефон случайно не оказался в причине аудита.

Предлагаемый DSL-фасад (имена становятся контрактом среза C):

```text
Результат = ПоискЗащищенныхПолей("document", "А_Заявка",
    ПоляТелефона, ПолныйТелефон, КолонкиВыдачи, "incoming_call");
// Результат.Строки — ТаблицаЗначений с маской, Результат.Усечено — булево.
Телефон = РаскрытьЗначение(СсылкаЗаявки, "ТелефонМобильный", "Проверка звонка");
```

Явное раскрытие не принимает произвольный map/созданный объект: только сохранённую
типизированную ссылку справочника/документа и имя существующего поля шапки.
Пустая ссылка, неизвестное поле, неподдержанный тип источника — ошибка.
Причина после trim — 1..512 UTF-8 байт; вызывающий не должен включать туда ПДн.
Для открытого немаскированного поля новый явный метод тоже проверяет disclose и
пишет аудит: поведение метода не зависит от текущей маски.

UI использует POST с CSRF на `/ui/{kind}/{entity}/masked-search`; REST —
POST `/api/v2/{catalog|document}/{name}/masked-search` с обычной авторизацией
токена. DSL вызывает тот же сервис без loopback HTTP. UI-поиск вызывается явно
кнопкой/Enter, не на каждый набранный символ. Ошибки: 400 — контракт, 403 —
права, 429 — квота с Retry-After, 503 — аудит/защитное хранилище недоступны.
DSL получает соответствующее исключение; ошибка никогда не заменяется пустой
таблицей. Существующие UI/REST способы раскрытия остаются совместимыми.

Предложение общего API: пакет `internal/protecteddata` с
`Search(ctx, SearchRequest) (SearchResult, error)` и
`Disclose(ctx, DisclosureRequest) (any, error)` на узких интерфейсах metadata,
policy, row-access, storage и audit. Пакет не импортирует UI/API. При реализации
сначала проверить направление импортов; интерфейс передаёт типизированные
параметры, а не callback «выполнить произвольный SQL с правами».

Поиск компилирует только собственный шаблон с явными колонками и уникальными
алиасами, используя `metadata.TableName/ColumnName`, текущий dialect и общий
построитель row filters. Маскирование доказанной проекции остаётся общим с
QueryMaskPlan; право выполнить предикат остаётся внутри Search, а не в
общедоступном bool `allowMasked`. Прямой вызов Compile/Run или обычного Запрос
не получает исключение. Исходный запрос формы передаётся новому фасаду данными,
без автоматического распознавания и переписывания произвольного DSL/SQL.

Связанный [PR #2338](https://github.com/ivanarama/onebase/pull/2338) защищает
запись заглушек маски. Его предложение сырого DSL-чтения явно отложено до
решения по #2242. Не переносить его реализацию или ветку в этот план;
после merge перепроверить совместимость записи и новых раскрытых значений.
Планы [88](88-field-level-masking-pii.md) и [79](79-row-level-access.md)
остаются основанием маскирования и доступа к строкам.

## Хранилище / SQL

Нужна новая служебная таблица `_pii_search_budget`: составной ключ
`(user_id, window_kind, window_start)`, целочисленный `used`. Два UTC-окна:
20 попыток в минуту и 500 в календарные сутки на пользователя **в одной базе**,
суммарно по объектам, HTTP/DSL и процессам. Это ограничение попыток, а не
доказательство невозможности перебора; право выдаёт администратор осознанно.
V1 не даёт конфигурационного способа увеличить лимит или обходить его токеном.
Новая таблица входит в service schema, dbtest и inventory служебных таблиц;
прикладные метаданные, обмен и обычный поиск её не адресуют.

После проверки auth/контракта сервис одной короткой самостоятельной транзакцией
атомарно резервирует оба счётчика и пишет `_audit` с action=`masked_search`,
именем объекта, именами полей, reason_code, actor и ID запроса. Без значения,
SQL-текста, хеша телефона, числа совпадений или найденных id. Логирование
безусловно, независимо от выключения обычного журнала. Отказ записи или commit
откатывает оба счётчика и запрещает выполнение поиска. При исчерпанной квоте
ответ 429 не выполняет поиск. Авторизационный отказ не раскрывает наличие строк.

Зарезервированная попытка остаётся потраченной при SQL-ошибке, отмене HTTP,
потерянном ответе и повторной отправке; она не возвращается через rollback
прикладной транзакции. Внутри активной DSL-транзакции новые Search/Disclose
отказывают **до** чтения/квоты, чтобы не получить SQLite deadlock и исчезающий
после rollback аудит. UI/REST disclose переводятся на общий сервис с сохранением
прежнего внешнего контракта. Доступная строка и её значение читаются в одном
согласованном снимке; аудит раскрытия успешно коммитится до выдачи этого значения.
После commit повторно читать поле и выдавать другое значение запрещено.

Окна считаются по времени БД; параллельные инкременты условные, с проверкой
количества изменённых строк. Не держать SQL-курсор между аудитом и commit.
Удалять только окна старше двух суток, небольшими порциями вне критического
пути; очистка не может сбросить действующую квоту. Проверить backup/restore:
действующие окна сохраняются, общий аудит также; пользователь не может получить
новую квоту обычным перезапуском процесса. Административный restore старой базы
может вернуть старое состояние квот — это явное операционное ограничение.

## Последовательность небольших PR-срезов и публичные тесты

Каждый срез — отдельный PR, собственный REVIEW и человеческий ship.
Срезы B/C не включаются частично как незаконченный поиск.

| Срез | Результат и оценка | Публичная приёмка |
|---|---|---|
| A | Opt-in модель/валидация, 2–3 дня; runtime поиска ещё отсутствует | Загрузить YAML штатным loader; onebase check принимает exact, отклоняет неверные типы/источники/значения; round-trip роли через HTTP конфигуратора сохраняет ключ и прежние права |
| B | Общий сервис раскрытия и DSL РаскрытьЗначение, 3–4 дня | Через UI POST, REST field endpoint и исполняемый DSL-модуль: read+disclose+reason выдаёт одно значение и запись аудита; без каждого условия отказ; audit failure/активная транзакция — исключение без значения; обычный Get остаётся маской |
| C | Цельный защищённый поиск: квота, audit, сервис, UI/REST/DSL входы, 5–7 дней | Вызвать новый POST и DSL-функцию под настоящей ролью; точный телефон находит разрешённую строку, её поле маскировано; та же запись за RLS не видна; 21 строка даёт только 20+Усечено; отказ аудита/квоты не выполняет запрос |
| D | Прикладной пример, диагностика и документация, 1–2 дня | Запустить тестовую конфигурацию через onebase run/check/test; оператор вводит полный телефон, видит маску, отдельно раскрывает, без причины видит понятный отказ |

В C нужны dbtest.ForEachDialect на SQLite и PostgreSQL через публичные HTTP/DSL
входы и два независимых подключения: конкурентные 21 попытка не выдают больше
20 ответов; две одновременные операции на границе дневной квоты; отказ аудита
не оставляет частичный budget; рестарт сохраняет расход. Для PG обязательна
проверка rollback после ошибки аудита, а для SQLite — отсутствие ожидания
самого себя при активной прикладной транзакции.

Для каждого входа отрицательная матрица: нет auth, только read, только disclose,
только search_masked без field grant, отсутствующий read в grant-роли,
конфликтующий deny другой роли, admin без opt-in, другой объект/поле, hide,
пустой/длинный ввод, `%`/`_`, кириллица и длинные SQL-имена. Проверять и ошибку,
и отсутствие raw-значений в ответе/журнале/логе. Обычный DSL Get, Find,
`Новый Запрос`, отчёт/REST/composition, экспорт, подзапрос/алиас/UNION/JOIN,
агрегат и регистр продолжают прежний запрет: новый grant не разрешает обход.

Тесты обязаны идти через зарегистрированные маршруты или реально исполняемый
модуль с новым глобалом. Тест приватного predicate не заменяет эту приёмку.
Существующие TestUI_DiscloseField_FailClosedWhenAuditFails, API disclose,
TestQueryMaskPlan и DSL field-mask тесты остаются регрессионной базой.

## Совместимость и миграция

Старые роли и конфигурации не получают новых возможностей. Автоматически
копировать disclose в search_masked или проставлять search: exact запрещено.
Для включения администратор обновляет бинарь/служебную схему, явно правит роль,
проверяет onebase check, адаптирует форму на новый поиск и пробует ограниченную
учётку. Первым включается тестовый объект на синтетических данных. Вернуть роль
к прежнему состоянию можно удалением grant; это не стирает историю аудита.

Срез A обновляет парсер/схемы/линтер одновременно. Срезы B–D обновляют
DEVELOPER.md, docs/dsl-reference.md, справку/langref и ai-guide в местах новых
публичных функций; срез D добавляет docs/features.md. CHANGELOG предупреждает
о новых явных разрешениях, ограничении полного телефона, квотах и запрете
вызова внутри транзакции. Документация не обещает паритет старого ПОДОБНО.
Новая таблица добавочная, без преобразования пользовательских данных.
Downgrade поддерживается только после удаления новых ключей/вызовов из
конфигурации; старый бинарь не считается понимающим search-политику.

## Verification

1. На отдельной SQLite-базе и затем PostgreSQL загрузить синтетические записи:
   совпадающий телефон в доступной/недоступной строке, различия формата и масок.
2. Роль с read+disclose без search grant получает 403/исключение; обычное чтение
   возвращает маску. После явного grant точный поиск отдаёт только разрешённую
   строку; номер в SQL-логе, HTTP URL, теле ошибки и аудите отсутствует.
3. Отдельное раскрытие с причиной отдаёт телефон; повторный обычный Get снова
   возвращает маску. Удалить право или сделать аудит недоступным: выдачи нет.
4. Исчерпать 20 попыток через HTTP и продолжить через DSL/другой процесс:
   общий 429. Перезапуск не помогает. Проверить суточную границу через тестовые
   часы БД/фикстуру, не ждать сутки и не менять системные часы оператора.
5. Запустить go build ./..., тесты auth/access/query/storage/ui/api/configcheck/
   launcher и PG-интеграцию; новый пример проверить onebase check и onebase test.
   Обязательные CI и независимое ревью каждого среза сохраняются.

При подготовке этого документа выполнены только проверки плана/ссылок.
Описанные продуктовые тесты — критерии будущих срезов, не заявления о прогоне.

## Риски, откат, критерии завершения и эстимейт

Основной риск — оракул существования и автоматизированный перебор. Защита:
явный field grant, exact, общий durable budget, RLS до LIMIT, аудит до поиска.
Она не исключает обход через множество легально созданных учёток или уже
существующие каналы поиска; их аудит не является разрешением расширять этот
срез. Политика и аудит выдачи учёток остаются у администратора базы.

Другие риски: утрата ключей редактором ролей, различия collation двух СУБД,
потеря аудита при DSL rollback, deadlock SQLite, маска на неверном алиасе,
избыточный SQL-лог параметров, конкуренция квот и раскрытие сырого значения
самим прикладным модулем. Отдельные приёмочные проверки выше закрывают каждый
технический риск; произвольный SQL не получает «trusted» флаг.

Откат: отключить grant и вызовы в конфигурации, вернуть предыдущий бинарь после
удаления новых YAML-ключей. Служебную таблицу и аудит не удалять автоматически.
Никакое аварийное отключение аудита не включает выдачу данных. До разрешения
проблемы оператор получает явную ошибку и использует существующее отдельное
раскрытие уже найденной записи, если оно доступно.

Готовность: все четыре среза влиты последовательно, пройдена матрица публичных
входов на обеих СУБД, тестовый оператор проходит Verification, доказаны сохранение
маски/аудита и отсутствие автоматического расширения disclose. Закрытие исходной
issue — только реализацией согласованного объёма с явным указанием ограничений;
слияние этого plan PR её не закрывает.

Оценка: **11–16 рабочих дней**, включая публичные тесты и документацию, без
времени REVIEW/решения ship. Поиск по фрагменту/ПОДОБНО, поиск в регистрах,
разрешение произвольных запросов и отслеживание дальнейшего распространения
раскрытого значения требуют отдельного решения/плана.
