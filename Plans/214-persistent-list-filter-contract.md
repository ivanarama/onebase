## Синтаксис / YAML и наблюдаемая семантика

Действующий формат сохраняется:

```yaml
schema: onebase.form/v1
form:
  name: ФормаСписка
  kind: list
  entity: Задача
  filter:
    - field: Выполнена
      value: "false"
      removable: true
      label: {ru: "Только невыполненные"}
```

`filter` — правило интерфейса. Оно не заменяет `row_access`, не закрывает
прямое чтение карточки и не начинает действовать на REST v2 или отчёты.
`roles`, административное исключение и отсутствие пользователя для
`@ТекущийПользователь` сохраняют текущие правила применимости. Неснимаемое
условие нельзя отключить адресом; `lf_off` относится только к `removable`.

### Валидация

`onebase check` и `check --lint` проверяют все условия независимо от роли,
текущего пользователя и будущего `lf_off`. Ошибка содержит исходный файл формы,
номер условия и проблемный `field`/`op`; это ошибка конфигурации, не warning.

- Поле разрешается по метаданным, включая существующие системные поля и их
  алиасы. Одно разыменование допустимо только через ссылочное поле в известную
  сущность и существующий конечный реквизит. Пустой сегмент, неизвестный хвост
  и второе разыменование отклоняются. Имена сравнивать действующим способом,
  не вводить новый casefold всей конфигурации.
- Пустой `op` — `eq`. Сохраняются фактически работающие скалярные операции
  `eq`, `ne`, `empty`, `not_empty`; комментарий «пока eq» не является основанием
  сломать рабочий `ne`. `in`/`not_in` требуют списка, которого нынешний
  `FormListCondition.Value string` не задаёт: не придумывать CSV/JSON-разбор
  строки, а диагностировать неверную форму значения. Неизвестная операция —
  ошибка. Для `empty`/`not_empty` значение не интерпретируется как сравнение.
- Литерал проверяется по типу конечного поля теми же правилами, что при
  построении предиката: decimal без float-потерь, существующие bool/UUID/date
  преобразования и пустые значения. Не делать невалидный bool равным false.
- `@ТекущийПользователь` остаётся символическим значением до привязки к
  запросу; статическая проверка не требует пользователя. Проверяются допустимый
  тип поля и сам символ, а при выполнении — действующее правило применимости.
- Query-ветка сохраняет нынешние параметры и executable-check. Непустые
  `query` и `field`/неприменимые `op`/непустой `value` вместе — неоднозначная
  конфигурация; выдавать ошибку вместо зависимости от порядка ветвей кода.

### Уже загруженная ошибочная конфигурация

Применимость (`roles`, пользователь, removable) вычисляется отдельно от ошибки
активного условия. Нельзя представить «ошибку» тем же `ok=false`, что означает
«правило к этому пользователю не относится».

При невалидном активном field-условии список возвращает HTTP 200 с нулём
строк/нулевым счётчиком и безопасным уведомлением «Отбор списка настроен
некорректно». Никакое активное ошибочное условие не выбрасывается для расширения
выдачи. Прямой Excel-export возвращает диагностическую HTTP 400 до записи
workbook, без SQL и частичной выгрузки. Это явный контракт плана; не считать
успешно скачанный пустой файл сообщением об ошибке.

Отказ RBAC/RLS остаётся 403, независимая ошибка storage не маскируется как
ошибка конфигурации. Существующий fail-closed query-filter и его собственные
отказы сохраняются; этот срез не переписывает весь механизм query-ошибок.
Полные технические причины с путём формы/индексом условия доступны в журнале;
пользовательский ответ не содержит SQL и значений чужих реквизитов.

### False, NULL и иерархия

Во втором срезе `eq false` для булева поля означает `false OR NULL`, как
панель «Нет». `eq true` — только true. Общая семантика SQL NULL для других
типов и `ne` не меняется; ни RLS, ни DSL-запросы не получают новый глобальный
`COALESCE`. Правило действует и на конечный bool-реквизит разрешённой ссылки.

Отбор элементов формы отделяется от доступа. Для навигационных групп
иерархического справочника UI-условие не применяется, но исходный RLS и
маскирование остаются. Формула — `RLS AND (is_folder OR UI_form_filter)`,
а не `(RLS AND UI_form_filter) OR is_folder`. Для некорректного активного
условия результат целиком пустой, включая группы.

Активный отбор формы включает полный поиск иерархии в плоском списке тем же
путём, что `q`/`f.*` в `listSearchesWholeHierarchy`; это даёт доступ к
подходящему элементу даже при недоступном родителе. Подпись/ссылка родителя
добавляется только после существующей проверки `batchReadableLabels`.
В дереве остаются только доступные группы; закрытый RLS предок не появляется
ради пути к ребёнку. Такой ребёнок доступен через полную плоскую выдачу,
а не через раскрытие запрещённой ветки.

Индекс и порядок условий не менять: `lf_off=0` продолжает означать первое
условие. Переключение списка/плиток/дерева, страницы, родителя, загрузка детей и
Excel переносят снятые removable-условия; неизвестный индекс не отключает
другое условие. Переход вида сбрасывает страницу, но сохраняет остальные
действующие параметры стандартным `listURL`.

## Хранилище / SQL и границы изменений

Новых колонок и миграции данных нет. NULL остаётся в базе; исправляется
интерпретация UI-отбора. Не переписывать существующие записи на false.

Ввести небольшой независимый `internal/listfilter` с разрешением метаданных,
операции и типизированного значения. Он зависит от metadata и существующих
низкоуровневых преобразований, но не от UI/interpreter; не создавать цикл
импорта. Общий validator возвращает проверенное условие либо типизированную
ошибку, а не SQL. Query-ветка остаётся у своего исполнителя.

| Граница | Изменение |
|---|---|
| `internal/listfilter/` — новые resolver/validator | Единый разбор field/op/value и диагностические ошибки; явная привязка символического пользователя отдельным шагом |
| `internal/configcheck/check.go`, формы из файлов/configdb | Проверка field-условий через общий validator; SourcePath и индекс условия в диагностике, а не только проверка query |
| `internal/ui/row_access.go` | Различить inactive/valid/invalid; не терять RLS при добавлении UI-отбора и не пропускать активную ошибку |
| `internal/storage/crud.go`, `predicate.go` | Отдельное UI-поле в `ListParams` и согласованное применение в List/Count; bool-NULL и исключение групп задаются UI-предикатом, общий RLS-компилятор не меняет смысл |
| `handlers_entity.go`, `handlers_export.go`, tree-children | Передать один результат компиляции по всем маршрутам, сохранить RowFilterEvaluated; не обойти фильтр дополнительным запросом дерева |
| `templates.go`, `docs/forms.md`, `docs/features.md`, `CHANGELOG.md` | `listURL` для дерева, безопасная диагностика, семантика false/NULL/групп и предупреждение совместимости |

`RowFilter` остаётся предикатом доступа. Новое служебное UI-поле не доступно
через пользовательский REST и не разрешает клиенту прислать готовый Predicate.
Для bool false строится локальное UI-условие `Any(eq false, is null)` с
обязательными скобками при AND с RLS. Валидный список/Count/Excel должны
использовать одинаковые условия и формат аргументов на SQLite/PostgreSQL.

1. **A — #2375:** общий validator, `check`, явная runtime-ошибка и безопасные

   меняя пока false/NULL и группы. Один delivery PR закрывает только #2375.
2. **B — #2376, после A:** отделение UI-предиката, bool false/NULL,
   доступные группы/полная плоская выдача и перенос `lf_off` реальными href.
   Один согласованный PR по существующей ведомой, без второго параллельного
   изменения `row_access.go`. `Blocked-by: #2375` остаётся до принятия A.

Оба среза проходят обычные REVIEW, человеческое решение ship и CI. Ведомой
сохранять hold; после merge A сопровождающий проверяет фактический main и
заменяет зависимость на принятый предшественник/разрешает B. Plan-only PR не
закрывает ни одну исходную issue и не включает продуктовые изменения.

## Тесты

- Публичные `onebase check` и `check --lint`: неверное простое поле, хвост
  ссылки, лишнее разыменование, тип/оператор и неоднозначные query+field;
  валидные системные алиасы, пустые значения, роли и символ пользователя.
- Настоящий router, загруженная YAML-форма и обычный/административный user:
  активная ошибка даёт пустой список с диагностикой; неактивное условие не
  расширяет права; export 400 не содержит workbook или SQL. Исправленный файл
  после reload снова открывает список — cache ошибки не вечный.
- SQLite/PostgreSQL: true/false/NULL, поле добавлено к непустой таблице,
  запись через REST/DSL без bool, конечный bool ссылки, Count/полная выдача/
  Excel. После B панель «Нет» и form `eq false` дают одинаковые элементы.
- Иерархия глубины не менее трёх: подходящий/неподходящий элемент, пустая
  группа, запрещённые RLS группа/элемент и скрытая подпись родителя. Нельзя
  получить закрытую запись через OR-ветку, tree-children или export.
- Браузер нажимает фактические переключатели и «📂», раскрывает узел и
  скачивает export; проверить `lf_off`, parent, q, f.*, subsystem и пагинацию.
  Одного поиска подстроки в шаблоне для переходов недостаточно.
- Контроль неизменного REST v2/карточки/отчёта, неснимаемого условия,
  административного исключения и старых query-фильтров. Наличие фильтра
  интерфейса не становится новой политикой доступа.

## Verification, совместимость и откат

На копии рабочего проекта с тремя задачами true/false/NULL и вложенными
группами: запустить check, открыть форму оператором, снять/вернуть отбор,
переключить виды, раскрыть группу и выгрузить Excel. Сравнить с панелью «Нет»
и повторить с закрытым RLS родителем. Затем внести опечатку и неверный литерал:
check отказывает, уже загруженный активный отбор не раскрывает строки.
Повторить на обеих БД; отсутствие PostgreSQL явно назвать, не считать тестом.

Строгий check начнёт отклонять ранее пропускавшиеся ошибочные формы. После B
«Нет» включает NULL, а доступные группы перестанут исчезать из-за UI-условия.
Оба изменения описать в CHANGELOG, сохранив исключения прав. До обновления
рекомендуется проверить формы check-командой на копии проекта. Автоправки YAML
и данных не нужны. Откат кода не меняет БД; сохранить исходные формы, поскольку
откат A вернёт прежнее позднее обнаружение ошибок.
