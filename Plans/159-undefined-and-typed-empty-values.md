# План 159 — `Неопределено` и типизированные пустые значения в DSL

Дата проектирования: 2026-09-03.
Статус: 📋 **проектирование**, код не начат.
Уровень: **движок** — модель значений DSL, метаданные полей, объектные и
запросные границы, хранение и сериализация.
Заявка: [#1274](https://github.com/ivanarama/onebase/issues/1274).
Выбранный вариант: **1** — отдельное внутреннее значение `Неопределено` и
нормализация пустых реквизитов по их метаданному типу. Это именно отдельный
план, как потребовали триаж и маршрут `plan-needed`; продуктовый код в plan-PR
не входит.
Связано с: issue [#1136](https://github.com/ivanarama/onebase/issues/1136) и
реализованной в PR #1139 совместимостью «пустое числовое поле = 0»; планы
[42](42-decimal-money.md) (точные числа) и [153](153-attribute-defaults.md)
(явные значения по умолчанию при создании объекта).

## Зачем

Сейчас одно Go-значение `nil` означает сразу четыре разные вещи:

1. литерал DSL `Неопределено`, необъявленную переменную и параметр без
   значения;
2. «не найдено» у `Соответствие.Получить`, `Массив.Найти`, индексирования и
   объектных прокси;
3. SQL `NULL` у незаполненного реквизита известного типа;
4. отсутствие результата у процедуры/метода и `null` на границе JSON/XML.

После #1136 `equalOperator` и `compareOperator` вызывают
`nilAsNumericZero`: если рядом с `nil` стоит число, `nil` временно становится
`decimal.Zero`. Это починило важную 1С-идиому для реквизита ТЧ
`Если Строка.Цена = 0`, но одновременно сделало истинным
`Соответствие.Получить("нет") = 0`. Через оператор уже нельзя отличить индекс
первого найденного элемента от «не найдено» и отсутствующий ключ от
сохранённого нуля.

Локальная правка только `=` не годится. Пустое числовое поле действительно
должно вести себя как число 0, а результат отсутствующего поиска — как
`Неопределено`; без происхождения значения оператор различить их не может.
Происхождение известно раньше — метаданным поля и границе, на которой внешнее
`nil` вошло в интерпретатор. Поэтому решение состоит из двух частей, и обе
обязательны до удаления обхода #1136:

- реквизит известного типа получает каноническое пустое значение **до**
  вычисления выражения;
- семантическое `Неопределено` внутри вычислителя больше не является Go `nil`.

## Что есть сейчас

| Граница | Текущее поведение | Почему одной правки оператора мало |
|---|---|---|
| `evalExpr` / `env` | неизвестный идентификатор, объявленная без значения переменная и любой вернувший `nil` вызов дают `nil` | у значения нет признака происхождения |
| `decimal_helpers.go` | `nilAsNumericZero` подставляет 0 в `=`, `<>`, `<`, `>`, `<=`, `>=` | подстановка срабатывает и для честного «не найдено» |
| арифметика в `interpreter.go` | отдельные ветки `nil + N`, `nil - N`, `nil * N`, `nil / N`, `nil % N` поддерживают пустые числа | после типизации полей эти ветки перестанут быть способом распознавать поле |
| `formObjectThis.Get` | только поля сущности известных типов `number` и `bool` частично превращает из `nil` в `0`/`false` | скалярный `FormAttribute` с собственным `TypeRef` остаётся `nil`, строки ТЧ, writers, запросы и прямые хуки идут другими путями |
| `FormAttribute` / `ValueTable` | пустой ввод скалярного реквизита формы сохраняется как `nil`, а временный `metadata.TablePart` для `ValueTable` переносит только имя колонки и `RefEntity` | известные `TypeRef` скалярного реквизита и колонки таблицы теряются до чтения из DSL |
| `refAwareMapThis`, `tpProxy`, `catWriter`, `docWriter` | в основном возвращают сырой `nil`; `tpProxy` даже теряет метаданные ТЧ | один реквизит меняет смысл в зависимости от точки входа |
| `ConstantsRoot` | `dslvars.Common.Build` передаёт только имена констант, а `Get` возвращает `nil` для объявленной, но не установленной константы | уже известный `metadata.Constant.Type` теряется, поэтому пустая числовая константа становится общим `Неопределено` |
| `query.Result` | знает булевы, даты и ссылки; числовые колонки отдельно не перечисляет, а ссылочный rewrite живёт особым путём | у `NULL` результата DSL не знает тип числа; без общей модели можно перепутать представление `Проект` со ссылкой `Проект.Ссылка` |
| storage | форма пишет пустые number/date как SQL `NULL`; чтение сохраняет `nil` | это нормальное представление хранения, но не готовое DSL-значение |
| JSON/XML и Go API | `nil` — установленный контракт `null`/`undefined` | внутренний sentinel нельзя выпустить сюда как неизвестный Go-тип |

Отдельная ловушка — несколько продакшен-путей запускают модуль с сырым
`*runtime.Object` (`runEntityHook`), хотя рядом управляемые формы используют
метаданный `formObjectThis`. Если починить только форму, одинаковый
`Объект.Сумма` будет числом в обработчике формы и `nil` в `ПриЗаписи`.

## Выбранная модель

### 1. Внутреннее `Неопределено`

В `internal/dsl/interpreter` появляется неизменяемый закрытый тип и одно
каноническое значение, условно `undefinedValue`. Наружу экспортируются только
узкие операции `IsUndefined`, `FromHostValue` и `ToHostValue`; сам тип нельзя
конструировать и использовать как прикладное значение.

Инвариант:

- результат **каждого** DSL-выражения определён: внешний `nil` на входе в
  `evalExpr` становится `undefinedValue`;
- локальные/модульные переменные без значения и отсутствующий идентификатор
  содержат/возвращают `undefinedValue`;
- `missingNamedArg` остаётся другим sentinel. Пропущенный аргумент включает
  default параметра, явно переданное `Неопределено` — нет;
- встроенная функция, внешняя фабрика, `MethodCallable`, `This.Set`, query
  parameter, storage и публичные `Call`/`RunWithResult`/`EvalExpr` получают
  прежнее внешнее представление `nil`, а не внутренний тип;
- массивы, структуры и соответствия могут хранить внешнее `nil`: при чтении
  оно снова материализуется как `undefinedValue`;
- в текущем `Map.CallMethod` метода проверки наличия ключа нет: `Получить`
  возвращает `nil` и для отсутствующего ключа, и для сохранённого `nil`. В
  срезе C добавляется `Соответствие.СодержитКлюч` (`ContainsKey`) с регистрацией
  в `mapMethods`; он проверяет только `findIdx(key) >= 0`, не читает значение и
  поэтому различает «ключ есть со значением Неопределено» и «ключа нет».
  Метод входит в публичную документацию DSL и тестируется через исполнение
  модуля, а не прямым вызовом `Map.CallMethod`.

Так sentinel остаётся деталью вычислительного ядра. JSON `null`, XML
`undefined`, драйвер БД, HTML-шаблоны, debugger protocol и пользовательские
Go-callback'и не получают новый тип.

### 2. Каноническое пустое значение реквизита

Нормализация применяется только после успешного поиска **объявленного** поля
в `metadata.Field`. Неизвестное имя поля не превращается в правдоподобный ноль
или пустую строку.

| Метаданный тип | Пустое DSL-значение | Наблюдаемая семантика |
|---|---|---|
| `number` | `decimal.Zero` | `ТипЗнч` = `Число`, `= 0` истинно, арифметика числовая |
| `bool` | `false` | `ТипЗнч` = `Булево`, условие ложно |
| `string`, `richtext`, строковое enum | `""` | `ТипЗнч` = `Строка`, `ЗначениеЗаполнено` ложно |
| `date` | `time.Time{}` | `ТипЗнч` = `Дата`, `ЗначениеЗаполнено` ложно, `Число()` = 0 |
| `reference:*` | типизированная пустая `*Ref` с пустым UUID и известными `Type`/`Kind` | `ПустаяСсылка` истинно, `ТипЗнч` сохраняет вид ссылки |
| `image` и неизвестный/составной тип | `Неопределено` | отдельного безопасного пустого DSL-типа пока нет |

`default:` из плана 153 и эта таблица — разные механизмы. `default:` один раз
заполняет новый объект бизнес-значением (`сейчас`, константой, литералом).
Таблица выше — только представление всё ещё пустого реквизита при чтении DSL;
она не вызывает default повторно и не меняет объект в памяти.

Для ссылки типизированное пустое значение строит UI/DSL-адаптер, которому
доступен registry. Общий слой metadata не должен импортировать interpreter и
знать про `Ref`.

Носитель метаданных не обязан быть именно `metadata.Field`. Общая функция
принимает узкий неизменяемый дескриптор (`Type`, `RefEntity`, `EnumName`,
`Length`, `Scale`): поле сущности уже содержит его напрямую, `FormAttribute` и
`FormAttributeColumn` получают его из `TypeRef`, а `metadata.Constant` — из
собственных полей. Имя без такого дескриптора остаётся нетипизированным и не
даёт права превращать `nil` в правдоподобное пустое значение.

### 3. Операторы

После того как все известные числовые поля дают `decimal.Zero`, обход
`nilAsNumericZero` удаляется.

Фиксируется следующий публичный контракт:

| Выражение | Результат |
|---|---|
| `Неопределено = Неопределено` | `Истина` |
| `Неопределено <> 0` | `Истина` |
| `Неопределено = 0` | `Ложь` |
| пустой реквизит `number` `= 0` | `Истина` |
| отсутствующий ключ `Соответствие.Получить(...) = Неопределено` | `Истина` |
| сохранённый в Соответствии 0 `= Неопределено` | `Ложь` |
| `ТипЗнч(Неопределено)` | `Неопределено` |
| `Если Неопределено Тогда` | ложная ветка |
| `ЗначениеЗаполнено(Неопределено)` | `Ложь` |

Для порядка задаётся явное, не зависящее от `fmt.Sprintf` правило:
`Неопределено` меньше любого определённого значения и равно по порядку только
самому себе. Оно одинаково действует в операторах и сортировке коллекций;
поиск равенства использует семантическое равенство, а не случайное совпадение
строковых ключей.

Арифметическую совместимость в этом плане **не расширяем**. Ветки, которые
сейчас трактуют `nil` как 0, переписываются на явный `IsUndefined`, сохраняя их
наблюдаемый результат для прикладного кода. Пустые числовые реквизиты при этом
идут обычной decimal-веткой. Ужесточение `Неопределено + 1` до ошибки — отдельное
решение: оно не требуется #1274 и добавило бы несовместимость без ответа автора.

## Где нормализовать значения

Нужна одна функция вида `typedEmpty(field, registry) (value, ok)`, но не один
универсальный «заменить любой nil»: только владелец метаданных вправе назвать
`NULL` пустым числом.

Порядок чтения защищённого поля:

```
сырой результат БД → row/field security и masking → поиск metadata.Field
                  → типизированное пустое значение → FromHostValue → DSL
```

Masking идёт раньше нормализации. Иначе `NULL` защищённого числового поля
превратится в 0 до policy-gate и появится новый боковой канал «поле пусто/не
пусто». Маска, выданная политикой, обратно типизироваться не должна.

### Объекты и табличные части

- `formObjectThis.Get` переходит с локального switch number/bool на общий
  адаптер всех типов из таблицы. После поиска поля сущности он отдельно ищет
  скалярный `FormAttribute` и строит дескриптор из его `TypeRef`; пустое
  значение `save:false` поэтому получает тот же тип, что и сохранённое поле.
- `formAttributeTablePart` для `ValueTable` переносит в каждый временный
  `metadata.Field` не только `Name`/`RefEntity`, но и разобранные `Type`,
  `EnumName`, `Length` и `Scale` колонки. `refAwareMapThis` затем типизирует
  пустую ячейку по этому полному описанию, а не по совпадению имени.
- `refAwareMapThis.Get` нормализует известную колонку ТЧ и только затем
  обогащает непустую ссылку resolver'ом.
- `docWriter` и `catWriter` передают в `tpProxy` саму
  `metadata.TablePart`; `Добавить`, `Получить` и итерация возвращают тот же
  metadata-aware row proxy, что форма.
- `CatalogRecordWriter` уже хранит `metadata.Entity` и применяет ту же политику
  к объявленным, но ещё не установленным полям.
- `runEntityHook` и остальные места, где metadata уже известны, больше не
  запускают DSL с сырым `runtime.Object`; они используют один адаптер объекта.
  У `runtime.Object` как общего контейнера семантика не меняется.
- `ЗначениеРеквизитаОбъекта` и пакетный вариант нормализуют значение после
  проверки RLS/masking. «Запись не найдена» остаётся `Неопределено`, а
  «запись найдена, number-поле NULL» становится 0.

Полностью пустая строка формы по-прежнему отбрасывается **до** DSL-нормализации
(`convertManagedTablePartRows`/`typedFormFieldValue`). Иначе нули и ложь,
созданные только для чтения, превратят пустую строку браузера в реальную строку
ТЧ — повторение исходной грабли #1136.

### Константы

`dslvars.Common.Build` передаёт в `NewConstantsRoot` не `[]string`, а полные
дескрипторы объявленных `metadata.Constant`. `ConstantsRoot` хранит отдельно
каноническое имя и метаданный тип: если объявленная константа отсутствует в
снимке либо её сохранённое значение равно `nil`, `Get` материализует пустое
значение её типа. Неизвестная константа и историческое значение без оставшейся
декларации не получают выдуманный тип; их `nil` остаётся `Неопределено`.

Запись сохраняет внешний контракт: перед `SetConstant` внутренний sentinel
превращается в Go `nil`, а явно присвоенные `0`, `false` и `""` остаются
значениями. Публичный тест строит переменные настоящим `Common.Build` поверх
registry и storage, чтобы проверить именно production-путь, а не отдельно
сконструированный `ConstantsRoot`.

### Запросы

`query.Result` дополняется описанием доказанно типизированных проекций: минимум
`NumberColumns`, а для общего механизма — закрытой картой семантического типа
выходной колонки. Одна запись результата различает scalar `FieldType` и ссылку
с точным `RefEntity`; существующие `BoolColumns`, `DateColumns`, `RefColumns` и
новая числовая нормализация либо выводятся из неё, либо проверяются на точное
совпадение с ней. Независимые догадки по имени колонки запрещены.

Существующей пары `ProjectionPlan` + глобальная `colTypes` для этого
недостаточно. `ProjectionPlan.Simple` означает только один `SELECT` без
подзапроса/`ОБЪЕДИНИТЬ` и остаётся истинным для `JOIN`; `simpleFieldRef` при
этом отбрасывает квалификатор, а `buildColTypes` строит карту полей первого
источника по одному имени. Использовать эту карту для типа результата нельзя:
`ВЫБРАТЬ b.Value КАК X ИЗ A a JOIN B b` иначе либо не увидит тип `B.Value`,
либо возьмёт тип одноимённого `A.Value`.

Первый этап вводит отдельное, не связанное с `ProjectionPlan.Simple`,
fail-closed доказательство типоинференса результата:

- в текущем `SELECT` должен быть ровно один объявленный источник данных;
- план проекции сохраняет ссылку на поле вместе с квалификатором, а отдельная
  per-`SELECT` запись происхождения связывает aliases с точным источником
  метаданных (существующий `SourceRef` при необходимости расширяется: сейчас в
  нём есть только `Kind`/`Name`). Выходной `КАК` задаёт только имя результата и
  не заменяет provenance;
- допустима голая ссылка на поле единственного источника либо квалификатор,
  который точно называет этот источник. Для ссылочного поля доказательство
  строится **после** существующего compiler rewrite: голый `Проект` означает
  строку-представление из `refDimInfo.displayCol`, а точная одношаговая форма
  `Проект.Ссылка` означает UUID и типизированную `reference:<RefEntity>`, уже
  отмечаемую `noteRefOutput`/`RefColumns`. `Ссылка` самого источника аналогично
  получает его сущность. Произвольная более длинная цепочка разыменования,
  неизвестный квалификатор или неоднозначное имя закрывают доказательство;
- любой явный `JOIN` или другой многотабличный `FROM` в первой реализации
  считается нетипизированным целиком, даже если `b.Value` квалифицировано и
  имя `Value` встречается только в `B`. Для его SQL `NULL` DSL получает
  `Неопределено`; ненулевые значения не меняются. Полный per-source inference
  можно добавить отдельно, не ослабляя этот безопасный контракт.

Технически `buildColTypes` может остаться служебной картой транслятора для
`CAST`/квалификации, но не источником типа выходной колонки. Результат получает
тип только из metadata точно разрешённого единственного `SourceRef` и
семантики уже выбранного SQL-выражения. Автоматический JOIN, которым компилятор
получает представление ссылочного реквизита, не превращает текстовый запрос в
пользовательский многотабличный `FROM`, но меняет тип результата на строку.
Отсутствие полного доказательства означает отсутствие записи в карте типов.

Правила вывода типа не расширяются:

- простая проекция одного поля доказанного единственного источника, включая
  выходной алиас, получает его тип;
- голый ссылочный реквизит и `<Реквизит>.Ссылка` получают разные дескрипторы:
  первый — `string` для presentation-колонки, второй —
  `reference:<RefEntity>` для UUID. Алиас результата сохраняет дескриптор;
  пустой `Проект` материализуется как `""`, а пустой `Проект.Ссылка` — как
  типизированная пустая ссылка, не как строка и не как общее `Неопределено`;
- выражение, агрегат, wildcard, `ОБЪЕДИНИТЬ` и неоднозначный подзапрос типа не
  обещают; их SQL `NULL` остаётся `Неопределено`;
- `JOIN` и иной многотабличный источник типа не обещают. Обязательные тесты
  покрывают как уникальное имя поля второго источника, так и одинаковое имя с
  разными типами в обоих источниках; ни один случай не должен попасть в
  `NumberColumns`/общую карту типов;
- query security guard видит сырые строки первым; общая backend-нормализация
  bool/date идёт следом; только DSL-потребитель затем материализует пустые
  значения;
- отчёты, REST, CLI и AI не начинают получать 0 вместо SQL `NULL` побочно.

Параметр запроса `Неопределено` по-прежнему уходит в драйвер как `nil`/SQL
`NULL`. Пустое число — как 0, пустая ссылка и пустая дата — как `NULL`.

### Регистры и остальные типизированные источники

Тот же адаптер применяется к измерениям, ресурсам и реквизитам регистров
сведений, а также к metadata-aware строкам движений. Системные поля
(`Период`, `Регистратор`, `ВидДвижения`) получают отдельные явные правила и не
угадываются по имени. Сырая `MapThis`, параметры отчёта/обработки и произвольная
структура без метаданных ничего не типизируют: их `nil` — `Неопределено`.

## Граница хранения и сериализации

Миграции схемы и массового `UPDATE ... SET 0` **нет**. Существующие SQL `NULL`
остаются в базе; типизированное пустое значение — DSL-view, а не перепись
данных.

На записи:

- внутренний `undefinedValue` обязан быть превращён в Go `nil` до любого
  storage/API callback;
- пустая ссылка и `time.Time{}` канонизируются в SQL `NULL` в общей
  `fieldValueDialect`/регистровой воронке;
- `decimal.Zero`, `false` и `""`, явно присвоенные модулем, записываются как
  обычные значения. Семантически они и являются пустыми значениями своих
  типов; скрыто восстанавливать их в SQL `NULL` нельзя;
- чтение для DSL не мутирует `runtime.Object.Fields` и строки ТЧ. Поэтому одно
  обращение к реквизиту само по себе не создаёт изменение и не влияет на
  optimistic lock/audit.

JSON и XML сохраняют текущий внешний контракт: `Неопределено` ↔ `null` /
`undefined`; публичные `MarshalDSLValue`, callback'и, debugger protocol и
`RunWithResult` видят `nil`. Для вложенных Array/Struct/Map тест проверяет, что
sentinel не просочился в JSON как `{}` или имя Go-типа. Типизированные пустые
значения сериализуются своим типом: 0, `false`, `""`; пустая ссылка и пустая
дата используют уже документированное пустое представление соответствующего
формата.

## Совместимость и миграция

### Что сохраняется

- сценарий #1136: пустое number-поле шапки/ТЧ сравнивается с 0 и участвует в
  арифметике как 0;
- SQL `NULL`, фильтры `ЕСТЬ ПУСТО`, nullable-схема и данные не мигрируют;
- пропущенный аргумент и явно переданное `Неопределено` остаются различимыми;
- внешние Go API и callbacks продолжают использовать `nil`;
- JSON/XML `null`, пустые строки формы и отсечение пустых строк ТЧ не меняются.

### Что меняется намеренно

- `Неопределено = 0` и «не найдено = 0» становятся ложными;
- пустые реквизиты известных string/date/reference типов получают свой тип,
  а не `ТипЗнч(...)=Неопределено`;
- порядок с участием `Неопределено` перестаёт зависеть от строки `"<nil>"` и
  становится стабильным;
- пустая типизированная ссылка отличается от общего `Неопределено` по
  `ТипЗнч`, но остаётся пустой для `ПустаяСсылка` и `ЗначениеЗаполнено`.

Перед включением новой семантики нужен поиск по `examples/**.os`, тестовым
конфигурациям и документации на конструкции, которые полагаются на
`Реквизит = Неопределено` для известного scalar/reference-поля. Для миграции:

- number/bool/string/date проверять через `ЗначениеЗаполнено` или сравнение с
  каноническим пустым значением;
- ссылки — через `ПустаяСсылка`;
- `Неопределено` оставлять для результатов поиска, необязательных параметров и
  значений без метаданных.

В release notes отдельно назвать несовместимость. Автоматически переписывать
DSL нельзя: по тексту невозможно доказать, является выражение реквизитом
известного типа или произвольным результатом функции.

## Проверки

Минимальная обязательная матрица:

1. **Ядро через публичный API.** `RunWithResult`, `Call`, `CallSandboxed` и
   `EvalExpr`: `Неопределено`, отсутствующий идентификатор, результат процедуры
   без `Возврат`, missing key/index, явный 0 и первый индекс массива.
2. **Аргументы.** Пропуск с default, пропуск без default, явное
   `Неопределено`; встроенная/внешняя функция и метод видят Go `nil`, но
   пользовательская процедура различает missing sentinel и explicit undefined.
3. **Коллекции.** Новый публичный метод
   `Соответствие.СодержитКлюч/ContainsKey` зарегистрирован в подсказках и
   документации; исполнение DSL различает отсутствующий ключ, ключ с
   `Неопределено` и ключ с 0. Рядом проверяются `Получить`, `Массив.Найти`,
   `ТаблицаЗначений.Найти/НайтиСтроки/Сортировать`, ключи `0` и
   `Неопределено`; операторы и `Утверждать.Равно` дают одну семантику.
4. **Типизированные поля и форма.** number/string/bool/date/reference для
   шапки, ТЧ, скалярного `FormAttribute` и колонки `ValueTable`: новая и
   загруженная запись, пустой HTTP submit, присваивание, form event, entity
   hook, doc/catalog writer и разыменование ссылки. Отдельно проверяется, что
   перенос `TypeRef` не создаёт ghost-row и не пишет прочитанный 0 обратно.
5. **Константы.** Production-путь `dslvars.Common.Build` с настоящими registry
   и storage: незаданные number/string/bool/date/reference получают
   каноническое пустое значение, неизвестное имя остаётся `Неопределено`, а
   чтение не создаёт запись в БД. Явные значения и запись sentinel проходят
   прежнюю host/storage-границу.
6. **Запрос.** простое поле и выходной алиас единственного источника на
   SQLite/PostgreSQL; выражение, aggregate, wildcard, UNION и masked column как
   отрицательные случаи типоинференса. Два обязательных JOIN-теста: уникальное
   поле второго источника и одноимённые поля разных типов; оба остаются без
   типа и возвращают `Неопределено` для `NULL`. Для ссылочного поля матрица с
   пустым и непустым значением сравнивает `Проект` (presentation-строка) и
   `Проект.Ссылка` (типизированный `*Ref`), включая выходные алиасы и
   `ПустаяСсылка`; существующий контракт `RefColumns` не должен откатиться.
7. **Хранение.** чтение не мутирует объект; пустая дата/ссылка пишутся NULL;
   явные 0/false/`""` пишутся значениями; ни один driver argument не содержит
   sentinel.
8. **Сериализация.** JSON null round-trip, XML
   `XMLТипЗнч/XMLСтрока/XMLЗначение`, service response, вложенные коллекции,
   debugger/read-only condition и форматирование.
9. **Регрессия #1136.** пустая строка формы не сохраняет ghost-row; пустое
   number-поле равно 0 во всех object paths и участвует в арифметике без
   `"<nil>"`/SQLSTATE 22P02.

Для каждого среза — узкие package-тесты и публичный сквозной тест; перед
закрытием плана — `go test ./...` и матрица PostgreSQL/SQLite, которую уже
используют storage/UI tests. Тест, напрямую вызывающий приватный helper, не
считается приёмкой.

## Риски и откат

- **Sentinel протёк наружу.** Симптом — `%T`/`{}` в JSON, unsupported driver
  type или имя Go-типа в debugger. Предохранитель — одна пара
  `FromHostValue`/`ToHostValue` и contract tests на каждом публичном выходе.
- **Потеря metadata на одном прокси.** Симптом — значение зависит от того,
  пришло оно из формы, writer или запроса. Предохранитель — общая матрица одного
  поля через все пути, а не отдельные unit-тесты switch'ей.
- **`TypeRef` формы или константы отброшен до адаптера.** Симптом — поле сущности
  даёт 0, а однотипный `FormAttribute`, `ValueTable` или `Константы.X` даёт
  `Неопределено`. Предохранитель — передавать полный дескриптор, а не имя/
  `RefEntity`, и проверять публичные production-композиции.
- **Представление ссылки ошибочно объявлено ссылкой.** Симптом — `Проект`
  оборачивается в `*Ref` со строкой-наименованием вместо UUID либо
  `Проект.Ссылка` деградирует в строку/`Неопределено`. Предохранитель — единый
  семантический дескриптор после compiler rewrite и парный матричный тест обеих
  проекций.
- **Обход masking/RLS.** Типизация строго после guard; тест с пустым защищённым
  полем не должен позволять отличить его от другого masked значения.
- **Ghost-row ТЧ.** Канонические значения создаются при чтении DSL, не во время
  разбора формы и не записываются обратно без явного присваивания.
- **Неожиданная смена `ТипЗнч` пустой ссылки/даты.** Это заявленная миграция;
  поиск конфигураций и release note обязательны до включения.
- **Неоднозначная колонка запроса названа числом.** Fail closed: одного
  `Projection.Simple` недостаточно; без доказанного единственного источника и
  точной привязки ссылки на поле значение остаётся `Неопределено`.

Откат делается в обратном порядке. Срез C можно откатить, вернув
`nilAsNumericZero`, не снимая безопасные metadata-adapters A/B: #1136 останется
закрыт, а #1274 снова станет известным ограничением. Срезы A/B не требуют
обратной миграции данных, потому что чтение не переписывает SQL `NULL`.

## Готово, когда

- сценарий #1274 и обе 1С-идиомы зафиксированы одним публичным тестом;
- `nilAsNumericZero` удалён, а equality/ordering не зависят от `fmt("<nil>")`;
- `Соответствие.СодержитКлюч` реализован, документирован и отличает
  отсутствующий ключ от сохранённого `Неопределено`;
- для каждого metadata-aware пути, включая scalar `FormAttribute`, колонку
  `ValueTable` и объявленную константу, есть один и тот же контракт пустого
  поля;
- query provenance различает presentation ссылочного реквизита и его
  `.Ссылка`, сохраняя тип через выходной алиас и не типизируя явный `JOIN`;
- SQL/JSON/XML/Go boundary не видит внутренний sentinel;
- PostgreSQL и SQLite дают одинаковые DSL-типы и результаты;
- существующие данные не мигрированы, чтение не создаёт audit/version change и
  пустая браузерная строка не превращается в строку ТЧ;
- документация объясняет разницу между `default:`, пустым реквизитом,
  `Неопределено` и SQL `NULL`;
- каждый срез имеет отдельную публичную приёмку, а #1274 закрывается только
  после завершения всех срезов.
