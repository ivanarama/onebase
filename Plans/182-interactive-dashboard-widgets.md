# Этап 182 — Интерактивность виджетов дашборда

## Контекст

План ведёт [#1620](https://github.com/ivanarama/onebase/issues/1620) и собирает
в один контракт четыре связанные заявки:

- [#1617](https://github.com/ivanarama/onebase/issues/1617) — переход из строки
  `list`-виджета в карточку записи;
- [#1618](https://github.com/ivanarama/onebase/issues/1618) — ручное обновление
  одной карточки без F5 всего дашборда;
- [#1619](https://github.com/ivanarama/onebase/issues/1619) — обновление после
  записи или удаления данных;
- [#1620](https://github.com/ivanarama/onebase/issues/1620) — типизированные
  интерактивные фильтры над `list`-виджетом.

Выбран вариант 2: сначала общий план, затем небольшие последовательные PR.
Делать четыре независимых механизма нельзя: строке нужна идентичность записи,
refresh должен сохранять фильтры, а кеш обязан различать результаты тех же
запросов с разными параметрами.

### Что уже есть

- `metadata.Widget` описывает запрос, статические `params`, колонки и тип
  карточки (`internal/metadata/widget.go`).
- `widget.Runner` компилирует запрос с параметрами, RLS и маскированием полей
  (`internal/widget/runner.go`).
- сервер **уже кеширует** результаты виджетов на 60 секунд. Ключ сейчас состоит
  из имени виджета, пользователя и security fingerprint
  (`internal/widget/cache.go`, `internal/ui/server.go`). Это уточняет старый
  триаж #1618/#1619, где кеш ошибочно был назван отсутствующим.
- план 87 уже даёт одну SSE-сессию, события `данные.<сущность>`, RLS-aware
  адресацию, debounce, ожидание видимой вкладки и перечитывание живого списка.
- `recent`-виджет строит `_url` внутри runner, но это внутреннее поле результата,
  а не типизированный пользовательский контракт произвольного запроса.

### Почему одного AJAX-вызова недостаточно

Если добавить кнопку поверх текущего `Runner.Run`, она в течение TTL получит тот
же кешированный результат. Если передать фильтры, не меняя cache key, два набора
параметров одного пользователя разделят одну запись кеша. Это не только
устаревший экран: результат одного отбора может появиться в другом.

Поэтому foundation этого плана — единый partial-render и кеш по полным
типизированным effective params. Навигация, live refresh и фильтры строятся уже
поверх него.

## Цели и границы

Входит:

1. ручной refresh одной карточки для серверных data-widget (`kpi`, `list`,
   `chart`, `recent`), без специального YAML opt-in;
2. refresh этих типов по доверенным onebase-событиям без нового SSE-соединения;
3. opt-in источник и безопасная ссылка строки для `list`-виджета;
4. типизированные параметры фильтров `list` без конкатенации SQL;
5. одинаковое поведение в глобальном и подсистемном дашборде;
6. конфигуратор, `describe`, `onebase check`, документация и пример.

`actions` не получает кнопку или live refresh: у него нет query/cache result,
который можно перечитать. `source.entity`/`source.id_field` относится только к
навигации строк `list`; ручное обновление от `source` не зависит.

Не входит:

- произвольный JavaScript или SQL-фрагмент из значения фильтра;
- WebSocket или второй EventSource;
- пользовательский конструктор запросов;
- серверная пагинация карточки;
- drill-down графиков и редактирование строк внутри виджета;
- автоматическое угадывание навигационной сущности по первому `FROM`;
- глобальная инвалидация всех результатов после каждой записи.

## Публичный YAML-контракт

Рабочий пример для сценария автора:

```yaml
name: ЗадачиКоллЦентра
type: list
title: Задачи
limit: 30

source:
  entity: А_Задача
  id_field: Ссылка

refresh_on:
  - данные.а_задача

filters:
  - name: Исполнитель
    label: Исполнитель
    type: reference:Пользователи
    param: Исполнитель
  - name: Выполнена
    label: Выполнена
    type: bool
    param: Выполнена

query: |
  ВЫБРАТЬ
    Ссылка,
    Тема,
    Исполнитель,
    Выполнена
  ИЗ Документ.А_Задача
  ГДЕ (&Исполнитель ЕСТЬ ПУСТО ИЛИ Исполнитель = &Исполнитель)
    И (&Выполнена ЕСТЬ ПУСТО ИЛИ Выполнена = &Выполнена)
  УПОРЯДОЧИТЬ ПО Дата УБЫВ

columns:
  - field: Тема
    label: Задача
  - field: Исполнитель
    label: Исполнитель
  - field: Выполнена
    label: Выполнена
```

Пустой интерактивный параметр передаётся как типизированный `nil`/SQL `NULL`.
Запрос сам определяет семантику пустого отбора. В примере явная проверка
`&Параметр ЕСТЬ ПУСТО` превращает пустой фильтр во «все строки», включая строки
с пустым значением поля. Формулировка из исходной заявки `НЕ &Исполнитель` не
является переносимым контрактом: PostgreSQL не применяет булево `NOT` к UUID.

### `source`

```go
type WidgetSource struct {
    Entity  string `yaml:"entity"`
    IDField string `yaml:"id_field"`
}
```

- `entity` разрешается только через серверный `runtime.Registry`; kind
  (`document`/`catalog`) берётся из метаданных, а не из браузера.
- `id_field` — алиас сырой ссылочной колонки результата. Компилятор обязан
  подтвердить через `Result.RefColumns`, что она ссылается именно на
  `source.entity`; простого совпадения с UUID недостаточно. Значение забирается
  до `resolveUUIDs`, не показывается в автоколонках и не превращается в
  presentation. Неоднозначная/несовпадающая проекция fail-closed без ссылки.
- ссылка строится сервером как внутренний маршрут сущности. Пустой, битый или
  не-UUID `id_field` оставляет конкретную строку некликабельной.
- открываемая карточка повторно выполняет обычные RBAC/RLS/read-hook проверки;
  наличие ссылки не является разрешением доступа.
- отсутствие блока `source` сохраняет нынешнее некликабельное поведение строк;
  ручной refresh data-widget при этом остаётся доступен.

### `refresh_on`

Верхнеуровневый `refresh_on` не зависит от навигационного `source` и содержит
имена уже существующих onebase-событий. Поэтому агрегатный KPI/chart может
подписаться на несколько сущностей, не объявляя ложную сущность строки. Для
штатного `данные.<сущность>` у сущности должен быть включён `notify_changes`;
check выдаёт понятное предупреждение, если подписка объявлена, а издателя нет.
Поле допустимо для `kpi`, `list`, `chart`, `recent`; у `actions` это ошибка check.

Публичный `_url` из произвольного запроса не вводится. Он заставил бы автора
самому собирать путь, смешал бы пользовательские данные с навигацией и всё равно
не дал бы источника для refresh. Существующий `_url` `recent`-виджета остаётся
внутренней деталью без изменения совместимости.

### `filters`

```go
type WidgetFilter struct {
    Name    string            `yaml:"name"`
    Label   string            `yaml:"label,omitempty"`
    Labels  map[string]string `yaml:"labels,omitempty"`
    Type    string            `yaml:"type"`
    Param   string            `yaml:"param"`
    Values  []WidgetFilterValue `yaml:"values,omitempty"`
    Default any               `yaml:"default,omitempty"`
}
```

Первый срез фильтров поддерживает:

- `string`;
- `number` (`decimal`, не `float64`);
- `date`;
- `bool` с тремя состояниями «все / да / нет»;
- `select` с объявленными `values`;
- `reference:<Entity>` через существующий RLS-aware reference picker.

Правила:

- `name` уникально внутри виджета и служит стабильным ключом UI;
- `param` уникален и обязан встречаться в query;
- интерактивный `param` не может совпадать со статическим `params`;
- неизвестный тип/сущность, повтор имени/параметра и неподходящий default —
  ошибка `onebase check`, а не молчаливое игнорирование;
- сервер принимает только объявленные параметры и сам разбирает тип. Лишние
  ключи, неверный UUID/decimal/date и слишком длинная строка дают 400;
- reference UUID дополнительно проверяется на чтение и RLS. Недоступное и
  несуществующее значение имеют одинаковый fail-closed ответ;
- параметры передаются только в `query.CompileOpts.Params`; текст запроса не
  переписывается значением и не конкатенируется;
- значения фильтров в URL namespaced обратимо закодированными именами:
  `w.<base64url(widget)>.<base64url(filter)>=...` (UTF-8, без padding). Поэтому
  точки, пробелы и Unicode в именах не создают неоднозначность; два виджета не
  делят параметры, F5 и Back/Forward восстанавливают состояние;
- browser не присылает `type`, `entity`, `param` или query: только значение по
  известному имени фильтра. Остальной контракт сервер перечитывает из registry.

## Partial-render и клиентский контроллер

Добавляется защищённый read-only endpoint одной карточки, рабочее имя:

```text
GET /ui/_widget/{name}?subsystem=<name>&w.<b64-widget>.<b64-filter>=...
```

Endpoint:

1. заново разрешает global/subsystem home page;
2. проверяет видимость подсистемы и что виджет действительно входит в её
   effective layout;
3. находит metadata widget только в registry;
4. разбирает только объявленные фильтры;
5. выполняет тот же Runner/RBAC/RLS/masking path;
6. возвращает JSON-envelope с HTML тела карточки и, для chart, тем же
   `EChartsOption`, который использует полная страница.

Ответ всегда содержит `Cache-Control: private, no-store`: он зависит от
пользователя, RLS и фильтров и не должен сохраняться browser/shared cache.

Отдельного упрощённого renderer не появляется: полная страница и partial
исполняют общие named templates. Ошибка refresh оставляет прежнее содержимое и
показывает неблокирующий статус в карточке; пустой/403/redirect login ответ не
заменяет данные HTML страницы ошибки.

Один клиентский контроллер обслуживает три входа:

- кнопка «Обновить»;
- изменение/сброс фильтра;
- событие из верхнеуровневого `refresh_on`.

На карточке хранится `AbortController`, монотонный sequence и fingerprint
текущих значений. Поздний ответ старого набора фильтров не может перезаписать
новый. Live-события склеиваются debounce; скрытая вкладка остаётся dirty и
обновляется один раз при возврате. `__oblive_refresh_all__` после SSE reconnect
обновляет подписанные карточки. Новый EventSource не создаётся.

## Кеш и параметры

Runner получает явные options вместо скрытого различия путей:

```go
type RunOptions struct {
    Params map[string]any
    Fresh  bool
}
```

Effective params строятся на сервере в одном месте:

1. разрешённые статические `Widget.Params` после template/constant resolver;
2. проверенные интерактивные значения;
3. типизированный `nil` для незаполненного фильтра.

Cache key включает:

- имя виджета;
- пользователя;
- существующий security fingerprint;
- SHA-256 канонического представления **всех effective params**, включая тип и
  признак `nil`.

UUID, date/time, decimal, bool и string сериализуются канонически; порядок map
не влияет на fingerprint, исходные значения не попадают в лог или открытый
ключ. Если значение нельзя канонизировать, кеш отключается для этого запуска.

`Fresh` пропускает чтение кеша, выполняет запрос и перезаписывает только точный
entry. Любой partial-запрос карточки — manual, live, изменение/сброс фильтра и
`popstate` — всегда fresh; обычная первая отрисовка страницы может взять тот же
exact entry. Поэтому возврат к ранее использованному набору фильтров не оживляет
старую запись кеша после события. Глобальный `Cache.Invalidate()` остаётся для
reload конфигурации, но не вызывается после каждой записи: это сбросило бы
результаты всех пользователей и создало бы шторм запросов.

После merge PR #1509, если он произойдёт раньше реализации, сохраняется его
`ConstantResolver`: fingerprint считается по уже разрешённым типизированным
значениям, а не по строке `{{constant:...}}`.

## Права и границы доверия

- YAML конфигурации доверенный, HTTP query и содержимое GitHub issue — нет.
- partial endpoint не принимает текст query, source entity, id field, событие
  или список фильтров от клиента.
- обычные object permissions, query row filters и field masking применяются до
  выдачи результата так же, как при полной загрузке дашборда.
- SSE передаёт только сигнал изменения, без строки данных или значения
  защищённого поля. Адресация `данные.*` остаётся RLS-aware из плана 87.
- reference options и выбранное reference-значение проверяются независимо:
  ручная подстановка UUID не обходит права.
- HTML и labels проходят `html/template`; значения не попадают в trusted HTML,
  CSS или JavaScript literal.
- route и cache не различают недоступную и несуществующую ссылку сообщением.

## Хранилище / SQL

Новой таблицы и миграции нет. Все значения фильтров идут bind-параметрами
существующего query compiler. Поведение должно совпадать на SQLite и PostgreSQL.

Изменение кеша только in-memory. Старые entries без params fingerprint после
перезапуска отсутствуют; отдельной миграции не требуется.

## Тесты

### Кеш

- два набора фильтров одного пользователя имеют разные entries;
- `nil`, `false`, `0` и `""` не склеиваются;
- порядок map не меняет fingerprint;
- manual/live/filter-change/popstate fresh видит запись БД до истечения 60
  секунд и обновляет только точный entry;
- соседний widget и другой набор параметров не инвалидируются;
- user/security isolation остаётся прежней;
- неподдерживаемое значение отключает кеш fail-closed.

### Публичный HTTP-путь

- initial dashboard и partial дают одинаковое тело для тех же params;
- неизвестный/неразмещённый/недоступный widget не исполняется;
- global и subsystem layout различаются корректно;
- два виджета на странице не смешивают URL-state;
- 400/403/network error не стирает прежнее содержимое;
- partial-ответ всегда содержит `Cache-Control: private, no-store`.

### Фильтры и SQL

Матричный `dbtest.ForEachDialect` покрывает string/date/number/bool
tri-state/select/reference, пустое значение и настоящий запрос. Строка с
кавычками/оператором SQL остаётся одним аргументом и не меняет текст SQL.
Строка с `NULL` в фильтруемом поле остаётся в результате при пустом параметре —
это отдельно защищает канонический паттерн `&Параметр ЕСТЬ ПУСТО ИЛИ ...`.

Отдельно:

- лишний HTTP-параметр отклоняется с 400 и никогда не попадает в CompileOpts;
- duplicate/collision/bad type/bad default/bad entity ловит `onebase check`;
- reference UUID невидимой по RLS записи отклоняется тем же ответом, что
  несуществующий;
- reference options не содержат закрытые записи.

### Навигация

- raw UUID забирается до `resolveUUIDs` и не попадает в колонку;
- `Result.RefColumns` подтверждает ссылку именно на `source.entity`; обычный
  UUID, ссылка другой сущности и неоднозначная проекция не получают URL;
- malformed/nil id оставляет строку обычной;
- корректная строка получает внутренний URL нужного kind/entity;
- открытие разрешённой карточки проходит, закрытая карточка fail-closed;
- клавиатура (`Enter`) и клик не конфликтуют с выделением текста/ссылками в
  ячейках.

### Live refresh

- production save/delete публикует событие и перечитывает виджет;
- текущие фильтры сохраняются;
- пачка событий даёт один запрос;
- скрытая вкладка ждёт visibility, reconnect перечитывает один раз;
- старый медленный ответ не перезаписывает новый filter fingerprint;
- вкладочная оболочка по-прежнему держит единственный SSE stream.

## Verification

На примере `А_Задача`:

1. Открыть дашборд с list-виджетом и выбрать исполнителя.
2. Убедиться, что видны только его задачи, F5/Back сохраняют фильтр.
3. Выбрать «Выполнена = Нет», затем «Все» — `false` не смешивается с `nil`.
4. Нажать refresh: меняется одна карточка, остальной дашборд не перерисовывается.
5. В другой вкладке создать/изменить/удалить задачу — открытая карточка обновится
   без F5 и сохранит фильтры.
6. Нажать строку — откроется именно её карточка.
7. Повторить пользователем с ограниченным RLS: закрытые значения отсутствуют в
   reference picker, событие и строка не раскрывают чужие данные.
8. Искусственно задержать первый ответ, быстро сменить фильтр и получить второй:
   на экране остаётся результат второго.

## Совместимость, откат и пересечения

- Старые widget YAML остаются валидными: `kpi`/`list`/`chart`/`recent` получают
  только общую кнопку ручного refresh без opt-in; подписка, навигация и фильтры
  не появляются без новых `refresh_on`/`source`/`filters`. `actions` не меняется.
- Каждый срез откатывается кодом; schema/data migration нет.
- PR #1408 и Plan 170 не смешиваются с этим контрактом. Reference filter
  переиспользует их server-authoritative options/RLS, но не `choice_filter`.
- PR #1342 меняет URL обычных списков, не dashboard rows; при необходимости
  переиспользуется только безопасный helper построения пути.
- PR #1509 затрагивает `widget.Runner`; после его merge effective typed params и
  ConstantResolver должны остаться одной цепочкой.
- Открытые PR query compiler не требуют расширения грамматики в этом плане:
  параметры уже bind-ятся существующим CompileOpts.

## Критерии завершения

- одна карточка обновляется вручную и по событию без F5;
- refresh не возвращает старый 60-секундный cache entry;
- разные фильтры, пользователи и security states не делят кеш;
- строка открывает правильную запись без доверия UUID/URL от браузера;
- filter values типизированы, bind-параметризованы и проходят RLS;
- stale AJAX response не перезаписывает более новый выбор;
- старые виджеты работают без изменений;
- `onebase check`, public HTTP tests, Node/browser behavior tests,
  SQLite/PostgreSQL matrix и обновлённый example зелёные.
