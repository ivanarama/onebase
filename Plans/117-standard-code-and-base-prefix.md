# План 117 — Стандартный «Код» справочников, единая точка нумерации и префикс базы

Дата проектирования: 2026-08-08.
Статус: ⬜ **Проект** (не начато). Issue #658.

## Контекст

Пользователь (issue #658) просит три вещи: реквизит «Код» у справочников и
«Номер» у документов, автонумерацию для них и **префиксацию** — «префиксы часто
помогают понять, из какой базы была выполнена загрузка документов».

Половина запрошенного уже работает, половины нет вовсе, а одна часть выглядит
рабочей и молча не работает. Состояние на 2026-08-08 (все ссылки проверены):

Отдельно: **`DEVELOPER.md:1698-1730` описывает формат, которого не существует** —
`numerator: <имя>` со ссылкой на `numerators/<имя>.yaml`, маски `{YYYY}`/`{MM}`,
`pad`, `period: day|never`. Грепы `numerators/` и `{YYYY}` по `internal/` пусты.
Читатель документации получает молчаливое несрабатывание.

Корень: механизм нумерации проектировался планом 07 исключительно под документы
и остался зашитым в путь документа на всех уровнях. Справочник как вид объекта
из механизма выпал: у него нет ни стандартного «Кода», ни точки генерации, ни
валидации — при том что метаданные `numerator:` он принимает.

Часть про префиксы «из какой базы загрузка» не реализуема сегодня в принципе:
`Numerator.Prefix` едет **вместе с конфигурацией** и одинаков во всех базах, а
базо-специфичной величины, кроме кода узла обмена, не существует. `app.yaml` для
этого не годится по той же причине — он тоже часть конфигурации.

## Цель

1. У справочника появляется стандартный «Код» — объявляемый или синтезируемый
   нумератором, автоматически заполняемый на **всех** путях записи.
2. Точка генерации ровно одна, а не пять.
3. Префикс, отражающий **базу**, а не конфигурацию: загруженный обменом элемент
   видно по коду.
4. Опциональная уникальность кода/номера с проверкой **до** применения DDL — в
   духе плана 81.
5. Попутно закрыты тихие дефекты: no-op `numerator:` у справочника, немой
   `НайтиПоКоду`, недетерминированный `ComputePeriodKey`, ложная документация.

## Принятые решения

Зафиксированы здесь, чтобы реализатор их не переигрывал.

1. **«Код» — обычный строковый реквизит, а не системная колонка.** Так же
   устроены «Наименование» (`metadata/label.go:20`) и «Номер» (`yaml.go:184`).
   Это снимает миграцию колонки `code` во всех таблицах справочников, а поиск,
   список, пикер ссылок, ФТС и DSL начинают работать без единой правки. Вариант
   «системная колонка, как в 1С» вырастает в миграцию каждой базы плюс правки
   проекций, бэкапа и обмена — оценка меняется с дней на недели.
2. **Синтезируемый «Код» дописывается в КОНЕЦ `e.Fields`, а не в начало.** Для
   документа «Номер» кладётся первым (`yaml.go:185`) и это верно, но у
   справочника первым идёт «Наименование», а `metadata.RowLabel`
   (`label.go:20`) берёт **первый строковый реквизит**. Код впереди сломал бы
   представление во всех пикерах ссылок, строковых колонках регистров и в
   `Строка(Ссылка)`.
3. **Период по умолчанию для справочника — `none`** (код не сбрасывается по
   годам). У документа остаётся `year` (`yaml.go:164`).
4. **Префикс базы живёт в `_settings` под ключом `numbering.base_prefix`, а не в
   `app.yaml`.** `app.yaml` едет вместе с конфигурацией и одинаков во всех базах
   — для «из какой базы загрузка» бесполезен.
5. **Генерация только на путях создания объекта пользователем или прикладным
   кодом.** Приём обмена (`exchange/package.go:732` пишет `store.Upsert` мимо
   `entityservice.Save`) и восстановление бэкапа код **не** перегенерируют:
   иначе префикс источника, ради которого всё затевается, стирается на
   приёмнике.

## Синтаксис / метаданные

Блок `numerator:` у справочника — тот же, что у документа, плюс два новых ключа:

```yaml
name: Контрагенты
numerator:
  prefix: "К-"
  length: 6
  period: none        # для справочника по умолчанию none
  base_prefix: true   # НОВОЕ: подставить префикс базы перед prefix
  unique: true        # НОВОЕ: уникальный индекс по коду
fields:
  - {name: Наименование, type: string}
```

Поведение: при наличии `numerator:` и отсутствии явного реквизита «Код» он
синтезируется как `{Name: "Код", Type: FieldTypeString}` и дописывается в конец;
явно объявленный «Код» (со своими `title`/`label`) не трогается — ровно так же
сделано для «Номера» (`yaml.go:176`, тесты `types_test.go:183`).

`base_prefix` и `unique` работают и для документа: запрос из issue про префиксы
касается и номеров тоже.

## Хранилище / SQL

- **Новых системных таблиц не нужно.** Счётчик есть — `_numerators (entity_name,
  period_key, last_number)` (`storage/numerator.go:14`); ключом для справочника
  служит его имя, коллизий с документами нет (имена сущностей в реестре
  уникальны).
- **Префикс базы** — строка в существующей `_settings` под ключом
  `numbering.base_prefix`, чтение и запись через `storage.GetSetting` /
  `storage.SaveSetting` (`settings_raw.go:57`, `:192`).
- **Уникальность.** При `numerator.unique: true` в `ensureEntityIndexes`
  (`migrate.go:575`) создаётся уникальный индекс по колонке `код` (или `номер`),
  имя — через существующий `stableIndexName` (`ddl.go:120`). **До** создания
  индекса — проверка дублей отдельным `SELECT … GROUP BY … HAVING COUNT(*)>1` с
  отказом и примерами значений в сообщении. Это приём из плана 81: проверять
  преобразуемость до DDL. Молча индекс не создавать и молча дубли не терять.
- `unique` по умолчанию `false` — иначе существующие базы с дублями перестанут
  мигрировать.

## Дизайн — единая точка генерации

Сегодня код заполнения номера скопирован пять раз (см. таблицу в «Контексте»).
Все REST- и UI-пути записи проходят через `entityservice.Service.Save` —
проверено: `ui/handlers_entity.go:574` и `:1214`, `ui/ai_actions.go:552`,
`ui/dsl_form_object.go:128`, `ui/dsl_catalogs.go:222`, `api/handlers.go:283`,
`:424`, `:564`, `api/v2.go:195`, `:254`, `:332`, `bench/service.go:40`.
Единственный путь мимо — `docWriter` из `Документы.X`
(`ui/dsl_documents.go:20-23` это прямо признаёт).

Отсюда:

- новый метод `func (s *Service) ensureAutoNumber(ctx context.Context, req
  SaveRequest)` зовётся в начале `Save` (`service.go:206`) при `req.IsNew`. Он
  находит реквизит «Номер» (`KindDocument`) или «Код» (`KindCatalog`), проверяет
  пустоту **регистронезависимо** (грабли #359: `obj.Set` нормализует ключи в
  нижний регистр) и вызывает общий хелпер;
- хелпер выносится из `ui`/`api` в одно место:
  `func GenerateNumber(ctx context.Context, store *storage.DB, entity
  *metadata.Entity, fields map[string]any, basePrefix string) string`. Место —
  пакет `storage` (там уже `FormatNumber`/`ComputePeriodKey`) либо новый
  `internal/numbering`; выбрать при реализации;
- `docWriter.autoNumber` (`dsl_documents.go:707`) сводится к вызову того же
  хелпера, пять старых копий удаляются.

Откуда берётся `basePrefix`: читать `_settings` на каждой записи дорого —
кэшировать в `Service`/`runtime.Registry` с инвалидацией при смене либо читать
при старте. Решить при реализации, замерив (см. риски).

## Префикс базы

Ключевая связь с планом 86 (обмен данными). Значение задаётся один раз на базу:
CLI (`onebase base prefix --set "ЦБ-"` либо расширение `onebase exchange init`,
`cli/exchange.go:179` уже пишет per-base код узла) плюс поле в администрировании
и конфигураторе.

Правила:

1. При настроенном `exchange.this_node.<план>` предлагать префикс по коду узла —
   именно это связывает «понять, из какой базы загрузка» с планом 86.
2. В универсальном бэкапе ключ обрабатывается **как** `exchange.this_node.*`:
   экспортируется (`backup/universal.go:704`), но при восстановлении в режиме
   clone гасится вместе с идентичностью узла (`universal.go:1098`). Иначе клон
   выдаёт те же префиксованные коды, что и оригинал, и обмен склеит разные
   объекты.
3. Смена префикса задним числом **не** перенумеровывает существующие записи (см.
   «Ограничения»).

## Попутные дефекты, которые план закрывает

- **Д1. `ComputePeriodKey` недетерминирован.** `storage/numerator.go:58` выбирает
  дату итерацией по `map`: `for _, v := range fields { if t, ok :=
  v.(time.Time); ok && !t.IsZero() { date = t; break } }`. У документа с двумя
  date-реквизитами в разных годах (Дата и ДатаОплаты) ключ периода скачет от
  записи к записи, и счётчик случайно прыгает между годами. Порядок объявления
  полей известен, но в функцию не передаётся. Фикс: передавать
  `*metadata.Entity` и брать первое date-поле **по объявлению** — как уже делает
  `entityservice.SetPeriodFromFields` (`service.go:33`). Дефект существует
  независимо от #658 и бьёт по уже работающей нумерации документов; выносить его
  отдельным фиксом нельзя — он конфликтует с этапом 117B, который переписывает
  ту же функцию.
- **Д2. `numerator:` у справочника — тихий no-op.** Конфигурация выглядит
  рабочей, поведения нет.
- **Д3. `НайтиПоКоду` без реквизита «Код» молча возвращает `Неопределено`**
  (`predefined.go:337` → `catalogs_proxy.go:474`). Заменить на
  `RaiseUserError` с внятным текстом — рядом это уже делается для неверного
  идентификатора (`catalogs_proxy.go:479`).
- **Д4. `DEVELOPER.md:1698-1745` описывает несуществующий формат.** Переписать
  под фактический.
- **Д5. Конфигуратор не редактирует нумератор** (`launcher/configurator_types.go:44`
  только сохраняет блок при round-trip).

## Риски и ограничения

1. **`RowLabel` — главный риск регрессии.** См. решение №2: код, попавший первым
   строковым реквизитом, меняет представление ссылок по всей платформе.
2. **Существующие конфигурации уже объявляют «Код» руками**
   (`examples/trade/catalogs/МестоХранения.yaml:8`,
   `examples/callcenter/catalogs/ПравилаВалидации.yaml:11`) — синтез не должен
   их дублировать. Конвертер 1С тоже добавляет Код и Наименование
   (`converter/writer/yaml.go:314`) — пересечение согласовать.
3. **Уникальность на живых базах обязана отказывать до DDL** с примерами дублей,
   а не падать сырой ошибкой драйвера.
4. **Производительность.** Перенос генерации внутрь транзакции `Save` убирает
   «дырки» в нумерации при откате, но удерживает строку `_numerators` до конца
   транзакции и сериализует параллельные записи одной сущности. Гейт `bench`
   (`tools/benchgate`) валит просадку выше 25% — замерить до и после, цифру
   записать сюда.
5. **Смена префикса не перенумеровывает прошлое.**
6. **CI.** Новые `tr()` требуют перевода минимум в
   `internal/i18n/locales/en.json`, иначе `i18ncheck` роняет джоб `build`.

## Открытые вопросы

- Переиспользовать блок `numerator:` для справочников или ввести отдельный
  `code:`? Переиспользование дешевле и наполовину уже работает (метаданные
  парсятся), но слово «нумератор» для кода справочника читается натянуто.
- Уникальность кода — в разрезе чего: глобально по справочнику, по (период,
  scope) или с учётом префикса базы? От ответа зависит, склеятся ли коды двух баз
