# Этап 197 — Строковый доступ по карточке сотрудника (`user_card`)

## Контекст и принятое решение

Ведущая заявка: [#1911](https://github.com/ivanarama/onebase/issues/1911).
Кладовщик должен видеть складские ордера своего филиала; филиал хранится в
прикладном справочнике сотрудников, связанном с учёткой через `reference:_users`.
Повторять прикладные данные в `_users` или вручную переназначать роли филиалов
не требуется. Источник используется в существующем `row_access`, после RBAC.

Принят **вариант 2** канонического триажа `5994368833`, подтверждённый решением
владельца `6055945801` от 2026-10-08 и `approved` + `decision:2`: отдельный
plan-PR, затем скалярный срез и отдельный срез табличных частей. Этот документ
определяет оба контракта. Его слияние не реализует возможность и не закрывает
заявку. Каждый кодовый срез проходит отдельные REVIEW и проверки.

Основание — код `main` на `85e4caf09e928484a97e0ed5f28beccc7a906f2d`.
Проверены границы ниже; сведения триажа о ранее выполненных тестах не являются
результатами проверки новой реализации. В PLAN продуктовый код не менялся.

## Синтаксис / YAML

Канонический скалярный источник задаётся структурой, все три поля обязательны:

```yaml
row_access:
  documents:
    А_ОрдерСкладской:
      read:
        field: ФилиалАйсберг
        op: eq
        value:
          user_card:
            catalog: Пользователи
            account_field: УчётнаяЗапись
            field: ФилиалДляФильтраЗадач
      write:
        same_as: read
```

`account_field` — реквизит именно этого справочника с типом `reference:_users`.
`field` — обычный реквизит карточки. Имена разрешаются регистронезависимо,
как существующие имена метаданных, но сохраняются в каноническом написании.
Системные псевдополя, произвольный SQL, цепочки разыменований и путь в ТЧ здесь
запрещены. Другие справочники со ссылками на `_users` никак не участвуют.
При нескольких таких реквизитах выбор остаётся явным. UUID учётки берётся
только из аутентифицированного `auth.User`, а не из параметров формы/запроса.

Предложенную в issue строку `user_card: Пользователи.ФилиалДляФильтраЗадач`
поддержать как сокращение: допускается ровно один реквизит `reference:_users`
в названном справочнике. При нуле или нескольких связях — ошибка загрузки с
подсказкой перейти на полную структуру; runtime не выбирает первую связь.
Это новый синтаксис, ранее строка могла игнорироваться YAML-парсером и не
предоставляла работающей авторизации. Успешный старый `check` не служит
обещанием её поведения. `describe` и редактор роли выводят полный формат.

В срезе табличных частей та же структура содержит другой селектор значения:

```yaml
read:
  field: ФилиалАйсберг
  op: in
  value:
    user_card:
      catalog: Пользователи
      account_field: УчётнаяЗапись
      table_part: СписокФилиалов
      column: Филиал
```

`field` и пара `table_part`/`column` взаимоисключающие. Смешанные селекторы,
неполные структуры, неизвестные ключи `RowValue`/`user_card`, несколько
источников (`user`, `user_attr`, `literal`, `list`, `user_card`) отклоняются,
а не выбираются по порядку. Наличие `literal` определяется по YAML-узлу,
включая явно заданный `null`; отсутствие не равно `literal: null`.
Строгую проверку ограничить этими узлами, не ужесточать все исторические поля
роли одним глобальным `KnownFields`.

Скалярный источник разрешён для `eq`/`ne`; набор из ТЧ — для `in`/`not_in`.
`not`, `all`, `any`, `same_as` сохраняют структуру политики. Скаляр с `in`,
набор с `eq`, а также `empty`/`not_empty` с `user_card` — ошибки конфигурации.
Первый кодовый срез распознаёт селектор ТЧ, но явно отклоняет его как ещё
неподдержанный; молча игнорировать его до следующего среза нельзя.

Тип источника должен совпадать с полем ограничения: для ссылки — та же цель,
для перечисления — то же перечисление, для числа — совместимая точная числовая
семантика существующего predicate, для строки/boolean/даты — тот же тип.
Не сравнивать ссылки по представлению. `number` не переводить во `float64`.
Несовместимость диагностируется до runtime. `false` и `0` — полноценные
значения; пустой источник — `NULL`, пустая строка, пустая ссылка/UUID, а для
ТЧ также отсутствие строк. Для строк пробелы не удалять неявно.

## Наблюдаемая семантика и инварианты

1. Найти непомеченный на удаление элемент названного справочника с
   `account_field = текущий user.ID`; папки и помеченные элементы исключены.
   Вычитать не более двух подходящих ID, не использовать `LIMIT 1` для выбора
   победителя. Ноль — источник отсутствует, два — неоднозначность.
2. При одной карточке прочитать только выбранный реквизит или выбранную
   колонку её ТЧ. Дубли значения ТЧ убрать по типизированному значению.
   Набор ограничить 1000 исходными строками: читать максимум 1001, превышение
   закрывает политику с диагностикой, не разрешает доступ по усечённому набору.
   Пустая/невалидная строка ТЧ делает источник недоступным целиком, даже если
   другие строки валидны. Набор не склеивается из нескольких карточек.
3. Отсутствие карточки, дубли, пустое или невалидное значение дают отдельное
   состояние `Unavailable`, **не обычный `NULL`, пустой список или false-лист**.
   Это состояние распространяется до корня ограничивающей политики данной
   роли через `all`/`any`/`not` и запрещает её целиком. Поэтому `ne`,
   `not_in`, `not(not(...))` и `any` с другим разрешающим листом не могут
   превратить отсутствующий источник в доступ. Все источники дерева проверяются
   до вычисления его boolean-выражения, без обходящего lookup short-circuit.
4. Роли по-прежнему объединяются разрешением: действующая другая ограниченная
   роль может дать доступ своей политикой; роль с правом операции без политики
   снимает ограничение. Сначала собрать все роли и проверить unrestricted,
   затем читать источники. Результат не зависит от алфавита названий ролей.
   Ошибка конфигурации остаётся ошибкой, а не новой разрешающей ролью.
5. Техническая ошибка чтения/таймаут/отменённый context возвращает ошибку всей
   операции после unrestricted-проверки, как текущие ошибки компиляции RLS.
   Она не превращается в сравнение или ответ «нет карточки». Запись откатывается;
   PostgreSQL-транзакция после SQL-ошибки не продолжается. Другие роли не
   оправдывают продолжение уже сбойной транзакции. HTTP/DSL получают безопасный
   отказ без карточки, филиала, количества дублей или SQL в ответе; причина
   доступна администратору в диагностике. Формы сохраняют незаписанные данные
   при техническом сбое, используя существующее различение ошибки и отказа.
6. Проверка записи использует одно решение для старой строки и предлагаемой
   строки: нельзя прочитать свой филиал и перенести документ в чужой.
   `post`/`unpost`/`delete` соблюдают собственные политики и `same_as`.
   Автоподстановка допускается только для успешно разрешённого простого `eq`
   по существующим правилам `AutoFillPredicateFields`, без перезаписи ввода.
7. Администратор и существующий режим без аутентификации сохраняют текущую
   семантику. `user_card` не превращает фоновые доверенные контексты в
   пользователя и не создаёт новое освобождение от RLS.

## Служебное чтение, актуальность и транзакции

Выбор карточки — узкая инфраструктурная возможность, выданная конфигурацией
политики, а не пользовательское чтение справочника. Она не требует у сотрудника
`read` на карточки, не применяет к карточке её собственные RLS/masking-политики
и потому не рекурсирует. Извлечённое значение не экспортируется, не включается
в DSL-объект, HTTP-ответ, `describe` текущих прав или SSE payload. Назначение
роли с этим источником остаётся администраторским действием.
`user_card` не выдаёт права менять связь с учёткой или филиалы карточки.
Прикладная конфигурация обязана ограничивать такую запись существующим RBAC/RLS:
сотрудник, которому разрешено произвольно менять источник своей политики,
может менять и свой доступ. Пример и приёмочная конфигурация запрещают ему
изменение этих данных; новый универсальный редактор полномочий здесь не вводится.

Не реализовывать lookup вызовом пользовательского `List` с фальшивым
`RowFilterEvaluated=true` и не открывать общий bypass. Новый узкий storage-reader
принимает разрешённый по метаданным descriptor и user UUID, параметризует
значения, использует существующие правила физических колонок/имён таблиц,
в том числе `_id` у ссылок. Не требует JOIN к `_users`: сравнивается FK в
карточке, учётка уже проверена аутентификацией. Ошибка query-сценария #1912
не является обязательной зависимостью этого lookup.

Reader разрешает один descriptor **одним SQL statement** через
`DB.Query(ctx, ...)` на той же базе и активной транзакции из `ctx`. Выбор
карточки, проверка её единственности и чтение скаляра/ТЧ входят в этот statement;
промежуточный ID не используется во втором запросе. Курсор полностью вычитать,
проверить `rows.Err()` и закрыть до следующей операции.

Конкретная форма запроса — CTE с ограниченными промежуточными наборами:

1. `matched_cards` выбирает ID допустимых карточек по user UUID, исключая
   помеченные элементы и папки, в порядке ID с `LIMIT 2`. Для скалярного
   descriptor выбранный реквизит читается уже в этом CTE.
2. `card_count` вычисляет `COUNT(*)` только по `matched_cards`: 0, 1 или 2.
   Скалярный результат — `card_count LEFT JOIN matched_cards` с условием
   `card_count.n = 1`, возвращающий количество, ID и значение.
3. Для ТЧ `limited_values` соединяет её с `matched_cards` по `parent_id`,
   допускает строки только при `card_count.n = 1`, выбирает ID строки и
   нужную колонку, сортирует по `строка, id` и применяет `LIMIT 1001`
   **до** dedupe. Последний SELECT делает
   `card_count LEFT JOIN limited_values ON TRUE` и возвращает количество,
   ID строки и значение с тем же порядком строк. Все CTE и SELECT — части
   одного запроса; отдельно считать карточки или читать ТЧ нельзя.
4. `card_count` всегда даёт одну строку, поэтому ноль карточек, дубли и пустая
   ТЧ различимы даже без значений. NULL ID строки после LEFT JOIN обозначает
   отсутствие строки; непустой ID с NULL значением — существующую невалидную
   строку. 1001 полученная строка означает превышение лимита, даже если значения
   повторяются. Во всех этих случаях действует `Unavailable` из инвариантов.

Имена/колонки строятся только из проверенного descriptor по правилам metadata
и dialect; UUID остаётся параметром. Предикат папок добавляется только для
иерархического справочника. CTE не требует PostgreSQL-only `MATERIALIZED`:
согласованность обеспечивает один statement, а не способ выполнения CTE.

На PostgreSQL `BeginTx`/`BeginTxForExecution` используют обычный READ COMMITTED,
а `WithReadSnapshot` при `HasTx(ctx)` только вызывает callback. Поэтому два
чтения в такой вложенной области могут видеть разные версии. Один statement
читает карточку и ТЧ на одном снимке и в уже начатой READ COMMITTED транзакции,
при этом видит её собственные записи. Не менять изоляцию поздним
`SET TRANSACTION`, не добавлять блокировки карточек и не открывать вторую
транзакцию/SQLite-соединение для lookup. Вне транзакции тот же единый запрос
достаточен; существующий standalone `WithReadSnapshot` можно сохранить там,
где он уже нужен вызывающей операции, но он не заменяет этот контракт reader.

Данные источника **не кэшировать** между запросами, операциями, проверками
авторизации или по времени жизни сессии. Каждое новое решение перечитывает
источник; старую/новую строку одной записи проверяет один уже вычисленный
predicate. Внутри DSL после изменения карточки следующий вызов авторизации
видит свои записи той же транзакции. План компиляции источника по неизменяемым
метаданным кэшировать можно; значения — нельзя в первых срезах.

Смена филиала действует с очередной проверки доступа, без перелогина; уже
начатая операция сохраняет своё решение. Это не обещание мгновенного отзыва
доступа посреди SQL-запроса или отмены уже отправленного ответа. SSE проверяет
подписчика заново при отправке события. Для отчётов/выгрузок решение принимается
в начале исполнения; streaming не получает межзапросный кеш прав.

## Хранилище / SQL и совместимость

Новых таблиц, DDL и переноса прикладных реквизитов в `_users` нет. Связь на
`_users` уже поддерживается `metadata.SystemUsersEntity` и storage (#1646).
Уникальность `account_field` автоматически не добавляется: старые базы могут
содержать дубли; такие источники закрываются, администратор исправляет данные.
Для крупных карточных справочников рекомендован обычный индекс связи через
существующий механизм индексов после измерения плана запроса.

Пустые наборы старых `literal`/`list` сохраняют свой контракт: сейчас SQL для
пустого `in` даёт `1=0`, для `not_in` — `1=1`. Эта семантика **не применяется**
к недоступному `user_card`. Нужен явный постоянный predicate запрета в SQL и
in-memory evaluator либо эквивалентное `Decision.Allowed=false`, когда все
роли недоступны. Его нельзя передавать под исходный `not`; он возникает только
после распространения `Unavailable` до корня роли. SQL, `MatchPredicateWithRefs`
и автоfill обязаны одинаково обрабатывать этот результат.

`user`/`user_attr` и существующие статические значения не меняют смысл.
Новые роль/конфигурация должны проходить check именно новой версией движка.
При downgrade старый YAML-парсер может проигнорировать новый ключ: до отката
бинаря убрать/заменить новые роли проверенными `literal`/`list` или закрыть
доступ сотрудникам. Автоматического безопасного downgrade здесь нет.

Предлагаемые API: `access.DecideWithContext(ctx, user, ..., decisionContext)` и
`QueryRowFiltersWithContext(...)`, где контекст содержит metadata lookup и
`UserCardResolver`, без импорта `ui` в `access`. Descriptor проходит статическую
проверку до reader. Имена API проектные; совместимые wrappers старого API
сохраняются для статических политик. Если старый API получил `user_card` без
resolver, он возвращает ошибку, а не разрешение. Все прямые runtime вызовы
из таблицы переводятся в первом работающем срезе, без временного HTTP-only RLS.

Поиск вызовов повторить в реализации на её актуальном `main`; таблица не
заявляет, что вызовы в будущих коммитах уже охвачены. UI/REST, picker, отчёты,
выгрузки, DSL сущностей/регистров и `Новый Запрос` должны сходиться на общем
решении; SQL filter остаётся параметризованным в каждой ветви запроса.

## Последовательность PR-срезов и публичные тесты

### A — Скалярный источник во всём действующем контуре (~4–6 дней)

Один поставляемый результат: филиал одной карточки ограничивает чтение и запись.
Добавить формат, статическую проверку, reader, unavailable propagation и
подключить все runtime границы таблицы. Обновить YAML-schema/describe/редактор
роли в тех местах, где они публикуют формат, документацию RLS и пример роли.
Срез ТЧ явно отклоняется. Не выпускать парсер отдельно от enforcement.

Публичная матрица SQLite/PostgreSQL через `dbtest.ForEachDialect`:

- Два сотрудника и два филиала: HTTP список/счётчик/picker, прямое открытие,
  REST v2, отчёт и экспорт, DSL получение объекта/`Новый Запрос` показывают
  только свой филиал. Проверить JOIN и `ОБЪЕДИНИТЬ` через guarded query entry.
- HTTP и DSL create/update/delete/post: разрешён свой филиал, запрещён чужой,
  запрещена смена филиала существующего документа; отказ не оставляет записи
  и побочных движений. Дефолт «единственный» не выбирает скрытую строку.
- Нет карточки, два элемента, папка, пометка удаления, пустая ссылка/строка:
  отказ при `eq`, `ne`, вложенном `not` и `any`; другая разрешающая роль и
  unrestricted сохраняют документированную OR-семантику в обоих порядках ролей.
- Карточка имеет собственную RLS с `user_card`, у сотрудника нет read на неё:
  разрешённые ордера доступны без рекурсии; карточка и значение не раскрываются.
- Смена филиала между запросами без нового login; изменение в DSL-транзакции
  и следующий Запрос видит новый филиал, rollback возвращает старый. Создать
  объект Запрос до открытия транзакции. Параллельное соединение не получает
  необязательных блокировок/утечки из глобального кеша. SSE не шлёт чужое событие.
- Ошибка reader через storage failure injection на настоящем HTTP/DSL пути:
  отказ, rollback и сохранение незаписанной формы, без успеха по пустому значению.
- Запустить публичный `onebase check --project <fixture> --lint`: отсутствующий
  справочник/связь/поле, два account fields в сокращении, конфликт источников,
  неизвестный ключ, неверный тип/оператор и неподдержанная ТЧ диагностируются;
  корректные структуры и сокращение с одной связью проходят.

### B — Набор филиалов из ТЧ (~2–3 дня)

Один результат: сотрудник с несколькими филиалами видит объединение своего
набора. Включить selector ТЧ, единый statement карточка+ТЧ, типизацию, dedupe и
лимит. Обновить редактор/документацию с примером `in` и безопасной диагностики.
Применить те же публичные HTTP/DSL сценарии, дополнительно:

- Два разрешённых филиала и третий чужой; `in`, `not_in`, вложенный `not`.
- Пустая ТЧ, невалидный элемент, несколько карточек и сбой чтения: недоступная
  роль, включая отрицательные операторы; повтор значения не меняет результат.
- `0`/`false`, числа с дробной частью, ссылки и перечисления: одинаковые наборы
  в SQL и in-memory. 1000 строк допустимы, 1001 отклоняется без усечения.
- Изменение ТЧ и следующий HTTP/DSL доступ; чтение ID+ТЧ на двух соединениях
  не смешивает версии карточки внутри одного statement. Обязательно включить
  PostgreSQL с уже открытой DSL-транзакцией **READ COMMITTED**, а не только
  standalone `WithReadSnapshot`/REPEATABLE READ. Через публичный DSL/HTTP путь
  и управляемый барьер после получения снимка lookup конкурентное соединение
  одним commit переназначает связь `user_a → user_b` и заменяет филиал ТЧ
  `branch_a → branch_b`. Текущее решение для user_a видит старую согласованную
  пару; следующий lookup в той же READ COMMITTED транзакции не находит карточку.
  Повторить с конкурентной пометкой удаления и изменением ТЧ: текущий lookup
  сохраняет старую пару, следующий получает `Unavailable`. Проверить через
  публичный результат доступа, что branch_b не разрешён старым ID user_a.
- В конкурентной PostgreSQL проверке барьер должен разделять внутренние фазы
  **одного** SQL statement, не вводить второй production SELECT; sleep без
  синхронизации не считается доказательством. Отдельная диагностическая
  двухзапросная реализация должна воспроизводить смешанную пару, чтобы тест
  действительно ловил прежнюю гипотезу. Проверить SQLite на том же публичном
  сценарии с учётом блокировок/WAL: ошибка конкурентной записи не считается
  доказательством смешения или успешной смены версии.
- Изменить связь/ТЧ собственными записями внутри DSL-транзакции: следующий
  lookup видит именно эти записи (read-your-writes), commit сохраняет их,
  rollback возвращает старые права в следующей операции. Параллельное
  соединение не видит незакоммиченные изменения. Дополнить standalone
  сценариями без транзакции и под `WithReadSnapshot`, а также 0/1/2 карточками,
  пустой ТЧ и 1000/1001 исходными строками единого запроса на обоих backend.

Оба среза включают собственные тесты, `go build ./...`, затронутые пакеты,
configcheck и обязательный CI (`build`, `lint`, `postgres-integration`, `vuln`,
`smoke`, `e2e`, `test-windows`, `launcher-webview-build`). PostgreSQL прогон
выполняется с `TEST_DATABASE_URL`; SQLite-only успех не заменяет эту матрицу.
Закрывающий keyword по #1911 добавляется только в финальный кодовый PR, когда
весь согласованный контракт принят. Плановый PR содержит только Plan-Issue/Path.

## Verification

На минимальной конфигурации с `Пользователи.УчётнаяЗапись: reference:_users`,
филиалами и ордерами настроить две неадминистраторские учётки. Выполнить
`onebase check --project <dir> --lint`, migrate и run на SQLite; повторить на
PostgreSQL. Под одной сессией открыть список, карточку, picker, экспорт и
обработку с DSL-запросом; попробовать запись чужого филиала и перенос своего
ордера. Администратор меняет филиал сотрудника — следующий запрос меняет
доступ. После B добавить второй филиал в ТЧ и проверить только эти два.
Удалить связь/создать дубль — положительный и отрицательный фильтры закрываются.
Проверить ответы и события на отсутствие карточных данных. Приложить сценарий
и результаты обоих backend к соответствующему кодовому PR.

## Риски, откат и критерии завершения

Основные риски: deny превращается в allow под `not`, обход в прямом compiler
caller, рекурсивное чтение, второй SQLite connection, неверная типизация,
устаревший кеш и дорогой lookup. Их закрывают явное состояние недоступности,
полная инвентаризация вызовов, узкий reader и публичная матрица. Число запросов
не зависит от числа ордеров; измерить список/экспорт с большим справочником
карточек и индексом связи. Оптимизацию кешем значений вынести отдельно, если
измерения её потребуют. Не добавлять произвольные цепочки ссылок в этот план.

Откат до внедрения — revert кодового среза без DDL. После назначения новых
ролей сначала заменить источники статическими `literal`/`list` либо снять
доступ сотрудников, проверить политику публичными запросами, затем откатывать
бинарь. При ошибке доступ закрывается; оператор исправляет данные/роли,
автоматика не выбирает карточку и не расширяет права.

Завершено, когда A и B поставлены, одинаковые HTTP/DSL и SQL/matcher сценарии
прошли на обоих backend, документы/схемы описывают фактический синтаксис,
unavailable ни в одной отрицательной конструкции не даёт доступ, все runtime
caller-ы используют текущий context и не раскрывают источник. Общая оценка
**6–9 дней** плюс REVIEW/CI; отдельной миграции данных нет. Новые требования
(цепочки ссылок, несколько карточек как union, межзапросный кеш, немедленный
отзыв внутри операции) требуют отдельного решения.
