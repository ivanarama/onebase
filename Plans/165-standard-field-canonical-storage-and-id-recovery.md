# Этап 165 — Каноничное хранение стандартных «Кода»/«Номера» и восстановление их ID

## Контекст

План закрывает ведущую issue #1358 и задаёт общий контракт для ведомой issue
#1359. Выбран вариант 1 из триажа #1358: до изменения кода сначала определить
единое хранение стандартного поля и безопасную миграцию уже сохранённых YAML.

Сейчас `numerator:` объявляет стандартный «Код» справочника или «Номер»
документа. `metadata.LoadFile` синтезирует это поле с устойчивым ID `std_code` /
`std_number`, если одноимённой строки нет в `fields`. Конфигуратор показывает
загруженное поле как обычный реквизит и при любом сохранении записывает его
обратно в `fields`. Получаются два источника истины: формат и генерацию задаёт
`numerator`, а ID и свойства поля — отдельная строка.

Фикс PR #1199 засевает служебный ID перед `ensureFieldIDs`, но намеренно отдаёт
приоритет уже лежащей в файле строке. Поэтому ранее записанный `f_xxxxxxxx` не
исправляется повторным сохранением. Если `_schema_fields` уже связывает колонку
`код`/`номер` с `std_code`/`std_number`, планировщик миграции видит коллизию. Если
база впервые мигрировала из испорченного YAML, владельцем той же колонки,
наоборот, оказывается случайный `f_*`. Простое удаление строки из YAML не
покрывает оба состояния и может оставить карту схемы противоречивой.

План развивает решения этапа 117: стандартный реквизит остаётся полноценным
элементом `Entity.Fields`, имеет канонические имя, строковый тип и устойчивый ID.
Меняется только его исходное представление в YAML и безопасное восстановление
владельца существующей физической колонки.

## Выбранный вариант и наблюдаемая семантика

Канонический источник стандартного поля при включённой нумерации — блок
`numerator`. Строки `Код`/`Номер` в `fields` новый конфигуратор не пишет.
Необязательные пользовательские свойства синтезируемого поля хранятся во
вложенном `numerator.field`; имя, ID и тип там не задаются:

```yaml
name: Контрагенты
numerator:
  prefix: "К-"
  length: 6
  period: none
  unique: true
  field:
    title: Код контрагента
    titles:
      en: Customer code
fields:
  - id: f_name
    name: Наименование
    type: string
```

`numerator.field` хранит только свойства, которые применимы к стандартному
строковому полю: `title` (с чтением legacy-синонима `label`), `titles`,
`required`, `default` и `pii`. Пустой блок не сериализуется. `name`, `id` и
`type` запрещены: загрузчик всегда получает соответственно `Код`/`Номер`,
`std_code`/`std_number` и `string`. `numerator.length` по-прежнему задаёт
разрядность генерируемой строки; второго параметра длины у поля нет.

Старый формат остаётся входным форматом совместимости:

```yaml
numerator: {prefix: "К-", length: 6}
fields:
  - {id: f_12ab34cd, name: Код, type: string, title: Артикул}
```

При чтении ровно одна одноимённая строка при активном `numerator` считается
legacy-описанием стандартного поля. В памяти она нормализуется до канонических
имени, типа и ID, а поддерживаемые пользовательские свойства переносятся без
изменения. Любое последующее сохранение через конфигуратор переписывает её в
`numerator.field`. Загрузка сама файл не меняет.

Если одновременно заданы `numerator.field` и legacy-строка в `fields`, либо
одноимённых строк несколько, загрузка/`onebase check` отказывает с указанием двух
конфликтующих источников. Неоднозначность нельзя разрешать порядком элементов.

При выключении `numerator` конфигуратор материализует показанный стандартный
реквизит обратно как обычную строку `fields` с тем же `std_code`/`std_number` и
пользовательскими свойствами. Так колонка и значения не становятся
разрушительным удалением. При повторном включении нумерации эта строка снова
поглощается `numerator.field`.

## Инварианты

1. При активном `numerator` в `Entity.Fields` есть ровно одно стандартное поле:
   для справочника `Код/string/std_code`, для документа
   `Номер/string/std_number`.
2. Канонический YAML с активным `numerator` не содержит стандартную строку в
   `fields`; `numerator.field` не дублирует имя, ID или тип.
3. Legacy-YAML читается без потери поддерживаемых свойств, но в памяти получает
   служебный ID независимо от записанного `f_*`.
4. Переход `legacy fields → numerator.field`, включение и выключение нумерации
   не переименовывают физическую колонку, не меняют её тип и не переписывают
   значения.
5. Автоматическое восстановление `_schema_fields` разрешено только при
   однозначном доказательстве, что старый и новый ID обозначают одну существующую
   колонку. При любом конфликте миграция завершается до записи.
6. Перепривязка ID, остальные изменения схемы и финальная запись карты одной
   таблицы атомарны на SQLite и PostgreSQL.
7. Повторные `check`, сохранение и миграция идемпотентны: второй прогон не меняет
   YAML, DDL, данные или `_schema_fields`.
8. Обычный пользовательский `Код` без `numerator` и `Код` у документа не
   получают служебный ID. Сопоставление всегда учитывает вид сущности и наличие
   нумерации.

## Инвентаризация затронутых границ

- `internal/metadata/yaml.go`, `types.go`, `validate.go` — схема
  `rawNumerator`, нормализация legacy-строки, построение единственного
  `metadata.Field`, запреты неоднозначного формата.
- `internal/configcheck/lint.go` и публичная YAML-схема/описание — допустимые
  ключи `numerator.field` и диагностика конфликтов.
- `internal/launcher/configurator_types.go`, `configurator_load.go`,
  `configurator_entity.go`, `configurator_field_ids.go` — зеркальная save-модель,
  отделение стандартного поля от обычных реквизитов, перенос скрытых от формы
  свойств, переходы включения/выключения.
- `internal/launcher/configurator_tmpl_tree.go` — стандартное поле показывается
  внутри секции нумерации: имя и тип read-only, разрядность остаётся
  `numerator.length`, подписи редактируются там же. В таблицу обычных полей оно
  не отправляется.
- `internal/storage/schemaplan.go`, `schemaapply.go` — наблюдаемая
  неразрушительная операция перепривязки ID в `_schema_fields` и её атомарное
  применение.
- `internal/metadata/*_test.go`, `internal/launcher/configurator_*_test.go`,
  `internal/storage/*schema*_test.go` — контракты загрузки, публичного
  HTTP-round-trip и матрицы диалектов.
- `DEVELOPER.md`, `docs/features.md` и генерируемая подсказка конфигурации — новый
  канонический YAML и правила совместимости. Эти файлы меняются в продуктовых
  срезах, не в plan-PR.

Не меняются таблицы сущностей, имена колонок, `_numerators`, формат значений,
автонумерация в `entityservice`, запросы, REST/DSL и обмен: после загрузки они
по-прежнему видят обычный `metadata.Field`.

## Хранилище / SQL и атомарное восстановление

В `PlanTableChanges` вводится неразрушительный вид изменения
`ChangeRebindFieldID`: заменить владельца одной и той же колонки в
`_schema_fields` со случайного legacy-ID на `std_code`/`std_number`. Он попадает
в dry-run и отчёт миграции отдельной строкой, но не требует
`--allow-destructive` и не выполняет DDL.

Автоперепривязка допустима только когда одновременно верно:

- желаемое поле имеет зарезервированный стандартный ID и каноническое имя;
- запись с новым ID отсутствует;
- физическая колонка `код`/`номер` существует;
- ровно одна старая запись карты с другим ID указывает на эту колонку;
- старый ID не принадлежит другому живому полю, а колонка не нужна второму
  желаемому полю;
- сохранённая и желаемая сигнатуры поля совместимы; смена типа не маскируется
  перепривязкой.

Применение делает условный `UPDATE`/`DELETE + INSERT` по
`(table_name, old_field_id, expected_column)` и проверяет число изменённых строк.
Операция выполняется внутри существующего `WithTxScope` вместе с остальным
планом и `saveSchemaMap`. Если строка исчезла, появился целевой ID или дальнейшее
изменение схемы упало, откатывается и перепривязка. Два конкурирующих запуска не
могут оба подтвердить успех.

При двух старых ID на колонке, уже существующей конфликтующей записи
`std_code`/`std_number`, отсутствии колонки, несовпадении сигнатур или живом
использовании старого ID планировщик ничего не исправляет и возвращает
диагностику с таблицей, колонкой и обоими ID. Данные и карта остаются без
изменений.

## Совместимость и миграция

- Конфигурации без `numerator` не меняются.
- Канонический формат этапа 117 без явной строки уже совпадает с новым форматом;
  `numerator.field` нужен только для переопределений.
- Legacy-строка с каноническим или случайным ID принимается на чтение. Первый
  save через конфигуратор переводит её в новый формат; обязательной массовой
  переписи репозитория нет.
- База с картой `std_* → код/номер` продолжает работать: нормализация YAML даёт
  тот же желаемый ID. База с картой `f_* → код/номер` проходит безопасную
  перепривязку без DDL и без изменения данных.
- База без `_schema_fields` использует существующий путь первичного запоминания:
  найденная колонка сразу записывается за `std_*`.
- Старый бинарь проигнорирует неизвестный вложенный `numerator.field`,
  синтезирует поле с тем же именем/типом/ID и сохранит данные. На время отката он
  не увидит пользовательскую подпись и другие вложенные свойства, поэтому
  rollback-памятка требует не редактировать такую сущность старым
  конфигуратором. Возврат нового бинаря восстанавливает представление без
  миграции данных.
- Ручная строка `Код`/`Номер` при активном `numerator` остаётся поддерживаемым
  входом, но документация рекомендует `numerator.field`; это не hard migration
  исходников.

## Последовательность небольших PR-срезов

### Срез A — неразрушительная перепривязка карты схемы

Добавить `ChangeRebindFieldID`, строгий предикат однозначности, dry-run/report и
атомарное применение в `schemaplan.go`/`schemaapply.go`. Поведение обычных полей
не менять; срез подготавливает безопасный нижний слой до нормализации YAML.

Публичные тесты через `DB.Migrate` и `PlanTableChanges`, обязательно
`dbtest.ForEachDialect`:

- `f_* → std_code` и `f_* → std_number` сохраняют строки и физическую колонку,
  меняя только одну запись `_schema_fields`;
- второй план пуст;
- два старых владельца, занятый целевой ID и живой старый ID дают отказ без
  записей;
- ошибка последующего изменения той же таблицы откатывает уже выполненную
  перепривязку вместе со всем планом.

### Срез B — единый контракт загрузки YAML

Добавить `numerator.field`, нормализацию ровно одной legacy-строки и проверку
конфликтов. `Entity.Fields` во всех совместимых входах должен получать один
канонический стандартный `Field`. Обновить lint-схему, `DEVELOPER.md`, примеры и
пользовательское описание формата.

Публичные тесты через `metadata.LoadFile`, `project.Load`, `onebase check` и
настоящую миграцию:

- чистый, новый и legacy-YAML дают эквивалентную метаданность для справочника и
  документа;
- `title`/`label`, `titles`, `required`, `default`, `pii` переживают
  нормализацию, а имя/тип/ID остаются каноническими;
- два источника и две case-insensitive одноимённые строки отвергаются;
- обычный `Код` без `numerator` остаётся обычным;
- матричный сценарий «данные + старая карта `f_*` + новый loader + Migrate»
  сохраняет значения и заканчивается картой `std_*`.

### Срез C — каноническая запись конфигуратора

Разнести стандартное поле и обычные строки в view/save-модели, перенести
настройки в секцию нумерации и заменить `withStandardFieldSeed` на явное
извлечение/материализацию. Один алгоритм используется для файлового и DB-режима
хранения конфигурации.

Публичные тесты отправляют реальную HTML-форму в
`configuratorSaveFields`, затем читают сохранённый YAML через `project.Load`:

- добавление постороннего реквизита не записывает `Код`/`Номер` в `fields`;
- испорченный `f_*` преобразуется в `numerator.field`, свойства и
  `numerator.length` не теряются;
- файловый и DB-режимы дают одинаковый результат;
- выключение нумерации материализует поле с `std_*`, повторное включение
  поглощает его обратно, данные после `Migrate` неизменны;
- повторное сохранение байт-стабильно после нормализации;
- негативные случаи из #1199 остаются закрыты: пользовательский `Код` без
  нумерации и `Код` документа не получают чужой служебный ID.

## Риски и откат

- **Ложная перепривязка ID.** Снижается точным allowlist стандартных ID,
  совпадением колонки/сигнатуры и требованием единственного кандидата. Любая
  неоднозначность — отказ до записи.
- **Потеря скрытых от формы свойств.** Перенос строится из исходного YAML и
  отправленной формы вместе, а полноту зеркальных ключей охраняют структурные
  тесты `rawNumerator ↔ saveNumerator` и round-trip каждого поддерживаемого
  свойства.
- **Смешение выключения нумерации с удалением поля.** Переход материализует поле
  до удаления блока и проверяется dry-run без разрушительных операций.
- **Гонка миграций.** Условная DML-перепривязка и проверка affected rows живут в
  одной транзакции с `saveSchemaMap`; проигравший запуск откатывается.
- **Откат бинаря.** Данные и схема совместимы, но старый конфигуратор не знает
  `numerator.field`. До возврата новой версии конфигурацию не сохранять; при
  необходимости временно развернуть вложенные свойства обратно в legacy-строку
  с ID `std_*`.

Откат каждого среза — обратный коммит. После уже выполненной перепривязки
возвращать случайный `f_*` не нужно: этап 117 изначально закрепляет колонку за
`std_*`, а старые бинарники понимают этот ID. Ни откат, ни повторное применение
не требуют копирования или восстановления пользовательских строк таблиц.

## Критерии завершения

- Конфигуратор в обоих режимах хранения не пишет стандартное поле в `fields`
  при активном `numerator`.
- Новый и legacy-форматы дают ровно одно поле с каноническими именем, типом и ID;
  поддерживаемые пользовательские свойства сохраняются.
- Обе исторические карты `_schema_fields` (`std_*` и `f_*`) мигрируют без DDL и
  потери значений; неоднозначные состояния fail-closed.
- Включение/выключение нумерации не создаёт разрушительного плана и
  идемпотентно.
- Публичные round-trip и SQLite/PostgreSQL matrix-тесты зелёные, полная сборка и
  `go test ./...` проходят.
- Документация называет `numerator.field` каноническим форматом и содержит
  rollback-памятку.
