# Этап 204 — Устойчивая пагинация order_by и явный dir без sort

## Контекст и выбранный вариант

Ведущая заявка: [#1713](https://github.com/ivanarama/onebase/issues/1713).
Связанный дефект REST: [#1714](https://github.com/ivanarama/onebase/issues/1714).
Каноничный триаж — комментарий `5848364422` автора `ivanarama`; выбран
рекомендованный **вариант 2**, подтверждённый handoff `6086076623`:

- без явного направления использовать `order_by`, дописав уникальный `id ASC`;
- при явно переданном `dir` без `sort` использовать `id` в этом направлении;
- реализовать оба дефекта одной работой по #1713, без отдельного FIX по #1714.

Проверено по `main` **85855213b6655c1e67698173713a60e617377e4d** (09.10.2026).
`storage.DB.List` добавляет `id ASC` только когда список ключей `order_by`
полностью пуст. При действующих ключах равные строки остаются без уникального
порядка; `Dir` в этой ветке не читается. OFFSET режет этот неопределённый
порядок на страницы. Конкретное случайное дублирование страниц триаж не поймал:
основание дефекта — отсутствие полного порядка, а не обещание воспроизвести
особенность планировщика на каждой СУБД.

[План 189](189-document-creation-order.md) упоминает #1713 только в разделе
«Дальше (вне плана)». `_seq` из него не является предпосылкой этой работы:
UUID `id` уже уникален, а его порядок здесь не объявляется хронологическим.
[#1724](https://github.com/ivanarama/onebase/pull/1724) меняет умолчания списков
без `order_by` в том же `crud.go`. Это пересечение кода, требующее сверки при
реализации и после обновления базы ветки, а не основание объединять PR задним числом.

## Синтаксис / YAML и наблюдаемая семантика

Новых YAML-полей и HTTP-параметров нет. Пример существующей конфигурации:

```yaml
order_by: [ПорядокВОтчётах, Наименование]
```

Матрица приоритетов для `DB.List`:

| Вход | Порядок |
|---|---|
| `AfterID` или `ThroughID` | Существующий keyset: только `id ASC`, прежние проверки `Sort`, `Dir`, `Offset` |
| Непустой `Sort` | Существующая явная сортировка по выбранному полю; `Dir` применяется по прежнему правилу |
| Пустой `Sort`, непустой `Dir` | **`id DESC` для `desc` без учёта регистра, иначе `id ASC`** |
| Пустые `Sort` и `Dir`, непустой `OrderBy` | Все ключи метаданных с прежними направлениями и обработкой пустоты, затем **`id ASC`** |
| Пустые `Sort`, `Dir` и `OrderBy` | Прежнее умолчание актуального main, включая иерархию и принятые изменения #1724 |

Явное направление определяется непустым `ListParams.Dir`: HTTP-парсеры уже
сохраняют эту информацию, отдельный флаг присутствия не нужен. `?dir=` эквивалентен
отсутствию направления. Для неизвестного непустого значения сохраняется
существующая нормализация направления в ASC; новая ошибка 400, обрезка пробелов
и новое правило повторяющихся query-параметров в эту работу не входят.

При `?dir=asc` или `?dir=desc` без `sort` пользователь сознательно выбирает
порядок UUID вместо метаданных. Для иерархического каталога это также чистый
`id`, без скрытого префикса `is_folder DESC`; отбор по родителю, доступность
групп и построение дерева не меняются. Без явного направления группы по-прежнему
первые, а тай-брейкер находится **после всех** ключей метаданных.

Инварианты ветки `order_by`:

1. Равенство всех пользовательских ключей завершается сравнением уникального
   `id ASC`, включая равенство всех ключей у групп и пустых строк.
2. `NULL` и `''` остаются одним классом пустоты для текстовых/перечислимых
   полей, для которых код уже считает пустую строку незаполненной. Этот класс
   остаётся в конце при ASC и DESC; внутри него работают следующий ключ и `id`.
3. Направления в `OrderBy` не инвертируются из-за `dir`. Выбран вариант 2.
4. Числовое выражение, dialect-specific CAST и сопоставление строк не меняются.
   План не обещает устранить отдельные ограничения точности SQLite/колляций.
5. При устаревших метаданных неизвестные ключи пропускаются как сейчас;
   финальный `id ASC` остаётся даже когда валидных ключей нет. Для иерархии
   сохраняется `is_folder DESC, id ASC`.
6. RLS, фильтры, поиск, проекция колонок, `CountList`, лимит и смещение остаются
   прежними. Порядок строится только из проверенных метаданных и служебного `id`.

Гарантия OFFSET относится к **неизменному набору строк и значений ключей**:
повторный обход страниц получает одну последовательность без повторов и потерь.
Вставка, удаление или изменение ключа между запросами может сдвинуть OFFSET;
snapshot между HTTP-запросами и keyset по составному `order_by` здесь не вводятся.
Явная сортировка по неуникальному `sort` остаётся отдельным сценарием и не получает
новую гарантию полной упорядоченности от этого плана.

## Хранилище / SQL, совместимость и миграция

DDL, перенос данных, номер схемы и `_seq` не нужны. У `id` уже есть уникальность.
В типовом случае SQL заканчивается так:

```sql
ORDER BY
  CASE WHEN порядоквотчётах IS NULL THEN 1 ELSE 0 END ASC,
  CAST(порядоквотчётах AS NUMERIC) ASC,
  CASE WHEN (наименование IS NULL OR наименование = '') THEN 1 ELSE 0 END ASC,
  CASE WHEN (наименование IS NULL OR наименование = '') THEN NULL ELSE наименование END ASC,
  id ASC
```

Это иллюстрация SQLite, реальные имена берутся из `metadata.ColumnName`.
Для PostgreSQL сохраняется существующее выражение числа без этого CAST.

Старые конфигурации начинают получать определённый порядок равных ключей.
Клиенты с явным `dir` снова получают UUID-порядок. Клиент, раньше передававший
`dir=asc` как нейтральное умолчание и ожидающий `order_by`, должен убрать параметр.
Это описывается в `DEVELOPER.md`, описаниях REST/OpenAPI и заметке об изменении
поведения в `CHANGELOG.md` в продуктовых PR. Существующие версии и способы
авторизации REST не меняются.

## Последовательность PR-срезов и публичные тесты

### Срез A — Полный порядок метаданных (#1713)

Одна локальная правка построения SQL: дописать `id ASC` после всех частей
`OrderBy`, заменив условный fallback. Комментарий `ListParams` должен правильно
описывать уже существующее умолчание. Без изменения `Dir` в этом срезе.

Тесты через `DB.Migrate`, `DB.Upsert`, `DB.List` и `dbtest.ForEachDialect`:

- фиксированные UUID, вставка в обратном/перемешанном порядке; одинаковый числовой
  ключ, несколько страниц по 1 и 2 строки, последняя неполная страница;
- составные ключи с ASC/DESC: tie по первому, затем по всем ключам;
- отдельно `NULL`/`''` для текста с равным вторичным ключом и различным вторичным
  ключом; пустой числовой ключ; число 3/20/100 для сохранения текущего CAST;
- иерархия: несколько равных групп и элементов, ожидаемый порядок
  `is_folder DESC → ключи → id ASC`;
- неизвестные ключи устаревшего объекта метаданных: fallback по id, включая группы;
- объединённые UUID страниц точно равны заранее заданному эталону и полной
  выборке с теми же фильтрами; повторный обход равен первому;
- прежние explicit-sort и keyset-тесты проходят.

Проверяется конкретный ожидаемый UUID-порядок. Одного сравнения двух запросов
или надежды на случайное дублирование недостаточно: СУБД может случайно выдать
тот же порядок и без исправления. Фикстуры намеренно противопоставляют порядок
вставки и UUID; проверка состава страниц обязательна для всех диалектов.

### Срез B — Явный dir и поставка общего контракта (#1714)

Добавить ветку `Sort == "" && Dir != ""` до обоих умолчаний. Она выбирает
чистый уникальный id в прежней нормализации направления. API и UI не должны
подставлять ASC при отсутствии `dir`. Сигнатуры парсеров менять не требуется.

Публичные тесты:

- матрица `DB.List` для отсутствующего/пустого/ASC/DESC/смешанного регистра и
  неизвестного непустого `Dir`, при пустом и непустом `OrderBy`, плоской и
  иерархической сущности; отдельные проверки явного `Sort` и keyset;
- HTTP через настоящий роутер: REST v1 `/catalogs/<имя>` и REST v2
  `/api/v2/catalog/<имя>`, `limit=2`, offset/page; порядок метаданных намеренно
  обратен id, так что пропуск `Dir` или искусственное ASC видны в ответе;
- страницы REST v2 и v1 при `dir=desc` дают эталон UUID DESC без повторов;
  total/заголовки счётчика и фильтры остаются прежними;
- HTTP UI `/ui/catalog/<имя>`: отсутствие `dir` сохраняет метаданные, `dir=desc`
  даёт id DESC, ссылка следующей страницы сохраняет направление; явный sort
  остаётся override; выгрузка и ссылочный подбор используют тот же контракт;
- пользователь с RLS получает только доступные ему строки на каждой странице,
  запрос без read запрещён как прежде; новые маршруты обхода RBAC не создаются.

Матричные HTTP-тесты строятся на `dbtest.ForEachDialect`; при необходимости
добавляется отдельный `internal/api/list_order_matrix_test.go`. В CI нужно
явно включить этот API-пакет в прогон с `TEST_DATABASE_URL`, актуальный
postgres-integration не запускает его: локальный SQLite не доказывает
HTTP-паритет PostgreSQL. Документация REST и CHANGELOG входят в этот срез.

Каждый срез проходит обычное REVIEW и отдельный человеческий `ship`; слияние
плана не является разрешением на поставку кода. Если безопасного автоматического
next-slice handoff для этой issue ещё нет, срез B маршрутизируется отдельно
доверенным решением сопровождающего, а завершение A не закрывает всю #1713.
Продуктовый delivery PR завершает ведущую issue только после A+B; связанную
#1714 закрывает тот же конечный PR с обоими английскими closing references.

## Риски и откат

- Старый клиент с автоматически добавленным `dir` увидит другой порядок.
  Документация и HTTP-тесты отсутствия параметра входят в обязательную поставку.
- #1724 меняет соседнюю ветку умолчаний: при rebase сохранить его пользовательские
  умолчания только для запроса без sort/dir; повторить матрицу после интеграции.
- Финальный ключ может повлиять на SQL-план/стоимость сортировки. Проверить
  время типового постраничного списка на репрезентативном наборе; новые индексы
  и изменение колляций не вводить без отдельного обоснования.
- UUID-порядок различим от времени создания; `_seq` не подменяет выбранный id.
- Параллельные изменения данных не превращаются в snapshot от тай-брейкера;
  это ограничение должно оставаться явно указанным в документации.

Откат — revert соответствующего продуктового среза и его документации.
Данные и схема остаются совместимы; откат A возвращает неопределённость ties,
откат B снова оставляет `dir` без sort зависимым от старой ветки. Компенсирующая
миграция не нужна. До завершения B общий маршрут не объявлять исправленным.

## Критерии завершения и эстимейт

- A: в metadata-order всегда есть конечный `id ASC`; матричный эталон страниц
  покрывает равные, пустые и составные ключи, иерархию и stale metadata.
- B: реальный HTTP v1/v2 соблюдает таблицу приоритетов, включая `dir` без sort;
  UI, подбор, экспорт, RLS и keyset прошли регрессионные проверки.
- PostgreSQL-тесты действительно выполнены в CI, а не только отмечены Skip;
  обязательные проверки конвейера зелёные для поставляемого HEAD.
- Контракт и ограничение OFFSET описаны; #1714 не имеет конкурирующего FIX;
  закрытие обоих дефектов связано с конечным delivery PR, а не с plan PR.

A — 0,75–1,25 дня; B с HTTP-матрицей, документацией и CI-подключением API —
1,25–2 дня; интеграционная сверка #1724 и приёмка — 0,25–0,5 дня.
Итого **2,25–3,75 дня**, без нового механизма snapshot/keyset по составным ключам.
