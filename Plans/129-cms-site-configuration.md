# План 129 — Сайт на OneBase: конфигурация CMS (`examples/cms`)

Дата проектирования: 2026-08-17.
Статус: 🟡 **Частично реализовано** 2026-08-18 (PR #983).

Сделано: C1, C3–C7, C9–C12 — каркас, роутер со слагами/редиректами/404,
рендер на шаблонах, SEO (`<head>`, sitemap, robots), публикация медиа, кэш с
инвалидацией в `ПриЗаписи`, поиск, демо-контент и `onebase test`, README,
импорт из YML. C8 сделан без письма: заявка сохраняется, honeypot и
ограничение частоты работают, уведомление на почту не отправляется.

Не сделано: **управляемые формы** из C2 (каталога `forms/` нет — контент
правится через автогенерируемые формы), **письмо по заявке** (C8),
**витрина товаров** (`Товары` и `КатегорииКонтента` заполняет импорт C12, но
страниц каталога на сайте нет) и **правила `МаршрутыURL`** из C3 — справочник
заведён, роутер подбирает контент по слагу.

Ветка: `feature/129-cms-example`.
Уровень: **прикладной** — YAML + DSL, правок движка не требует (кроме
опциональной мелочи в разделе 10).
Зависимости: планы **124** (регексы), **125** (HTML-шаблоны), **126** (кэш
ответов), **127** (публичные URL файлов), **128** (сжатие/заголовки).

## Контекст

Заказчик (сайт nortena.ru на 1С-Битрикс) просит уйти с Битрикса и вести сайт в
той же системе, где ведётся учёт. Прислана конфигурация `SiteNortena` и ТЗ
«довести до полноценной CMS» (`C:\Project\CMS\ТЗ-доработка-CMS.md`).

Что прислано по факту: 5 справочников (Товары, СтилиСайта, ШаблоныСайта, Сайты,
Блоки), 3 маршрута (`/`, `/catalog?group=`, `/product?group=`), общий модуль на
650 строк и `демоданные.module.os` на 7516 строк — автогенерированный дамп
каталога nortena.ru. То есть содержательного кода ~700 строк, остальное —
фикстура; HTML собирается конкатенацией строк, CSS и HTML-макет лежат в полях
`type: string`.

Разбор ТЗ (сделан отдельно) дал границу: вся CMS-семантика — прикладная, в ядро
идут только универсальные веб-примитивы (планы 124–128), каждый из которых
полезен вне сайта. Этот план — прикладная часть.

## Принятые решения

1. **Эталон живёт в репозитории платформы: `examples/cms/`.** Не в конфигурации
   заказчика. Причины:
   - CI уже гоняет `onebase check`, `migrate`, `procrun ЗаполнитьТестовуюБазу` и
     `onebase test` по всем `examples/*` (`.github/workflows/ci.yml:61,97,103,125`)
     — конфигурация не сгниёт молча при изменениях движка;
   - это витрина «сайт на OneBase», а не разовая поставка;
   - сайт nortena.ru собирается как производная: `examples/cms` + свои стили,
     шаблон и контент.
   **Подтверждено владельцем платформы 2026-08-17.** Конфигурация заказчика
   (сайт nortena.ru) собирается как производная от эталона, а не наоборот.
2. **Демо-данные — отдельная обработка, не боевой путь.** В присланной
   конфигурации `ГарантироватьДемоДанные()` вызывается на каждом HTTP-запросе
   (`общие.module.os:8`, `Nortena.service.os`). В `examples/cms` наполнение
   делает обработка `ЗаполнитьТестовуюБазу` (имя обязательное — его зовёт CI).
   Боевой сайт стартует пустым.
3. **HTML собирается шаблонами (план 125), а не конкатенацией.** Правило без
   исключений: любое значение из базы попадает в вывод через `{{.Поле}}`
   (автоэкранирование) или через `БезопасныйHTML(...)` (санитайзер) — и никак
   иначе. Это единственная защита от XSS на публичном контуре.
4. **Контентный контур — общий набор реквизитов** у всех контентных
   справочников: `Слаг`, `Активен`, `ДатаПубликации`, `ЗаголовокSEO`,
   `ОписаниеSEO`, `OGКартинка`. Одинаковые имена → один код рендера и роутера
   на все типы (идея инфоблоков Битрикса, но без второго уровня «тип инфоблока»).
5. **Роутер — таблица правил, а не «поиск слага».** Справочник `МаршрутыURL`:
   шаблон → тип контента → рендер. Даёт SEF-подобную гибкость Битрикса
   (`/catalog/<группа>/<товар>`) и обратную совместимость со старыми
   `?group=`-адресами через `Редиректы` (301).
6. **Публикация: `СтатусПубликации` (Черновик/Опубликовано/Архив) + условие
   `ДатаПубликации <= Сейчас`.** Документы с проведением для этого не заводим —
   реквизита достаточно, а история правок контента ждёт платформенного
   версионирования данных (не в этой группе планов; ТЗ 7.4).
7. **Медиа — вложения платформы + публикация (план 127).** Своё хранилище
   файлов не изобретаем. Внешний CDN из демо-данных остаётся только в демо.
8. **Кэш — обязателен для публичного сервиса** (план 126, `auth: none`), а
   инвалидация — обязанность конфигурации: `КэшСервисов.Очистить("Сайт")` в
   `OnWrite` контентных справочников. Без этого правка страницы не видна до
   истечения TTL, и это выглядит как поломка.
9. **Сайт живёт под `/hs/<root>/`.** Корневой домен (`root_url: ""`) в этой
   группе планов не делаем: приоритет над `/ui`, `/api`, `/hs` — отдельный
   риск, а reverse proxy (nginx/Caddy) решает задачу без правок движка.
   Инструкция по proxy — в README конфигурации.
10. **Многосайтовость — по `Host`** (справочник `Сайты`, поле `Домен`). Ссылка
    выбранного сайта обязательным параметром ограничивает все публичные
    выборки контента, маршрутов, меню, sitemap и поиска; при промахе по Host
    чужой сайт не используется как запасной. `КатегорииКонтента` остаются
    общей таксономией базы и по сайту не фильтруются.

## Модули (`examples/cms/src/`)

| Модуль | Содержимое |

| `медиа.module.os` | `СсылкаНаМедиа(Медиа)` — публикует вложение при первом обращении (план 127), кэширует ссылку в реквизите |
| `слаги.module.os` | `Слаг(Строка)` — транслитерация + нормализация регексом (план 124); `ПроверитьУникальность` |
| `формы.module.os` | Валидация полей (регексы), honeypot, запись `Заявки`, письмо (`ОтправитьПисьмо`) |
| `общие.module.os` | Хуки `OnWrite` контентных справочников: сброс кэша (`КэшСервисов.Очистить("Сайт")`), генерация слага, пересчёт sitemap-метки |

HTTP-сервис `services/Сайт.yaml`:

```yaml
name: Сайт
root_url: site
auth: none
rate_limit: 600
compress: true                      # план 128
cache:                              # план 126
  ttl: 60
  vary: [query, host]
  public: true
security_headers:                   # план 128
  csp: "default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'"
  frame_options: DENY
templates:
  - template: /sitemap.xml
    methods: { GET: ОтдатьSitemap }
  - template: /robots.txt
    methods: { GET: ОтдатьRobots }
  - template: /search
    methods: { GET: ОтдатьПоиск }
  - template: /api/forms/{код}
    methods: { POST: ПринятьЗаявку }
  - template: /{*путь}
    methods: { GET: Роутер }
```

Порядок шаблонов важен: `{*путь}` последний, иначе он перехватит всё.

## Роли (`examples/cms/roles/`)

- `КонтентМенеджер` — чтение/запись Страниц, Новостей, Меню, Медиа, Заявок;
  **без** доступа к Стилям/Шаблонам/Блокам/МаршрутамURL, без конфигуратора,
  без обработок с сетью.
- `РедакторСайта` — то же + Стили/Шаблоны/Блоки/Маршруты.
- Проверка ролей — **под не-админом** (грабля из заметок: право на обработку
  надо выдавать явно, `processors: X: [run]`).

## Приёмка

1. На **чистой** базе (без демо-данных) через веб-интерфейс создаётся сайт:
   главная, «О компании», «Контакты», 3 новости, меню в шапке и подвале.
2. Адреса: `/`, `/about`, `/news`, `/news/<слаг>`, `/catalog/<группа>`,
   `/product/<товар>`; несуществующий → 404 со своим шаблоном; старый
   `?group=` → 301 на ЧПУ.
3. `<head>` содержит title/description/canonical/OG; `/sitemap.xml` и
   `/robots.txt` отдаются.
4. Картинки загружены в Медиа и отдаются по `/pub/<токен>` с `Cache-Control`.
5. **XSS-проверка приёмки:** товар с именем `<script>alert(1)</script>`
   отображается как текст; richtext-описание с `<script>` теряет скрипт, но
   сохраняет форматирование.
6. Повторный запрос страницы не исполняет DSL (метрика `http_cache_hits_total`
   растёт); нагрузочный прогон ≥ 100 req/s на SQLite.
7. Правка страницы сбрасывает кэш — изменение видно следующим запросом.
8. Роль `КонтентМенеджер` не видит Конфигуратор, не может править Шаблоны,
   не может включить сеть. Проверено входом под не-админом.
9. `onebase check --project examples/cms` — без ошибок; `onebase test` — зелёный.

## 10. Побочные правки платформы, вскрытые конфигурацией

**Редактирование HTML/CSS в карточке справочника.** В форке заказчика правили
`internal/ui/templates_managed.go`, чтобы `<textarea>` для HTML-макета была выше
пяти строк (отчёт `ВысотаСтрок.MD`). **Правка не нужна**: в актуальной
платформе есть `kind: ПолеКода` (`templates_managed.go:55`) — textarea на 12
строк с редактором кода и подсветкой по `language`. Конфигурация обязана
использовать `ПолеКода` с `language: html`/`css` для МакетHTML, CSS и
Содержимого блоков, а не `ПолеВвода` + `multiline`.

Что при этом остаётся правдой и стоит небольшой правки (**опционально,
отдельным микро-PR, не блокирует план**):

- `rows="5"` у `multiline`-варианта `ПолеВвода` (`templates_managed.go:146`)
  и `height:320px` у контейнера редактора кода (`:66`) зашиты жёстко;
  `FormElement.Height` (`internal/metadata/form_module.go:172`) на них не
  влияет. Прокинуть `height` в `rows` (для multiline) и в `height` контейнера
  (для `ПолеКода`) — обратно совместимо (при незаданном `height` поведение
  прежнее), даёт конфигурации управление высотой длинных текстовых полей.
- Семантика `height` при этом остаётся разной для разных видов элементов (px у
  картинок, строки у textarea) — если владелец платформы хочет строгости, ввести
  отдельный ключ `rows:`; решение за ним.
- Тест: managed-форма с `height: 10` рендерит `rows="10"`, без `height` —
  `rows="5"`.

## Границы (чего не делаем)

- Корзина, заказы, оплата, личный кабинет — отдельное ТЗ.
- Визуальный конструктор страниц (drag-and-drop).
- Мультиязычный контент (только структура: поле `Язык` у сайта).
- История версий контента (ждёт платформенного версионирования данных).
- Комментарии, RSS, счётчики просмотров — после приёмки, если попросят.
- Маркетплейс тем.
