# Этап 187 — ввод ссылки по строке и событие «АвтоПодбор»

## Контекст и решение

Ведущая issue #1529, включая сценарий #1623: оператор на форме `А_Заявка` должен найти улицу или дом среди примерно 2,1 млн адресов, напечатав начало названия прямо в ссылочном поле, и записать UUID выбранной записи. Сейчас верхнеуровневое поле управляемой формы — `<select>` и кнопка «…»; поиск находится в отдельном picker. Доверенный triage #1529 рекомендует вариант 1: сначала отдельный план, затем малые PR-срезы для безопасного combobox и прикладного `АвтоПодбор`.

План опирается на `main` `a4509741b8b8ab92ecaf357185f8fb0d85b837a8` (2026-09-27). Со времени triage состояние изменилось: `choice_filter` v1 уже определён в `internal/metadata/form_module.go`, а `/ui/_ref-options/<entity>` восстанавливает условия из серверных метаданных через `resolveChoiceRequest`. Issue #1303 ещё открыта; перед расширением семантики отбора нужно сверить её фактический остаток. Для глубоких источников и табличных частей есть отдельный план 183 (#1552). Уже существующий v1 применяется к новому контролу в первом срезе; обещать поведение v2 до его реализации нельзя.

## Наблюдаемая семантика и инварианты

1. Редактируемый ссылочный `ПолеВвода` принимает строку. После 2–3 символов и короткой задержки запрашивает первые ограниченные результаты через существующий `/ui/_ref-options/<entity>?q=...`; запрос включает тот же серверный контекст `choice_filter`, что и picker. Никакой загрузки миллионов строк в HTML или браузер нет. Кнопка «…» и открытие текущей карточки сохраняются.
2. Видимая подпись и значение ссылки — разные состояния. Единственный отправляемый при сохранении реквизит `name=<поле>` содержит UUID выбранной серверной строки либо пустую строку при явной очистке. Текст поиска никогда не становится UUID и не записывается как значение. Ввод после выбора инвалидирует прежний UUID; Enter выбирает подсвеченную строку, но не произвольный текст и не неоднозначное совпадение. Пустой запрос не выбирает первый результат. Ошибка сети не должна подставлять старый UUID.
3. `↑`/`↓` двигают активный вариант, `Enter` выбирает, `Esc` закрывает список, `Tab` переводит фокус без неявного выбора. Мышь выбирает ту же строку. Связка label/input/listbox/option использует роли ARIA, `aria-expanded`, `aria-controls`, `aria-activedescendant`; результаты и ошибки доступны экранному диктору. `required`, постоянный и условный readonly, скрытие элемента, `ПриИзменении`, inline create и обработчики открытия карточки не теряют прежний смысл.
4. Ответ применим только к живому полю с тем же поисковым текстом, выбранным UUID и fingerprint источников `choice_filter`, что были при отправке. Новый ввод, изменение источника, закрытие формы и программное обновление значения отменяют запрос или увеличивают поколение; даже ответ на уже отправленный запрос не может вернуть устаревший список. При `selected_allowed=false` прежняя ссылка очищается с наблюдаемым `change`; при ошибке обновления связанного отбора fail-closed, без локального обхода через предзагруженные опции.
5. Кандидаты остаются серверно авторизованными: endpoint проверяет право чтения, row filter, `search_fields`, `choice_filter` и маскирование до вычисления `_label`. Клиент показывает `_label` как текст. Предзагруженные опции не становятся альтернативным источником кандидатов при защищённом поиске. На POST серверная запись принимает только UUID и повторно применяет существующую проверку типа ссылки/прав записи; клиентская подпись не является доказательством прав.
6. Существующие конфигурации без `АвтоПодбор` получают базовый поиск. Событие не запускается на чтении формы, при простом открытии picker или при выборе готовой строки; оно запускается на вводе после порога и только у ссылочного `ПолеВвода` с обработчиком. Неизвестный или неподходящий элемент не может вызвать его через ручной POST.

## Синтаксис / YAML и контракт `АвтоПодбор`

Первый срез не добавляет YAML: объявленные `search_fields` и `choice_filter` продолжают действовать. Во втором срезе используется уже известное имя события на элементе ссылочного ввода:

```yaml
kind: ПолеВвода
name: Улица
data_path: Объект.Улица
events:
  АвтоПодбор: АвтоПодборУлицы
```

Контракт второго среза: обработчик получает неизменяемую строку запроса и текущий контекст формы, возвращает ограниченный список **ID записей целевой сущности** в заданном порядке либо не вмешивается и оставляет стандартный поиск. Пустой результат означает пустую выдачу, ошибка видна пользователю и не вызывает fallback к более широкой выдаче. Произвольные подписи/HTML и смена целевой сущности не принимаются. Перед ответом сервер повторно проверяет каждый ID теми же правами, row filter, `choice_filter` и маскированием, что у стандартного endpoint; недоступные строки исключает. Лимит результатов, размер ввода и время выполнения ограничены. Конкретную DSL-сигнатуру и сериализацию результата закрепить тестом публичной формы в PR-срезе события до документирования; совместимость с конвертером 1С означает сохранение имени события, а не обещание полной семантики 1С.

## Хранилище / SQL

Схема БД и миграция не нужны: сохраняется существующий UUID ссылочного поля. Серверный поиск использует `storage.List`/`CountList` с ограничением выдачи и условиями доступа. Приёмка на большом каталоге должна подтвердить, что страница формы и каждый ввод не вызывают полного перечисления записей; если текущий поиск сканирует слишком дорого, оптимизацию индекса или поискового пути вынести в измеряемый отдельный PR до включения сценария 2,1 млн записей в критерии готовности.

## Совместимость и переход

Старые сохранённые UUID отображаются с подписью через существующую загрузку выбранной опции, включая запись вне текущей страницы. Если ссылка вне нового `choice_filter`, форма может показать сохранённое значение, но не предлагать его как кандидат; изменение источника следует существующему `selected_allowed`. Неизвестный/удалённый UUID нельзя превращать в пустое значение без явного решения пользователя или серверного сигнала. Для форм обработок без загруженных `RefOptions` сохранить текущий текстовый fallback до отдельного подтверждения контракта их ссылочных реквизитов. Автоформы и табличные части сохраняют свои контролы до самостоятельного среза. Перехода данных нет; откат двух срезов — возврат старого UI/диспетчера, уже записанные UUID остаются совместимыми.

## Последовательность PR-срезов и публичные тесты

1. **Combobox.** Заменить верхнеуровневые редактируемые ссылочные поля управляемой формы, связать их с существующим endpoint, picker и `choice_filter` v1. HTTP/DOM тест через GET формы → ввод текста → защищённый GET `/ui/_ref-options` → выбор Enter/мышью → POST создания и правки → чтение записанного UUID. Отдельно: сотни и 2,1 млн записей без полной выдачи, RLS/маскирование, пустой/неоднозначный ввод, очистка, required/readonly/условный readonly, внефильтровое старое значение, смена источника, сетевой отказ и обратный порядок ответов, сущность и реквизит формы. Проверить picker, программное `applyValues` и экранный диктор/клавиатуру через пользовательский путь.
2. **`АвтоПодбор`.** После зелёного первого среза добавить событие и ограниченную выдачу ID с повторной серверной проверкой. Тест через ввод на реальной managed-форме и её публичный event/choice endpoint: handler меняет порядок/состав разрешённых ID; недоступный ID, чужая сущность, поддельный element/event, readonly и ошибка обработчика не расширяют выдачу. Проверить конфигурацию, импортирующую имя события из 1С, и исчезновение `АвтоПодбор` из предупреждения `form.event-not-dispatched`. Зафиксировать отличие от 1С в документации.
3. **Связанный отбор и масштаб, если остаётся пробел #1303.** Перед срезом сверить #1303 и план 170 с `main`: v1 уже участвует в срезе 1, поэтому отдельный PR нужен только для обнаруженной недостающей семантики или производительности. Публичный тест формы `А_Заявка`: улица зависит от выбранного адресного контекста, дом — от улицы; смена улицы инвалидирует старую выдачу домов и не допускает чужой UUID. Если зависимость относится к deep-source/ТЧ, маршрутизировать её по плану 183, не расширяя этот срез без решения.

Каждый продуктовый PR запускает `go build ./...`, затронутые Go/JS тесты, `onebase check` на конфигурации примера и проверку переводов; тесты данных запускаются на SQLite и PostgreSQL через `dbtest.ForEachDialect`, где меняется семантика SQL. Проверки идут через публичный HTTP/форму, а не только приватные функции.

## Риски, откат и критерии завершения

Риски: расхождение текста и UUID, потеря значения при программном обновлении формы, гонки ответа и источников фильтра, утечка через подпись, недоступность клавиатурой, дорогой поиск на большом каталоге. Все они имеют отдельные сценарии выше. Не создавать ведомые issues или метки `hold` одним plan-PR: после его merge маршрут и приоритеты оформляются отдельным handoff по канонической процедуре.

План выполнен, когда оператор заполняет ссылку из крупного каталога с клавиатуры без модального picker, в записи оказывается выбранный UUID, поиск учитывает права и актуальный отбор, `АвтоПодбор` реально вызывается только для разрешённого элемента и не может показать чужую запись. Открытая #1303 или план 183 остаются отдельными зависимостями только для ещё не реализованной глубокой семантики отбора.

## Verification и эстимейт

Ручной маршрут: открыть `А_Заявка`, набрать начало улицы, выбрать стрелками и Enter, выбрать дом, записать форму, переоткрыть и сравнить UUID/подпись; повторить с пользователем без доступа и со сменой исходного реквизита в момент запроса. Повторить ввод с обработчиком `АвтоПодбор` и с выключенным обработчиком. Оценка: combobox 3–5 дней, событие 2–3 дня, сверка/остаток связанного отбора и масштабирования 1–3 дня после замера; время на review и приёмку отдельно.
