# План 160 — явные права на обработки и переход к fail-closed

Дата проектирования: 2026-09-07.
Статус: 📋 **проектирование**, код не начат.
Уровень: **безопасность и совместимость** — роли, авторизация обработок,
конфигуратор ролей, lint и пользовательская документация.
Заявка: [#1191](https://github.com/ivanarama/onebase/issues/1191).
Выбранный вариант: **1** — сначала сделать неявный доступ видимым и дать
совместимый способ зафиксировать решение каждой роли, затем в объявленном
минорном релизе перевести отсутствие `permissions.processors` в запрет.

Plan-PR не меняет продуктовый код. Реализация должна идти небольшими срезами:
переходный срез не меняет действующий доступ, а несовместимое переключение не
вливается до выпуска предупреждения и миграции конфигураций.

## Контекст

У всех обычных видов объектов отсутствие записи в роли означает отсутствие
доступа. Для обработок сейчас действует единственное исключение:

- `internal/auth/roles.go:User.Has` немедленно разрешает любую обработку, если
  хотя бы у одной роли пользователя `Permissions.Processors == nil`;
- `internal/auth/roles.go:PermissionHas` независимо повторяет ту же ветку;
- `processors: {}` создаёт non-nil карту и запрещает всё, а отсутствующая
  секция и `processors: null` дают `nil` и разрешают всё;
- `CheckLintRoles` считает любой такой `nil` глобальным покрытием и поэтому не
  сообщает ни об открытой роли, ни об обработках без явного владельца.

Это не только пункт меню. Производственные GET/POST обработок проходят через
`getProcessor` → `requirePerm(..., "processor", name, "run")`; тем же правом
защищены события управляемой формы обработки и запуск из AI actions. Поэтому
неявное разрешение открывает код обработки, который может писать данные,
читать файлы и использовать сетевые builtins.

Документация усиливает ошибочное ожидание: пример роли в `DEVELOPER.md`
перечисляет каталоги, документы, регистры и отчёты, но не показывает
`processors`; компактная схема роли в `internal/launcher/ai_generate.go`
делает то же. Автор конфигурации не видит, что роль получила все обработки.

## Цели и границы

План должен:

1. дать одному месту в `internal/auth` владеть семантикой processor-permission;
2. в переходном релизе предупреждать о каждой роли с неявным allow-all, не
   меняя её фактический доступ;
3. дать три явных состояния: запретить всё, перечислить разрешённые обработки
   или осознанно сохранить глобальный доступ;
4. подготовить файловые и database-backed конфигурации к переключению;
5. в следующем объявленном минорном релизе сделать отсутствие секции запретом;
6. проверить не только helper, но меню, прямой HTTP-запуск и managed-form path.

Вне рамок:

- классификация обработок как «опасных» по статическому анализу DSL;
- изменение прав администратора;
- запрет системного запуска обработок планировщиком, `procrun` или внутренним
  кодом без пользовательской сессии;
- пересмотр дополнительного правила внешних обработок: недоверенная внешняя
  обработка по-прежнему доступна только администратору;
- новая схема БД или миграция прикладных данных.

## Публичный YAML-контракт

После переходного среза поддерживаются следующие явные формы:

```yaml
# запретить роли все обработки
permissions:
  processors: {}
```

```yaml
# разрешить только перечисленные обработки
permissions:
  processors:
    ИмпортПрайса: [run]
    ПересчётЦен: [run]
```

```yaml
# осознанно сохранить прежний глобальный доступ
permissions:
  processors_default: allow
```

`processors_default` допускает ровно значение `allow`. Оно разрешено только
при отсутствующей/null-секции `processors`; сочетание с любой map-секцией,
включая `{}`, является ошибкой конфигурации как неоднозначное. Отдельное
значение `deny` не нужно: явный запрет уже записывается как `processors: {}`.

Новый ключ выбран вместо wildcard `"*"` внутри карты. Старый бинарь воспринял
бы `processors: {"*": [run]}` как non-nil карту без записи конкретной
обработки и запретил бы запуск при откате. Незнакомый старому парсеру
`processors_default` игнорируется, карта остаётся `nil`, и прежний бинарь
сохраняет прежнее allow-all. Старый `onebase check --lint` может назвать ключ
неизвестным, но обычный `check` и runtime не должны отказывать в загрузке.

### Семантика по этапам

| Конфигурация роли | Переходный релиз | Релиз переключения |
|---|---|---|
| `processors` отсутствует или `null`, default отсутствует | allow-all + lint warning | deny-all |
| `processors: {}` | deny-all | deny-all |
| явная карта имён | разрешены перечисленные `run` | разрешены перечисленные `run` |
| `processors_default: allow` | allow-all без implicit-warning | allow-all |

Права нескольких ролей объединяются как сейчас: достаточно одного явного
разрешения. После переключения одна роль с отсутствующей секцией больше не
перебивает ограничения остальных. Администратор продолжает проходить любой
processor-gate.

## Инварианты

- `User.Has`, `Role.Allows` и `PermissionHas` дают одинаковый результат для
  отсутствующей, пустой, явной и compatibility-конфигурации.
- Имя операции остаётся `run`; новый ключ не расширяет набор операций.
- В переходном срезе ни одна существующая конфигурация не теряет доступ только
  из-за обновления бинаря.
- После переключения новая роль без processor-настроек не получает обработку,
  добавленную позднее.
- Прямой URL, меню, POST запуска, событие managed form и AI action не расходятся.
- Lint предупреждает по каждой конкретной роли, а не одним общим сообщением по
  проекту, и сообщает число доступных нетестовых обработок.
- `kind: test` не появляется в пользовательском доступе и не заставляет роль
  объявлять права.
- Явный compatibility-режим не скрывает `rbac.object-without-role`: lint
  считает его глобальным покрытием, но отдельным кодом может сообщать, что
  allow-all сохранён осознанно.
- Редактор роли сохраняет комментарии, aliases, неизвестные операции и
  различие absent/null/empty; сохранение соседнего права не меняет processor
  mode.

## Инвентаризация затронутых границ

### Авторизация и модель роли

- `internal/auth/roles.go` — поле `ProcessorsDefault`, нормализация/слияние,
  единый helper выбора processor-policy и удаление двух расходящихся веток из
  `User.Has`/`PermissionHas`.
- `internal/auth/role_check_test.go`, `roles_has_test.go` — матрица обеих фаз,
  union ролей, admin и точная эквивалентность публичных методов.
- JSON-представление прав в `internal/auth/roles.go` и `describe` — новый ключ
  не должен потеряться между файловой и database-backed конфигурацией.

### Проверка конфигурации и миграционная диагностика

- `internal/configcheck/lint.go` — новый advisory code
  `rbac.processors-implicit-allow`; существующий `processorsOpen` должен
  учитывать текущую фазу и явный compatibility mode.
- `roleYAMLSchema` — известный ключ и проверка значения; cross-ref карты
  обработок остаётся строгим.
- `internal/configcheck/lint_test.go`, `cross_refs_test.go` и CLI-тест
  `onebase check --lint --json` — диагностика через пользовательскую команду.

Сообщение переходного lint:

```text
роль "Менеджер" не объявляет permissions.processors и поэтому сейчас получает
все обработки (N); задайте processors: {}, явную карту или
processors_default: allow до следующего минорного релиза
```

Для `processors_default: allow` допустим отдельный менее срочный warning
`rbac.processors-explicit-allow-all`: риск остаётся, но это уже записанное
решение и оно не блокирует переключение.

### Конфигуратор ролей

- `internal/launcher/roles_handlers.go`, `roles_yaml.go` и шаблон матрицы ролей
  — явный выбор режима «запретить все / выбрать / разрешить все».
- При первом открытии legacy-роли UI показывает отдельное состояние
  «неявный старый режим», а не выдаёт его за осознанное «разрешить все».
- Сохранение требует выбора и записывает `{}`, карту или
  `processors_default: allow`; AST-редактор не пересобирает файл с нуля.
- Для database config используется существующая атомарная запись полного
  role-файла; отдельной таблицы или теневого значения не вводится.

### Производственные потребители

- `internal/ui/server.go` — фильтрация меню обработок;
- `internal/ui/handlers_processors.go:getProcessor` — GET/POST и managed form;
- `internal/ui/handlers_managed_events.go` — события формы обработки;
- `internal/ui/ai_actions.go` — action, запускающий обработку;
- `internal/ui/extprocessors.go` — дополнительный trusted/admin gate внешней
  обработки сохраняется после обычного processor-permission.

Эти места не должны реализовывать новый default самостоятельно: они уже зовут
общий `s.can`/`requirePerm`, поэтому реализация меняет их только при
необходимости тестового шва.

### Документация и генераторы

- `DEVELOPER.md` — полный блок `processors`, таблица absent/null/empty/map и
  переходная инструкция.
- `internal/launcher/ai_generate.go` и contract-test гайда — AI обязан
  генерировать явный processor mode для каждой роли.
- шаблоны `onebase init`, примеры `examples/*/roles` — отсутствие секции
  устранено осознанным `{}` или точной картой;
- release notes и `CHANGELOG.md` релиза переключения — заметная несовместимость
  с командой проверки до обновления.

## Совместимость и миграция

Миграция выполняется до релиза переключения и не затрагивает БД:

1. Запустить `onebase check --project <dir> --lint` (или `--id <base> --lint`)
   новым переходным бинарём.
2. Для каждой `rbac.processors-implicit-allow` выбрать одно:
   - `processors: {}` — роль не должна запускать обработки;
   - явную карту — безопасный рекомендуемый путь;
   - `processors_default: allow` — точное сохранение прежнего поведения,
     включая обработки, добавленные позже.
3. Повторить lint до отсутствия implicit-warning, проверить роли через UI и
   только затем обновлять узлы до релиза переключения.

Явная карта и `{}` понятны старым и новым бинарям. Compatibility key сохраняет
allow-all и при rolling update/откате: старый runtime игнорирует ключ и видит
прежний `nil`, новый читает его явно. Пока остаётся хотя бы одна неразобранная
роль, смешанный кластер после переключения может давать разные ответы и не
считается поддерживаемым сценарием.

Файлы ролей, хранящиеся в `_onebase_config`, проходят ту же миграцию через
конфигуратор или экспорт/правку/deploy. Копировать решение в `_settings` нельзя:
права принадлежат версии конфигурации и должны ехать в `.obz`, backup и diff.

Откат релиза переключения безопасен для трёх явных форм. Обратной миграции
данных нет. Удалять `processors_default: allow` при откате не нужно; старый
runtime сохраняет тот же эффективный доступ.

## Нарезка на PR

### Срез A — контракт и видимое предупреждение (~1 день)

Добавить `processors_default: allow`, единый policy helper и строгую валидацию
взаимоисключения с `processors`. Текущее правило отсутствующей секции пока
оставить allow-all. Добавить два lint-кода, документацию и ai-guide.

Публичная приёмка: временный проект с одной обычной и одной test-обработкой
запускается через настоящий `onebase check --lint --json`. Legacy-роль получает
ровно один implicit-warning с `N=1`, `{}` и явная карта не получают его,
compatibility-роль получает только explicit-allow-all warning; обычный
`onebase check` остаётся зелёным. Runtime-тест доказывает, что доступ legacy
пока не изменился.

### Срез B — миграционные поверхности и репозиторные конфигурации (~1–1.5 дня)

Добавить трёхрежимный выбор в редактор ролей и атомарный round-trip для файла и
database config. Обновить init/AI-шаблоны и все `examples/*/roles`: каждая роль
получает `{}`, явную карту или осознанный compatibility mode. Опубликовать в
release notes дату/версию будущего переключения; выдержать минимум один
минорный релиз с предупреждением.

Публичная приёмка: HTTP-тест конфигуратора загружает по очереди absent,
`null`, `{}`, map и compatibility-файл, сохраняет соседнее право и повторно
читает YAML/runtime. Комментарии и aliases сохранены, неоднозначное сочетание
отклонено до записи, повторное сохранение байтово стабильно. Затем
`onebase check --lint` по каждому `examples/*` не находит implicit-warning.

### Срез C — fail-closed в объявленном минорном релизе (~1–1.5 дня)

Изменить только default единого helper: отсутствующая/null-секция без
`processors_default` запрещает запуск. Переписать переходные ожидания тестов,
обновить release notes/CHANGELOG и оставить compatibility mode поддерживаемым.
Issue #1191 закрывает только этот срез; предыдущие PR не используют
`Fixes #1191`.

Публичная приёмка: пользователь с legacy-ролью не видит обработку в меню,
получает 403 на прямые GET и POST, не может вызвать managed-form event или AI
action. `{}` ведёт себя так же; явная карта открывает только названную
обработку; `processors_default: allow` открывает все. Тот же сценарий проверяет
union двух ролей и неизменный admin bypass.

## Проверки

Для каждого среза обязательны узкие package-тесты и одна публичная приёмка:

1. `internal/auth`: table-driven матрица absent/null/empty/map/default,
   несколько ролей, admin, регистр операций и равенство `User.Has`,
   `Role.Allows`, `PermissionHas`.
2. `internal/configcheck`: lint включён/выключен, число только нетестовых
   обработок, путь конкретного role-файла, `--json`, неоднозначный YAML и
   отсутствие ложного `rbac.object-without-role`.
3. `internal/launcher`: HTML/HTTP-редактор и YAML AST round-trip для файлового
   и database-backed источника, включая comments/anchors/aliases.
4. `internal/ui`: меню, прямой GET, прямой POST, managed event и AI action
   проходят одну таблицу ролей; отрицательный ответ — 403 без исполнения DSL и
   без побочной записи.
5. `examples/*`: `onebase check --lint`; generated ai-guide/init fixture
   содержит явный processor contract.
6. Перед каждым implementation PR: `go test ./internal/auth
   ./internal/configcheck ./internal/launcher ./internal/ui`; перед закрытием:
   `go test ./...` и обязательные CI jobs репозитория.

Прямой вызов приватного policy helper не считается регрессией #1191 без
проверки хотя бы одного пользовательского HTTP/CLI пути.

## Риски и откат

- **Тихая потеря доступа при раннем переключении.** Предохранитель — отдельный
  переходный релиз, per-role warning и запрет закрывать issue до среза C.
- **`User.Has` и `PermissionHas` снова разъехались.** Оба делегируют одному
  helper; общая table-driven матрица сравнивает публичные ответы.
- **Редактор превратил `{}` в absent или стёр compatibility key.** AST
  round-trip и семантическая read-back проверка обязательны до атомарной записи.
- **Старый бинарь не понимает миграцию.** `{}`/map уже поддерживаются;
  compatibility mode выбран отдельным ключом, а не wildcard-map.
- **Новая обработка неожиданно открылась.** Это возможно только у роли с явно
  записанным `processors_default: allow`; lint продолжает напоминать об этом.
- **Системные задания перестали работать.** Системные пути без пользователя не
  переводятся на role gate этим планом и получают отдельные regression tests.
- **Внешняя обработка обошла trust gate.** Processor permission проверяется
  первым, существующий trusted/admin gate — дополнительно, не вместо него.

Срез A откатывается без изменения конфигураций. После среза B явные `{}`/map
совместимы со старым кодом, а compatibility key старый runtime фактически
трактует как прежний allow-all. Срез C можно откатить возвратом transitional
default; данные и YAML переписывать назад не требуется.

## Критерии завершения

- отсутствие `permissions.processors` в релизе переключения означает deny;
- старое allow-all доступно только через явный `processors_default: allow`;
- `DEVELOPER.md`, ai-guide, init-шаблон и конфигуратор показывают один контракт;
- все роли репозиторных примеров разобраны, implicit-warning отсутствует;
- файловый и database-backed role editor сохраняют выбранный mode атомарно;
- меню, HTTP GET/POST, managed event и AI action подтверждают fail-closed через
  публичные пути;
- смешанный переход и откат описаны, миграции БД нет;
- release notes и CHANGELOG называют несовместимость до установки;
- #1191 закрывается только финальным implementation-срезом, не plan-PR.
