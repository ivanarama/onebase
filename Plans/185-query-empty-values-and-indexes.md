# Этап 185 — пустые значения в запросах и индексируемость отбора

## Контекст и решение

Основание: [#1534](https://github.com/ivanarama/onebase/issues/1534), одобренный вариант 2 доверенного triage. Это маршрутная issue для plan PR. Предмет общего плана — ведущая [#1535](https://github.com/ivanarama/onebase/issues/1535) (`В (...)`), ведомая #1534 (индексируемость равенства) и [#1183](https://github.com/ivanarama/onebase/issues/1183) (типы присоединённых источников). После слияния плана владельцем последовательных продуктовых срезов должна стать #1535; ведомые заявки координируются с ней, не закрываются самим планом. План не даёт разрешения автоматически менять состав результатов `В`: это отдельный срез с явным критерием совместимости на review.

На `main` `b752bfd83c4f1935d6bbff10a99d45d14365f0b8` компилятор `internal/query/query.go` вызывает `needsEmptyTextCoalesce` для текстовой или enum-колонки основного источника рядом с `=`, `<>`, `!=`. `COALESCE(колонка, '')` нужен для `= ""` и неравенства, но в положительном фильтре `колонка = "Непусто"` мешает обычному индексу. Замена *везде* неверна: `НЕ (Колонка = "Непусто")` после неё исключит SQL `NULL`, который сейчас проходит. `В ("Новая", "")` сейчас не применяет правило, поэтому не находит `NULL`. Для присоединённой таблицы правило намеренно выключено: типизация по имени поля могла принять её числовую колонку за строковую колонку первого источника и сломать PostgreSQL.

План разграничивает три работы: безопасное снятие обёртки в доказанном положительном фильтре, типизацию по конкретному источнику, затем явно утверждённое расширение `В`. Исправление индексного плана не должно само менять результаты существующих запросов.

## Наблюдаемая семантика и инварианты

### Текущий контракт, сохраняемый первыми срезами

| Выражение над строкой/enum основного источника | `NULL` в колонке сейчас | Первые срезы |
|---|---|---|
| `Колонка = ""` | совпадает | сохранить `COALESCE` и результат |
| `Колонка <> "X"` или `!= "X"` | совпадает | сохранить |
| `Колонка = &Параметр` | при пустом параметре совпадает | сохранить обёртку, так как значение неизвестно при компиляции |
| `Колонка = "X"`, где X непусто, как положительный `ГДЕ` | не совпадает | допустим прямой индексируемый предикат, если весь итоговый набор строк неизменен |
| `НЕ (Колонка = "X")` и другие отрицательные контексты | совпадает | сохранить нынешний результат; прямой предикат без компенсации запрещён |
| `Колонка В ("X", "")` | не совпадает | сохранить до отдельного среза расширения |
| `Колонка НЕ В (...)` при непустом списке | не попадает в `WHERE`: результат `UNKNOWN` при любом составе списка | сохранить до отдельного среза расширения |
| `ПО` в JOIN | не склеивает два `NULL` | не включать пустые значения в равенство соединения |

SQL `NULL` **в списке** влияет на непустое значение колонки, отсутствующее среди остальных элементов: `'Y' NOT IN ('X', '')` даёт `TRUE`, а `'Y' NOT IN ('X', NULL)` — `UNKNOWN`, поэтому во втором случае строка не проходит `WHERE`. Для `NULL` в самой колонке оба выражения дают `UNKNOWN`.

Здесь «сохранить» означает одинаковые идентификаторы и кратность строк через публичный `query.Compile` → `storage.DB.RunQuery` на SQLite и PostgreSQL, включая NULL, пустую и непустую строки, enum, сочетания `НЕ`/`И`/`ИЛИ`, обе стороны равенства, скобки, алиасы, подзапросы и параметр. Одного совпадения текста SQL недостаточно. Для прямого предиката `NULL = 'X'` имеет SQL-значение `UNKNOWN`, а `COALESCE(NULL,'') = 'X'` — `FALSE`: они эквивалентны **только по включению строки в доказанном положительном фильтре**, а не как произвольное булево значение. Консервативный fallback — нынешний `COALESCE`, если контекст или происхождение колонки не доказаны.

Числа, даты, булево, проекция, `ГРУППИРОВАТЬ`, сортировка, `ЕСТЬ ПУСТО`, виртуальные таблицы и условия `ПО` сохраняют текущий контракт. Синтаксис запросов и YAML конфигурации для первых срезов не меняется.

### Предлагаемое расширение после review отдельного среза

Для #1535 предлагаем трактовать пустой строковый/enum элемент литерального списка `В` как запрос также к незаполненной колонке, то есть включать `NULL` там, где положительный `В` явно содержит `""`. Это изменение результата, поэтому до реализации надо зафиксировать в тестовой таблице поведение `В` и `НЕ В` для: пустого и непустого литерала, пустого списка если грамматика допускает, параметров со значениями `""`/`NULL`, `NULL` внутри SQL-списка, подзапроса, отрицания вокруг всей группы, JOIN и поля присоединённого источника. Для неоднозначных случаев (особенно `НЕ В`, список с `NULL`, параметр или подзапрос) сохранить старое поведение до отдельного подтверждённого правила; не превращать механически каждый `IN` в `COALESCE`. `МЕЖДУ` в этот объём не входит. Изменение результата требует заметки о совместимости в `DEVELOPER.md` и релизных заметках продукта.

## Синтаксис / YAML

Новых ключей YAML и операторов DSL нет. Примеры пользовательских запросов, которые должны быть явно проверены:

```text
ВЫБРАТЬ Номер ИЗ Документ.Заявка ГДЕ Состояние = "Завершено"
ВЫБРАТЬ Номер ИЗ Документ.Заявка ГДЕ НЕ (Состояние = "Завершено")
ВЫБРАТЬ Номер ИЗ Документ.Заявка ГДЕ Состояние В ("Новая", "")
ВЫБРАТЬ Т.Номер ИЗ Документ.Заявка КАК Т
  ЛЕВОЕ СОЕДИНЕНИЕ Справочник.Клиент КАК К ПО Т.Клиент = К.Имя
  ГДЕ К.Категория <> "Розница"
```

## Хранилище / SQL и индекс

DDL и данные не мигрируют. Используются обычные индексы конфигурации и индексы строковых стандартных полей; функциональный индекс на `COALESCE` не требуется. На SQLite проверить `EXPLAIN QUERY PLAN` на таблице с индексом по строковому полю: положительное равенство непустому литералу должно давать `SEARCH ... USING INDEX`/covering index по самой колонке, а не `SCAN`. На PostgreSQL проверить `EXPLAIN` при репрезентативном объёме и отключённом последовательном сканировании **только в тестовом сеансе** (`SET LOCAL enable_seqscan = off` в транзакции): индексный путь должен быть доступен. Не утверждать, что оптимизатор всегда выберет индекс на маленькой таблице. Зафиксировать прежний план и новый, без тайминга как критерия. После оптимизации отрицания и `= ""` могут оставаться с `COALESCE` и без обычного индексного пути — это осознанная граница.

## Инвентаризация границ в текущем коде

- `internal/query/query.go`: `translator.emitOwnColumn`, `emitQualifiedColumn`, `needsEmptyTextCoalesce`, `equalityOpAt` сейчас решают по соседнему токену и типу, без контекста отрицания. `sourceContext` уже хранит SELECT-scope, секцию и основной источник; расширение должно опираться на структурный контекст выражения, а не поиск отдельного `НЕ` рядом. `sourceScope.mainColTypes`, `isMainSourceColumn` и `buildColTypes` знают в основном первый источник. `sourceColumnTypes` получает типы полей отдельного источника, а `needsNumberCast` по-прежнему использует карту по имени. При переносе типизации не смешивать источники, одноимённые поля и scope подзапроса/UNION.
- `internal/query/empty_text_compare_test.go`: контракт эмиссии равенства, alias, JOIN и подзапросов. `internal/query/empty_text_compare_matrix_test.go`: публичное исполнение SQLite/PostgreSQL, включая существующий тест одноимённого строкового/числового `Код`; сюда добавлять матрицу результатов и индекса. `internal/query/sources_test.go` и `sourcekind_test.go` помогают сверить разбор источников и виртуальных таблиц.
- `internal/storage/` и `internal/dbtest/`: публичная миграция, запись, выполнение SQL и диалектная матрица. Продуктовый DDL не менять ради этой оптимизации.
- `DEVELOPER.md`, раздел «Сравнение с незаполненным значением»: описывает текущую границу только основного источника и равенства/неравенства. После каждого изменения семантики обновлять примеры и ограничения; при расширении `В` явно назвать изменение состава выборки.

## Последовательность небольших PR-срезов

1. **Контракт и безопасный индексный отбор (#1534).** Сначала закрепить исполняемую матрицу текущих результатов и индексный baseline. Ввести ограниченный распознаватель контекста положительного предиката `ГДЕ`: непустой строковый литерал справа *или слева* от `=`, прямая колонка известного основного источника, без `НЕ` на пути к корню. `И`/`ИЛИ` допустимы лишь после проверки конечной фильтрации для всей формы; для неподдержанных форм оставить обёртку. Не трогать `<>`, `!=`, пустой литерал, параметр, `HAVING`, `ПО`, скалярные выражения и подзапросные границы без доказательства. Код и тесты должны показывать отсутствие лишнего `COALESCE` и идентичные результаты, а не одну строковую замену SQL.
2. **Типы всех источников (#1183).** Представить типы по identity/alias источника внутри SELECT-scope, включая одноимённые поля, присоединённые источники и поддерживаемые табличные части/виртуальные таблицы. Сначала использовать эту карту для `needsNumberCast` и безопасного решения по текстовым полям, не меняя семантику `ПО`; применять правило к присоединённому источнику в `ГДЕ` только после матричного доказательства и отдельного описания нового охвата. Неизвестная или неоднозначная ссылка должна сохранить старую эмиссию либо выдать штатную ошибку, но не угадать тип другого источника. Если расширение охвата меняет результаты, оно требует явного review и заметки о совместимости в этом срезе.
3. **Оператор `В` (#1535).** После закрепления матрицы и одобрения точного изменения результата добавить только согласованные формы `В`. Явно проверить `НЕ В`, отрицание группы, литерал/параметр/подзапрос и NULL в списке; не распространять на `МЕЖДУ`. Обновить документацию и релизную заметку с примером отчёта, который начнёт включать ранее пропущенные строки. Срез не должен менять индексный контракт среза 1 и типизацию среза 2.

Каждый срез — отдельный продуктовый PR с публичными тестами; этот PR содержит только план. Если срез 2 требует иной структуры компилятора, разбить его на механическое введение карты источников без изменения результата и отдельное включение поведения.

- **Срез 1:** unit-проверки SQL-эмиссии через `query.Compile`; матричный `dbtest.ForEachDialect` через `DB.Migrate`/`Upsert`/`RunQuery` для NULL, `""`, `"X"`, `"Y"` и каждой формы выражения. Проверить одинаковые результаты до/после на обеих БД. Отдельно SQLite `EXPLAIN QUERY PLAN` и PostgreSQL `EXPLAIN` на проиндексированной колонке. `go test ./internal/query`, `go build ./...`.
- **Срез 2:** та же матрица с `ЛЕВОЕ СОЕДИНЕНИЕ`, полями `Код` разных типов, comma JOIN, вложенным SELECT, UNION и виртуальной таблицей; публичный тест на PostgreSQL обязан доказать отсутствие строковой обёртки у числового поля. Проверить `needsNumberCast` на SQLite числовым сравнением с разными разрядами. `go test ./internal/query`, `go build ./...`.
- **Срез 3:** исполняемая матрица `В`/`НЕ В`, параметров, NULL в списке и подзапроса на обеих БД; тест должен явно показывать утверждённую дельту наборов строк относительно baseline. Проверить примеры из `DEVELOPER.md` через публичный `query.Compile` и выполнение. `go test ./internal/query`, `go build ./...`, `onebase check --project examples/trade` при наличии затронутых запросов.

PostgreSQL-прогон требует `TEST_DATABASE_URL`; если он недоступен, продуктовый срез не считать проверенным для изменения SQL-семантики. При ручной end-to-end проверке создать документ с NULL, пустым и непустым состоянием, выполнить четыре запроса выше, сравнить номера и планы выполнения до/после соответствующего среза.

## Совместимость, риски и откат

Срез 1 должен сохранять состав выборки и не требует миграции. Риск — неверно классифицировать отрицание или выражение вне фильтра и потерять NULL-строки; неизвестный контекст сохраняет старый SQL. Срез 2 может расширить применение правила на присоединённые поля и потому требует отдельного обзора результатов, особенно у `LEFT JOIN` и одноимённых колонок. Срез 3 намеренно добавит NULL-строки к некоторым `В`, что меняет отчёты: перед merge перечислить точные формы и предупредить пользователей. Схема и сохранённые значения не меняются; откат каждого среза — возврат его компиляторного правила и документации, с повтором матрицы на обеих БД. Не полагаться на состояние чекбоксов старых планов как доказательство реализации.

## Критерии завершения и оценка

- У #1534 есть доказанный обычный индексный путь для положительного равенства непустому строковому литералу на SQLite и PostgreSQL; все прежние результаты первой матрицы сохранены.
- У #1183 есть привязка типа к источнику, без чужого типа и без склейки NULL в JOIN; согласованное расширение отбора по присоединённым полям закреплено матрицей.
- У #1535 принят и задокументирован точный контракт `В`/`НЕ В`; тесты показывают только утверждённую дельту результатов, а сведения о совместимости опубликованы.
- Каждый срез проходит `go build ./...`, матричные тесты и обычный REVIEW; работу нельзя считать завершённой по одному зелёному SQLite-тесту.

Оценка: контракт и индексная оптимизация 2–3 дня, типизация источников 3–5 дней, `В` и документация 2–3 дня; всего 7–11 дней без ожидания review.
