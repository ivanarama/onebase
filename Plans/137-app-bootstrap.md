# Этап 137 — Сборка приложения: `internal/app` вместо композиции внутри `api.New`

## Статус

⬜ **Проект (2026-08-19, issue #787, ARCH-01).** Сам рефакторинг сознательно не
начат: владелец в комментарии к заявке зафиксировал условие — «делать, когда
скажете, что фичи притормаживаем». План существует, чтобы к этому моменту не
пришлось заново восстанавливать картину и числа.

🟡 **Срез (2026-08-20): цена заморожена.** Отложенное решение имело цену, и цена
росла сама: 545 строк в аудите 11.08 → 823 через четыре дня, 5 вызовов UI из API
→ 17. Поставлены два бюджета, которые держат её на сегодняшнем уровне, ничего не
перестраивая:

- `internal/cli/startup_budget_test.go` — операторов в `runServerGeneration` не
  больше, чем сейчас (519; считаем операторы, а не строки, чтобы не наказывать
  за комментарии). Ужалась — бюджет опускается, иначе освобождённое место молча
  займут обратно.
- `internal/api/ui_surface_test.go` — список методов `ui.Server`, которые зовёт
  `api`, заморожен на семнадцати. Новый вызов не запрещён, но требует строки в
  списке и объяснения в PR: сейчас восемнадцатый добавляется незаметно, рядом
  уже есть такие же.

Бюджеты не заменяют рефакторинг и не приближают его — они лишь не дают цене
вырасти, пока решение ждёт. Когда работа начнётся, оба теста снимаются вместе с
`runServerGeneration`.

## Контекст

Аудит (`Plans/audit-report-2026-08-11.md`) назвал три вещи одной находкой:
разросшийся запуск сервера, зависимость `api` от `ui` и «божественный»
`storage.DB`. При разборе выяснилось, что это не три задачи, а одна с хвостом:
дешёвой ступеньки «развязать API и UI интерфейсом» не существует, потому что
`api.New` — не потребитель UI, а **композиционный корень**: он сам зовёт
`ui.New`, монтирует маршруты UI в свой роутер и забирает оттуда прикладные
сервисы. Интерфейс вокруг вызовов жизненного цикла импорт `ui` не убирает.

Первые шесть — монтирование маршрутов, следующие три — прикладные объекты,
остальные — жизненный цикл и кэш. Разной природы вызовы, один импорт.

## Что делать

### Шаг 1. Композиция уезжает из `api.New` в `internal/app`

Появляется `internal/app` с тремя операциями:

```go
app, err := app.Build(ctx, cfg)   // открыть БД, миграции, реестр, сервисы, собрать ui и api
err = app.Run(ctx)                // слушать порт, стартовать фон (планировщик, очередь, обмен)
err = app.Close(ctx)              // остановить в обратном порядке
```

`Build` не слушает порт и не пишет в stdout — это и есть условие тестируемости:
сборку можно проверить тестом, не поднимая сервер. `runServerGeneration`
превращается в чтение флагов, `Build`, `Run` и обработку сигналов;
перезапускающий цикл `runServer` остаётся как есть.

Кто кого строит после шага: `app` строит `ui.Server`, строит `api.Server`,
передаёт второму первый — а не второй сам создаёт первого.

### Шаг 2. `api` сводится к узким интерфейсам

Только после шага 1 это перестаёт быть косметикой. Разрезать по природе
вызовов, а не одним интерфейсом на 17 методов:

- `RouteMounter` — шесть `Mount*`;
- `AppServices` — `EntitySvc`, `Incidents`, `BuildJobDSLVars`;
- `Lifecycle` — `BeginShutdown`, `Shutdown`, плюс кэш/диагностика.

Признак успеха один и проверяется тестом: `internal/api` больше не импортирует
`internal/ui`.

### Шаг 3. Consumer-side интерфейсы к `storage.DB` — НЕ начинать

425 методов режутся только по внятной границе, иначе получаются те же 425
методов через четыре интерфейса. Повод начать — конкретная боль: тест, который
нельзя написать, или пакет, который нельзя собрать отдельно. Пока такого нет,
шаг остаётся незапланированным намеренно.

## Риски

- **Конфликты.** Трогается единственная точка запуска сервера. Во время
  активной работы над фичами рефакторинг конфликтует с каждым вторым PR — это
  и есть причина, по которой шаг 1 ждёт явного «фичи притормаживаем».
- **Молчаливая потеря порядка остановки.** Сейчас порядок завершения задан
  последовательностью кода в одной функции. При переносе в `Close()` его надо
  зафиксировать тестом, иначе перестановка двух строк однажды оставит открытым
  соединение или потеряет дренаж очереди.
- **Тихая смена поведения флагов.** 814 строк содержат ветвления по флагам
  (`--watch`, `--open`, `--reload-binary`, демо-сброс). Перенос обязан
  сопровождаться характеризующими тестами ДО правки, а не после.

## Тесты

1. **Характеризующие, до рефакторинга:** запуск с каждым сочетанием флагов
   доходит до «слушаю порт» и корректно завершается по сигналу.
2. `TestBuild_NoSideEffects` — `Build` не открывает порт и не пишет файлы вне
   рабочего каталога базы.
3. `TestClose_Order` — остановка идёт в обратном порядке к старту (проверяется
   по журналу компонентов, а не по внутренним полям).
4. `TestAPIDoesNotImportUI` — запрет импорта проверяется `go list -deps`, чтобы
   развязка не разъехалась обратно первым же PR.
5. **Уже есть (срез 2026-08-20):** `TestStartupCompositionDoesNotGrow` и
   `TestUIServerSurfaceIsFrozen` — бюджеты на размер сборки и на поверхность
   API → UI. Обе проверки сняты мутациями: добавленный оператор в
   `runServerGeneration` и лишний вызов `ui.Server` из `api` валят их с текстом,
   называющим причину.

- Шаг 2 — 1–2 дня.
- Шаг 3 — не оценивается (не начинать).
