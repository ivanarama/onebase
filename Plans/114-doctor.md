# План 114 — `onebase doctor`: тестирование и исправление базы

Дата проектирования: 2026-08-03.
Статус: ✅ **Реализовано** (2026-08-03, ветка `feature/114-doctor`).

## Что сделано

- ✅ `internal/dbcheck` — проверки за общим интерфейсом, отчёт с уровнями
  ok/warn/error и находками (объект, количество, примеры).
- ✅ Шесть проверок: `integrity` (PRAGMA integrity_check), `schema`
  (`PlanMigration` из плана 81), `refs` (битые ссылки), `orphan-movements`,
  `totals`, `blobs`.
- ✅ `onebase doctor` с `--check`, `--fix`, `--json`; код возврата 1 при
  ошибках состояния базы (для мониторинга и CI).
- ✅ Тесты: битая ссылка находится, чинится и не задевает живые; прогон без
  `--fix` не меняет данные; расхождение итогов находится и лечится пересчётом;
  здоровая база — тишина.

### Отличия от исходного проекта

- **`maintenance` (REINDEX/ANALYZE/VACUUM) не делался.** Это обслуживание СУБД,
  а не состояние конфигурации: у него другие права, другое время выполнения и
  другой владелец (DBA, а не прикладной администратор). Отдельной задачей.
- **`--fix refs` очищает ссылку в NULL** — вариантов «создать объект» и «оставить
  как есть» из 1С нет: создавать объект по битому UUID означало бы плодить
  пустышки, а «оставить» — это и есть поведение без `--fix`.
- **Веб-админка пока не переведена** на общие проверки: у неё свой набор кнопок
  и свой формат. Стоит сделать следующим шагом, чтобы CLI и веб не разъезжались.

### Исправлено следом (2026-08-03)

Разведены два случая, которые раньше считались одним: «регистратор удалён»
(сирота — удаляется) и «документа нет в конфигурации» (движения целы — НЕ
удаляются). Прежний код выполнял по неизвестному типу безусловный
`DELETE FROM рег_x WHERE recorder_type = ?`, то есть переименование документа
или запуск против другой конфигурации стирали всю его историю движений.
Удалить их всё же можно — `onebase doctor --forget-document <Имя>`, поимённо.

### Найдено при реализации

Битую ссылку в тесте не удавалось создать обычной записью: у колонок,
объявленных вместе с таблицей, есть `FOREIGN KEY`, и SQLite их проверяет. Это
важно для понимания области применения проверки: битые ссылки появляются там,
где внешнего ключа нет или он не действовал, — у колонок, добавленных к
существующей таблице (`AddColumnIfMissing` создаёт колонку без `REFERENCES`),
при восстановлении части данных, при обмене и при правках в обход платформы.

## Контекст

В 1С есть «Тестирование и исправление информационной базы» (и `chdbfl.exe` для
файловых баз) — одна операция, которая проверяет базу по нескольким осям и
чинит найденное. В OneBase половина этих проверок уже написана, но живёт
порознь и частью недоступна из CLI:

| Проверка 1С | Состояние в OneBase |
|---|---|
| Реструктуризация таблиц | ✅ план 81: `onebase migrate --dry-run` / `--allow-destructive` |
| Логическая целостность (структура ↔ метаданные) | ⬜ нет отчёта; движок есть — `storage.PlanMigration` |
| Ссылочная целостность (битые ссылки) | ⬜ нет вообще |
| Пересчёт итогов | ✅ `onebase recalc-totals` |
| Реиндексация / сжатие | ⬜ нет (`REINDEX`/`ANALYZE`, `VACUUM`) |
| Физическая целостность файла (chdbfl) | ⬜ нет (`PRAGMA integrity_check`) |
| — | ✅ сверх того: `gc-blobs` (сироты-блобы), `rollup` (свёртка) |

Отдельная дыра: удаление **движений с несуществующим регистратором** реализовано
(`storage.OrphanMovements` / `DeleteOrphanMovements`), но вызывается только из
веб-админки (`internal/ui/admin.go`). Базу, которую нельзя поднять, чинить нечем.

## Цель

Одна команда, которая отвечает на вопрос «всё ли в порядке с этой базой» и, по
явному разрешению, чинит найденное. Read-only по умолчанию: диагностика,
которая может что-то испортить, не запускается «на всякий случай».

## Синтаксис

```
onebase doctor --project <dir> --sqlite <f>          # только отчёт
onebase doctor --check refs,schema                   # выборочно
onebase doctor --fix orphan-movements,totals         # чинить перечисленное
onebase doctor --json                                # машинный отчёт
```

Проверки (`--check`, по умолчанию все):

| Ключ | Что смотрит | Что умеет чинить (`--fix`) |
|---|---|---|
| `schema` | расхождение схемы с метаданными (`PlanMigration`) | — (чинит `onebase migrate`) |
| `refs` | ссылочные поля, указывающие на несуществующий объект | очистить ссылку в NULL |
| `orphan-movements` | движения с несуществующим регистратором | удалить |
| `totals` | итоги регистров расходятся с движениями | пересчитать |
| `blobs` | блобы и вложения без владельца | удалить (та же логика, что `gc-blobs`) |
| `integrity` | `PRAGMA integrity_check` (SQLite) / доступность таблиц (PG) | — |
| `maintenance` | давность `ANALYZE`, распухание индексов | `REINDEX`/`ANALYZE`/`VACUUM` |

## Почему отдельная команда, а не флаг `migrate`

`migrate` обязана быть быстрой и предсказуемой: она в CI и в деплое. Doctor —
редкая ручная операция, которая сканирует таблицы целиком (поиск битых ссылок —
это проход по всем ссылочным колонкам всех объектов). Смешать их значит либо
замедлить деплой, либо получить диагностику, которую никто не гоняет.

## Изменения в коде

- `internal/dbcheck/` — проверки как независимые единицы с общим интерфейсом
  (`Name() string`, `Run(ctx, *storage.DB, *runtime.Registry) Result`,
  `Fix(ctx, …) error`); отчёт — общая структура с уровнями (ok/warn/error);
- `internal/storage/refs.go` — поиск битых ссылок пакетно (по колонке за запрос,
  а не по строке), с ограничением на число примеров в отчёте;
- `internal/cli/doctor.go` — команда, вывод текстом и `--json`;
- `internal/ui/admin.go` — страницу «Обслуживание» перевести на те же проверки,
  чтобы веб и CLI не разъезжались.

## Тесты

- битая ссылка находится и (с `--fix`) очищается; целая — не трогается;
- расхождение итогов находится на подготовленной базе и лечится пересчётом;
- `doctor` без `--fix` ничего не меняет (сверка дампа до/после);
- отчёт `--json` разбирается и содержит все ключи проверок.

## Verification

1. Сломать ссылку прямым SQL → `onebase doctor` показывает её с объектом и полем.
2. `onebase doctor --fix refs` → ссылка очищена, повторный запуск чист.
3. `onebase doctor` на здоровой базе → «проблем не найдено», код возврата 0.

## Эстимейт

4–6 дней: каркас проверок и отчёта (1), битые ссылки (1–2), перенос
существующих операций под общий зонтик (1), обслуживание СУБД (0.5), CLI и
JSON (0.5), тесты (1).

Риск средний: сами проверки читающие, но `--fix` меняет данные — каждая правка
обязана быть точечной (по конкретному id), а не массовым `UPDATE`.
