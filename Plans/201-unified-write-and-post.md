# Этап 201 — Единая транзакционная запись и проведение документа

## Контекст

Ведущая заявка — [#1887](https://github.com/ivanarama/onebase/issues/1887).
Выбран вариант 1 канонического триажа, подтверждённый решением `ivanarama`
от 05.10.2026: сначала отдельный план общего пути «записать и провести».
Контракт: `OnWrite → запись, видимая в той же транзакции → OnPost → финальная
запись/commit`; `OnWrite` исполняется ровно один раз, отказ любого объектного
хука откатывает всю операцию. Новые объектные события `ПередЗаписью` и
`ОбработкаЗаписи` не добавляются. События managed-формы остаются отдельными.

Связанный [план 176](176-write-context-and-load-mode.md) по
[#1435](https://github.com/ivanarama/onebase/issues/1435) задаёт принятый
контекст загрузки. Этот план согласует порядок хуков, а не заменяет
`WriteContext`, права `load` или отсутствие ambient-наследования режима.
На момент подготовки #1435 имеет `hold`: пересекающаяся реализация общего
сервиса ждёт согласования этого плана. Её метки данным PR не меняются.
[План 132](132-document-write-paths.md) задаёт направление сведения путей;
здесь нужен ограниченный общий шов записи, а не перенос всего UI в сервис.

## Наблюдаемая семантика и инварианты

### Два вида операции

| Публичный вход | Объектные хуки после реализации |
|---|---|
| Автоформа/managed-форма «Записать» | Один `OnWrite`; текущая семантика обычной записи сохраняется |
| Форма «Провести»/«Провести и закрыть», REST post с телом или без тела, DSL `Объект.Провести()` | Один `OnWrite`, затем один `OnPost` |
| Кнопка проведения из списка, DSL `Ссылка.Провести()` | Один `OnPost` над загруженным документом; не добавлять неявную запись через `OnWrite` |
| Отмена проведения | Существующий `OnUnpost`; не включать в новую цепочку |

REST post без тела уже имеет сервисную семантику записи/проведения; его
новый `OnWrite` — явное изменение поведения, описываемое в релизных заметках.
Для проведения сохранённого документа сохраняются текущие права `post`;
проведение с переданными полями требует действующих `write` и `post`.
План не расширяет права пользователя ради запуска прикладного кода.

### Фазы «записать и провести»

1. Проверить вид операции, права вызывающего, write-guard и входные enum.
   Начать `WithTxScope`: собственная транзакция либо savepoint внешней
   DSL-транзакции. Получить исходный снимок и состояние удаления в этом scope.
   Для существующего документа с клиентской expected version ранний отказ
   на уже известный конфликт происходит до объектных хуков; окончательная
   защита — атомарный CAS, а не отдельный SELECT.
2. Для нового документа выдать номер внутри scope. Выполнить caller
   `Preflight`, подготовить rich refs и ТЧ, восстановить платформенную self-ref.
   Caller остаётся владельцем form-level и RBAC-проверок. Для FK-потомков
   нового документа оставить tx-local provisional parent до `OnWrite`, как
   уже делает `Save`; отсутствие полей required в нём допустимо только пока
   открыт конкретный lifecycle.
3. Выполнить `OnWrite` над живым объектом ровно один раз. Отсутствующий хук
   означает успешную пустую фазу. Проверить enum шапки и переданных ТЧ снова.
   Изменения хуком карты целиком (`Fields`/`TablePartRows`) учитываются; нельзя
   продолжать сохранять устаревшие указатели из входного `SaveRequest`.
4. Сделать снимок после `OnWrite` видимым запросам `OnPost` через тот же
   `txCtx`: шапка и все участвующие ТЧ. Для existing использовать CAS prelude,
   для new — уже открытый provisional lifecycle; при необходимости добавить
   узкую промежуточную запись нового родителя без финализации lifecycle.
   Финальный create-writer здесь не подходит. Отказ CAS откатывает и ранее
   выполненные DB-записи `OnWrite`; `OnPost` не запускается.
5. Запустить `OnPost` над тем же логическим объектом в том же scope. Его
   запросы видят пересчитанные `OnWrite` реквизиты и строки ТЧ. Внешние
   соединения промежуточную запись не видят. Признак `posted` до финализации
   сохраняет исходное значение, а не обещает успех ещё не завершённого хука.
6. Проверить финальные enum и required, разрешённость перехода этапа,
   дату запрета проведения по итоговой дате и deletion-mark. Финализировать
   шапку и каждый открытый lifecycle ТЧ, записать движения и `posted=true`,
   регистрацию обмена. `FinalPreflight` проверяет точную сохранённую строку,
   после чего разрешается release savepoint/commit.
7. Вернуть одну окончательную версию. `OnPersisted` относится к завершению
   всей операции внутри scope; `OnCommitted`, observer и внешние уведомления
   относятся к успешному внешнему commit. Промежуточный снимок не публикуется.

Каждая hook-фаза сохраняет действующий timeout, живой DSL `TxState` и общий
lock scope. `FinishTxExecution` не должен коммитить внешнюю транзакцию между
хуками. Ошибка, timeout, panic или незавершённый storage lifecycle приводят к
откату. Внешняя DSL-транзакция может поймать ошибку: откатывается savepoint
операции, а не ранее сделанные независимые изменения внешней транзакции.

### Проверки и финальный снимок

- **Enum:** входная проверка до объектных хуков и повторная после каждого
  хука; нельзя давать `OnPost` чинить заведомо неверный enum от `OnWrite`.
- **Required:** только финальная проверка после `OnPost`, потому что он уже
  вправе заполнить пустое обязательное поле шапки или ТЧ. Обычная запись
  проверяет required после `OnWrite`. Промежуточные исключения остаются
  tx-only и принадлежат конкретному объекту/ТЧ; вложенные записи не получают
  освобождения от required. Временные ошибки SQL/FK/типов не игнорируются.
- **Версия:** create завершается на `_version=1`; existing получает ровно
  одно увеличение. Клиентский token сохраняется до CAS, final writer не
  увеличивает версию второй раз. При nil token caller не обязан начинать
  передавать его: сервис читает актуальную версию внутри scope и использует
  её как внутренний CAS token. Конкурентное изменение до CAS означает
  конфликт и полный откат, без автоматического повторного запуска хуков.
- **Частичный ввод:** отсутствующий реквизит existing сохраняет старое
  значение; отсутствующий ключ ТЧ сохраняет строки; явные nil/пустой список
  очищают ТЧ. Хук вправе добавить ключ, тогда он участвует в записи.
  Семантическая проверка required использует эффективный снимок
  `старое + переданное + изменения хуков`, а не только REST patch.
  Не превращать загрузку данных для проверки в разрешение переписать
  непереданные или защищённые поля. `OnPost` видит эффективное состояние
  через запрос, даже если patch-объект содержит лишь переданные ключи.
- **Окончательное состояние:** результат `OnPost`, сохранённый с обычными
  storage backstops. Аудит update сравнивает исходную строку с финальной;
  prelude не создаёт отдельного update/create, stage history или FTS-эффекта.
  На new нужно проверить, что stage/FTS-effects provisional также не оставляют
  второго логического события: существующий audit-skip сам по себе этого
  не доказывает.

### Движения, побочные записи и уведомления

Для проводимого документа финальные регистровые движения формирует только
collector `OnPost`. Collector `OnWrite` не объединяется автоматически с ним:
это сохраняет нынешний DSL-контракт и исключает повтор проводок из обхода,
который вызывает общий расчёт в обоих хуках. Прямые записи других объектов
из любого хука участвуют в общей транзакции и сохраняются при успехе;
платформа не удаляет их по совпадению значений. Для обычной записи сохранить
действующую политику `OnWrite`-движений и отмены проведения, не переносить
`OnUnpost` в промежуток между двумя хуками. Период итогового collector берётся
после изменений даты в `OnWrite`; при изменении даты в `OnPost` повторно
согласуется с финальным объектом и проверкой закрытого периода.

Обновление итогов/блокировки регистров сохраняют текущий порядок захвата.
Вопрос удаления старых движений из не затронутого новым хуком регистра —
отдельная открытая работа [PR #1778](https://github.com/ivanarama/onebase/pull/1778):
этот план не объявляет её уже реализованной и не дублирует её fix.

На логическое «записать и провести» оставить одну регистрацию обмена и одно
финальное событие `document.post`/«проведён». Отдельное `document.save` и
промежуточное «записан» на DSL `conduct` исключить; callbacks и payload
получают финальные копии полей/ТЧ, а не mutable map prelude. Это явное
выравнивание с сервисным путём. Простая запись по-прежнему даёт `document.save`.
При внешней DSL-транзакции до её commit ничего не публикуется. Аудит остаётся
набором предусмотренных записей create/update/post, без удвоения из prelude.

HTTP/email/файловые эффекты непосредственно из прикладного хука не становятся
обратимыми от наличия DB-транзакции. Их нельзя обещать откатить; конфигурация
должна откладывать такие действия до успеха или использовать собственную
очередь доставки. `Сообщить` собирает сообщения обоих хуков по порядку;
ошибка сохраняет действующий формат прикладного отказа.

## Синтаксис / YAML

Новых YAML-полей, объектных событий или аргументов `Провести` не требуется.
Форма и REST используют существующие действия. Пример наблюдаемого поведения:

```os
// src/Заказ.os
Процедура ПриЗаписи()
    this.Комментарий = "Проверен";
КонецПроцедуры
```

При `Док.Провести()` и кнопке формы `OnPost` получает `this.Комментарий` и
читает через `Новый Запрос` ту же строку со значением «Проверен». Если любой
хук бросает исключение, предыдущее состояние документа остаётся в БД.

Когда будет реализован план 176, один `WriteContext` normal/load передаётся
в оба объектных хука данной операции. Read-only `КонтекстЗаписи.Загрузка`
не теряется при переходе в `OnPost`, load не пропускает проверки/хуки, а
вложенная запись остаётся normal без явного аргумента. Публикация этого API,
REST Bearer-only право `load` и его audit-marker принадлежат #1435.

## Хранилище / SQL

DDL и миграции данных не требуются. Используются существующие lifecycle-пары
`UpsertProvisional`/`UpsertPreserveVersion`,
`UpsertPostingPreludeVersioned`/`UpsertAfterVersionBump`,
`UpsertPostingPreludeTablePartRows`/`FinalizePostingPreludeTablePartRows`.
Общий шов добавляет в consumer port ровно нужные методы.

Узкий новый writer для обновления ещё открытого provisional parent должен
проверять существующий lifecycle, сохранять версию, не писать долговечные
логические эффекты и не потреблять lifecycle до финала `OnPost`. Не добавлять
общий публичный `skip_validation`/`skip_audit`, не выключать FK и не применять
сырой SQL из service. Если целевой writer не поддерживает необходимую
семантику, до переключения сервиса расширить конкретный storage lifecycle
с матричными тестами; commit незавершённого prelude запрещён.

## Совместимость и миграция

Изменение включается единым сервисным контрактом, без постоянного legacy-флага.
Перед обновлением конфигурации проверить `ПриЗаписи` и `ОбработкаПроведения`:
если оба вызывают общий модуль записи дочерних документов/регистров, оставить
write-side часть в `ПриЗаписи`, а post-side проводки — в `OnPost`.
Платформа не умеет отличать намеренный второй вызов от старого обхода и не
обещает дедупликацию произвольного DSL. Чистые вычисления могут повториться
без вреда; необратимые внешние эффекты требуют предметной проверки.

Особенно проверить REST post без тела и интеграции, рассчитавшие поля заранее:
новый `OnWrite` может их пересчитать. После реализации #1435 это регулируется
явным контекстом load, который сам по себе не означает skip hook.
Старые calls без режима сохраняют normal. Удаление DSL `document.save` из
комбинированного проведения описать для потребителей webhook/живых списков.
Никакие API-токены или права автоматически не выдаются.

## Последовательность небольших PR-срезов

### Срез B — общий Service.Save и форма/REST

Переключить posting на две фазы; защитить partial input, final validation,
движения и committed callbacks. Документацию изменения поведения поставить
в том же PR, не после выпуска. Публичная проверка: HTTP router автоформы
для new/existing, `_action=post`/`post_and_close`, а также mounted REST v1/v2
с телом/без тела, readonly calculated field и конфликт версии. Тесты вызывают
пользовательский endpoint, а не helper выбора хука. Managed save проверить
отдельным HTTP-сценарием, включая form events без удвоения entity hook.

### Срез C — DSL parity и завершение единой операции

Согласовать `conduct` с общим persistence seam, убрать промежуточные observer,
exchange и delivery; post-only методы сохранить. Публичная проверка:
настоящий `RunProcessor` выполняет create/load, `Записать` и `Провести`,
проверяет trace хуков, SQL read-your-writes, финальные поля/ТЧ/версию,
внешний rollback и ловлю ошибки savepoint. Списочный HTTP post и
`Ссылка.Провести()` подтверждают отсутствие `OnWrite`. Не тестировать
контракт только прямым вызовом `conduct`/`postInContextAfterAccess`.

## Тесты

Для A–C SQL-семантика проверяется одной матрицей SQLite/PostgreSQL; PostgreSQL
прогон обязателен перед поставкой. Расширить существующие
`required_document_paths_test.go`, `posting_guarantee_parity_test.go`,
`required_fields_final_state_test.go`, `required_persistence_matrix_test.go`
и API router tests следующими наблюдаемыми проверками:

- trace дочерних записей показывает ровно `OnWrite`, затем `OnPost`; readonly
  итог рассчитан, а запрос `OnPost` видит новую шапку и изменённые ТЧ;
- missing required заполняется каждым хуком; финальное очищение required
  и неправильный enum откатывают номер, шапку, ТЧ, движения/итоги и потомков;
- исключение/timeout каждого хука, CAS-конфликт и ошибка записи движений
  оставляют исходные `_version`, `posted`, audit/stage history и exchange;
- частичный REST patch сохраняет непереданные поля/ТЧ, пустая ТЧ очищается,
  хук может добавить или заменить карты; masking/RLS не обходятся;
- OnWrite DB-side effects сохраняются один раз, движение OnPost не
  удваивается от OnWrite collector; повторное проведение сохраняет
  действующие ограничения и не объявляет PR #1778 уже вошедшим;
- new завершается с версией 1, existing с v+1, nil token не ломает callers;
  две независимые PG-сессии доказывают CAS-конфликт без lost update;
- audit/stage/FTS отражают исходный → финальный снимок; webhook/notify/observer
  получают финальный payload ровно после commit, при rollback отсутствуют;
- внутри ambient DSL-транзакции успешная операция ещё обратима, пойманный
  отказ не удаляет предшествующие изменения; платформенные writer flags
  восстанавливаются и допускают корректную повторную попытку.

На каждом кодовом срезе: `go build ./...`, `go test ./...`, targeted matrix
с `TEST_DATABASE_URL` и обязательный CI. Плановый PR проверяется отдельно:
`go run ./tools/plannum`, локальные ссылки и отсутствие изменений вне `Plans/`.
Эти команды для будущих срезов не означают, что они уже выполнены.

## Риски и откат

Главные риски — повтор уже продублированных прикладных эффектов, обход required
через незавершённый prelude, stale CAS, потеря omitted ТЧ, промежуточный audit
и публикация mutable payload. Их закрывают описанные public/matrix tests и
проверка всех callbacks относительно внешнего commit. Не расширять scope
до всей архитектуры приложения или до unrelated fixes движения/прав.

Откат кодовых срезов выполняется в обратном порядке после сверки зависимости
#1435: нельзя оставить новый orchestration без соответствующего storage
lifecycle. Данные/DDL не требуют обратной миграции. Старый бинарь снова
пропустит `OnWrite` на сервисном post, поэтому возврат версии требует вернуть
нужный прикладной обход. Уже созданные дочерние документы и внешние эффекты
проверяются предметно; автоматическое удаление по предположению запрещено.

## Критерии завершения

Форма, REST и DSL object post дают один `OnWrite` и один `OnPost` с общей
транзакционной видимостью и полным DB-rollback. Enum/required/CAS/права не
ослаблены, версия увеличивается один раз, omitted/empty сохраняют различие.
Post-only и обычная запись имеют явно проверенный прежний контракт.
Итоговый snapshot используется для persistence, audit и committed delivery.
Опубликована инструкция миграции прикладного обхода; #1435 сохраняет принятый
план 176. Обязательная SQLite/PG-матрица и CI зелёные для каждого среза.
