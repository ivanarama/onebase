# Этап 195 — Технические handoff и продуктовые решения REVIEW/FIX

## Контекст

Ведущая заявка: [OneBase #1836](https://github.com/ivanarama/onebase/issues/1836).
Выбран вариант 1 канонического триажа: сначала согласованный план, затем
минимальная техническая передача под выключенным флагом, после неё Dashboard
и измерение результата. Основание — доверенный triage-комментарий
[5920052692](https://github.com/ivanarama/onebase/issues/1836#issuecomment-5920052692),
`pp:recommend=1`, `approved`; явной `decision:*` нет.

Сейчас третий блокирующий круг означает `needs-decision` независимо от природы
блокера. Владельцу приходится вручную передавать воспроизведённые дефекты
исполнителю. Сценарий #1759 из заявки — исторический пример такой передачи,
а не разрешение менять этот PR или доказательство нынешнего дефекта UI.

Цель: доказанный технический дефект получает конечную, наблюдаемую передачу
одному исполнителю; выбор пользовательского поведения остаётся у владельца.
Неизвестный тип и сбой инструмента не расширяют полномочия автоматического FIX.
Независимые REVIEW, человеческий `ship` и все merge-гейты сохраняются.

Связанная PromptPilot #144 отвечает за парковку одной цели и продолжение серии.
Её реализация — отдельная работа: здесь определяется причина парковки и
контракт передачи, а не создаётся второй механизм управления всей серией.

## Синтаксис / протокол

Ниже — проект нового контракта, а не уже поддерживаемые ключи или маркеры.
Продуктовый YAML конфигураций OneBase не меняется.

Предлагаемые параметры pipelinectl и checker:

```json
{
  "technical_handoff": {
    "enabled": false,
    "protocol": "review-routing-v1",
    "max_extra_attempts": 2
  }
}
```

`max_extra_attempts` — максимум дополнительных технических доработок после
обычных двух кругов, суммарно для серии данного PR. Значение 2 — начальный
конечный бюджет пилота, изменение требует явной операторской настройки.
Несогласованные версии, отсутствующий capability или невалидные параметры
дают отказ включения, а не частичный новый маршрут.

В отчёт REVIEW добавить `routing_version` и обязательную категорию каждого
блокирующего пункта:

| `kind` | Обязательное содержание | Получатель |
|---|---|---|
| `technical` | Воспроизведение на точном HEAD: публичная точка входа, среда/команда, ожидаемое и фактическое поведение, результат; ссылка на violated invariant | Один разрешённый исполнитель до исчерпания бюджета |
| `product` | Нумерованные варианты поведения, последствия и рекомендация | Владелец, `needs-decision` |
| `safety_exception` | Конкретная граница безопасности или требуемое исключение | Человек; никакой автоматической доработки по этой категории |
| `insufficient_data` | Что не доказано и какая проверка нужна | Инженерный разбор; никакого auto-FIX |

Отдельный operational status `tool_error` описывает невозможность провести
проверку/получить полный снимок. Он не является результатом содержательного
REVIEW и не создаёт completion по недоказанному snapshot. Dashboard показывает
его из результата запуска отдельно от product decisions.

Не выводить категорию из произвольной прозы, количества кругов или текста
`needs-decision`. Незнакомое значение/отсутствующая категория не считается
`technical`. Для смешанного отчёта вся цель остаётся у человека/инженера;
автоматическая передача допустима только если все блокеры технические и
каждый имеет проверенное доказательство. Продуктовая развилка содержит именно
выбор поведения, а не инструкцию владельцу выполнить `gh` или поставить метки.

Типизированный payload привязать к review id, earliest claim id, completion id,
точному HEAD, server epoch hash и repository/ref identity. Содержимое отчёта
коммитится hash в версии proof; редактирование категории или evidence
инвалидирует передачу. Предлагаемый технический outcome — новая маршрутная
метка `technical-handoff` и `Outcome-Label: technical-handoff` в versioned
review-proof. Старое значение `needs-decision` не переопределяется задним числом.

Расширение outcome требует совместимого обновления **всех** читателей proof:
REVIEW, FIX, MERGE, TAIL и внешнего pipelinectl. MERGE/TAIL не получают новые
полномочия: технический outcome не является успешным REVIEW, не разрешает merge
и не создаёт хвост как будто PR уже принят. Неподдерживаемый proof — стоп,
а не fallback к новому аудиту того же HEAD.

## Семантика и инварианты

1. Первые два обычных блокирующих круга сохраняют прежний маршрут. На третьем
   при выключенном флаге действует старый контракт. При включённом флаге
   доказанный `technical` может получить новый handoff; остальные категории
   не превращаются в технические автоматически.
2. Любое служебное доказательство или human decision доверено только от
   точного `ivanarama`. Внешний автор PR получает уведомление/назначение,
   но его комментарий не может выдать машинному FIX полномочия.
3. Перед каждым внешним изменением повторяются гейты нужной стадии: полный
   GraphQL timeline/proof с двумя стабильными проходами там, где этого требует
   существующий протокол, актуальные HEAD/ref identity/open/main/draft,
   labels, canonical owner и отсутствие hold/позднего override. Для обычного
   REVIEW target-v1 сохраняются HMAC/expiry lease и локальный completion gate;
   integration/fallback сохраняют глобальный allowlist/owner gate.
4. Edit/delete доказательства, новый lifecycle/HEAD anchor, ABA HEAD/base,
   чужой actor, partial/stale snapshot или конфликт переходов запрещают
   передачу и мутацию. Health — выбор/диагностика, не замена mutation gate.
5. Machine handoff не синтезирует `pp:fix-decision` или `pp:review-again`.
   Эти существующие human-переходы остаются человеческими и имеют прежний
   порядок относительно completion.
6. Одновременно выбран ровно один executor: разрешённый pipeline FIX **или**
   автор/назначенный инженер. Для внешнего авторского PR по умолчанию нужен
   author handoff; auto-FIX разрешается только прежней execution/identity
   policy. Назначение не означает автоматическое исполнение кода fork.
7. Тот же HEAD с тем же committed blocker не запускает повторный содержательный
   REVIEW/FIX. Recovery может закончить уже начатую публикацию без нового
   аудита. Новый HEAD получает независимое REVIEW, но не обнуляет общий бюджет.
8. `ship` автоматика не ставит. Технические метки/proof не заменяют успешный
   текущий REVIEW, человеческий ship-event, CI, base-sync owner, HEAD/CAS и
   compare-and-merge. Существующий ship обрабатывается нынешними гейтами;
   новый технический outcome никогда не делает PR mergeable.

## Передача, атомарность и предел попыток

Новый переход должен иметь отдельные immutable intent/done markers версии v1,
связанные с указанным proof. Точная грамматика и canonical serialization общие
для Go/Python; ids — decimal strings/BigInt, UTF-8/LF и SHA-256 фиксируются
общими golden fixtures. Текст GitHub считается данными, поля не превращаются
в shell-команды.

Порядок перехода: валидировать proof и избрать earliest owner → зарезервировать
одну попытку persistent intent → повторить state gate → подтвердить маршрутную
метку → адресовать доработку одному executor → подтвердить handoff-done.
Конкурирующие workers продолжают только один canonical intent. Резервация
расходует бюджет до отправки задания; recovery одной резервации не расходует
вторую. Сбой после неопределённого POST требует exact-source read-back, а не
повторного неидемпотентного уведомления. При невозможности доказать результат
цель уходит в инженерный разбор. Для lease сохранить 30-минутное владение,
renewal/takeover и проверку returned active id/UUID перед каждой фазой.

`series_id` связан с первым proof, потребовавшим дополнительную техническую
передачу, и номером/repository PR. Каждый последующий intent содержит previous
и исходный completion; проверяется непрерывность цепочки. `blocker_id` —
стабильная identity нарушения инварианта, отдельно от hash evidence. Изменение
слов отчёта, SHA, списка блокеров или создание нового intent не создаёт новую
серию и не сбрасывает её счётчик. В бюджете учитываются все дополнительные
technical attempts этого PR, а не только повторы одинакового текста.

После CAS-push FIX-completion связывает новый HEAD с source proof/intent;
сохранить прежний `PP-Fix-Transition`, добавив versioned technical source,
а не подменяя human proof. Перед независимым REVIEW завершить post-push фазу.
Старый handoff не разрешает повторную правку нового HEAD.

После двух дополнительных попыток — `engineering-handoff`: явный получатель,
доказательство, накопленная история и список остающихся дефектов. Это parked
state для данной цели, не executable FIX/REVIEW candidate. Если назначенного
инженера нет, Dashboard показывает «нужно назначение инженера». Смена HEAD
сохраняет парковку/бюджет до явного инженерного resume, связанного с новым SHA;
resume допускает один REVIEW и не выдаёт новый бесконечный бюджет.
Новая продуктовая развилка переводит в product decision независимо от бюджета.

Для инженерной парковки также предлагаются одноимённая маршрутная метка и
versioned `Outcome-Label: engineering-handoff`. `insufficient_data` третьего
круга попадает сюда сразу, без расходования technical attempt; safety/product
остаются в `needs-decision` с явной категорией. Health различает описательную
корзину technical handoff и executable FIX allowlist: назначение автору не
является кандидатом auto-FIX. Ни один из двух новых outcome не входит в MERGE.

Новые переходы нельзя восстанавливать удалением общей метки, если более поздний
owner/human event изменил маршрут. Late hold/close/ship/override прекращает
операцию; чужое re-label не восстанавливает доверенную передачу.

## Хранилище / SQL, совместимость и миграция

Продуктовая БД и схемы PostgreSQL/SQLite не меняются. Долговечная история —
GitHub proof/intent/done, с неизменяемыми ссылками; локальный cache/Dashboard
производны и после удаления восстанавливаются из этих данных. Внешний
PromptPilot может потребовать расширить собственную БД operational events:
точная схема определяется при его инвентаризации в срезе A, без предположений
о существующих таблицах.

Старые proof и human handoff не переписываются. При флаге off отсутствуют
новые маршруты и действует существующий третий круг. Для уже созданного v1
handoff выключение флага запрещает новые auto attempts, но совместимый reader
должен безопасно завершить/припарковать recovery, а не потерять владение.
Откат на бинарь без reader v1 запрещён при активных v1 intents: сначала drain
или инженерная парковка, затем downgrade. Несогласованная пара процедур/checker/
pipelinectl не включает флаг.

## Последовательность PR-срезов и публичные тесты

Каждый срез — отдельно проверяемая поставка. Промежуточные PR ссылаются на #1836,
но не закрывают её. До каждого среза проверяются ownership и отсутствие
параллельного FIX/авторской реализации. План 163 описывает будущий multi-slice
handoff; на его ещё не реализованный механизм не опираться: задания следующих
срезов выдаются явно, финальный кодовый PR закрывает #1836 после общей приёмки.

### A. Минимальный маршрут под флагом — согласованная пара OneBase/PromptPilot

В OneBase ввести schema/parser proof, категории, capability/flag и новые
описательные/executable корзины health; согласовать канонические REVIEW/FIX
и безопасное игнорирование технического outcome в MERGE/TAIL. В PromptPilot
сначала проверить фактические entrypoints, затем изменить публичные
`next/complete`, report validator и owner/intent recovery. Реализовать конечный
бюджет и одно назначение сразу: без этих ограничений даже пилот не включается.
Dashboard пока использует существующее минимальное отображение статуса.

Публичные тесты: OneBase CLI `pipelinehealth -prs/-issues/-contract -json` на
fixtures; PromptPilot `next review` → `complete review` → один `next fix` через
fake GitHub transport. Третий круг technical даёт один handoff, product и
unknown не дают auto-FIX; флаг off воспроизводит legacy. Две REVIEW-реплики и
crash в каждой фазе дают одну резервацию/назначение. Partial/stale snapshots,
изменённый proof/actor/HEAD и поздний hold запрещают mutations. Fork policy
проверяется через публичный dispatch, без выполнения credentials-bearing кода.

### B. Полная межстадийная регрессия и парковка одной цели

Проверить смену HEAD и source trailer, post-push recovery, continuous series,
исчерпание бюджета и engineering resume. Подключить существующий механизм
PromptPilot #144 через его публичный контракт; не реализовывать его второй раз.
Техническая парковка не создаёт integration owner и не блокирует другие PR.

Публичные тесты: та же неизменная цель в двух `next` не возвращается для нового
аудита; два новых HEAD не сбрасывают бюджет; переименование blocker не даёт
третью попытку; другая eligible цель исполняется после парковки. Positive/
negative tests `next/complete merge` сохраняют ship/CI/HEAD/CAS, single-flight,
target-v1 HMAC/expiry и identity proof. Старый third-round human handoff всё
ещё допускает ровно одну доработку/одно ревью. Тестировать ABA и edit/delete
timeline через публичный transport, не только прямой вызов parser.

### C. Dashboard, диагностика и пилот

Добавить отдельные technical/engineering handoff, product decisions,
insufficient data и tool failures. Показывать PR/HEAD, категорию, evidence,
получателя, попытку/лимит и время перехода. Health экспортирует эти состояния
аддитивно; старые корзины не переименовываются. operational error не выдаётся
за human product decision. Обновить maintenance guide/CLAUDE и сообщения
оператора. Codex-адаптеры остаются тонкими.

Публичные тесты: Dashboard API/UI читает реальные новые health/run JSON fixtures,
не объединяет все статусы в одну «решите» корзину; вопрос product содержит
варианты поведения. Закреплённый checker и установленная пара процедур/
pipelinectl проходят smoke на staging. После этого оператор включает флаг
для ограниченного пилота, не меняя ship-гейт.

## Verification

Для кода каждого среза: `go build ./...`, целевые `go test -count=1` и `go vet`
в затронутых Go-пакетах; проверки внешнего исполнителя из его собственного
проекта. CLI fixtures и public workflow tests обязательны: строковые проверки
процедур в `internal/pipelinecontract` не доказывают исполнение маршрута.
Не запускать product-конфигурации только из-за изменения maintenance contract.

На test repo создать technical blocker третьего круга с точным evidence,
пройти REVIEW → handoff → одну доработку → новый независимый REVIEW. Проверить
второй дополнительный круг и конечную engineering-парковку, одновременно
запуская другой PR. Отдельно пройти product/unknown/tool failure и пары
конкурирующих workers/crash-recovery. Ни один сценарий не ставит `ship`.

На исходном main локально проверены существующий third-round контракт и четыре
health-регрессии (completion retry, override, waiting ship, issue queues).
Новая семантика этим планом не реализована и этими проверками не подтверждается.

## Риски, откат и критерии завершения

Главный риск — ошибочная technical-классификация выдаст лишние полномочия.
Митигировать обязательным evidence, смешанным fail-closed outcome, независимым
REVIEW и негативными public tests. Другие риски: несогласованные Go/Python
