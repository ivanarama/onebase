## Синтаксис / YAML

Новый `kind: Список` допустим в managed-объектной форме документа или
справочника, включая несохранённый объект. Первая версия читает только
документы и справочники. Обработки, регистры, журналы, SQL/DSL-источники,
поиск, пользовательская сортировка, редактирование и бесконечная прокрутка
не входят в контракт.

Пример фрагмента `elements:` в `forms/обращение/ФормаОбъекта.form.yaml`:

```yaml
elements:
  - kind: Список
    id: client-orders
    name: ЗаявкиКлиента
    title: {ru: Заявки клиента, en: Customer orders}
    entity: Заявка
    filter:
      - field: Клиент
        op: eq
        source: Объект.Контакт
    order_by: [ДатаВызова desc, Номер asc]
    limit: 5
    columns: [Номер, ДатаВызова, Состояние, Направление]
    on_row_click: открыть
```

Это предлагаемый синтаксис: исходный `filter: {Клиент: Объект.Контакт}`
из issue заменён типизированным массивом. `source` — ровно один скалярный
реквизит `Объект.<Имя>` либо `Форма.<Имя>`; без переходов по ссылкам,
индексов ТЧ и произвольных выражений. Условие имеет либо `source`, либо
`value` с литералом известного типа. В v1 поддерживается только `eq`,
не более восьми разных полей; все условия соединяются AND.

`onebase check` блокирует неизвестную сущность/колонку/источник, неоднозначные
имена, повтор поля, несовместимые типы, неверное направление порядка,
неизвестные ключи спецификации, отсутствие обоих операндов или их сочетание.
Ссылки источника и целевого поля должны иметь одну `RefEntity`, число —
decimal, дата — существующую семантику `date`, bool — bool. UUID проверяется
до запроса. Составные типы и литералы ссылок не входят в v1.

`limit` по умолчанию 5, допустимы 1–100; максимум восемь списков на форме,
одна или больше уникальных колонок, до четырёх ключей порядка. Для
иерархического справочника v1 показывает элементы без папок, по всем уровням;
пометка удаления отображается как в обычном списке, автоматического скрытия нет.
`on_row_click` — `открыть` или `нет` (по умолчанию `нет`).

## Наблюдаемая семантика и инварианты

1. Пустой динамический источник даёт пустой список с состоянием «Выберите
   значение», без запроса к целевой таблице. Не превращать его в снятый отбор
   или сравнение с SQL NULL. Для литералов пустые/null значения запрещены
   в v1; ошибочный непустой ввод даёт ошибку компонента без выдачи строк.
   Пусты: nil/Неопределено, пустая или пробельная строка, пустая ссылка,
   нулевая дата. Число 0 и bool false — полноценные значения отбора.
2. Начальная выдача использует текущие значения после инициализации формы.
   После успешного события — значения после обработчика, включая изменения
   через DSL. Изменение источника без прикладного обработчика тоже обновляет
   список. Несохранённый объект не обязан существовать в БД.
3. Явный `order_by` имеет приоритет; без него используется порядок целевой
   сущности. Если и он пуст — `id ASC`. Всегда дописывается уникальный
   `id ASC` для разрешения равенств. Числа и пустые значения сортируются
   по существующим правилам метаданных одинаково на SQLite/PostgreSQL.
4. Список — серверная проекция, отдельная от `TablePartRows`, `FormTables`
   и ValueTable. У него нет скрытых inputs со строками, editable-grid,
   команд добавления/удаления, DSL-мутаций строк или участия в dirty-state.
   Поддельные строки списка в save/form-event не могут изменить данные.
5. При смене источника старые строки и ссылки сразу убираются. Ответ
   применяется только к совпадающим элементу, ревизии источников и живому
   экземпляру DOM-формы. Поздний ответ, закрытие формы или удаление элемента
   его отменяет; AbortController сам по себе это не доказывает.
6. Ошибка/отказ доступа очищают строки, не оставляют историю предыдущего
   клиента. Ошибка чтения списка не отменяет уже выполненную запись
   прикладного обработчика, не повторяет этот обработчик и не обнуляет
   несохранённые поля/ТЧ. Состояния: loading, ready, empty, denied, error.
7. Нажатие и Enter на строке используют относительную ссылку, построенную
   сервером по фактической сущности и UUID. Открытие идёт в отдельной вкладке
   без потери текущей формы; карточка повторно проверяет read/RLS. Нет
   произвольного URL из YAML или браузера; при `нет` строки не интерактивны.

## Модель доступа

Каждый путь (первый HTML, form-event и refresh) заново проверяет право чтения
владельца формы и целевой сущности. Для существующего владельца — read/RLS
до загрузки его полей; для нового — штатное право создания и разрешённый
контекст новой формы. Доступ к обращению сам по себе не разрешает заявки.

Целевая выборка соединяет конфигурационный отбор с SQL-предикатом `read` из
`rowDecision` и выставляет `RowFilterEvaluated`. RLS действует **до LIMIT**,
а не после получения первых N строк. Нет count/total в v1 и скрытого
сообщения о числе запрещённых записей. Нейтральное denied без данных
используется и при техническом сбое построения политики.

Перед выдачей: `maskRecords` целевой сущности → разрешение допустимых ссылок
→ проекция только объявленных колонок и разрешённого UUID/URL. Не отдавать
`SELECT *` как JSON, сырые значения в data-атрибутах/логах, скрытые UUID,
необъявленные `_label`, версии и поля исходной записи. Подписи ссылок должны
соблюдать доступ и маски связанного объекта, как в защищённом UI.

Фильтр и сортировка по замаскированному/скрытому целевому полю запрещены
для текущего пользователя: маска на выходе не защищает от вывода значения
через состав строк или их порядок. То же относится к защищённому источнику
владельца формы. Колонка может отображать разрешённую маску или исчезнуть
по штатному `FieldDecision`; сырое значение не попадает в браузер.

Непустая ссылочная величина источника также проверяется на существование
и read/RLS самой связанной записи, по модели `choiceRefVisible`:
недоступная ссылка даёт пустую выдачу без различения «нет» и «закрыта».
Технический сбой проверки даёт нейтральную ошибку без результатов.

Браузер передаёт только идентичность владельца/формы/элемента и текущие
значения объявленных источников. Entity, field, op, order, columns, limit
всегда восстанавливаются из серверных метаданных. Подмена идентичности не
даёт прочитать чужую карточку или элемент другой формы. Источник от клиента
— параметр поиска, а не доказательство доступа. Разбор источников применяет
те же ограничения редактируемости и восстановления защищённых значений,
что действующий managed-form путь. Для readonly источника существующего
объекта используется сохранённое значение, а не подставленное браузером.

## Хранилище / SQL, совместимость и миграция

Новых таблиц, колонок, индексов и преобразований данных нет. Равенство
компилируется по метаданным с bind-параметрами; имена полей и направления
не берутся из HTTP. Для SQLite decimal-колонки остаются TEXT: сравнение
и порядок требуют существующей числовой нормализации, не строкового `=`.
Пустые динамические источники вообще не доходят до SQL.

Новые ListParams необязательны; прежний list/picker, metadata OrderBy,
keyset, дерево и CountList не меняют поведение. Конфигурация без `Список`
имеет прежний HTML/response. Старый бинарь новый kind не поддерживает:
сначала обновление платформы, затем внедрение YAML; откат требует убрать
элемент из конфигурации до возврата старого бинаря. Данные при этом сохраняются.

С [планом 172](172-managed-form-runtime-structure.md) согласуется отдельный
канал данных и stable ID. V1 реализуется на статическом дереве, не ждёт
runtime structural API. Если runtime-дерево уже поставлено к началу среза,
loader использует актуальный разрешённый snapshot; create/remove/rebind
списков через DSL потребует отдельного расширения. Интерактивные dashboard
виджеты [плана 182](182-interactive-dashboard-widgets.md) не подменяют
контекст unsaved-формы; их row navigation можно переиспользовать после проверки.

## Verification и критерии завершения

Минимальный пример содержит клиентов A/B, обращения и 7 заявок: часть
недоступна оператору по RLS, у части одинаковая дата, телефон защищён.
Открыть обращение A и сверить первые 5 **доступных** строк, порядок и маски;
перейти к B без сохранения, очистить контакт, вернуть A. Повторить пользователем
без read к заявкам и с доступом к другому набору строк на SQLite и PostgreSQL.
Проверить замаскированную ссылку и отсутствие секретов в HTML/JSON/URL.

Замедлить сеть, изменить A→B→A, закрыть форму в полёте; поздние ответы
не возвращают чужую историю. Изменить контакт из обработчика и без него,
создать новое обращение; dirty и заполненная ТЧ не теряются. Открыть заявку
мышью и Enter, убедиться, что обращение не записалось и осталось открытым.
Отредактировать форму в конфигураторе, сохранить/перезагрузить — источник
и все ограничения сохраняются.

Готово, когда эти сценарии автоматизированы, SQL-матрица и штатный CI зелёные,
новый путь не имеет обхода RBAC/RLS/masking, refresh не пишет данные, редактор
не теряет спецификацию, есть пример и инструкция для пользователя. Отсутствие
нового kind в конфигурации подтверждено regression-тестом старых форм.

## Риски, откат и эстимейт

Главный риск — новый путь чтения с обходом прав или утечкой через сортировку,
подписи и payload. Security-матрица блокирует каждый срез; нельзя выпускать
«пока без RLS». Второй риск — stale history и потеря unsaved-данных:
изолированный read-only канал и ревизии обязательны до поставки B.
Третий — нагрузка: максимум 8 ограниченных запросов на форму, без COUNT,
только списки с изменёнными зависимостями; срок запросов наследует request
context. Нет глобального кэша результатов между пользователями. При внедрении
больших таблиц измерить EXPLAIN и latency; индексы конфигурации решаются
отдельно по фактическому отбору, этот план DDL не добавляет.

Откат среза: убрать элементы из прикладного YAML, вернуть предыдущий бинарь;
выборки ничего не изменили. При ошибке списка сохраняется ручной переход
в обычный защищённый список; не пытаться показывать старые строки.
Реалистичная оценка: A 4–6 дней, B 3–5, C 2–3; всего **9–14 дней**,
включая SQL-матрицу и browser e2e, без runtime API и импорта списков 1С.
