# Этап 180 — Доказательство перехода HEAD при base-sync

## Контекст и выбранное решение

Ведущая заявка: [#1561](https://github.com/ivanarama/onebase/issues/1561).
Выбран вариант 1 канонического триажа
[5715821300](https://github.com/ivanarama/onebase/issues/1561#issuecomment-5715821300):
сначала отдельный план, затем согласованные изменения REVIEW, MERGE, recovery
и тестов. `approved` без `decision:N` принимает рекомендацию 1. #1564 закрыта
как дубль; #1565 про дедупликацию TAIL в объём этого плана не входит.

Проверено по main `a8a2744048cea97961d01287a1f0e06520e8411a` (2026-09-18).
В legacy-процедурах REVIEW и MERGE carry требует один `PullRequestCommit`
после intent, а recovery re-ship — между intent и done. В примере из триажа
PR #1221 коммит `8b00d34f393ed00c7634e617d2085e2c50d1c2fe` датирован раньше
intent и стоит перед ним. Это контрпример, а не доказательство, что условие
не проходит никогда. Ни Git-дата, ни положение commit edge не удостоверяют
момент изменения ref. Родители доказывают граф, но не происхождение операции.

Цель: сохранить автоматический перенос одного человеческого `ship` через
проверенное обновление от main, исключив зависимость от часов коммита.
Недоказанный переход остаётся закрытым. Общее число коммитов «три» из одного
PR не становится правилом. Этот документ не включает реализацию.

## Наблюдаемая семантика и инварианты

1. Перед обновлением нужны открытый same-repository PR в `main`, каноничный
   proof `reviewed` исходного HEAD и действующий trusted `ship`; `hold` и
   `needs-decision` остаются стопами. Fork и неизвестная идентичность ref закрыты.
2. MERGE заранее фиксирует конкретный исходный `from`, конкретный `base` и
   конкретный будущий `to`; затем меняет только этот ref через CAS с expected
   `from`. Нельзя после неуспеха CAS подставить новое ожидание и повторить push.
3. `to` имеет ровно двух родителей **в порядке** `[from, base]`. Его дерево
   включает разрешение конфликтов, которое обязательно проверяет интеграционный
   REVIEW. Родители сами по себе не доказывают корректность дерева.
4. Порядок intent → done проверяется по server timeline комментариев, с
   `author.login == ivanarama`, `lastEditedAt == null`, полными id и пагинацией.
   Commit edges используются как сведения о графе, никогда как часы push.
5. Один непрерывный `ship-event` связывает всю carry-цепочку; любое снятие или
   повторная постановка, чужой actor, override, edit/delete доказательства,
   HEAD/base force-push, delete/restore либо смена base отменяют старый carry.
   События проверяются независимо от того, вернулся ли итоговый SHA к прежнему.
6. До каждого внешнего изменения остаются два полных стабильных GraphQL прохода
   и точечный HEAD/ref/label/proof gate; commit edges не смешиваются с журналом
   lifecycle. Недоступная страница или неизвестное событие не означают пустоту.
7. После done REVIEW проверяет интеграционную дельту и CI; MERGE ждёт новый proof
   точного `to`. В интеграционной очереди остаётся один владелец до его merge.
8. CAS атомарно защищает ref. Метки и timeline защищены последней проверкой
   перед запросом, а не общей транзакцией с GitHub. Позднее обнаруженный опасный
   event аннулирует carry; отсутствие задержек доставки событий не обещается.

## Синтаксис протокола вместо YAML

Пользовательский YAML, DSL и продуктовый API не меняются. Новые точные маркеры
имеют отдельное имя `pp:base-sync-v2-intent` / `pp:base-sync-v2-done`, чтобы v1
reader не принял неполное доказательство за старое. Комментарий intent содержит
строго версионированный ASCII/LF payload (полный список, не ссылки на временные
локальные файлы):

```text
pp-base-sync-v2
repository=ivanarama/onebase
pr=<decimal>
head-repository-id=<decimal>
head-ref=<ref>
owner=<uuid>
from=<40hex>
base=<40hex>
to=<40hex>
review-comment=<decimal>
claim=<decimal>
completion=<decimal>
ship-event=<GraphQL node id>
previous=<v2 done id|none>
source-epoch-sha256=<64hex>
source-snapshot-sha256=<64hex>
graph-sha256=<64hex>
<!-- pp:base-sync-v2-intent payload-sha256=<64hex> -->
```

`done` адресует intent id и его payload hash, повторяет `from/to/base/previous`,
`ship-event`, содержит hash полного проверенного post-snapshot и точную строку
`<!-- pp:base-sync-v2-done intent=<id> payload-sha256=<64hex> -->`.
Грамматику done и включённых snapshots зафиксировать в срезе A до writer:
дубликаты ключей, лишние ключи, неизвестная версия и несовпадающие hashes — отказ.
ID сравнивать строками после проверки десятичной грамматики, без float/32-bit.

Payload включает канонические исходные данные snapshot: ordered non-commit
edges с node id/cursor, типом, actor, адресованными значениями и телами proof
комментариев; отдельный отсортированный набор `(oid, ordered parents, tree)`
для графа. Hash без самих доступных данных не считается архивом. Два одинаковых
прохода проверяют данные, а не только `updatedAt`. Схема и golden bytes с UTF-8
телами, LF и SHA-256 общие для всех readers; Unicode-нормализацию не применять.
Если объём не помещается в комментарий, writer отказывает до intent: разбивка
на произвольные редактируемые вложения и молчаливое усечение запрещены. Выделенный
content-addressed архив возможен отдельным решением после измерения fixtures.

## Доказательство графа и операция записи

Обозначим `R(x)` множество достижимых коммитов Git, включая x. Источник графа —
полный fetch адресованных SHA с проверкой объектов, без shallow-усечения;
страницы PR commits не заменяют достижимость относительно фиксированного base.
Ожидаемое равенство: `R(to) = R(from) ∪ R(base) ∪ {to}`. Сравниваются объекты и
рёбра, а не количество и не сортировка по времени. PR diff рассматривается к
зафиксированному base: продвижение main не должно менять исходный снимок.

Для v2 дополнительно требуется, чтобы `from` и `base` не были предками друг
друга. Если base уже в from, синхронизация не нужна; если from уже в main,
нужна отдельная диагностика состояния PR, а не создание carry. Тогда между
from и merge to нет другого допустимого fast-forward HEAD: to имеет first
parent from, а другая ветвь не содержит from. Лишний push либо оставляет другой
HEAD/граф, либо требует обратного non-fast-forward и обнаруживается lifecycle
fence. ABA и delete/restore проверяются по событиям, а не только по графу.

Последовательность writer:

1. Получить исходный proof, стабильные snapshots, точные remote HEAD и main.
   Подготовить merge в изолированном worktree без push. Случай DIRTY включает
   разрешение конфликтов, проверки затронутого кода и проверку полного diff.
2. В сообщение merge-коммита внести `PP-Base-Sync-V2: owner=<uuid> from=<SHA>
   base=<SHA>`. UUID связывает заранее созданный объект с будущим intent без
   циклической зависимости от comment id. Git author/committer metadata не
   удостоверяют GitHub actor; полномочия даёт только trusted protocol writer.
3. После нового полного gate опубликовать intent с конкретным `to`, read-back
   через `@base64` и точным UTF-8 сравнением. Выбрать earliest intent для
   `(repository, pr, from, authorization)` по comment edges. Поздний worker
   ничего не пушит. Новый writer не получает владение от текста чужого автора.
4. Повторить gate и отправить только `to:refs/heads/<head-ref>` с
   `--force-with-lease=refs/heads/<head-ref>:<from>`. Предварительно доказать
   fast-forward from → to; lease не даёт права переписывать произвольную ветку.
   Явный expected SHA независим от фонового fetch; это свойство описано в
   [документации git push](https://git-scm.com/docs/git-push).
5. Прочитать ref, родители, граф, все lifecycle/label/comment events; проверить
   прежнее владение и authorization. После стабильного gate опубликовать done,
   проверить UTF-8 read-back. Завершить запуск MERGE, сохранив `ship`.

В v2 base закреплён: продвижение main после intent не меняет подготовленный
объект. Если закреплённый base остался предком main, REVIEW проверяет именно
его, а следующий sync — новое звено после proof. Force-push main прерывает
carry даже если проверка ancestry случайно проходит. Это сознательное отличие
от v1 `update-branch`, где фактический второй parent мог обогнать intent.base.
Не использовать API `update-branch` внутри v2: он не принимает заранее выбранный
to. Произвольный HEAD после ошибки CAS не объявляется нашим обновлением.

## Recovery, эпоха и авторизация

| Состояние после сбоя | Допустимое действие после полного gate |
|---|---|
| Intent отсутствует | Локальные объекты не дают права push; начать обычную подготовку. |
| Earliest intent есть, HEAD == from | Повторить тот же CAS на **тот же to**, только если объект доступен и proof/labels/lifecycle целы. Потерянный локальный объект — человек; заново созданный другой SHA не подставлять. |
| HEAD == to, done отсутствует | Проверить заранее адресованный объект, граф и все fences; опубликовать done без повторного push. Это recovery доверенного intent, а не угадывание авторства по parents. |
| HEAD иной / marker изменён или удалён / ship изменился | Carry недействителен; никаких push/done от старого worker. Существующая безопасная передача в REVIEW либо человек по типу отказа. |
| Done уже есть | Принять только каноничный valid done; не создавать второй. REVIEW либо ожидание proof. |

v2 sync-epoch получает anchor **done node**, а не commit edge:
`pp-review-epoch-v2\nhead=<to>\nanchor-node=<done-node>\ntransition-sha256=<intent-hash>\n`.
Это новая версия proof для sync-перехода; обычные v1 review epochs автоматически
не переписываются. REVIEW, MERGE, FIX и TAIL должны реконструировать один и тот
же anchor, hash и fences. Новый trusted `pp:review-again` после done начинает
новый аудит по общей процедуре и прекращает старую carry-авторизацию.
Чужой commit после done нельзя скрыть более ранней Git-датой: HEAD/граф
сверяются отдельно. Полный lifecycle scan защищает возврат к тому же to.

## Совместимость и миграция

- V1 intent/done не редактировать, не дополнять задним числом v2 snapshots и не
  признавать v2 по похожим parents. Старый формат остаётся читаемым для
  диагностики и выбора владельца интеграционной полосы.
- На включении v2 незавершённый v1 carry автоматически не переносит `ship`.
  Его можно завершить после нового явного разрешения **точного HEAD**; старое
  недоказанное разрешение не оживает. Это разовый миграционный путь, а не
  выбранный в триаже вариант 2 для всех будущих base-sync.
- Для legacy и protocol-recovery вместо зависимости от commit-position нужен
  trusted неизменяемый `pp:base-sync-reauthorize-v2` с явным `head=<SHA>` и
  текущим snapshot hash, затем новое trusted добавление `ship` после него.
  Снятие старого label до нового допустимо. HEAD/proof/lifecycle перепроверить
  перед публикацией запроса человеку и перед каждым последующим действием.
  Исторический intent/done сохраняется как контекст, но не доказательство carry.
- При недоказанном исходном transition новое разрешение ведёт на полное
  содержательное REVIEW текущего HEAD; нельзя обещать интеграционное сокращение
  только из-за формы merge-коммита. Следующий v2 sync начинает `previous=none`.
- Смешанные v1/v2 `previous` запрещены. Ни один reader не должен считать
  неизвестный v2 marker отсутствием протокола и уходить в legacy guessing.
- Сначала выпустить все readers и fail-closed fallback, потом включить writer.
  Внешний PromptPilot должен подтверждённо направлять v2 в совместимый fallback
  либо читать v2 сам. Его исходники этим исследованием не проверялись; до
  контрактного теста фактической установленной версии writer выключен.

## Хранилище / SQL

Бизнес-БД и DDL не меняются. Постоянное состояние — Git-объекты и неизменяемые
GitHub-комментарии. Локальный worktree/кэш не является единственным носителем
доказательства. Snapshots публикуются без токенов, конфигурационных секретов и
локальных путей. Недоступность исходного объекта закрывает recovery.

## Тесты: обязательная отрицательная матрица

Для каждого отказа проверить не только exit/диагноз, но и **ноль запрещённых
внешних записей**. Fixtures сохраняют raw edges, cursor, fullDatabaseId и
пагинацию; test input не содержит готового `singleHeadEvent=true`.

- Неверный/переставленный parent, третий parent, лишний коммит, другой tree/to,
  ветка/fork/PR другой идентичности, shallow или пропущенная страница.
- Backdated и future-dated дополнительный push; from → X → from и
  to → X → to; force-push, delete/restore, base switch туда-обратно.
- Edit/delete intent, done, source proof или earliest конкурента, включая
  ту же секунду; чужой marker, чужая постановка ship после trusted снятия.
- Два конкурентных intent, проигравший CAS, истечение процесса после каждого
  внешнего шага, потерянный ответ push; recovery никогда не заменяет to.
- Main продвинулся обычным образом; main переписан; from оказался в main;
  base уже в from; неизвестный actor/event; два различающихся snapshot.
- Новый review override, новый HEAD после done, stale completion,
  повторный done и смешанный previous; владелец полосы не меняется из-за
  очередного звена, но новая авторизация начинает новую цепочку.
- Старые v1 markers остаются нетронуты; отсутствие поддержки во внешнем
  pipelinectl даёт fallback/stop, а не merge или бесконечную скрытую очередь.

Для срезов с Go: `go build ./...`, `go test ./internal/pipelinecontract
./tools/pipelinehealth`, тесты нового пакета/CLI и необходимые CI-гейты.
SQL-матрица не требуется: SQL-семантика не меняется. Тест самого плана:
`go run ./tools/plannum`, `git diff --check`, проверка локальных ссылок.

## Verification

В отдельном тестовом репозитории подготовить reviewed PR с одним человеческим
ship и main впереди. Зафиксировать commit date до intent, пройти чистый sync,
интеграционный REVIEW и merge без второго ship. Повторить с будущей датой,
конфликтом, продвижением main и обрывом после push. Затем подмешать посторонний
push и ABA: carry должен быть отвергнут до merge. В OneBase не экспериментировать
на чужой рабочей ветке и не использовать текущие PR как тестовые данные для
мутаций. Исторический PR #1221 годится только для read-only fixture.

## Риски, откат и критерии завершения

Основные риски: неполный журнал событий, слишком большой snapshot, разнобой
версий consumers, ошибки разрешения конфликтов и потерянный локальный объект
до push. До включения writer измерить размер fixtures и проверить совместимость
установленного PromptPilot. Не доказывать полноту GitHub delivery двумя чтениями:
они защищают наблюдаемый snapshot, а не недоступную серверную транзакцию.

Откат: выключить v2 writer, оставить v2 readers/диагностику и безопасный stop для
активных v2 цепочек. Не возвращать старое угадывание по commit-position и не
удалять маркеры; уже созданные PR идут через точное новое разрешение и полный
аудит при необходимости. Продуктовые данные не требуют обратной миграции.

Готово, когда A–D приняты, публичная положительная/отрицательная матрица зелёная,
REVIEW/MERGE/recovery используют одно доказательство, FIX/TAIL принимают ту же
эпоху, queue health объясняет каждый stop, исторические markers не переписаны,
а перестановка Git-даты не меняет разрешение. Оценка: **7–11 рабочих дней**,
включая миграцию и проверку внешней интеграции; ожидание решения/выпуска
PromptPilot в оценку не входит.
