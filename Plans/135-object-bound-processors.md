# План 135 — Обработки, привязанные к объекту

Дата проектирования: 2026-08-19.
Статус: ⬜ **Проект**.
Ветка проекта: `docs/135-object-bound-processors`; реализация — `feature/135-object-bound-processors`.

Повод — вопрос «а внешние отчёты и обработки будут?». Они есть с 2026-06-03
(`internal/extform`, коммиты `979583b5`/`6b7ffdb0`/`c337d440`): печатные формы,
отчёты и обработки грузятся администратором в работающую базу, живут в её
таблицах, переносятся бандлом `*.obform`. Не хватает ровно одного — **привязки
обработки к объекту**: в 1С внешняя обработка подключается к документу или
справочнику и появляется командой в его форме, у нас же она попадает только в
общий список «Обработки». Пользователь, которому нужно «дозаполнить эту
реализацию по договору», обязан выйти из документа, найти обработку в списке и
руками выбрать в ней тот же документ.

## Контекст

Разрыв виден по самому контуру: у **печатной формы** привязка к объекту есть —
поле `document:`, и форма документа честно показывает её в меню печати
(`internal/ui/handlers_entity.go:1308`). У **обработки** такого поля нет, хотя
именно она — рабочая лошадка внедренца: заполнить реквизиты по правилу
заказчика, создать связанный документ, отправить объект во внешнюю систему.

Ценность привязки не в кнопке, а в том, что она делает контур завершённым:
доработка под конкретную установку перестаёт требовать правки конфигурации
**и** остаётся на своём месте в интерфейсе. Сегодня внедренец выбирает между
«поправить конфигурацию (форк, деплой, ветка)» и «положить обработку рядом, но
пользователь её не найдёт».

## Что мешает в текущем коде (проверено по `f034507e`)

1. **Привязку негде объявить.** `processor.Processor`
   (`internal/processor/processor.go:22`) знает `Name`, `Title`, `Kind`,
   `Params`, `TableParts`, `Forms` — про сущности не знает ничего. Зато этот же
   тип разбирает обе стороны: и `processors/<имя>.yaml` конфигурации, и единый
   YAML внешней обработки (`extform.ParseProcessorContent`,
   `internal/extform/bundle_processor.go:87`). Одно поле закрывает оба контура.
2. **Реестр не умеет отвечать «что относится к сущности X».** Для печатных форм
   такой срез есть — `Registry.GetAllPrintForms(entityName)`
   (`internal/runtime/registry.go:553`) сводит конфигурационные, DSL- и внешние
   формы в один список ссылок. Для обработок среза нет, есть только плоские
   `Processors()`/`GetProcessor(name)`.
3. **Форма объекта ничего, кроме печати, не предлагает.**
   `handlers_entity.go:1308` кладёт в шаблон `PrintForms`, `DSLPrintForms`,
   `AllPrintForms` — и всё.
4. **Транспорт «выполнить над текущим объектом» уже готов, и это главное.**
   `handleManagedFormEvent` (`internal/ui/handlers_managed_events.go:73`)
   собирает **несохранённые** данные формы в `runtime.Object`, обогащает
   ссылочные реквизиты и табличные части и отдаёт коду как `Объект`/`ЭтотОбъект`
   (`:324-336`) через `formObjectThis` (`internal/ui/dsl_form_object.go:35`),
   который умеет и `Объект.Товары.Добавить()`, и `Объект.Записать()` в живой
   транзакции. То есть «заполнение ещё не записанного объекта» — не мечта, а
   существующий путь: не хватает лишь маршрутизации «код берём не из
   `<форма>.form.os`, а из обработки».
5. **Контракт внешней обработки жёстко требует `Выполнить()`** —
   `ParseProcessorContent` (`bundle_processor.go:87`) отвергает файл без неё.
   Обработке, которая осмысленна только над объектом, эта процедура не нужна и
   будет написана заглушкой — а заглушка попадёт в общий список обработок.
6. **Права и доверие уже сведены в две точки** — `requirePerm(... "processor",
   proc.Name, "run")` внутри `getProcessor`
   (`internal/ui/handlers_processors.go:311`) и `canRunExternalProc`
   (`internal/ui/extprocessors.go:201`). Новая точка входа обязана звать **обе**,
   иначе кнопка в форме превращается в обход модели доверия: недоверенная
   внешняя обработка исполняет произвольный код с правами интерпретатора.
   Образец такого теста уже есть — `internal/ui/processor_formevent_security_test.go`.

## Синтаксис

Блок `binding:` в YAML обработки — одинаковый для конфигурации и внешнего
контура (парсер общий):

```yaml
name: ЗаполнитьПоДоговору
title: Заполнить по договору
binding:
  objects: [РеализацияТоваров, ЗаказПокупателя]  # к чему цепляем
  placement: form                                 # form | list | form+list
  title: Заполнить по договору                    # подпись кнопки; по умолчанию title обработки
  requires_saved: false                           # true — кнопка неактивна на незаписанном объекте
```

Контракт кода — отдельная процедура, объект приходит первым аргументом:

```
Процедура ВыполнитьДляОбъекта(Объект)
    Договор = Объект.Договор;
    Если Не ЗначениеЗаполнено(Договор) Тогда
        Сообщить("Договор не заполнен");
        Возврат;
    КонецЕсли;
    Объект.Комментарий = "Условия по договору " + Договор.Номер;
    // Объект.Записать() — по желанию обработки; без него правки останутся
    // в открытой форме и уедут в базу обычной записью пользователя
КонецПроцедуры
```

`Объект` — то же самое, что в обработчике управляемой формы: с табличными
частями, разыменованием ссылок и `Записать()`. Английский псевдоним
`ExecuteForObject` поддерживается так же, как `Execute` рядом с `Выполнить`
(`hasProc`, `bundle_processor.go:112`).

Правила совместимости:

- `binding:` нет → всё как сейчас: обработка в общем списке, нужна `Выполнить()`.
- `binding:` есть → обязательна `ВыполнитьДляОбъекта`, а `Выполнить()`
  становится необязательной; без неё обработка **не показывается** в общем
  списке — она принадлежит объекту, а не разделу «Обработки».
- Есть обе процедуры → обработка и в списке, и на форме объекта.

## Хранилище / SQL

Новых таблиц и миграций нет. `binding:` едет внутри `content` — того самого
YAML, который уже лежит в `_ext_processors.content` и в
`processors/<имя>.yaml`. Записи, загруженные до плана, работают без изменений:
нет блока — нет привязки. В универсальный бэкап `_ext_processors` уже входит
(`internal/backup/universal.go:109`).

## Изменения в коде

**A. Метаданные и валидация (`internal/processor`, `internal/extform`)**

- `processor.Binding{Objects []string; Placement string; Title string; Titles map[string]string; RequiresSaved bool}`, поле `Binding *Binding` в `Processor`.
- `Binding.AppliesTo(entityName string) bool`, `Binding.OnForm()/OnList()` — разбор `placement` в одном месте, а не по шаблонам.
- `ParseProcessorContent`: при `binding:` требовать `ВыполнитьДляОбъекта`, иначе — прежнее требование `Выполнить()`. Ошибки — текстом, который увидит администратор в форме загрузки.
- `ParseProcessorUpload`: отказ, если `binding.objects` пуст или называет неизвестную реестру сущность («обработка привязана к `РеализацияТоваро`, такой сущности в конфигурации нет» — опечатка ловится при загрузке, а не молчанием кнопки).

**B. Реестр (`internal/runtime/registry.go`)**

- `Registry.ObjectProcessors(entityName string) []ProcessorRef` по образцу `GetAllPrintForms` (`:553`): сводит конфигурационные и внешние, сортирует по имени, отдаёт `External`/`Trusted` вызывающему — решение о показе принимает UI, реестр политикой не занимается.
- `Processors()` фильтрует обработки, у которых есть `binding:` и нет `Выполнить()`.
- Коллизия имени решается как сейчас: приоритет у конфигурации + warning (`:1003-1007`).

**C. Точка входа и исполнение (`internal/ui`)**

- Маршрут `POST /ui/{kind}/{entity}/object-processor/{name}` рядом с `form-event` (`server.go:382`).
- Хендлер переиспользует сборку объекта из `handleManagedFormEvent`: кусок от `buildObjectFromForm` (`:261`) до подстановки `Объект`/`ЭтотОбъект` (`:335`) выделяется в общий хелпер, чтобы обе точки входа строили `Объект` **одинаково**; расхождение здесь = ещё одна реализация записи, ровно то, чем занят план 132.
- Порядок проверок в хендлере: `requirePerm(processor/<Имя>/run)` → `canRunExternalProc` → `binding.AppliesTo(entity)` (иначе привязка к другому объекту становится универсальным запуском) → `requires_saved`.
- Исполнение — `CallSandboxed` с `processorSandboxTimeout`, как в `handlers_processors.go:227`.
- Аудит: `auditExtProcRun` (`extprocessors.go:209`) получает объект — `EntityKind`/`EntityName`/`RecordID` вместо одного имени обработки. Сейчас в журнале видно «запустил обработку», но не «над чем».

**D. Интерфейс**

- D1. Управляемая форма: кнопки привязанных обработок в командной панели рядом с `kind: Кнопка` (`templates_managed.go:228`), отправляют форму на новый маршрут и перерисовывают её ответом — тем же способом, что и обработчик команды.
- D2. Автогенерированная форма: кнопка рядом с меню печати (`handlers_entity.go:1308`), только над записанным объектом.
- D3. Список: команда над выделенной строкой. Делать **после** D1/D2 и только если найдётся сценарий, где строка списка достаточна: пакетный запуск по многим строкам — это очередь заданий (план 130), а не кнопка.

**E. Проверка конфигурации (`internal/configcheck`)**

- `binding.objects` против метаданных; наличие `ВыполнитьДляОбъекта` в `src/<имя>.proc.os`; неизвестный `placement`. Для конфигурационных обработок это ловит `onebase check`, для внешних — валидация при загрузке (пункт A): контуры разные, правило одно.

**F. Документация**

- `docs/features.md` — дополнить секцию «Внешние обработки, отчёты и печатные формы» (сейчас в ней прямо написано, что привязки нет).
- `AGENTS.md` через `onebase ai-guide` — блок про `binding:` и контракт процедуры.
- Пример в `examples/trade`: обработка, привязанная к `Реализация`.

## Тесты

1. `internal/processor`: разбор `binding:`, дефолты (`placement: form`), `AppliesTo` без учёта регистра.
2. `internal/extform`: отказ при `binding:` без `ВыполнитьДляОбъекта`; отказ при неизвестной сущности; загрузка бандла с `binding:` и обратный экспорт (round-trip не теряет блок).
3. `internal/runtime`: `ObjectProcessors` сводит оба контура; выключенная внешняя не попадает; обработка с `binding:` и без `Выполнить()` исчезает из `Processors()`.
4. `internal/ui` — **публичным путём**, HTTP-запросом, а не вызовом приватной функции (CLAUDE.md, issue #611):
   - GET формы документа под админом содержит кнопку; под пользователем без права `processor/<Имя>/run` — не содержит;
   - POST нового маршрута под не-админом для **недоверенной** внешней обработки → 403 (образец: `processor_formevent_security_test.go`);
   - POST для обработки, привязанной к другой сущности → 403;
   - `requires_saved: true` на незаписанном объекте → отказ с внятным текстом;
   - успешный запуск: правки, сделанные обработкой в `Объект`, видны в ответе формы; при `Объект.Записать()` — в базе;
   - в журнале аудита запись `extprocessor.run` содержит сущность и идентификатор объекта.
5. `internal/configcheck`: неизвестная сущность в `binding.objects` и отсутствие процедуры — ошибки `onebase check`.
6. i18n: новые строки шаблонов — в `internal/i18n/locales/en.json` (гейт `i18ncheck` в джобе `build`).

## Verification

1. `onebase run --project examples/trade --sqlite trade.db`.
2. Загрузить внешнюю обработку с `binding: {objects: [Реализация], placement: form}` через «Расширения и оборудование» → «Внешние обработки».
3. Открыть любую Реализацию — на форме кнопка «Заполнить по договору». Нажать: комментарий заполнился **без перезагрузки страницы**, объект не записан.
4. Записать документ, убедиться, что правка сохранилась.
5. Создать новую Реализацию, не записывая — кнопка работает (это и есть отличие от «сначала запишите»).
6. Зайти обычным пользователем: кнопки нет (обработка недоверенная). Пометить «Доверенная» — кнопка появилась. Снять право `processor/<Имя>/run` у роли — кнопка снова исчезла, а прямой POST на маршрут отвечает 403.
7. Журнал аудита: `extprocessor.run` с именем документа и его идентификатором.

## Что не делаем и почему

- **Виды подключения БСП** (`ЗаполнениеОбъекта`, `СозданиеСвязанныхОбъектов`,
  `ПечатнаяФорма`, `Отчёт`) — не переносим. `ПечатнаяФорма` в контуре уже есть
  отдельным видом артефакта с полем `document:`; остальные три в нашем движке
  различаются только подписью кнопки, а не поведением — значит, это не вид, а
  название. Заводить перечисление ради совместимости словаря — плодить
  сущности, которые ничего не решают.
- **Пакетный запуск по выделенным строкам** — очередь заданий (план 130).
  Обработка, запущенная по 5000 строк из браузера, упрётся в тайм-аут
  песочницы, и правильный ответ здесь — фоновое задание, а не увеличение
  тайм-аута.
- **Автоматический запуск по событию объекта** (аналог подписок на события
  внешней обработкой) — это исполнение стороннего кода внутри транзакции записи;
  тема отдельная и опасная (см. план 108 про побочные эффекты в хуках), и
  начинать её кнопкой в форме неправильно.
- **Привязка внешних отчётов к объекту** («отчёт по этому контрагенту») — та же
  механика, но отчёт не меняет данные и не требует модели доверия; если
  понадобится, добавится тем же блоком `binding:` в YAML отчёта после обкатки на
  обработках.
