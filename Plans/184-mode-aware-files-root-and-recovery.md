# Этап 184 — файловый root по фактической операции и безопасное открытие recovery

## Контекст и принятое решение

Ведущая заявка: [#1523](https://github.com/ivanarama/onebase/issues/1523).
Ведомая: [#1525](https://github.com/ivanarama/onebase/issues/1525), уже на `hold`
с `Blocked-by: #1523`; отдельная реализация для неё не нужна. Основание —
вариант 1 канонического [триажа #1523](https://github.com/ivanarama/onebase/issues/1523#issuecomment-5680956382),
рекомендованный и одобренный без другого `decision:N`: сначала общий план
контракта открытия, режимов и recovery, потом продуктовые срезы.

Это продолжение [плана 166](166-durable-files-and-clean-restore-rollback.md),
который сознательно оставил слишком раннюю проверку home отдельной задачей.
Осмотр выполнен по `main` **b752bfd83c4f1935d6bbff10a99d45d14365f0b8**.
Слияние этого документа не закрывает заявки и не означает реализации.

Сейчас `storage.ConnectWithPool` и `ConnectWithSchema` вызывают
`defaultFilesDirForConfig` до открытия PostgreSQL. Отсутствующий home блокирует
даже SQL-операции и хранение блобов в БД/S3. В
`cli.openExclusiveRecoveryStorage` известный `filesDir` передаётся через
`SetFilesDir` только после `Connect`, то есть слишком поздно.

**Решение:** общий API открытия принимает явный постоянный каталог до создания
handle; неявный каталог проверяется лениво перед операцией, которой нужен disk.
Режим читается из `_settings` после соединения, с различением отсутствия значения
и ошибки чтения. Проверять только режим при открытии недостаточно: существующие
объекты могут иметь другой `loc`, а режим разрешено менять без рестарта.

Два ограничения текущего продукта определяют объём:

- `db` относится к `_blobs.data`; `UploadAttachment` при `db` всё ещё пишет на
  диск. План не добавляет вложения в БД и не обещает их работу без disk root.
- S3 скачивается не только потоком: `MaterializeAttachment` и обычный
  `OpenAttachment` создают копию под `filesDir/_attach_tmp`. Эту временную
  копию надо отделить от постоянного хранилища, иначе S3 без home работает
  лишь при части способов чтения.

## Наблюдаемая семантика и инварианты

| Операция | Нужен постоянный root | Поведение без home и override |
|---|---|---|
| Открыть PostgreSQL, выполнить SQL, прочитать настройки | Нет | Соединение работает; ошибки БД остаются ошибками БД |
| Создать/прочитать/удалить блоб `loc=db` | Нет | Только БД, без пробного удаления файла на диске |
| Создать/прочитать/удалить объект `loc=s3` | Нет | Нужен настроенный S3-клиент; нет fallback на disk |
| Материализовать S3-вложение в путь или читать без streaming | Нет | Нужен доступный временный каталог; копия удаляется по lifecycle |
| Создать disk-блоб или вложение при режиме `disk`/`db` | Да | Ошибка до создания файла и записи метаданных |
| Прочитать/удалить старый объект `loc=disk` при текущем `db`/`s3` | Да | Ошибка до удаления метаданных; смена режима не переносит объект |
| `DemoReset` / импорт с заменой дерева вложений / recovery этого дерева | Да | Явный проверенный target либо ошибка до destructive-фазы |

1. Постоянные файлы никогда не выбирают `os.TempDir`, текущий каталог или
   `filepath.Join("", ...)` в качестве неявного root. Пустой путь не означает
   «файлов нет» и не разрешает исключить destination из recovery allowlist.
2. Приоритет PostgreSQL root: `ConnectOptions.FilesDir` → непустой
   `ONEBASE_FILES_DIR` → прежний `<home>/.onebase/files/<database>`.
   API/env задают **точный абсолютный root**, а не родительский каталог.
   Синтаксически неправильный явный путь отвергается при открытии, даже если
   текущая операция не использует disk; это ошибка явной конфигурации.
3. Отсутствующий/непригодный home без override больше не является ошибкой
   самого `Connect`. Он становится объяснимой ошибкой первого запроса disk root.
   Не создавать объявленный, но отсутствующий home автоматически. Проверять
   существующий root/предков и права до полезной записи; ошибка ОС всё равно
   остаётся возможной между проверкой и I/O и должна возвращаться вызывающему.
4. Выбор backend новой записи берётся один раз на операцию из актуальной БД.
   Старые записи читаются/удаляются по сохранённому `loc`; legacy `loc` разбирается
   по существующей совместимости, неизвестный `loc` не разрешает запись на disk.
5. Отсутствующий ключ или ещё не созданная `_settings` дают исторический `disk`.
   Permission denied, timeout, cancellation, network error и повреждённое
   значение — ошибка, а не разрешение использовать disk. В транзакции PostgreSQL
   нельзя ловить `undefined_table` и продолжать в aborted transaction: наличие
   таблицы проверять безопасной интроспекцией текущей схемы до чтения.
6. Ошибка root/режима не меняет `_blobs`, `_attachments`, `loc`, настройку режима
   или restore intent. Для удаления disk-объекта root проверяется до DELETE;
   root и backend захватываются вместе с cleanup callback. Сохранить имеющиеся
   правила commit/rollback и компенсаций внешнего хранилища.
7. Recovery сохраняет существующие exclusive lifetime leases, повторную проверку
   pending marker, schema revision barrier и точное сопоставление destinations.
   Каталог из недоверенного содержимого архива/журнала не становится разрешённым
   только потому, что он там назван. Известный target передаёт владелец операции.
8. Отсутствие S3-клиента при выбранном `s3` — ошибка операции до внешних записей.
   Один факт наличия `file_storage.s3` в YAML не меняет `_settings.ui.file_storage`.

## Синтаксис / YAML и API открытия

Новых YAML-ключей и пользовательских режимов нет. Сохраняются
`file_storage.s3`, CLI/UI настройки `ui.file_storage` и `ONEBASE_FILES_DIR`.
Пример установки с disk-файлами: `ONEBASE_FILES_DIR=/srv/onebase/app-files`.
Пример установки без home: режим `db` допускает блобы в БД, но загрузка обычного
вложения требует этот override; `s3` допускает оба типа объектов без disk root.

Предлагаемый внутренний Go-контракт (имена уточнять только без изменения смысла):

```go
type ConnectOptions struct {
    Pool     PoolConfig
    Schema   string // прежний контракт search_path: schema,public
    FilesDir string // пустой = env/home; явный абсолютный target для recovery
}
func ConnectWithOptions(ctx context.Context, dsn string, opts ConnectOptions) (*DB, error)
func (db *DB) RequireFilesDir() (string, error)
func (db *DB) ReadFileStorageMode(ctx context.Context) (string, error)
```

`Connect`, `ConnectWithPool`, `ConnectWithSchema` становятся обёртками общего
открытия. Сохранить pool precedence, `search_path`, ping и существующую настройку
каста UUID; не унифицировать попутно разные исторические настройки размера пула
schema-open. Перед открытием сохранить источник пути (явный/env/home), чтобы
изменение окружения позже не переместило данные текущего handle. Системную
проверку пригодности неявного home и каталога делать при `RequireFilesDir`.
Доступ к кэшу пути синхронизировать; не публиковать частично разрешённый путь.
Ошибку доступности можно перепроверить при повторе по тому же сохранённому пути.

Не добавлять `Mode` в `ConnectOptions`: для обычной базы authoritative-значение
лежит в `_settings`, а recovery может заменить сами настройки. Переданный
вызывающим кодом режим создал бы вторую расходящуюся истину. Recovery передаёт
именно root и явно требует его до файловых действий.

Безошибочный `FilesDir() string` удалить из внутренних производственных путей:
заменить вызовы на `RequireFilesDir`, обработав ошибку. `SetFilesDir` заменить
инициализацией через options; для SQLite/тестовых fixture допустим отдельный
проверяемый initializer **до публикации handle**, возвращающий ошибку. Не
оставлять возможность hot-switch root, особенно при живых cleanup callbacks.
Это внутренний API; обновить всех вызывающих в том же срезе. SQLite сохраняет
свою историческую раскладку, включая специально временные in-memory fixture;
правило PostgreSQL об отсутствии temp-fallback на них не распространяется.

`ReadFileStorageMode` используется в storage I/O и управляющих настройкой путях.
Старый `GetFileStorageMode` нельзя использовать как разрешение на disk. Если он
временно остаётся для отображения, явно ограничить эту роль и показывать ошибку
там, где ранее UI изображал успешное чтение настройки. `SaveFileStorageMode`
для выбора `disk` проверяет root до изменения настройки; выбор `db` root не
требует, но не обещает дисковым вложениям новый backend. Требования к S3-клиенту
не ослабляются. SQL-ошибки чтения не маскируются нормализацией неизвестных значений.

## Временные копии S3

Для S3 staging/materialization использовать отдельный приватный случайный
каталог процесса/handle под системным temp, создаваемый только по необходимости.
Это воспроизводимые копии; ни `loc=disk`, ни restore destination на них не
указывают. Staging upload уже использует `os.CreateTemp`; свести ownership и
удаление с новым механизмом, не менять лимиты и проверку размера.

`OpenAttachment` владеет копией до `Close`, `MaterializeAttachment` возвращает
идемпотентный cleanup с прежним контрактом; cancellation и ошибка загрузки
удаляют только собственную копию. Закрытие DB удаляет принадлежащий handle
каталог после завершения его потребителей. Не выполнять широкую зачистку
другого процесса и не вызывать `RemoveAll("_attach_tmp")` при пустом root.

Убрать зависимость `applyFileStorageS3 → SweepAttachmentTemp` от durable root.
Старый общий `_attach_tmp` не переносится: он не содержит первичных данных.
Оставшиеся после аварийного завершения процесса копии могут потребовать системной
очистки temp; межпроцессный сборщик с распознаванием живых владельцев — вне плана.
Документировать это ограничение, а не объявлять `DB.Close` гарантией при crash.

Перед реализацией каждого среза повторить инвентаризацию `filesDir`, `FilesDir`,

все найденные места без разбора: доказать для каждого, что он либо требует
постоянный root, либо не использует файловую систему. В частности, нельзя просто
удалить два вызова resolver и оставить относительные пути в `blobs/attachments`.

## Хранилище / SQL, совместимость и миграция

DDL, `_settings` key, значения `loc`, пути существующих файлов, формат `.obz`
и schema revision не меняются. Нет массового переноса содержимого между disk,
DB и S3. Смешанная база после переключений остаётся допустимой: читать старые
объекты по loc, а новый режим влияет только на новые записи.

Существующий home и абсолютный override сохраняют прежние пути. Оператор без
home теперь может открыть SQL/db/S3-инсталляцию; первая настоящая disk-операция
возвращает ошибку с именем `ONEBASE_FILES_DIR`, без DSN/паролей. Это явное изменение
момента отказа относительно плана 166, требующее release note. Не обещать
успешный `DemoReset` без root только потому, что текущий режим `db`: он заменяет
дерево вложений и может восстановить старые disk-объекты.

Full export/import и DemoReset сохраняют действующие ограничения, включая
отказ при неподдерживаемых S3-ссылках в universal backup. Поддержка S3-бэкапа
или backup без файлового destination не входит в задачу. Операции с деревом
файлов требуют root до начала своей изменяющей фазы; их отказ не блокирует
обычный старт S3/db-сервера, если операция не запрошена.

## Последовательность небольших PR-срезов и публичные тесты

Каждый срез — отдельный PR с проверкой по актуальному main. #1523 остаётся
ведущей до завершающего среза; #1525 не запускать отдельным FIX. Продолжение
передавать через поддерживаемый конвейером handoff/явную маршрутизацию, а не
закрывать ведущую issue после промежуточного результата.

### A. Проверяемый root и чтение режима (~2–3 дня)

Ввести `RequireFilesDir` и `ReadFileStorageMode`, перевести disk I/O и изменения
режима на error-aware пути. Пока сохранить прежнюю eager-проверку в Connect:
новое поведение открытия включается только после защиты всех потребителей.
Убрать пробное disk-удаление db-блоба. Проверять root до удаления метаданных,
не менять порядок компенсаций и транзакционную семантику в несвязанных местах.

Публичные регрессии через `PutBlob`, `OpenBlob`, `DeleteBlob`,
`UploadAttachment`, `OpenAttachment`, `DeleteAttachment`, `SaveFileStorageMode`:

- disk/db/s3 и смешанные старые loc; переключение режима не меняет старые файлы;
- отказ root оставляет строки/данные и sentinel в рабочем/temp каталоге нетронутыми;
- permission denied/отмена при чтении `_settings` не создают disk-файл;
- новая пустая БД без `_settings` корректно выбирает disk, транзакция PG остаётся
  работоспособной; изолированная схема не наследует режим из `public`;
- commit/rollback вложенной транзакции сохраняет прежние гарантии внешних файлов.

SQL-семантику проверять единым `dbtest.ForEachDialect` на SQLite и PostgreSQL,
ошибки PostgreSQL permissions дополнительно через ограниченную тестовую роль.
Тесты не ограничивать вызовом нового приватного resolver.

### B. S3 без постоянного root для временных копий (~1–2 дня)

Перенести materialization/staging в собственное временное пространство, убрать
зависимость startup sweep от root. До среза C Connect ещё требует старую
конфигурацию, поэтому этот PR не объявляет всю #1523 исправленной.

Публичные тесты `UploadAttachment → OpenAttachment/MaterializeAttachment` и
существующий CLI-тест подключения S3: fake S3 с тем же интерфейсом, streaming
on/off, равенство байтов, cancellation, обрыв/неверный размер, cleanup при Close
и ошибке. Два handle/читателя не удаляют копии друг друга; файлы в durable root
и cwd не меняются. В тесте отсутствие использования durable root доказывается
наблюдением I/O/каталогов, а не одним вызовом helper временного пути.

### C. Общее открытие, recovery и итоговая приёмка (~3–4 дня)

Добавить options и передать известный recovery root до Connect; включить lazy
неявный root в трёх PG entry points. В том же PR убрать безошибочные getters и
post-open setters из производственных путей, обработать все backup/recovery
потребители. Сохранить SQLite layout, lease и schema revision gates. Обновить
тест старого `TestConnectPostgresMissingHomeFailsClosedBeforeDial`: ожидание
отказа до dial больше не соответствует принятому контракту.

Публичная матрица на реальном PostgreSQL, с отдельной тестовой базой/схемой:

- `Connect`, `ConnectWithPool`, `ConnectWithSchema` без home: SQL работает;
  db-блоб и S3 roundtrip работают, disk upload отказывает без побочных записей;
- отсутствие home + явный options root работает для disk/recovery; options
  побеждает env, env побеждает home; relative override отвергается; обычный home
  сохраняет старую раскладку и чтение созданных до обновления объектов;
- CLI `run`/`procrun` с применением реального app-конфига и fake S3 endpoint
  подтверждают wiring, а не только прямой `SetBlobStore` в storage-тесте;
- scheduled DemoReset и launcher restore HTTP-вход без home используют pinned
  root; успешный restore и crash/recovery возвращают согласованную пару БД/файлов;
- нет допустимого root: никаких DELETE, swap, удаления intent или расширения
  allowlist; известная future schema и отсутствие exclusive lease по-прежнему
  запрещают recovery; ошибка закрывает pool и освобождает принадлежащую lease;
- backup c существующими disk-loc не пропускает отсутствующие файлы после смены
  режима; S3 export остаётся явно запрещён там, где запрещён сейчас.

Использовать существующие `schema_gate_test.go`, `run_dblock_test.go`,
`dbopen_schema_revision_test.go`, restore и external-integrity suites для
регрессий guards; дополнить end-to-end путь PostgreSQL через публичный CLI/HTTP.
Прямой тест `openExclusiveRecoveryStorage` полезен лишь дополнительно.

## Проверки и Verification

Во время подготовки плана выполнены четыре существующих теста каталога:
`TestConnectPostgresMissingHomeFailsClosedBeforeDial`,
`TestDefaultFilesDirUsesExplicitAbsolutePath`,
`TestDefaultFilesDirKeepsExistingHomeLayout`,
`TestDefaultFilesDirRejectsRelativeOverride` — успешно. Они подтверждают текущий
контракт, но не являются доказательством работы предлагаемого API. Продуктовый
код этим plan-PR не меняется; будущая матрица PostgreSQL ещё не выполнена.

Для каждого продуктового PR: `go build ./...`, тесты затронутых пакетов, для
storage SQL — dialect matrix с непустым `TEST_DATABASE_URL`; для финального
среза также `go test ./...`, `-race` затронутых storage/temp тестов и соответствующие
PostgreSQL integration suites. Пропуск PG из-за отсутствия сервера не считается
прохождением PG-приёмки. Изменения примера конфигурации проверять `onebase check`.

Ручная приёмка на временной тестовой инсталляции PostgreSQL:

1. Подготовить базу/роли и `db` либо `s3`-режим при доступном home. Затем запустить
   отдельный процесс с недоступным home и без `ONEBASE_FILES_DIR`.
2. Выполнить SQL и roundtrip блоба в обоих режимах; в S3 загрузить/скачать вложение
   с streaming on/off и материализовать его через штатный DSL-путь. Сверить байты.
3. При `db` загрузить обычное вложение: получить понятный отказ, ноль новой строки
   и ноль файлов в cwd/temp как постоянном хранилище.
4. Остановить процесс, назначить постоянный абсолютный root, повторить disk upload,
   перезапустить и проверить чтение. Сменить режим и прочитать старый disk-объект.
5. Через штатный recovery/restore путь восстановить тестовый snapshot с известным
   target при отсутствии home. Повторить с ошибкой и прерыванием процесса;
   проверить sentinel, intent, целостность БД и запрет операции без lease/root.
6. Удалить только созданную тестовую базу и её каталоги. Не использовать рабочую БД.

## Риски, откат и критерии завершения

Главный риск — пропущенный raw `filesDir`/getter, превращающий пустой путь в cwd.
Срез C не включать до полного перевода disk-потребителей и проверок sentinel.
Другие риски: чтение настроек из `public` вместо текущей схемы, подавленный сбой
SQL, удаление metadata до проверки root, гонка смены root с cleanup и расширение
recovery allowlist. Для каждого выше указан наблюдаемый отрицательный тест.

Откат кодовый, без миграции БД/loc. При откате C старый бинарь снова потребует
home/override даже для db/S3: заранее задать постоянный root либо вернуть
доступный home. Откатывать срезы в обратном порядке; временные S3-копии можно
удалить после остановки процессов, первичные disk-файлы не перемещать и не
удалять. Структуры restore intent не меняются, старые barriers сохраняются.

Готово, когда все три PG entry points и реальные CLI/launcher-пути удовлетворяют
матрице; ни один production disk I/O не использует непроверенный путь; db/S3
без home работают в заявленных границах; recovery сохраняет прежние гарантии;
документация явно различает db-блобы, disk-вложения и временные S3-копии.
Последний продуктовый PR закрывает #1523 и #1525 вместе после полной приёмки.

## Эстимейт

A: 2–3 дня; B: 1–2 дня; C с интеграционной приёмкой и документацией: 3–4 дня.
Итого **6–9 рабочих дней**. Изменение формата backup, новый backend вложений,
автоматическая миграция файлов и глобальный temp-GC в оценку не входят.
