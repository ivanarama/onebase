# План 175 — поиск владельца по полям табличных частей

Дата проектирования: 2026-09-11.
Статус: 📋 **проектирование**, продуктовый код в этом PR не меняется.
Заявка: [#1372](https://github.com/ivanarama/onebase/issues/1372).
Выбранный вариант: **1** — закрепить единый контракт путей в `search_fields` и
`fulltext`, затем реализовать поиск списка и полнотекстовый поиск отдельными
проверяемыми срезами.

План продолжает реализованные планы
[23](23-search-filters.md) и [82](82-fulltext-search.md). Первый добавил
подстрочный поиск по реквизитам шапки, второй — одну полнотекстовую строку
`_fts` на владельца и намеренно оставил табличные части за границей объёма.

## Контекст

Телефоны, Email и другие повторяющиеся контакты естественно хранить строками
табличной части справочника. Сейчас оба штатных поиска видят только шапку:

- `metadata.SearchFields` и `metadata.FullTextFields` возвращают плоский
  `metadata.Field` из `Entity.Fields`;
- `storage.List` и `storage.Count` независимо строят `LIKE` только по колонкам
  таблицы владельца;
- `storage.IndexObject` получает карту полей шапки из `Upsert`, а
  `rebuildEntityFTS` читает только таблицу владельца;
- `UpsertTablePartRows` заменяет дочерние строки после шапочного FTS-upsert и
  не обновляет `_fts`.

Поэтому контакт в ТЧ нельзя найти ни в строке списка/подборе ссылки, ни в
глобальном UI, REST v2 и DSL. Денормализовать контакты в поле шапки можно, но
это создаёт вторую копию данных и отдельный протокол синхронизации.

## Объём и синтаксис

Оба существующих YAML-ключа принимают прежнее имя реквизита шапки либо путь
ровно из двух сегментов `ТабличнаяЧасть.Поле`:

```yaml
name: Клиенты
search_fields:
  - Наименование
  - Контакты.Значение
fulltext:
  - Наименование
  - Контакты.Значение

fields:
  - name: Наименование
    type: string

tableparts:
  - name: Контакты
    fields:
      - name: Вид
        type: string
      - name: Значение
        type: string
```

Контракт пути:

1. Имена сущности, ТЧ и поля регистронезависимы, как остальные метаданные;
   диагностический и сохранённый канонический путь использует объявленный
   регистр `Контакты.Значение`.
2. Допустима ровно одна точка. Пустой сегмент, `ТЧ.Поле.Подполе`, служебные
   `parent_id`/`строка` и имя несуществующей ТЧ или колонки дают ошибку
   `onebase check`, а не молча исключаются из поиска.
3. Для `search_fields` явный путь ТЧ повторяет правило явного поля шапки:
   допустим любой нессылочный тип, который диалект приводит к тексту;
   `reference:*` отклоняется, потому что в колонке лежит UUID.
4. Для `fulltext` допустимы только `string` и `richtext`; ссылки и enum
   отклоняются, как сейчас для шапки.
5. Дубликат одного канонического пути без учёта регистра — ошибка. Поля с
   одинаковым именем в разных ТЧ не являются дублями.
6. Отсутствующий ключ сохраняет прежнее умолчание — только строковые поля
   шапки. ТЧ никогда не включаются автоматически: у существующей конфигурации
   не меняются ни результаты, ни стоимость запросов. Явный `[]` по-прежнему
   выключает соответствующий поиск.
7. Путь не разыменовывает ссылку и не ищет по представлению связанного объекта.
   Это отдельная семантика с другим жизненным циклом индекса.

## Наблюдаемая семантика и инварианты

### Поиск списка и подбор ссылки

- Совпадение хотя бы в одном указанном поле шапки или ТЧ возвращает владельца.
- Один владелец присутствует в выдаче ровно один раз, даже если совпали
  несколько строк или колонок ТЧ. Для этого SQL использует коррелированный
  `EXISTS`, а не `JOIN` внешней выборки.
- `List` и `Count` используют один построитель поискового предиката и одинаковые
  аргументы. Пагинация не может показывать строку, которой нет в счётчике.
- Условия по полям одной ТЧ группируются в один `EXISTS` с `OR`; разные ТЧ — в
  разные `EXISTS`. Каждый placeholder получает собственный pattern, потому что
  SQLite использует позиционные `?`.
- Корреляция идёт по `tp.parent_id = owner.id`. Существующий индекс
  `(parent_id, строка)` остаётся достаточным; обычный индекс текста не ускоряет
  `LIKE '%подстрока%'`, поэтому новая DDL-миграция не вводится.
- Существующие `RowFilter`, strict-RLS checkpoint, сортировка, лимит и cursor
  применяются к владельцу без изменений. Поиск по ТЧ не обходит объектный или
  строковый доступ.

### Полнотекстовый индекс

- Схема не меняется: в `_fts` остаётся одна строка на `(owner_name, owner_id)`.
- `title` строится только из `presentation`/label-полей шапки. Значение ТЧ
  добавляется только в `body`, поэтому найденный по телефону клиент не получает
  телефон вместо устойчивого представления.
- Текст собирается детерминированно: пути в порядке YAML, для каждого пути —
  строки ТЧ по `строка`, затем нормализация и общий лимит `ftsMaxBody`.
  Повторяющиеся значения сохраняются: частота уже влияет на ранжирование FTS,
  и молчаливое схлопывание изменило бы существующий принцип подсчёта веса.
- Полная переиндексация не делает запрос на каждого владельца. Одна страница
  читает шапки, затем по одному запросу на каждую задействованную ТЧ выбирает
  строки всех `parent_id` страницы и агрегирует их в Go. Это сохраняет единый
  алгоритм для SQLite и PostgreSQL без диалектных `string_agg/group_concat`.
- Запись шапки собирает документ из её финальных `effectiveFields` и текущих
  строк ТЧ. Замена индексируемой ТЧ после последнего INSERT пересобирает ту же
  строку `_fts` владельца. Промежуточные пересчёты нескольких ТЧ допустимы
  только внутри общей транзакции и снаружи не видны.
- Замена ТЧ, очистка всех строк, изменение одного значения, удаление владельца,
  откат транзакции и `onebase reindex` не оставляют старого текста в `_fts`.
- Запись дочерних строк и их FTS-пересчёт атомарны и для вызова без внешней
  транзакции: общий writer оборачивает delete/insert/reindex в
  `WithTxIfNeeded`. Ошибка построения или записи FTS откатывает замену ТЧ.
- Прямая загрузка SQL мимо платформы, как и сейчас для полей шапки, требует
  `onebase reindex`.

### Доступ и отсутствие ложной гарантии

`field_access` сейчас адресует только `Entity.Fields`; `pii: true` на поле ТЧ
валидатор отклоняет. Этот план не добавляет маскирование ТЧ и не заявляет, что
оно уже есть. Пользователь, которому разрешено читать строку владельца, имеет
тот же доступ к её ТЧ, что и до поиска. Текущие entity permission, row filter и
проверка результата глобального поиска сохраняются.

Если отдельный план в будущем добавит field-level policy для ТЧ, он обязан
одновременно расширить SQL-гейт поиска списка и `search.visibleMatch`, иначе
индекс станет оракулом скрытого значения. Поля ТЧ с действующей политикой
нельзя просто начать индексировать без такого гейта.

## Модель метаданных и внутренний контракт

В `internal/metadata` нужен типизированный результат разрешения, например
`EntityFieldPath` с каноническим `Path`, `Field` и опциональной ссылкой/именем
`TablePart`. `SearchFieldPaths` и `FullTextFieldPaths` должны быть единственной
точкой разбора dotted path, умолчаний и регистронезависимого разрешения.

`LabelFields` остаётся шапочным: ТЧ не участвует в представлении. Старые
`SearchFields`/`FullTextFields` нельзя оставлять параллельным источником истины.
Их вызовы переводятся на typed paths, а сами функции либо удаляются, либо
остаются узкими header-only адаптерами с именем и тестом, которые не позволяют
случайно потерять пути ТЧ.

Валидация применяет режим механизма после общего синтаксического разрешения:
`search_fields` запрещает ссылки, `fulltext` разрешает только string/richtext.
Это не должно расходиться между `metadata.Validate`, загрузчиком YAML,
`onebase check`, configurator round-trip и описанием схемы для AI.

Для дочерней записи выбран явный typed API вместо скрытого реестра метаданных в
`storage.DB`:

```go
UpsertTablePartRows(
    ctx context.Context,
    entity *metadata.Entity,
    tp metadata.TablePart,
    parentID uuid.UUID,
    rows []map[string]any,
) error
```

Posting prelude/finalize и replicated writer получают ту же пару
`entity + tp`. Приватный SQL-helper может принимать уже разрешённые имена, но
наружу пакета не остаётся метода только с `entityName/tpName`: такой метод не
может узнать остальные fulltext-пути владельца и неизбежно создаёт stale index.

## Инвентаризация затронутых границ

| Граница | Текущее состояние | Планируемое изменение |
|---|---|---|
| `internal/metadata/types.go` | `SearchFields`/`FullTextFields` возвращают поля шапки | typed path resolver с прежними default/empty правилами |
| `internal/metadata/validate.go`, `yaml.go` | плоское имя, pointer отличает key absent от `[]` | строгая проверка двухсегментного пути; wire-формат остаётся `[]string` |
| `internal/configcheck`, `internal/cli/aiguide.go` | схема знает ключи, но не dotted-семантику | публичная диагностика и актуальный AI-guide/describe контракт |
| `internal/launcher/configurator_types.go` | `[]string` уже проходит YAML round-trip | сохранить dotted строки побайтно по смыслу; добавить round-trip тест |
| `internal/storage/crud.go` | `List` и `Count` дублируют header-only `LIKE` | общий builder: header predicates + grouped correlated `EXISTS` |
| `internal/storage/fts.go` | `BuildFTSDoc` и rebuild получают только шапку | разделить header title и body fragments; batch-загрузка ТЧ |
| `internal/storage/crud.go:UpsertTablePartRows` | общий дочерний writer не знает полного `Entity` и не трогает FTS | передать метаданные владельца через typed writer/сигнатуру и атомарно reindex при нужной ТЧ |
| `internal/entityservice/ports.go` и writer-вызовы UI/DSL/exchange | порт принимает имя сущности и отдельную ТЧ | провести typed parent metadata через все вызовы, не оставлять обходного старого writer |
| `internal/search/search.go`, `internal/ui/search.go` | права и masked-header verification поверх `_fts` | сохранить owner/row gates; явно оставить ТЧ вне header masking до отдельного контракта |
| `DEVELOPER.md`, `docs/features.md`, пример | описаны только поля шапки | синтаксис, ограничения, `reindex` и контактная ТЧ в проверяемом примере |

Перед изменением сигнатуры writer нужно инвентаризировать все прямые вызовы
`UpsertTablePartRows`, включая posting prelude/finalize, обмен и тестовые
fixtures. Старый публичный метод удаляется в том же срезе; приватный SQL-helper
не должен стать обходом индекса за пределами `internal/storage`.

## Совместимость и миграция

- SQL-схема сущностей, ТЧ и `_fts`, backup/restore и REST-форматы не меняются.
- Конфигурации без dotted paths работают и индексируются как раньше. Особенно
  важно не включать все строковые ТЧ по умолчанию.
- Новая конфигурация с `search_fields: [Контакты.Значение]` действует сразу.
- После первого добавления/изменения пути ТЧ в `fulltext` оператор выполняет
  `onebase reindex --project <dir> ...`; существующий
  `fts_backfill_done` не является хешем конфигурации и не запускает повторное
  наполнение автоматически. Документация и сообщение configurator/check должны
  не скрывать это требование.
- Старый бинарник не понимает dotted path и fail closed на валидации. Перед
  rollback нужно вернуть прежний YAML, затем старый бинарник; данные ТЧ при этом
  не преобразуются и не теряются.
- `ftsMaxBody` остаётся общим лимитом владельца. Подключение большой ТЧ может
  вытеснить поздние поля из body; порядок и это ограничение документируются,
  автоматическое повышение лимита не входит в план.

## Последовательность небольших PR-срезов

### Срез A — контракт путей и поиск списка (~2 дня)

1. Ввести typed path resolver и строгую валидацию для обоих ключей, но включить
   runtime dotted path сначала только в `search_fields`.
2. Вынести общий SQL-builder из `List`/`Count`, добавить `EXISTS` по ТЧ.
3. Сохранить dotted values через configurator round-trip и описать первый
   пользовательский срез в `DEVELOPER.md`/features.

Публичная приёмка: конфигурация с контактной ТЧ проходит `onebase check`, UI
списка и picker находят владельца по телефону, показывают его один раз и дают
одинаковые list/count на SQLite и PostgreSQL. Невалидный путь отклоняется
`onebase check` с именем сущности и исходным путём.

### Срез B — единая сборка FTS и пакетный reindex (~1.5–2 дня)

1. Отделить выбор title шапки от сборки body fragments.
2. Расширить `rebuildEntityFTS` пакетной загрузкой выбранных колонок ТЧ без N+1.
3. Зафиксировать детерминированный порядок, лимит body и отсутствие дублей
   владельца; dotted `fulltext` ещё не публиковать в пользовательской
   документации, пока инкрементальный путь не атомарен.

Публичная приёмка: `ReindexEntityFullText`/`onebase reindex` на настоящей базе
строит одну строку владельца из шапки и нескольких строк ТЧ, сохраняет label в
title, удаляет старый текст после очистки и выполняет ограниченное число SQL
запросов на batch, а не на каждый объект.

### Срез C — атомарный инкремент и все поверхности поиска (~2–3 дня)

1. Провести полный `Entity` через единственный writer ТЧ и его специальные
   exchange/posting wrappers; удалить или закрыть обходной путь без reindex.
2. Выполнять replace строк ТЧ и пересчёт `_fts` в одной транзакции, включить
   dotted `fulltext` в валидаторе и документации.
3. Проверить UI, `GET /api/v2/search` и `ПолнотекстовыйПоиск`; добавить
   контактную ТЧ в один reference example и инструкцию `onebase reindex`.

Публичная приёмка: запись, правка и очистка контакта через реальную точку записи
объекта немедленно меняет глобальную выдачу; принудительная ошибка/rollback не
публикует ни новые строки ТЧ, ни новый FTS-документ. Результат одинаков на двух
диалектах и во всех трёх публичных входах поиска.

## Тесты и verification

### Автоматические проверки

1. `internal/metadata`: header path, case-insensitive `ТЧ.Поле`, неизвестные и
   трёхсегментные пути, служебные колонки, type/ref/enum ограничения, canonical
   duplicate, отсутствующий ключ против `[]`.
2. `internal/launcher`: сохранение dotted `search_fields`/`fulltext` и отсутствие
   самопроизвольного ключа у старой конфигурации.
3. `internal/storage` через `dbtest.ForEachDialect`: `List` и `Count` по одной и
   нескольким ТЧ, несколько совпавших строк без дубля владельца, numeric explicit
   search, очистка, pagination/row filter и placeholder parity.
4. FTS-матрица: incremental header write, direct typed TP writer, posting
   prelude/finalize, replicated rows, clear, delete, rollback и полный reindex.
   Старое значение после commit нигде не находится, после rollback остаётся
   только старое.
5. Query-count test или инструментированный store доказывает batch-схему
   rebuild: число чтений ТЧ зависит от числа ТЧ и страниц, не владельцев.
6. `internal/ui`/`internal/api`: настоящий HTTP/DSL путь находит клиента по
   контакту и не возвращает владельца, запрещённого object permission или row
   filter; title остаётся представлением шапки.
7. `onebase check` на example подтверждает пользовательский YAML и понятные
   ошибки испорченного пути.

Команды по мере срезов:

```text
go test ./internal/metadata ./internal/configcheck ./internal/launcher -count=1
go test ./internal/storage ./internal/search -count=1
go test ./internal/ui ./internal/api -count=1
go test -tags=integration ./internal/storage ./internal/search ./internal/ui ./internal/api -count=1
go test ./... -count=1
go run ./tools/plannum
```

PostgreSQL-матрица использует `TEST_DATABASE_URL`; локальный skip не заменяет
обязательный `postgres-integration` в CI.

### Ручная проверка

1. Взять справочник с ТЧ `Контакты`, добавить по два телефона двум владельцам и
   один совпадающий Email в нескольких строках первого.
2. Указать dotted path в `search_fields`, выполнить `check`/`migrate`, найти
   обоих владельцев из списка и picker; первый должен появиться один раз.
3. Добавить тот же путь в `fulltext`, выполнить `onebase reindex`, проверить
   глобальный UI, REST и DSL, а также неизменный заголовок владельца.
4. Изменить телефон через форму, затем очистить ТЧ. Новое значение находится
   сразу после commit, старое и очищенное — нет.
5. Повторить запись с намеренно падающим hook: после rollback поиск видит старое
   значение, а строки ТЧ не изменены.
6. Пользователем без read и пользователем, отсекаемым row policy, убедиться, что
   совпадение в ТЧ не раскрывает существование владельца.

## Риски и откат

- **Дубли и сломанная пагинация из-за JOIN.** Предохранитель — только
  коррелированный `EXISTS` и общий builder `List`/`Count`.
- **Устаревший `_fts` после дочерней записи.** Предохранитель — один typed writer,
  обязательный reindex внутри его транзакции и тесты всех специальных wrappers.
- **Частично записанная ТЧ при FTS-ошибке.** `WithTxIfNeeded` охватывает
  delete/insert/index; тест инъекции ошибки сверяет обе таблицы после rollback.
- **N+1 на полной пересборке.** Batch loader и query-count regression; запросы
  группируются по ТЧ и странице владельцев.
- **Рост стоимости list search.** ТЧ включается только явно, `EXISTS` опирается
  на parent index и останавливается на первом совпадении. До включения большого
  массива оператор сравнивает `EXPLAIN`/benchmark с оговорённым бюджетом.
- **Усечение полезного FTS-текста.** Стабильный порядок и прежний 64 KiB лимит
  документированы; телеметрия/отдельные лимиты — follow-up, не скрытое изменение.
- **Будущее маскирование ТЧ превратит поиск в оракул.** План прямо фиксирует
  текущую модель доступа и блокирующее требование расширить оба search-gate при
  появлении field policy для ТЧ.
- **Rollback на старый бинарник.** Сначала убрать dotted paths, затем откатить
  бинарник и выполнить `onebase reindex`. SQL down-migration и преобразование
  пользовательских данных не нужны.

Каждый продуктовый срез откатывается отдельным PR. Если сбой ограничен FTS,
можно временно убрать путь только из `fulltext`, пересобрать индекс и сохранить
работающий `search_fields`; обратная операция также независима.

## Критерии завершения

- один документированный dotted-path контракт используется обоими механизмами,
  а ошибочные пути fail closed в `onebase check`;
- старые конфигурации сохраняют header-only умолчание и прежние результаты;
- list/picker находят владельца через ТЧ без дублей, `List` и `Count` совпадают
  на SQLite и PostgreSQL и не обходят row/object access;
- `_fts` содержит одну актуальную строку владельца, title остаётся шапочным, а
  write/clear/delete/rollback/reindex дочерних строк доказаны тестами;
- полная пересборка загружает ТЧ пакетно без N+1 и сохраняет детерминированный
  порядок при усечении body;
- UI, REST v2 и DSL дают согласованную выдачу по контакту;
- configurator round-trip, `DEVELOPER.md`, features/AI-guide и reference example
  описывают синтаксис, ограничения доступа и обязательный reindex;
- все матричные тесты, `go test ./...`, обязательный CI и `plannum` проходят на
  свежем `main`; продуктовый код не входит в plan-PR.
