# Текущий приоритет развития onebase

Дата ревизии: 2026-07-06.

## Рекомендуемый порядок

1. **План 79 / 76 E-F — runtime-лимиты, backpressure и slow operations.**
   Первый срез плана 76 уже реализован. Следующий шаг — аккуратно закрыть
   тяжёлые отчёты, export, обработки и HTTP-сервисы таймаутами, семафорами,
   slow logs и operation metrics без изменения поведения конфигураций без
   `limits:`.

2. **План 78 — параллельные сессии и изолированные окна Предприятия.**
   Сейчас `CreateSession` удаляет старые сессии пользователя перед созданием
   новой. Это мешает ручной проверке ролей, параллельным окнам одной базы и
   сценарию "два пользователя в одном браузерном профиле".

3. **План 80 — явный batch-доступ к реквизитам ссылок.**
   Скрытое `this.X.Y` не делаем, чтобы не получить неявные запросы в цикле.
   Вместо этого добавляем `ЗначенияРеквизитовОбъектов(Ссылки, "Номенклатура",
   Поля)`: один явный batch-запрос и кэш в прикладном коде.

4. **План 26 — REST API v2.**
   Делать после guardrails из плана 76: v2 должен сразу наследовать RBAC,
   пагинацию, токены, OpenAPI и лимиты. Без этого новый API закрепит старые
   многопользовательские риски.

5. **План 60B — marketplace конфигураций.**
   Версионирование конфигурации в БД и UI истории уже реализованы. `examples/`
   и `templates/` проходят `onebase lint`, так что они готовы быть первыми
   устанавливаемыми конфигурациями.

## Зафиксированные находки аудита

- **План 60A уже не нужно брать.** Ядро `_config_versions`, snapshots, diff,
  rollback, UI истории и export ZIP/OBZ уже есть в коде; впереди только
  marketplace-часть.
- **План 43.2 уже закрыт готовым PR #203.** После merge он должен уйти из
  активного списка.
- **План 76 A-D закрыт свежим merge.** Текущий REST API получил RBAC и caps
  списков, `storage.UpsertVersioned` пишет через conditional update,
  миграция создаёт metadata/tablepart indexes, UI получил server-side
  reference picker.
- **План 34 F3 снят как скрытое разыменование ссылок.** Решение: не делать
  `this.X.Y`/`Стр.X.Y`, чтобы не прятать SQL-запросы в обычном доступе к полю.
  Безопасная замена — план 80.
- **`onebase lint` по поставляемым конфигурациям зелёный.** Проверены все
  `examples/*` и `templates`.
- **Особая находка:** `examples/tasks/src/учёт_времени.posting.os` привязан к
  имени файла с подчёркиванием и использует `this.Задача.Проект`; это хороший
  тест-кейс для нормализации имён posting-файлов и миграции на явный batch-доступ
  из Plan 80.
